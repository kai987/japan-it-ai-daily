### 1. 日本語のFull-duplex音声対話モデルを実際に動かしてみた話

**原文：** https://zenn.dev/knowledgework/articles/12a80d8cd4b21f

**公開日時：** 2026-11-27 11:27:39 JST

Kyutai の Moshi は、音声コーデック Mimi が逐次処理する利用者とモデルの音声を、並行するストリームとして扱います。Temporal Transformer は時間をまたぐ文脈を、Depth Transformer は同じ時点のトークンの関係を担当します。相手を聞きながら声を返せる仕組みが、会話に適切な相槌を保証するわけではありません。

検証に使ったのは、M4 Pro とメモリ48GBを備えた Mac 上の J-Moshi-ext の第三者による MLX 変換版で、重みは量子化していない BF16 です。モデル配布物は約15.8GBで、推論プロセスの使用メモリは観測範囲で最大約25.9GBでした。配布時のファイルサイズだけから、実行に必要な容量を決められない例です。

約一分の雑談を三回試すと発話が自然につながる場面がありましたが、長めに話しかけると相槌が反復しました。長時間の継続対話では三回とも約四分付近で意味を取りにくい発話が続きました。推論サーバーを各試行前に再起動しており、同じセッションを伸ばしたときの変化を見ています。

割り込みは一回の観察で、旧話題を続けた理由を入力の聞き取り失敗と応答の切り替え失敗に分けられていません。発話停止までの時間は測定せず、元モデルと MLX 変換の影響も切り分けていないのが制約です。採用試験なら、同じ音声で割り込み後の停止時間と話題の切り替えを別々に記録したいところです。

**読む価値：** Mimi が支える同時入出力を、相槌の繰り返しや長時間の安定性と分けて評価する視点が得られます。

### 2. 止められないDBをAWS DMSで移行してハマったこと（RDS for Oracle）

**原文：** https://zenn.dev/kiri0728/articles/c8d5f349b047dd

**公開日時：** 2026-11-27 11:37:34 JST

約150GBの RDS for Oracle を別の AWS 環境へ移した事例で、既存行は AWS DMS のフルロードで転送し、その後の更新は CDC で追いかけました。旧 DB に接続した別システムが書き込みを続けるため、初期コピーが終わっただけでは新側のデータを最新にできません。

フルロードが進む一方で CDC が止まった原因は、移行元にサプリメンタルロギングとアーカイブログの保持設定がなかったことです。REDO ログに主キーなどの行を識別する情報を補い、rdsadmin の手順でログを24時間残すと、差分を同期できました。保持にはストレージが必要で、この事例では事前に20GBを増設しています。

接続テストの ORA-12545 は、同じ宛先を IP アドレスで指定すると通ったため、調査対象を名前解決側に絞れました。結局はホスト名のタイプミスでした。疎通の比較は障害を区別するためのもので、IP を本番の固定設定にする提案ではありません。

実作業では DNS を切り替え、停止は約十分でした。切り替え後も旧側で書き込みが続くので CDC を動かし、新側は参照だけに限っています。この条件での運用記録であり、両側が更新する構成や CDC の終了までは確認されていません。

**読む価値：** 切り替え時間の短縮は、Oracle が差分を残す条件と、切り替え後の書き込みの持ち主に依存します。

### 3. OpenSearch Service の新エンジンがサポートした join、高カーディナリティ集計、query DSL を試してみた

**原文：** https://dev.classmethod.jp/articles/opensearch-new-engine-joins-and-dsl/

**公開日時：** 2026-11-27 22:43:52 JST

東京リージョンの OpenSearch 3.9.0 で OPTIMIZED モードを有効にし、or2.medium.search 一台、レプリカゼロで検証しました。ログ百万件や span 約五十一万件など、乱数 seed を固定した合成データを四つのインデックスに入れています。PPL と SQL を別々の宛先に送り、返った数値とクライアントからの往復時間を見ています。

trace_id で ERROR ログと span を結合すると、PPL と SQL は三回とも176,806行と49,905トレースで一致しました。ログ一行に複数の span が付くと、結合結果では行が増えます。span のないログを捨てたくない場合は left join にして未対応の行を数え、このデータでは期待値どおり10,372件でした。

サービスのデプロイ履歴を lookup すると、先頭のエラーログ三件から十九行が返りました。結合キーが一対多なので、バージョン列を増やすだけと思って件数を集計すると、ログ件数と違う値になります。別の集計では百万件のログに対し、432,279種類の user_id を PPL と SQL の両方で確認しています。

既存アプリと同じ query DSL の _search は、フィルター集計とメッセージ検索の二例に HTTP 200 を返しました。加速になるかは要求ごとに OpenSearch が選ぶため、成功応答だけで実行経路は確定できません。単一ノードの合成データ、各三回の往復時間なので、規模を変えた場合の速度は未検証です。

**読む価値：** join 後の行と障害の件数を分け、HTTP の成功と検索の加速を混同しない検証例です。

### 4. CloudWatch エージェントのログ収集パスを変更する手順（SSM パラメータストア + Run Command）

**原文：** https://dev.classmethod.jp/articles/cloudwatch-agent-change-log-path/

**公開日時：** 2026-11-28 00:04:36 JST

対象は、起動時に一度だけ SSM パラメータストアから設定を取得する Windows EC2 です。収集先の file_path をパラメータで編集しても、既に起動した CloudWatch エージェントの設定は変わりません。保存と再取得を別の工程として扱います。

Run Command の AmazonCloudWatch-ManageAgent を configure にして、SSM の対象パラメータを取得し直す手順です。再起動するのはエージェントだけで、EC2 の再起動は不要です。ただし、この間はログとメトリクスの送信が一時的に止まるので、作業前に見るべき監視を決めておきます。

手順の確認では、指定フォルダーの直下に新しいログを出し、対象インスタンスのログストリームに表示されるところまで見ています。ログの到着まで数分かかる場合があり、コマンドの成功だけを到着の証拠にしません。サブフォルダーはこの例の収集範囲外です。

パラメータを CloudFormation で管理している場合は、画面から変えた値がスタックのテンプレートとずれる制約があります。次のスタック更新で戻る可能性があるので、テンプレートの差分も整合させます。反映後の送信状況やローテーションは、サーバーごとの運用条件に合わせて確認します。

**読む価値：** 設定を書いた時点、エージェントに反映した時点、ログが届く時点を区別できます。

### 5. SmartHRの「フロントシステム」の品質保証は、なぜ一言で語れないのか —— むずかしさに向き合う現場の取り組み

**原文：** https://tech.smarthr.jp/entry/2026/11/27/120641

**公開日時：** 2026-11-27 12:06:41 JST

SmartHR が人給基幹でいうフロントシステムは、ブラウザー側実装だけを指さず、従業員の情報を集めて必要な情報を届ける機能群です。入社手続きと招待管理は入力の正確さが重要で、給与明細では従業員がスマートフォンなど多様な環境から見られることも問題になります。機能をまたぐ連携が増えると、一つのチームの見方だけでは不具合を捉えにくくなります。

インシデントや不具合の可視化は進んだものの、利用者や目的が違うため、集計からエリア全体の弱点を導きにくいのが現状です。数を並べるより、誰のどの業務で起き、どの機能の境界で失敗したかを、改善の議論に持ち込める形で残す必要があります。これは著者の問題提起から考えた使い方です。

エリア QAL は EM と PO と方向性を議論し、開発の早い段階でリスクや取り組むべきことを見つけるテスト戦略と、個別の案件で試験を選ぶテスト計画を分けています。例えば詳しい担当者による探索的テストが適する案件もあり、同じ書式や手順を全チームに強制する方針ではありません。

Notion のデータベースにテストケースを集約し、仕様書と不具合なども参照できるようにして、AI で考慮漏れを減らす取り組みを導入しました。工数を減らすのは期待であり、記事は効果を測定した実験ではありません。活動途上の一事例という制約があるので、時間短縮と見落としの減少は、同種の案件を対象に別々に確かめる余地があります。

**読む価値：** 正しい情報を集める入口と給与明細を届ける出口で、異なる品質基準を持つ理由を具体化できます。

## 4. 今日の技術テーマ

### 処理が通ってから、仕事が終わるまで

ログ監視の変更では、SSM に値が残った時点、端末が取り込んだ時点、ログが届く時点が離れています。DB の移行でも全量の完了に加えて、差分がどこまで追いついたかを確認します。両方とも、先に進んでよい条件を、利用側から見える記録に落とす設計です。

音声対話は打ち返せる状態から意図の理解を、検索は HTTP 応答から実際の件数と実行経路を見ます。採用時の検証で、負荷や機器、入力を揃えて比較し、未計測の条件は運用の合意に含めないようにします。

日本の開発現場への応用例として、受け入れの観点を案件の早い段階で決め、利用者の手続きやログの到着を担当チームと一緒に確かめることが考えられます。KPI の実績や他社での普及を示す資料ではないので、導入効果は自社の案件で調べます。

### 1. 苦労（くろう）｜N3

- 品詞：名詞・サ変動詞
- 意味：物事を進めるために心身に負担がかかることです。
- 連語：苦労する / 苦労が続く / 苦労を重ねる
- 記事文脈：品質保証で、機能を越えて共通の方向を見つけにくいという悩みを表しています。
- 例文：対象が違うチームの評価基準をそろえるのに苦労しました。
- 例文の意味：対象が異なるチームの基準をそろえるのが難しかったです。
- ニュアンス：「苦戦」は競争や難局でうまく進めない場面に合い、「苦労」は作業を進めるために負った労力にも使えます。

### 2. 時期（じき）｜N3

- 品詞：名詞
- 意味：物事の起きる、ある程度の幅を持つ時間を指します。
- 連語：時期が異なる / 導入時期を決める / 時期によって変わる
- 記事文脈：組織内で機能群の説明が、時期や立場によって異なることを示しています。
- 例文：同じ指標でも、手続きを見直す時期によって優先度が変わります。
- 例文の意味：手続きを改める時期が違うと、同じ指標でも優先する度合いが変わります。
- ニュアンス：「時点」はある一つの時を示し、「時期」は季節や期間のように幅を持たせられます。

### 3. 軸（じく）｜N1

- 品詞：名詞
- 意味：ここでは複数の判断を支える中心の方針を指します。
- 連語：判断の軸 / 軸をそろえる / 軸が定まる
- 記事文脈：品質の議論が行き詰まったとき、どの観点へ戻るべきかを考えています。
- 例文：複数の部署で迷ったときは、利用者が正しく手続きを終えられるかを判断の軸にします。
- 例文の意味：部署ごとに判断が分かれたら、利用者が手続きを完了できるかを基準にします。
- ニュアンス：「指標」は測定や比較に使う値も指し、「軸」は判断全体のよりどころを示せます。

### 4. 全般（ぜんぱん）｜N2

- 品詞：名詞
- 意味：ある分野を広く含めて述べる語です。
- 連語：技術全般 / 業務全般 / 全般に当てはまる
- 記事文脈：一つの変換版で見られた結果から、全二重モデル全般を判断しないという範囲を示します。
- 例文：一台で出た挙動が音声モデル全般に当てはまるかは、別の環境でも調べます。
- 例文の意味：一台で観察したことをほかの音声モデルにも当てはめられるか、別の環境で確認します。
- ニュアンス：「全体」は一まとまりの全体像にも使い、「全般」は話題の範囲を広げて示します。

## C-2. IT/AI専門用語

1. **Mimi（ミミ）**：ストリーミング音声をトークンとして扱う音声コーデックです。 Moshi の利用者とモデルの二つのストリームを支えます。

2. **Supplemental logging（サプリメンタルロギング）**：更新行を識別できるように REDO ログへ補足情報を記録する構成です。 この移行では主キーの情報を追加し、CDC の適用に使いました。

3. **Left join（左外部結合）**：右側に一致する行がなくても左側の行を残す結合です。 実験では span のないエラーログの件数を出しました。

4. **Configuration drift（構成のドリフト）**：実環境の設定が管理している定義からずれた状態です。 手で変更した SSM の値が CloudFormation の次回更新で戻る可能性があります。

5. **Exploratory testing（探索的テスト）**：試しながら得た知見で以後の観点を調整するテストです。 機能をよく知る人が探索するほうが適する案件もあると紹介しています。
