### 1. 日本語のFull-duplex音声対話モデルを実際に動かしてみた話

**原文：** https://zenn.dev/knowledgework/articles/12a80d8cd4b21f

**发布时间：** 2026-11-27 11:27:39 JST

Moshi 通过流式音频编解码器 Mimi 持续处理声音，同时维护用户与模型的语音流。Temporal Transformer 跟踪随时间推进的对话上下文，Depth Transformer 处理同一时间步内各个 token 的依赖。这个结构让模型能在听用户说话时出声，体验是否自然仍要靠对话样本验证。

作者在配有 48 GB 统一内存的 M4 Pro Mac 上，运行第三方转换的 J-Moshi-ext MLX 版，使用未量化的 BF16 权重。模型下载约 15.8 GB，活动监视器里 Python 推理进程实际观察到的用量最高约 25.9 GB。为应用选设备时，不能把磁盘上的模型体积直接当成推理内存。

简短闲聊中有衔接自然的片段。用户长时间说话时模型有连续重复的应和声，三次长对话都在约四分钟附近出现了难以理解的发言。作者在每轮试验前重启推理服务，长对话的现象来自单次连续交互，而不是跨实验保留的历史。

试验只安排了一次中途打断，并没有量化语音停止的延时，也不能判断未切换主题是听取失败还是生成控制失败。样本数量、第三方转换和运行实现都限制了归因。做训练助手时可以固定输入音频，分别验证重叠发言、停止时间和切换话题。

**推荐理由：** 这次试验把能同时听说，与能自然回应且持续稳定地区分开，给语音产品设计提供了可检验的切入点。

### 2. 止められないDBをAWS DMSで移行してハマったこと（RDS for Oracle）

**原文：** https://zenn.dev/kiri0728/articles/c8d5f349b047dd

**发布时间：** 2026-11-27 11:37:34 JST

这不是单次停机搬库。旧 AWS 环境的 RDS for Oracle 数据约 150 GB，依赖旧地址的系统仍会更新数据。DMS 用全量加载把已有行复制到新库，再用 CDC 驱动后续变动，停机主要留给最后变更应用连接地址。

在验证中，全量成功并没有带动增量同步，原因是源 Oracle 日志未提供 CDC 需要的定位信息和保留期。用 rdsadmin 启用补充日志，将主键等列写进 REDO 日志，并让归档日志保留 24 小时后，变动能够传到新库。团队为保留日志先追加了 20 GB 空间，说明延长保留期也要考虑写入量。

端点报 ORA-12545 时，直接填 IP 的对照连接成功，把排查从网络可达性转向了域名。原因最终是主机名手误。这里的 IP 是诊断对照，并非生产环境固定 IP 的迁移方案。

DNS 切换的实际停机约十分钟。此后旧库仍接收写入，新库只负责读取，CDC 在两者之间继续运行。这个记录的边界是单边写入的具体迁移案例，不能推广成双写无冲突，也没有记录最终停用 CDC 的结果。

**推荐理由：** 这次迁移在旧系统持续写入的条件下拆开复制、追差分和切换三步，也给出了排错线索。

### 3. OpenSearch Service の新エンジンがサポートした join、高カーディナリティ集計、query DSL を試してみた

**原文：** https://dev.classmethod.jp/articles/opensearch-new-engine-joins-and-dsl/

**发布时间：** 2026-11-27 22:43:52 JST

这篇实测在东京区配置了 OpenSearch 3.9.0 的 OPTIMIZED 模式，运行一个 or2.medium.search 节点，索引副本数为零。四个索引来自固定随机种子的合成数据，包含一百万条日志与约五十一万条 span。客户端计时包含 HTTPS 网络往返，各项只测三次。

对 ERROR 日志和 span 用 trace_id 连接时，PPL、SQL 三次都返回 176,806 条连接行、49,905 个不同的 trace。一条日志可对应多个 span，因此前一个数不能当作故障数。再用 left join 检查没有 span 的 ERROR，得到与预期相符的 10,372 条。

另一个 lookup 实验给前三条 ERROR 添加部署历史，因同一服务对应多次部署而扩为十九行。这里不仅添加了列，也改变了行数。高基数实验则在一百万条日志上数出 432,279 种 user_id，两种查询语言结果一致。

针对客户端兼容性，作者向 _search 发送过滤聚合和文本检索两种 query DSL，均返回 HTTP 200。该结果支持这两类查询可执行，不能由状态码认定走了加速路径，单节点的小规模样本也不支持生产吞吐承诺。

**推荐理由：** 从已知答案的合成数据核对结果，比只看一次查询成功更能暴露连接和计数语义。

### 4. CloudWatch エージェントのログ収集パスを変更する手順（SSM パラメータストア + Run Command）

**原文：** https://dev.classmethod.jp/articles/cloudwatch-agent-change-log-path/

**发布时间：** 2026-11-28 00:04:36 JST

这套 Windows EC2 只在实例启动时读一次 SSM 参数存储中的配置。修改其中的 file_path 不会自动刷新已经运行的 CloudWatch Agent，因此保存参数与让主机应用参数是两项操作。

通过 Systems Manager 的 Run Command，调用 AmazonCloudWatch-ManageAgent 的 configure 来重新取配置。这个步骤只重启采集代理，不需要重启实例。限制是代理重启时日志和指标暂时停发，监控时间线上可能出现空档。

文章按具体实例做验证，在变更后路径写出日志，到对应日志组查看按实例标识生成的流。远端展示可能晚几分钟，仅看到 Run Command 成功不足以确认数据抵达。该示例只采目录下直接存放的文件，不递归采子目录。

参数如果由 CloudFormation 管理，手动改值会使运行配置与模板发生漂移，下一次更新还可能覆盖修改。把云上变更与模板对齐，能把一次成功操作变成可持续的配置，尤其值得在批量切换前验证。

**推荐理由：** 从配置保存到日志到达有两个可独立失败的过渡环节，这个案例给出了检查方法。

### 5. SmartHRの「フロントシステム」の品質保証は、なぜ一言で語れないのか —— むずかしさに向き合う現場の取り組み

**原文：** https://tech.smarthr.jp/entry/2026/11/27/120641

**发布时间：** 2026-11-27 12:06:41 JST

案例中的「フロントシステム」是 SmartHR 的业务分工，用于收集员工资料并向相关人发放信息。在入职与邀请管理中，人事要拿到正确资料。在发放工资明细时，员工使用的手机等阅读环境也影响是否可用。功能之间串联后，故障可能落在两个开发团队的交界。

团队已经能看见事故和缺陷的分布，但各功能的目的不同，汇总数量并不能导出共同的优先级。实际工作中，可以进一步区分事故发生在谁的流程、影响什么数据、卡在哪个交接点，让跨团队会议能根据同一维度讨论。

区域 QAL 和 EM、PO 一起定方向，并将测试战略与测试计划分开。前者在开发早期发现风险、列出应关注的问题，后者选择这个改动适合的测试方法。对熟悉业务的人员做探索性测试等方法，仍给各团队留下选择空间。

团队先把用例集中到 Notion，再让 AI 参考用例、事故、缺陷和规格以提示遗漏。文章给出的是做法和期望，不是证明工时减少的受控试验。评估时可对相似改动观察新增的有效风险项和审查耗时，两者分别记录。

**推荐理由：** 这篇团队实践把公共质量边界落实到具体的入职、审批或发放场景，适合讨论测试如何因风险而异。

## 4. 今日技术主题

### 以结果为准设计可复核的检查

一条成功消息能证明的范围取决于它从哪发出。Run Command 的成功只能说命令执行成功，最终还要在日志接收端验收。搜索能执行与走了何种加速路径，也是两条不同的验证线。

给数据管道制作样本时，可先写出预期：一次故障关联多条 span 时，行数与故障数分别如何变化。再让真实客户端运行，记录数据规模、节点数和端到端耗时，避免把一次短延时误当成普遍性结论。

在日本业务团队中落地时，可以从已知业务场景建立可验证的质量目标，例如工资明细在员工常用终端上的展示。不要从团队采用了 AI 推出节省了多少工时，而是比较相同范围的工作是否遗漏关键风险。

# B. 重点总结与可用于面试的知识

### 1. 日本語のFull-duplex音声対話モデルを実際に動かしてみた話

1. **中文：** 核验时区分音频通道支持并发输入输出和对话行为是否自然。
   **日本語：** 同時入出力の可否と、相槌や割り込みの自然さは評価項目を分ける。

2. **中文：** 应用上线前分别监测模型包的空间占用和推理峰值。
   **日本語：** 配布物の容量と実測したプロセスのピークメモリを並べて見る。

### 2. 止められないDBをAWS DMSで移行してハマったこと（RDS for Oracle）

1. **中文：** 先让旧库产生包含行定位信息且保留足够久的日志，再验证 CDC 能实际追上源端。
   **日本語：** フルロードの完了と、CDC が更新を反映できることは別々に確認する。

2. **中文：** 将连接测试的失败按网络路径和名字解析分开排查。
   **日本語：** 切り替え後に旧側の書き込みが残るなら、新側の更新可否と同期停止の条件を明示する。

### 3. OpenSearch Service の新エンジンがサポートした join、高カーディナリティ集計、query DSL を試してみた

1. **中文：** 先用已知答案验证一对多展开和未匹配的记录，别用连接行数替代原始日志数。
   **日本語：** ログを数えるのか、結合した行を数えるのかを決め、seed から出した期待件数と照らす。

2. **中文：** 分别验证既有 DSL 的兼容性和真实负载下的速度。
   **日本語：** DSL 互換性の確認と、実運用での応答時間の測定を別にする。

### 4. CloudWatch エージェントのログ収集パスを変更する手順（SSM パラメータストア + Run Command）

1. **中文：** 配置取用方式决定单改参数能否生效，起动时只取一次需要显式刷新。
   **日本語：** パラメータを編集しただけでは、起動済みのサーバーには反映されない。

2. **中文：** 按实例检查日志到达，并对齐 CloudFormation 模板以免回退。
   **日本語：** ホストを再起動しなくても送信の一時停止はあるので、実際のログ到着を追う。

### 5. SmartHRの「フロントシステム」の品質保証は、なぜ一言で語れないのか —— むずかしさに向き合う現場の取り組み

1. **中文：** 用例的分工由业务风险决定，不能只用跨功能的缺陷总量决定优先级。
   **日本語：** 同じ件数でも、対象機能や利用者が違うと品質指標の意味が変わる。

2. **中文：** 把经验变成可检索的记录后再用 AI 提示遗漏，并用人工审查判断新增案例是否有用。
   **日本語：** テスト戦略では早期にリスクを出し、計画では案件に合う試験を選ぶ。

## C-1. 新学JLPT词汇

查对全108期的432份文件，本次收录原文用法及参考等级均可确认的四个新词。已有词汇留作复习。

### 1. 苦労（くろう）｜N3

- 词性：名詞・サ変動詞
- 含义：指为推进事情付出辛苦或承受难处。
- 搭配：苦労する / 苦労が続く / 苦労を重ねる
- 文章语境：作者说明跨功能的质量保障难以形成共同方向。
- 例句：対象が違うチームの評価基準をそろえるのに苦労しました。
- 例句含义：我们为统一服务对象不同的团队的评估标准费了不少功夫。
- 辨析：「苦戦」常用于竞争或陷入不利局面，「苦労」也能描述长期投入的辛劳。

### 2. 時期（じき）｜N3

- 词性：名詞
- 含义：指某事发生的时期，可表示一段时间范围。
- 搭配：時期が異なる / 導入時期を決める / 時期によって変わる
- 文章语境：文章介绍组织内部对功能群的定义会随时期和立场而异。
- 例句：同じ指標でも、手続きを見直す時期によって優先度が変わります。
- 例句含义：即使是同一指标，优先度也会随修订手续的时期变化。
- 辨析：「時点」强调一个时间点，「時期」可以包含阶段或时段。

### 3. 軸（じく）｜N1

- 词性：名詞
- 含义：此处指支撑多项决定的中心尺度或原则。
- 搭配：判断の軸 / 軸をそろえる / 軸が定まる
- 文章语境：作者讨论多个团队对质量观点不一时，如何找到能够回归的共同依据。
- 例句：複数の部署で迷ったときは、利用者が正しく手続きを終えられるかを判断の軸にします。
- 例句含义：多个部门难以抉择时，我把用户能否正确办完手续作为判断基准。
- 辨析：「指標」可指定可测量和比较的数值，「軸」更强调一系列判断共同围绕的依据。

### 4. 全般（ぜんぱん）｜N2

- 词性：名詞
- 含义：指某一类别或领域的总体范围。
- 搭配：技術全般 / 業務全般 / 全般に当てはまる
- 文章语境：文章限定单个转换版本的试验结果不能代表整个全双工模型领域。
- 例句：一台で出た挙動が音声モデル全般に当てはまるかは、別の環境でも調べます。
- 例句含义：一台机器上的观察能否应用到各类语音模型，我会用另一环境检验。
- 辨析：「全体」可指某个整体结构，「全般」强调覆盖的范围广。

## C-2. IT/AI专业词汇

1. **Mimi（ミミ）**：把连续语音编码为可逐步处理的 token 的编解码器。 Moshi 用它处理用户和模型的语音流。

2. **Supplemental logging（サプリメンタルロギング）**：给 REDO 日志添加用于定位变更行的补充信息。 这次启用主键补充日志以支持 CDC。

3. **Left join（左外部結合）**：即使右侧找不到匹配，仍保留左侧行的连接。 试验借此统计没有对应 span 的错误日志。

4. **Configuration drift（構成のドリフト）**：实机配置与声明管理的配置发生偏差。 手动修改 SSM 后，下一次栈更新可能覆盖改动。

5. **Exploratory testing（探索的テスト）**：在实际试用时根据发现继续调整检查方向的方法。 文章给出适合熟悉功能的人执行探索性测试的例子。
