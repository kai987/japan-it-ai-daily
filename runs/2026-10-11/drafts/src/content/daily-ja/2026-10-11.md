### 1. Claude Code v2.1.296 の主要アップデート - サブエージェントの autoCompactWindow と Read の allow_large 追加

**原文：** https://dev.classmethod.jp/articles/20261010-cc-updates-v2-1-296/

**公開時刻：** 2026-10-10 17:00:13 JST

**課題と機能。** Claude Code 2.1.296 の Read に、通常より大きなテキストを一度に取得する `allow_large` が加わりました。全文が必要で、コンテキストに余裕があることが前提です。サブエージェントの `autoCompactWindow` は子会話だけを早めに圧縮する別の設定ですが、frontmatter の値の形式は執筆時点の公式文書にまだありません。取得量の拡大と会話の圧縮は同じ機能ではありません。

**比較の条件。** 著者は空のディレクトリで、68バイトの行を3000行並べた204000バイトの big.txt を用意しました。project 設定だけ、MCP なし、Read を許可した `claude -p` を stream-json で実行します。`--max-turns 1` は Read の結果をモデルへ戻す前に止める条件です。終了コード1と error_max_turns が出ても、読み取り自体は行われています。一方は allow_large を禁止し、もう一方は全文が必要だと伝えて、モデルが選んだ入力を記録しました。

**取得結果。** Opus 5.5 では通常の Read が732行で終わり、totalLines=3001、truncatedByTokenCap=true でした。全文を求めた側は allow_large=true を使い、3001行すべてを返しました。wc の3000行と異なるのは、末尾の改行の後ろを空行として数えるためです。実際の末尾も確認されています。Haiku 5.5 も同じ行数・終了理由でした。記録費用は Opus が0.0643468／0.052076ドル、Haiku が0.00186747／0.00142273ドルで、この二回では全文取得側の方が低い値でした。

**限界と変更への備え。** 一回ずつの条件比較であり、費用の分布や読んだ内容の理解は検証されていません。全行取得を正確な回答の保証にはできません。また、非 UTF-8 の Edit／NotebookEdit は文字化けを起こす編集から拒否へ変わりました。BASH_ARGV0 の権限確認やマスキングも修正一覧にありますが、Read の実験とは証拠の種類が異なります。Shift-JIS が残る環境では、変換方法を決めてから更新する判断につながります。

**読む価値：** 取得量と打ち切りの記録を見て、読み取りと理解を分けられます。

### 2. OpenAI の Decisions API に書類の種類を分類させて Clef と比べてみた

**原文：** https://dev.classmethod.jp/articles/openai-decisions-doc-classification/

**公開時刻：** 2026-10-10 10:07:41 JST

**比較する仕事。** Decisions API の gpt-6-luna に書類画像を渡し、Clef の clef／clef-flash と同じ分類をさせた検証です。OCR の文字列は与えません。`choice` は七種類と other の八択から一つを選び、確率と confidence を返します。請求書、見積書、領収書、納品書、注文書、契約書、履歴書を見分ける仕事で、自由な文章生成の評価ではありません。

**実験条件と正解。** 1240×1754の PNG を、日本語14枚・英語14枚、合計28枚用意します。各種類の二枚目には、別名、小さい見出し、他の書類への言及などを入れています。REST API で一枚一要求、一回ずつ、同じ質問です。Decisions は28/28、Clef の二種類は27/28で、日本語の一枚ずつを外しました。架空の小さなデータでの結果であり、実書類全体の正解率ではありません。

**確信度を使えるか。** Decisions の confidence と選択した種類の確率は全件1.0、残りは0でした。Clef の正解は0.7957～0.9707、誤りは0.2384または0.5175です。以前の Clef 試験では0.8未満を確認に回せましたが、今回の Decisions は全問正解なので、誤ったときに値が下がるかは分かりません。紛らわしい別の書類で誤分類と人へ回し損ねる件数を調べる必要があります。分類の精度とスコアの運用価値は別です。

**速さと費用の読み方。** 日本からの往復時間の中央値は Decisions が0.517秒、clef が0.976秒、flash が0.3535秒でした。入力は一枚2444／1367／1367トークン、28枚の費用は0.0068／0.0092／0.0034ドルです。換算は1ドル150円です。Decisions は clef より安い一方、flash より安い・速いわけではありません。入力だけの課金という仕様を踏まえた比較で、反復分布や大量並列処理の測定は示されていません。

**読む価値：** 正解率と、人へ戻す基準としての確信度を分けて説明できます。

### 3. WAF でブロックする前に確かめていること

**原文：** https://zenn.dev/azunyan/articles/7a105969d7d16c

**公開時刻：** 2026-10-10 12:17:20 JST

**記事の立場。** Cloudflare Enterprise と Bot Management を契約し、基本のマネージドルールやレート制限を入れた環境での運用整理です。実際の値、条件や閾値は公開されていません。オリジンまで届く偵察の404などと、既知の攻撃で止まった記録を別の入口にし、絞った送信元のアクセス全体を確認します。誤検知率を測った比較実験ではありません。

**何を止めるか。** 一つの IP を会社、携帯回線や VPN の利用者が共有することがあります。ASN は事業者のネットワーク全体に及びます。JA4 は TLS ClientHello の特徴であり、同じブラウザや社内ツールは同じ値を持ち得ます。模倣するライブラリもあるため、人の身元とは扱えません。Bot Score は自動化らしさ、Verified bot は確認済みの bot、攻撃スコアは攻撃らしさで、違う判断材料です。

**止める前の判断。** 成功応答、人間寄りのスコア、User-Agent／JA4 の種類、事業者と業務上の用途を見て、正常な利用者が混じらないか調べます。国や一般的なブラウザの指紋だけで締め出さず、自動化や攻撃の条件を AND で加えます。影響が読めなければ Log から始め、決め手がなければ保留します。アカウントレベルのルールは先に評価され、そこでのブロックをサイト側の例外で覆せない点も重要です。

**運用上の境界。** 例外はパスと送信元の両方で絞り、必要な検査だけを飛ばします。止めた理由と止めなかった理由を記録しておくことで、次の担当者が判断を追えます。IP の持ち主や通信ソフトは変わるので、追加日と設定を突き合わせて見直します。一部の機能には契約条件があり、実際の閾値や改善の測定値もありません。この判断手順を自社の正常な通信で確かめることが、記事からの応用です。

**読む価値：** 通信の特徴と利用者の身元を混同せず、誤検知の影響を考えられます。

### 4. [アップデート] Route 53 Global Resolver DNS Firewall に 分析タブが追加されたので確認してみた

**更新の意味。** DNS Firewall の分析タブに CloudWatch メトリクス、Contributor Insights、ログのインサイトがまとまり、別画面へ移らずに確認できるようになりました。公式発表は Global Resolver と DNS Firewall の両方を対象にしますが、著者が試したのは VPC の DNS Firewall です。タイトルから Global Resolver の一連の動作まで実証済みとは読みません。

**表示と未確認部分。** 分析画面には VPC 単位の `VpcFirewallQueryVolume` が表示されました。ただし、Contributor Insights などは出力を確認できず、著者は設定が原因かもしれないとしています。原因は確定していません。サービスが壊れているとも、すべての分析が成功したとも言えません。公式の分析・アラーム能力と実測の範囲を分け、記録の入力、設定、表示を順に確認する学びになります。

**読む価値：** 設定、記録、表示を順に見て、未確認の機能を分けられます。

### 5. GitHub ActionsのOIDCでAWS認証が通らない時にsubクレームを確認して信頼ポリシーを直してみた

**原文：** https://dev.classmethod.jp/articles/try-github-actions-oidc-immutable-subject-claim/

**公開時刻：** 2026-10-10 15:43:42 JST

**なぜ新しいものだけ落ちるか。** immutable subject claim は、可変の組織名・リポジトリ名に不変の ID を加えます。削除やリネーム後の同名取得で、別のリポジトリが以前と同じ信頼を使う弱点を塞ぐ仕組みです。GitHub の公式発表では2026年7月15日後の新規・リネーム・移管が対象で、既存は明示的なオプトインです。github.com の変更であり、GHES 全般へは一般化しません。

**失敗を切り分ける。** id-token:write の権限、aud=sts.amazonaws.com、sub の条件を分けます。拒否の文面は IdP の ARN の誤りでも出るので、それだけでは原因を決められません。著者は認証失敗と debug の両条件で診断ステップを動かし、token 全体ではなく sub／aud／repository／ref の四項目を確認します。sub は `repo:OWNER@OWNER-ID/REPO@REPO-ID:ref:refs/heads/main` ですが、repository は元の名前のままです。旧 StringEquals の条件との不一致を確定しています。

**変更後の確認。** CloudFormation で組織ID・リポジトリIDをパラメータ化し、StringLike の新形式へ直しました。変更前の sts:AssumeRoleWithWebIdentity の拒否から、configure-aws-credentials の成功と get-caller-identity の AROA で始まる UserId へ変わっています。アカウント情報はマスクされます。ただしロールに業務の許可ポリシーはなく、本人確認にはその権限が不要です。認証成功とデプロイ権限の成立は別です。

**通る範囲に注意。** テンプレートの RepositoryId=* は、各自で ID を調べる負担を避けた例です。同じ組織で同じ名前を作り直しても通せるため、厳密に固定するなら実際の数値を渡します。StringLike の * は / も含む任意の文字列に一致します。数値か単独 * に限定する入力検査は部分的なワイルドカードを防ぎますが、* 自体の広さは残ります。認証を通すことだけを目的に、対象を無関係なリポジトリへ広げない判断が必要です。

**読む価値：** 実際の claim と信頼条件の差を追い、ワイルドカードの範囲を説明できます。

## 4. 技術テーマ：観察できた証拠から判断する

共通の問いは、目の前の信号が何を証明するかです。全行を返したことは取得量の証拠で、一ターンで止めた試験では理解を示しません。28枚全問正解でも、誤ったときのconfidenceは分かりません。読み取りと回答の質、正解率と人へ回す境界は、別々に確かめます。

防御や認証でも証拠の範囲があります。JA4はソフトの通信の特徴であり、共有IPには別の利用者がいます。DNSのルール関連付け、ログの受信、指標の表示は別の段階です。OIDCのsubが一致することと、ロールに業務の権限があることも同じではありません。各段階で成立した結果を記録します。

企業で応用するなら、入力条件、観察結果、未確認部分を並べて残します。Readの末尾、分類の誤りと確認漏れ、WAFでの正常な通信、DNSの記録と分析、数値IDの信頼と業務権限が対象です。原文にない誤検知率、処理量、全機能の成功を足しません。これは読後の検証設計であり、新たな実測ではありません。

**回答要点：** 誤りの事例がないので、失敗時に値が下がるか分かりません。別の難しい書類で誤りと確認漏れを測り、費用・時間もモデル別に比べます。

### Q3

**回答要点：** WAFは正常な通信とルールの順番、DNSは拒否・ログ・表示を確認します。未確認の分析は残します。OIDCは実物のclaimとIDを照合し、業務権限も別に調べます。

## C-2. IT/AI専門用語

1. **allow_large（大きな読み取り）**：Read で通常より大きな本文を取得する指定。 全文が必要で余裕があることが条件です。

2. **truncatedByTokenCap（トークン上限による打ち切り）**：上限で返却が打ち切られたことを示す値。 行数と末尾も合わせて見ます。

3. **choice（選択式の判定）**：用意した選択肢から一つを選ぶ質問型。 記事では書類を八択で分類します。

4. **confidence（確信度）**：判定をどの程度迷わず選んだかを表す値。 誤りのリスクと同じ値とは決められません。

5. **JA4（TLS通信の指紋）**：ClientHello の特徴から作る識別の手がかり。 同じ値や模倣があり、本人確認とは異なります。

6. **Bot Score（botらしさの点数）**：自動化された通信らしさの値。 記事の Cloudflare の契約が前提です。

7. **VpcFirewallQueryVolume（VPCのFirewall問い合わせ数）**：VPC 単位の DNS Firewall クエリ数。 分析タブで表示を確認した値です。

9. **StringLike（パターンによる照合）**：IAM の信頼条件をパターンで照合する指定。 * で通る範囲を確かめる必要があります。

## C-3. 新規文法

新規文法は2件です。原文5本と60日・106項目の履歴を表記と機能で照合し、原文の場所を直接示せる「～ぶん」「～ておく」を選びました。ぶんは事情と結果の対応、ておくは後のための記録の保持です。物の分量や位置の動詞は含めません。既習のだけでなく、に限らず、に応じてなどは復習へ分け、名前を変えて5件にしません。JLPTレベルは難度の目安で、公式認定ではありません。

### 1. ～ぶん｜N2

- 意味：ある程度や事情に応じた結果を示す
- 接続：普通形／名詞の＋ぶん
- 使い方：前の程度や事情を、後の結果の理由・対応関係として示します。
- 原文出現形：ぶん
- 原文根拠：[ルールの設定と記録は、手作業が挟まるぶん食い違いやすくなります。](https://zenn.dev/azunyan/articles/7a105969d7d16c)
- 独自例文：条件が広いぶん、巻き添えの範囲も大きくなります。
- 例文の意味：広い条件に対応して、影響する利用者も増えるという説明です。
- 注意：時間や物の分量ではなく、事情と結果の対応を示す用法です。

### 2. ～ておく｜N3

- 意味：後のために行い、その状態を保つ
- 接続：動詞て形＋おく
- 使い方：後の確認に備えて記録などを残します。物を置く位置の話とは区別します。
- 原文出現形：記録に残しておく
- 原文根拠：[止めた理由だけでなく、止めなかった理由も記録に残しておくのがおすすめです。](https://zenn.dev/azunyan/articles/7a105969d7d16c)
- 独自例文：保留した理由を、次の調査のために記録しておきます。
- 例文の意味：次に調べるときに使えるよう、理由を先に残すという意味です。
- 注意：完了そのものより、後に使える準備や状態を表します。
