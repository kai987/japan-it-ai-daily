### 1. Claude Code v2.1.296 の主要アップデート - サブエージェントの autoCompactWindow と Read の allow_large 追加

**原文：** https://dev.classmethod.jp/articles/20261010-cc-updates-v2-1-296/

**发布时间：** 2026-10-10 17:00:13 JST

**背景与机制。** Claude Code 2.1.296 为 Read 增加 `allow_large`，面向必须取得完整文本且上下文有余量的场景。新增的子代理 `autoCompactWindow` 可让子会话比主会话更早压缩，但原文指出子代理 frontmatter 的值形式当时尚未写入官方文档。读取上限与会话压缩是不同机制，不能把扩大一次读取量说成无限上下文。

**实验条件。** 作者在空目录生成每行68字节、共3000行的 big.txt，总计204000字节。使用非交互 `claude -p`、仅加载 project 设置、严格 MCP 配置、允许 Read、stream-json 输出，并设 `--max-turns 1`。一次明确禁止 allow_large，另一次只要求“完整文件、一次 Read”，模型自行设置 true。这个单轮设置会在把 Read 结果交回模型前停止，因此退出码1、error_max_turns 不表示 Read 本身失败。

**结果。** Opus 5.5 的未开启调用返回732行，totalLines=3001、truncatedByTokenCap=true；开启后返回3001行且没有截断标志。wc 的3000与工具的3001并不矛盾：末尾换行之后被显示为空行。作者检查了输出尾部，第二次确实包含原始第3000行。Haiku 5.5 的行数、选项和结束原因相同。记录费用分别为 Opus 0.0643468／0.052076美元、Haiku 0.00186747／0.00142273美元，这两次中读取更多反而费用较低。

**边界与兼容性。** 上述费用是特定提示与单次运行的结果，不是重复分布，也没有后续内容理解测试，不能推出完整读取必然更省钱或更准确。原文还整理非 UTF-8 的 Edit／NotebookEdit 改为拒绝操作，以避免非 ASCII 被替换，并列出 BASH_ARGV0 权限检查和日志脱敏修复；它们是更新说明，不能冒充本文逐项实测。日本项目残留 Shift-JIS 时，需先明确编码转换流程。

**阅读价值：** 用返回行数与截断标志判断原文是否读全，区分读取、理解和任务完成。

### 2. OpenAI の Decisions API に書類の種類を分類させて Clef と比べてみた

**原文：** https://dev.classmethod.jp/articles/openai-decisions-doc-classification/

**发布时间：** 2026-10-10 10:07:41 JST

**背景与接口。** 作者沿用 Clef 实验的书类，比较 OpenAI Decisions API 的 gpt-6-luna 与 clef／clef-flash。输入是单页 PNG 图像，不提供 OCR 文本；`choice` 从七种书类加 other 的八选项中选一，并返回选项概率与 confidence。按输入作结构化判断与生成自由文本是不同任务，本实验只覆盖书类分类。

**条件与数据。** 28张架空文档包括日文14张、英文14张，图像为1240×1754。七类各语言两张，第二张刻意使用缺失或小标题、别名、正文提及其他书类等干扰。每张通过 REST API 请求一次，沿用相同问题。Decisions API 正确28/28，两个 Clef 模型各27/28，误判均在日文；这只是准备好的小样本，不能当生产正确率。

**置信度的边界。** Decisions API 的 confidence 全为1.0，选中类别概率也全为1.0，其他七类为0；Clef 正确项为0.7957～0.9707，错误项为0.2384或0.5175。旧 Clef 测试可用0.8以下复核拾起误判，但这28张中 Decisions 没有错误，因而无从判断它答错时是否降分。高正确率并未证明分数可用于风险分流，需用更难、更多样的文档验证错误和漏审。

**时间与费用。** 日本发起的往返时间中位数依次为0.517、0.976、0.3535秒。每张输入为2444／1367／1367 token，28张费用为0.0068／0.0092／0.0034美元，按1美元150日元换算。Decisions 比 clef 便宜但并非比 clef-flash 更便宜或更快；它输入量更大，输入单价更低。作者报告仅输入计费，本文不新增精度置信区间、批量吞吐或重复延迟分布。

**阅读价值：** 把正解率与置信度的运营价值分开，保留同数据比较的条件。

### 3. WAF でブロックする前に確かめていること

**原文：** https://zenn.dev/azunyan/articles/7a105969d7d16c

**发布时间：** 2026-10-10 12:17:20 JST

**前提与证据类型。** 原文是 Cloudflare Enterprise 与 Bot Management 环境的运营经验，已有托管规则与速率限制；不公开实际规则、IP值或阈值。作者区分从404等异常响应发现偵察，与从已阻断请求找持续攻击源，再看该来源全部访问。文中没有误拦率对比实验，不能据此估计准确率或承诺阻断效果。

**机制与影响范围。** IP可能由CGN、公司出口、VPN和中继服务共用；ASN涵盖运营商网络；JA4依据 TLS ClientHello 特征形成指纹，同软件与设置会共用，浏览器形态也可被工具模仿。JA4并不是人的身份。Bot Score 低值倾向自动化，Verified bot 表示确认身份的合法 bot，攻击分数是另一轴；攻击请求、正常浏览和业务爬虫应分开判断。

**选择规则。** 作者先确认正常成功响应、人类倾向分数、User-Agent与JA4多样性、运营商类别及合作方用途。国家、常见浏览器JA4、共享IP等宽条件应与自动化或攻击信号做AND；不确定时先 Log 或确认画面，没有决定证据则保留。账户级规则先于站点级执行，被前者阻断后不能靠站点例外放行。因此广域规则只放各站都不需要的流量，业务特例保持窄范围。

**限制与维护。** 例外只跳过必要规则，并按路径与来源双重限定；不要关闭整个规则集合。阻断与不阻断均记录日期、对象、理由、筛选画面及来源调查，并定期复查，因为IP归属、软件指纹和User-Agent会变。Bot Score、JA4、Log等能力依赖产品与套餐；这套经验是减少误拦的判断流程，无法替代实际业务流量下的测试。

**阅读价值：** 以请求行为与受影响范围做阻断判断，而不是把 IP、ASN、JA4 当人的身份。

### 4. [アップデート] Route 53 Global Resolver DNS Firewall に 分析タブが追加されたので確認してみた

**原文：** https://dev.classmethod.jp/articles/route-53-dns-analytics-insights/

**发布时间：** 2026-10-10 18:07:32 JST

**背景与范围。** Route 53 DNS Firewall 的分析 tab 把 CloudWatch メトリクス、Contributor Insights、日志分析入口放进同一控制台，减少在服务间找指标和日志的操作。官方公告同时涉及 Global Resolver 与 DNS Firewall，但本文作者的实测是 VPC 内 DNS Firewall，不能由标题的 Global Resolver 推导其全球解析场景也已验证。

**设置与观察。** 作者准备域名列表，以 BLOCK 规则组成规则组并关联 VPC，再将 Resolver 查询日志送到 CloudWatch Logs。从同一 VPC 的 EC2 发起解析，阻断域名失败、其他域名正常；日志里的 `firewall_rule_action=BLOCK` 与动作一致。这里验证的是查询经过防火墙后的行为和记录，不能仅看控制台已配置就判定生效。

**结果与限制。** 分析 tab 显示 VPC 级的 `VpcFirewallQueryVolume`，说明能在原界面查看查询数量。作者尝试 Contributor Insights 等却没有确认到输出，并表示可能设置有误；原因没有确定，不能把它写成服务故障或成功。官方给出日志过滤与报警能力，但文章未完成报警投递或所有 tab 的测试。本日报保留未确认项，提出逐层查日志输入、功能设置和显示结果作为应用建议。

**阅读价值：** 从防火墙规则、日志到指标逐层核验，保留没有确认到输出的事实。

### 5. GitHub ActionsのOIDCでAWS認証が通らない時にsubクレームを確認して信頼ポリシーを直してみた

**原文：** https://dev.classmethod.jp/articles/try-github-actions-oidc-immutable-subject-claim/

**发布时间：** 2026-10-10 15:43:42 JST

**背景。** GitHub 的 immutable subject claim 把原先基于可变 owner/repository 名称的 sub 加上不变数值ID，避免删除或改名后，其他同名仓库得到相同身份。官方说明2026/7/15之后新建、改名或转移的仓库采用新格式，既存仓库可显式选择；仅 github.com，不能扩展为 GHES 全部适用。原文针对新仓库无法匹配旧 AWS 信任条件的再现实验。

**诊断机制。** 先区分工作流 id-token:write、aud=sts.amazonaws.com 与 sub 条件，拒绝信息本身无法区分信任条件不符或IdP ARN错误。作者在认证失败且启用 debug 时，取得OIDC token后只选 sub、aud、repository、ref 四个 claim 输出，不输出完整 token；仅开debug并不会自动展示掩码 token 内容。新 sub 是 `repo:OWNER@OWNER-ID/REPO@REPO-ID:ref:refs/heads/main`，而 repository 仍是名字路径。

**修复与结果。** CloudFormation 参数化组织ID和仓库ID，以 StringLike 匹配新 sub，再调用 configure-aws-credentials 与 sts get-caller-identity。原文先复现 Not authorized to perform sts:AssumeRoleWithWebIdentity，改后认证成功，UserId 以角色AROA开头；账号信息被掩码。实验角色没有业务权限策略，身份查询不需要该权限，所以成功证明角色可承担，不证明部署权限已齐全。

**安全边界。** 示例默认 RepositoryId=* 是设置便利性选择；同组织同名仓库重建后，ID改变仍会通过，削弱这项保护。限定目标时应填实际数值ID；StringLike 的*也可覆盖斜线，参数校验只允许数字或单独*，并不自动把通配符变成最小权限。旧仓库的格式与新策略需另核对，不能为“让CI变绿”把范围无条件放宽。

**阅读价值：** 以实际OIDC claim解释信任匹配，同时认识通配符可能削弱不变身份保障。

## 4. 技术主题：依据可观察的证据作出判断

五篇共同的问题是“眼前的信号到底证明了什么”。返回全行证明取得量，单轮停止并未验证模型理解；28张全部分类正确也没有提供错误时的confidence分布。因此，读取完整性与答案质量、正解率与复核阈值分别需要证据，不能用一次绿灯替代后续判断。

防护与云端认证有另一种边界。JA4是软件通信特征，共享IP包含不同使用者，广域阻断必须考虑正常请求；DNS规则关联、日志到达、指标显示是不同阶段；OIDC的真实sub是否匹配以及承担角色后能否操作资源，也是不同验证。每个阶段的收据都有自己的范围。

作为阅读后的企业应用建议，可把“输入条件—观察结果—尚未核实部分”写进验收记录：Read行数和尾部、分类误判与复核漏审、WAF正常流量、DNS日志与分析输出、精确ID信任与业务权限。来源没有提供的吞吐、误拦率、全功能成功与生产保证均不补造。本文提出验证顺序，没有新增实测结果。

## 5. 面试复习卡

### Q1

### Q2

> 全件正解でconfidenceが全部一なら、確認の基準は決められますか。

**回答要点：** 28张架空样本没有错误案例，不能证明答错时分数会降低。另备难例观察错误、分数和漏审，并分开比较Clef与flash的费用时间。

### Q3

> 防御と認証の変更を、何の証拠で受け入れますか。

**回答要点：** WAF看正常用户和规则顺序；DNS分别查解析拒绝、BLOCK日志与指标，未见分析输出保持未确认；OIDC查真实claim与精确ID条件，另核业务权限。

## C-1. 新学 JLPT 词汇

### 1. 見分ける（みわける）｜N2

- 词性：動詞・一段
- 含义：辨别不同对象
- 搭配：書類を見分ける / 誤りを見分ける
- 文章语境：分类测试讨论低置信度是否能辨别错误文档。
- 例句：確信度だけで誤りを見分けられるか、別の書類でも調べます。
- 例句译文：还要用其他文档检查能否仅凭置信度辨别错误。
- 语感区别：强调从外观或线索辨别，和单纯知道不同。

### 2. 受諾（じゅだく）｜N1

- 词性：名詞・サ変
- 含义：接受提案或请求
- 搭配：提案を受諾する / 受諾済みの見積書
- 文章语境：原文英文发票的干扰信息提到已受诺的报价。
- 例句：受諾済みの見積書への言及だけでは、書類の種類は決まりません。
- 例句译文：仅提及已接受的报价不能决定文档种类。
- 语感区别：比一般同意更正式，常用于契约或提案。

### 3. 往復（おうふく）｜N3

- 词性：名詞・サ変
- 含义：往返
- 搭配：往復時間 / 往復を測る
- 文章语境：原文计量日本发起的API往返时间。
- 例句：往復時間には、通信と応答を待つ時間も含まれます。
- 例句译文：往返时间也包括通信和等待响应的时间。
- 语感区别：不等于模型内计算时间，两者需分开。

### 4. 混じる（まじる）｜N2

- 词性：動詞・五段
- 含义：混入；夹杂
- 搭配：利用者が混じる / 正常な通信が混じる

- 例句译文：共享出口中攻击与普通浏览会混在一起。
- 语感区别：自动词，不表示操作者主动混合；主动为混ぜる。

### 5. 締め出す（しめだす）｜N1

- 词性：動詞・五段
- 含义：拒之门外；禁止进入
- 搭配：利用者を締め出す / 通信を締め出す

### 6. 名乗る（なのる）｜N1

### 7. 塞ぐ（ふさぐ）｜N2

## C-3. 新学语法

本日新语法2项。五篇原文与60天、106项历史语法逐项归一化并按功能查重后，选取可逐字定位的「～ぶん」「～ておく」。ぶん在此表示情况与结果相应，ておく表示为后续保留记录；不把普通名词分或位置动词置く算新语法。だけでなく、に限らず、に応じて等既习表达归入独立复习，不能换名称凑5项。JLPT等级是难度参考，不是官方认证。

### 1. ～ぶん｜N2

- 含义：与某种程度或情况相应地；因为这一点
- 结构：普通形／名詞の＋ぶん
- 用法：用前项的程度或因素说明后项结果；原文因手工环节而易产生偏差。
- 原文形态：ぶん
- 原文依据：[ルールの設定と記録は、手作業が挟まるぶん食い違いやすくなります。](https://zenn.dev/azunyan/articles/7a105969d7d16c)
- 独立例句：条件が広いぶん、巻き添えの範囲も大きくなります。
- 例句译文：条件越宽，牵连的范围也越大。
- 注意：这里不是时间段或物理份量的分，也不等于程度上限的ほど。

### 2. ～ておく｜N3

- 含义：预先做；做完保留该状态
- 结构：動詞て形＋おく
- 用法：为后续调查提前记录；保留记录是动作用途，非位置的置く。
- 原文形态：記録に残しておく
- 原文依据：[止めた理由だけでなく、止めなかった理由も記録に残しておくのがおすすめです。](https://zenn.dev/azunyan/articles/7a105969d7d16c)
- 独立例句：保留した理由を、次の調査のために記録しておきます。
- 例句译文：提前记录保留的理由，以便下次调查。
- 注意：与只是完成的てしまう不同，强调事先准备或状态保留。
