### 1. Cloudflare AI Searchで日本語のキーワード検索を使うなら、trigramトークナイザを作成時に選ぼう

**原文：** https://dev.classmethod.jp/articles/cloudflare-ai-search-cjk-keyword-tokenizer/

**公開時刻：** 2026-11-05 23:35:32 JST

日本語の検索で該当する文書が返らないとき、生成モデルを替える前に、検索語をどう区切っているかを見る必要があります。記事では Cloudflare AI Search のキーワード検索を対象に、Porter 型の語幹処理を使う porter（ポーター）と、文字を一つずつずらして三文字の並びを作る trigram（トライグラム）を比較しました。ベクトル検索が失敗を覆い隠さないよう、ハイブリッド検索を外し、キーワード検索だけで試しています。

検証は Workers Free のアカウントと、経費精算・有給休暇を説明する二つの文書で行われました。一致モードは AND、しきい値は既定の0.4です。作成時から trigram を選んだインスタンスでは自然文の質問が経費文書にヒットしましたが、porter は0件でした。三文字の「締め日」はヒットする一方、二文字の「経費」はしきい値を0にしても0件です。表示上の AND を、質問中の全三文字列が必須という意味にまで広げて解釈できないことも、この少数例で分かります。

既存インスタンスを切り替えると、設定表示と再インデックスのジョブは更新されても、約9分の観察では検索結果が変わりませんでした。逆方向の切り替えでも作成時の挙動が残りました。ただし、著者は仕様か不具合か、反映待ちなのかを確定していません。二、三ファイルの結果を大規模索引へ一般化せず、設定値・ジョブ完了・実際の日本語クエリを別々に照合する事例として読みます。

**読む価値：** 日本語の取りこぼしと設定変更の反映を、検索方式を分離した実験で考えられます。

### 2. 【MLflow 3.18】Skill Registryでスキル管理してみた

**原文：** https://zenn.dev/rrioh/articles/c0d66deddddafe

**公開時刻：** 2026-11-06 00:24:47 JST

エージェントへ配る指示を単なるファイル共有にすると、何を直した版が動いているのか追いにくくなります。記事は MLflow 3.18.0 の Experimental な Skill Registry（スキルレジストリ）を試し、スキル本文と補助ファイルを一緒に登録しています。同じ名前で再登録すると元の版を残して次の版を作れ、草稿（下書き）として確認してから有効化し、production という別名（エイリアス）を割り当てる流れです。

取得では固定した版とエイリアスを使い分けられます。著者は変更前後の指示と補助ファイルが取得先にそろうことを確認しました。既存の取得先へ再度 pull すると例外となり、空または存在しないディレクトリが必要でした。登録したものの検索と、製品に同梱されたスキルの一覧表示も別です。最新版を示す名前と、その時点で実際に得た版を区別することが、再現性の出発点になります。

後半では compare_evaluations() を使い、同じ12件の整数入力で二つの実行を比べています。正解率は0.5から1.0、平均絶対誤差は0.5から0となり、対応のある比較で p値0.03125、差の信頼区間も表示されました。ただし、偶数だけ正しく扱う基準関数を置いたダミーデータの実験です。LLMが実務で改善した証拠ではありません。評価値の向きと同じ入力同士の対応を保ち、平均だけでは見えない差を確認するAPIの使用例として扱います。

**読む価値：** 指示の版を配布する工程と、同じ入力で結果を比較する工程をつなげて説明できます。

### 3. 非同期の操作が競合して更新が消える問題を、小さなキューで直す

**原文：** https://zenn.dev/carecraft/articles/react-action-queue-lost-update

**公開時刻：** 2026-11-06 09:00:11 JST

経費精算のデモで、処理直後に操作する人を切り替えると、更新や表示が消える問題が起きました。構成はブラウザの Web Worker（ウェブワーカー）をAPIに見立て、クライアントが現在の状態と操作を送る方式です。二つの操作が同じ古い状態から出発すると、後から返った結果に先の更新が含まれず、最後の書き込みで消えてしまいます。React のクロージャが描画時の値を保持する点も、この競合に関わっています。

著者は useActionQueue で Promise（プロミス）をつなぎ、前の操作が終わってから次を実行するようにしました。成功時と失敗時のどちらからも次の処理へ進め、内部の連鎖に失敗を残さず、呼び出し元には元の Promise を返してエラーを伝えます。処理対象の状態は実行時の useRef（レフ）から読みますが、操作した人はクリック時点で確保します。両方を実行時に読むと、順番待ちの間に別の人の操作へ変わり、監査記録まで誤るためです。

人の切り替えに伴う画面取得とリセットも同じキューに入れ、削除後に古い処理が保存データを戻す競合を防ぎました。検証では Playwright でクリック直後の切り替えを同じページ内の処理で再現し、繰り返しています。ただし、これは一つのクライアント内の順序制御です。複数利用者が実サーバーへ同時更新する場合は、トランザクションやバージョン確認など、サーバー側の整合性制御も必要です。

**読む価値：** 最新状態を読む時点と、操作者を確定する時点が異なるという実装上の判断を学べます。

### 4. Database Insights のスタンダードモードで、Amazon RDS for PostgreSQL のロック待ちとブロック元を確かめてみた

**原文：** https://dev.classmethod.jp/articles/rds-postgresql-lock-wait-database-insights-standard-mode/

**公開時刻：** 2026-11-05 11:30:24 JST

Database Insights の標準モード（スタンダードモード）でロック待ちが分かっても、原因となる接続がグラフに現れるとは限りません。記事は東京リージョンの RDS for PostgreSQL 18.3、db.t4g.micro で、一つの未コミット更新が同じ行を更新する四セッションを待たせる状態を作りました。モードが standard でも、CLIで作成したインスタンスは Performance Insights が無効だったため、途中で有効にした点も記録しています。

ダッシュボードには Lock:transactionid と Lock:tuple が現れましたが、原因の接続は idle in transaction、つまりトランザクションを終えずにアイドルのまま次の命令を待っており、実行中のクエリとして負荷に出ません。pg_stat_activity と pg_blocking_pids() を60秒ごとに記録すると、先頭の待機セッションは原因のトランザクションを待ち、後続の三つはタプルのロックを待つ関係がたどれました。待機イベントの種類と、誰にブロックされているかは、別の観測です。

原因側をロールバックした後、待機中の更新は725.5～725.7秒で返り、検証では後続もロールバックして在庫値を保ちました。720秒という保持指定との差には、監視の間隔と開始時点が関わっています。ただし、スタンダードモードで有償モードのSQLロック分析が使えるという結果ではありません。この一行更新の再現実験から、負荷の高いSQLだけを探すとアイドル接続の未完了トランザクションを見逃せることを学びます。

**読む価値：** 待機を起こした側と待たされた側を分けて追う、障害調査の手順が具体的です。

### 5. Vite+ 1.5 がリリースされたので、vp migrate は ts-node をどこまで移行してくれるのか試してみた

**原文：** https://dev.classmethod.jp/articles/hasuto-vite-plus-1-5-migrate-ts-node/

**公開時刻：** 2026-11-05 21:58:57 JST

TypeScript の移行では、スクリプトが動くことと、型の誤りを実行前に止めることを分けて確認します。記事は Vite+ 1.5.0 の vp migrate（ブイピーマイグレート）という移行コマンドを、ESM の小さな ts-node プロジェクトへ適用しました。Node.js 26.13.0 の検証で enum を含む計算処理を使い、型注釈を除くだけでは済まないコードが変換されていることを確かめています。

最初は三つのスクリプトが残りましたが、設定ファイルを明示する TS_NODE_PROJECT を付けると、型検査をしない実行用スクリプトが Node.js の事前読み込みへ移りました。テストも、node:assert/strict の既定インポートを名前付きへ変えると移行できました。一方で型検査ありのスクリプトは自動変換されず、vp check（ブイピーチェック）という型検査を先に実行する構成へ手で分けています。

わざと価格を文字列にすると、移行先の実行処理は数値へ変換して同じ結果を返しましたが、型検査は誤りを検出しました。出力が一致しても保証が保たれたとは限らない例です。vp check が失敗したら実行へ進まない接続にした後で、不要になった ts-node を外しました。ただし、同じ検証でも CommonJS は相互運用の警告で自動変換されませんでした。Node.js の対応版やモジュール形式を確認し、警告を安全に無視できる成功表示と取り違えないことが重要です。

**読む価値：** 移行後の正常出力に隠れた型検査の欠落を、わざと誤りを入れて検証できます。

## C-1. 新規JLPT語彙

### 1. 現れる（あらわれる）｜N3

- 品詞：動詞・下一段
- 意味：それまで見えていなかったものが、見えるようになること。
- 連語：画面に現れる / グラフに現れる / 差が現れる
- 記事文脈：原因接続が負荷グラフに出ないという観測範囲を説明する語です。
- 例文：原因の接続が負荷グラフに現れない場合もあります。
- 例文の意味：問題を起こした接続でも、負荷の図では見えない場合があるということです。
- ニュアンス：ここでは人が来る意味ではなく、観測画面に状態が見える意味です。

### 2. 吐く（はく）｜N3

- 品詞：動詞・五段
- 意味：技術の会話で、プログラムが例外やエラーを出すこと。
- 連語：例外を吐く / エラーを吐く / メッセージを吐く
- 記事文脈：評価の改善条件を満たさないときに例外を出すことを、原文はくだけた言い方で表しています。
- 例文：改善の条件を満たさなければ、検査は例外を吐きます。
- 例文の意味：改善したと認められない場合に、検査処理が例外で知らせるという意味です。
- ニュアンス：会話的な表現です。正式な仕様では「例外を送出する」とも言います。

### 3. 分ける（わける）｜N3

- 品詞：動詞・下一段
- 意味：一緒になっているものを、別々の役割やまとまりにすること。
- 連語：役割を分ける / 処理を分ける / 実行と検査を分ける
- 記事文脈：実行と型検査、状態と操作者など、意味の異なるものの役割を説明します。
- 例文：実行と型検査を分けても、検査が先に終わる順序は守ります。
- 例文の意味：処理を別々にしても、確認してから動かす順番は保つという意味です。
- ニュアンス：障害原因を絞る「切り分ける」より広く、役割を別にする意味です。

### 4. 並べる（ならべる）｜N5/N4

- 品詞：動詞・下一段
- 意味：複数のものを、比較したり確認したりできるように置くこと。
- 連語：結果を並べる / 同じ入力を並べる / 指標を並べる
- 記事文脈：同じ入力に対する二つの実行結果を、比較画面で見比べる場面です。 学習参考レベルはN4です。
- 例文：同じ入力に対する結果を並べて、差を確認します。
- 例文の意味：入力をそろえたうえで、二つの結果を見比べるという意味です。
- ニュアンス：見比べやすくする動作であり、並べるだけで改善を証明するものではありません。

### 5. 外す（はずす）｜N3

- 品詞：動詞・五段
- 意味：付いていたものや含まれていたものを、その範囲から取り除くこと。
- 連語：依存から外す / 対象から外す / 設定を外す
- 記事文脈：移行後の実行と型検査を確かめてから、元の依存を除く場面です。
- 例文：型検査が残っていることを確かめてから、古い依存を外します。
- 例文の意味：必要な検査を保った状態で、使わなくなった依存を除くという意味です。
- ニュアンス：対象を除く他動詞です。予想や範囲から自然にずれる「外れる」と区別します。

### 6. いずれ（いずれ）｜N2

- 品詞：副詞
- 意味：今すぐではなくても、将来のある時点でそうなること。
- 連語：いずれ移行する / いずれ必要になる / いずれ確認する
- 記事文脈：TypeScriptを上げるなら、いつか実行方法を移す必要があるという文脈です。
- 例文：今は動いていても、いずれ移行が必要になります。
- 例文の意味：現時点で動くことと、将来もそのままでよいことは別だという意味です。
- ニュアンス：ここでは将来の時点を表します。「いずれも」の全部を指す用法とは分けます。

### 7. 直後（ちょくご）｜N2

- 品詞：名詞・副詞的用法
- 意味：ある動作や出来事が終わって、すぐ後の時点。
- 連語：操作の直後 / クリックした直後 / 変更の直後
- 記事文脈：操作を押してすぐ人を切り替える、手作業では再現しにくい条件を示します。
- 例文：クリックした直後に利用者を切り替え、競合を再現します。
- 例文の意味：二つの操作の間をほとんど空けずに、問題が起きる条件を試すという意味です。
- ニュアンス：後というだけでなく、時間をほとんど置かない点を強調します。

## C-2. IT/AI専門用語

1. **trigram（文字トリグラム）**：一文字ずつずらした三文字の並びで文字列を区切る方式。 日本語のキーワード検索では、二文字語を別に試す必要があります。

2. **Skill Registry（スキルレジストリ）**：エージェントの指示と補助ファイルを版として登録する仕組み。 記事ではMLflow 3.18.0の実験的な機能を試しています。

3. **paired evaluation（対応のある評価）**：同じ入力に対する二つの実行結果を対応させて比較する評価。 十二件のダミーデータの統計値を、そのまま業務へ広げられません。

4. **Promise queue（プロミスのキュー）**：前の非同期処理が終わってから、次の処理を始める順序制御。 記事で直列化しているのは、一つのクライアントの操作です。

5. **idle in transaction（トランザクション中のアイドル状態）**：トランザクションを終えず、次の命令を待っている接続の状態。 ロックを持っていても、実行中のクエリとして負荷に出ない場合があります。

6. **pg_blocking_pids()（ブロック元PIDの取得関数）**：指定した接続を待たせているバックエンドの識別番号を返す関数。 接続の状態と一緒に見て、待機の関係をたどります。

7. **type checking（型検査）**：値や式が型の規則に合うか確かめる検査。 記事では検査と実行を別にして、失敗時に実行へ進まないようにつなげています。
