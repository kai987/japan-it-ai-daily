### 1. クラウドAIに貼るログから機密を自動で伏せる仕組みをPythonで作った話（ユーザー名はwhoamiで）

**原文：** https://zenn.dev/bpf/articles/ca75c3bd9356b9

**发布时间：** 2026-11-05 07:54:02 JST

作者把终端输出贴到云端助手询问故障，发现其中带有用户名、主机名及其他标识。后来加了一层本地转换，正则匹配可识别的敏感模式，再换成带类型的占位值。IP 和端口用原值的短哈希建立稳定标签，接收方仍能关联同一地址出现的多条记录。这种关联标记自身不能保证低熵地址无法被猜到。

工具将运行命令和输出写入原始日志，使用已处理行数定位增量，再把转换结果追加到可分享的日志。作者在 Suna 的真实输出上比对转换前后的差异，以便发现遗漏和误遮。试验是单机、人工复制粘贴场景，没有给出跨环境的脱敏覆盖率或自动泄漏测试结果。

账号更换后，硬编码旧用户名的规则悄悄失效。修改后从 whoami 获取当前账号并转义，再处理主目录、提示符和单词边界上的名字。局限在于执行者只能代表当前账号。多用户日志、未知凭据格式与原始文件的权限还要单独检查。

**阅读价值：** 这一案例适合说明日志脱敏如何兼顾排错线索与传输前检查。

### 2. AIエージェントの試行錯誤に「見た目が崩れていないか」の検査を組み込む 判定をLLMに任せない理由

**原文：** https://zenn.dev/miyanaga/articles/zenn-2026-11-05

**发布时间：** 2026-11-05 07:02:11 JST

在优化网页速度时，作者的团队用 Playwright Chromium 分别捕获改动前后的页面，再比较结果。此前曾由模型直接判断画面是否改变，作者观察到它会把一些重要副作用归为可接受误差。让代理每次更改后提交图片证据，可以让检查有可复查的输入。

同一个演示电商页面在两个时点也会产生差异。工具先控制截图条件，例如关闭 CSS 动画和过渡，固定时间与随机数，替换 IntersectionObserver 以触发延迟加载，并让主要轮播停在首屏。这些处理减少与代码改动无关的波动。

然后用像素热图定位发生变化的位置，再用 SSIM 判断整体结构相似程度。字体边缘的细小变化与布局错位可以结合两个指标复核。文章展示的是工具设计和演示，未公布通用阈值或对照误检率。需要判断键盘可达性、交互与动态状态时，仍需其他测试。

**阅读价值：** 可把截图条件、差异定位和结构评分拆成可复验的工程步骤。

### 3. 生成したCREATE TABLEを3つのDBに流したら、25パターン中16で失敗した

**原文：** https://zenn.dev/a1221/articles/ddl-builder-real-db-failures

**发布时间：** 2026-11-05 08:01:58 JST

这个 DDL 工具原先只确认输出包含主键字样。作者将生成结果送入 MariaDB 10.11、WASM 版 PostgreSQL PGlite 和 Node.js 22 的 SQLite，25 种样例中有 16 种在至少一种引擎失败。SQLite 试验启用外键检查，但建表阶段的行为与另两种引擎有差别。

JSON 数组被推成子表，递归却让子表先于父表生成，已有的外键列还可能重名或沿用固定整数类型。修改同时处理标识符冲突、父子创建次序和外键类型。依赖排序遇到环时，支持相应命令的方言将一条约束延迟添加，SQLite 继续写在建表定义中。

其他问题包括用保留词命名、把复合主键错误地声明成多个主键，以及把默认函数当字符串。修复后有 24 种在三套环境都通过，剩下的是把 PostgreSQL 专用函数交给 MySQL 方言。结果的边界是 MariaDB 兼容测试，MySQL 自身的某些默认值约束没有得到实机验证。

**阅读价值：** 三种数据库的实际执行结果，能帮助解释静态字符串断言漏掉了哪些错误。

### 4. AWS IoT Jobsで100台にファームウェア更新を配り、失敗・拒否・応答なしを混ぜたときの動きを確かめてみた

**原文：** https://dev.classmethod.jp/articles/hasuto-iot-jobs-100-devices-failures/

**发布时间：** 2026-11-04 22:42:14 JST

实验在东京区域模拟 100 个设备，每台使用独立证书和 MQTT 连接接收 Jobs 通知。作者模拟从 1.0.0 更新到 1.1.0 的状态报告，分别注入设备主动失败、工作前拒绝、开始后不回报以及完全不连接四种行为，未下载或刷写真正的固件。

作者设置了至少 30 台完成后达到 20% 失败才中止的条件。配合每分钟十台的限制时，有十个未开始的执行被取消。去掉限速后，通知在中止触发前已发完，最终 67 台成功、33 台失败，取消数为零。停止继续分发和让已经开工的端点停止，需要两条不同机制。

重试试验报告了 133 个执行记录，原因是每次重试为同一台设备创建新的执行编号。已进入执行中的设备才能开始计算超时，七个不连接的设备一直处于排队状态。对真实部署还需验证刷写、停止恢复、离线淘汰等条件，不能把模拟器回报当作固件验收。

**阅读价值：** 可以用同一个设备模拟实验解释取消策略、限速与设备状态的关系。

### 5. Amazon Athena の Iceberg テーブルへの同時 UPDATE で ICEBERG_COMMIT_ERROR になったクエリを再試行してみた

**原文：** https://dev.classmethod.jp/articles/athena-iceberg-update-commit-error-exponential-backoff/

**发布时间：** 2026-11-04 16:30:11 JST

作者在东京用 Athena 建了 1000 行 Iceberg 表，两个线程几乎同时将待处理订单改为已打包，查询覆盖的编号在 401 到 600 重叠。提交接口返回之后仍需轮询最终执行状态。实验中失败出现在 Iceberg 提交阶段，未重试的五轮都只有 600 行实际生效。

脚本只对识别出的提交冲突重新送出失败语句，采用带随机抖动的指数退避，并让 WHERE 只匹配仍待处理的订单。两批共十轮重试中有九轮最终达到千行。首批有一轮的错误消息字段为空而漏掉重试，后续改为也保留状态变更原因，并在消息空缺时用它分类。

后五轮的五条冲突都标记为 Retryable=false，但在该实验的条件下重新送出仍成功。因此重试应按明确错误类别与业务幂等性控制，同时记录无法分类的失败。实测针对两个重叠区间与单一状态转换，无法推断任意并发量或累加操作的成功率。

**阅读价值：** 使用最终写入行数作为验收，能防止把查询已接收当成更新完成。

### 4. AWS IoT Jobsで100台にファームウェア更新を配り、失敗・拒否・応答なしを混ぜたときの動きを確かめてみた

### 5. Amazon Athena の Iceberg テーブルへの同時 UPDATE で ICEBERG_COMMIT_ERROR になったクエリを再試行してみた

**面试问题：**

> Athenaで並列の更新が失敗したとき、どのように再試行しますか。

**约30秒回答：**

> まず実行結果を取り、アイスバーグの確定時の競合かを確認します。記事ではエラーの欄が空なら、状態が変わった理由も調べました。競合と分かれば、待ち時間にばらつきを入れ、失敗した更新だけを送り直します。すでに変えた行を条件から外して、最後は反映された行数を数えます。ただし、同じ処理を繰り返せない更新には、そのまま使えません。

**相关项目例：** 对并发批任务记录查询状态、重试原因与业务行数。

**关键词：** ICEBERG_COMMIT_ERROR / StateChangeReason / 冪等性

## 4. 技术主题：用独立证据验收自动化结果

给自动化建立独立可观测的验收面。页面改动要用同条件截图验证，SQL 生成要用实际数据库执行，日志脱敏要保留转换前后的本地对照。验收对象不同，证据也不同。

远端接收请求之后还要追到最终状态。设备任务按端点和尝试次数计数，数据更新按错误类别决定是否重试，并在结果端核对行数。保留能解释异常的状态和证据，恢复时就能从确切失败点继续。
