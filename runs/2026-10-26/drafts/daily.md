### 1. Azure OpenAI で Decisions API が一般提供（GA）されたので早速試してみた

**原文：** https://dev.classmethod.jp/articles/azure-openai-decisions-api-ga/

**发布时间：** 2026-10-25 21:06:53 JST

Decisions API适合答案空间已经确定的业务：例如在几个部门中选择一个，或判断是否符合某个条件。它不先生成一段自由文本再让应用解析，而是按预设类型返回结果。predicate给出条件成立的概率；choice返回一个候选值及各候选概率、confidence；score则计算有顺序的等级编号的概率加权平均。因而1.08这样的分值不是离散的“第一级”，更不直接等于业务审批结论。原文展示的是Azure OpenAI资源上的调用，与名字近似的Microsoft-Decision-1不是同一个服务入口和模型。

验证环境是eastus的gpt-6-luna部署、Microsoft Entra ID认证，以及日本Mac上的curl计时。作者对一条键盘故障、要求退换货的文本，同时提出三类问题；另用一张960×640的犬照片提出图像问题。正文明确表示两种请求各重复三次，因此不能把导语的“一次调用”理解成整个实验只请求过一次。文本使用477个输入Token，耗时约2.05、1.61、1.40秒；图片请求为1207个输入Token，约5.53、2.42、2.79秒。这些耗时包含跨区域网络，不能作为接口延迟承诺。

具体结果比“可以分类”更有学习价值：文本被分到产品不良对应的部门，三次选择相同，但choice的confidence仍在0.96与0.95之间变化。图片的犬、猫、项圈问题得到了明确结果，毛色却在作者认为黑色和茶色都说得通时，以0.99选了黑色。这里既没有带标准答案的大规模评测，也没有概率校准实验。重复稳定和高confidence都不能替代准确率；对含糊输入，应另外设计待确认状态或人工处理路径。

原文记录的Azure条件包括专用判定端点、gpt-6-luna、每次最多400个问题、128张且总计32MB的图片，并说明地域在逐步开放、East US 2不在当时支持范围。作者按文中输入单价与1美元150日元换算，文本和图片示例约为每次0.007及0.018日元；这是特定时间、特定请求的算例。正式采用时仍需确认当前地域、配额、价格和业务误判成本。面试可以借此解释：接口让返回形式可控，并不让判断的真实性自动变得可保证。

**阅读价值：** 从真实返回值理解类型、概率和业务结论的不同层次，能把分类接口设计与含糊输入的处理联系起来。

**规格补充：** [Microsoft Learn](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/decisions)

### 2. MCPのツール定義は軽くできる？Foundry Tool Searchを試した

**原文：** https://zenn.dev/kazu_aiengineer/articles/foundry-tool-search-ga

**发布时间：** 2026-10-26 03:50:29 JST

当MCP接入多个工具时，工具还没有真正被使用，名称、描述和参数定义就可能先占去大量输入。Foundry Tool Search将完整目录延后提供：模型最初只看见tool_search和call_tool，前者按能力检索候选，后者按名称调用已找到的工具。底层用BM25匹配工具名称、说明和参数信息，默认返回5项、上限10项。它减少的是起始时暴露的定义，而不是承诺整个任务只需更少Token。

作者在japaneast用azure-ai-projects 2.9.0创建Toolbox，将Microsoft Learn三项、DeepWiki三项、Web搜索和代码执行组成同样的八工具集合。测量时把取得的目录作为函数工具传给gpt-5.4-mini的全球标准部署，并没有运行Foundry Agent。初次输入重复三次，均从1193降到215 Token，定义JSON从14516缩到1462字符，初轮约少82%。官方建议的典型场景是超过10～15个工具，此处八工具属于较小例子。

若把观察范围扩展到回答完成，第一组总输入却从3722增至4934。无搜索版两轮结束，有搜索版需要查找、两次工具调用，合计四轮。第二组则从3844降至3257，且有搜索版的起始输入已变成392：之前调用的工具因自动固定到目录而保留下来，并在另一会话中也可见。两组数据不是同一初始状态的无限重复，也不能据此断言总是增量或总是节省；用户历史、自动固定与任务所需轮次都会改变比较条件。

另一个边界在检索语言。纯日文请求找不到只有英文元数据的工具，GitHub后面直接连上日文也可能漏检；补充additional_search_text之后，空格分词的日文能匹配，但带助词连写的形式仍失败。作者没有保存模型实际产生的搜索词，因此还没有证明完整Agent流程中的日文召回问题得到解决。总量测试各两次，也没有给出端到端速度和费用优势的充分结论。面试时应将初轮目录成本、检索是否命中、完成总量和使用后的目录状态分别测量。

**阅读价值：** 同一篇中既有初轮82%的下降，也有总输入上升的反例，适合训练不把局部指标当作端到端收益的工程判断。

**规格补充：** [Microsoft Learn](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/tool-search)

### 3. Next.js 16 で images.domains 廃止 — 3 アプリを remotePatterns に書き直す

**原文：** https://zenn.dev/cosoado/articles/nextjs16-images-domains-to-localpatterns

**发布时间：** 2026-10-26 09:14:07 JST

这篇的直接触发点是升级Next.js 16后出现图片配置弃用警告。虽然原始标题使用“廃止”，正文实际上描述images.domains的deprecation warning，并非证实该配置已经完全删除。官方文档仍说明该配置，并标注从14开始弃用。因此保留文章标题以便检索，但不沿用“已经移除”、错误的旧版本发布年份等说法。作者对SparMate、NetaPair、BoardLink三个应用进行的是配置迁移经验记录。

迁移的技术目的在于缩小图片优化服务能获取的URL范围。domains只有主机名粒度，不能限制协议、端口和路径；remotePatterns可把HTTPS、实际主机和业务所需路径组合起来。作者将GitHub头像与Google图片分别限制到所用的路径，却也曾用允许全部主机的通配配置消除警告。自查在push之前发现了这一点。警告消失只证明一种配置形式被接受，并不能证明允许范围没有扩大。官方文档明确旧domains不支持通配匹配，原文将旧配置星号与新配置全主机类比的部分，不能直接当作规格。

本地图像是另一个独立规则：带查询参数的本地URL经Image组件优化时，作者遇到需要localPatterns许可的错误。search为空字符串表示不允许查询字符串；省略search则允许该路径下任意查询参数。这两个状态不能混同。若业务可以固定参数，应尽量显式限定；若用户标识等参数确实可变，也应限定路径并审阅用途，而不是开放所有本地资源。原文提到ImageResponse生成OG图不经过Image组件，所以不能把两类图像生成路径一概视为受同一变化影响。

文章提供三应用配置修改与人工复查经历，但未展示覆盖所有禁止URL的回归执行证据。当前官方图片配置文档可用于核对规则，仍不等于我们已在这三个应用复现。实际工作宜先盘点来源，再用合法图像和不应通过的主机、路径、查询参数分别测试。对前端面试而言，这比只说“更新配置、运行build”更能说明图像可用性和来源约束是两套受入条件。

**阅读价值：** 保持Next.js与React求职方向的具体价值，能讲清图片来源限制、查询参数默认行为以及正反向回归用例。

**规格补充：** [Next.js Image公式資料](https://nextjs.org/docs/app/api-reference/components/image)

### 4. 事故ってサーバーを破壊させないためのリトライ設計

**原文：** https://zenn.dev/kaji_kaji/articles/retry-backoff-jitter-budget-measured

**发布时间：** 2026-10-26 09:00:12 JST

重试既可能挽救请求，也会把失败转成更多到达服务端的工作。作者用Ruby客户端和按固定概率返回500或503的练习服务器，先发送1000个请求、每个最多追加三次。失败率为50%时，成功率达到93.6%、实际到达1891次；失败率为90%时，成功率只有35.5%、到达却达3403次。模型服务器不会因负载继续恶化，因此这些数字展示请求放大，不能说已复现生产服务被压垮的过程。

指数退避将等待延长为100、200、400毫秒。在固定随机失败的50%条件下，成功95.1%、到达1844次，与立即重试接近，而结束耗时从约1.16秒变成151秒，因为等待并没有改变随机失败概率。换成100客户端同时发起、最初0.5秒全部失败而随后恢复的环境后，立即重试四次都耗在故障期，成功为0；退避把最后一次推迟到0.7秒后，100件全部成功。但两者到达次数仍都是400次，恢复成功和减少请求量并没有同时成立。

再对等待引入抖动，每种方式测试三次。Full jitter在每轮上限内随机，三段等待总和常落在恢复之前，成功只有100件中的16～31件。按前次等待动态决定范围的Decorrelated jitter成功95～97件，将50毫秒窗口内的峰值从100件压到约30～40件，总到达约340次；代价是全体到达结束约需1.15～1.35秒。随机化不是无条件提高成功率的按钮，分布、恢复时间与重试次数必须一起看。

最后增加“追加重试总数不超过最初请求量10%”的retry budget。永久故障下到达从400减至110次，成功仍是0；在另一次0.5秒短故障比较中，原本98～99件成功也降为0，因为仅有的十次额度在恢复前就耗尽了。该试验只发初始100件便停止，后续没有新请求补充预算，作者也明确没有验证持续流量场景。circuit breaker只列为参考，没有作为这次已实测的第四种对策。企业外部接口设计应分别确定成功、峰值、总量和等待目标，避免把有限批次结果直接推广。

**阅读价值：** 用反例解释退避、抖动与总预算各自改变什么，尤其保留负载减少却丧失成功机会这一取舍。

### 5. 外部LLMに原稿を送る前に、ローカルでマスキングする校正パイプラインを作った

**原文：** https://zenn.dev/yuu7/articles/llm-masking-proofread-pipeline

**发布时间：** 2026-10-26 09:48:21 JST

作者要把未公开原稿交给sarashina3-mini校正，但不愿同时外送链接、标识符等不参与语句校对的信息，因此把本地准备与外部发送拆成两个阶段。prepare完全不通信，将链接、特定格式密钥、作者名和Windows绝对路径替换为代用标记；重复链接共用同一标记，保持出现顺序，标题则仅替换URL以保留结构。恢复原值的对照表只留在本机的任务目录。这种对应关系使校正后的链接能够回填到原位置。

准备阶段产生真正要发送的JSON和对应SHA-256；人工完整查看后，批准的就是这个字节内容。send只有在当前内容哈希与批准值一致时才请求外部服务，密钥只从环境变量读取，响应里的标记也在本地恢复。这约束的是批准内容与发送对象的一致性，不能替代人对原稿能否外送的判断。即使对照表没有离开本机，剩余上下文仍可能泄露或使人推断敏感信息，不能声称获得了普遍匿名化保证。

为避免同一任务再次发送，程序在请求之前先写入试行记录，错误后也不自动重试。应保留这一实现选择，同时区分作者较强的表述与它实际能证明的范围：本地标记无法证明服务器已收件。标记写完但尚未发出、或者发出后丢失响应，都需要恢复时审慎判断；它们不会只因“先记再发”就变成可确认的送达。建立新任务重新发送也不是对旧任务未知结果的自动证明。这是依据处理顺序做的分析，不是原文额外测得的网络保障。

实用记录是一篇约6200字的内核问题报告，经过脱敏、一次发送、恢复完成一轮；配置的输入上限是12000字。更多字数、其他文体和漏检率没有得到实验验证。面试可从这例说明如何减少外部披露、如何检测批准后的内容变动，以及为何对结果不明的发送不宜自动重放。其效果与重试文章并不矛盾：查询重试和未公开材料的再披露，承担的是不同的重复代价。

**阅读价值：** 把“AI隐私”转为可检查的加工、批准、发送、恢复步骤，并明确可逆替换无法消除语义推断或送达不明。

### 1. Azure OpenAI で Decisions API が一般提供（GA）されたので早速試してみた

**面试问题：**

> 業務の振り分けにAIの判定APIを使う場合、何を先に決め、どう確かめますか。

**约30秒回答：**

> 自由文を後から解析する代わりに、判定の型を先に決めます。Decisions APIのchoiceは部署の選択肢を返し、scoreは順序付き段階の確率加重平均を返します。ただし犬の毛色には迷う入力でも高い確信度が付きました。三回同じ結果でも正解率の保証にはならないため、曖昧な業務例を集め、人へ戻す条件も設けます。

**相关项目例：** 练习例：以可公开的模拟工单定义部门候选和待确认状态，分别检查类型正确、分类正确以及人工接管条件；不把作者的数次调用当作精度基准。

**关键词：** Decisions API / choiceとscore / 確信度と正解率

### 2. MCPのツール定義は軽くできる？Foundry Tool Searchを試した

**面试问题：**

> ツールの定義を検索して渡す方式の効果を、どう評価しますか。

**约30秒回答：**

> 最初の要求と、回答し終えるまでの合計を分けます。Foundry Tool Searchは一覧をtool_searchとcall_toolに置き換え、八ツールの例では入力が1193から215に減りました。ただし検索の往復で合計が増えた回もあります。日本語の検索漏れと自動ピン留めによる次回の一覧も確認し、毎回軽くなると決め付けません。

**相关项目例：** 练习例：固定一组工具和中日文依赖任务，比较未使用与使用后的目录；保留模型真实搜索词、漏检、调用轮次和完成总输入。

**关键词：** tool_searchとcall_tool / BM25 / 自動ピン留め

## 4. 技术主题：在执行之前确定可选范围

把五篇放在一起，值得练习的是在执行之前明确可选范围：判定接口定义返回类型，工具目录只暴露需要的能力，图片优化限制来源，重试限制追加量，外部校正只接受已经批准的内容。它们分别作用于输出结构、上下文、资源获取、负载和披露对象。不能因为都在“限制”，就把其中一种边界当作另一种保障。这里是依据原文作出的工程分析。

收益与代价也要逐层衡量。延后加载工具定义可缩小初始输入，却增加发现工具的来回；退避和抖动可等到恢复或分散峰值，也可能延迟结束或提前耗尽机会。缩小图像URL范围要维护实际来源清单，本地脱敏要维护对应表并承担人工审查成本。明确选择边界的收益，是让多余工作和披露减少；其代价是更多条件、状态和拒绝路径需要维护。

验收应针对每种机制各自的证据：正解样本检验分类而非只看confidence；同一初始状态下记录工具调用到完成的总量；合法与非法图像分别测试；随机失败与恢复型故障分别注入；发送对象匹配批准哈希后仍审查上下文隐私。尤其要防止把局部“下降82%”推广成端到端降费，或把本地发送试行标记推广成远端送达证明。

面向日本企业面试，可用客户支持系统作教学设想，解释如何定义部门候选、图片来源、允许外送的信息和重试规则，再说明含糊分类、取图拒绝、预算耗尽、发送结果不明时的人工路径。练习的核心是让例外有明确去处，而不是再叠一层通用的AI运营术语。这是学习用设计，并不声称原文已经共同验证了一套生产系统。

### 1. 排除する（はいじょする）｜N1

- 词性：動詞・サ変（他動詞）
- 含义：排除、去除不需要或重复的事物
- 搭配：重複を排除する / 不要な経路を排除する / 競合を排除する
- 文章语境：脱敏阶段将同一链接对应到同一个代用标记，排除的是对应记录的重复，不是删除原稿中所有重复出现的位置。
- 例句：対応表の重複を排除し、同じリンクには同じ代替記号を使います。
- 例句含义：去除对照表中的重复记录，对同一链接使用同一代用标记。
- 辨析：「除外」偏向从候选范围中不选入；「排除」更强调移去不需要的因素。这里保留「排除する」的动词用法。

### 2. 回復する（かいふくする）｜N3

- 词性：動詞・サ変（自動詞）
- 含义：从异常或受损状态恢复
- 搭配：障害から回復する / サービスが回復する / 回復を待つ
- 文章语境：重试试验让服务最初0.5秒失败、随后恢复；等待的意义取决于服务是否真的随时间恢复。
- 例句：サービスが回復した後に送れるよう、再試行の枠を残しておきます。
- 例句含义：为能在服务恢复后发送，事先保留一些重试额度。
- 辨析：这里是服务状态恢复的自动词用法，不等于提高原本正常状态的性能；参考等级保留N3。

### 3. 警告（けいこく）｜N3

- 词性：名詞・サ変
- 含义：警告、提醒危险或应注意的问题
- 搭配：非推奨の警告 / 警告を確認する / 警告が消える

- 辨析：警告可能提示仍可运行但应迁移的用法；与使处理直接失败的错误不同。保留N3等级。

## C-2. IT/AI专业词汇

1. **Typed answers（型付きの判定結果）**：按事先定义的类型返回判断结果。 原文的三种类型分别表达条件概率、候选选择与有序分值。

2. **Confidence（確信度）**：接口返回的确信程度字段，不等于经过校准的整体准确率。 犬的模糊毛色被以高置信度归类，作者保留疑问。

3. **BM25（語の一致を使う順位付け）**：利用词频、逆文档频率和长度等信息为匹配候选排序。 Tool Search以工具名、说明、参数元数据匹配能力需求。

4. **Auto-pinning（ツールの自動固定）**：把调用过的工具留在模型可见目录中的机制。 第二次测量起始输入变成392，不能与未使用目录视为同一状态。

5. **remotePatterns（外部画像の取得条件）**：按协议、主机、路径等限定可优化的外部图片。 不能通过允许所有主机来完成名义上的迁移。

6. **localPatterns（ローカル画像の取得条件）**：限定本地图片路径及其查询字符串。 search为空与省略具有不同的允许范围。

7. **Decorrelated jitter（前回の待ちを用いるばらつき）**：按上次等待决定随机范围的重试等待方式。 实验降低同时到达峰值，但整体完成变慢。

8. **Retry budget（再送の全体予算）**：为整体追加重试数量设置上限。 原文设初始数量的10%，有限批次可能在恢复前耗尽。

9. **SHA-256（承認内容の同一性を確かめるハッシュ）**：以哈希确认实际发送内容与批准内容是否一致。 不能用哈希匹配代替敏感信息判断或服务器收件确认。
