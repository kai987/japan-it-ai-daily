### 1. 自社AIエージェントの「教育ロジック」をOSSにした - AIに「何年住みますか？」と聞き返させるまで

**原文：** https://zenn.dev/asahi_terass/articles/7266e919b4648a

**发布时间：** 2026-10-29 09:55:48 JST

企业咨询AI答非所问，有时不是算不出，而是在条件不足时就开始比较。TERASS这篇开发记录把“先确认什么”做成可维护的工程资产：先问居住年限，租买比较采用同等住宅的市场租金，信息缺失时暂不下结论。本文关注业务判断顺序如何落地，不把其中的住宅方案改写成面向读者的购买建议。

它把原則、指示、数值前提和失败用例分开管理。约190项数值放在YAML，短版材料与README从同一原本生成；每个PR重新生成，出现未提交差分就让CI失败，短版另有7,000字上限。这样修正规则时，不必依赖人工同时修改三份说明。Python计算引擎还复算文中约30项数字，发现并修正了五处文章侧错误。能复算只证明实现与所列前提一致，不能替前提本身背书。

评估条件是11个问题、3个模型、每种条件各重复3次，即每模型每条件33个回答。作者报告整体合格率从24%到84%，按失败结果修改后到90%。这里“合格”是未触及对应NG项，不是所有业务判断都正确。评分模型看不到被评模型名及是否带框架；评分引用须在回答中真实存在，预检的32个坏答案仍漏判1个。文章还采用按问题重采样的区间。应同时保留这些防偏措施和限制：修正规则后又在同一组问题上评估，不能当作未见咨询的独立泛化证据。

MCP部分不只是多个计算器。它用咨询开始、事实更新、条件试算和发送前自检组织流程，诊断附带“哪些条件会改变结论”和下一条问题。服务器不保存咨询内容，而把压缩状态放进来回传递的咨询ID；该ID仍是外部输入，所以检查长度、解压后大小和字段，并设置每来源每分钟60次的限制。无状态减少数据库依赖，却没有免除输入校验与资源上限。

小模型在修正后仍会一次抛出多个问题，说明流程约束不是写进提示词就自动落实。某模型33次全过也不能推广为咨询准确率100%。可迁移到日本企业面试的重点，是把业务失败案例、条件确认、材料更新、评估器自身错误分别变成能追踪的对象，再用未参与调优的问题检查。

**阅读价值：** 能把提示词维护、业务评估与MCP输入边界连成具体的工程解释。

### 2. Intl.Segmenterで見た目通りの文字数を正確にカウントする

**原文：** https://zenn.dev/ushi_osushi/articles/intl-segmenter-grapheme-count

**发布时间：** 2026-10-29 08:00:05 JST

同一段输入在“长度”上可以有多个正确答案：JavaScript的length统计UTF-16代码单元，展开字符串统计代码点，而用户想知道的往往是看起来有几个字符。原文用家庭表情说明差别：length为11，展开后为7，按书写素簇分段才是1。简单的笑脸表情可以靠展开解决，组合附加符号和ZWJ连接序列却不能因此一并解决。

Intl.Segmenter可选择grapheme粒度，即面向这种字符边界的书写素簇。带重音的字母既能用单代码点表示，也能拆成基本字母和组合符，显示相同而代码单元数不同。日本国旗等例子也可分成一个簇。文章是基于这些示例的API用法说明，没有给出处理速度或多端性能对比。

输入事件频繁触发时，作者建议在函数外创建分段器并复用实例。还要把浏览器实际能力与TypeScript类型定义区分：运行环境支持不代表工程的lib配置已包含类型，现行主流浏览器支持也不能代表每台旧设备。进一步用于表单时，可以把显示字数与服务端存储字节上限分别验证；这是从字符单位差别推导的设计应用，不能把该API描述成字节计数工具。

**阅读价值：** 适合React、Next.js等前端面试，能从用户可见规格讲到Unicode与运行环境。

### 3. Lambda の再帰ループ検出が EventBridge の新しい Custom Event Bus に対応したので試してみた

**原文：** https://dev.classmethod.jp/articles/lambda-recursive-loop-detection-eventbridge-custom-bus/

**发布时间：** 2026-10-28 14:11:58 JST

这篇东京区域的实测，价值在于证明“EventBridge已支持”不能省略资源代际。新Custom Event Bus以订阅者配送，Classic及默认事件总线以规则和目标组织；CloudFormation类型分别是AWS::EventsV2::EventBus与AWS::Events::EventBus。作者让Lambda收到事件后向同一总线重新发布，主动制造有自设终点的循环，比较哪些配置会被平台阻止。

环境使用Python 3.13；运行时自带的boto3 1.42.97缺少eventbridgev2客户端，因此加上1.43.118的层。实验把批量设为1，分别使用EVENT异步调用及REQUEST_RESPONSE同步调用，并在30跳主动结束，避免检测未生效就无限继续。我们没有执行文中的云端创建或循环命令，下面的数值均为作者报告。

新总线两种调用都在第16跳代码执行后停止，第17次在函数执行前被挡住。异步情况下，失效目的地SQS收到包含原事件的记录，条件为RecursiveInvocation，RecursiveInvocationsDropped记为1。同步情况下，订阅者另有2次重试，遮断指标因此为3；失败记录提供事件ID等元信息，不带原始事件正文。排查时需要同时看调用方式、重试策略和失败目的地，而不是把指标3理解成三个不同业务事件。

Classic与默认总线一直运行到作者的30跳上限，即使追踪值继续增长也没有阻止。新总线若在函数层允许递归，同样会运行到这个自设上限。Health通知约三小时后才到，不能代替即时监控。复用到项目时，应确认资源类型、SDK和函数配置，并保留调用量、并发与异常告警；该测试不是所有事件源都受到保护的保证。

**阅读价值：** 能在面试中把功能声明拆成资源、依赖版本、重试和可观测结果。

### 4. 不具合の知見を、次のレビューへ —— レビュー観点を蓄積・活用する3層構造の運用

**原文：** https://tech.smarthr.jp/entry/2026/10/28/112702

**发布时间：** 2026-10-28 11:27:02 JST

SmartHR面对的问题不是缺少检查清单，而是事故复盘积累的知识没有稳定回到后续评审；如果全塞进AI输入，又会挤占上下文并引入不相关检查。其方案把知识保存与每次加载拆开，目标是保留过去的失败经验，同时只在适当场景带入。

三层中，Universal每次全部参照；Bug-driven保存从不具合提炼的风险，只加载相关内容；Archived退出日常AI参照但不删除历史。Bug-driven还拆成轻量元数据索引与详细正文：先按“功能领域”和“检查视角”两个标签筛选，再读取选中的正文。这与先读全库再决定不看什么有本质区别。原文把长标签、长半角字符串造成的界面问题，提炼为可以跨功能复用的“长文本显示”观点评审。

月度运维包含新增、更新复发次数和盘点。累计复发3次以上可升入Universal，6个月无复发则归档；可由测试防住的事故不必等月会，归档后再发也可回到Bug-driven。同一问题反复出现时，还要审视表述和是否真正被引用，不能只累加计数。

文章说初期已有AI在测试用例评审时指出长文本显示风险的正向感受，但没有给出准确率、耗时或上下文成本的量化实验。作者也指出归档规则的反例：不再发生可能恰恰是检查有效，贸然移出日常参照会带来复发。以引用程度和效果补充归档判定仍在考虑中。因此三次、六个月是该团队的运维规则，不是可直接套用到所有日本团队的标准。

**阅读价值：** 适合解释AI代码评审的上下文组织，以及如何让事故经验持续发挥作用。

### 5. 5.5 KB の DXF が 1 億本の線に展開される：ブラウザの DXF ビューアを固まらせない上限の数え方

**原文：** https://zenn.dev/openedfile/articles/dxf-viewer-work-budget

**发布时间：** 2026-10-29 08:00:05 JST

DXF是图形交换格式，其中的块可以重复引用、成阵列放置及相互嵌套。作者自制的5.5 KB样本把十条基础线逐层扩大十倍，最终可展开为一亿条线。因此限制上传文件大小，甚至把解析移到Web Worker，都不足以保证页面可用：展开内存、生成中间数组和主线程绘制还有各自的开销。

最初只统计最终接受的图形，会漏掉没有可画内容的展开、临时边界点、最后为空的文字格式，以及造出来后才拒绝的副本。作者把资源记账移到创建前，统一扣除工作预算，丢弃也不退还；访问图形和展开块本身也要计数。这里的“扣除”是本机预算，不是云费用。800万工作单位的条件下，最初样本在约248万条线、Node端1.6秒时停止；这些是作者特定环境的实验数值。

主线程把线分成每块1,024段等有限单元，在约20 ms后交出控制权。但canvas命令可以先排队、晚些时候才真正栅格化，只测调用耗时会低估阻塞。原文曾在短时间排入约44万条线，随后读一个像素就用了1.7秒。于是每一步通过getImageData读回一像素，把实际绘制推进到可观测的边界再计时。这是有额外成本的特定实现取舍，不应推广为所有canvas都能无代价加速的方法。

印刷也出现另一种放大：26 MB、约19.6万个文字元素的SVG，令Chromium渲染进程从81 MB增至1.9 GB。元素数和文件体积并未约束实际内存，作者改用按元素种类校准的估算并设400 MB上限；复杂填充则按扫描行跨越的边数估算工作量，过重时只显示轮廓，并把降级告诉用户。

边界必须和结果一起保留：44个自制样本、34张实际图纸并不覆盖全部DXF，校准只在Chromium，Firefox和Safari未测；不再卡死也不等于快，复杂星形图在特定重画条件仍需57秒。预算耗尽会部分绘制。对前端项目有用的经验，是把展开、拒绝前开销、真实绘制时间、内存和显示完整性分别验收，而不是把“页面还能点”当成全图已正确显示。

**阅读价值：** 提供了浏览器性能面试中少见的具体反例：限制的量必须接近真正消耗的资源。

### 1. 自社AIエージェントの「教育ロジック」をOSSにした - AIに「何年住みますか？」と聞き返させるまで

**面试问题：**

> 業務AIに判断手順を教えた効果を、どう確かめますか。

**约30秒回答：**

> 業務で誤る判断を先にケース化します。TERASSの住宅相談では、居住年数を先に聞く手順と、同等物件の家賃を使う条件を明示しました。評価は十一問を三モデルで各三回試し、採点根拠の引用も照合しています。ただし同じ問題で直した結果なので、未使用の相談でも確認し、合格率を相談全体の正しさとは扱いません。

**相关项目例：** 为申请辅助AI制作条件缺失用例，要求逐项确认；独立记录评分器漏判。这是学习项目设想，不是已实装成果。

**关键词：** 確認順序 / 採点根拠 / 状態の入力検証

### 2. Intl.Segmenterで見た目通りの文字数を正確にカウントする

**面试问题：**

> 入力フォームの文字数を、利用者の見た目に合わせるにはどうしますか。

**约30秒回答：**

> 画面で一文字と数える単位を、仕様として決めます。lengthはUTF-16のコード単位なので、家族の絵文字は十一になります。スプレッド構文でも七ですが、Intl.Segmenterのgraphemeなら一です。入力欄では分割器を使い回し、旧ブラウザと型定義も確認します。ただし、保存容量のバイト上限は別に検証します。

**相关项目例：** 制作个人介绍输入框，显示书写素剩余数，同时单独校验存储容量。

**关键词：** UTF-16 / 書記素クラスタ / Intl.Segmenter

### 3. Lambda の再帰ループ検出が EventBridge の新しい Custom Event Bus に対応したので試してみた

**面试问题：**

> イベント連携の再帰防止を、サービス名だけで判断してよいですか。

**约30秒回答：**

> EventBridgeという名前だけで、検出対象とは判断しません。記事の東京リージョンの検証では、新しいCustom Event Busは十六ホップで止まり、Classicは三十回の独自上限まで続きました。同期配信では再試行二回により、遮断件数は三件です。バスの世代、SDKと失敗時の送信先を確認し、呼び出し回数の監視も残します。

**相关项目例：** 为隔离的事件连携实验加上自设跳数上限与失败队列，对比重试前后的遮断数量。

**关键词：** Custom Event Bus / 再試行 / 遮断メトリクス

### 4. 不具合の知見を、次のレビューへ —— レビュー観点を蓄積・活用する3層構造の運用

**面试问题：**

> 不具合の知見をAIレビューへ渡すとき、何を工夫しますか。

**约30秒回答：**

> 観点の蓄積と、毎回読ませる範囲を分けます。SmartHRはUniversal層を常時参照し、Bug-driven層は機能領域と観点のタグで絞ってから本文を読みます。Archived層には履歴を残します。ただし、六か月再発しない理由が対策の効果かもしれません。参照から外す前に有効性を確かめ、再発時に戻せる運用にします。

**相关项目例：** 从缺陷台账提炼检查观点，以功能与风险标签选取材料，并保留撤出日常参照后的恢复路径。

**关键词：** 三層の参照 / メタデータの絞り込み / 再発と効果

### 5. 5.5 KB の DXF が 1 億本の線に展開される：ブラウザの DXF ビューアを固まらせない上限の数え方

**面试问题：**

> ブラウザで外部の図面を開く際、どの上限を設けますか。

**约30秒回答：**

> ファイル容量ではなく、展開と描画の仕事量を制限します。DXFの入れ子は五・五キロバイトでも一億本に増えます。記事では作る前に予算を消費し、捨てた写しの分も戻しません。canvasは後で描くため、一画素の読み出しまで測ります。ただし較正はChromiumだけなので、他のブラウザでの時間や部分描画も確認します。

**相关项目例：** 制作本地文件预览，加入创建前预算、分帧绘制和部分结果提示，在实机测阻塞而非只测函数返回。

**关键词：** 作成前の予算 / 描画の完了計測 / 部分表示の通知

## 4. 技术主题：让计量单位与目标一致，在工作前检查边界

今天五篇文章可以放在同一个设计问题下理解：指标是否真的约束了目标。NG合格率只对应所列失败规则，length数的是代码单元，DXF文件大小又不代表展开工作量。先确定需要保护的判断或用户体验，再决定单位及失败条件，比单独寻找一个“高分”更实用。

落实时则要在开始工作之前缩小输入或检查边界。SmartHR先查标签索引再读详细材料，DXF先扣资源预算再建图形；Lambda递归保护还得确认实际使用的新总线与SDK。它们是不同系统中的相似设计思路，并非一个组件就能统一解决的产品承诺。

对日本企业的业务AI和前端开发，可以从少量真实失败案例做起：写明不足条件、资源上限和停止通知，随后用未参与调优的输入验收。这样便于解释取舍，但上限可能牺牲完整性，分帧也可能延长总完成时间。单一团队、单一浏览器的结果仍需要在实际部署环境复核。

## 5. 面试复习卡

**回答要点：** NG合格率、UTF-16代码单元数和DXF文件大小，分别不是咨询整体正确率、可见字符数和展开资源量。先定义实际目标、单位与观测边界。

### Q3

**回答要点：** 保留事件总线代际、SDK、重试条件，以及QA归档反例、浏览器校准范围。另测实际环境中的失败、未见输入与降级结果，不把单环境数字设为通用保证。

### 1. 寄せる（よせる）｜N2

- 词性：動詞・一段（他動詞）

- 搭配：作成時点に寄せる / 処理を一か所に寄せる

### 2. 固まる（かたまる）｜N2

## C-2. IT/AI专业词汇

1. **evaluation harness（評価の実行枠組み）**：组织问题执行、评分和结果记录的评估程序。 11问、3模型、各3次的结果须保留评分口径。

2. **stateless MCP（状態をサーバーへ保存しないMCP）**：由来回传递的数据携带状态，不靠服务端会话库维持咨询。 仍要校验ID及解压后的资源量。

3. **grapheme cluster（書記素クラスタ）**：把基本字符和附加符等视作一个可见字符单位的边界。 家庭表情的11个代码单元可成为1个簇。

4. **UTF-16 code unit（UTF-16のコード単位）**：JavaScript字符串length统计的单位。 不能与代码点或存储字节数混同。

5. **RecursiveInvocationsDropped（再帰による呼び出し遮断の指標）**：Lambda拒绝递归调用的计数指标。 同步实验有两次重试，因此计为3。

6. **metadata-first retrieval（メタデータによる事前の絞り込み）**：先用轻量标签等元信息筛选，再加载相关正文的设计。 这里是对SmartHR实现的说明性命名，不是原文产品名。

7. **work budget（作業量の予算）**：对展开、创建及遍历等工作消耗设定上限。 在创建前扣除，被拒的数据也不退还。

8. **getImageData（canvasの画素の読み出し）**：从canvas读取指定区域像素的接口。 原文用单像素读回观察此前实际绘制开销。
