### 1. Claude Code v2.1.294〜v2.1.295 の主要アップデート - hooks の onFailure: "block" 追加と OSC 7501 対応

**原文：** https://dev.classmethod.jp/articles/20261009-cc-updates-v2-1-295/

**公開時刻：** 2026-10-09 13:34:59 JST

**背景と対象。** 著者は10月8日に公開された Claude Code 2.1.294 と2.1.295を整理しています。中心は、権限やポリシーを判断するフック自体が故障した際、操作を続けるか止めるかです。command／HTTP フックの `onFailure: "block"` は故障時の扱いを選ぶ仕組みであり、チェック内容があらゆる危険を検出するという保証ではありません。

**仕組み。** 多くのフックイベントでは、標準出力が空のまま終了コード1を返しても、非ブロッキングエラーとして処理が続くと原文は説明します。`onFailure: "block"` は `type` や `command` と同じ階層に置き、起動失敗、時間切れ、想定外の終了コードで操作を通さない設定です。ただし、執筆時点の hooks 公式ページにはこの項目がまだ掲載されていないという文書上の境界も示されています。

**検証条件。** プロジェクト設定のない空の作業ディレクトリで、`UserPromptSubmit` に `exit 1` だけの command フックを登録した二つの設定を用意します。違いは onFailure の有無です。`claude -p` に1ターンの上限を付け、project 設定のみと厳格な MCP 設定を選び、OKだけを返すよう求めます。ユーザー設定のフックなどの混入を避ける条件で、HTTP フックや起動失敗、時間切れの試験ではありません。

**結果と運用上の読み方。** 指定なしでは OK が返り、block 指定時はブロックのメッセージが出て回答は返りませんでした。一方、どちらも本体の終了コードは0です。自動化では終了コードだけでプロンプトの実行を判定できず、ブロック情報と期待した応答を確かめる必要があります。プロセスの終了、チェックの成立、対象操作の完了を分けるのは、この結果を実務へ応用する整理です。フックの不具合でも止まるため、原因を追える記録が必要です。

**関連変更と限界。** OSC 7501 は対応する端末で作業中・応答待ち・完了を表示します。端末側の対応が条件です。指示文で書いた prompt／agent フック、ツール制限、mod に渡る入力の切り詰めなどの修正も列挙され、context-1m beta を拒否する環境では beta 指定なしで再送する変更もあります。これらをすべて著者の実測結果とは扱いません。直接比較されたのは `exit 1` のケースだけで、起動失敗や時間切れは確認されていません。

**読む価値：** 安全確認の故障時の扱いと、処理の終了・操作の成立を分ける考え方を学べます。

### 2. Claude Sonnet 5.5 で cache read 価格が半額に改定、値下げ効果を実測してみた

**原文：** https://dev.classmethod.jp/articles/bedrock-sonnet-5-5-cache-read-price-cut/

**公開時刻：** 2026-10-09 19:59:43 JST

**背景と価格の範囲。** 著者は Amazon Bedrock の Sonnet 5.5 の cache read 改定を確認し、Converse API で会話を実行しました。us-east-1 の Price List API による単価では、Global の読み取りは100万トークンあたり0.20ドルから0.10ドル、Geo は0.22ドルから0.11ドルです。通常入力、出力、キャッシュ書き込みは別の費目です。読み取りの半額化を、リクエスト全体の半額化とは読みません。

**キャッシュの仕組み。** 先頭から同じ内容が続き、tools→system→messages の順でチェックポイントが処理されます。前段の変更は後段にも影響します。最小のプレフィックスは Sonnet 5.5 が512トークン、Sonnet 5 が1024です。5分または1時間の TTL 内で再利用し、ヒットで期限が延びますが、1時間は書き込み単価が高くなります。今回は system と最新のユーザーメッセージの末尾に `cachePoint` を置いています。

**測定条件と記録。** 約1万6400トークンの固定文書を system に置き、その文書だけを根拠に3文以内の日本語で答えるよう指定します。短い日本語の20問を履歴を引き継いで順に送り、出力上限は300トークンです。us-east-1、Global Sonnet 5.5、AWS CLI、5分のキャッシュが条件です。2ターン目は読み取り16,433、書き込み246、通常入力4、出力300という usage が示され、実際に再利用された量を確かめられます。

**結果と比較対象。** 20ターンの合計は出力5,302、読み取り350,380、書き込み20,681、通常入力80トークンです。同じ使用量に旧・新単価を掛けると0.1750ドルから0.1399ドルとなり、約20%減でした。旧費用の40.1%を占める読み取り部分が半額になったためです。一方、キャッシュなしの別実行は0.7950ドルで、キャッシュありは約82%低い値です。20%は単価改定、82%は利用有無の比較です。初回は書き込みで高く、2ターン目の累計で逆転しました。

**限界と実務への応用。** 同じ題材の Sonnet 5 は0.1787ドルでしたが、出力数も異なるため、単価だけを変えた比較とは区別します。回答品質の統一採点、繰り返し実行の分布、独立した遅延の統計は示されていません。全業務で20%減る、品質も上がるとは言えません。短い会話、前段の変更、期限切れでは構成が変わります。実務では usage を通常入力・出力・読み取り・書き込みに分けて計算するのが、この記事からの応用です。

**読む価値：** 読み取り単価と会話全体の費用を区別し、比較の基準をそろえる練習になります。

### 3. return await は付けても付けなくても同じ？ try の中では catch と finally の動きが変わる

**原文：** https://qiita.com/ennagara128/items/6abdd7057d7b50dba194

**公開時刻：** 2026-10-09 13:22:32 JST

**背景と環境。** async 関数の末尾の `return await` は不要だという説明に対し、著者は Node.js 24.14.1 の `.mjs` で挙動を確かめています。try／catch の外では呼び出し元の値や拒否の結果は同じです。ただし、関数内での捕捉、finally の順番、デバッグ情報まで同一とは言えません。古い ESLint の no-return-await は非推奨で、記事は速度の優劣を計時して主張したものではありません。

**例外が生まれる場所。** `return fail()` は Promise を返すため、その拒否は関数内の try で投げられる例外になりません。`return await fail()` は await の場所で拒否を例外として受け止め、内側の catch が動きます。10ミリ秒後に拒否する例では、await ありは代替値を返し、なしは呼び出し元へ失敗が届きました。拒否済みの Promise や直ちに失敗する async 関数でも同様です。一方、普通の関数の同期的な throw は、その場の catch で拾えます。

**片付けの順番。** 10ミリ秒後に完了する Promise と配列の記録を使った比較では、await なしは finally→処理完了、ありは処理完了→finally です。保存中のボタンを finally で戻す場合、待たずに Promise を返すと通信前にボタンが押せる状態へ戻る可能性があります。これは記録された順番からの設計上の説明で、React の端末別試験や二重登録率の測定ではありません。

**スタックと静的検査。** inner が await null の後に失敗すると、await ありの外側の関数名がスタックに残りました。その待ちを消すと、どちらにも名前が出ます。存在しないファイルの読み取りでは差が出た一方、失敗する fetch では外側の名前はどちらにも出ませんでした。必ず差があるわけではありません。型情報を使う typescript-eslint の return-await は、in-try-catch と always で try の外の扱いが異なるため、目的に合う設定を選びます。

**限界と確認方法。** ESLint の説明は、仕様変更で余分なマイクロタスクがなくなり、スタックが読みやすくなる場合があるというものです。すべての処理の性能比較ではありません。AI が書いた関数を見る際は、その関数で失敗を扱うのか、後片付けをいつ行うのかを確認し、意図的な失敗で順番と代替値を試します。Node.js の版と fetch の反例を残し、全ブラウザや全I/Oで同じスタックになるとは広げません。

**読む価値：** 保存中の表示や例外処理について、書き方と実際の順番を結び付けて説明できます。

### 4. [アップデート] IAM Identity Center の Identity Store API にネットワーク制限をかけられるようになりました

**原文：** https://dev.classmethod.jp/articles/aws-identity-store-network-controls/

**公開時刻：** 2026-10-09 13:37:31 JST

**背景。** Identity Store は IAM Identity Center のユーザーやグループを保存し、Identity Store API は一覧取得や作成・更新・削除を行います。外部 IdP との同期には SCIM という別の経路があります。記事は両者の接続元ネットワーク制限を確認しました。当日のコンソールに設定項目が見当たらなかったため UpdateIdentityStore を使っています。これは当日の観察で、将来もコンソールで設定できないという断定ではありません。

**設定と例外。** VpceAccessRequired は VPC endpoint の必須化、ApiRestrictSourceVpcs は API を許可する VPC、ApiAllowSourceIps は API の接続元CIDR、ScimAllowSourceIps は同期側のCIDRです。重要なのは `ApiAllowSourceIps` が例外である点です。許可IPからは、endpoint や VPC に関する他の API ネットワーク制限を満たさなくても通せます。公式記述も照合しました。すべての条件の交差とは解釈せず、ネットワーク通過と IAM 権限付与も分けます。

**確認した条件と結果。** Organizations の管理アカウント、us-east-1 で describe を実行し、初期値 VpceAccessRequired=false を確認します。true に変更して自分のパブリックIPを許可し、反映を読み直しました。203.0.113.10/32 は例示用です。許可元の list-users は成功し、不許可元は AccessDeniedException で拒否され、リソースベースポリシーの明示的 deny が示されました。SCIM 同期を動かした測定ではありません。

**管理経路を失わない仕組み。** 自分のIPを外す更新は ValidationException になり、現在の呼び出し元がアクセスできなくなると示されます。呼び出し元IPを追加するか、対応する VPC endpoint 内から要求するよう案内されました。また、VpceAccessRequired=false のまま IP／VPC リストを指定する更新も拒否されました。無権限、設定の不整合、自分が解除できない変更を、結果の種類から区別できます。

**限界と実務での確認。** VPC endpoint の一連の疎通試験、全リージョン、SCIM の実際の許可・拒否ログは記事にありません。それらの成功は未確認として扱います。実務では例外IPの範囲と戻す経路を先に決め、許可元と不許可元を試します。外部IdPの出口と同期は別に確認します。これはフィールドの意味と API 実験からの提案であり、著者が接続全体を検証済みという意味ではありません。

**読む価値：** 許可リストの組み合わせと、管理経路を失わないためのエラーを具体的に説明できます。

### 5. AWS Lambdaで自前JSONログがINFO扱いになる仕様と対処法

**原文：** https://dev.classmethod.jp/articles/lambda-log-level-filtering-json-timestamp/

**公開時刻：** 2026-10-09 14:53:23 JST

**問題と設定。** 自前の JSON に level=error を書いているのに CloudWatch Logs に届かない経験から、著者は Lambda のログ判定を確認しました。ログ形式は JSON が前提で、アプリケーションとシステムのレベルは独立です。例は ApplicationLogLevel=WARN、SystemLogLevel=INFO です。managed runtime の初期形式はプレーンテキストなので、レベル設定だけで前提が満たされたとは考えません。

**出力方法の違い。** 対応する Python logging や Node.js console はランタイムがレベルを処理します。print や非対応のライブラリから stdout／stderr に自前の JSON を出す場合は構造をそろえます。原文と AWS の説明では、level が不正・欠落なら INFO、日時が有効な `RFC 3339` でない・欠落する場合も INFO にして日時を付けます。時間のキー名はランタイムの規則に従うため、すべての標準ロガーに同じ手書き項目を要求する話ではありません。

**見えなくなる仕組み。** 例の timestamp=1790000000 は数値の Unix 時間で、指定した形式ではありません。level=error でも INFO と判断され、WARN 以上の設定では CloudWatch へ送る前に破棄されます。受信されていない記録は、下流の ERROR フィルターやアラームでも検知できません。アラームだけを直しても解決しない段階です。有効な日時には日付・時刻・タイムゾーンを含め、原文には Z 付きの文字列が示されています。

**逆向きの問題。** 閾値が INFO の場合、除外したい debug も不正な日時によって INFO となり、転送される可能性があります。記録の欠損だけでなく量と費用が増える方向もあります。JSON 形式、level と日時、転送閾値、実際の受信、下流の検知の順に見るのは、この規則を調査へ応用する整理です。出力したという事実と、監視が受け取ったという事実を分けます。

**証拠の範囲。** ただし、記事は個人の障害経験、公式仕様、具体的な入力例を示しますが、全ケースの CloudWatch 実行ログ、反復回数、費用の統計は示していません。当方で再現した測定値や両側の転送率は追加しません。標準ロガーと自前 JSON を区別し、実際の組み合わせで正常・異常イベントを送り、監視で受信したことまで確認するのが実務上の判断です。

**読む価値：** 出力、解析、転送、監視を分け、なぜエラーが見えなくなるのかを具体的に追えます。

> 関数内で失敗を処理し、完了後に片付けたい場合は残します。記事では return await にすると、失敗をその関数の catch で拾え、finally も処理完了後に動きました。await なしでは、呼び出し元へ失敗が伝わり、片付けが先に走ります。保存中の表示などは成功時だけでなく失敗時の順番も確認します。ただし、スタック表示は処理によって違います。

**関連プロジェクト：** React／Next.js の保存処理、代替値、読み込み表示の制御に応用します。

**キーワード：** return await / catch / finally

### 4. [アップデート] IAM Identity Center の Identity Store API にネットワーク制限をかけられるようになりました

**面接質問：**

> ID管理APIのネットワーク制限で、何に注意しますか。

**約30秒回答：**

> 設定の組み合わせと、管理者が戻せる経路を確認します。記事の ApiAllowSourceIps は、許可したIPならVPC側の制限を通らずに使える例外です。自分のIPを外す変更は、ロックアウト防止で拒否されました。許可元と不許可元の両方で確かめ、外部のID同期は別に確認します。ただし、同期側の実測結果は未確認です。

**関連プロジェクト：** ID同期の接続元制限と、設定変更前後の疎通確認に応用します。

**キーワード：** ApiAllowSourceIps / VpceAccessRequired / SCIM

### 5. AWS Lambdaで自前JSONログがINFO扱いになる仕様と対処法

**面接質問：**

> エラーログを出したのに監視へ届かない場合、どう調べますか。

**約30秒回答：**

> 出力した文字列だけでなく、転送前の判定を調べます。記事では自前のJSONログにRFC 3339の日時がないと、error と書いてもINFO扱いになります。WARN以上の設定なら、そのログは監視先へ届きません。正しい日時と level をそろえ、実際の受信まで確認します。ただし、標準ロガーは扱いが違うので、使用する出力方法も確認します。

**関連プロジェクト：** Lambda のログ転送とアラームの受信確認に応用します。

**キーワード：** RFC 3339 / ApplicationLogLevel / CloudWatch Logs



## 4. 技術テーマ：状態が変わる場所で成立した結果を確かめる

共通点は製品名ではなく、入力やプロセスが正常でも、その先の結果まで成立したとは限らないことです。フックのexit 1が処理を止めず、本体のexit 0がブロックに対応する場合があります。Promiseを直接返すか内部で待つかでも、例外を扱う場所とfinallyの時点が変わります。外側の状態だけではなく、実際の結果を観察します。

クラウドにも異なる変換があります。cachePointによって使用量は通常入力・書き込み・読み取りに分かれ、費用は実測usageで計算します。許可IPの例外はIdentity Storeのネットワーク条件の関係を変えます。不正な日時はログをerrorからINFOにし、その後の閾値が受信の可否を決めます。どの段階で何を解釈するのか、個別に知る必要があります。

実務で試すなら、入力、判断規則、観察する出力、反例を対にします。フックの成功と故障、読み取りと書き込み、許可と拒否、Promiseの拒否と同期throw、有効と不正な日時です。これは読後の検証設計であり、新しいクラウド実験や遅延・品質の測定値を追加したものではありません。

## C-2. IT/AI専門用語
