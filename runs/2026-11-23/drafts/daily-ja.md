### 1. BigQuery Daya Engineering AgentのAgent Observabilityを試してみた

**原文：** https://dev.classmethod.jp/articles/bigquery-dea-agent-observability-ga/

**公開日時：** 2026-11-23 02:14:45 JST

BigQueryのData Engineering Agentでは、プロジェクトの監視設定を有効にすると、Cloud Monitoringでトークンやモデル遅延を、Cloud Traceでモデルとツールの実行を調べられます。東京の検証環境では同じ公開タクシーデータを使い、監視設定の前後でDataformのSQLX定義を作らせました。

監視前にもA2Aの依頼回数は取得できました。設定の有効化後は、agent_type=DEAの時系列が実行終了から約1分で現れ、SendStreamingMessageの下にcall_llmとexecute_toolを含む二つのトレースが記録されました。設計案の確認を待ったターンと、SQLXを書いてコンパイル・検証したターンを、それぞれ追えます。

二つのターンではSQLXの検証まで行い、テーブルの作成や定期実行は見送っています。集計で見えたモデル呼び出しは15件、会話履歴上は12件でした。この差だけで内訳の原因は確定できません。収集開始前のトークンは補われず、監視値を請求額へ直結させる公式の換算式も示されていません。検証の範囲は、一つの東京プロジェクトで同じ公開データを使った二条件です。

**読む価値：** 呼び出し数と遅さの原因を、集計とターン単位のトレースから別々に調べられます。

### 2. S3 Storage Lens がインテリジェント階層化ストレージクラスのアクセス階層別の内訳に対応したので確認してみた

**原文：** https://dev.classmethod.jp/articles/amazon-s3-storage-lens-intelligent-tiering-access-tiers/

**公開日時：** 2026-11-23 09:47:55 JST

S3 Storage Lensのアドバンスト階層では、Intelligent-Tieringのアクセス階層ごとにバイト数とオブジェクト数を確認できます。アカウントの全バケットを集計できる初期ダッシュボードで、三つのバージョニング済みバケットを調べた記事です。

設定して約31.5時間後、ストレージクラスの表やグラフで、有効化当日の内訳を確認できました。シンガポールの一つのバケットでは、高頻度アクセスが4個、Archive Instant Accessが1個でした。後者の1個は旧バージョンに当たり、バージョンを残す設定も集計の読み方に関係します。

有効化前の二日には、同じ階層別表示がなかったと報告されています。反映時間は一つの観測例です。さらに、復元が必要なのはArchive AccessとDeep Archive Accessで、今回のバケットのArchive Instant Accessとは読み分ける必要があります。観測の制約として、調べたのはアドバンスト階層に切り替えた一つのダッシュボードです。

**読む価値：** バージョンを保持するバケットで、見えている件数と復元が必要なデータ量を読み分けられます。

### 3. Azure Service Busの重複検出で二重処理は防げる？同じMessageIdの再送と再配信を試した

**原文：** https://dev.classmethod.jp/articles/azure-service-bus-duplicate-boundaries/

**公開日時：** 2026-11-22 23:58:30 JST

Azure Service Busの重複検出は、設定した時間窓に登録済みのMessageIdを覚えます。東日本のStandardキューで、パーティションを無効にし、重複検出窓を1分、受信ロック時間を30秒にして挙動を比較しました。

同じIDで2回送ると送信処理はどちらも成功し、キューの有効件数は1件でした。最初の受信を完了した後でも時間窓の中では同じIDが落とされ、窓を過ぎた送信は入りました。別操作のIDや、再送のたびに新しいIDを振った場合も受け付けられています。

PeekLockで受けた側が完了を通知せずに接続を閉じると、35秒待って再受信した時点で同じメッセージが届き、delivery_countは0から1に変わりました。閉じた瞬間にロックが解除されたかは調べていません。注文DBへの反映と受信の完了通知が異なる工程なら、再配信時にDB側で二重反映を防ぐ設計が要ります。ただし、プロセスの異常終了やネットワーク切断はこの実験の対象外です。

**読む価値：** 同じ送信IDの記憶期間と、処理途中の再配信を分けて考えられます。

### 4. CloudFormation StackSets の操作の進捗が ステージ別・リージョン別に確認可能になったので試してみた

**原文：** https://dev.classmethod.jp/articles/aws-cloudformation-stacksets-progress-visibility/

**公開日時：** 2026-11-23 00:02:07 JST

CloudFormation StackSetsの操作結果は、ステージとリージョンに分けて進捗を返します。検証したself-managed StackSetは一度に一つのリージョンを進める設定で、東京、バージニア北部、オレゴンへ順に配布しました。

約10秒おきに取得した結果は、スタックインスタンスが終わるごとに33.3%、66.6%、100.0%と更新されました。DNSで証明書を検証する間はしばらく0%でした。集計では三つのリージョンが同時にIN_PROGRESSと表示される時点もあり、実行と待機は別の取得で各インスタンスのDetailedStatusを見て判定しています。

別の二リージョン並列実験では、スタック内の三つのSNSトピックが作成済みでも、証明書が残っている間は0%でした。ここで集計している単位は個々のリソースでなくスタックインスタンスです。記事のself-managed構成ではRoleProvisioningの状態はNOT_APPLICABLEでした。

**読む価値：** 配布がどこまで終わったかと、個々のスタックが何を待っているかを順に調べられます。

### 5. Next.jsのストリーミングはLambda Web Functionsで動くか

**原文：** https://zenn.dev/ryota_09/articles/nextjs-suspense-streaming-lambda-web-functions

**公開日時：** 2026-11-22 11:30:19 JST

Next.jsのサーバー描画を載せたLambda Web Functionsで、ページが段階的に届くかを調べた実験です。東京から、シェルを先に返し、Suspenseで待つ箇所を二つ設けたページへアクセスしました。ヘッダーや最初のバイトに加え、Nodeのfetch、curl、ブラウザーで中身の到着を調べています。

待ち時間を1秒と3秒にした条件では、ウォーム時の直接アクセスで二つの部分がシェルの約1秒後と3秒後に届きました。CloudFrontでも、キャッシュ無効と圧縮有効の二設定で段階配信を観測しました。同じ部品からSuspenseを外した対照ページは、約10秒後までまとめて到着しませんでした。

コールドスタート条件では、Web Functionsの最初のバイトまで約1.2秒かかる例がありました。実験した構成はNext.js 16.4.6、React 19.3.1、Node.js 24で、特定の二つの遅延を仕込んだ試験です。別のランタイムやプロキシ設定でも同じ到着時刻になるとまでは言えません。

**読む価値：** 早い応答開始と段階的な中身の到着を、独立した測定結果として扱えます。

**面接質問：**

**関連プロジェクト例：** 注文登録と取消に別IDを割り当て、登録の再試行には同じIDを使い、DBの一意制約も含めて試す。

**関連プロジェクト例：** 遅延を二つ入れたNext.jsの検証ページを使い、本番相当の配信経路で本文の部分ごとの到着を回帰テストする。

## 4. 今日の技術テーマ

### 運用画面の数字を、測った単位から読む

同じ「成功」でも、送った依頼の受領、キューへの追加、業務処理の完了は、それぞれ別の事象です。境界ごとに識別子を残して、どの事象が観測されたのかを後から調べられるようにします。

ダッシュボードでは集計対象と開始日を押さえます。Data Engineering Agentでは監視の有効化時点、Storage Lensでは有効化した日と旧バージョンの扱い、StackSetsではインスタンスが完了と数えられる条件が、数字の意味を決めます。

利用者の体感に関係する検証では、中間結果の到着まで測ります。シェルと二つの境界に別々の目印を付けた試験なら、応答開始が早い場合にも、本文が一括で届く問題を見つけられます。

3. 部分作成を完了数へ足す計算にすると公式の進捗率と食い違います。

### 5. Next.jsのストリーミングはLambda Web Functionsで動くか

1. 応答ヘッダーだけのチェックでは段階表示の証拠が足りません。

2. 固定した遅延とSuspenseの有無で対照条件を作れます。

3. ウォーム時の境界到着とコールド時の最初のバイトを別の指標で扱います。

### 1. まとまり（まとまり）｜N1

- 品詞：名詞
- 意味：複数の要素が集まってできた一つの単位です。
- 連語：データのまとまり / 一つのまとまり / まとまりごとに分ける
- 記事文脈：受信の間隔を使って、連続して届いたチャンクを一つに数えます。
- 例文：短い間隔で届いたデータを一つのまとまりとして扱います。
- 例文の意味：続けて届いた複数のデータをまとめて扱います。
- ニュアンス：「集合」は要素の集まりを広く指します。この記事の「まとまり」は受信の時間差を手がかりにして区切る単位です。

### 2. 当日（とうじつ）｜N2

- 品詞：名詞・副詞
- 意味：予定や出来事の基準になっているその日です。
- 連語：当日のデータ / 開催当日 / 当日分を集計する
- 記事文脈：アクセス層メトリクスには、有効化した日の内訳が表示されました。
- 例文：設定を切り替えた当日の記録を、翌日に確認しました。
- 例文の意味：設定を変えた日に作られた記録を、次の日に見ました。
- ニュアンス：「今日」は話している日です。「当日」は設定日や開催日など、文脈が指定する日です。

### 3. 捨てる（すてる）｜N5/N4

- 品詞：一段他動詞
- 意味：不要なものを手元に残さず処分することです。
- 連語：データを捨てる / 無効な値を捨てる / 不要な下書きを捨てる
- 記事文脈：同じIDの再送は成功応答が返った後、新たなメッセージとして保持されませんでした。
- 例文：重複と判定したイベントを捨てる前に、件数をログに残しました。
- 例文の意味：二重だと判断したイベントを残さない処理の前に、何件あったかを記録しました。
- ニュアンス：「切り捨てる」は不要な部分を削る場合や数字を丸める場合にも使います。「捨てる」は対象を保持しないことを端的に述べます。

## C-2. IT/AI専門用語

1. **Cloud Trace（実行トレース）**：一つの依頼に含まれる処理の時刻と関係を記録します。 DEAのモデル呼び出しとツール処理を見分けます。

2. **S3 Storage Lens（S3利用状況の可視化）**：バケットやクラスを横断してS3の利用状況を集計します。 アドバンスト階層ではアクセス層のオブジェクト数も確認できます。

3. **PeekLock（ロック付きメッセージ受信）**：メッセージを一時的にロックした状態で受け取ります。 Completeのない受信を再配信と分けて観察します。

4. **CompletedStackInstancesCount（完了スタックインスタンス数）**：StackSetsの操作で完了したインスタンスを数えます。 一つのスタックにある個別リソースの進み具合とは測定単位が異なります。

5. **Suspense（待機中に代替表示を出す境界）**：準備中の内容にフォールバックを置けます。 サーバー描画では、準備のできた中身を順に送る試験に使われました。
