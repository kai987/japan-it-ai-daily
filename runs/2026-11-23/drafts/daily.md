# 日本 IT/AI 日报｜2026年11月23日（第104号）

同一个百分比、成功响应或耗时，往往只能解释流程中的一步。今天从五份原始实验读起，看看如何给观测指标找到对应的处理阶段。

# A. 详细文字版

## 1. 今日推荐的五篇原文

### 1. BigQuery Daya Engineering AgentのAgent Observabilityを試してみた

**原文：** https://dev.classmethod.jp/articles/bigquery-dea-agent-observability-ga/

**发布时间：** 2026-11-23 02:14:45 JST

BigQuery 的 Data Engineering Agent 开放了面向代理的观测能力。作者在东京测试项目用公开出租车数据构造同一个任务，在开启监控前后分别让代理生成 Dataform SQLX。两组都有 A2A 请求计数，开启后的新执行才留下相应的令牌和跟踪记录。

Cloud Monitoring 中，作者用 agent_type=DEA 区分时序数据。Cloud Trace 则按 SendStreamingMessage 查看每次对话，分辨模型调用和工具执行。首轮耗时约57秒，停在方案确认。第二轮约40秒，写入 SQLX 并完成编译和校验。

此次流程未创建实际数据表。会话记录列了12次模型调用，而监控延迟样本有15次。作者把差异解释为可能有子代理参与，实验未独立证实这一点。监控启用前的令牌数据没有回补，监控计数也缺少正式的账单换算关系。

**推荐理由：** 有了分阶段跟踪，团队能追查一次请求慢在模型、工具还是等待用户确认。

### 2. S3 Storage Lens がインテリジェント階層化ストレージクラスのアクセス階層別の内訳に対応したので確認してみた

**原文：** https://dev.classmethod.jp/articles/amazon-s3-storage-lens-intelligent-tiering-access-tiers/

**发布时间：** 2026-11-23 09:47:55 JST

AWS S3 Storage Lens 把 Intelligent-Tiering 的访问层拆进了仪表板。付费高级层可按访问层展示对象数和容量，弥补了 CloudWatch 按层观察容量时缺少相应对象数的情况。实测使用覆盖账户所有区域和存储桶的默认仪表板，样本是三个启用版本控制的存储桶。

启用约31.5小时后，作者在存储类别页看到了启用日的分层数据，用临时筛选核对了新加坡桶中的五个对象版本。图表给出四个高频访问，一个即时归档访问。其中落入即时归档的正是一个旧版本。

作者检查的两个启用前日期仍没有分层明细。31.5小时只是访问仪表板时看到结果的时点。估算提取计划时也要辨别名称相近的层级，Archive Access 和 Deep Archive Access 需要先发起恢复。 限制是该试验只观察了三个启用版本控制的存储桶，反映时延也只有一次记录。

**推荐理由：** 可用同一套仪表板检查容量与对象数量，并识别旧版本在盘点里占的位置。

### 3. Azure Service Busの重複検出で二重処理は防げる？同じMessageIdの再送と再配信を試した

**原文：** https://dev.classmethod.jp/articles/azure-service-bus-duplicate-boundaries/

**发布时间：** 2026-11-22 23:58:30 JST

Azure Service Bus 的重复检测关注发送时的 MessageId。实测在日本东部的 Standard 队列进行，重复判定窗口为一分钟，PeekLock 锁为30秒，未开启分区。作者用相同 ID 模拟无法确认发送结果后的重试。

两次发送都正常返回，约17秒后查询到的活跃消息只有一条。即使已完成第一条的消费，在窗口内再发同一 ID 仍会被抑制。超出窗口之后，使用同一 ID 的请求重新进入了队列。

作者还在首次接收后直接关闭了接收方，未发送 Complete。等待35秒重收时收到同一消息，delivery_count 从0变成1。本次没有确定关闭连接是否提前释放锁。实际订单系统还应考虑数据库写完但没有确认消费的情形，用业务键阻止重复入库。

**推荐理由：** 原文把发送去重与接收侧重做拆成了两个可单独复现的场景。

### 4. CloudFormation StackSets の操作の進捗が ステージ別・リージョン別に確認可能になったので試してみた

**原文：** https://dev.classmethod.jp/articles/aws-cloudformation-stacksets-progress-visibility/

**发布时间：** 2026-11-23 00:02:07 JST

CloudFormation StackSets 新增了按阶段和区域展示操作进度的方式。作者用自行管理权限的 StackSet 顺序部署三个区域，观察到部署状态会同时汇总在操作和区域层级。准备访问角色的阶段在这组实验中标为不适用。

顺序发布每完成一个实例，进度从0跳到33.3%、66.6%和100%。早期汇总却把三个区域都标成 IN_PROGRESS。文章在另一组顺序实验用 DetailedStatus 看到了实例级的 RUNNING 和 PENDING，从而找出正在执行与排队的区域。

两区域并行的另一轮实验里，三项 SNS 资源已经建好，只剩 ACM 证书仍在验证，当时总进度仍为0。进度百分比按已完成的堆栈实例计算。遇到长时间不变的值，需要下钻到资源事件才能解释具体等待。 该结果的适用条件是文中的自管理 StackSet 和选定模板。并行实验主要用于核对完成比例的计数单位。

**推荐理由：** 这一实验给出了识别灰度发布进度停滞的两个观测层级。

### 5. Next.jsのストリーミングはLambda Web Functionsで動くか

**原文：** https://zenn.dev/ryota_09/articles/nextjs-suspense-streaming-lambda-web-functions

**发布时间：** 2026-11-22 11:30:19 JST

Zenn 作者借两段可控的异步等待来判断 Next.js 在 Lambda Web Functions 上能否真的流式展示。实验固定了 Next.js、React 和 Node.js 版本，把到达时刻分到页面外壳和两个 Suspense 边界，并使用 fetch 与 curl 交叉核对。

热启动条件下，外壳先到，两个组件约在预设的一秒和三秒处到达。CloudFront 的关闭缓存与开启压缩两套配置都观察到了分段传输。无 Suspense 的对照使用相同组件和延迟，测试中约十秒后才收到整块内容。

冷启动实验里的首次字节延迟可达约1.2秒。原文给出的结果对应这些具体部署和测试路由，尤其是 CloudFront 的设置及固定的等待时间。页面只检查响应头和 TTFB 时，会漏掉正文在下游被缓冲的情况。

**推荐理由：** 测试把首段响应和用户实际等到两个内容区块的时间都量化了。

**相关项目示例：** 建立按区域聚合的分层报告，针对启用版本控制的桶分别核对历史版本以及需要恢复的归档层。

### 3. Azure Service Busの重複検出で二重処理は防げる？同じMessageIdの再送と再配信を試した

**面试问题：**

> Service Busで同じ注文が二回処理される経路を、どのように検証しますか。

**约30秒回答：**

> まず、同じメッセージアイディーで再送して、一分の重複検出窓にある間は送信成功でもキューが増えないことを確かめます。それから、ピークロックで受信した側が完了通知の前に止まる状況を試します。記事では、このとき同じメッセージが再配信されました。ただし、この設定だけで注文の二重登録は防げないので、データベースの一意制約も確認します。

**相关项目示例：** 用订单号和操作类型生成消息标识，并用唯一约束验证重复投递时只有一次注册落库。

**关键词：** MessageId、PeekLock、Complete、幂等处理

**相关项目示例：** 为跨区域部署建立操作面板，从汇总进度切换至实例状态和事件详情，并记录等待 DNS 验证的时间。

## 4. 今日技术主题

### 用阶段内的证据解释端到端结果

排查请求时，可以先把“成功”的返回值对应到具体接口。Service Bus 已受理发送时，队列里未必增加一份。相似地，Dataform 编译和校验通过后，数据表是否建成仍需要执行阶段的证据。

对运维面板，先标记观测范围。S3 的旧版本计入对象总数，StackSets 的百分比按实例完结变化。归档指标出现慢或证书还在核验，都可能给出暂时不变的曲线，进一步查询才能定位原因。

回归测试应把可观测结果安排到用户路径。对分段网页，在预先指定的延迟点分别查组件。对消息任务，在接收方故障后重查落库记录。每一步的结果都能和流程图上的处理阶段对齐。

## 5. 面试复习卡

### Q1

> 集計値だけでは処理が止まった理由が分からないとき、次に何を見ますか。

**回答要点：** 代理任务先选中请求对应的父跨度，区分模型和工具。部署则从区域汇总进一步查实例状态和资源事件。

### Q2

> 時刻を条件にした検証では、どの時点を記録しますか。

**回答要点：** 分层统计记录启用日。发送去重记录首次发送和重试时间，接收再投递则另查锁与完成通知的时间。

### Q3

> 利用者に返した成功や先頭部分から、後続処理をどう確かめますか。

**回答要点：** 队列清点实收消息，流式网页测量每个 Suspense 边界的到达时间，都直接取后续结果作为证据。

   **日本語：** 時間窓の長さは、再送期間と負荷を見て決めます。

   **日本語：** 受信の完了前に処理が中断した場面を、送信の再試行と別の検証にします。

1. **中文：** 首次轮询可能还没有区域详情，保留未产生指标的状态。
   **日本語：** 集計の始動段階ではリージョン別欄がまだ返らない場合があります。

2. **中文：** 区域汇总代码相同的时候，实例状态仍能给出排队与执行的差别。
   **日本語：** IN_PROGRESSの内訳を知るには、インスタンス単位の状態が必要です。

3. **中文：** 堆栈实例内部做完一部分资源，并不会按资源比例增加发布进度。
   **日本語：** 部分作成を完了数へ足す計算にすると公式の進捗率と食い違います。

### 5. Next.jsのストリーミングはLambda Web Functionsで動くか

1. **中文：** 给每个边界打标记，可以在响应字节中确定到达先后。

# C. 日语学习

## C-1. 新学JLPT词汇

查对全103期的412份文件，本次收录原文用法及参考等级均可确认的三个新词。已有词汇留作复习。

### 1. まとまり（まとまり）｜N1

- 词性：名詞
- 含义：多个要素集中在一起形成的整体或单位。
- 搭配：データのまとまり / 一つのまとまり / まとまりごとに分ける
- 文章语境：作者用停顿划分收到的字节，把连续到达的若干块视为一组。
- 例句：短い間隔で届いたデータを一つのまとまりとして扱います。
- 例句含义：短时间内连续到达的数据作为一组处理。
- 辨析：「集合」可广泛指元素的集合。原文强调能按到达间隔分出来的组。

### 2. 当日（とうじつ）｜N2

- 词性：名詞・副詞
- 含义：以某项活动或发生的事情为基准的当天。
- 搭配：当日のデータ / 開催当日 / 当日分を集計する
- 文章语境：分层指标最先显示的是启用当天的数据。
- 例句：設定を切り替えた当日の記録を、翌日に確認しました。
- 例句含义：在第二天查看了切换设置当天的记录。
- 辨析：「今日」以说话的时点为参照，「当日」以语境所指的事件为参照。

### 3. 捨てる（すてる）｜N5/N4

- 词性：一段他動詞
- 含义：把不需要的东西丢掉，不再留存。
- 搭配：データを捨てる / 無効な値を捨てる / 不要な下書きを捨てる
- 文章语境：同一 ID 在窗口内重发时虽然收到成功响应，这份消息没有进入队列。
- 例句：重複と判定したイベントを捨てる前に、件数をログに残しました。
- 例句含义：丢弃判定为重复的事件之前，把数量写到了日志。
- 辨析：「切り捨てる」也指砍掉一部分或舍去数位。「捨てる」直接表达不保留当前对象。
