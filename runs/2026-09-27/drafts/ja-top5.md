### 1. DeepEvalの公式Jev対応でjudgeを判定特化モデル「Jev」に置き換えて検出力・安定性・コストを比べてみる

**原文：** https://dev.classmethod.jp/articles/litellm-deepeval-jev/

判定役を安くすれば評価工程もそのまま置き換えられるのか。この記事はDeepEval 4.2.6とJevを使い、その前提を確かめています。TypeSafeModelをsystem_one_modelに渡すsystem_oneモードでは、同梱の質問を使ってテストケースを判定します。llmは抽出や理由生成もLLMに任せ、hybridは判定の一部をJevへ分担させます。一方、Noul・Score・Choiceで質問を作るJevEvalは別の入口です。標準設定のLLM版Faithfulnessが主に矛盾を見るのに対し、system_oneの質問は資料による裏付けも求めるため、名前だけをそろえても同一の測定にはなりません。

作者は六事例を三つの指標で三回ずつ評価しました。理由ありの実行では、Jevの平均が0.46秒・0.000330ドル、gpt-5.4が4.39秒・0.089058ドルでした。時間はevaluate()の範囲、費用はevaluation_costの合計であり、アプリ全体の応答時間ではありません。理由なしの別実行は0.47秒と3.21秒で、その実行ではエージェントが生成した回答も変わっています。したがって前者の安定性と後者の短縮率を一つの条件として扱えません。期待値のある判定数も標準側15、裏付け重視側16と異なります。

ただし正答を落とす例もあります。リモート勤務の正しい回答に前置きが付くとFaithfulnessは0.56～0.57となり、設定した閾値0.7を下回りました。前置きを外した場合は0.99です。閾値を下げればよいという話ではなく、境界例を含む正解付きデータで誤合格と誤不合格を調べる必要があります。日本語の業務全般への一般化や、別モデルで発生した一度の長い待ち時間の原因は未検証です。RAGの評価画面なら、問題定義、モデル版、入力、根拠を保存し、数値だけでなく失敗の種類を説明できる形にするのが本日報の提案です。

**読む理由：** 指標の名称が同じでも合格の意味が変わることを、RAGの評価設計として説明できる記事です。

### 2. Claude Code v2.1.282〜v2.1.283 の主要アップデート - /doctor prompt-audit の追加と auto mode の既定化

**原文：** https://dev.classmethod.jp/articles/20260924-cc-updates-v2-1-283/

開発ルールはコードの変更に追いつかず、存在しないパスや古い実行方法を残しがちです。Claude Codeの更新解説では、/doctor prompt-auditを使い、CLAUDE.mdやskills、agents、commandsを点検しています。/checkup prompt-auditという呼び方も紹介されています。手元に作ったサンプルでは、古いパス、未定義のnpmコマンド、コミット言語の衝突が報告されました。出力は監査レポートと提案差分までで、原本の自動修正ではありません。実ファイルとpackage.jsonを照合する材料として読む機能です。

ただしsettings*.jsonと.mcp.jsonは対象外です。指示文を監査しただけで権限やMCP設定の点検が済んだとは扱えません。また結果はモデルに依存し、Git履歴がないサンプルでは、英語と日本語のどちらでコミットすべきかを履歴から決められませんでした。こうした衝突は保守担当者へ判断を委ね、実在する危険操作の禁止は残す必要があります。本日報では、存在確認で解ける誤りとチームの合意が要る事項を分け、差分の根拠と承認を記録する使い方を勧めます。

権限モードとテレメトリーの変更にも条件があります。第三者プロバイダーを使う場合など、一部の対話実行で未設定時の既定モードが変わりますが、明示したpermissions.defaultModeが上書きされるという意味ではありません。autoを権限確認の全面解除と混同してはいけません。さらに、リポジトリのproject/local設定だけでテレメトリーの有効化や送信先、内容収集を決めない方向の変更が説明されています。ユーザーまたは管理側が信頼する設定を使うことと、モデルへ渡す文章の品質は別の問題です。チームでは指示、実行権限、外部送信を別々に確認します。

**読む理由：** 自動監査の便利さと承認の責任を切り分け、開発ドキュメントを保守する手順へ落とし込めます。

### 3. Kiro Web にローカルの .kiro 設定をアップロードしてみた

**原文：** https://dev.classmethod.jp/articles/kiro-web-upload-local-kiro/

Kiro Webへローカルの.kiro設定を移した検証です。Syncという画面名でも、この記事が使うのはローカルからクラウドへの単方向インポートで、逆方向に新しいローカルセッションへ設定を適用する機能とは別です。~/.kiro全体を選ぶと拒否され、作者は対応するsteering、settings、skills、agentsなどの子フォルダーを個別に指定しました。八つのsteeringファイルは取り込めています。この結果が示すのはファイルの受付であり、ローカルで使う機能一式の再現ではありません。

実行まで進むと依存関係の違いが表れます。MCPの設定に本機の実行パスが残ったままでは、クラウドのサンドボックスで同じプログラムを呼び出せず、利用時に失敗しました。カスタムエージェント用のPDFには4 MBを超えてアップロードできないものもありました。明示的なカスタムエージェント選択に関する制約も、作者が観察した範囲の報告です。設定が受理されたとしても、実行ファイルや資料まで自動でそろうわけではありません。

本日報の提案は、可搬な指示、環境ごとの起動方法、公開してはいけない設定値を分離することです。指示は版を付けて差分を確認し、起動方法は移行先の実ファイルと権限に照らして点検します。そのうえでツール呼び出しと目的の作業を試し、どの段階まで成立したかを残します。ネットワークや権限の制限を外すことを移行の成功条件にはしません。この記事だけでは、あらゆる環境で双方向同期や同等の動作が保証されるとは言えず、検証時点の観察と自分の環境の受け入れを分ける必要があります。

**読む理由：** 設定の移植で残るローカル依存を見つけ、クラウド側で何を受け入れ確認すべきか考えられます。

### 4. QdrantからZilliz Cloudへ移行する方法――データ移行から検索確認まで

**原文：** https://qiita.com/sphereSky/items/3956d10b9d8b280516de

Zilliz, Inc.所属と表示されるsphereSkyによる、QdrantからZilliz Cloudへの移行手順です。ベンダーに関係する著者の公開チュートリアルであり、独立した性能比較としては扱いません。デモではVARCHARの主キー、384次元のFLOAT_VECTOR、COSINE、AUTOINDEXを設定し、総件数と索引化済み件数はいずれも1178でした。見出し、年、本文、出典URLなども持つので、アプリの検索カードや絞り込みに必要なフィールドまで移行対象として考える必要があります。

接続可能な移行元、許可する移行用IP、読取専用の認証情報、移行先の権限と容量が前提です。記事によるとpayloadの型推定には100件の標本を使うため、少数の型違いや欠損、配列がないかは別に確かめます。AutoIDを有効にすると元のIDを捨てる点も、更新や削除、他データからの参照に影響します。データの取り込み後は索引の作成とコレクションのロードが別に必要です。Search Dataの成功は検索リクエストの実行確認であり、移行前後の関連度や業務上の正しさを保証しません。非公開のデモ録画は本日報では参照していません。

受け入れでは同じ埋め込みモデル、次元、質問、フィルターを固定し、主キーと出典、返された候補を突き合わせるのが本日報の提案です。移行と同時に埋め込みまで替えると、差の原因を特定しにくくなります。React側でもレスポンスをカードへ写す処理を契約テストにし、リンク切れや絞り込みの変化を見つけます。ただし記事の手順は継続的な差分同期や無停止切り替えを証明していません。切り替え後の更新をどう戻すかも含め、追加書き込みと切り戻しの計画を用意します。

**読む理由：** 件数の一致から一歩進み、RAGの検索結果、参照先、更新・削除の契約を守る移行を説明できます。

### 5. GPU なしの Ubuntu 24.04 に Amazon DCV でリモートデスクトップ環境を作る手順

**原文：** https://dev.classmethod.jp/articles/amazon-dcv-remote-desktop-ec2-ubuntu2404/

GPUを持たないEC2でも遠隔デスクトップを用意できるかを、Ubuntu 24.04.5 LTSで確認した記事です。条件は東京リージョンのm7i.xlarge、50 GiBのgp3、Amazon DCV 2025.0 r20103でした。GNOME/GDM3をXorgで使い、XDummyの仮想画面とMesaのソフトウェア描画でconsoleセッションを作ります。Waylandの設定とは区別が必要です。デスクトップの依存パッケージを入れる容量も確保しますが、作者の約五分という導入時間や容量を、そのまま別環境の必要量と決めつけることはできません。EC2上で追加のDCVライセンス料金がなくても、計算・ストレージ等の利用料は残ります。

セキュリティグループの受信を開けず、SSMのポートフォワーディングで本機の8443番をインスタンスの8443番へつなぎ、localhost:8443#consoleへ接続します。SSMを開始する許可と、リージョン別のライセンス用S3オブジェクトを読む許可、PAMによるOSの認証は別々です。通信が届くだけではログインは完了しません。cloud-initの完了とconsoleセッションの存在を先に確認し、インスタンス再起動時はトンネルを張り直す必要もあります。遠隔のブラウザー操作には役立つ構成ですが、GPU計算や重い描画を検証した記事ではありません。

通信方式の確認も実践的です。サーバーはUDP 8443を待ち受けていましたが、SSM経由で接続したログに記録されていたのはWebSocketでした。QUICが設定上有効であることと、この接続で使われたことは違います。本日報では、インストール、表示セッション、トンネル、認証、実際に選ばれた通信を順に調べ、最後に必要な画面操作を確認する進め方を提案します。ただし表示できたという事実だけから、応答速度や画質、あらゆる利用負荷への適合まで一般化しないことが重要です。

**読む理由：** 受信ポートを公開せず遠隔UIを使う構成から、認証と実際の通信方式を確かめる順序を学べます。
