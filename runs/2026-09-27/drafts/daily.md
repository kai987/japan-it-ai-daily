# 日本 IT / AI 日报｜2026年9月27日（第47号）

本期固定选材窗口为2026年9月26日10:00至9月27日10:00（JST）。五篇文章均在窗口内首次发表，来自DevelopersIO和Qiita；其中既有更新解读，也有作者实测和迁移教程。文章发表日期不等于产品发布或实验日期：Claude Code一文讨论9月24—25日的版本，DCV作者的验证日期为9月25日。本期只使用完整公开原文，不把工具作者的测量当成本团队的测量，也不把厂商教程当作独立比较实验。

## 1. 今日最值得看的5篇

### 1. DeepEvalの公式Jev対応でjudgeを判定特化モデル「Jev」に置き換えて検出力・安定性・コストを比べてみる

**原文：** https://dev.classmethod.jp/articles/litellm-deepeval-jev/

DevelopersIO的作者在DeepEval 4.2.6中将判定役替换为TypeSafe的Jev。接口上，把TypeSafeModel传入system_one_model，并设置eval_mode="system_one"，就会用库中预设的问题对整条测试记录判定；llm模式主要由生成式模型完成提取、判定和解释，hybrid则把其中的判定环节交给Jev。JevEval是另一种自定义评估入口，可使用Noul、Score、Choice问题，不能因为同样调用Jev就当成同一评估定义。最重要的变化不是模型名字，而是Faithfulness在默认LLM配置下侧重检查矛盾，system_one的内置问题还要求主张有资料支持；“没有明显矛盾”不等于“有可核对的出处”。

测量范围是6个案例、3个指标、各重复3次，时间仅覆盖evaluate()调用，费用为各指标evaluation_cost的合计。在包含解释的这一轮，Jev平均0.46秒、0.000330美元，对照gpt-5.4为4.39秒、0.089058美元。另一轮关闭解释生成时是0.47秒与3.21秒，且代理新生成的答案也发生了变化，不能把两轮的耗时、稳定性和检测结果混成一个结论。原文的15/15和15/16分别对应不同定义下的有效期望数，也不是可直接排序的同一准确率分母。

限制在正确答案上同样可见：带有“社内規定によると”前置语的正确回答，在Jev的Faithfulness上只有0.56—0.57，低于作者设置的0.7阈值；移除前置语后得到0.99。这是阈值校准与问题定义的警讯，不是应当无条件放宽门禁的理由。作者还没有证明它能泛化到各类日语业务资料，某次延迟异常的原因也未确定。对RAG Web项目，本期建议固定标注样本、问题定义、模型版本与生成答案，分别统计错误放行和错误拒绝，再决定何时引入人工复核；这是工程推导，不是原文已经完成的生产验证。

**为什么值得看：** 先对齐评估定义和错误类型，再比较费用，适合说明RAG回归测试为什么不能只看总分。

### 2. Claude Code v2.1.282〜v2.1.283 の主要アップデート - /doctor prompt-audit の追加と auto mode の既定化

**原文：** https://dev.classmethod.jp/articles/20260924-cc-updates-v2-1-283/

Claude Code v2.1.282—v2.1.283的这篇解读重点展示了/doctor prompt-audit，原文也用/checkup prompt-audit调用同类指令审计。作者构造了带有旧路径、未定义npm脚本和提交语言冲突的示例项目，检查CLAUDE.md、skills、agents及commands中的约定是否仍符合实际代码。输出包含报告和建议差分，原始文件没有被自动改写。它能帮助定位“文档仍要求旧做法”的位置，但真正的修复还需要核验当前文件、package.json及团队明确的决策。

审计有清晰边界：settings*.json与.mcp.json不在该项审计范围，不能把提示词检查成功解释成权限或MCP配置也已通过安全审查。输出取决于模型；没有Git历史时，示例中的英语与日语提交要求无法只凭文本可靠判断谁应优先，应由维护者决定。规则中有根据的危险操作禁令也不能当作陈旧文字一并删除。本期建议把“可由实际文件验证的事实错误”和“需要团队选择的约定冲突”分开列出，先审差分，再只批准必要的改动。

版本变更还涉及信任来源。原文说明，部分第三方模型提供商或关闭遥测的交互场景，在未显式设置模式时调整了默认权限模式；已经指定permissions.defaultMode的配置不因此失去效力，auto也不能理解为全面跳过授权。项目或本地仓库中的遥测设置不再能自行决定可信的导出目的地与内容采集，应由用户或组织管理层配置。对团队AI开发环境，审计指令、执行权限与数据导出策略属于三条不同控制链，不能用其中一条的“绿色”替另外两条背书。

**为什么值得看：** 将AI给出的修正建议、仓库实际状态和修改授权分开，直接关联团队规则维护与安全开发。

### 3. Kiro Web にローカルの .kiro 設定をアップロードしてみた

**原文：** https://dev.classmethod.jp/articles/kiro-web-upload-local-kiro/

Kiro Web的试用文章把本地.kiro设置上传到云端。界面里的Sync包含不同方向的功能，本次操作是本地到云端的一次性单向导入，不是双向实时同步，也不等于从云端向新建本地会话应用配置。作者直接上传整个~/.kiro文件夹时被拒绝，随后按steering、settings、skills、agents等支持的子目录分别导入。八个steering文件成功出现于云端，可说明指示文件被接收，不能据此确认所有本地工作流已经迁移。

失败揭示了两层依赖：部分自定义代理PDF超过所观察到的4 MB文件上限，未能导入；另一些MCP配置虽然上传成功，却保留了只在本机存在的可执行文件路径，因此在实际使用时失败。配置里的路径只是字符串，云端沙箱不会因接收字符串而自动获得同一程序、文件系统和运行权限。作者还记录了在Kiro Web显式选择自定义代理的限制，未展示与本地完全等价的端到端成功。这里应保留作者观察的时间和环境边界，而不能宣布所有版本永远存在同样问题。

工程上可把可移植的行为说明、环境专属的启动参数和敏感配置分别管理：前者版本化并审阅差分，后者在目标环境中核验依赖是否存在，敏感值不进入公开配置包。验收至少包括“文件已导入”“依赖可解析”“工具调用成功”“目标任务结果符合预期”，不应仅看上传提示。本期提出的是迁移检查清单，不是建议关闭网络或权限限制来强行运行原配置；实际授权仍应采用目标环境已有的受控方式。

**为什么值得看：** 配置文件可复制不代表工具运行环境可复制，适合讨论本地与云端AI开发环境的依赖管理。

### 4. QdrantからZilliz Cloudへ移行する方法――データ移行から検索確認まで

**原文：** https://qiita.com/sphereSky/items/3956d10b9d8b280516de

Qiita的sphereSky以Zilliz, Inc.成员身份说明从Qdrant到Zilliz Cloud的控制台迁移流程。这是带实例的厂商相关教程，不是独立性能对比。示例把集合映射到目标数据库，选择VARCHAR主键、384维FLOAT_VECTOR、COSINE距离和AUTOINDEX，迁移后画面显示总实体数与已索引实体数均为1178。字段还包含标题、年份、正文和来源URL，因而迁移对象不只是向量本身；RAG界面使用的出处和业务过滤字段也必须一起核对。

需要注意的条件包括来源可达性、允许的迁移IP、可读取来源数据的密钥、目标端角色和容量。文章指出，payload类型推定只抽样100条，因此极少出现的字段、混合类型、数组和空值仍可能需要另行检查；如果启用AutoID，原ID会被丢弃，这会影响引用、更新和删除。数据导入后，索引创建和集合加载还是独立步骤。API Playground中的Search Data成功，只证明请求能够执行，并没有给出召回质量或业务结果与Qdrant等价的结论；本期没有观看文中链接的演示录屏。

对应用迁移，本期建议冻结同一嵌入模型、维度、查询集合和过滤条件，对照主键、来源文档及候选结果，再确认API响应到前端卡片的映射。若同时更换嵌入模型，就难以区分差异来自迁移还是向量空间改变。控制台教程也没有证明增量写入、删除和切换期间的数据一致性可以自动解决；回退方案应包含切换后新增数据的处理，而不是只保留旧端点。件数相同是必要检查之一，不足以替代业务验收。

**为什么值得看：** 把向量数据搬迁扩展为稳定ID、过滤语义和查询结果的验收，直接关联RAG前端及API适配。

### 5. GPU なしの Ubuntu 24.04 に Amazon DCV でリモートデスクトップ環境を作る手順

**原文：** https://dev.classmethod.jp/articles/amazon-dcv-remote-desktop-ec2-ubuntu2404/

DevelopersIO给出了GPU-less EC2上安装Amazon DCV远程桌面的步骤。作者的验证条件是东京区域m7i.xlarge、Ubuntu 24.04.5 LTS、50 GiB gp3磁盘和DCV 2025.0 r20103。GNOME/GDM3切换到Xorg而非Wayland，通过XDummy虚拟显示与Mesa软件渲染建立console会话。较大的磁盘用于容纳桌面环境等依赖；文中安装耗时约五分钟是该次记录，不是所有实例的保证。EC2上无额外DCV许可证费用也不等于免除EC2、存储及相关资源费用。

网络入口采用Systems Manager：安全组不开放入站规则，使用SSM把本地8443端口转发到实例8443，再连接localhost:8443#console。SSM会话权限、实例读取区域DCV许可证对象的权限，以及DCV/操作系统的PAM登录并不是同一层；隧道打通不代表无需系统认证。还要先确认cloud-init安装结束及console会话存在，实例重启后也需恢复隧道。上述步骤可支持远程浏览器操作与开发环境排障，但原文没有提供高帧率图形任务或GPU计算的性能证明。

作者进一步检查了真实连接日志：虽然服务端UDP 8443处于监听状态，经SSM端口转发的此次连接记录为WebSocket，不能因配置中启用QUIC就称当前会话用了QUIC。这提供了很好的排障顺序：先看安装和会话，再看隧道与身份认证，最后看实际协商的传输及目标画面操作。本期建议把远程UI测试所需的操作响应、画面质量和访问审计纳入验收；不要把“桌面能连接”扩展成对所有渲染负载都适用。

**为什么值得看：** 用最小网络入口搭建可复现的远程浏览器环境，同时区分设置、认证和真实连接方式。

### 1. DeepEvalの公式Jev対応でjudgeを判定特化モデル「Jev」に置き換えて検出力・安定性・コストを比べてみる

**面试问题：**

> DeepEvalの判定役をJevに替えるとき、速度以外に何を検証しますか。

**约30秒回答：**

> 判定の定義をそろえてから比較します。DeepEvalのsystem_oneは同梱の質問で裏付けを調べますが、標準設定のLLM版は矛盾を中心に見ます。記事では正しい前置きでも閾値0.7を下回りました。ただし六つの事例だけでは日本語全般に一般化できません。自社の正解付きデータで誤った合格と不合格を測ります。

**相关项目：** RAG答案评估面板：同时呈现判定问题、出处和误判类别，避免把一个分数当作全部质量。

**关键词：** system_one / 裏付け / 閾値の校正

### 2. Claude Code v2.1.282〜v2.1.283 の主要アップデート - /doctor prompt-audit の追加と auto mode の既定化

**面试问题：**

> Claude Codeのprompt-auditを、チームの開発ルールの保守にどう使いますか。

**相关项目：** React/TypeScript团队的开发约定维护：用可核验的命令和路径检查减少新人按旧文档操作的成本。

**关键词：** prompt-audit / 差分レビュー / 信頼境界

**相关项目：** React RAG检索页：保持文档ID与出处链接稳定，对过滤条件、结果卡片和更新删除做契约测试。

### 5. GPU なしの Ubuntu 24.04 に Amazon DCV でリモートデスクトップ環境を作る手順

**面试问题：**

> GPUなしのEC2へAmazon DCVで接続する構成を、どう安全に評価しますか。

**约30秒回答：**

> 入口の制限と接続後の認証を分けます。記事の構成はセキュリティグループの受信を開けず、SSMで8443番を転送し、OSの認証も通します。ただしサーバーがUDPを待ち受けても、記録された接続はWebSocketです。設定値だけで通信方式や描画性能を決めつけず、ログと必要な画面操作で確認します。

**相关项目：** 远程Web UI复现环境：不开放公共桌面端口，使用已有受控SSM权限并核验浏览器实际交互。

**关键词：** SSM / XDummy / WebSocket


## 4. 今日技术主题｜工具替换之后，原来的业务语义还成立吗？

把迁移看成三个合同的交接：输入合同规定字段、维度、身份和上下文；行为合同规定判定问题、过滤逻辑、工具依赖及授权；验收合同规定什么结果才算合格。Jev替换后Faithfulness含义变化，Kiro接收了路径但未获得程序，向量库导入成功但未证明检索等价，都说明格式兼容不自动带来行为兼容。

一种可复用的做法是保存“旧配置版本＋固定输入＋期望结果＋真实执行证据”，在隔离环境下对候选配置重放。对于RAG，可以让后端适配层统一ID、来源URL和过滤条件，前端用契约测试验证响应到卡片的映射；对于AI判定，保存问题定义与模型版本，分别看误拒绝和误放行。这样能把“哪里变了”从笼统的质量下降缩小到字段、语义或执行依赖。

收益是更容易解释变化、定位故障和控制回退，不过固定样本无法覆盖全部生产流量，身份权限与增量数据也不能靠一次重放证明安全。回退触发条件、切换后的写入处理和受控访问仍需单独设计。在日本团队落地时，可把这套对照记录纳入受入条件与変更管理；本期的日文技术文章提供了讨论素材，但没有证明这些做法已经在日本企业普遍采用。面试可从具体API、数据契约和证据边界讲起，而不是只列工具名字。

### Q1

**回答要点：** prompt-audit提出差分不等于修改已获批准；UDP端口监听不等于连接使用QUIC。前者看实际修改及授权记录，后者看真实连接日志与端到端测试。

Qdrant迁移教程说明启用后会丢弃原ID，影响业务引用和更新删除。

### COSINE｜コサイン類似度による比較

依据向量方向接近程度进行相似性比较的方法。

Zilliz示例采用384维向量和COSINE；迁移时要固定嵌入与比较条件。

### XDummy｜仮想ディスプレイ構成

在没有物理显示设备时提供Xorg显示环境的配置方式。

GPU-less DCV示例使用它与Mesa建立可捕获的console桌面。

### SSM port forwarding｜SSMのポート転送

通过Systems Manager会话将本地端口连接到实例端口。

本例转发8443且不开放安全组入站；OS认证及真实传输方式仍要确认。
