### 1. ローカルLLMのRAGが『資料からはわかりません』ばかり返す原因は、検索ではなかった（M1 Mac・25問で実測）

**原文：** https://zenn.dev/hoshihoshi/articles/5f07aa9a13f042

**发布时间：** 2026-11-11 08:44:11 JST

本地规章问答给出「资料中找不到」，排查时要先看实际送进模型的内容。作者在配有16 GB内存的 M1 MacBook 上使用 Ollama 的 qwen3:8b，以 FAISS 检索并用 LangChain 串起流程。测试只有一份3页的虚构规章和25道题，20题能从资料中作答，5题应当拒答。检索分数看证据词是否出现在传入片段中，作答分数则看答案词或正确的拒答，再辅以人工检查。

初始提示词的三种配置一共答错12次，其中11次对应的依据已经进入上下文。将规章按500字切分时只得到3段，最多取4段相当于全部送入。因此20道有答案的问题都命中依据，并不能说明扩大文档后仍能找到正确段落。诸如用产品名询问规章中的通用类别，还要求模型正确识别两种说法的关系。

同为500字切分、最多4段，允许在依据明确时处理同义表达，正确数由21升至24，无依据的5题仍全部拒答。保留旧提示词并启用思考模式，则25题全对，响应中位数从1.4秒增至22秒。PDF换行清理仅在部分配置下改变结果。局限是每种设置仅运行一次，题量很小，且评分没有覆盖解释的清晰度。

**阅读价值：** 面试中可以展示如何先定位检索、上下文与回答三个环节，再决定改提示词还是检索。

### 2. Cloudflare D1で読み取り上限超過！NOT INの罠と99.8%削減・オフラインキャッシュ戦略

**原文：** https://zenn.dev/feedge/articles/cloudflare-d1-query-optimization-and-offline-cache

**发布时间：** 2026-11-11 09:01:26 JST

feedge 的文章把一次数据库配额耗尽追溯到文章列表。D1 统计中，47次列表请求读取约334万行，而页面每次只返回20篇。团队看执行计划时发现，在订阅和暂时隐藏条件组合之下，SQLite 先广泛读取候选，再用临时 B 树排序。输出有20行，底层工作量却由过滤和排序路径决定。

改动同时处理了订阅判断与排除判断。查询以 EXISTS 确认用户订阅相应 Feed，以 NOT EXISTS 检查该用户是否存在尚未到期的隐藏记录。两处都与当前文章关联，分别利用用户与 Feed、用户与文章组成的主键。团队观察到，改写后能按发布时间索引倒序读取，找到20条合格记录即停止。

文章列出的单次行数从约7.1万变为20至30，时间从110毫秒变为2毫秒。标题的99.8%与这些行数的直接计算口径不一致，因此保留原始行数与耗时作为作者报告。前端另存最近100篇的元数据，用30秒有效期处理短间隔访问，服务失效时只能展示已存内容。改写的限制在于计划取决于索引和数据分布，NULL 与过滤后结果顺序也须单独核对。

**阅读价值：** 把执行计划、读取预算与页面在故障时的能力联系起来，能说清优化发生在哪一层。

### 3. テストが通っても YAML フィクスチャは壊れている — JSON Schema と yajsv で実行前に検出する

**原文：** https://zenn.dev/kyrenzk/articles/yaml-testdata-json-schema-yajsv

**发布时间：** 2026-11-11 09:08:11 JST

订单测试全部通过，但其中一份 YAML 缺少通货，还多了一个拼错的金额字段。作者用 Go 1.24.7 与 yaml.v3 v3.0.1 搭建了两份夹具的实验。默认反序列化忽略未知键，缺少通货时结构体拿到空字符串。已有 Valid 方法检查 ID 和金额，未触及通货字段，所以用这两份数据运行 go test 依然成功。

要在进入业务测试前看见缺陷，作者用 draft-07 JSON Schema 声明必填键、类型、金额最小值与通货枚举，同时拒绝额外键。通过 Make 调用 yajsv 后，正常文件通过，异常文件同时报告缺失和拼写错误。文章也实测了 Go 的 KnownFields，能报未知键，却没有替结构体表达通货必填的约定。

这个检查放在 CI 的测试之前，可以直接把失败定位到夹具文件。业务关系仍应由业务测试承担，结构体和 Schema 也要同步维护。原文只验证了每个文件一份 YAML 文档的条件，未衡量多文档、拆分 Schema 或大批文件的处理时间。

**阅读价值：** 可用于说明同一次 CI 中为什么需要输入契约检查和行为测试各自提供证据。

### 4. 縦動画の文字のはみ出しを、ffmpeg と Python の標準ライブラリだけで落とす

**原文：** https://zenn.dev/tarowhitey/articles/ffmpeg-vertical-video-frame-check

**发布时间：** 2026-11-11 08:24:53 JST

原有视频检查覆盖画幅、时长、音频和后来叠加的字幕，却让嵌在画面里的标题越过右边界。作者改用 ffmpeg 把每秒4帧缩到270×480，输出灰度原始字节。单帧大小固定，可直接用 Python 标准库按位置统计与背景亮度差超过阈值的像素，无需额外图像库。

作者把画框边缘、右侧按钮区、左右偏移和最小留白分开检验。只看左右差值会放过两边都很窄的标题，所以另用换算到1080宽的140像素下限。为了减少场景切换造成的误判，持续性检查要求连续两张采样帧符合条件。字幕保留带的浅色边框还需要不同的亮度阈值，背景由外围采样估计，避免被中央白框带偏。

作者用合成的合格和失败视频，以及无法解码的空文件组成14例。4核环境重复3次，整套自测用时9.4至9.5秒，结果都符合预期。取不到任何帧会标为 UNMEASURED。限制是这套几何规则无法识别内部字形重叠或断行不自然，还得另行抽帧审查。

**阅读价值：** 可以讲清区域检查各自保护什么，以及缺少观测值时为什么不能放行。

### 5. Snowflake Dashboards 2.0が最高な理由と、これからBIに求められること

**原文：** https://zenn.dev/dataheroes/articles/snowflake-dashboards-2-and-future-of-bi

**发布时间：** 2026-11-11 09:21:10 JST

作者从团队例行看数的流程出发，介绍 Snowflake Dashboards 2.0。报表定义存在 Snowsight Workspaces 的 .dash 文件内，单个瓦片定义 SQL 及表格、文本或图表的呈现方式，图表采用 Vega-Lite。选地区或日期后，条件会进入 SQL，再按筛选后的数据聚合。下钻可以对各层级重新查询，避免把不能直接相加的去重指标当作普通求和。

报表可以只读副本的形式按角色共享，用户在 CoWork 打开后可围绕某个瓦片继续提问。分享权限决定能否拿到报表，底层查询再按查看者自己的权限运行。因而同一个共享链接可以分别用有权限和无权限的角色验证。官方文档也写到，可能返回该查看者较早的结果快照，界面需要让刷新和数据时效可辨认。

文章主要记录作者的使用体验，没有跨 BI 产品的成本或时延实测。对只需要固定指标、筛选和少量下钻的团队，减少独立报表应用是可以试验的方向。不过实际费用仍受仓库计算、查看人数和刷新次数限制，聊天能否解释指标也要按业务定义核对。

**阅读价值：** 面试可以用两种角色、一个筛选和一个不可加指标，设计可复查的报表验收。

## 4. 技术主题：为中间状态保留可复查的证据

先为过程中的中间状态设计观测。RAG 可以把找到依据、实际传入和生成答案逐项留证。夹具检查把输入契约置于单测之前。数据库优化则用读取行数和查询计划补足页面耗时。这样定位问题时，可以重现某一环节的结果，并看见改动是否改变了下游的输出。

为降级与缺失证据给出能被识别的状态。视频解码失败应保留未测量，资料不足的问答应保留拒答。RSS 页面切换到已保存列表时，可以同时展示数据获取时间和刷新失败状态。使用 Snowflake 报表时，还要以不同角色检验同一瓦片，确认分享范围与底层数据可见性。

在日本企业场景中，可以用一份有版本号的内部规程与一张定期报表做小范围验收。让业务人员给出容易混淆的表述、例外条件和预期查看角色，工程侧用少量可复查的样本积累边界。扩大文档数、订阅规模或使用人数之前，再补测延迟、成本与错误类型。

# B. 重点总结与可用于面试的知识

### 1. ローカルLLMのRAGが『資料からはわかりません』ばかり返す原因は、検索ではなかった（M1 Mac・25問で実測）

1. **中文：** 把每题的依据命中和答案判定分别记下来，区分缺证据与误拒答。
   **日本語：** 根拠の命中と正答を別々に記録します。

2. **中文：** 500字切分得到3段时，最多取4段无法检验大语料中的排序。
   **日本語：** 全断片を渡す条件では、大きな資料の順位付けを評価できません。

3. **中文：** 比较思考模式和提示词改动时，保留无答案题，并记录正确率与延迟。
   **日本語：** 応答時間に加えて、根拠のない質問に答えていないかも調べます。

### 2. Cloudflare D1で読み取り上限超過！NOT INの罠と99.8%削減・オフラインキャッシュ戦略

1. **中文：** 核对 LIMIT 前的扫描与排序，避免拿返回行数估算数据库配额。
   **日本語：** 返る件数だけで、読み取り行数は判断できません。

2. **中文：** 关联存在性判断利用复合主键，发布时间索引提供可提前停止的读取顺序。
   **日本語：** 複合主キーで照合し、公開日時の順序を利用します。

3. **中文：** 正常期内复用缓存与数据库故障时使用旧列表是不同策略。

### 1. しっくり（しっくり）｜N1

- 词性：副詞
- 含义：契合、协调，没有违和感的样子。
- 搭配：しっくり来る / しっくり合う / しっくりしない
- 文章语境：作者说明过去的产品组合与日常看数的用途不够契合。
- 例句：今の画面は、毎朝数字を見る使い方にしっくり来ます。
- 例句含义：现在这个界面很契合每天早晨查看数据的用法。
- 辨析：常用于感受、设计与关系上的契合感。「ぴったり」还可突出尺寸或数值正合适。

### 2. 落ちる（おちる）｜N5/N4

- 词性：動詞・上一段・自動詞
- 含义：未通过检查或考试。
- 搭配：検査で落ちる / 試験に落ちる / 審査に落ちる
- 文章语境：原文对无法测量的视频采取不放行处理。
- 例句：空の動画は、未計測として検査で落ちます。
- 例句含义：空视频会以未测量状态在检查中不通过。
- 辨析：此处为判断未通过的用法，以失败对象作主语，区别于主动剔除的「落とす」。参考N4，站内归入N5/N4。

### 3. 見せる（みせる）｜N5/N4

- 词性：動詞・下一段・他動詞
- 含义：给人看，使对方能看到。
- 搭配：数字を見せる / 根拠を見せる / 画面を見せる
- 文章语境：原文讨论报表要向谁展示什么内容。
- 例句：権限を確かめてから、利用者に数字を見せます。
- 例句含义：核实权限后，再给使用者展示数值。
- 辨析：强调让对方看见的动作。「表示する」可专指在画面上输出内容。参考N5，站内归入N5/N4。

## C-2. IT/AI专业词汇

1. **根拠命中（こんきょめいちゅう）**：答案所需的依据实际出现在传入片段里。 与模型回答是否正确分别打分。

2. **相関サブクエリ（そうかんサブクエリ）**：依赖外层当前行取值的子查询。 用于核对当前用户与文章的隐藏条件。

3. **一時Bツリー（いちじビーツリー）**：排序等处理临时使用的树形结构。 查询计划用它完成返回结果之前的排序。

4. **JSON Schema（ジェイソンスキーマ）**：声明数据类型、必填项等约束的格式。 借助yajsv在测试前验证YAML夹具。

5. **グレースケール（灰色の階調）**：用亮度等级描述图像的方式。 以固定大小的原始字节帧统计边缘像素。

6. **UNMEASURED（未計測）**：缺少所需测量数据的状态。 无法提取任何视频帧时使用。

7. **caller’s rights（呼び出し元の権限）**：按调用者自身的数据权限执行的方式。 共享报表瓦片据此限制读取范围。
