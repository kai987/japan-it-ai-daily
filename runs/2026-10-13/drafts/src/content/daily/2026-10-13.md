### 1. AIチューニングエージェントの設計：推論と決定論的探索を組み合わせる

**原文：** https://zenn.dev/kudan_jp/articles/e4607229e35382

**发布时间：** 2026-10-13 09:14:41 JST

Kudan 为采用 SLAM 技术的机器人开发导航软件，参数调优的一次离线实验可能耗费数小时乃至数日。瓶颈不仅是运行实验，还包括等待结果、判断原因、选择下一组参数。文章提出的目标是让反馈循环能够持续推进：AI 负责阅读源码与结果、提出可检验假设，确定性程序负责约束、记录和停止。它是架构设计稿，作者把最小实现与真实系统接入留给后续文章，不能据此声称已有性能提升比例。

传统网格扫描把人工列出的候选值作直积，容易复现并可无人值守，却不会阅读源码，也可能把计算量花在当前负载根本不经过的代码路径上。一次只改变一个参数的 OAT 方法还可能遗漏多个参数相互作用时才有效的组合。另一方面，LLM 的概率性行为也不适合承担严密的试验账本，更不能修改被调系统源码或既有试行记录。因此文章把职责切成 agent、engine、adapter 三层，而不是把完整优化流程交给对话。

适配器只连接一个目标系统、实现一次试行。describe 声明可调参数、真实基线、合法范围或枚举值、相关源码位置、预计时间与资源以及结果解释；run 接收已验证的一个候选并把输出写到约定位置；evaluate 把输出变成结构化数值与合否判定。这三操作由一个可执行文件提供，采用子进程边界可以跨语言接入，并不要求所有系统加入 Python 插件运行时。作者在此范围内认为无需额外 MCP 服务，这不是对所有 MCP 场景的否定。

评价时必须分开数值指标和必须满足的约束：先选出满足约束的结果，再比较主要目标，次要指标的取舍交给代理与人判断。文章明确不使用一个加权总分掩盖这些差别；缺失的指标也不能默默丢掉，必须说明它是结构上无法测量，还是再次执行可能获得。这样才能识别某些失败其实来自系统能力边界，而不是调参不够。

起点也有两个：源码默认值说明代码声明了什么，当前已部署值才说明真实系统正在运行什么。首个试行与改善比较要采用部署基线；默认值与基线的差异则用于提出假设。连续或整数轴中的 values[] 是优先候选，bounds 才是允许探索的范围；只给 values[] 仍会退化为候选点扫描。枚举按声明顺序探索邻近值，布尔与类别值则声明完整空间。kind 必须显式声明，不能从数值或真偽值猜测。

长期运行的对象应是独立保存的调优执行，而不是聊天记录。每次试行保存配置、结果、修改理由，并区分候选来自代理还是系统探索，其他人或另一个会话才能复核和恢复。停止条件包括试行次数、时间和资源上限，目标及约束达成，候选探索耗尽，或带理由的明确停止。文章没有提供数据集、硬件、提升率、成本或全局最优证明；其价值在于可审计的职责边界，不能把预期收益写成实测结论。

**阅读价值：** 适合学习 AI 推理与可审计实验控制如何分工，并练习把架构预期和实测证据分开。

### 2. Next.js（Pages Router）+ react-i18next で多言語化を実装する

**原文：** https://zenn.dev/socialplus/articles/f363cdf24340cf

**发布时间：** 2026-10-13 09:44:01 JST

Social PLUS 为 Shopify 等服务提供 Next.js 登录与会员注册画面，这次将原先单语应用扩展为多语言。文章采用 Next.js 16.3.8 的 Pages Router、i18next 21.9.2、react-i18next 11.18.6。选择后两者是因为内部其他应用已有用例，并非完成全面库比较后的最优结论；next-i18next 和按页面动态获取字典都没有在这次实现中采用。

业务前提是后端重定向到带语言前缀的路径，前端以该路径决定语言。next.config.mjs 声明 ja、en、zh-TW、ko，默认 ja，并设 localeDetection:false，避免由浏览器语言改变业务选择。示例中 /en/sites/... 用英文，无前缀的旧 URL 仍显示日文，/ja 也可显示日文，不支持的 /nl 路径返回 404。利用内置路由后不需要另加 locale 动态目录；页面从 useRouter().locale 读取语言。

在 _app 下放置 I18nProvider，将 router.locale 交给 i18next。基础实例的默认与回退语言均为 ja，并持有各语言资源；Provider 使用 cloneInstance 按语言克隆，再由 useMemo([locale]) 避免每次重新渲染都创建实例。由于翻译键直接采用日文原句，键中可能含冒号，所以设置 nsSeparator:false，防止它被当成命名空间分隔符。路由负责选择哪种语言，i18next 负责在该语言字典中取文案，两者不是同一个职责。

字典按组件分文件，先定义只有键的 template，日文字典把键直接作为值，其他语言字典则使用 typeof template 约束形状。增加键而遗漏译文会成为类型错误。合并各组件字典时，作者又从日文字典构建全局 Translation 类型，用递归的 StringifyLiterals 保留嵌套键、把字符串字面量改成 string，既能检查各语言是否都包含组件，又不把英文值错误地限制成日文原句。

t() 的参数同样受字典约束：CustomTypeOptions 扩展配合 useComponentTranslation 包装 useTranslation，以 keyPrefix 把组件名和文案键绑定，未知键会产生类型错误。这里必须保留版本条件：文章在 react-i18next v11 扩展 react-i18next 模块；v12 起 CustomTypeOptions 移到 i18next，不能把示例模块声明不加调整地当成新版通用做法。官方资料用于核对这条兼容边界，而不是替换文章的已用版本。

本次没有按页面延迟加载字典，也没有给出包体大小、首屏、切换耗时、SSR 水合或 SEO 的测量结果。编译期检查能发现键缺失与结构不一致，但不能证明译文自然、文字长度合适或日期格式全面正确。可迁移做法是让语言选择有唯一业务来源，并分别检查旧 URL、未支持语言、字典键和真实渲染；这些是本文基础上的验证建议，不是作者已经全部完成的测试。

**阅读价值：** 直接服务 React/Next.js 面试：解释路由、实例生命周期与类型约束的分工，并保留版本边界。

### 3. 耐量子暗号ML-KEMとは？Cloudflare WorkersのWeb Cryptoで共有秘密を生成・復元してみた

**原文：** https://dev.classmethod.jp/articles/workers-ml-kem-local-shared-secret/

**发布时间：** 2026-10-12 21:42:05 JST

ML-KEM 是密钥封装机制，作用是让双方建立共享秘密，再供对称密码等后续机制使用，而不是直接把业务数据加密。它源于 CRYSTALS-Kyber，安全性与模块格上的困难问题有关，NIST 在 2024 年 8 月发布 FIPS 203。原文区分这种机制、常见 TLS 密钥交换与具体 Workers API；耐量子目标不等于对任意使用方式作绝对安全保证。

标准包含 512、768、1024 三组参数，表中共享秘密均为 32 字节。Workers 当前支持 ML-KEM-768 与 1024，而文章只测试 768：其公钥长 1184 字节、封装密文长 1088 字节。不能把共享秘密长度和封装密文长度混为一谈，也不能把另外两组标准参数的存在当成当前平台都可调用。

调用链分三步：generateKey 创建密钥对，encapsulateBits 使用公钥产生 sharedKey 与 ciphertext，decapsulateBits 使用私钥和封装密文恢复共享秘密。作者把生成方与恢复方放在同一个 Worker 请求里，逐字节比较两段秘密；返回算法、长度和 equal，不输出秘密本身。这是本地往返验证，没有实现两台机器之间的业务加密通道、TLS 握手或用户身份验证。

实验于 10 月 11 日在 Ubuntu 24.04.5 LTS aarch64 的一次性 Docker 容器中执行，Node 24.21.0、npm 11.19.0，初始 Wrangler 4.146.0 / workerd 1.20261001.1。配置 compatibility_date 为 2026-10-01，并显式加入 webcrypto_modern_algorithms。结果为 HTTP 200，原始与恢复秘密均为 32 字节、密文 1088 字节、equal:true。作者也在 Wrangler 4.149.0 / workerd 1.20261006.1 复核标志的有无。

删除标志后，保持同样代码和兼容日期，本地 generateKey 报 NotSupportedError，返回 HTTP 500。因此兼容日期不能替代显式启用条件。Cloudflare 的官方兼容资料同样把此功能列为 flag，并说明它实现的是仍在演进的现代 Web Crypto 草案的子集，API 可能改变；文章不能被解释为某个日期后自动默认可用。

作者未部署到 Cloudflare 正式运行时，也没有测量耗时、吞吐量、密文传输开销或对接其他客户端。1024 参数、不同系统和真实网络通信同样不在本次实验内。可迁移知识是区分密钥建立、业务加密和身份认证，连同版本、标志和负向案例保存验证范围。本日报复核原文与官方定义，没有独立执行其中的密码实验。

**阅读价值：** 练习把密码原语、平台启用条件和端到端安全验收分开，避免用成功响应代替系统验证。

### 4. pnpm 12.11のRust toolchain管理を試す：rust-toolchain.tomlからcargo、pnx、グローバル導入まで

**原文：** https://dev.classmethod.jp/articles/pnpm-12-11-rust-toolchain-management/

**发布时间：** 2026-10-12 21:23:19 JST

pnpm 12.11.0 在 10 月 9 日加入 Rust 工具链管理，同日 12.11.1 补充 pnx --package=rust@<channel>。但 cargo.enabled 以及 crate 管理此前已存在，且默认关闭、仍是实验性功能，不能把两者都写成当天新功能。作者于 10 月 11 日使用 pnpm 12.11.1，选择 Ubuntu 24.04.5 LTS aarch64 Docker、Node 24.21.0，并故意从没有 rustup、cargo、rustc 和 cc 的环境开始。

启用 cargo.enabled 后，pnpm install 读取当前项目或上层最近的 rust-toolchain.toml，按 channel、profile、components、targets 准备 Rust。示例固定 Rust 1.95.0 与 minimal profile，工具链放入 pnpm store 的 rust 目录，通过 .pnpm/rust 链接；pnpm run 和 exec 把它加入 PATH。pnpm add rust@1.95 修改的是工具链文件，不是给 package.json 安装一个名为 rust 的普通 npm 依赖。

作者加入 itoa crate，Cargo.toml 中为 1.0.18，并通过 .cargo/config.toml 引入 .pnpm/crates/config.toml，使 crates.io 来源可指向下载后的 vendor 目录。这种配置 include 要求 Cargo 1.95 以上。Rust crate 的版本仍记录在 Cargo.lock 中，pnpm-lock.yaml 没有 itoa。这里统一的是下载与工具链入口，不是把 Rust 的依赖语义全部转换成 npm 的锁文件。

在空缓存的该容器中，初次准备工具链与 crate 约耗 48.6 秒，随后安装约 116 毫秒，工具链和 crate 占用 store 约 513 MB。这些是特定缓存与网络条件的观察，不是普遍速度承诺。离线原生构建能编译 crate，但最终因 linker cc 缺失而失败：有 rustc 和 cargo 并不等于操作系统的链接环境已齐备。

加入 wasm32-wasip1 target 后，pnpm 根据不同配置选择新的 store 工具链目录和链接，相关安装耗时约 41.7 秒。作者阻断 crates.io DNS 后，示例的该目标离线构建成功，并用 Node WASI 执行验证输出。pnx 可临时运行 dated nightly，重复调用使用缓存，不改变项目的 1.95.0；全局 1.94.0 与项目 1.95.0 也分别生效。这些对比说明入口与缓存边界，但只涉及简单 itoa 示例，不能推出任意仓库都可断网构建。

path、自定义链接工具链、缺少 channel 或其他 profile 的情况按文档交还 rustup；runtimeOnFail 设为 error、warn、ignore 会关闭 pnpm 工具链管理。作者只测试没有 rustup 时的 ignore，最终 cargo metadata 找不到 cargo 而失败，不能理解为自动忽略所有故障。Rust 发布签名、哈希验证、移动 channel 的每日检查是官方声明，原文未注入错误实测。镜像、Git crate、不同平台、rustup 共存和复杂项目均未验证，迁移时应分别检查这些前提。

**阅读价值：** 适合解释可复现工具链、缓存、依赖锁和系统链接器各自解决什么，保留成功与失败条件。

### 5. ServiceNow Voice with Amazon Connect で発信者電話番号から Consumer 情報を自動紐付けできるか試してみた

**原文：** https://dev.classmethod.jp/articles/servicenow-voice-amazon-connect-consumer-phone-matching/

**发布时间：** 2026-10-13 09:17:19 JST

作者在已有 ServiceNow PDI 与 Amazon Connect 标准连携的基础上，进一步检验发信者号码能否对应到 CSM 的 Consumer 个人客户。Interaction 是电话或聊天等接触记录，作用接近 Connect Contact，但不能把两套对象当成完全相同的表结构。文章是在前一篇配置完成之后的增量实验，不能省略这些环境前提而宣称新实例开箱即用。

测试首先创建 Consumer，并在 Mobile phone 登记用例号码。此前服务账户有 sn_cti_core.service、flow_operator、sn_customerservice_agent 三个角色；本次为号码查询再加 sn_customerservice.customer_data_viewer，才确认关联正常。官方资料说明该角色可读取 account、consumer、household 及相关列表客户数据，这与能操作 Interaction 的权限不是一回事。部署判断应复核客户数据访问范围，而不是仅因消除错误就扩大所有权限。

从登记号码拨入时，OpenFrame 软电话在响铃阶段只显示电话号码，作者没有确认客户信息弹窗。通话完成后，Interaction 的 Consumer 字段出现链接，进入详情后匹配到该测试客户。这里必须分别说明来电中和通话结束后的界面：后者有记录关联，并不能推出前者已经实现实时客户卡片。

关联后，Consumer 的 Customer Information 中可看到联系信息、优先案件和最近聊天，History 时间线与 Interactions 列表也可以追踪通话。因而验证不止观察一个字段，而是从 Interaction 与 Consumer 两个方向回读记录。文章没有提供关联延迟、吞吐量、负载或不同实例版本的对照数据。

作者另建一个相同号码的 Consumer 后，这次观察到记录仍关联先创建的客户，没有关联第二个。该小例子不能证明系统公开规定了通用的先建优先算法，但足以说明号码不唯一时不能期待自动识别用户意图。客服流程应明确重复号码的处理与人工选择；把匹配号码当成身份已验证，也是本文事实不能支持的进一步推断。

本文只确认所用 PDI 与既有集成下的登记号码、所加角色、结束后关联以及一次重复用例。未登记号码、规模化重复数据、生产权限配置和实时弹窗都未完成验证。可迁移结论是把访问权限、生命周期时点、记录回读与唯一性分别验收。本日报保留这些观察，没有复跑原文中的电话或改动任何客户数据。

**阅读价值：** 用实际界面时点与重复案例理解集成验收，避免把号码匹配等同于实时展示或本人认证。

## C-2. IT/AI 专业词汇

1. **OAT / grid sweep（一軸ずつの調整・格子状の候補探索）**：OAT 每次只变一个轴；grid 作候选直积。 可能遗漏交互作用，不能当成读源码推理。

2. **values[] / bounds（優先候補・許容範囲）**：连续或整数参数的优先值与合法空间。 候选列表不等于整个允许范围。

3. **cloneInstance（翻訳インスタンスの複製）**：从基础 i18next 实例产生特定语言实例。 useMemo 的依赖是 locale。

4. **CustomTypeOptions（辞書の型拡張）**：让翻译键受资源结构约束的类型扩展。 v11 与 v12 以后的声明模块不同。

5. **ML-KEM（格子に基づく鍵カプセル化）**：建立共享秘密的密码机制。 本例是 768 本地封装与解封装，不是业务加密。

6. **rust-toolchain.toml（Rustツールチェーンの指定ファイル）**：声明 Rust channel、组件与目标。 pnpm 下载入口统一后仍须独立考虑 cc。

7. **Cargo.lock（Rust依存のロックファイル）**：保存本例 crate 依赖的版本记录。 pnpm-lock.yaml 中未出现 itoa。
