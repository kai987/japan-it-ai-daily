### 1. Claude Code on the web で複数リポジトリを接続する：CLAUDE.md・Skillsの挙動

**原文：** https://dev.classmethod.jp/articles/claude-code-web-multiple-repositories/

複数リポジトリを接続したとき、指示が読み込まれることと、同じ名前のスキルが意図どおり選ばれることは別問題です。この記事では Claude Code 2.1.278 の Web 環境で、二つのリポジトリを A→B、B→A の順に選び、それぞれ一回ずつ試しています。両方のルートと `.claude/CLAUDE.md` に置いた指示が初期回答に反映され、さらに各リポジトリの生成ファイルと Draft PR の差分でも内容が確かめられています。単なる自己申告で終えない検証になっています。

環境変数 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` が設定されていたことも、この結果を説明する条件です。ローカル CLI の任意の構成まで同じだと推奨する根拠にはなりません。固有名の `probe-a` と `probe-b` は呼び出せましたが、同名の `shared-probe` は先に選んだリポジトリ側が使われました。ただし各条件一回なので、今後も変わらない優先規則と誤認するべきではありません。自動呼び出しを止める設定と、手動でスキルを使えるかどうかも切り分ける必要があります。

フロントエンドと API を別々のリポジトリで開発する現場なら、リポジトリ名を含むスキル名と、指示の適用先を明記する運用が考えられます。使いこなすには、会話に指示が現れたかだけでなく、どのファイルへ何を書き込んだかを確かめます。これは本稿の実務上の提案であり、新たな動作保証ではありません。掲載された実験の本文とコードは確認していますが、私たちが環境を起動して再現したわけではありません。

**読む価値：** 二つのリポジトリの指示と同名スキルを通じて、適用範囲と差分による検証を学びます。

### 2. Strands Agentsに「Strands harness」が追加されました！

**原文：** https://dev.classmethod.jp/articles/strands-harness-vs-agent/

Strands harness は、既存の Agent に実用的な初期構成を与える仕組みとして読めます。記事の条件は Python 3.13.13、`strands-harness 0.1.2`、`strands-agents 1.57.0` です。`create_harness()` から作ったエージェントには十二個のツールと `SnapshotSessionManager` が入り、CSV の集計をシェルで行って報告ファイルを書き出しています。一方で比較対象の `Agent()` にはツールを渡していません。結果の違いは構成の差であり、同じ能力を与えたモデル同士の優劣ではありません。

会話を続ける仕組みと、別の会話から過去の事実を取り出す仕組みも区別できます。既定では `.agent` に保存し、新しい会話では `search_memory` が使われました。別の例では `AgentCoreMemorySessionManager` に保存と検索を任せ、Harness 側を `memory=False` にしています。検索の `top_k=5` と関連度 `0.3` はこの例の設定です。保存先を統合する場合も、どちらが履歴と長期記憶を管理するかを曖昧にしないことが大切です。

簡便な設定でも、最終的なツール一覧は別途調べます。`builtin_tools` を三つに絞った例に、プラグイン由来の四つが残る点は重要です。`interventions="ask"` では実行前に中断し、`interruptId` を含む `interruptResponse` で続きを処理します。業務画面には承認待ち、拒否、再開の状態を表現する必要があります。記事が外部ブログから紹介したコスト削減率は独立に検証していないため、ここでは効果として採用しません。初期構成の便利さを、権限や記憶の安全性の保証に置き換えないことが面接の論点です。

**読む価値：** 既定のエージェント構成、記憶の保存先、実行前の承認を具体的に点検できます。

### 3. Cognito で AdminInitiateAuth を使ったときの SSO を試してみた

**原文：** https://dev.classmethod.jp/articles/slug-aws-cognito-sso-oidc-adminInitiateAuth/

同じ Cognito ユーザープールを使っていても、サーバー側で認証しただけでブラウザの SSO が成立するとは限りません。記事の A アプリは独自フォームから `AdminInitiateAuth` を呼び、自分の `a_session` を設定します。B アプリは OIDC の RP として `/oauth2/authorize` へブラウザを移します。A で認証済みでも、ブラウザは Cognito ドメインでログインしていないため、B への移動時にログイン画面が表示されました。

注意すべきなのは、Cookie があることとログイン済みであることの隔たりです。ログイン画面を開くだけでも `cognito` Cookie が発行されますが、その状態では再び認証が求められました。ログイン後には値が変わり、B のアプリ独自セッションだけを破棄しても Cognito 側のセッションで再認証できます。調べる場所は、認可リクエストの宛先と Cookie を確認できる Network タブです。トークンを得たこと、画面が切り替わったこと、認証基盤のセッションが有効なことを同一視しません。

A もマネージドログインへそろえる方法と、A を変えられない場合に SaaS が別途提供する SSO を検討する方法を、製品要件に応じて説明できます。ただし後者の対応可否は SaaS 次第です。掲載コードはメモリ上のセッションを使い、RP で JWT 署名検証を省いているため、本番へそのまま持ち出す構成ではありません。実務では署名、有効期、クライアントの制約と安全なセッション管理を別に整えます。Web 開発の面接では、画面上のログイン表示よりも認証状態の所在を説明できることが役立ちます。

**読む価値：** トークンと二種類のセッションを区別し、SSOが成立する条件を説明できます。

### 4. Kiro Crew の Auto (Jev) によるモデルルーティングをローカル Kev で試してみた

**原文：** https://dev.classmethod.jp/articles/kiro-crew-auto-jev-model-route-local-kev/

Kiro Crew の Auto (Jev) は、質問の複雑さを判定してから回答用のモデルを選ぶ二段階の構成です。記事では M4 Pro 上の MLX で Kev 4B を動かし、Apple container 内の Crew 0.7.1／kiro-cli 2.24.0 から `/v1/systemone` を呼びます。返された simple、medium、complex を `decisions.model_route` に対応付けます。互換名 `jev-latest` を受け付けるため、名称だけを見て遠隔の Jev を呼んでいると判断しないことが重要です。

判定の待ち時間は既定の 1000ms から 5000ms に延ばしています。endpoint と利用者の同意を結び付け、接続先を変更すると同意が外れることも説明されています。ホストのサービスをコンテナから到達可能にする設定では、Bearer 認証を加えても HTTP の内容が暗号化されるわけではありません。記事自身が信頼できるネットワークに用途を限っています。記載されたサンドボックスの互換性対処も、一般に隔離を弱めてよいという推奨ではありません。

三つの例の判定時間は 367ms、433ms、1291ms でした。`model_chosen`、`applied`、`model_used` を照合し、選択モデルが実際に使われたかを確認しています。ただし三件では平均的な精度や P95 は出せませんし、掲載ログの実行日と記事の公開日は異なります。判定処理をローカルに置いても、回答生成までローカルになるわけではありません。面接では、段階別の送信先、タイムアウト時の扱い、選択と実行を分けた監査を説明すると、運用上の判断が伝わります。

**読む価値：** 判定と実行のログを照合し、ローカル化の範囲と送信先を整理できます。

### 5. AWS Backupの復旧ポイントからEC2を別のAZへ、プライベートIPを指定してリストアする

**原文：** https://dev.classmethod.jp/articles/202609-aws-backup-ec2-restore-to-another-az/

AWS Backup による EC2 復元では、ジョブが終わったことと、目的の場所で業務を再開できることを分けて考えます。この記事は、東京リージョンの同一 VPC 内で別 AZ のサブネットへ復元し、未使用のプライベート IP を指定する例です。コンソールでは指定できない IP を扱うため、`get-recovery-point-restore-metadata` で設定を取り出し、`start-restore-job` に渡しています。例の `10.2.1.54` から `10.2.2.54` への変更は、移動先の CIDR に合わせたアドレス変更です。

`Placement` と `NetworkInterfaces` の値は JSON 文字列なので、そのまま子の項目を変更できません。`fromjson` でオブジェクトに戻し、AZ、サブネット、主 IP を設定してから再び文字列にします。元の `NetworkInterfaceId` と競合する外側のネットワーク項目も残さないようにします。この例ではインターフェース側のセキュリティグループを維持していますが、複数の NIC を持つ構成まで無条件に同じ手順で扱えるとは限りません。

ジョブの `COMPLETED` を確認したうえで、EC2 の配置と IP、EBS ボリュームの AZ を照合しています。停止保護、自動復旧、タグなど、引き継がれない設定の再設定も必要です。堅実な復旧訓練にするなら、通信、業務の正常性、接続先の切り替え、復旧時間を別の受け入れ項目にします。これらは本稿の提案で、記事がすべて実施済みという意味ではありません。同じ復元意図の再試行と、新しい復元の開始も区別し、余裕を持って結果を追える記録を残します。

**読む価値：** 復元メタデータの型と復元後の確認から、別AZへの復旧手順を組み立てます。

## 5. 面接復習カード

### Q1

> エージェントに指示やツールを渡したことと、安全に実行できることをどう区別しますか。

**回答要点：** 複数リポジトリの実験は二つの順序での観測であり、同名スキルの優先規則を保証しません。Harnessでも指定した組み込みツールと最終的なツール集合は別です。実ファイルの差分、ツールの列挙、承認による中断と再開を確認します。

### Q2

> 認証やモデル選択で、途中の成功を最終結果と誤認しないために何を追跡しますか。

**回答要点：** APIのトークン、アプリのCookie、認証基盤のログイン済みセッションを分けて観測します。ルーティングではmodel_chosen、applied、model_usedを照合し、判定がローカルでも応答生成までローカルとは限らない点を確認します。

### Q3

> 別AZへの復旧訓練を、リストアジョブの成功だけで終了してはいけないのはなぜですか。

**回答要点：** COMPLETEDは復元処理の状態です。EC2とEBSのAZ、サブネット内の未使用IP、通信、引き継がれない停止保護やタグなどを確かめます。業務の正常性や接続先の切り替え、復旧時間は別の受け入れ項目であり、記事の結果だけでは完了したと言えません。

# B. 記事から整理する要点と面接知識

### 1. 記事1・2：使えることと許可することは同じではない

指示が会話に現れたかに加えて、生成ファイルにどう反映されたかを確認します。ツールの指定も、プラグインを含む最終的な一覧とは分けて考えます。面接では同名スキル、追加ツール、中断と再開という具体例を使い、差分や承認記録がなぜ必要かを説明します。

### 2. 記事3：認証状態を持つ場所を特定する

APIの戻り値とアプリのセッション、認証基盤のセッションには異なる役割があります。CognitoのCookieがあるのにログインが必要だった例から、名前や存在だけで状態を決めないことを学べます。ブラウザが訪れたドメインと、認可リクエストに送った内容を追うのが具体的な調査手順です。

### 3. 記事4・5：選択と実行結果を対応付ける

model_chosenとmodel_usedの照合は、選んだものが本当に使われたかを確かめる作業です。EC2とEBSの配置確認も、ジョブ完了が目的の構成につながったかを確かめます。三件の例を一般的な精度と呼ばず、インフラ復元を業務復旧と呼ばないように、証拠の範囲を保った説明が大切です。

# C. 日本語学習

語彙は新規10語と復習10語の計20語、文法は新規0項目と復習8項目の計8項目です。復習は当日の本文と全履歴から実際に算出した結果であり、8項目は上限です。JLPTレベルは学習上の目安であり、公式語彙一覧を示すものではありません。以下の例文は本稿の学習用作文で、外部記事の引用ではありません。

## C-1. 今回の新規語彙

### 1. 統合する（とうごうする）

**品詞：** 名詞・サ変動詞　**参考レベル：** N1

**意味：** 分かれている仕組みや情報をまとめ、一つのまとまりとして扱えるようにすること。

**よく使う形：** 保存先を統合する ／ 認証基盤を統合する ／ 情報を統合する

**ITでの使い方：** 会話と長期記憶を一つの保存基盤へまとめる場面で使えます。ただし保存場所をまとめても、管理する責任まで自動的に一つになるわけではありません。

**学習用例文：**

> 会話と長期記憶の保存先を統合する前に、それぞれの管理責任を決めます。

**例文の意味：** 二種類の情報をまとめて保存する場合でも、誰がどの情報を管理するかを先に決めるという意味です。

**使い分け：** 「集める」よりも、まとまりのある仕組みにする意味が強くなります。単に一か所へ置くだけなら「集約する」が適切な場合もあります。

### 2. 推奨する（すいしょうする）

**品詞：** 名詞・サ変動詞　**参考レベル：** N1

**意味：** 条件に照らして望ましいと考える方法を勧めること。

**よく使う形：** 設定を推奨する ／ 方式を推奨する ／ 利用を推奨する

**ITでの使い方：** 技術文書では、理由と適用条件を添えて使います。一回動いたことだけでは、すべての環境に勧める根拠にはなりません。

**学習用例文：**

> 単発の成功だけを根拠に、同じ設定を全社へ推奨することは避けます。

**例文の意味：** 一度うまくいった設定でも、他の部署や環境で同じように使えるとは決めないという意味です。

**使い分け：** 「おすすめする」より改まった言い方です。「推奨」は通常、義務や必須条件とは区別します。

### 3. 誤認する（ごにんする）

**品詞：** 名詞・サ変動詞　**参考レベル：** N1

**意味：** 実際とは違う状態や意味だと思い込んで認識すること。

**よく使う形：** 状態を誤認する ／ 成功と誤認する ／ 別人と誤認する

**ITでの使い方：** Cookieの存在をログイン済みの証拠だと思うような場面に使えます。何を何として捉えたのかを明記すると、誤りの所在が伝わります。

**学習用例文：**

> Cookieが存在するだけで、利用者が認証済みだと誤認してはいけません。

**例文の意味：** Cookieが付いていても、ログインが完了した状態とは限らないという注意です。

**使い分け：** 話の趣旨を取り違えた場合は「誤解する」、状態や対象の判別を誤った場合は「誤認する」が使いやすい表現です。

### 4. 読み込む（よみこむ）

**品詞：** 動詞・五段　**参考レベル：** N2

**意味：** プログラムがファイルなどの内容を取り込むこと。文脈によっては文章を十分に読む意味にもなります。

**よく使う形：** 設定を読み込む ／ 履歴を読み込む ／ ファイルを読み込む

**ITでの使い方：** 設定や会話履歴を取り込む操作に使います。読み込み、解釈、実行の各段階を分けると、障害の説明が正確になります。

**学習用例文：**

> 履歴を読み込んだ後に、保存先が想定したセッションのものかを確認します。

**例文の意味：** 取り込んだ内容が別の会話の履歴ではないかを確かめる、という確認手順です。

**使い分け：** コンピューターの話では取り込みの意味が中心です。「仕様書を読み込む」なら、内容を深く理解するために読む意味になります。

### 5. 書き込む（かきこむ）

**品詞：** 動詞・五段　**参考レベル：** N2

**意味：** 決められた場所やファイルなどへ情報を入れて残すこと。

**よく使う形：** ファイルに書き込む ／ 設定を書き込む ／ 結果を書き込む

**ITでの使い方：** 変更先と内容を一緒に述べると、操作の対象が明確になります。エージェントの説明では、書き込みの申告と実際の差分を分けます。

**学習用例文：**

> 生成した設定を本番ファイルに書き込む前に、差分の承認を受けます。

**例文の意味：** 生成物をそのまま反映せず、どこが変わるかを見てもらってから保存するという意味です。

**使い分け：** 「書き出す」は外部へ出力する動作に焦点があり、「書き込む」は情報を入れる先に焦点があります。

### 6. 持ち出す（もちだす）

**品詞：** 動詞・五段　**参考レベル：** N2

**意味：** ある場所や管理範囲の外へ物や情報を移すこと。また、話題として取り上げること。

**よく使う形：** 資料を持ち出す ／ 社外へ持ち出す ／ 話題を持ち出す

**ITでの使い方：** 検証専用のコードを本番へ移す場面や、資料を社外へ移す場面で使えます。今日の例では管理範囲の外へ出す意味に限ります。

**学習用例文：**

> 検証用の認証コードを、確認せずに本番環境へ持ち出すことはできません。

**例文の意味：** 検証のために省いた安全確認をそのまま残して、本番で使ってはいけないという意味です。

**使い分け：** 「会議で別の問題を持ち出す」では、問題を話題にする意味になります。目的語と移動先で用法を見分けます。

### 7. 使いこなす（つかいこなす）

**品詞：** 動詞・五段　**参考レベル：** N1

**意味：** 仕組みや特徴を理解し、目的に合う形で十分に使えること。

**よく使う形：** ツールを使いこなす ／ 機能を使いこなす ／ 複数の環境を使いこなす

**ITでの使い方：** 単に起動できるだけでなく、得意なことと制約を理解して扱う意味があります。面接では、何をどう判断したかを例で示すと伝わります。

**学習用例文：**

> エージェントを使いこなすには、成功例だけでなく拒否された場合の動きも理解します。

**例文の意味：** 便利な機能に加えて、動けないときの扱いまで理解して利用するという意味です。

**使い分け：** 「使い込む」は繰り返し十分に使うことに重点があり、「使いこなす」は適切に扱える能力に重点があります。

### 8. 簡便（かんべん）

**品詞：** 形容動詞　**参考レベル：** N1

**意味：** 手間が少なく、扱いやすいこと。

**よく使う形：** 簡便な手順 ／ 簡便に試す ／ 簡便な設定

**ITでの使い方：** 初期設定や手順の手軽さを説明するときに使います。操作が簡単なことと、安全性が十分であることは別に評価します。

**学習用例文：**

> 簡便な初期設定であっても、実行できるツールの範囲は点検します。

**例文の意味：** 手軽に始められる場合でも、どこまで操作できるかの確認は省かないという意味です。

**使い分け：** 「簡単」と近い言葉ですが、手軽さや便利さを説明する改まった文章で使いやすい表現です。

### 9. 堅実（けんじつ）

**品詞：** 形容動詞　**参考レベル：** N1

**意味：** 無理な期待や大きな冒険を避け、確かさを重視して進めること。

**よく使う形：** 堅実な運用 ／ 堅実に進める ／ 堅実な設計

**ITでの使い方：** 復旧訓練や導入計画を、確かな手順で進める姿勢を表せます。単に作業速度が遅いという意味ではありません。

**学習用例文：**

> 復元後の通信と設定を確かめる手順が、堅実な復旧を支えます。

**例文の意味：** 処理完了の表示だけで終えず、使える状態まで確かめることが確実な復旧につながるという意味です。

**使い分け：** 「慎重」は注意深さに、「堅実」は確実さを重んじる方法や姿勢に重点があります。

### 10. 余裕（よゆう）

**品詞：** 名詞　**参考レベル：** N2

**意味：** 必要な量や時間を満たしたうえで、さらに残っているゆとり。

**よく使う形：** 時間に余裕がある ／ 容量に余裕を持たせる ／ 余裕を持って進める

**ITでの使い方：** メモリや待ち時間、復旧計画に使える表現です。余裕を持たせる量は測定と要件から決め、無制限に増やせばよいとは考えません。

**学習用例文：**

> 判定時間のばらつきを調べ、応答期限に余裕があるかを評価します。

**例文の意味：** 平均値だけでなく変動も考慮して、期限までに処理できるかを確認するという意味です。

**使い分け：** 気持ちの落ち着きを表す場合もあります。技術文書では時間、容量などの対象を添えると明確です。

以下の8項目は技術用語です。新規語彙や復習語彙の件数とは別に扱います。

### 1. Instruction scope｜指示の適用範囲

指示がどのディレクトリや操作に対して適用されるかという範囲。

**記事での文脈：** 複数リポジトリのCLAUDE.mdを使うときは、指示の対象と実際の変更先を照合します。

### 2. Skill name collision｜スキル名の衝突

同じ名前のスキルが複数あり、どれを使うかが曖昧になること。

**記事での文脈：** 記事の二つの順序での結果にとどめ、恒久的な優先順位として一般化しません。

### 3. Harness｜エージェントの実行基盤

ツール、指示、会話や文脈の管理を組み合わせてエージェントを動かす仕組み。

**記事での文脈：** Strandsの例では初期構成が用意されますが、実際のツール一覧と保存先を点検します。

### 4. Interrupt / resume｜中断と再開

処理をいったん止め、必要な入力を受けて対応する位置から続ける仕組み。

**記事での文脈：** 承認待ちの識別子と応答を対応させ、拒否した操作が実行されないことも確認します。

### 5. IdP session｜認証基盤のセッション

認証を提供する側が、ブラウザのログイン後に維持する状態。

**記事での文脈：** アプリ独自のセッションやAPIで得たトークンと混同せず、認可先へのCookieを確認します。

### 6. Model routing｜モデルの振り分け

依頼の特徴や方針に応じて、回答を担当するモデルを選ぶこと。

**記事での文脈：** 選んだモデルと実際に使われたモデルを分けて記録し、判定と応答の送信先も確認します。

### 7. Restore metadata｜復元メタデータ

復元先の配置やネットワークなどを指定するための設定情報。

**記事での文脈：** 例ではJSON文字列を展開して変更し、再び文字列へ戻して復元APIに渡します。

### 8. Idempotency token｜冪等性の識別子

同じ操作の再送を区別し、重複した実行を避けるための識別子。

**記事での文脈：** 同じ意図の再試行と新規の復元を分け、ジョブIDとあわせて結果を追跡します。
