### ① 企業資産の「36％」が“脆弱性ゾーン”で放置　AI攻撃時代に旧来の防御モデルは限界か： 「重要資産を重点的に守る」は通用しない？　最新調査が明かす限界

**出典：＠IT｜2026年9月7日 08:00**  
**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2609/07/news017.html

EYのGlobal Cybersecurity Leadership Insights Study 2026は、経営層・Security責任者840人を対象に調査した。記事によると、企業Assetの平均36％が、存在や依存関係の可視性とSecurity Coverageの両方が不十分な「Vulnerability Zone」に入っている。カテゴリ別ではOT / Physical Asset 57％、Third-party / Ecosystem 49％、AI System / Tool 47％、Network Infrastructure 38％だった。

重要なのは、AIを使う攻撃者が「忘れられたAsset」「古いID」「設定不備」を高速に探索し、侵入の足掛かりとして組み合わせられる点だ。したがってCrown Jewelだけを重点的に守る考え方では不十分で、Asset Inventory、Dependency Visibility、Identity、Third-partyまで含めて継続的に可視化し、Controlを更新する必要がある。EYが示す“Secure Creator”ではVulnerability Zoneの平均が約30％で、その他の企業は約42％だった。

**注目ポイント：★★★★★**

AI Securityを「新しいAI攻撃だけへの対策」と捉えず、既存の未管理AssetやIdentityの発見速度が上がる問題として考えられる。面接では、**Asset Inventory → Dependency Mapping → Identity / Third-party → Continuous Control → Cyber Resilience**という流れで説明しやすい。

### ② Claude Fable 5.1 + EFS で企業 AI を安全に実装 — ZDR ロードマップ

**出典：Zenn｜2026年9月6日**  
**原文：** https://zenn.dev/kashiwabaray/articles/25d934bfd1a5c9

記事はClaude Fable 5.1をEnterpriseで利用する際のData RetentionとEnterprise Frontier Safeguards（EFS）を整理している。Fable 5.1は複雑なReasoningやAgent Workloadを想定したFrontier Modelで、記事では公開情報として1M Context、最大128K Output、Input $10/M、Output $50/M、Cache Readが$1.00/Mから$0.25/Mへ下がった点などを扱う。EFSはCustomer-owned Cloud Storage、Customer-managed Encryption、Automated Safety Monitoringなどを組み合わせ、Frontier CapabilityとEnterprise Governanceの両立を狙う。

記事内のBedrock Playground実測では、同一の数学問題にFable 5.1とFable 5がともに正答した。単一RunではFable 5.1のOutput Tokenが1402対1468、Latencyが15068ms対19472msだったが、著者自身が「1回の結果を一般化できない」と明記し、複数回・中央値での再測定を求めている。また、Retention設定を変更する前はModelが利用できなかったことから、**Model QualityとEnterprise Eligibilityは別の問題**だと分かる。

**注目ポイント：★★★★★**

Enterprise LLMの採用順序は、**Data / Compliance → Capability → Quality → Latency / Cost**と考える方が安全である。Vendor Benchmark、単発実測、Production WorkloadをEvidence Levelとして分けて扱う姿勢も実務的だ。

### ③ 三菱UFJグループ会社、DBコストを87％削減――なぜ「Aurora Serverless」ではなく「Aurora DSQL」を選んだ？：同じサーバレスでも何が違った？

**出典：＠IT｜2026年9月7日 08:00**  
**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2609/07/news026.html

三菱UFJフィナンシャル・グループのJapan Digital Design（JDD）は、新しいDocument Search SystemでAmazon Aurora DSQLを採用した。夜間にPDF / Web Dataを集中的に処理し、約1800個のECS Taskが並列に動き、1晩で10万件を超えるFile / Recordを書き込む。一方、日中はWeb ApplicationからのReadが中心で、Production / Staging / Developmentを含む複数Environmentを維持する必要があった。

Aurora ServerlessでCold Startを避けるため最小ACUを0.5にすると、利用していない時間にもEnvironmentごとに固定Costが発生する。Aurora DSQLは長時間未使用時にResourceをほぼゼロまで縮小でき、再接続時に自動で立ち上がる。JDDはこの比較条件でDatabase Costを約87％削減し、運用負荷もほぼゼロになったと報告している。さらにData量が約10倍へ増えた際にもDB Parameterの再調整を行わず、性能劣化は確認されなかったという。なお、同一Recordを高頻度で同時更新しないこと、Analytics / Aggregate中心ではないことも採用前に確認している。

**注目ポイント：★★★★★**

「Serverless」というラベルだけでCostを比較してはいけない好例である。**Idle Cost、Burst Concurrency、Transaction Pattern、Environment数、Team Skill、将来Scale**をWorkload単位で見る必要がある。87％という数字も、この特定構成との比較結果として理解するのが重要だ。

### ④ Prometheusとの関係から整理、なぜGrafanaは「OpenTelemetry」を推進する？：オープンへ向かうオブザーバビリティー（1/2 ページ）

**出典：＠IT｜2026年9月7日 05:00**  
**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2609/07/news010.html

記事はGrafanaとPrometheusの歴史的な関係から、Grafana LabsがOpenTelemetryを推進する理由を整理している。GrafanaはVisualization / Dashboardを中心に普及し、PrometheusのMetricsと組み合わせて使われることが多かった。その後Grafana LabsはMetricsのMimir、LogsのLoki、Distributed TraceのTempoへBackend領域を広げた。

それでもPrometheus CompatibilityやOpen Standardを重視する理由は、Telemetry Dataを特定Vendorへ閉じ込めず、将来のBackend変更や複数Backend併用を可能にするためだ。OpenTelemetryはMetrics・Logs・Tracesの生成、収集、転送を共通化する方向を提供し、Cloud、Kubernetes、Serverless、AI Agentなど観測対象が増えるほど価値が高まる。

**注目ポイント：★★★★★**

OpenTelemetryの目的を「新しいMonitoring Tool」と誤解せず、**Instrumentation / Telemetry InterfaceとStorage / Analysis Backendを分離するための標準**として説明できる。SRE面接でVendor Lock-inとPortabilityを語る材料になる。

### ⑤ JavaScriptをC言語にコンパイルする「porffor」がアルファ版に到達。ネイティブやWASMを生成可能

**出典：Publickey｜2026年9月7日**  
**原文：** https://www.publickey1.jp/blog/26/javascriptcporfforwasm.html

PorfforはJavaScript / TypeScriptをAhead-of-Timeで中間表現へ変換し、Cを経由してNative BinaryまたはWebAssemblyを生成するCompiler / Runtime Projectで、Alpha段階に到達した。一般的なJavaScript Runtimeと大量のLibraryを同梱せずに実行できる構成を目指しており、Project側はSelf-containedなJS + Node Runtimeと比べてBinary Sizeを最大約1/50にできる可能性を示している。1GB Memory上でNode.js App約28個に対しPorfforでは1000+を動かせるという例も公開している。

一方、これはProduction Compatibilityを保証する数字ではない。Publickeyも、Alpha段階では既存Applicationがそのまま動く可能性は高くなく、Node Compatibilityが主要な課題だと説明している。Sub-1ms級のCold StartやClosure最適化もProject側の測定値として捉え、実際にはNode API、Dependency、Dynamic JavaScript、Debugging、Build Pipelineまで検証する必要がある。

**注目ポイント：★★★★☆**

Runtime選定では、**Compatibility ↔ Binary Size / Cold Start / Memory Density**のTrade-offを見る必要がある。Serverless、CLI、Edge、Agent Toolなど、起動時間とMemoryが支配的な環境では今後注目すべき方向だ。

## 4. 今日の技術テーマ

### Workload Contract First — Product Labelより先に、実際の利用条件を書く

今日の5本はSecurity、LLM、Database、Observability、JavaScript Runtimeと分野が異なるが、共通する考え方は明確である。**“何という製品か”より先に、“どのData・Risk・Load・Cost条件で使うか”を定義する。**

```text
Workload / Risk Contract
  ├─ Data / Identity / Compliance
  ├─ Traffic / Concurrency / Idle Pattern
  ├─ Latency / Cost / Scale
  ├─ Compatibility / Portability
  └─ Failure / Recovery / Observability
            ↓
     Candidate Technology
            ↓
        Real Validation
```

Top 1では「重要Asset」という分類だけではSecurity Coverageを保証できない。Top 2では「Frontier Model」という性能カテゴリだけではData Retention条件を満たせない。Top 3では同じ“Serverless Database”でもIdle時のPricingとScale Behaviorが異なる。Top 4ではObservability VendorとTelemetry Interfaceを分離する必要がある。Top 5ではAOT JavaScriptが高Densityを狙えても、Node CompatibilityがContractになる。

**メリット：** Architecture Decisionの理由を説明しやすい。Cost / Security / Reliabilityを比較可能な条件にできる。新Serviceが出ても同じ評価軸で比較できる。Model RouterやDatabase Selection、Cloud Architecture Reviewにも流用できる。

**制約：** Requirement自体が間違っていれば選定も誤る。Production Workloadは変化する。最低Costと最高Availabilityなど複数条件は衝突する。Vendor BenchmarkやCommunity Benchmarkは実Workloadを代替しない。

**国内企業での導入時の注意点：** PoC前にMust / Should / Nice-to-haveを分け、Data Retention、Permission、Peak Concurrency、Idle Ratio、Recovery Target、Budget、Ownerを明文化する。採用後もADRと測定値を残し、3〜6カ月後にWorkload Contractを再確認する。金融・医療・個人情報を扱う場合は、性能評価よりData / Compliance Gateを先に通す。

面接では次のようにまとめられる。

> **技術選定では製品カテゴリやBenchmarkを先に見るのではなく、Data、Security、Concurrency、Cost、Compatibilityを含むWorkload Contractを定義し、その条件に候補Serviceが適合するかを実測で確認することが重要だと考えています。**

3. **Technology ChoiceにはTeam Skillも入る。** DynamoDBよりSQLを選んだ背景にはData ComplexityとTeamのRDB経験もあった。
4. **Scale時にTuning不要であることも運用価値。** Dataが約10倍になってもDB Parameter変更が不要だった点はSRE Cost削減につながる。

## 4. Prometheusとの関係から整理、なぜGrafanaは「OpenTelemetry」を推進する？：オープンへ向かうオブザーバビリティー（1/2 ページ）

1. **Telemetry InterfaceとBackendを分離する。** Telemetry Dataは長期Assetであり、Vendor Toolは交換可能なImplementationとして扱う。
2. **PrometheusとOpenTelemetryは単純な代替関係ではない。** PrometheusのMetrics資産を活用しつつ、OTelでより広いTelemetry Standardizationを進められる。
3. **Grafana LabsはBackend領域を拡大してもOpen Compatibilityを重視する。** Mimir / Loki / Tempoと既存Open Ecosystemを共存させる。
4. **Agent時代は横断Traceがより重要になる。** Model Call、Tool Call、Application Traceを共通Telemetryで結べるとTroubleshootingが容易になる。

## 5. JavaScriptをC言語にコンパイルする「porffor」がアルファ版に到達。ネイティブやWASMを生成可能

1. **JavaScript RuntimeにもAOTという選択肢がある。** PorfforはJS / TSをCへ変換し、Native / WASMを生成する。
2. **Performance ClaimとCompatibilityを同時に見る。** Project側はBinary SizeやCold Startの大幅改善を示すが、Alpha段階である。
3. **Node CompatibilityがProduction Adoptionの主要Boundaryである。** DependencyやDynamic Featureが動くかはMicrobenchmarkより重要になる。
4. **Serverless / CLI / Edgeが初期適用候補になりやすい。** Cold Start、Binary Size、Memory Densityの価値が大きい環境だからである。

## C-3. JLPT文法

### 1. ～にとどまらず
**Level：N1｜意味：** ある範囲だけで終わらず、さらに広がる。  
**形：** `名詞 + にとどまらず / 動詞辞書形 + にとどまらず`  
**使い方：** Security / Architectureの対象範囲を広げる説明に向く。  
**例：** `AI時代のAsset Managementは重要Serverの保護にとどまらず、IDやThird-party、AI Toolまで可視化する必要があります。`  
**補足：** Top 1の重点防御から全体Visibilityへの転換と対応する。

### 2. ～かねない
**Level：N1｜意味：** 望ましくない結果が起こる可能性がある。  
**形：** `動詞ます形から「ます」を取る + かねない`  
**使い方：** Security / Cost / CompatibilityのRisk警告。  
**例：** `忘れられたAssetを放置すると、AIを使う攻撃者の侵入口になりかねません。`  
**補足：** 単なる可能性より警戒のニュアンスが強い。

### 3. ～に至るまで
**Level：N1｜意味：** ある範囲が端から端まで広く及ぶ。  
**形：** `名詞 + に至るまで`  
**使い方：** 多Layerの条件をまとめて示す。  
**例：** `ModelのData RetentionからDatabase Cost、Telemetry形式に至るまで、Workloadごとの条件を確認します。`  
**補足：** 今日のTop 5の広いEngineering Constraintを表せる。

### 4. ～に応じて
**Level：N2｜意味：** 条件・状況の変化に合わせて対応を変える。  
**形：** `名詞 + に応じて / 名詞 + に応じた + 名詞`  
**使い方：** Load、Risk、Policyに合わせる設計。  
**例：** `Applicationの負荷に応じてDatabaseの処理能力が自動的に調整されます。`  
**補足：** Serverless Scalingの説明に自然。

### 5. ～一方で
**Level：N2｜意味：** 一つの側面と別の側面を対比する。  
**形：** `普通形 + 一方で`  
**使い方：** Architecture Trade-offを述べる。  
**例：** `OpenTelemetryはVendor Lock-inを減らせる一方で、CollectorやSchemaの運用設計は必要です。`  
**補足：** メリットだけを述べないInterview Answerに使いやすい。

### 6. ～たうえで
**Level：N2｜意味：** 前の行為を重要な前提として、その後に判断・行為を行う。  
**形：** `動詞た形 + 上で / 名詞 + の上で`  
**使い方：** Validation後のTechnology Selection。  
**例：** `同時更新のPatternを確認したうえで、Aurora DSQLがWorkloadに適合するか判断します。`  
**補足：** Top 3の選定Processと一致する。

### 7. ～に伴って
**Level：N2｜意味：** ある変化と一緒に別の変化も起こる。  
**形：** `名詞 + に伴って / 動詞辞書形 + のに伴って`  
**使い方：** AI利用拡大とGovernance Requirementの増加。  
**例：** `AI活用の拡大に伴って、Asset VisibilityとTelemetryの標準化も重要になります。`  
**補足：** Top 1とTop 4の共通Trendを説明できる。
