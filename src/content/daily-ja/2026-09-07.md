### ① 企業資産の「36％」が“脆弱性ゾーン”で放置　AI攻撃時代に旧来の防御モデルは限界か： 「重要資産を重点的に守る」は通用しない？　最新調査が明かす限界

**出典：＠IT｜2026年9月7日 08:00**  
**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2609/07/news017.html

EYの2026年調査は経営層・Security責任者840人を対象としており、記事では企業Assetの平均 **36％** が「Vulnerability Zone」にあると紹介されている。ここでいうZoneは、Assetの存在やDependencyの可視性が不十分で、同時にSecurity Coverageも不足している状態を指す。カテゴリ別ではOT / Physical Asset 57％、Third-party / Ecosystem 49％、AI System / Tool 47％、Network Infrastructure 38％という数字が示されている。

AI時代に問題になるのは、新しい攻撃手法だけではない。AIを使う攻撃者は、忘れられたAsset、古いID、設定不備、Third-party Connectionのような「人が見落としやすい入口」を高速に探索し、それらをAttack Pathとして組み合わせられる。そのためCrown Jewelだけを重点防御するより、**Asset Inventory → Dependency Mapping → Identity / Third-party → Security Coverage → Continuous Control**を継続的に回す必要がある。

**Evidence Boundary：** 36％はEY調査の平均値であり、自社にも36％の未管理Assetが存在するという意味ではない。Secure Creator約30％、その他約42％という差も調査結果として扱い、自社ではOwner、Identity、Coverageを棚卸しして実態を確認すべきである。

**注目ポイント：★★★★★**  
AI SecurityをModel固有のSecurityだけに限定せず、既存Enterprise Securityの「発見速度が上がる問題」として説明できる点が面接で強い。

### ② Claude Fable 5.1 + EFS で企業 AI を安全に実装 — ZDR ロードマップ

**出典：Zenn｜2026年9月6日**  
**原文：** https://zenn.dev/kashiwabaray/articles/25d934bfd1a5c9

記事はClaude Fable 5.1、Data Retention、Enterprise Frontier Safeguards（EFS）をEnterprise導入の観点から整理している。Customer-owned Storage、Customer-managed Encryption、Automated Safety Monitoringなどを組み合わせることで、Frontier CapabilityとData Governanceをどう両立するかが中心テーマである。重要なのは、**Model QualityとEnterprise Eligibilityを別々に判断する**ことだ。RetentionやCompliance条件を満たさなければ、高性能でもProduction Candidateにはできない。

Bedrock Playgroundでの同一問題の実測では、Fable 5.1とFable 5はいずれも正答した。単一RunではOutput Tokenが1402対1468、Latencyが15068ms対19472msで、約 **22.6％のLatency差**が観測された。ただし著者自身が一回の測定を一般化できないと明記している。またCache Read単価の変化も紹介されており、長いContextやAgent WorkloadではCache Hit率を含めてCostを考える必要がある。

**Evidence Boundary：** Vendorの公開仕様・Pricing、Playgroundの単発実測、Production Workloadの測定は同じEvidenceではない。採用順序は **Data / Compliance Gate → Capability → Quality → Latency / Cost → 複数回の自社Workload検証**と分けるのが安全である。

**注目ポイント：★★★★★**  
「新Modelが出たのでBenchmarkを見る」から一段進み、Enterprise AIの採用条件をPolicyとEvidence Levelで説明できる。

### ③ 三菱UFJグループ会社、DBコストを87％削減――なぜ「Aurora Serverless」ではなく「Aurora DSQL」を選んだ？：同じサーバレスでも何が違った？

**出典：＠IT｜2026年9月7日 08:00**  
**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2609/07/news026.html

Japan Digital Design（JDD）はDocument Search SystemでAmazon Aurora DSQLを採用した。Workloadは夜間にPDF / Web Dataを集中的に処理し、約 **1800個のECS Task** が並列実行され、1晩で10万件を超えるFile / Recordを書き込む。一方、日中はWeb ApplicationからのRead中心である。Production、Staging、Developmentなど複数Environmentを維持するため、Idle時間の固定費も選定条件になった。

Aurora ServerlessでCold Startを避けるため最低ACUを0.5にすると、利用していない時間でもEnvironmentごとにCostが発生する。Aurora DSQLは長時間未使用時にResourceをほぼゼロまで縮小し、再接続時に自動で立ち上がる。JDDはこの特定比較条件でDatabase Costを約 **87％削減**し、その後Data量が約10倍になってもDB Parameterを再調整せずに運用したと報告している。

採用判断ではCostだけでなく、同一Recordを高頻度で同時更新しないこと、Analytics / Aggregate中心ではないことも確認している。つまり、Serverlessという名前ではなく、Transaction Patternまで含むWorkloadとの適合性を見ている。

**Evidence Boundary：** 87％はこのSystemと比較設定における結果であり、すべてのAurora Serverless利用者に当てはまる数字ではない。再利用すべきなのは **Idle Cost、Burst Concurrency、Read/Write Pattern、Environment Count、Team Skill、Future Scale**を同時に評価する方法である。

**注目ポイント：★★★★★**  
日本企業の具体的Architecture Decisionとして使いやすく、Cloud面接で「Serverlessだから安い」という表面的な説明を避けられる。

### ④ Prometheusとの関係から整理、なぜGrafanaは「OpenTelemetry」を推進する？：オープンへ向かうオブザーバビリティー（1/2 ページ）

**出典：＠IT｜2026年9月7日 05:00**  
**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2609/07/news010.html

記事はGrafanaとPrometheusの関係からOpenTelemetryの位置付けを整理している。GrafanaはVisualization、PrometheusはMetricsで広く使われ、その後Grafana LabsはMimir（Metrics）、Loki（Logs）、Tempo（Trace）へBackend領域を広げた。それでもPrometheus CompatibilityやOpenTelemetryのようなOpen Standardを重視している点が重要である。

OpenTelemetryの価値は「新しいMonitoring Product」であることではなく、**Instrumentation / Telemetry GenerationとStorage / Analysis Backendを分離すること**にある。ApplicationがVendor固有SDKへ強く依存すると、Backend変更やMulti-backend構成へ移行するときのCostが大きくなる。Metrics、Logs、Tracesの収集・転送方法を共通化すれば、Telemetryを長期的なAssetとして扱いやすくなる。

**制約：** OpenTelemetryを導入してもSampling Strategy、Alert、Retention、Cardinality、Backend固有の運用設計が自動的に解決されるわけではない。StandardizationとObservability運用そのものは分けて考える必要がある。

**注目ポイント：★★★★★**  
SREだけでなくAI Agent Observabilityでも、Telemetry InterfaceとBackendを分離するArchitectureとして説明できる。

### ⑤ JavaScriptをC言語にコンパイルする「porffor」がアルファ版に到達。ネイティブやWASMを生成可能

**出典：Publickey｜2026年9月7日**  
**原文：** https://www.publickey1.jp/blog/26/javascriptcporfforwasm.html

PorfforはJavaScript / TypeScriptをAhead-of-Time（AOT）で中間表現へ変換し、Cを経由してNative BinaryやWebAssemblyを生成するCompiler / Runtime Projectで、Alpha段階に到達した。Project側はRuntimeを一緒に配布する構成と比べ、Binary Sizeを最大約 **1/50**にできる可能性、1GB MemoryでNode.js App約28個に対してPorffor 1000+、Sub-1ms級Cold Startなどを示している。

Serverless、CLI、Edge、Agent ToolではCold Start、Binary Size、Memory Densityが重要なので、この方向は魅力的である。一方でProduction採用ではNode.js API、Dynamic JavaScript、Dependency、Debugging、Build Pipelineが動くかどうかが先に問題になる。

**Evidence Boundary：** 数値はProject側の公開測定を中心としたもので、PorfforはまだAlphaである。記事も既存Applicationがそのまま動く可能性は高くなく、**Node Compatibility**が主要課題だと説明している。現時点ではNode.jsの即時代替ではなく、Runtime Architectureの方向性として評価するのが妥当である。

**注目ポイント：★★★★☆**  
React / Next.js / TypeScript経験者が、FrontendだけでなくJavaScript Execution ModelとDeployment Runtimeまで議論する材料になる。

## 2. カテゴリ別サマリー

### 🤖 AI / Agent

本日のAIテーマは **Eligibility before Benchmark**。AI攻撃では既存AssetのVisibilityが重要になり、Enterprise LLMではData Retention / ComplianceがModel性能より前のGateになる。AIを「Model性能」だけで考えないことが共通点である。

### 💻 Frontend / Web

Frontend寄りではPorfforが重要である。JavaScript / TypeScriptをAOTしてNative / WASMへ持っていく発想は、Runtime依存を見直す材料になる。ただしAlpha段階ではCompatibilityの実証が最優先である。

### ☁️ Cloud / Backend

Aurora DSQLはWorkload-aware Database Selection、OpenTelemetryはVendor-neutral Telemetry Designを示している。いずれもProduct Categoryより、実際の利用パターンと長期運用条件を先に定義する必要がある。

### 🏢 日本企業の実践

JDDの事例では、夜間Burst、日中Read、複数Environment、SQL Skill、将来Scaleを明示してからAurora DSQLを選んでいる。この意思決定の書き方自体が面接で再利用しやすい。

## 4. 今日の技術テーマ

### Workload Contract First

5本を共通の判断フレームへ落とすと、次の形になる。

```text
Workload / Risk Contract
  ├─ Asset / Identity / Third-party
  ├─ Data Retention / Compliance
  ├─ Traffic / Burst / Idle / Transaction
  ├─ Telemetry / Portability
  └─ Runtime / Compatibility
            ↓
        Candidate Technology
            ↓
       Evidence-based Validation
```

Top 1では「重要Asset」というLabelより全体Visibility、Top 2では「Frontier Model」というLabelよりRetention、Top 3では「Serverless」というLabelよりBurst / Idle / Transaction、Top 4ではMonitoring ProductよりTelemetry Interface、Top 5ではAOT性能よりCompatibilityが先に来る。

**メリット：** 技術選定理由を説明しやすくなり、Security / Cost / Reliability / CompatibilityのTrade-offを記録できる。  
**制約：** Contract自体が誤っていれば判断も誤る。Workloadは時間とともに変わるため、一度のPoCやBenchmarkで固定しない。  
**日本企業での運用：** ADRなどにMust / Should / Nice-to-have、Evidence Source、未検証項目、再確認日を残し、3〜6か月後に実Workloadで前提を見直す。

# B. 重要ポイントと面接で使える知識

## 1. Asset Visibility / AI攻撃

1. EY調査の36％はVulnerability Zoneの平均値であり、自社の実測値ではない。
2. AIによって忘れられたAsset、古いID、Third-partyの探索速度が上がるため、Visibility不足そのものがRiskになる。
3. Asset InventoryはOwner、Identity、Dependency、Security Coverageまで含めて継続更新する。
4. Cyber ResilienceをIncident後の復旧だけでなく、発見・統制・復旧の循環として説明できる。

## 2. Fable 5.1 / EFS / Data Retention

1. Model QualityとEnterprise Eligibilityは別のGateとして扱う。
2. Data Retention、Encryption、利用条件を確認してからQuality / Latency / Costを測る。
3. 22.6％のLatency差は単発実測であり、複数回の中央値で再確認する必要がある。
4. Prompt Cacheの単価とHit率も長Context / Agent WorkloadのTCOに影響する。

## 3. Aurora DSQL / Workload-aware Database

1. DatabaseはServerlessというCategoryではなくWorkload Shapeから選ぶ。
2. 夜間1800 ECS TaskのBurst、日中Read、複数Environmentという条件がCost構造を作る。
3. 約87％削減は最低0.5 ACUなど特定比較条件に依存する。
4. 同一Recordの高頻度更新が少ないこともDSQL採用条件の一つだった。

## 4. OpenTelemetry / Observability

1. OpenTelemetryはMonitoring BackendではなくTelemetry Interfaceの標準化として理解する。
2. Mimir / Loki / TempoのようなBackendとInstrumentationを分離することでPortabilityが上がる。
3. PrometheusとOpenTelemetryは単純な置き換え関係ではない。
4. Sampling、Alert、Retention、CardinalityはOTel導入とは別に設計する必要がある。

## 5. Porffor / AOT JavaScript

1. JavaScript / TypeScriptをAOTし、C経由でNative / WASMへ変換するRuntime方向である。
2. Binary Size、Cold Start、Memory DensityはServerless / CLI / Edgeで重要な指標になる。
3. 最大約1/50やSub-1msはProject側の測定であり、Production Guaranteeではない。
4. Alpha段階ではNode Compatibility、Dependency、Debugging、Build Pipelineの確認が先である。

## C-2. IT / AI専門語彙

1. **Asset Inventory**：組織内外のIT / Cloud / SaaS / Identityなどを継続的に把握する仕組み。
2. **Vulnerability Zone**：記事内調査で、VisibilityとSecurity Coverageがともに不十分なAsset領域を示す表現。
3. **Data Retention**：Providerが入力・出力・Logなどを保存するPolicyと期間。
4. **Enterprise Frontier Safeguards（EFS）**：Frontier ModelとEnterprise Governanceを組み合わせるための記事中のControl構想。
5. **Aurora DSQL**：AWSの分散SQL Database。本記事ではIdle / Scale特性とCostが焦点。
6. **OpenTelemetry**：Metrics、Logs、TracesのInstrumentation / Collectionを標準化するOpen Standard。
7. **AOT（Ahead-of-Time）**：実行前にCompileする方式。JITとは異なるTrade-offを持つ。
8. **WebAssembly（WASM）**：Portableな低レベル実行形式で、Porfforの出力Targetの一つ。

## C-3. JLPT文法

### 1. ～にとどまらず｜N1
**意味：** ～だけではなく、さらに範囲が広がる。  
**接続：** 名詞 + にとどまらず  
**例文：** `AI攻撃の影響は新しいThreatにとどまらず、既存Assetの探索速度にも及びます。`

### 2. ～に際して｜N1
**意味：** 重要な行為・場面を行うとき。  
**接続：** 名詞 + に際して / 動詞辞書形 + に際して  
**例文：** `Frontier Modelの導入に際して、Data Retentionを先に確認します。`

### 3. ～に即して｜N1
**意味：** 実際の状況・基準に合わせて。  
**接続：** 名詞 + に即して  
**例文：** `料金表ではなく、実際のWorkloadに即してDatabaseを選定します。`

### 4. ～とは限らない｜N2
**意味：** 必ずそうなるとは言えない。  
**接続：** 普通形 + とは限らない  
**例文：** `一回Latencyが低かったからといって、常に高速だとは限りません。`

### 5. ～を踏まえて｜N1
**意味：** ある事実・条件を考慮した上で。  
**接続：** 名詞 + を踏まえて  
**例文：** `Compatibilityの制約を踏まえて、AOT採用範囲を決めます。`

### 6. ～に伴い｜N2
**意味：** 変化と同時に別の変化が起こる。  
**接続：** 名詞 + に伴い / 動詞辞書形 + に伴い  
**例文：** `Agentの利用拡大に伴い、Telemetryの統一が重要になります。`

### 7. ～かねない｜N2
**意味：** 好ましくない結果になる可能性がある。  
**接続：** 動詞ます形（ます除去） + かねない  
**例文：** `古いIDを放置すると、攻撃の足掛かりになりかねません。`
