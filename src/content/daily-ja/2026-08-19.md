# A. 詳細版

## 1. 今日読むべき5本

### ① AWS、Anthropic・OpenAIと連携し「AWS Continuum」をClaude Code / Codex / Kiroへ統合

**出典:** AWS Security Blog
**原文 URL:** https://aws.amazon.com/blogs/security/aws-partners-with-anthropic-and-openai-to-bring-aws-continuum-into-developer-workflows/

AWSは、コード脆弱性向けのAWS ContinuumをPreviewとして紹介し、AnthropicおよびOpenAIと協力してClaude Code、Codex、Kiroの開発ワークフローへ統合すると説明しています。Continuumは複数モデルを組み合わせ、検出、顧客環境に即した優先順位付け、Sandboxでの検証、修正を行う仕組みです。

記事では、モデルそのものを車のエンジンにたとえ、Tool、Guardrail、Memory、WorkflowをつなぐAI Harnessを周辺の基盤として扱います。既存コードではオンデマンドのスキャン結果を受け取り、AWS環境の設定、IAM Policy、Network Topology、Exposure Surfaceを踏まえて検証します。Greenfieldでは、PluginがSecurity-validatedな提案を返す構想です。

**注目ポイント:** 検出精度だけでなく、モデル選択・オーケストレーション・Contextual Validationを基盤として一体化している点です。既存コードの「書く、Scanする、Triageする、直す、再Scanする」という流れを、開発者が受け取る一つの結果へまとめようとしています。

### ② Zed Agent Panel：OS SandboxでAgentを強制的に制限

**出典:** Zed
**原文 URL:** https://zed.dev/blog/sandboxing

Zedは1.14からAgent PanelのTerminalとFetchを既定でSandbox化しました。既定の規則では、Project Directoryの外への書き込み、`.git`への書き込み、Network Requestを禁止し、権限が必要な場合はAgentが理由とともに一時的な昇格を求めます。macOSではSeatbelt、LinuxではBubblewrapを使うなど、OSの機能で制約を適用します。

記事は、Promptで「このファイルを編集しない」と伝えるだけではPrompt Injectionに弱いと説明します。また、単純なコマンド規則は迂回できるため、OSレベルの境界とは役割が異なります。Symlink SwapによるTOCTOUのような攻撃を挙げつつ、SandboxもEdit Tool、ACP、LSP、MCP Server、通常のTerminalまでは保護しないため、Defense in Depthの一層にすぎないと明記しています。

**注目ポイント:** Agentの善意や命令理解ではなく、許可されないResourceへの到達そのものを防ぐことです。一方でSandbox外で実行されるBuild ScriptやGit Hookなどの経路が残るため、開発環境全体の境界設計が必要です。

### ③ MCPは本当に常にDirect APIより優れているのか？

**出典:** Zenn
**原文 URL:** https://zenn.dev/taru_neko/articles/mcp-or-direct-api

記事は、GitHub、Jira、Slack、社内システムなど数個のサービスを一つのAIアプリから使うだけなら、各APIを直接呼び出してFunction CallingでToolとして公開する方が簡単な場合があると整理します。MCPを導入しても接続処理やAPI仕様変更への対応が消えるわけではなく、「外部サービス接続ならMCP」と機械的に決めるべきではありません。

一方、AIアプリや利用者、チームが増えると、MCP Serverを共通の接続方式として使う価値が上がります。MCPはCredential管理を不要にするものではなく、HostからMCP Serverへの認可と、MCP ServerからGitHubなどへの認証を分けて考えます。記事ではOAuthベースの認可やEnterprise-Managed Authorizationにも触れ、2026年7月仕様のステートレスなProtocol Coreによる水平スケール、GatewayでのRouting・認可・Meteringも紹介しています。

**注目ポイント:** 判断軸はAPIの個数ではなく、AIとToolの接続をどこまで共通化したいかです。利用者・アプリ・共有チーム・監査要件が増えるほど、標準化の運用価値と導入コストを比較する意味があります。

### ④ Wantedly：ObservabilityをInfraからLLMへ拡張

**出典:** ＠IT
**原文 URL:** https://atmarkit.itmedia.co.jp/ait/articles/2608/19/news016.html

取得できた記事本文は文字化けしていますが、見出しと判読できる記述から、Wantedlyが開発者の生産性と安定したユーザー体験を支える仕組みを、インフラだけでなくサービス品質まで広げてきたことが確認できます。2014年にPaaSからIaaSへ移行し、コンテナ環境とDatadogによる監視を整え、その後Kubernetesを検証・導入して2018年までに全サービスのマイクロサービス化を進めた経緯が示されています。

記事は、SREとObservabilityを軸に、インフラチームが単にツールを導入するのではなく、エンジニアやユーザーにどう使ってほしいかを設計することを重視していると伝えます。後半は生成AIやAI Agentの本番利用を踏まえ、AIが生成したコードの未知のリスクや、LLMを含む新しい運用管理の観測点を考える流れにつながっています。

**注目ポイント:** インフラのメトリクスだけでなく、サービスの品質、開発者体験、LLMを含むアプリケーションの状態を継続的に捉える視点です。記事の取得本文が不完全なため、具体的な新製品名や数値は断定しません。

### ⑤ Google HEIR：AIが暗号化状態のデータを直接処理する

**出典:** Publickey
**原文 URL:** https://www.publickey1.jp/blog/26/googleaiheirai.html

Googleは、完全準同型暗号を利用したAIモデル用のオープンソースコンパイラ「HEIR」を発表しました。HEIRは学習済みAIモデルのPythonコードをコンパイル・変換し、暗号化データを復号せずに入力して推論できるようにするツールチェーンです。暗号化トラフィックの分析や、顧客のプライベート情報を内容を見ずに処理するサービスなどが想定されています。

記事では、深層学習によるRecommendation、クレジットカード詐欺検出、暗号化Network Trafficの異常検出、Hotword検出の4例を紹介しています。HEIRはモデルのLogicをFHE対応のLogicへ変換し、プログラマーがPythonコード上でSecretのまま処理するデータをAnnotationで指定できる設計です。まだ開発段階ですが、GoogleはFHEの業界標準Compilerを目指しています。

**注目ポイント:** AI処理の前にデータを平文へ戻さないことで、Cloud ProviderやService Providerが内容を見ない構成を目指せる点です。FHEはPrivacyを高める一方、実運用では性能や対応範囲を検証する必要があります。

### AI / Agent

AWS Continuumは、複数モデルとAgent Team LoopをHarnessで統合し、脆弱性の発見から修正までを開発環境へ戻します。Zedは、Agentの判断ではなくOS SandboxでTerminalとFetchを制限します。AIの能力を高めるだけでなく、実行境界と検証結果を設計することが共通の論点です。

### Frontend / Web

今回の原文には、Frontend実装やWeb UIの新機能を主題にした意味のある項目はありません。ZedのAgent Panelは開発者向けUIですが、記事の中心はUIではなくOSレベルのSandboxです。

### Cloud / Backend

MCPの記事は、複数AIアプリから共有Toolを使うための接続基盤、認証・認可、Gateway、水平スケールを扱います。Wantedlyの記事は、PaaSからIaaS、コンテナ、Kubernetes、マイクロサービスへ移行し、Datadogを使った監視を整えた経緯を示します。

### 日本企業 Tech Blog / enterprise engineering signals

Wantedlyの事例は、インフラチームの役割を開発者の生産性とユーザー体験の支援へ広げる企業内エンジニアリングのシグナルです。MCPの認可・監査やAWS Continuumの企業環境Contextも、AIを個人の実験から組織運用へ移す際の論点になります。

## 3. 面接で使えるポイント

### 1. AI Agentの権限制御

**質問:** AI Agentに自由なTerminal権限を与えずに自動化するには、どう設計しますか。
**回答（約30秒）:** まずOS SandboxでProject外、`.git`、NetworkなどのResourceを既定で制限し、必要な操作だけを明示的な承認で昇格させます。Promptの指示だけには依存せず、RuntimeでPolicyを強制します。そのうえでEdit Toolや通常のTerminalなど、Sandbox外の経路も含めて監査します。
**関連プロジェクト:** Agent実行基盤のSandbox導入
**キーワード:** OS Sandbox / Policy Enforcement / Defense in Depth

### 2. MCPとDirect APIの選択

**質問:** MCPをDirect APIより優先する判断基準は何ですか。
**回答（約30秒）:** 接続先の個数だけでは判断しません。一つのAIアプリが少数のAPIを使うだけならDirect APIが簡単です。一方、複数のAIアプリ、利用者、チームが同じToolを共有し、認証・認可・監査を組織的に管理するなら、MCPで接続方式を標準化する価値が高まります。
**関連プロジェクト:** 社内AI Tool Gateway
**キーワード:** MCP / 認可 / 標準化

### 3. LLM Observability

**質問:** LLMを含むサービスで、従来のインフラ監視に何を加えますか。
**回答（約30秒）:** インフラのメトリクスだけでなく、LLMの入力・出力、Tool Call、処理の遅延、失敗、ユーザー体験まで追跡可能にします。Wantedlyのように、インフラ移行とサービス品質の改善を別々にせず、開発者が使いやすい運用基盤として設計します。
**関連プロジェクト:** LLM利用機能の運用可視化
**キーワード:** SRE / Observability / ユーザー体験

### 4. FHEの企業利用

**質問:** 完全準同型暗号をAIサービスに使う場合の利点と課題は何ですか。
**回答（約30秒）:** データを復号せずに推論や検知を行えるため、Privacyを守りながら外部基盤を利用しやすくなります。HEIRはAIモデルをFHE対応へ変換するCompilerです。一方で、処理コストや対応できるモデルの範囲を測定し、業務要件に合うか検証する必要があります。
**関連プロジェクト:** 機密データ向けプライバシー保護推論
**キーワード:** FHE / HEIR / 復号せずに処理

## 4. 今日の技術テーマ

### Agentの実行境界をRuntimeで設計する

今日の中心テーマは、AI Agentを賢くすることと、Agentが実際に触れられるResourceを狭く保つことを分けて考える設計です。AWS ContinuumはHarness、検証Sandbox、Policy、Observabilityをモデルの周辺基盤として扱います。ZedはOSがファイル・Networkの制約を強制し、MCPは共有Toolへの認可と監査の境界を整理します。

**メリット:** Prompt Injectionや誤った判断が起きても、未許可のファイル・Tool・Networkへ到達しにくくなります。操作履歴を監査でき、複数モデルや複数アプリを運用する際もPolicyを共通化できます。
**制約・リスク:** Sandboxの実装バグ、TOCTOU、Sandbox外のEdit・Build・Git Hookなどは残ります。制限を強くしすぎると自動化の価値が下がり、許可昇格の運用も複雑になります。
**日本企業で導入する際の注意点:** まず業務データ、Credential、Networkの境界を洗い出し、原則拒否・最小権限で始めます。承認者、監査ログの保管期間、Incident時の停止手順を決め、開発者の通常TerminalやCIまで含めて責任範囲を明確にします。

## 5. 面接復習カード

### Q1. PromptだけでAgentの安全性を確保できないのはなぜですか？

**回答ポイント:** Prompt Injectionや誤判断を防げず、コマンド規則も迂回され得るためです。OS Sandboxなど実行時の境界でResourceへの到達を制限します。

### Q2. MCP導入でCredential管理の問題は消えますか？

**回答ポイント:** 消えません。HostからMCP Serverへの認可と、MCP Serverから接続先APIへの認証は別です。MCPの利点は認証・認可の共通化を進めやすい点です。

### Q3. FHEは何を保護しますか？

**回答ポイント:** データを復号せずに計算できるため、処理中の内容を秘匿しやすくします。ただし性能とモデル対応範囲の検証が必要です。

# B. 重要ポイントと面接で使える知識

## ① AWS Continuum

- Continuumは脆弱性を検出するだけでなく、顧客のAWS環境Contextで優先順位を付け、Sandboxで検証し、修正へつなげる。
- Claude Code、Codex、Kiroの開発環境に、オンデマンドScanとSecurity-validatedな提案を戻す構想である。
- AI HarnessはModelをTool、Guardrail、Memory、Workflowと接続するOrchestration Layerであり、AWSはこれを基盤として扱う。

## ② Zed Agent Panel

- TerminalとFetchはOS Sandboxで既定制限され、Project外への書き込み、`.git`、Network Requestが禁止される。
- macOSはSeatbelt、LinuxはBubblewrap、WindowsはWSLを利用する。権限昇格には理由と範囲の確認が伴う。
- Promptや細かなコマンド規則は攻撃者の迂回を完全には防げず、Edit Toolや通常のTerminalなどSandbox外の経路も残る。
- Symlink SwapのTOCTOUのように、Sandbox自体も攻撃者を前提にFail-closedで設計・検証する必要がある。

## ③ MCPとDirect API

- AIアプリ一つ、接続先数個、利用者も限定的なら、Direct APIの方がMCP Serverを追加するより単純な場合がある。
- MCPの価値はAPI呼び出しを消すことではなく、複数Host/ClientとToolの接続方式を標準化することにある。
- MCP Serverへの認可と、MCP ServerからGitHubなどへの認証は別問題であり、Credential管理は残る。
- 複数アプリ・チーム・大量ユーザー・監査要件があるほど、Gateway、水平スケール、組織的な認可の価値が高まる。

## ④ WantedlyのObservability

- WantedlyはPaaSからIaaSへ移行し、コンテナ環境、Datadog、Kubernetes、マイクロサービス化を段階的に進めた。
- インフラチームの役割はツール導入だけでなく、開発者の生産性と安定したユーザー体験を支える基盤づくりである。
- SREとObservabilityを、インフラ状態だけでなくサービス品質や生成AI・AI Agentの運用課題へ広げる視点が示される。
- 本文の一部が文字化けしているため、取得できない具体的な製品機能や数値は推測しない。

## ⑤ Google HEIR

- HEIRはAIモデルのPythonコードをコンパイルし、FHE対応のLogicへ変換するオープンソースのCompilerとToolchainである。
- 暗号化データを復号せず、Recommendation、カード詐欺検出、暗号化Trafficの異常検出、Hotword検出へ利用する例が紹介される。
- Secretのまま扱うデータをAnnotationで指定し、CompilerがFHE対応への変換を行う。
- 開発段階の技術であり、Privacyの利点と、実用上の処理コスト・対応範囲を分けて評価する必要がある。

# C. 日本語学習｜JLPT + IT日本語

## C-1. JLPT語彙

### 1. 監査（かんさ）｜名詞・N1

- **意味:** システムや業務が規則どおりか、記録や証拠に基づいて調べること。
- **コロケーション:** 監査ログ／監査証跡／定期監査
- **記事の文脈・補足:** MCPやTool利用で、誰がいつ何を実行したかを後から確認する記録。
- **例文:** すべてのTool Callを監査できるように履歴を保存します。
- **例文の意味:** Toolの呼び出しをすべて監査できるよう、履歴を保存します。
- **ニュアンス:** 規則・統制への適合を確認する硬い表現。

### 2. 暗号（あんごう）｜名詞・N2

- **意味:** 情報を読めない形式へ変換し、必要に応じて元へ戻す技術や仕組み。
- **コロケーション:** 暗号技術／暗号方式／暗号化
- **記事の文脈・補足:** FHEでは暗号化データを保護したまま計算する。
- **例文:** 機密Dataを暗号化した状態で処理できる方式を検討します。
- **例文の意味:** 機密データを暗号化したまま処理できる方式を検討します。
- **ニュアンス:** 「暗号化」は変換行為、「暗号」は技術や方式を指すことが多い。

### 3. 復号（ふくごう）｜名詞・N1

- **意味:** 暗号化されたデータを元の形式に戻すこと。
- **コロケーション:** 復号Key／復号処理／復号せずに処理する
- **記事の文脈・補足:** HEIRとFHEでは処理側で復号しないことがPrivacy保護につながる。
- **例文:** Server側でDataを復号せずに推論処理を行います。
- **例文の意味:** サーバー側でデータを復号せずに推論処理を行います。
- **ニュアンス:** 「解読」より技術的な変換を戻す語。

### 4. 脅威（きょうい）｜名詞・N1

- **意味:** システムや情報に損害を与える可能性のある危険や攻撃要因。
- **コロケーション:** Security脅威／脅威Model／脅威を分析する
- **記事の文脈・補足:** Agentが外部ToolやNetworkへ到達できる場合に先に洗い出す。
- **例文:** 外部Toolを利用する際の脅威を事前に分析します。
- **例文の意味:** 外部Toolを使う前に脅威を分析します。
- **ニュアンス:** 攻撃者や悪用の可能性まで含む。

### 5. 整合（せいごう）｜名詞・N1

- **意味:** 複数の仕様や情報が食い違わず、互いに合っていること。
- **コロケーション:** 仕様との整合／整合性を保つ／Data整合性
- **記事の文脈・補足:** MCP Tool SchemaとBackend APIの仕様が一致しているか確認する。
- **例文:** MCP Tool SchemaとBackend APIの仕様との整合を確認します。
- **例文の意味:** MCP Tool SchemaとBackend APIの仕様が一致しているか確認します。
- **ニュアンス:** 「整合性」は状態、「整合」は一致を確かめる行為にも使う。

### 6. 強制する（きょうせいする）｜動詞・サ変・N2

- **意味:** 規則や条件に従わせること。
- **コロケーション:** Policyを強制する／設定を強制する／Ruleを強制する
- **記事の文脈・補足:** Agentの善意でなくRuntimeの仕組みで禁止事項を守らせる。
- **例文:** 危険な操作の禁止をRuntime Policyで強制します。
- **例文の意味:** Runtime Policyによって危険な操作を禁止します。

### 7. 制御する（せいぎょする）｜動詞・サ変・N2

## C-2. IT/AI専門用語

- **Runtime-enforced Security（Runtime強制型Security）:** モデルの指示でなく実行時の仕組みで規則を適用する。ZedのOS SandboxやPolicyの文脈。
- **MCP（Model Context Protocol）:** AIアプリとToolの接続方式を共通化するプロトコル。複数Host・Clientで共有するTool基盤の文脈。
- **REST API（REST API）:** HTTPの資源・操作でサービス連携を行う一般的なAPI方式。少数接続でMCPと比較される。
- **LLM Observability（LLM可観測性）:** LLMの入出力、推論、Tool利用を計測・追跡できる状態。Wantedlyの運用基盤拡張に関連する。
- **FHE（完全準同型暗号）:** 暗号化データを復号せず計算できる暗号技術。HEIRがAIモデルを対応Logicへ変換する。
- **DevSecOps（DevSecOps）:** 開発・運用の流れにSecurity対策を組み込む方法。AI生成コードやTool利用を統合的に扱う。
- **Policy Enforcement Point（Policy強制ポイント）:** 認可や実行規則を検査し、許可・拒否を決める場所。AgentのRuntime境界。
- **Zero Trust（ゼロトラスト）:** 内外を問わず要求ごとに認証・認可を確認する原則。MCP ServerやTool Accessの管理に関係する。

## C-3. JLPT文法

### ～ことなく｜N1

- **意味:** ～しないで。ある動作を行わずに別の動作をする。
- **構造:** 動詞辞書形 + ことなく
- **使い方:** 前の処理を省略・回避したまま後の処理を行う説明に使う。
- **例文:** Dataを復号することなく計算処理を行います。
- **例文の意味:** データを復号しないで計算処理を行います。
- **補足:** 「～ないで」より硬く、仕様書向き。

### ～恐れがある｜N1

- **意味:** 悪い事態が起こる可能性がある。
- **構造:** 動詞辞書形 / 名詞 + の + 恐れがある
- **使い方:** セキュリティ上のリスクを断定せずに示す。
- **例文:** Promptだけに制御を任せると、危険なCommandが実行される恐れがあります。
- **例文の意味:** Promptだけに制御を任せると、危険なコマンドが実行される可能性があります。
- **補足:** 重大なリスクを改まって述べる。

### ～にとどまらず｜N1

- **意味:** ～だけでなく、それより広い範囲に及ぶ。
- **構造:** 名詞 / 普通形 + にとどまらず
- **使い方:** 対策や影響が一領域だけで終わらないことを強調する。
- **例文:** Agent SecurityはPrompt設計にとどまらず、RuntimeでのPolicy Enforcementまで必要です。
- **例文の意味:** Agent SecurityにはPrompt設計だけでなく、RuntimeでのPolicy Enforcementも必要です。
- **補足:** 「～だけでなく」より硬く、広がりを強調する。

### ～上で｜N2

- **意味:** ～する際に。ある目的のために行うときに。
- **構造:** 動詞辞書形 + 上で
- **使い方:** 導入・運用の前提として考慮点を述べる。
- **例文:** MCPを本番利用する上で、認可と監査は重要です。
- **例文の意味:** MCPを本番で利用する際、認可と監査は重要です。
- **補足:** ここでは「～た上で」ではなく「～する際に」の用法。

### ～に基づいて｜N2

- **意味:** ～を根拠や基準として。
- **構造:** 名詞 + に基づいて
- **使い方:** Identity、Policy、計測データなど判断の根拠を示す。
- **例文:** User Identityに基づいてTool Accessを制御します。
- **例文の意味:** ユーザーのIdentityを基準にTool Accessを制御します。
- **補足:** 明確な情報を根拠にする。

### ～一方で｜N2

- **意味:** ～という面がある反面、別の面では。
- **構造:** 普通形 + 一方で
- **使い方:** 技術のメリットとコスト、便利さとリスクを対比する。
- **例文:** FHEはPrivacyを高める一方で、処理Costが増えることがあります。
- **例文の意味:** FHEはプライバシーを高める反面、処理コストが増えることがあります。
- **補足:** 同じ主体の異なる側面を並べる。

### ～にかかわらず｜N2

- **意味:** ～と関係なく。条件が変わっても同じように。
- **構造:** 名詞 + にかかわらず
- **使い方:** 接続方式などに左右されない共通要件を述べる。
- **例文:** 接続方式にかかわらず、認証と認可を必ず適用します。
- **例文の意味:** 接続方式が何であっても、認証と認可を必ず適用します。
- **補足:** 規則や方針を例外なく適用する説明に合う。
