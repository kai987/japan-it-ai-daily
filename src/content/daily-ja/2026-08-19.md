# A. 詳細版

コードの脆弱性、OSによる隔離、ツール接続の共通化、利用者から見た障害、暗号化したままの計算を扱います。それぞれの技術が守る境界と、残る責任を確認します。

## 1. 今日読むべき5本

### ① AWS、Anthropic・OpenAIと連携し「AWS Continuum」をClaude Code / Codex / Kiroへ統合

**出典：AWS Security Blog**

**原文：** https://aws.amazon.com/blogs/security/aws-partners-with-anthropic-and-openai-to-bring-aws-continuum-into-developer-workflows/

AWSの公式発表は **AWS Continuum for code vulnerabilities** をClaude Code、Codex、Kiroの開発手順へつなぐ計画を説明しています。モデルが多くの問題を検出しても、どれが自社環境で重大かを絞り、検証と修正へ運ぶ作業が残ることが背景です。記事時点でContinuum本体は **Preview**、各開発環境への統合は **coming soon** で、全面提供済みではありません。

計画では開発環境からオンデマンドの検出結果を送り、Continuumが **IAMポリシー、ネットワーク構成、設定、外部への露出** を含むAWS環境の情報で優先順位を付けます。サンドボックスで検証した文脈付きの結果を開発支援側へ返し、その情報に基づいて提案を修正する流れです。コード上の疑わしさと、実環境で意味を持つ脆弱性を分けようとしています。

内部は複数モデルとエージェントを協調させる **agent-team loop** と説明され、検出、優先付け、検証、修正を一連の手順にまとめます。既存コード全体を調べる利用と、新規コードの提案へ統合する利用を分けています。ハーネスをID、ポリシー、観測などと同じ基盤として管理する方針で、単に高性能モデルを一つ選ぶ話ではありません。

Rivianの設計協力者による有用性のコメントはありますが、修正時間の数値比較、誤検知率、全脆弱性の検出率は提示されていません。したがって「すべて安全なコードになる」という保証は残しません。企業での検討では、必要な環境情報を与えられるか、優先順位の理由と検証の根拠をレビューできるかを確認する材料になります。

**注目ポイント：★★★★★**

脆弱性の検出数より、環境依存の到達性・優先順位・検証結果を説明できます。

### ② Zed Agent Panel：OS SandboxでAgentを強制的に制限

**出典：Zed**

**原文：** https://zed.dev/blog/sandboxing

Zedの公式記事は、**1.14からagent panelのterminalとfetchを既定でサンドボックス化**すると説明しています。指示を守るかどうかをモデルに委ねず、OSで実行可能な範囲を制限します。既定ではプロジェクト外への書き込み、`.git` の書き込み、ネットワーク通信を禁止します。必要な拡張は理由付きで求めますが、`.git` の書き込み権限は要求できません。外側で実行されるGit hookを仕込めるためです。

実装はmacOSの **Seatbelt**、Linuxの **Bubblewrapによるnamespaces**、WindowsのWSLです。LinuxとWSLではsetuidでない `bwrap` が必要で、Windowsの非WSLシェルは対象外です。コマンド名の禁止だけでは、別の実行経路で同じファイルを変更できるため、文字列ルールとOSの強制を区別しています。

記事は、許可画面の確認後からBubblewrapへ渡す間に対象ディレクトリをsymlinkへ差し替える **TOCTOU** を解説します。許可した文字列が同じでも、実際の参照先が変わる問題です。Zedはこの攻撃を検出して **fail-closed** にする、と説明しています。これは未修正の攻撃が成功した報告ではなく、対策が必要になる競合条件と実装上の防御の紹介です。

制約は明確で、通常のeditツール、ACP接続の別エージェント、LSP/MCPサーバー、通常ターミナルや外部アプリまでは保護しません。生成された `build.rs` や手続きマクロなどを別の場所で実行すると、サンドボックス外で動く場合があります。create_directoryも権限処理に参加しますが、拒否後に除去する前に一時作成する場合があるという注記があります。

したがって「Zed内のすべての処理が隔離された」とは言えません。公式の設計説明であり、無欠陥を独立に証明した監査結果でもありません。面接では保護対象のツール、OS条件、許可対象の実体、生成物を後で動かす経路まで分けて説明できます。

**注目ポイント：★★★★★**

OSによる強制と命令の禁止を区別し、対象外ツールや後続実行まで含めて境界を話せます。

### ③ MCPは本当に常にDirect APIより優れているのか？

**出典：Zenn**

**原文：** https://zenn.dev/taru_neko/articles/mcp-or-direct-api

Zennの記事は、**MCPか直接API連携か**を、接続サービス数だけで選ばないという設計上の考察です。一つのAIアプリから数個のAPIを使うだけなら、Function Callingに独自の処理を接続する方が単純な場合があります。ただし、MCPを入れてもGitHubなど下流APIの変更追従はなくならず、サーバーの実装・運用も増えます。

MCPの利点は、同じツールを複数のHost/Clientで共通利用する接続方式です。記事の **1アプリ×4ツール×10人と、10アプリ×4ツール×1,000人** は規模の違いを考える例で、損益分岐点を測定した数値ではありません。サービスの数に加え、アプリ、ユーザー、チーム、監査の範囲を見ます。

認可では **HostからMCP Serverへのアクセス** と **ServerからGitHubなどへの認証情報** が別です。**Enterprise-Managed Authorization（EMA）** は企業IdPを通じて前者を集中管理するための拡張で、下流の認証情報の管理を消しません。[公式説明](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization)でも利用には対応クライアントが必要で、拡張が自動的に有効になるわけではありません。

2026年7月のステートレス化も運用の共通化に関係します。[7月28日の変更点](https://modelcontextprotocol.io/specification/2026-07-28/changelog)ではプロトコルのセッションと初期ハンドシェイクを外し、各要求に版と能力情報を載せます。これはアプリの業務状態が不要になる意味ではなく、実装の対応版を確認する必要があります。記事は直接APIとの費用や速度の比較実験ではありません。共通化の便益が、導入・権限・保守の費用を上回るかを具体的に説明する材料です。

**注目ポイント：★★★★★**

MCPの価値を共通化の範囲で説明し、二つの認証境界と実装コストを分けられます。

### ④ Wantedly：ObservabilityをInfraからLLMへ拡張

**出典：＠IT**

**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2608/19/news016.html

＠ITの取材はWantedlyの基盤が、**HerokuからAWS、Kubernetes、分散トレーシング、RUM** へ進んだ背景を2ページでたどります。2026年時点で導入4万社超・利用者約450万人、社員約120人のうち技術者約50人という規模の事例です。数値は組織とサービスの背景で、ツールの性能比較ではありません。

2014年のAWS移行は、米国にあったHerokuのネットワーク遅延やモバイル展開がきっかけでした。開発者がコードに集中する利点を残そうとDockerを使い、当時のコンテナ監視に対応したDatadogを導入。2016年ごろからKubernetesを検証し、2018年までにマイクロサービス化を進めました。新規サービスのたびにインフラ担当が付ききりになる状態から、各チームが独立して配備できる方向への変更です。

一方で、障害を検知できても原因となった呼び出し元が分かりにくくなりました。**Datadog APMの分散トレーシング**でサービスをまたぐ要求を追い、インフラとアプリで別れていた監視を統合します。データベースの負荷が上がった場所と、その原因を作ったサービスは同じとは限らず、CPUなど単独の指標だけでは調べきれないためです。

**Wantedly HireのRUM** は、企業ごとに異なる採用フローや画面操作をバックエンドのトレースへ結び付けます。同じ画面でも利用方法が異なるため、利用者が何をした結果エラーになったかを調べる情報を補います。これはフロントエンドの操作履歴とサーバー側の挙動をつなぐ具体例です。

Bedrockを使ったプロフィール生成や候補者提案、書類選考支援も紹介されていますが、**LLMオブザーバビリティーは検討を進めている段階**です。記事は担当者への取材で、原因特定時間の前後比較や生成AI品質の実測はありません。他社の関連記事にある「5分」などはこの事例の成果ではないため混ぜません。開発の自律性と、横断して調査できる仕組みを両立させる面接の話題になります。

**注目ポイント：★★★★★**

インフラの監視から、RUMとAPMを使う利用者操作の追跡へ発展した理由を説明できます。

### ⑤ Google HEIR：AIが暗号化状態のデータを直接処理する

**出典：Publickey**

**原文：** https://www.publickey1.jp/blog/26/googleaiheirai.html

PublickeyはGoogleの **HEIR** を、**完全準同型暗号（FHE）** を使うAI向けのオープンソースコンパイラとして紹介しています。処理する側へ平文を渡さずに計算したいという課題に対し、暗号化したデータを復号せずに扱える演算へモデルのロジックを変換する考え方です。通信経路だけを暗号化する仕組みとは、守る段階が異なります。

プログラマーはPythonコードで、秘密のまま処理するデータを **アノテーション** で指定します。HEIRがコンパイル時にFHE用のロジックへ変換するため、開発者がすべての暗号演算を直接記述する負担を減らす狙いがあります。ただし記事は、どんなPythonコードや巨大モデルでも無修正で変換できるという仕様を示していません。

紹介された応用は推薦、クレジットカード不正検出、**Kitsune** を使うネットワーク異常検出、ホットワード検出の4つです。共同研究・共同プロジェクトの紹介で、読者環境での性能確認ではありません。暗号化入力を扱う仕組みを、既存のあらゆる暗号通信を鍵なしで解析できる機能と誤解しないことも大切です。

HEIRは開発段階で、記事には平文処理との遅延・費用・精度の数値比較がありません。そのため通常の推論と同等の速さ、すべてのプライバシー問題の解消といった説明は加えません。面接では、秘密にしたいデータと演算を先に決め、対応する処理と性能を確かめる技術選定として話せます。

**注目ポイント：★★★★★**

転送時の暗号化と計算中の秘密保持を分け、FHE変換の入力条件と性能評価を説明できます。

## 4. 今日の技術テーマ

### 境界は一つではない

ツールを呼ぶ権限、OSが許す実行、データを読める相手、ユーザーが体験する障害は、それぞれ異なる境界です。MCPの認可を揃えても下流APIの資格情報は残り、Zedのterminalを隔離しても別の道具による実行は別に考えます。

```text
呼び出し元の認可 → 実行可能な操作 → データへのアクセス → 結果と影響の観測
```

Continuumは環境の情報を検出結果へつなぎ、Wantedlyはユーザーの操作をトレースへつなぎます。HEIRは計算する相手に平文を見せない方向を扱います。どの問題を解決したかを明示すると、技術名だけの安全性の説明を避けられます。

# B. 重要ポイントと面接で使える知識

## 1. AWS、Anthropic・OpenAIと連携し「AWS Continuum」をClaude Code / Codex / Kiroへ統合

1. 本体のPreviewと開発環境への統合予定は別です。
2. コードと環境情報を組み合わせて優先順位を付けます。
3. 協力者の評価は数値による検出・修正性能の比較ではありません。

## 2. Zed Agent Panel：OS SandboxでAgentを強制的に制限

1. 既定の隔離はterminalとfetchに適用されます。
2. TOCTOUは確認時と使用時の参照先の差に関する問題です。
3. 編集や外部でのビルドまで一括して保護されるわけではありません。

## 3. MCPは本当に常にDirect APIより優れているのか？

1. 接続先の数だけでは共通化の便益は決まりません。
2. EMAの認可と下流APIの認証情報は別です。
3. ステートレスなプロトコルでも業務状態や実装互換性の管理は残ります。

## 4. Wantedly：ObservabilityをInfraからLLMへ拡張

1. 自律的な配備には、複数サービスを横断して調べる仕組みも必要です。
2. RUMは画面操作とバックエンドの追跡を結び付けます。
3. 生成AIの観測は検討段階で、既に実測済みの効果ではありません。

## 5. Google HEIR：AIが暗号化状態のデータを直接処理する

1. FHEは暗号化したままの計算を扱います。
2. HEIRは秘密データの指定に基づいてロジックを変換します。
3. 応用事例の紹介だけでは平文と同等の性能は分かりません。

## C-3. JLPT文法

### 1. ～ことなく
**Level：N1｜意味：** ある行為や状態を伴わずに、別のことを行う。  
**形：** `動詞辞書形 + ことなく`  
**使い方：** 必要な境界を崩さず処理することを述べます。  
**例：** `Dataを復号することなく計算処理を行います。`  
**補足：** 必要な境界を崩さず処理することを述べます。

### 2. ～恐れがある
**Level：N1｜意味：** 好ましくないことが起きる可能性がある。  
**形：** `動詞辞書形 / 名詞 + の + 恐れがある`  
**使い方：** 確認できたリスクと仮定のリスクを区別して使います。  
**例：** `Promptだけに制御を任せると、危険なCommandが実行される恐れがあります。`  
**補足：** 確認できたリスクと仮定のリスクを区別して使います。

### 3. ～にとどまらず
**Level：N1｜意味：** ある範囲だけでなく、さらに広い範囲にも及ぶこと。  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 前の範囲から後ろへ話題を広げます。  
**例：** `Agent SecurityはPrompt設計にとどまらず、RuntimeでのPolicy Enforcementまで必要です。`  
**補足：** 前の範囲から後ろへ話題を広げます。

### 4. ～上で
**Level：N2｜意味：** ある行為を行うとき、またはそのために。  
**形：** `動詞辞書形 + 上で`  
**使い方：** 技術を選ぶ際に欠かせない条件を述べます。完了後を表す「た上で」と区別します。  
**例：** `MCPを本番利用する上で、認可と監査は重要です。`  
**補足：** 技術を選ぶ際に欠かせない条件を述べます。完了後を表す「た上で」と区別します。

### 5. ～に基づいて
**Level：N2｜意味：** 情報や規則などを根拠として行動・判断すること。  
**形：** `名詞 + に基づいて`  
**使い方：** 何を判断の土台にしたのかを明確にします。  
**例：** `User Identityに基づいてTool Accessを制御します。`  
**補足：** 何を判断の土台にしたのかを明確にします。

### 6. ～一方で
**Level：N2｜意味：** 同じ事柄の、対照的な二つの側面を述べること。  
**形：** `普通形 + 一方で`  
**使い方：** 前後は逆の評価や異なる側面でもつなげられます。  
**例：** `FHEはPrivacyを高める一方で、処理Costが増えることがあります。`  
**補足：** 前後は逆の評価や異なる側面でもつなげられます。

### 7. ～にかかわらず
**Level：N2｜意味：** ある条件が違っても、同じことが成り立つこと。  
**形：** `名詞 + にかかわらず`  
**使い方：** 後ろには条件に左右されない行動や規則を置きます。  
**例：** `接続方式にかかわらず、認証と認可を必ず適用します。`  
**補足：** 後ろには条件に左右されない行動や規則を置きます。
