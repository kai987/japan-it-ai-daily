### ① Money Forward：ChatGPT / Claudeの利用量とコストを一元管理

**出典：ITmedia AI＋**

**原文：** https://www.itmedia.co.jp/aiplus/article/2608/18/2000000571/

ITmediaはマネーフォワードが8月17日に提供を始めた **マネーフォワード クラウドAIトークン管理** を紹介しています。複数のAIサービスを部署や従業員が使うと、利用実態と支出が分散するため、それらをまとめて確認する法人向けサービスです。記事時点では **マネーフォワードID** を取得すると無料で使えると発表されています。

ChatGPTやClaudeなどの利用量と費用を **API連携またはCSV取り込み** で集め、ユーザー別にダッシュボードで可視化します。マネーフォワード ビジネスカードを使った決済の集約も紹介されていますが、利用データの集計とカードでの支払いは別の機能です。利用履歴が取り込めたことと、すべての支出が自動で一つに決済されることを混同しません。

証拠は提供開始の発表であり、費用削減率や業務の投資対効果を実測した記事ではありません。制約として、APIで取得できる項目、CSVの更新間隔、重複や欠落の処理、超過時の自動停止については、この報道だけでは確認できません。したがって予算超過を自動で防ぐ機能は追加しません。企業での応用は、取り込み値を請求と照合し、利用量とは別に業務成果を評価できる集計単位を決めることです。

**注目ポイント：★★★★★**

利用量の可視化、請求の確認、業務成果の評価を別々に説明できます。

### ② Visual Studio Code 1.133正式リリース。プロンプトを見失わない固定スクロール、ローカルHTMLファイルの自動リロード、ClaudeとCopilotの混在可能など新機能

**出典：Publickey**

**原文：** https://publickey1.jp/blog/26/visual_studio_code_1133htmlclaudecopilot.html

**VS Code 1.133** は、長い会話で指示を見失わない表示、編集直後のHTML確認、Claudeセッションの接続先切り替えを改善しました。Publickeyの紹介と[公式リリースノート](https://code.visualstudio.com/updates/v1_133)に基づく機能の解説で、開発時間が何%短くなったという実測ではありません。

固定スクロールは、いま見ている応答がどのプロンプトに属するかを上部に表示し、前後のプロンプトへ移動できます。設定名は公式の **`chat.stickyScroll.enabled`** を使います。紹介記事にある `chat.stickyescroll.enabled` は公式表記と一致しないため、そのまま設定例としては残しません。

内蔵ブラウザーで開いたローカルHTMLは、ファイルの変更を検知して自動再読み込みできます。**Refresh Automatically** でタブごとに切り替えられ、既定値は `workbench.browser.autoReloadOnFileChange` で設定します。保存した変更を目で確認しやすくする機能で、JavaScriptの動作、アクセシビリティ、本番配信先まで自動検証する仕組みではありません。

Claudeセッションではモデル選択欄にAnthropicとCopilotの接続先が並び、次のターンの提供元を選べます。**Anthropic側はAPIキー、Copilot側は契約枠**を使うため、同じ会話でも請求元を確認する必要があります。制約として、混在できることは同時並列で応答を比較する機能や、両社の費用を統合する機能を意味しません。フロントエンド面接では、編集の確認を速める仕組みと検証の責任を分けて話せます。

**注目ポイント：★★★★★**

HTMLの自動再読み込みという具体的な画面確認と、ターン単位の接続先・請求先を説明できます。

### ③ AWS Transform：Continuous ModernizationでLegacy改善を継続化

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/aws-transform-continuous-modernization-hands-on/

**AWS Transform continuous modernization** は、コードの場所をSourceとして登録し、DiscoveryでRepositoryを見つけ、AnalysisでFindingを作り、選んだ問題をRemediationする流れです。分析と修正は別の操作で、問題を検出しただけではコードは変わりません。ローカルSourceはリポジトリ自身でなく、直下にGitリポジトリを置く親ディレクトリを指定します。

著者は **Node.js18、TypeScript4.9、CDKv1、AWS SDKv2** の小さな検証アプリを用意し、`rapid-techdebt-analysis` を実行しました。マニフェストを調べるクイック分析はNode.js更新とSDKv3移行の2件を検出。そこから `AWS/nodejs-aws-sdk-v2-to-v3` だけを選んでローカルで修正し、依存番号だけでなくDynamoDBの呼び出しコードも変更されました。

生成されたローカルブランチとコミットで、**TypeScriptビルドと既存Jest5件が成功**しました。選ばなかったNode.js18やCDKv1はそのままです。GitHubに書き込み可能な接続を用いる構成ならPRを作れますが、今回のローカル実行がGitHubへ自動投稿したわけではありません。レビューし、反映後に再分析するまでが運用上の確認になります。

計測は **44.3499 Agent minutes**、記事時点の1分0.035ドルで約1.55ドルです。Agent minutesはサーバー側の計画・推論・変更の稼働時間で、ローカルのビルド待ちを除き、並行エージェント分は合算されます。経過時間と同じではありません。東京のジョブでも推論は東京または大阪へ振り分けられ、保存先は東京、ローカル操作とビルドは端末側という区別も説明されています。

制約は小規模な1アプリ・選択した1変換の検証で、既存テスト5件に通ったことは全業務の互換性を保証しません。包括的分析や別の更新も同様に成功したという結論にはしません。自動修正をレビュー可能な状態まで進め、対象外の依存と業務動作を明示して確認する面接の材料になります。

**注目ポイント：★★★★★**

分析・修正・レビューを分け、ローカル実行とクラウド推論、稼働時間と経過時間の違いを話せます。

### ④ Codex Long Context：Context Windowが大きくても全部使うべきとは限らない

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/codex-context-window-1m-chatgpt-plan/

著者は8月17日、**ChatGPT契約でログインしたCodex CLI** の設定とステータス表示を調べました。`model_context_window` を広げる設定が契約経由でも反映されたという記録で、長い入力を最後まで処理させた性能試験ではありません。公式の[設定リファレンス](https://learn.chatgpt.com/docs/config-file/config-reference)も、文脈枠と自動圧縮のしきい値を別の設定として定義しています。

`~/.codex/config.toml` に **`model_context_window = 1000000`** と `model_auto_compact_token_limit = 900000` を置き、再起動後の新規会話で表示を確認しました。選べた4モデルの表示は既定258Kから **828K** へ増え、1,050,000を指定しても変わりませんでした。GPT-5.6 Solでは871,000指定で827K、872,000以上で828Kとなった表を残しています。

指定値の95%を表示する計算と、1Mから最大出力128Kを引いた872Kという説明は、表示と既存情報からの推定です。**著者は実装を読んで確かめていない**と明記しており、全契約に共通する内部仕様として断定しません。表示828Kに対して自動圧縮900Kでは高すぎると考え、750K付近へ下げて様子を見る予定ですが、その運用結果もまだ測っていません。

料金については、APIの長文単価と契約利用を分け、担当者投稿に基づく「契約では長文を理由とした追加課金をしない」という説明を紹介しています。これは当時の説明で、利用枠消費やあらゆる契約条件まで無制限と保証する話ではありません。圧縮待ち削減、キャッシュによる効率、回答品質の改善はいずれもこの記事で実測した結果ではなく、今後の比較対象です。

面接では指定値、画面に表示された枠、実際に処理できた入力、圧縮のタイミングを分けて説明できます。「1Mと書けたから1Mを安定して使える」とは判断せず、必要な文脈の保持と回答品質を実際の課題で確かめるという応用につながります。

**注目ポイント：★★★★★**

表示の観測と内部仕様の推測を分け、長文設定が品質や費用の保証ではないと説明できます。

### ⑤ AI Security：Human-in-the-Loopは「すべての操作を承認」ではない

**出典：＠IT**

**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2608/18/news011.html

＠ITの論考は、**FIRST CSIRT Services Framework v2.1** の業務を基に、AIとの役割分担を **S0〜S5** の6型に独自整理します。分類軸は意思決定者、成果物、評価時点、失敗の形、失敗の見え方です。番号は自律度や成熟度の順位ではなく、大きいほどAIに任せるという意味でもありません。証拠は業務設計の論考で、各手法の効果を定量比較した実験ではありません。

S0は遮断や隔離などの自動実行で、誤ったルールが静かに広がるため設計と監査を残します。S1は監視で、検知が増えるほど人が見る情報も増え得るため、精度だけでなく対応率や見逃しを確認します。S2はAIの分析を承認する役割ですが、正しい提案に慣れると独立した分析能力が使われなくなるリスクがあります。**AIの推奨を見ずに判断する訓練**と反証のレビューが対策として挙げられます。

S3は分析を分担する協働で、一貫した説明でも前提が誤っていないか、別の仮説を点検します。S4は危機対応や外部説明を人が主導する仕事で、AIの草案を先に見ると論点が固定されるため、人が先に判断軸を作る方法を示します。S5は教育・演習で、資料数や受講者数ではなく、**フィッシングの報告率、初動時間、判断品質**といった行動に近い成果を評価します。

2ページ目はS0とS5に「失敗がすぐ見えない」という共通点を見いだします。誤りを即時・局所的に評価できるか、他業務へ連鎖するか、説明責任や長期的能力に関わるかで、人の関与を選ぶ考え方です。自動化が進むほどルールやモデル自体を攻撃から守る **Cyber for AI** も必要になり、防御にAIを使うAI for Cyberとは区別します。

制約として、人が最終承認するだけで安全になると証明した記事ではありません。能力低下や形骸化は長く潜伏し得るというリスク分析です。AI導入数を成果にせず、「どの判断を人に残し、その能力をどう確かめるか」まで説明する面接の材料になります。

**注目ポイント：★★★★★**

人の承認を残すだけでなく、独立した判断力と実地行動を評価する方法を話せます。

## 4. 今日の技術テーマ

### 表示された数字と、達成した成果を分ける

利用費用が見えたこと、HTMLが更新されたこと、移行のテストが通ったこと、文脈枠が広がったことは、それぞれ違う観測です。一つの完了表示から、投資効果や業務の正しさまで推測しないことが共通の論点です。

```text
観測した対象 → 測っていない対象 → 残る判断 → 追加で確かめる行動
```

セキュリティの承認も同様です。承認ボタンが押されたという記録と、反証を検討できる判断力は別に確かめます。面接では、道具が自動化する範囲と自分が検証する責任を具体例で話せます。

3. Agent minutesは経過時間ではなく、選んだ修正以外は残ります。

## 4. Codex Long Context：Context Windowが大きくても全部使うべきとは限らない

1. 観測されたのは設定後の表示で、長文の完走試験ではありません。
2. 上限の計算理由は著者の逆算による推測です。
3. 文脈枠と自動圧縮しきい値は別に管理します。

## 5. AI Security：Human-in-the-Loopは「すべての操作を承認」ではない

1. S0〜S5は成熟度の順位ではなく業務型です。
2. 承認者がいるだけでは独立した判断力の維持を保証しません。
3. 教育は資料量より実際の行動と対応能力を確認します。

## C-3. JLPT文法

### 1. ～つつ
**Level：N1｜意味：** ある動作や状態と並行して別のことを行う。  
**形：** `動詞ます形去ます + つつ`  
**使い方：** 自動化を進めながら必要な監督を残すことを述べます。  
**例：** `品質を維持しつつ、Model Costを削減します。`  
**補足：** 自動化を進めながら必要な監督を残すことを述べます。

### 2. ～に伴って
**Level：N1｜意味：** ある変化と一緒に別の変化が起こる。  
**形：** `名詞 + に伴って`  
**使い方：** AI利用の拡大と管理上の課題の関係を説明します。  
**例：** `Agent利用の拡大に伴って、Cost Governanceの重要性も高まります。`  
**補足：** AI利用の拡大と管理上の課題の関係を説明します。

### 3. ～にとどまらず
**Level：N1｜意味：** ある範囲だけでなく、さらに広い範囲にも及ぶこと。  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 前の範囲から後ろへ話題を広げます。  
**例：** `AI FinOpsはToken Costの削減にとどまらず、Task当たりのBusiness Valueまで評価します。`  
**補足：** 前の範囲から後ろへ話題を広げます。

### 4. ～に応じて
**Level：N2｜意味：** 条件や変化に合わせて、対応を変えること。  
**形：** `名詞 + に応じて`  
**使い方：** 名詞に接続し、条件と対応の関係を示します。  
**例：** `Business Valueに応じてAI予算を配分します。`  
**補足：** 名詞に接続し、条件と対応の関係を示します。

### 5. ～たうえで
**Level：N2｜意味：** 前のことを済ませ、それを前提として次の行動をすること。  
**形：** `動詞た形 + 上で`  
**使い方：** 単なる順序だけでなく、必要な準備・確認の意味を含みます。  
**例：** `Costと成功率を計測したうえで、Model Routingを調整します。`  
**補足：** 単なる順序だけでなく、必要な準備・確認の意味を含みます。

### 6. ～一方で
**Level：N2｜意味：** 同じ事柄の、対照的な二つの側面を述べること。  
**形：** `普通形 + 一方で`  
**使い方：** 前後は逆の評価や異なる側面でもつなげられます。  
**例：** `Long Contextは便利な一方で、Token Costが高くなることがあります。`  
**補足：** 前後は逆の評価や異なる側面でもつなげられます。

### 7. ～とは限らない
**Level：N2｜意味：** 必ずそうなるわけではなく、例外や別の可能性があること。  
**形：** `普通形 + とは限らない`  
**使い方：** 全面的な否定ではなく、一般化を避ける表現です。  
**例：** `高価なModelを使えばTask当たりCost効率が高くなるとは限りません。`  
**補足：** 全面的な否定ではなく、一般化を避ける表現です。
