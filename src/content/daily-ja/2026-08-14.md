### ① Markdownログ検索Local MCP：個人KnowledgeをAgent Context Layerへ

**出典：Zenn**

**原文：** https://zenn.dev/yamk/articles/mdlog-mcp-local-markdown-search

著者はCodexのスケジュール機能で技術情報をMarkdownに保存し、別のリポジトリで作業するときにも過去ログを参照したいと考えました。対象は2026年4月24日〜8月13日の **229件**で、AI・Webの日次109件、インフラ・セキュリティ・データの日次105件、週次15件です。Gitで管理し、人が読めて `rg` でも探せる正本を残したまま、AIからの取得経路を追加しています。

**`mdlog-mcp`** はNode.js上のstdioサーバーで、ツールは4個です。`mdlog_overview` が件数・期間・種類を示し、`mdlog_list_entries` が日付やカテゴリで候補を絞り、`mdlog_search` が複数語のAND検索で行番号付き抜粋を返し、`mdlog_get_entry` が本文を取得します。長文はoffsetで分割できます。データベースや埋め込みは使わず、呼び出し時に日付付きMarkdownを探します。

読み取り専用で、日付がないMarkdownと指定ディレクトリ内のシンボリックリンクは対象外です。Claude Codeではユーザースコープ、Codexではユーザー設定へ登録したため、別のリポジトリから同じログを利用できました。一方で、**ローカルMCPが取得した本文は利用中のAIへ渡る**ため、機密メモなら送信先とクライアントを確認し、リポジトリ単位の設定も検討する必要があります。

著者は8月10日の週次と10〜13日の日次8本を参照させ、作業中のSpec Stackの構成と照合しました。提案は、Agent Plugins 1.0を1つのskillで試すことと、skill本体・配布コピー・ZIPの一致をCIで検査することでした。**MCPが担当したのは検索と本文取得までで、リポジトリとの比較はCodexが行っています。**

これは個人の利用経験であり、検索精度、応答時間、トークン削減率の比較実験は示されていません。229件を最初から全部渡さずに探索できた点と、元のMarkdown運用を保てた点が確認された利点です。大量データでの探索費用や、必要な記述を見落とさないかは別途検証が必要です。

**注目ポイント：★★★★★**

検索ツールとエージェントの推論の役割を分け、必要な範囲だけ読む設計と送信境界を説明できます。

### ② Guren：AI Agent時代のFull-stack TypeScript Framework

**出典：Zenn**

**原文：** https://zenn.dev/7nohe/articles/guren-ai-agent-framework

**Guren** は、Hono、Drizzle、Reactなどを毎回つなぎ合わせる手間と、AIが生成した「もっともらしいが微妙に違う」コードの検証を課題にしています。Bunを開発基盤に、HTTPはHono、ORMはDrizzle、画面はInertia.js・React・Vite、入力検証はZodで構成します。Laravel風の規約を与え、認証・Policy・キュー・メール・通知・キャッシュ・ストレージ・SSE・スケジュール・i18nなどを統合する、開発者自身による紹介です。

コントローラでは **`validateBody()` の失敗は422、`userOrFail()` は未認証なら401、`findOrFail()` は対象がなければ404**になります。`make:feature` はモデル、コントローラ、画面、ルート、バリデータをまとめて生成し、`add auth` などで機能を追加します。生成コードは利用者のリポジトリに置かれ、編集できます。

`bun run codegen` はルートとページから型情報を導出し、コントローラが渡す値とReactのPropsを照合します。Viteの監視で再生成され、データベースから画面までの変更漏れをビルドで検出する設計です。**`guren context Post`** は実際のモデル、ルート、Zodの入力、Props、テストをまとめ、エージェントが契約を推測しなくて済むようにします。

検証は、構造の整合性を調べる `guren check`、認証・入力検証・生SQL・秘密情報などを調べる **`guren audit`**、型を確認する `typecheck` の3系統です。記事の例では、`validateBody()` を `request.json()` に置き換えると、auditが該当ルートと修正方法を示し、非ゼロの終了コードを返しました。さらに `spec:generate` でER図などを導出し、コードから導出できない判断はADRに残して関連付け、`check --docs` でリンク切れを検出します。

公開評価は同じ機能追加を複数フレームワークで行い、型検査、テスト、エージェントに見せないHTTPスモークテストで採点しています。6回の評価を通算した45試行中43件が動作する機能を出荷した、と報告しています。新API公開直後のclaude-sonnet-5による比較では、補助設定込みで **3/3成功・費用中央値29%減、補助設定なしは1/3成功**でした。条件ごと3試行であり、統計的な優位や他のモデルへの再現性を示すものではありません。

配備先にはBunサーバーに加えAWS Lambda、Vercel、Cloudflare Workers向けプラグインを用意し、公式サイトはWorkersとD1を使っています。記事は開発中の枠組みと小規模評価であり、規約・型・静的検査が業務仕様の正しさまで保証するわけではありません。未知のAPIを理解させる情報と、誤った実装を落とす検査をセットにする点が面接で説明しやすい特徴です。

**注目ポイント：★★★★★**

ReactのPropsまでの型契約と、実行時の入力検証を区別し、生成支援と失敗検出を同じ設計で説明できます。

### ③ AWS IAM Role Manager：自動設定は最小権限を意味しない

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/iam-role-manager-lambda-execution-role/

8月12日に一般提供された **IAMロールマネージャ** は、サービステンプレートからロールを払い出す仕組みです。記事は対応する6サービスを挙げ、Lambdaに対象を絞って有効・無効アカウントの画面とAPIを比較しました。有効なアカウントでは関数作成時の実行ロール欄がなくなり、設定を省略して開始できました。検証リージョンは **us-east-1** です。

CloudTrailの **`AcquireRole`** には使用テンプレートと置換値、作られたロール名が残り、`get-role` の `SourceRoleTemplate` から出所を追えます。Lambdaに割り当てられたのは **`PowerUserRole`** で、信頼先はLambda、管理ポリシーは `PowerUserAccess` でした。記事が確認したv12はIAM、Organizations、Accountを除く広い操作を許し、それらにも一部例外を設けています。最小権限を自動推定する機能ではありません。

同じテンプレートはElastic Beanstalk、EventBridge、Step Functionsにも割り当てられますが、全サービスがPowerUserAccessになるわけではありません。Secrets Managerのローテーション用テンプレートは対象や条件を持つインラインポリシーです。`@{...}` にアカウントなどの値を入れ、`@Enabled` 付き部分は対応パラメータが有効な場合に適用されます。

デフォルトのLambdaコードを1回実行したログは、処理2.13ms、課金112ms、初期化109.34ms、設定メモリ128MBに対して最大使用37MBでした。`RoleLastUsed` に同リージョンでの利用が記録され、払い出したロールで実行されたことを確認しています。**1回の起動確認であり、性能比較ではありません。** 作成後は設定画面から専用ロールへ変更できます。

制約は権限の広さと共有です。`sts:AssumeRole` が許されるため、信頼ポリシー次第では同一・別アカウントの強いロールを引き受ける経路ができます。同じテンプレートの関数は同じPowerUserRoleを共有し、ロールマネージャを無効にしても既存の割り当ては残ります。共有ロールの変更は他の関数に影響し、権限や信頼ポリシーを変更するとテンプレート更新の管理対象から外れます。

著者は本番から分離した開発アカウントでの利用と、本番前の **関数専用・最小権限ロールへの切り替えと再テスト** を勧めています。広い権限のまま第三者が呼び出せる構成にせず、依存コードやLayersも同じ権限で動く点を確認します。GuardDuty、Budgets、費用異常検出は通知手段であり、API実行や費用発生を止める制御ではありません。

**注目ポイント：★★★★★**

設定を省略できることと最小権限を区別し、AcquireRoleから実際のポリシーまで追って確認できます。

### ④ Google Classroom × Gemini：Rubric自動生成でもHuman Reviewを残す

**出典：CodeZine**

**原文：** https://codezine.jp/news/detail/29295

Googleは8月5日、**Google Classroom** にGeminiによる **ルーブリック** 作成支援を追加すると発表しました。ルーブリックは課題の評価基準表です。課題作成の途中で内容に基づく案を生成し、教育者が確認・編集してから追加する流れに組み込まれています。評価基準を準備する負担の軽減を狙う機能で、採点の妥当性を自動的に保証するという説明ではありません。

既存のルーブリックファイルをClassroomの形式へ変換する経路もあります。また、Geminiタブで提供した情報から作成し、**Google SheetsやDocsへエクスポート**して授業に添付できます。新規生成だけでなく、既存資料の取り込みと出力先まで含む作業のつながりが具体的な特徴です。

対象は **18歳以上**で、ClassroomでGeminiが有効なら管理者の追加設定は不要とされています。Rapid ReleaseとScheduled Releaseの両方で8月5日から1〜3日以内の展開を予定し、Education Fundamentals、Standard、Plusが対象です。これは発表時の提供条件であり、利用者全員が無条件で使えるわけではありません。

原文は機能発表を伝える短いニュースで、教員の準備時間、評価の一致率、生成ミス率などの実測はありません。面接で応用するなら、生成した基準を誰が確認し、授業目標と一致しない項目をどう編集するかを説明できます。人の確認を工程に残すのは発表の利用手順に沿いますが、その効果を数値で実証したという主張はしません。

**注目ポイント：★★★★★**

生成結果をそのまま決定に使わず、確認・編集・配布まで含む業務フローとして説明できます。

### ⑤ QAをやめて、QAをはじめる──欠陥検出0件が続いた組織で、品質保証の重心を3回動かした話

**出典：LayerX Engineering Blog**

**原文：** https://tech.layerx.co.jp/entry/quit-qa-start-qa

LayerXのAi Workforceでは、5月下旬以降、週次リリース前の確認型テストで欠陥検出0件が続き、**6月は252シナリオを実行して0件**でした。しかし本番では環境差、設定、運用、基盤、外部連携に関する問題が残っています。重大障害が増えたという話ではなく、従来の仕様確認で拾いやすい場所からリスクの中心が移った、という組織の振り返りです。

一人目のQAエンジニアが入社した2025年10月は、まず重大度、報告手順、対応履歴、ポストモーテムを整えました。報告の増加は、以前は個別対応していた事象まで記録するようになった影響を含み、品質悪化だけでは説明できません。12月は観測された欠陥流出を受け、機能・回帰・ストーリー・探索的テストを厚くし、一時的な重複と速度低下を許容しました。その時点で、状況が収束したら手動確認を圧縮する出口条件も決めています。

検出減少の原因については、レビュー指摘が **CIのガードレール** へ移り、欠陥がテスト工程に届く前に除かれた可能性と、モデルの進化やセルフレビューで混入が減った可能性を挙げています。一方、実装と同じ文脈でAIがテストを作り、通るテストに偏った可能性も残します。**原因と減少の因果関係を示せるデータはなく、観測と仮説を分けています。**

方針はテスト廃止ではなく、活動配分の変更です。CIや開発者と重複する反復的な手動確認を減らし、自動回帰テスト、独立した探索、仕様・利用場面への批評、本番の観測を増やします。全案件の仕様理解をQAへ集中すると、理解速度が開発全体の上限になるため、高リスク案件などQAが関わる価値の大きい場所を選びます。AIで作業を速めても、出力を判断する仕様理解は残ります。

次の重心は **価値を判断できる基準・観測・証跡の設計** です。公開後に何を見れば機能の価値を確かめられるかを事前に決め、現場に近い人が受け入れ確認の主体になるよう組み直しています。観測、検出、価値の検証へと約10か月で3回重心を移した事例であり、この前提がない組織まで手動テスト削減を勧めるものではありません。

**注目ポイント：★★★★★**

欠陥0件を無欠陥と誤解せず、観測の変化、因果仮説、残るリスクからQAの投資先を説明できます。

## 4. 今日の技術テーマ

### 生成を速くする前に、判断の根拠を残す

必要な情報が読めること、機械が契約を検査できること、人が結果の適用範囲を判断できることをつなぎます。mdlog-mcpの行番号、Gurenの検査結果、IAMのAcquireRoleはそれぞれ異なる根拠です。Classroomでは教師が基準を確定し、LayerXでは現場が価値を判断できる観測を用意します。

```text
対象と根拠を取得
    ↓
生成・設定を実行
    ↓
型・権限・入力を検査
    ↓
人が目的と適用範囲を判断
    ↓
本番の結果を観測
```

## C-3. JLPT文法

### 1. ～にとどまらず
**Level：N1｜意味：** ある範囲だけでなく、さらに広い範囲にも及ぶこと。  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 前の範囲から後ろへ話題を広げます。  
**例：** `ログの検索にとどまらず、開発の相談にも情報を使います。`  
**補足：** 前の範囲から後ろへ話題を広げます。

### 2. ～かねない
**Level：N1｜意味：** 望ましくない事態が起こる可能性があること。  
**形：** `動詞ます形去ます + かねない`  
**使い方：** 動詞のます形から「ます」を除いて付けます。通常は悪い結果に使います。  
**例：** `共有ロールを変更すると、別の関数にも影響しかねません。`  
**補足：** 動詞のます形から「ます」を除いて付けます。通常は悪い結果に使います。

### 3. ～なくしては
**Level：N1｜意味：** それがなければ、後ろのことは難しい、またはできないこと。  
**形：** `名詞 + なくしては`  
**使い方：** 必要条件を強く示し、後ろに否定的な判断を置きます。  
**例：** `独立した観点なくしては、テストの偏りに気づくことは難しいです。`  
**補足：** 必要条件を強く示し、後ろに否定的な判断を置きます。

### 4. ～とは限らない
**Level：N2｜意味：** 必ずそうなるわけではなく、例外や別の可能性があること。  
**形：** `普通形 + とは限らない`  
**使い方：** 全面的な否定ではなく、一般化を避ける表現です。  
**例：** `検出がゼロでも、欠陥がないとは限りません。`  
**補足：** 全面的な否定ではなく、一般化を避ける表現です。

### 5. ～に基づいて
**Level：N2｜意味：** 情報や規則などを根拠として行動・判断すること。  
**形：** `名詞 + に基づいて`  
**使い方：** 何を判断の土台にしたのかを明確にします。  
**例：** `本番の観測に基づいて、QA活動の配分を見直します。`  
**補足：** 何を判断の土台にしたのかを明確にします。

### 6. ～たうえで
**Level：N2｜意味：** 前のことを済ませ、それを前提として次の行動をすること。  
**形：** `動詞た形 + 上で`  
**使い方：** 単なる順序だけでなく、必要な準備・確認の意味を含みます。  
**例：** `生成した基準を確認したうえで、課題に追加します。`  
**補足：** 単なる順序だけでなく、必要な準備・確認の意味を含みます。

### 7. ～一方で
**Level：N2｜意味：** 同じ事柄の、対照的な二つの側面を述べること。  
**形：** `普通形 + 一方で`  
**使い方：** 前後は逆の評価や異なる側面でもつなげられます。  
**例：** `開発の着手は早まる一方で、実行権限の確認は残ります。`  
**補足：** 前後は逆の評価や異なる側面でもつなげられます。
