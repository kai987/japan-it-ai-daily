# A. 詳細版

2026年9月8日午前から9月9日午前までの新着を中心に確認し、前日に扱ったIdentity-Aware AI Gateway、AI Coding Supply Chain、Memory Lifecycle、Figma Make→Claude Code、富士通のAI-driven Work RedesignはTop 5から外した。本日の共通テーマは、**AI Agentが現実のSystemへ作用するほど、Model CapabilityそのものよりExecution Boundary、Credential、Deterministic Control、Auditの設計が重要になる**という点にある。

## 1. 今日読むべき5本

### ① COBOL、VMware、.NETまで――AWS「45億行に及ぶコード処理」で見えたAIレガシー刷新の現状：「数年→6週間」「8カ月→数日」の事例に学ぶ「4つの知見」

**出典：＠IT｜2026年9月9日 08:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/09/news027.html

AWSは`AWS Transform`の一般提供開始から1年の成果として、45億行を超えるSource Codeを処理し、数十万台のVMを移行したと説明している。事例では、約25万行のMainframe ApplicationについてCode変換とTestを6週間で完了し、従来は数年かかっていた作業を短縮した。CSLでは数千台規模のVMware移行計画を従来の約10倍の速度で作成し、Signaturit Groupでは6～8カ月を見込んでいた.NET Modernizationを数日へ短縮したという。Cloud Migration全体で最大60％のCost削減などの数字も紹介されているが、これらはAWSおよび顧客の報告値であり、統一条件のIndependent Benchmarkではない。

AWSが45億行規模の経験から整理した4点の方が、Architectureの学びとしては重要だ。利用者ごとに普段使うToolが違うため、AWS Transformは**MCP Server**を介してKiro、Claude Code、Cursor、Codexから利用できるようになった。Extensionを許しつつ共通基盤でQualityを保つこと、Architect・Developer・Reviewer・Approver間で変更とHandoffを追跡できること、そして複雑なMigrationではAIへ任せ切らず、精度と再現性が必要な処理には**決定論的な手法**を選べることも求められた。**制約：** 6週間や60％という成果は対象System、依存関係、Test、組織体制によって変わるため、自社環境ではMigration ContractとRegression Testを別途設計する必要がある。

**注目ポイント：★★★★★**  
AI Legacy Modernizationを「Codeを書き換えるModel」ではなく、MCP、Change Tracking、Human Review、Deterministic Stepを持つWorkflowとして捉えられる。

### ② LLM乗っ取りでサイバー攻撃者がコスト節約　知財流出の危険性も高まる「LLMジャッキング」の深刻度

**出典：＠IT｜2026年9月8日 21:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/08/news083.html

Google Threat Intelligence Group（GTIG）は、盗んだAI AccountやCloud Resourceを使い、被害組織の負担で攻撃者自身のAI処理を実行する`LLM Jacking`を報告した。2026年にはDark WebでClaude、Gemini、Cursor Pro、DevinなどAI関連Accountの取引需要が増え、平均価格も年初から2倍以上になったという。LUMMAC.V2やACRSTEALERといったInfostealerはBrowser保存情報だけでなく、開発端末のAI Tool Local Configを直接狙うようになっており、平文のAPI KeyやRouting設定がAttack Surfaceになっている。Riskは請求だけではなく、企業独自Model、Prompt、Fine-tuning Skill、Training Data、RAG Knowledge Baseの流出にも及ぶ。

2026年4月にMandiantが調査したIncidentでは、露出した**GitHub PAT**からGoogle Cloudへ侵入し、Gemini Enterpriseを有効化、HPC Instanceを起動、Artifact RegistryへLiteLLMとManusのImageを置き、PublicなCloud RunへDeployした。さらに悪意あるEditor Service Accountを作成してKeyをExportし、**BigQuery**からEnvironment Variableや追加Credentialを探索、被害組織のDataでAI Workbench上にRAG Pipelineを構築した。最後には**Cloud Quotas API**を悪用して`NVIDIA RTX 6000 GPU`のQuotaを増やし、48 vCPU Instanceを複数起動した。**制約：** これはGTIG / Mandiantが扱った特定Incidentであり、一般的な発生率や固定Attack Patternを示すBenchmarkではない。実務上はCredential、Quota Change、Service Account Creation、Public Exposure、GPU Costを相関して見ることが重要になる。

**注目ポイント：★★★★★**  
AI Security、Cloud IAM、FinOps、Developer Endpoint、RAG Data Protectionが同じIncident Surfaceになっていることを具体的に理解できる。

### ③ Claude Codeを安全に使い倒すための、実行環境の隔離 はじめの一歩

**出典：DevelopersIO｜2026年9月8日**  
**原文 URL：** https://dev.classmethod.jp/articles/claude-code-isolation-20260901/

記事はClaude Codeの全Riskを一度に解こうとせず、「Software Supply Chain Attackが開発環境へ入ったとき、機密情報漏えいのBlast Radiusをどう小さくするか」にScopeを絞る。AI Codingでは`npm install`や`npx`の実行頻度が増え、人間がすべてのTransitive DependencyをReviewするのは現実的ではない。最初のBoundaryである**Bash sandbox**は`/sandbox`から設定でき、CommandとChild ProcessのWrite先やNetwork Accessを制限できる。ただしSandboxが失敗した場合にUnsandboxedでRetryする経路があるため、`sandbox.allowUnsandboxedCommands: false`で迂回実行を明示的に止める必要がある。

**Dev Container**はIDE Extension、Dependency、Test、さらに人間が実行する`npm run dev`までContainer内へ含められるが、MountしたDirectory、Environment Variable、Git Credential、Networkは自動的には安全にならない。DooDのようにHost Dockerへ強い権限を渡す構成もBoundaryを弱くする。3つ目の**Claude Code on the Web**はLocal Hostから実行を離せるが、記事ではResearch Previewとして扱われ、Bedrock / Vertex AI、Internal Network、Hardware依存などに適用制約がある。結局、隔離が守れるのは「壁の外に残したSecret」であり、ContainerやRemote Environmentへ何を持ち込むかが設計の中心になる。

**注目ポイント：★★★★★**  
「Sandboxを使っています」で終わらず、Command、Container、Remote RuntimeそれぞれのBoundaryとEscape Pathを説明できるようになる。

### ④ Meta、パーソナルAIエージェント「Muse」発表　メール送信や買い物も代行（まずは米国で無料提供開始）

**出典：ITmedia NEWS｜2026年9月9日 06:41**  
**原文 URL：** https://www.itmedia.co.jp/news/article/2609/09/2000001294/

Metaの`Muse`は米国でiOS、Android、Web版の提供を開始し、基盤Modelとして**Muse Spark 1.3**を採用する。質問応答だけでなく、Mail送信、旅行予約、Browser Formへの入力、交渉、長時間Taskの継続実行など、実世界のSide Effectを伴う処理を行える。PaymentではStripe LinkのDisposable Card Numberを利用し、今後Shop Payや1PasswordとのIntegrationも予定されている。Personal Agentが単なるChatからAction Executorへ変わることで、CredentialとAuthorizationをModelからどう分離するかが中心課題になる。

Museは専用Cloud環境の**Muse Secure VM**で動き、同じVM内にMuseとはSystem-levelで分離された`Sentinel`が常駐する。外部ServiceへのActionとNetwork CommunicationはSentinelの許可を必ず通り、Muse自身はこれを無効化できない。PasswordやPayment CredentialはMain Agentへ見せずProxy Tokenとして扱い、Real ValueはNetwork Egressで差し替える。Mail送信やPurchaseなど高Impact ActionではUser Confirmationも残る。**制約：** Meta自身がPrompt Injectionを未解決問題と明記しており、Untrusted Input、Classifier、Human Approvalを重ねてもZero Riskではない。Bug Bounty最大30万ドル、単一Userへ影響するPrompt Injection成功例最大13万ドルという数字はSecurity ProgramのIncentiveであり、発生確率の指標ではない。

**注目ポイント：★★★★★**  
`Agent ≠ Credential Owner ≠ Policy Enforcer`というRuntime分離を、具体的な製品設計として確認できる。

### ⑤ Amazon Linuxが4年ぶりにメジャーバージョンアップ、「Amazon Linux 2027」パブリックプレビュー。SELinuxがデフォルトで強制モードに

**出典：Publickey｜2026年9月9日**  
**原文 URL：** https://www.publickey1.jp/blog/26/amazon_linux4amazon_linux_2027selinux.html

AWSは`Amazon Linux 2027`をPublic Previewとして公開した。Amazon Linux 2023以来およそ4年ぶりのMajor Updateで、Fedora 44 / 45の一部を取り込みながらAWS独自のRelease CycleとSupport方針を維持する。Kernelは**7.1以上**、Package Managerは引き続きRPM / `dnf`、x86-64とARMに対応し、AWS NeuronなどAccelerator向けDriverも含む。Cloud / SRE Teamにとって最も大きなMigration PointはSecurity Defaultの変更だ。

Amazon Linux 2023ではSELinuxが有効でもDefaultは**Permissive**だったが、2027では**Enforcing Mode**がDefaultになる。つまりroot / AdministratorであってもPolicyに反するAccessは拒否されるため、Custom Daemon、Container Runtime、Monitoring / Security Agent、Volume Pathなどが従来通り動くとは限らない。**制約：** 現在はPublic Previewであり、記事にはProduction Performance Benchmarkや確定したGA Dateは示されていない。SELinux Audit、Custom Policy、Kernel / Driver Compatibility、x86-64 / ARMの双方を検証してからMigration Planを作る必要がある。

**注目ポイント：★★★★★**  
OSのDefault Security Policyが変わるとApplicationそのものが未変更でも運用Riskが変わる、というSRE / Cloud Migrationの基本を復習できる。

## 2. カテゴリ別サマリー

### 🤖 AI / Agent

AWS TransformとMuseに共通するのは、AIの推論能力をそのままProduction Side Effectへ直結させない点だ。Migrationでは決定論的StepとHuman Reviewを残し、Personal AgentではSentinelとProxy CredentialでExternal ActionをGateする。Agent PlatformはModel APIの集合ではなく、Workflow、Identity、Execution Boundary、Auditを持つRuntimeへ近づいている。

### 💻 Frontend

React / Next.jsの新着専用記事でTop 5を入れ替えるほどのものは確認できなかった。一方、Claude Code隔離の記事はFrontend / Node.js Teamにも直結する。`npm install`や`npx`をAgentが高頻度で実行する環境では、Source DiffだけでなくDependency Execution、Git Credential、Env Secret、Dev Server NetworkをThreat Modelへ含める必要がある。

### ☁️ Cloud-Backend

LLM JackingのIncidentはAI Credential LeakがCloud Run、BigQuery、Service Account、GPU Quotaへ横展開できることを示した。Amazon Linux 2027はHost側でSELinux EnforcingをDefaultにし、rootでも越えられないMandatory Access Controlを強化する。Cloud AI SecurityはIdentity PlaneとHost Policyの双方を扱う必要がある。

### 🏢 日本企業 Tech Blog

指定した国内大手Tech Blogから、厳密な時間Window内でTop 5より優先すべき新稿は見つからなかった。本日はAWS Transformの知見が企業面接に特に使いやすい。AIによるMigrationでも、Role分担、Handoff、Review、再現性は消えず、むしろAgentを組み込むために明文化が必要になる。

## 4. 今日の技術テーマ

### Agent Execution Boundary：高能力なModelほど実行権限を直接持たせない

本日の5本を一つのArchitectureとして見ると、IdentityやInputからAI Reasoningへ入り、その後に複数のExecution Boundaryを通してReal Side Effectへ到達する構造になる。AWS TransformではDeterministic Migration StepとHuman Review、Claude CodeではSandbox / Container、MuseではSentinel、Amazon LinuxではSELinuxがそれぞれBoundaryとして働く。LLM Jackingは逆に、このBoundaryとCredential管理が破られると、企業のModel、RAG、GPU、Cloud BudgetまでAttack Resourceへ変わることを示した。

**メリット：** Model ErrorやPrompt Injectionが即座に無制限Actionへ変換されにくい。PermissionをModel Versionから分離できるため、Model交換時もPolicyを保持しやすい。Incident発生時にはReasoning、Credential、Sandbox、Host Policyのどこで失敗したかを切り分けやすい。またRead、Write、External ActionをRisk別に段階開放できる。

**制約：** Isolation LayerはDeveloper ExperienceやEnvironment MaintenanceのCostを増やす。ContainerもMount、Network、Git Credential、DooDの設定次第では安全ではない。強いPolicyは正常なAgent Taskを止める可能性もある。さらにSELinuxやSentinelがActionを制御できても、Business判断そのものの正しさまでは保証しないため、Test、Evaluation、Domain Ruleが別に必要になる。

**国内企業での導入時の注意点：** Agent ActionをRead / Analyze、Code Write、Production Change、External Message / Paymentに分類し、Riskに応じてBoundaryを変えると運用しやすい。CredentialはShort-livedにし、Agent Contextへ直接埋め込まない。Legacy Migrationでは旧新SystemのDiff、Test Evidence、RollbackをDone Definitionに含める。人の承認を残す場合も、どのActionで誰が承認するかをWorkflowとして固定する必要がある。

面接では次のようにまとめられる。

> AI Agentを本番利用する場合、Modelの判断能力と実行権限を分離し、Sandbox、Policy Engine、OS Control、Human Approvalなど複数のExecution BoundaryでSide Effectを制御することが重要だと考えています。

# B. 重要ポイントと面接で使える知識

## 1. AWS TransformとAIレガシー刷新

- AWS TransformはCode変換単体ではなく、依存分析、Migration Planning、Change Tracking、Handoffを含むWorkflowとして見る必要がある。
- 45億行超の処理、25万行Mainframeを6週間という結果はAWS / 顧客事例であり、自社Systemで同じ効果を保証するBenchmarkではない。
- MCP Serverを介してKiro、Claude Code、Cursor、CodexからTransform機能を利用できるため、Modernization Capabilityが開発Workflowへ直接組み込まれている。
- 複雑な移行ではAI任せにせず、精度と再現性が必要なStepは決定論的にし、人が介入できる余地を残す。

## 2. LLMジャッキング

- AI CredentialはModel APIだけでなく、GPU、Cloud Budget、RAG、Training Data、企業独自Modelへ到達する入口になり得る。
- 2026年4月IncidentではGitHub PATからCloud Run、BigQuery、Service Account、Cloud Quotas APIまで侵害が拡張した。
- InfostealerがAI Tool Local Configを直接狙うため、Developer EndpointもAI PlatformのSecurity Boundaryとして扱う必要がある。
- Billing Spikeだけでなく、Quota Change、Service Account Creation、Public Exposureを相関して検知する。

## 3. Claude Codeの実行環境隔離

- Bash sandbox、Dev Container、Web Runtimeは守るScopeが違い、単純に「Sandboxあり」と評価してはいけない。
- `sandbox.allowUnsandboxedCommands: false`でSandbox外Retryを止め、意図しないBypassを防ぐ。
- Dev ContainerでもMount、Env、Git Credential、Network、DooDを別に管理する必要がある。
- Isolationが守るのは外側に残したSecretなので、不要Credentialを環境へ持ち込まないことが基本になる。

## 4. Meta Muse

- MuseはMail、購入、予約などReal Side Effectを持つため、通常のChatbotより強いAuthorization Layerが必要になる。
- Muse Secure VMと独立Sentinelにより、ReasoningとExternal Action Permissionを分離している。
- Main AgentにはProxy Tokenしか見せず、Real CredentialはEgressで差し替える。
- Prompt Injectionは未解決であり、ClassifierやHuman Approvalを追加してBlast Radiusを小さくする設計である。

## 5. Amazon Linux 2027

- Amazon Linux 2027はPublic Previewで、Kernel 7.1+、RPM / dnf、x86-64 / ARMを継続して提供する。
- 最大のCompatibility PointはSELinuxがDefault PermissiveからDefault Enforcingへ変わること。
- rootでもPolicy違反Accessが拒否されるため、Daemon、Container、Monitoring Agentを再検証する必要がある。

### 1. 仕掛ける（しかける）

**オリジナル例文：** 改善の議論を仕掛ける前に、具体的な課題を整理します。  
**ニュアンス：** 「始める」よりも意図的に働き掛けたり準備を施したりする響きがあり、普通の作業開始には使いにくい。

## C-3. JLPT文法（1項目）

全履歴との重複確認後、この日の新規文法は1項目。以前に紹介した文型は再登録せず、当日の原文で確認できる未収録項目だけを追加しています。5～8項目に満たない日も重複で補いません。

### 1. ～に対して
**学習目安：** N3  
**意味：** 動作や態度が向かう対象を示す。  
**接続：** `名詞＋に対して／に対する＋名詞`  
**使い方：** 操作や働き掛けの対象を示す。対比の用法もあるが、別の新項目には分割しない。  
**例文：** `管理者に対しても、同じアクセス制御を適用します。`  
**注意点：** 評価する立場を示す「にとって」と、動作の対象を示す「に対して」を区別する。 当日Top 5の原文表記：に対して。例文は学習用の創作。  
**原文出典：** [Top記事](https://www.publickey1.jp/blog/26/amazon_linux4amazon_linux_2027selinux.html)
