### 1. AIアシスタントにレッドチーミングを導入して学んだこと

**出典：SmartHR Tech Blog｜2026年9月18日**  
**原文 URL：** https://tech.smarthr.jp/entry/2026/09/18/113623

SmartHRのAIアシスタントは、事前に登録した就業規則や社内マニュアルを参照して従業員の質問へ回答する。ModelやSystem Promptを変更すると、以前は防げていた攻撃が再び通る可能性があるため、Security Checkを人手の一回作業にせずRed Teamingを継続CIへ組み込んだ。Risk分類は **OWASP Top 10 for LLM Applications 2026** に基づいて整理し、AIで生成した攻撃Caseを人が確認・手直しする。さらにpromptfooのPlugin一覧も参考にし、攻撃面を「質問受付」「AI Agentによる文書検索」「回答生成」の3層へ分けている。間接Prompt Injectionでは、攻撃文を混ぜた固定Mock文書をContextとして与える。

攻撃CaseはCSVで管理し、CIが毎朝1件ずつProductの回答生成を呼び出す。得られた回答は判定用LLMがRiskごとの合格条件と照合し、集計結果をSlackへ送る。ここで重要なのは、Security Scoreだけを上げないことだ。Guardrailを強めると、攻撃に似ただけの正常な質問まで断る可能性があるため、通常の回答精度Datasetも変更前後で実行し、Security RegressionとAnswer Quality Regressionを別Gateとして扱っている。

**ただし、**記事は攻撃成功率やJudge LLMのAccuracy改善率をBenchmarkとして公開していない。判定用LLM自体も誤判定し得るため、Case、合否条件、通常回答Datasetを継続的に見直す必要がある。学ぶべき点は「Promptに禁止文を書く」ことではなく、**OWASP分類→3層Test→毎朝CI→通常品質回帰**という外側の検証Loopである。

**注目ポイント：★★★★★**  
OWASPを土台に、質問・検索・回答の3層へ攻撃Caseを分け、毎朝CIでJudge LLMと通常回答の品質回帰を回す実装が具体的。

### 2. 生成 AI 機能開発を加速するゴールデンパス [DeNA インフラ SRE]

**出典：DeNA Engineering｜2026年9月18日**  
**原文 URL：** https://engineering.dena.com/blog/2026/09/golden-path-for-generative-ai-platform/

DeNAでは複数Productへ生成AI機能を継続追加するたびに、CloudごとのCredential、長時間推論の非同期化、Retry、Monitor、Deploymentを個別設計する認知負荷が課題になった。そこで **SQSとEKS** を中心に再利用可能な非同期推論基盤を作り、Golden Pathとして提供した。本体SystemはQueueへJobを入れ、WorkerがVendor公式SDKでBedrock、Gemini Enterprise Agent Platform、Microsoft Foundryなどを呼び、Callbackが成功してからMessageを削除する。Terraform ModuleがQueue/DLQ/Auth/Monitorを、Helm ChartがDeployment、Kubernetes ServiceAccount、Autoscalingを共通化する。

AuthはKubernetes ServiceAccountのOIDCを軸にする。BedrockはIRSA、Google CloudはWorkload Identity Federation、Microsoft FoundryはFederated Identity Credentialで短期Credentialへ交換する。SQSは **At-Least-Once** なのでCallback側に冪等性が必要だ。KEDAはQueue長でPodをScaleするが、推論APIのQuota/Rate Limitを超えないよう最大Pod数と同時Job数を制限する。`ApproximateAgeOfOldestMessage` はQueue滞留の兆候を見る指標であり、個別RequestのLatencyそのものではない。

**ただし、**約51.3%というSpot価格差は2026年9月9日時点のc8g.large価格比較で、Platform全体のTCO実測ではない。設計上の核心は、Auth・Async Runtime・Deploy・Autoscale・Monitorを標準化する一方、Model選定、Prompt、Guardrail、推論Callは独自共通APIへ隠さず公式SDKのままApplication Teamへ残すことだ。Common PlatformとModel固有Featureの責任分界が明確である。

**注目ポイント：★★★★★**  
SQS＋EKS、OIDC、Terraform/Helm、KEDAでマルチクラウドAIの運用面をGolden Path化しつつ、推論APIそのものは共通化しない責任分界が明快。

### 3. Claude Code v2.1.275〜v2.1.276 の主要アップデート - claude.ai のスキル・プラグイン同期とプロキシ経由の 400 エラー修正

**出典：DevelopersIO｜2026年9月18日**  
**原文 URL：** https://dev.classmethod.jp/articles/20260918-cc-updates-v2-1-276/

DevelopersIOはClaude Code v2.1.275～v2.1.276の97件のChangelogを、13 Features、21 Improvements、62 Fixes、1 Compatibility Changeとして整理している。Enterprise利用でまず確認したいのはGateway Regressionだ。v2.1.275では `ANTHROPIC_BASE_URL` がProxyやGatewayを指す環境で全Requestが `400 … Input tag 'advisor_20260301'` になるRegressionが入り、v2.1.276はその1件だけを修正した。社内Gateway経由でClaude Codeを使う組織なら、Version Numberではなく実際のGateway Routeを使うRegression Testが必要になる。

また、claude.aiで有効なSkill/Pluginが同一AccountのTerminal Sessionへ同期され、`syncClaudeAiSkills: false` と `syncClaudeAiPlugins: false` でOpt-outできる。npm Source Pluginは `npm pack --ignore-scripts` で取得し整合性を検証する方式になり、Install Scriptは実行されない。Supply-chain Riskを下げる一方、Install Script依存の初期化はCompatibility Riskになる。`/rewind` がfork/background SessionでZero-filledまたは切り詰めたFileを復元するBug、Marketplace URLに含まれたTokenがMessage/Logへ出る問題も修正された。

**ただし、**これはRelease Changelogと作者による動作確認で、Productivityの独立Benchmarkではない。Fix後も過去Logに残ったSecretが自動消去されるわけではない。Upgradeでは **ANTHROPIC_BASE_URL、Plugin Sync、npm pack --ignore-scripts、/rewind、Historical Log** を別々のCheck Itemにし、段階展開する方が安全である。

**注目ポイント：★★★★★**  
Gateway互換、Plugin同期、npm取得方式、/rewind復元、Secret露出が同じ更新系列で変わり、Coding AgentのUpgrade Regressionを考える材料になる。

### 4. 散在する“29万ファイル”をAmazon S3に集約、「AIに聞くだけ」で検索可能に――AWSはどう実現？：航空データを想定して実装

**出典：＠IT｜2026年9月18日**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/18/news025.html

AWSのReference実装は、航空会社の複数Systemに散在するDataをAmazon S3へ集約し、**38GB・約29万File** をAmazon Bedrock Knowledge BasesでVector化・Index化する。各業務Applicationは **Amazon Bedrock AgentCore Gateway** を共通入口として同じAI検索基盤を利用する。S3上のData追加・更新・削除は検索Indexへ自動反映される。音声はAmazon Transcribe、地図・航路はAmazon Location Service、分析・要約はClaude Sonnet 4とClaude 3.5 Haikuを組み合わせる。Turnaround Managementでは45～90分の清掃、給油、手荷物積み降ろし、機体点検などを一画面で扱う。

AWSは、複数Systemを開いて突き合わせると30分以上かかる情報探索を、AIへの質問で数秒にできるとしている。Reference実装自体もKiroのSpec-driven Developmentを使い、12 Subsystem、79 Spec File、24 Requirement、9 Phaseへ分けた。Data Catalog DashboardではCategoryごとの容量、File数、Last Updatedを可視化し、Corpusの偏りやCoverage不足も確認できる。つまりRAGの前に、Data Lake、Index Lifecycle、Gateway、Business UIの境界が整理されている。

**ただし、**この **38GB・約29万FileはKiroで生成した架空Demo Data** であり、「30分超→数秒」もVendor Reference Demoの説明だ。ProductionのRecall、P95/P99、ACL、Index反映遅延、TCOを示す独立Benchmarkではない。自社適用ではData量だけを合わせず、実Corpus、Access Control、Freshness、Answer Qualityを同じ条件で測り直す必要がある。

**注目ポイント：★★★★★**  
38GB・約29万FileをS3、Bedrock Knowledge Bases、AgentCore Gatewayで扱う構成が具体的で、Kiro生成の架空DataというEvidence Boundaryも明示される。

### 5. 資生堂、AIエージェントで原料探索時間を95％削減　研究員の「目利き」を複数LLMで再現：Google Cloud Next Tokyo 26

**出典：ITmedia エンタープライズ｜2026年9月18日**  
**原文 URL：** https://www.itmedia.co.jp/enterprise/articles/2609/18/news020.html

資生堂ジャパンのAIXは、約40部門・130名のAmbassadorと業務特化Agentを組み合わせている。4月以降100回以上のHands-onを実施し、会社報告ではGeminiのMonthly Active率が82%超、3日に1回以上実務利用する従業員が42%、Gemini Enterpriseで作った組織横断Search Agentが社内資料探索時間を約67%削減した。研究開発の「エキス原料探索エージェント」は単なる検索ではなく、研究員が膨大な候補からどれが **有望** かを見極める「目利き」を再現することを狙う。

Architectureでは **HyDE** で曖昧な依頼から仮回答を作って検索を補助し、**Hybrid RAG** でKeyword SearchとVector Searchを組み合わせ、専門用語・成分名の検索精度を高める。さらに複数LLM Reviewで候補の妥当性を多面的に評価する。SecurityにはModel ArmorとIAMを使い、Private Service ConnectとAlloyDBによるData連携基盤も整備中だ。資生堂は原料探索時間95%削減、提案数20～50%増と報告している。

**ただし、**これはGoogle Cloud Next Tokyo 26での自社発表を記事化したConference Caseで、Sample Size、Before/After定義、Expert Agreement、失敗例、長期TCOの詳細は公開されていない。95%や20～50%を他社へ一般化せず、再現するならExpert一致率、候補採用率、Retrieval Coverage、Security Incidentを自社KPIとして継続評価する必要がある。

**注目ポイント：★★★★★**  
HyDE、Hybrid RAG、複数LLM Reviewで研究員の判断を再現し、Model Armor/IAMと組織展開まで含めて業務特化Agentを考えられる。

## 4. 今日の技術テーマ

### Verification Outside the Model

```text
Business / User Intent
        ↓
AI / Agent Capability
        ↓
External Verification
├─ Security Red Team + Normal QA
├─ Queue Semantics + Idempotency
├─ Upgrade Regression + Supply Chain
├─ Data / Index Lifecycle
└─ Expert Judgment KPI
        ↓
Commit / Release / Business Action
```

SmartHRはSecurityと通常回答品質を別Gateにする。DeNAはSQSのAt-Least-Once、DLQ、Quota、短期IdentityをRuntime Contractにする。Claude CodeはVersion Upgrade時のGateway・Plugin・LogをRegression対象にする。AWS Referenceは架空Demo Dataと実Corpusを分ける。資生堂は「目利き」をHyDE、Hybrid RAG、複数LLM Reviewと業務KPIに分解する。

メリットは、ModelやProviderが変わっても外部Gateを再利用でき、FailureのLayerを特定しやすいことだ。**ただし、**Validatorも完全ではない。Judge LLMは誤判定し、Queue Metricは個別Latencyではなく、Vendor DemoはProduction結果ではない。国内企業では各Workflowに **Source of Truth / External Gate / Permission / Failure Metric / Human Owner / Rollback** を持たせ、実障害からGate自体を更新する運用が必要になる。

# B. 重要ポイントと面接で使える知識

### 1. SmartHR Red Teaming
Security Testを一回の攻撃演習ではなく、OWASP分類・3層Attack Surface・固定Mock Context・Judge Rubricを持つ毎朝CIへ変えている。Guardrail変更時は通常回答のAccuracy Datasetも同時に回し、Security強化によるFalse Positiveを検出する。

### 2. DeNA生成AI Golden Path
Auth、Queue、Deploy、Autoscale、Monitorは共通化する一方、Model固有APIは公式SDKで残す。SQS At-Least-Onceに合わせCallbackを冪等化し、Queue AgeをRequest Latencyと混同しない。

### 3. Claude Code v2.1.275–276
Upgrade対象はModelだけではない。`ANTHROPIC_BASE_URL`のGateway互換、Skill/Plugin Sync、`npm pack --ignore-scripts`、`/rewind`、Historical Secret LogまでRegression対象として扱う。

### 4. AWS 29万File RAG Reference
S3、Bedrock Knowledge Bases、AgentCore Gatewayを分離したArchitectureは参考になるが、29万FileはKiro生成の架空Dataである。ReferenceをPerformance Guaranteeにせず、実CorpusでACL、Freshness、Recall、Latencyを測る。

### 5. 資生堂業務特化Agent
HyDEで曖昧Intentを補い、Hybrid RAGで専門語検索を強化し、複数LLM Reviewで候補を多面的に評価する。95％削減・20～50％増は自社Conference Caseなので、Expert一致率や採用率を自社KPIとして持つ。
