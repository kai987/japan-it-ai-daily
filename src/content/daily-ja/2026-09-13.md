### ① Sakana AI、一部「GPT-6 Astra」「Fable 5.1」超えうたうFugu最新版　連携先に「両モデルは含まず」

**出典：ITmedia AI＋｜2026年9月11日 13:11**  
**原文 URL：** https://www.itmedia.co.jp/aiplus/article/2609/11/2000001405/

Sakana AIは `Fugu Ultra v2` と `Fugu Max` を同時に発表した。どちらも単独のFoundation Modelというより、複数ModelとAgentを内部で組み合わせるOrchestration Layerとして理解した方がよい。利用者は **OpenAI互換API** から一つのModelのようにRequestを送り、Fugu側がTaskの難易度に応じてModelを選択し、必要なら専用Agent Teamを構成する。Ultra v2については、DeepSWEなど一部BenchmarkでGPT-6 Astra、Claude Fable 5.1、Fable 5を上回るとSakana AIが説明しており、しかもその3ModelはUltra v2の連携先に含まれていない。

Cost志向の `Fugu Max` は、100万TokenあたりInput 2ドル、Cached Input 0.25ドル、Output 6ドル。Sakana AIはGPT-5.6 Terra、Claude Sonnet 5、Kimi K3と比べOutput Priceを40～60％抑えたとしている。ただし、これはVendorが示したBenchmarkとPricingであり、Multi-model Orchestrationでは最終的な利用Token、Routing先、Agent間処理、LatencyがTaskごとに変わり得る。したがってRate CardだけではTCOを判断できず、自社Taskで `success rate / route / latency / total usage / cost per successful outcome` を確認する必要がある。

**注目ポイント：★★★★★**  
企業のMulti-model戦略が、Application内の分岐Logicではなく独立したRuntime / Platform Capabilityになりつつある。AI Platformの面接では、単一BenchmarkではなくRouting Policy、Fallback、Observability、Cost Attribution、再現性まで含めて話せる。

### ② 業務の30％をAIエージェントがこなすIT運用部門、なぜ「パワポ文書」を禁止したのか？：NTTドコモソリューションズに聞く「AIエージェント実装」のリアル（前編）

**出典：ITmedia エンタープライズ｜2026年9月11日 08:00**  
**原文 URL：** https://www.itmedia.co.jp/enterprise/articles/2608/20/news009.html

NTTドコモソリューションズのプラットフォームサービス部では、現在IT運用の約 **30％** をAI Agentへ任せ、最終的に70％へ引き上げる目標を置いている。しかし記事の中心はAgentそのものではなく、RAGを成立させるKnowledge Sourceの品質だ。2024年7月から社内文書を対象にRAGをTuneしたところ、主語・述語が省略され、図や口頭説明を前提にする「**パワポ文書**」が多く、AIがContextを補えなかった。加えて `0.6版`、`0.7版` といった途中VersionやCopyが乱立し、どれをAuthoritative Sourceとして参照すべきか判断しにくかった。

そこで日報・週報などをText中心の書き方へ変更した。これはMicrosoft PowerPointそのものを禁止する施策ではなく、Document単体で意味が通るようにするData Governanceである。Ontologyの進歩により部署ごとの用語や略称の表記揺れを吸収できる範囲は広がっている一方で、Source DocumentのSemantic Qualityまで不要になるわけではない。駒沢氏はさらに **Why → Outcome → AI Implementation** の順序を強調しており、Outcomeを決めずにAgentを導入するとToken Consumptionだけが増えてROIを評価できないと指摘する。

**注目ポイント：★★★★★**  
RAGのAccuracyが低いとき、すぐModelやEmbeddingを入れ替えるのではなく、Documentの完全性、Version Governance、Question Formulation、Ontology、Business Outcomeから切り分ける。なお30％は現状値だが、**70％は将来目標であり実績ではない**。

### ③ フィジカルAI向け「データ収集工場」に"潜入"　実機写真で学習データ生成の流れを解説

**出典：ITmedia AI＋｜2026年9月11日 12:34**  
**原文 URL：** https://www.itmedia.co.jp/aiplus/article/2609/11/2000001402/

ITmediaは千葉県習志野市の `J-HRTI 関東データファクトリー` を現地取材している。5社の民間企業で構成するConsortiumが運営し、稼働開始時は **35台のHumanoid** を並べてDataを収集する。OperatorはVR GogglesとControllerでRobotを遠隔操作し、物を掴んで移す、ひしゃくで樹脂Pelletをすくう、二段の箱から商品を取り出す、といったTaskを反復する。Robotの頭部と両手首にある **3 Camera** で映像を記録し、Annotation AreaでTimelineを分割して英語のAction Labelを付ける。

特徴的なのはFailureをNoiseとして一律に捨てない点だ。箱の中で落としても掴み直せるような**復旧可能な失敗**はTagを付けて残し、RobotがRecoveryを学べる教材にする。一方、箱外へ落として自力復旧できないCase、Operator Error、Cameraのずれなど設備側の問題はTrainingから取り除く。整理したDatasetでModelを作り、実機のSuccess RateやBugを見てDatasetを作り直し、FieldへDeployした後の成功・失敗DataもFactoryへ戻す。つまりCollectionだけではなく、`Data → Model → Robot → Field Evidence → Data` のLearning Loopを設計している。

**注目ポイント：★★★★★**  
Physical AIではData VolumeだけでなくFailure Taxonomy、Sensor Placement、Annotation Granularity、Recovery可能性が重要になる。ただし当初の最大50台計画はBuilding Specにより35台での運用開始へ変わっており、2027年の全国10拠点や2028年の産業特化Modelはまだ計画段階である。

### ④ [アップデート] AWS Transform for .NET のモダナイゼーションが GA となり CLI でも実行できるようになりました

**出典：DevelopersIO｜2026年9月11日**  
**原文 URL：** https://dev.classmethod.jp/articles/aws-transform-dotnet-cli/

AWS Transform for .NETのModernizationがGAとなり、ATX CLIから一つのCommandで実行できるようになった。DevelopersIOの検証ではmacOS M1 Max、Node.js 22以上、Gitを用意し、`atx custom def list` でAWS Managed Definition `AWS/dotnet-modernization` を確認している。変換対象は `.NET Framework 4.8` の小規模Console Appで、非SDK形式の`.csproj`、`App.config`、`ConfigurationManager`、`packages.config`を含む。ATXはGit Repositoryを前提とするため、Authorは最初にRepositoryを初期化してCommitした。

実行Commandは `atx custom def exec -p . -n AWS/dotnet-modernization -x -t --limit 30`。`-x` はNon-interactive、`-t` は `--trust-all-tools` で、非対話実行ではToolごとのPermission確認ができないため必須だった。`--limit` はAgent Minutesの上限で、30分設定では **30.41 / 30.00 Agent Minutes** に達してExit Code 2で止まり、その後Conversation IDからLimitを増やして再開している。TransformationはProject検出、Migration Plan、SDK-style `.csproj`、Configuration方式の置換、Legacy File削除、`dotnet build`まで進み、各StepをGit Commitとして記録した。最終Targetは `net10.0` となり、SampleはBuild・Runとも通った。

**注目ポイント：★★★★★**  
CLI化によってCIやCoding Agentへ組み込みやすくなる一方で、Trust Boundaryは広がる。特に`-t`は全Toolを信頼するOptionであり、Author自身も**変換Codeの妥当性は評価していない**。小規模Console AppのBuild成功をLarge Solutionへ一般化せず、IAM Scope、Diff Review、Unit / Integration Test、Agent Minutesを別Gateとして設計したい。

### ⑤ 本物そっくり“AI生成レシート“が経費精算の脅威に　マネフォ「自力で見破るのは難しい」　企業はどう備える？

**出典：ITmedia NEWS｜2026年9月11日 16:11**  
**原文 URL：** https://www.itmedia.co.jp/news/article/2609/11/2000001409/

`ChatGPT Images 2.5` で作られたReceipt Imageが、本物と見分けにくいとして話題になった。ITmedia NEWSも生成を試し、実在店舗名は再現できなかったものの、架空Store NameにすればLogo、Layout、商品名、価格などを本物に近い形で作れた。Money Forwardは、領収書加工による架空経費は以前から存在する課題だが、Generative AIによって作成CostとSpeedが変わり、企業が画像だけで真偽を見極めることはさらに難しくなったと説明している。

`マネーフォワード クラウド経費` は、Receiptだけで完結させず、**コーポレートカードや外部Serviceの決済Data**を組み合わせて実際の支払いを確認する。個人CardのPayment Dataを連携する、Card利用可能なのにReceipt精算を選んだCaseへ理由を求める、System連携が難しい支払いではOriginal Receiptを保管して抜き打ち確認する、といったControlも紹介されている。これは「ImageがFakeか」を直接当てるより、Imageとは独立したTransaction Evidenceを使う設計である。

**注目ポイント：★★★★★**  
Generative AI時代のFraud対策では、Artifactの見た目よりProvenanceとCross-checkが重要になる。ただしAI生成Receipt Detectorは**検討段階**で、公開されたAccuracyやFalse Positive / False Negative Benchmarkはない。したがって現時点では、Image Classifierを唯一のGateにせずPayment Data ReconciliationとAudit Ruleを組み合わせる方が堅い。

## 4. 今日の技術テーマ

### Intelligent Automationの前にIndependent Evidenceを置く

今日の5本には共通する設計原則がある。**AIが出したOutputを、そのOutput自身だけで正しいと証明しないこと**である。

```text
AI / Agent Output
       ↓
Independent Evidence
├─ Route / Cost / Latency telemetry
├─ Authoritative document version
├─ Failure / success data from the field
├─ Build + Test + Diff review
└─ Payment transaction record
       ↓
Business Decision
```

FuguではVendor Benchmarkを自社Taskで再現し、Routing後のCostとLatencyを見る。RAGではModelより前にAuthoritative Documentを作る。Physical AIでは実機の成功・失敗をDatasetへ戻す。AWS TransformではBuild Successの後にTestとReviewを置く。AI生成ReceiptではImageとは独立したPayment RecordをEvidenceにする。

メリットは、ModelやVendorを変更してもValidation Contractを再利用できることだ。一方で、別Evidence Channelの構築にはTelemetry、Version Governance、Payment Integration、Test Dataset、Human Samplingなど追加Costがかかる。またEvaluatorやLogそのものが誤る可能性もあり、Evidence Source自体を定期的に検証しなければならない。

国内企業で導入するなら、各AI Workflowについて **Primary Output / Independent Evidence / Failure Threshold / Human Owner** を先に定義する。RAGなら回答と引用元、Code MigrationならDiffとTest、ExpenseならReceipt ClaimとPayment Recordを分離する。Automation Scopeが広がるほど、この責任分離が重要になる。

**意味：** 前のActionを完了し、その結果を前提に次を行うこと。  
**接続：** `動詞た形 + 上で / 名詞 + の上で`  
**使い方：** CheckやValidationを済ませてからDecisionする順序を示す。  
**例文：** 支払いDataと照合したうえで、経費精算を承認します。  
**例文の意味：** Payment RecordとCross-checkしてからExpenseをApproveする。  
**Note：** Top 5のEvidence Designに対応する。

### 5. ～に応じて（N2）
**意味：** 条件や変化に合わせて、対応を変えること。  
**接続：** `名詞 + に応じて / 名詞 + に応じた + 名詞`  
**使い方：** RoutingやPermission、処理方法のDynamicな切替に使う。  
**例文：** Taskの難易度に応じて利用するModelを切り替えます。  
**例文の意味：** Task DifficultyによってModelをRouteする。  
**Note：** FuguのModel Routingを説明できる。

### 6. ～一方で（N2）
**意味：** ある側面とは対照的な、別の側面を並べて示す。  
**接続：** `普通形 + 一方で`  
**使い方：** ArchitectureのTrade-offを説明する。  
**例文：** CLIで自動化しやすくなる一方で、trust-all-toolsのRiskは増えます。  
**例文の意味：** Automationが容易になる反面、Trust Boundaryは広がる。  
**Note：** Top 4の利便性とSecurity Boundaryに対応する。

### 7. ～とは限らない（N2）
**意味：** 前の事実があっても、必ず同じ結論になるわけではないこと。  
**接続：** `普通形 + とは限らない`  
**使い方：** BenchmarkやSample Resultの過度な一般化を避ける。  
**例文：** Buildが成功しても、変換Codeの業務Logicまで正しいとは限りません。  
**例文の意味：** Build SuccessだけではBusiness Correctnessを保証できない。  
**Note：** Top 4のEvidence Boundaryに対応する。
