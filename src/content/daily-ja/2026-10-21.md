### 1. Claude Code から GPU を借りて学習ジョブを回す（Runcrate MCP サーバー）

**原文：** https://zenn.dev/runcrate/articles/c9a383739c3856

**公開時刻：** 2026-10-21 09:57:59 JST

Runcrateの開発チームが、開発エージェントからGPUクラウドへ仕事を渡す方法を紹介しています。常駐できるインスタンスとは別に、一つのコマンドを実行して止まるジョブを用意し、最大実行時間を1分から24時間の範囲で必須にしています。終了時にマシンと課金を止める仕組みで、学習の収束や処理の成功を保証するものではありません。製品提供者による手順の説明であり、他社との性能比較ではないという証拠の種類を先に押さえます。

MCP接続はStreamable HTTPで、初回にOAuthの画面からワークスペースと環境を選びます。MCPの設定へ直接APIキーを書く形ではなく、承認した環境とその月間予算で利用範囲を絞る説明です。一方、OpenAI互換の推論APIには別途キーを発行する例があります。認証方式を一括りにせず、エージェントが何を承認され、どの枠から費用が出るかを分けて理解できます。

A4000で最長2時間の学習を頼む例では、まずボリュームを探し、その識別情報と120分の上限を添えてジョブを作ります。ログ取得は返されたカーソルを次回へ渡し、続きから読みます。完了表示の後も最終ステータス・終了コード・費用を確認するため、ログが途切れただけで成功とは答えません。作業用のディレクトリはボリュームへ保存され、データセットやチェックポイントを次の仕事へ残せます。ただし、強制停止中の保存や複数ジョブの書込競合を検証した記事ではありません。

CLIでも同じ仕事を起動でき、遠隔ジョブの終了コードを返し、時間上限なら124になります。20種類以上のGPU、200以上のモデルという規模や、RTX 4090の毎時0.64ドルから、H100の3.38ドルからという例も載っていますが、いずれも10月21日時点の提供情報です。前払い残高の消費と実際の仕事全体の見積りは同じではありません。面接では、運用上限と認可、継続ログ、最終結果という具体的な確認点を説明でき、未測定の処理速度や費用効果まで約束しない判断につながります。

**読む価値：** 学習を頼む一言の裏にある認可、保存先、ログの続き、終了確認を分けて説明する練習になります。

### 2. Google OAuthがDPoPに対応したらしいので検証してみたら...なんか違った

**原文：** https://zenn.dev/tanahiro2010/articles/e891ed813641f6

**公開時刻：** 2026-10-21 09:36:05 JST

Google OAuthのDPoP対応を実装した作者が、公式資料とRFC、署名の計測、実際の交換結果を突き合わせています。検証は10月19日、Apple M4上のNode.js24.22.0、jose6.2.12、hono4.13.13で、専用のテストアカウントとConfidential Clientを使ったものです。本日ここで再実験した結果ではありません。仕様上の選択と記述の誤り、書かれていない挙動を分ける姿勢が中心で、差があるだけで認証突破と結論づけてはいません。

DPoPは秘密鍵で署名した証明を添えることで、鍵を持つ側へトークンの利用を結び付けます。ただし記事のGoogle実装では、対象はRefresh Tokenで、Access TokenはBearerのままです。ブラウザのCookieも守備範囲の外にあります。認可コード交換時の証明識別子はコードのハッシュから作り、更新時には乱数を使うという違いもあります。ES256の署名では、JWSが必要とするP-256の64バイト形式と、長さが変動するDERを区別しなければならず、資料のサンプルを拝借するだけでは正しく動きません。

作者の交換試験では、初回の更新に新しいnonceを要求する応答があり、再試行の処理が必要でした。無効なgrantが証明の問題を隠すため、まず通常の更新を通し、次にDPoPを足して切り分けます。発行時刻の検査は過去3599秒と3600秒、未来10秒と11秒の間に境界を観測しています。同一証明は59分後にも通り、61分後には失敗しましたが、有効なRefresh Tokenなどの条件が必要です。報告はWon’t Fixとなり、他人のアカウントの乗っ取りを示した話ではありません。この実測値を将来も固定の仕様とは扱いません。

採用判断では、鍵を再起動後も使える形で守れるかが残ります。Nodeで非エクスポート鍵をそのまま使う案には永続化の難点があり、作者は暗号化やKMSによる保護を論じています。既存ユーザーの移行や鍵変更には再認可が必要で、鍵のバックアップがトークン利用の継続にも関わります。2万回のループで署名約26.2マイクロ秒、検証約50.5マイクロ秒という数字は同機の局所的な計測です。守る資産、形式、失敗の分類、移行の手間を一緒に説明する価値があり、全サービス共通の安全保証へ広げる記事ではありません。

**読む価値：** 認証の追加機能を、戻り値・署名形式・鍵の寿命まで分解して判断する材料になります。

### 3. 英語論文の PDF をブラウザで「対訳」表示する：pdf.js から段落を復元し、ページ単位でストリーミング翻訳する

**原文：** https://zenn.dev/taiyakujp/articles/caf0eda23633a0

**公開時刻：** 2026-10-21 08:00:06 JST

PDF対訳では、翻訳モデルの前後にも読みにくさの原因があります。Taiyakuの開発者は、pdf.jsが返す位置付きの断片を、まず行、その後に段落へまとめています。近いベースラインと横の隙間を使って行を作り、段落ではフォントサイズの差22%未満、行の横方向の重なり、典型的な行間の1.3倍以内などを組み合わせます。句点の後の余白、字下げ、箇条書きは段落の終わりや始まりを見分ける材料です。幾何的な推定であり、任意の論文に正しい読み順を保証するものではありません。

翻訳を一ページ一ジョブにし、直前のページの末尾も文脈として送ります。SSEで届く訳文を、可視ページを優先するキューで表示し、同時実行は二つです。画面外へ出た未開始の仕事は待機列から外します。Reactは差分ごとに更新せず80msごとにまとめ、ファイルのSHA-256、ページ、訳先、文体を含むキーでIndexedDBへ保存します。拡張機能のバックグラウンドとビューアをポートでつなぎ、切断後は最後のイベントIDから受信を再開する構成です。

訳文を元の場所へ重ねる表示は、段落の範囲をCSS座標へ変換して作ります。キャンバスを最近傍で縮小して色を拾い、背景と文字の中間色が増えないよう平滑化を止めています。useLayoutEffectで実際の高さを測り、はみ出す間は文字を10%ずつ小さくしますが、元の40%を下限に、なお入らなければ枠を下へ伸ばします。切り捨てない設計には意味がありますが、複雑な図表や数式、画像PDFまでの精度は本文で測定されていません。

Safariでの失敗は、作成したジョブが約40msで取り消されるログから追いました。最初の開始メッセージが同じポートへ二度届き、エラーを受けた画面がポートを閉じ、それが取消しにつながっていました。対策は同内容の連続した最初のメッセージだけを無視し、異なる二度目の開始は拒むものです。Safari全般の性質とは広げません。比較ベンチマークや翻訳正答率はなく、抽出・待機列・描画・通信の境界を具体的に説明できる実装経験として読むのが適切です。

**読む価値：** 抽出データ、Reactの更新、拡張機能の通信を一つの読書体験へ結び付けて説明できます。

### 4. モデルを疑う前に評価環境を疑う：LLMコード評価ハーネスの「gold check」

**原文：** https://zenn.dev/koheip/articles/gold-check-eval-env

**公開時刻：** 2026-10-21 04:08:05 JST

モデルのコードをpytestで採点する仕組みを作った作者が、正答率の前に評価環境の異常へ気付いた経験です。参照解を入れても失敗し、原因はテストだけが使うinline-snapshotやdirty-equalsの不足でした。アプリ本体の依存を入れただけでは、テストの収集に必要なものが不足する場合があります。失敗をすべて不正解へ数えると、処理は終わっているのに測りたい能力とは別の理由で点数が下がります。全タスク数や改善した点数は掲載されていません。

対策のgold checkは、モデルを呼ぶ前に正解のパッチを当て、ものさしの目盛りを確かめる手順です。例では元のリポジトリを一時領域へコピーし、評価と同じPythonからpytestを起動します。待ち時間は300秒で打ち切り、パッチ適用失敗、時間切れ、モジュール不足、import失敗、テスト未収集、通常の不合格を分けます。一件でも正常でなければCIを止めます。ただし一時コピーは作業元を守る手段であり、任意のコードを安全に走らせる隔離を証明するものではありません。

pytestの終了コードは0なら成功、1ならテスト失敗、2なら収集などの中断、5なら未収集という手掛かりです。例の分類は出力も調べるため、数字だけで原因を決めません。また、importする名前と配布パッケージ名は同じとは限らず、不足名を見て機械的に同名をインストールする前に照合します。依存は対象のテストに合う版へ固定します。本文のpytest8.3.3などは例示であって、すべての評価課題に指定する版ではありません。

CIで参照解の検査を先に置けば、壊れた前提でモデルを順位付けする事態を止められます。一方、参照解が通るだけでは、網羅性や出題の妥当性、実サービスでの正しさまで分かりません。落ちた課題を無言で取り除けば評価対象も変わってしまいます。面接では、環境の失敗をモデルの失敗へ混ぜない分類と、依存変更時の再確認、どの課題を評価に含めたかの記録まで説明できると、単にテストを増やす話より具体的です。

**読む価値：** 評価器の失敗とモデルの失敗を分け、測定の前提をCIの条件として示す練習になります。

### 5. S3 の Multi-Region Access Points でクロスリージョン参照性能が改善するか試してみた

**原文：** https://dev.classmethod.jp/articles/s3-multi-region-access-points-cross-region-latency/

**公開時刻：** 2026-10-21 06:03:12 JST

バージニアの一つのS3を遠くから読む遅延に対し、作者は東京・オレゴン・フランクフルトへ複製し、四つのバケットをMRAPへまとめました。AWS Global Acceleratorを経由し、遅延を基に近い保存先へ振り分けます。複製は別途S3のルールで行うため、入口を統一しただけで内容がそろうわけではありません。SigV4Aと、MRAP側・バケット側の両方の許可も必要です。Node.js22に同梱のSDKだけでは署名を読み込めず、記事では必要なクライアントとsignature-v4aをアプリへ同梱しています。

比較は四リージョンのNode.js22・512MBのEvent Functionで、128～714バイトのgzipファイル200件を一つずつ読むものです。八巡して各経路1600件を測り、接続の準備は計測外です。CloudFrontは毎巡キャッシュのない状態を作り、Origin Shieldを使いません。東京の直接取得のp50は173.6msから30.0ms、p95は193.3msから35.6msでした。CloudFrontでもp50が492.0msから38.2ms、p95が519.2msから53.0msへ縮んでいます。ただし小さなファイルの逐次取得であり、大容量転送やキャッシュ命中時まで同じ改善を示す比較ではありません。

新しい内容へ変わるまでの時間も別に測っています。同じキーを五回更新し、標準の複製設定で他の三バケットへそろうまで約22秒、東京からMRAPで新内容を読めるまでも約22秒でした。その間は古い内容でもHTTP200になります。状態コードの成功と最新版の到達は別です。CloudFrontではカスタムオリジンとSigV4AのOACを使い、両側のポリシーを対象ディストリビューションに絞っています。MRAP作成後に構成バケットを変えられない制約も、配置を決める際の条件になります。

追加費用は、約1KBの1200ファイルを毎日すべて更新し、日に1万回ダウンロードする想定で約月0.54ドル、主に複製先へのPUTです。古いバージョンを削除する前提で、その保存費は含みません。総費用の実績でも万能な価格でもありません。作者は性能の改善を認めつつ、必要な速さを既に満たすOrigin Shieldを当面続ける判断でした。毎日の複製と管理の複雑化が理由です。更新の待ち時間を許せるか、実際に何を節約したいかまで含める点が、面接で使える判断材料です。

**読む価値：** 速くなった結果と採用判断を分け、整合性や運用の複雑さを同じ条件で説明できます。

### 2. Google OAuthがDPoPに対応したらしいので検証してみたら...なんか違った

**面接質問：**

**関連プロジェクト：** 専用の検証用アカウントで通常更新、証明エラー、再起動後の鍵利用を比べます。実ユーザーの認可や秘密値は使いません。

### 3. 英語論文の PDF をブラウザで「対訳」表示する：pdf.js から段落を復元し、ページ単位でストリーミング翻訳する

**面接質問：**

> PDFの翻訳画面を、待たせず読みやすくするにはどう設計しますか。

**約30秒回答：**

> 文章の復元と表示の待ち時間を分けて考えます。Taiyakuはpdf.jsの断片を座標や行間から段落へ戻し、見えているページから最大二つずつ翻訳します。SSEの差分は80ミリ秒ごとにReactへまとめて反映します。ただし段落判定は幾何的なルールです。二段組みや長い訳文で、読み順と文字の欠落がないかを確かめます。

### 4. モデルを疑う前に評価環境を疑う：LLMコード評価ハーネスの「gold check」

**約30秒回答：**

## 4. 技術テーマ：成功の表示の後に、何をもう一度確かめるか

五つの記事で共通するのは、何を成功と呼べるかを細かくすることです。GPUのログが終わっても終了コードを見ます。OAuthは資料に載っているだけでは対象環境の交換を確かめたことになりません。PDFでは文字を取れたかと読む順、評価では完走と採点の前提、S3ではHTTP200と新内容の到着が別です。大きな一つの成功表示でまとめると、この違いを見落とします。

対策も一様ではありません。カーソルはログの続きを追い、署名形式とnonceの再試行は交換を成立させます。段落の幾何と80msの更新は読書の待ち方を変え、参照パッチは評価器を点検し、複製は読み出す場所を変えます。一般的な監視の話へ薄めず、どの中間状態が最終目的とずれるか、それを何で見分けるかを説明すると設計の理由が伝わります。

確認を分けると原因を追いやすくなりますが、状態と寿命の管理は増えます。提供者の手順、個人の実測、製品実装、評価用スクリプト、小さい対象1600件の比較は証拠の種類が異なり、同じ改善率へはまとめられません。面接では自分の得意分野に合う具体例を選び、学んだ判断と、実際に担当した経験を分けて話せます。

## C-2. IT/AI専門用語

1. **MCP（モデルと道具の接続規約）**：モデルの利用側と道具を提供する側をつなぐ規約。 RuncrateはHTTP接続とOAuthで利用環境を選びます。

2. **DPoP（鍵の保持を示す証明）**：署名した証明で鍵の保持を示し、トークンの利用を送信側へ結び付ける仕組み。 Refresh TokenとAccess Token、Cookieの範囲を分けます。

3. **JWS（JSONの署名形式）**：JSONに関わるデータへ署名を付ける形式。 ES256の64バイト形式とDERを混同しません。

4. **SSE（サーバーからのイベント送信）**：HTTPの接続を使い、サーバーからイベントを順に届ける方式。 訳文の差分を送り、切断後はイベントIDで続きへつなぎます。

5. **IntersectionObserver（要素の可視範囲の監視）**：要素が画面などの範囲へ入ったかを観察するブラウザAPI。 見えているPDFページの翻訳を優先します。

6. **gold check（参照解による評価前検査）**：モデルを採点する前に、参照解が同じテストを通るか確かめること。 環境の異常を分けますが、網羅性の証明ではありません。

7. **MRAP（S3マルチリージョンアクセスポイント）**：複数地域のS3バケットへ一つの入口からアクセスする仕組み。 経路と複製は別で、成功応答でも古い内容を読む場合があります。

8. **SigV4A（複数地域に対応するAWS署名）**：MRAPなどの複数地域にまたがる要求で使うAWSの署名形式。 SDKの署名実装と両側のアクセス許可を確認しています。
