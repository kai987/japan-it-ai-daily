### 1. Claude Code v2.1.289 の主要アップデート - sandbox auto-allow 時の Bash deny ルール修正と agent.spawn の teammate 対応

**原文：** https://dev.classmethod.jp/articles/20261005-cc-updates-v2-1-289/

**公開時刻：** 2026-10-05 17:15:59 JST

対象は10月3日公開のClaude Code v2.1.289で、記事の公開は10月5日です。変更27件の内訳は、新機能1件、セキュリティ修正5件、不具合修正19件、改善2件。不具合のうち15件がmodsとプラグインに関係します。権限面では、sandboxのauto-allowを使うときに、値が展開される環境変数の前置や、先行する単独の変数代入によってBashのdeny／askが効かないケースを修正しています。組織管理設定とユーザーmodの優先関係、MCPサインイン用ツールの説明、シンボリックリンクやIDE経由のRead拒否は、別の修正項目です。

実験は普段の設定を混ぜない構成です。新しい作業ディレクトリで一時設定を--settingsに渡し、--setting-sources projectを指定してユーザー設定を外します。sandboxとauto-allowを有効にし、failIfUnavailableによってsandboxが使えないときの素通りも防ぎます。拒否対象はtouchで、環境変数を前置した操作を実行させました。対照側ではdenyだけを取り外して同じ形の操作を試しており、成功・失敗の違いを拒否規則に結び付けやすくしています。

denyありではpermission_denialsに拒否が残り、対象ファイルは作られませんでした。denyなしでは拒否記録が空で、ファイルが作られています。両方のerror_max_turnsは--max-turns 1による終了で、権限拒否と同じ意味ではありません。ログとファイル状態を合わせるのがこの検証の肝心な点です。ただし、示されたのは一つのコマンド形態であり、すべてのOSやRead経路について同じ実験をしたわけではありません。

modsではteammateの起動直前にもagent.spawnが発火し、e.isTeammateで区別できます。hook間のagent id統一と$.agent.list()のidle／waiting追加は、起動を止めたり状態を観測したりする足場になります。短いコードブロックに含まれる閉じていないscriptタグなどによる表示のフリーズも修正されています。面接で説明するなら、リリース情報にある修正、この記事が再現した操作、自分の組織でさらに確かめる入口を分けると、根拠の範囲が伝わります。

**読む価値：** 設定の存在だけでなく、拒否記録と成果物を対照で確かめる考え方を学べます。

### 2. ECS のタスクをクラウド開発環境として使う

**原文：** https://dev.classmethod.jp/articles/ecs-task-sandbox/

**公開時刻：** 2026-10-05 17:37:33 JST

記事はECSのタスクを動的に作成・削除し、codercom/code-serverとClaude Codeを使える環境を用意した実装記録です。SageMaker Code EditorやCoderを代案として紹介していますが、その作り方は扱っていません。ECSを自作するとIAM系に縛られないユーザー管理やEFS以外の永続化を選べる反面、構築工数、管理する障害点、常駐Proxyの費用が増えます。要件への柔軟さと運用負担は一緒に比較する必要があります。

S3とCloudFrontのWeb UIからAPI Gatewayを呼び、Authorizerで認証します。Lambdaはタスクを起動・停止し、起動が終わるまで待ってENIのIPをDynamoDBへ記録します。別のECSサービスで動くProxyは、認証済みユーザーに紐づくIPを読み、その開発タスクへ振り分けます。code-serverにはWebSocket通信があるため、Proxyにも対応が必要です。開発環境から外へ出る通信はNAT Gatewayを通します。

動作確認では、ログイン後に起動するとリンクが現れ、ALB経由で開発画面に入り、停止後はNo running taskとなりました。これは経路を確かめた結果であり、同時利用や障害復旧の測定ではありません。また、ALBの既定ドメインにはTLS証明書がなく、自前の証明書を端末で信頼する方法は実運用に適さないと記事は述べています。Service Workerを使う拡張も考慮し、独自ドメインを用意する必要があります。

Lambdaの待機をEventBridgeへ置き換える案は、実行時間を抑えるための改善案です。その場合でも画面へ状態を返す仕組みは別に要ります。Fargateはオンデマンドでも保守で停止することがあり、サービス化や最大8時間などの寿命管理が対策として挙げられています。ただし、その寿命や安定性を実測した記事ではありません。導入時には保存先、再起動後の復元、Proxyの障害と常駐費用まで責任範囲に含めます。

**読む価値：** ユーザー認証から自分のタスクへ到達する経路と、自作する場合の運用責任を説明できます。

### 3. ジャンプアカウント運用下でAWS CLI（+ AIエージェント）の認証情報を安全に扱う

**原文：** https://dev.classmethod.jp/articles/aws-vault-mfa-claude-code/

**公開時刻：** 2026-10-05 14:26:34 JST

前提は、ジャンプアカウントから検証用アカウントへスイッチロールする運用と、長期キーの平文保存禁止です。最初に検討した1Password CLIプラグインは手動のaws呼出しには使えましたが、記事のClaude Codeからの呼出しには合いませんでした。aws loginとexport-credentialsはエージェントから使えたものの、期限切れ後の再認証と~/.aws/login/cacheへの保存が課題になりました。これはその環境での選定記録で、各方式の利用を一律に否定する結果ではありません。

採用構成では、aws-vaultがOSの暗号化ストアで長期キーを保管し、1PasswordはMFAコードを発行します。mainにはMFAを設定し、commonのcredential_processがaws-vaultのJSONを受け取り、targetがrole_arnとsource_profileで作業先へ切り替えます。macOSの保存先はKeychainです。目標アカウント側には信頼ポリシーと必要な権限を設定し、MFA条件も必要に応じて付けます。暗号化保管と権限の絞込みは別の仕事です。

get-caller-identityでアカウントとassumed-roleのARNを確認し、同じ端末でAWS_PROFILE=targetを指定してClaude Codeを起動しています。エージェント内部のCLIもこの連鎖を使い、S3の一覧取得を行えたと報告されています。osascriptによる対話入力と--duration=8hは再認証の負担を減らす設定ですが、切替先の一時キーまで8時間有効になるという意味ではありません。期限が来れば再入力を求められることがあります。

特に注意したいのは~/.aws/cli/cacheです。ジャンプ側の長期キーを暗号化していても、スイッチ後の権限を絞った一時情報はCLIのキャッシュに残り、記事では最大1時間とされています。したがって、どの一時情報も平文で保存しないという規則に、そのまま合うとは限りません。面接では保管、供給、ロール権限、寿命、キャッシュを分けて説明し、記事が確認していない実行時の漏えい防止まで保証しないことが大切です。

**読む価値：** 長期キーの保管、MFA、ロール切替、エージェントの子プロセスと一時キャッシュを分けて説明できます。

### 4. [アップデート] Amazon Quick のアプリでデータセットのライブデータが使えるようになったので、Direct Query と SPICE で比べてみた

**原文：** https://dev.classmethod.jp/articles/20261005-amazon-quick-live-data-in-app/

**公開時刻：** 2026-10-05 13:36:02 JST

今回のAppsは、構築時に取った値を固定表示する方式から、Quickのデータセットを実行時に読む仕組みへ進んでいます。記事が引く仕様では、クエリは閲覧者の権限で実行され、RLSとCLSも閲覧者ごとに適用されます。アプリを共有してもデータの権限は付いてきません。検証アカウントはEnterprise、ユーザーはADMIN_PROで、IDリージョンは東京ですが、アプリとデータセットはus-east-1です。東京でApps自体が使えたという記録ではありません。

同じAthenaテーブルからDirect QueryとSPICEを作り、S3のCSV18行を読みました。元の集計は18件、1,312,000。約5分でできた画面にはDirect QueryのKPI・地域棒グラフ・一覧とSPICE側の比較が並び、初期値は一致しました。ただし、通貨情報のないデータに¥が付いており、数値の一致だけでは表示の意味まで正しいといえません。データセットのSQL確認、読み取りアクセスの登録、プレビュー時の連携確認も異なる手順です。

200,000の案件を1行追加して再読込みすると、Direct Queryは19件、1,512,000になり、SPICEは18件、1,312,000のままでした。CreateIngestionの完了後に再び読むとSPICEも更新されます。Athenaには表示のたびに3本のクエリが入り、三つのDirect Queryビジュアルに対応していました。スキャン量も845から934バイトへ増えています。画面の最終更新日は変わらず、アプリ編集日を表すためです。データ鮮度は別の根拠で確かめる必要があります。

単一テーブル、同じアカウントとリージョン、1ビジュアル最大50,000行などの制約があります。東京はAppsの対応リージョンではなく、トピックやダッシュボードをライブデータソースにはできません。仕様上のSPICE等の最大12時間キャッシュについて、記事は取り込み直後の反映だけを確認しています。別ユーザーでRLSを比較した測定もありません。Direct Queryを選ぶなら、閲覧回数とビジュアル数に応じたAthenaの実行・スキャン費用を合わせて判断します。

**読む価値：** 生成された画面を、データの更新、権限、クエリ費用、表示の意味に分けて評価できます。

### 5. Claude Codeの入力欄でMarkdownが読みにくい問題をmd-promptで解決する

**原文：** https://zenn.dev/nogu66/articles/md-prompt-claude-code-markdown-painting

**公開時刻：** 2026-10-05 14:50:11 JST

md-promptは、Claude Codeへ送る前の下書きをMarkdownとして色分けするプラグインです。長い指示ではコードと地の文、見出しや箇条書きが見分けにくいため、入力中に構造を見せます。ただし、記事はAI名義で、入力欄を自分の目で見ていないと明示しています。根拠はコード、README、装飾関数とテストであり、画面の使いやすさを直接観測した記録や作業時間の実測ではありません。

function hooksのprompt.editで編集結果を受け取り、next(e)の戻り値を保持したままdecorationsへ範囲を足します。文字とカーソルは触らず、ほかのプラグインの装飾も通します。記号は消せないため薄く見せる設計です。閉じる前のコードフェンスも対象にし、未知の言語では文字列と数字だけを塗ります。乗算、ワイルドカード、__init__のような記号だけの文には空の装飾配列を返す例があり、Markdownの誤検出を抑えています。

装飾は状態を持たない純関数で、記事は7ファイル374件のテスト成功を報告しています。commonmark.jsとの比較対象は生成したインライン540件と文書500件。端末背景に直接置く色には白背景3.3:1、暗い背景4.3:1以上のテストがあります。ただし、これを全端末・全文字の視認性の保証へ広げることはできません。計算量を下書きの長さに比例させ、60,000文字を超えたら装飾せず、例外時も元の下書きを返します。

4行以上の貼り付けは折り畳まれて編集イベントが出ず、展開後に1文字打つと装飾されるという制約があります。背景は文字の下にしか付かず、右端や空行はそろいません。数式、YAML front matterや特定の注記も対象外です。function hooksはearly accessで、リリース間のAPI変更に注意が要ります。記事の導入説明では2.1.287以降は追加設定不要、2.1.285／286は有効化が必要で、READMEの確認版は2.1.285です。テストを通したことと実画面を確かめたことを分けるのが、フロントエンドの実践知になります。

**読む価値：** 純関数による装飾、入力を変えない境界、誤認識と性能の制約を、画面観察と分けて説明できます。

## 4. 技術テーマ：操作の終了から、状態を確かめられる検証へ

検証では、意図、操作の記録、実際の状態を分けます。Claude Codeの終了理由だけでは拒否もファイルの有無も分からず、ECSの起動だけではユーザーのIPやWebSocket経路は確かめられません。Quickも生成後のデータ更新が別にあり、md-promptは送信する文字を保ちながら装飾だけを変えます。この整理は5本から導く設計上の解釈で、各製品が同じ実装を持つという意味ではありません。成功の表示は、その境界で得た一つの根拠として扱います。

利点は、どこまで確認したかを具体的に残せることです。権限は対照操作、身元はアカウントとロール、鮮度は既知の追加行とクエリ履歴、装飾は純関数の計算と端末上の表示で確かめます。入力と検証結果を保持すれば、失敗後も完了した箇所から再開できます。ただし、少数の例で測ったことを、全操作の安全性や可用性へ一般化しない姿勢も必要です。

日本のチームで試す際は、ECSの常駐費用・保守停止、認証キーのキャッシュ規則、Quickのデータ所在と対応リージョン、early accessのhook変更を確認します。実際の利用者と入力方法で検証条件を決め、別ユーザーの権限や停止後の復元を当事者の環境で試します。記事には日本企業での普及率や採用規模の統計がないため、これは導入の検討点であり、普及の事実としては書きません。

## C-2. IT/AI専門用語

1. **autoAllowBashIfSandboxed（sandbox内の自動許可）**：sandbox内でBashを自動許可する設定。 明示的なdenyが効くかは別に検証します。

2. **permission_denials（権限拒否の記録）**：規則で拒否されたツール要求を示す記録。 max-turnsによる終了理由と区別します。

3. **ENI（ネットワークインターフェース）**：AWSリソースが使うネットワークの接続口。 起動したタスクのIPをDynamoDBへ記録します。

4. **credential_process（外部認証情報の供給処理）**：CLIが外部コマンドから認証JSONを受け取る仕組み。 aws-vaultとcommonプロファイルをつなぎます。

5. **Direct Query / SPICE（直接参照／取り込み型データ）**：ソースへ問合せる方式と、取り込んだデータを読む方式。 1行追加と取り込み更新後の反映を比べます。

6. **RLS / CLS（行・列単位のアクセス制御）**：利用者ごとに見られる行や列を制限する仕組み。 閲覧者に適用する仕様で、多ユーザーの対照実験とは別です。

7. **prompt.edit / decorations（編集イベント／装飾範囲）**：編集後の入力を受け、表示範囲を付け加える仕組み。 md-promptは文字・カーソル・既存の装飾を保ちます。

8. **commonmark.js（Markdown参照実装）**：Markdownの走査結果を比較する参照実装。 生成ケースの比較は全端末の画面確認とは違います。
