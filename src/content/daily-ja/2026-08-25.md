## 1. 今日読むべき5本

### ① GitHub Copilot Cloud Agent × Microsoft Teams

**出典：CodeZine**

**原文：** https://codezine.jp/news/detail/29421

CodeZineは、**GitHub Copilot cloud agentとMicrosoft Teams** の連携が8月21日にPublic Previewになったと紹介しています。チャネル、スレッド、DMで `@GitHub` を呼び、会話の参加者が背景や質問を追加して共同で方向を決めます。会議の決定事項を後で転記するのではなく、議論中に調査へ渡せるのが狙いです。

ただし会話参加とコード変更の権限は別です。参加者は相談や計画に加われますが、変更を実行させるには対象リポジトリの書き込み権限が必要です。処理はクラウドサンドボックスで非同期に進み、スレッドで進捗を追い、成果物をターミナル、IDE、Copilotアプリへ持ち越せます。画面を閉じることと処理の終了を同一視しません。

有料Copilotプランが必要で、セッションはAIクレジットを消費します。公式はサンドボックス利用が別課金で、管理者によるcloud agent・sandboxの有効化も必要と説明しています。GitHubアプリの導入とアカウント接続、必要に応じた既定リポジトリの設定が接続の前提です。

CodeZineは追加承認を必須と表現しますが、公式では **管理者が追加承認を要求する設定を有効にできる** という説明です。有効なら通常二承認のリポジトリで三承認が必要になる例が示されます。すべての導入で自動的に増えるとは断定しません。これは機能発表で、生産性や品質の比較実験ではありません。

補足確認：[GitHubの公式発表](https://github.blog/changelog/2026-08-21-shared-agentic-work-with-github-copilot-in-microsoft-teams/)。面接では会話、変更実行、マージ承認、課金を別の責任として設計できます。

**注目ポイント：★★★★★**

共同会話と変更権限、マージ条件を切り分けられます。

### ② Liquid AI DSpark：Speculative Decoding

**出典：CodeZine**

**原文：** https://codezine.jp/news/detail/29423

Liquid AIの **DSpark** は、LFM2.5-1.2B-Instruct、2.6B、8B-A1B向けの約3億パラメータのドラフトモデルです。軽いモデルが候補を出し、対象モデルがまとめて検証することで、デコード時に重みを読む費用を複数トークンで共有します。対象より小さいモデルへ最終回答を置き換える方式ではありません。

一次発表では、対象の特徴で条件付けした並列backbone、隣接トークンの依存を入れる **Markov head**、採択見込みの低い末尾を省くconfidence verifierを説明します。初版は5層のattention-only、block size9で、15epochの中から損失最小ではなく採択率最大を選びました。greedyでは対象が認めない候補を対象自身のトークンに戻すため、同じgreedy出力を保つという条件付きの品質説明です。

測定はbatch size1、temperature0、五データセット。GPUはH100 80GB・BF16・SGLang、端末はM4 Max・FP16 GGUF・llama.cpp/Metal・出力最大256トークンです。最大 **3.18倍** は8B-A1BのH100/MATH500、端末最大 **2.87倍** は1.2B/HumanEvalで、別条件です。2.6Bの平均はGPU2.67倍、端末2.27倍で、関数呼び出し遅延57%減も同モデルの提供者評価です。

8B-A1Bは採択率が高くても、端末平均は1.18倍にとどまります。複数候補の検証でより多くのexpertと重み転送が必要になり、当時のMetal MoE実装が影響すると説明されています。ドラフトの追加メモリも必要で、全端末・全入力に最大倍率は適用できません。

safetensorsとGGUFが公開されていますが、利用にはLFM2対応DSparkを含むSGLang/llama.cppビルドが必要です。配布初日対応を、任意の既存インストールでそのまま動くと読み替えません。面接では採択率、追加メモリ、greedy一致、実際の関数呼び出し時間を別々に確認する考え方が使えます。

実験条件：[Liquid AIの一次発表](https://huggingface.co/blog/LiquidAI/lfm25-dspark)。

**注目ポイント：★★★★★**

投機的デコードの品質条件と、機器ごとの速度差を具体的に説明できます。

### ③ AWS DevOps Agent × GitHub MCP：障害調査後はIssue作成だけを許可

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/aws-devops-agent-github-issue/

AWS DevOps Agentの検証記事は、障害を調査して **GitHub Issueだけを起票** する構成です。記事時点のネイティブGitHub接続は読み取り14ツールなので、公式remote MCPを別に接続します。公開ツール一覧から `issue_write`、`list_issues`、`search_issues` を選び、コード生成を始めるassign_copilot_to_issueやPR作成は渡しません。推測したcreate_issueという名前では動かない点も確認しています。

二つの権限層が必要です。DevOps AgentのAssociationでツールを渡しても、GitHub Appに **Issues: Read and write** がなければ403で拒否されます。著者はAppの権限を追加し、インストール側で承認して解消しました。OAuth 3LOの起票者はBotではなくユーザーで、使用Appは `performed_via_github_app` に残ります。自動起票の追跡をuser.typeだけで行わない点が重要です。

故障はCDKの `topic.grantPublish()` を省き、LambdaからSNSへの三回の送信をAuthorizationErrorExceptionで失敗させます。チャット経路は約3分で、ログ、二つのコード位置、修正方針を持つIssueを作りました。調査経路は六つの担当によるMetrics、CloudTrail、IAM等の照合に約9分使い、既存Issueがあれば再起票しませんでした。別の10秒処理・3秒timeoutの障害は約5分半で新規起票し、重複あり・なしの両分岐を確認しています。時間はこの検証の観測値です。

ランブックは、原因特定後の重複検索、根拠ログ・コード・修正案・確認範囲を含む起票、番号とURLの報告を定めます。Agent Spaceの許可リストが実行可能範囲を制限し、手順文書がその中での動きを整理します。ジャーナルではissue_write以外のブランチ・ファイル変更呼び出しがないことも確認しました。

ただし調査の自己説明には誤りがありました。起票403をツールのREAD_ONLY分類と説明しましたが、実際はGitHub App権限不足です。別の取得失敗もSCP拒否としましたが、CloudTrailはlambda:GetFunction等のidentity policy不足を示し、ログ検索失敗は保持期間外のクエリでした。原因特定が正しくても、途中の説明や提示JSONまで正しいとは限りません。

CDK自動命名のロググループでは28分経っても完了せず、`/aws/lambda/<関数名>` へ揃えると探索を省いて約3分で進みました。変更できない命名規約はスキルへ伝える案も示します。これは少数の意図的な障害での試験であり、あらゆる障害の調査・起票品質を保証しません。面接では権限の両側と、生のAPIエラーによる根拠確認を説明できます。

**注目ポイント：★★★★★**

許可リストと接続先の権限、自己診断と実エラーを分けて調査できます。

### ④ Claude Code Supervisor：SessionとCLI Processを分離

**出典：Zenn**

**原文：** https://zenn.dev/uehaj/articles/claude-code-supervisor-agent-view

Zennの解説は、Claude Codeの **supervisorデーモンとAgent view** を、端末・セッション・プロセスの三つに分けて説明します。通常のフォアグラウンドを閉じる場合は履歴からresumeする扱いですが、`/bg` や `claude --bg` で預けたセッションは `claude daemon run` の管理下で端末から独立します。すべてのCLI作業が閉じるだけで継続するわけではありません。

デーモンはユーザー単位でオンデマンドに起動し、**`roster.json`** がsessionId、pid、接続ソケット等を別々に記録します。Agent viewからattachやpeek、停止を行えます。完了状態とプロセスの生死は別で、プロセスを回収してもtranscriptから起動できます。記事の「スリープや更新をまたぐ」は継続・復元の設計であり、PCが眠っている間もCPU処理が進むという意味ではありません。

空の入力欄で左矢印を押すと、単なる一覧への移動ではなく現在セッションのバックグラウンド化になる場合があります。著者はv2.1.223で `leftArrowOpensAgents: false` を確認しています。`/bg` は自分ごと移し、`/fork` はコピーを並走させて元へ残り、`/branch` はコピー側へ移って一本で続ける違いがあります。内側のBashやサブエージェントをbackgroundにすることとも別です。

独立セッションの成果は親へ自動統合されません。Gitでは書き込み時のworktree分離とブランチ・PRで回収できますが、非Gitの同じ作業場所は分離されません。未回収の変更や未pushコミットのあるworktreeを清掃から保護する説明もあり、保存状態を確認して回収する責任が残ります。セッション間通信は宛先発見と送受信で、Agent Teamsの共有タスク管理やDynamic Workflowsの決定論的制御そのものを提供しません。

著者はdaemon status、ログ、台帳で、予備workerの補充、オンデマンド起動、更新時の再起動を観察しました。環境変数はデーモン起動時の土台と、dispatch時に更新するPATH・プロバイダー選択等の二層です。古いHTTP_PROXY等を保持すると、新端末は通信できてもbackgroundだけ失敗する場合があります。設定変更時はどの実行体が値を保持するかを確認します。

`/goal`、`/loop`、Stop hookは次ターンや停止条件、background sessionは端末との切り離し、Routinesはクラウド側実行という別軸です。これは特定版の文書と著者環境の観察で、全OSや将来版の同一挙動の保証ではありません。面接では、永続データと実行プロセスの寿命、作業場所の隔離、成果回収を分けて説明できます。

**注目ポイント：★★★★★**

端末からの切断、プロセス終了、会話の永続化を区別できます。

### ⑤ 建設業界でAI活用が深化：ボトルネックは人材・Expert・ROIへ

**出典：＠IT**

**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2608/25/news041.html

建築AI経営研究会の調査を紹介する＠IT記事では、部署以上の利用を示す **Level2以上が43.4%→61.3%→68.5%** と、3月、6月、8月に増えています。独自AIを構築・運用するLevel4は3.8%から9.3%、平均レベルは1.57、1.84、2.02です。ただし回答数は53人、31人、54人と異なり、同じ企業を追ったパネルだとは原文から確認できません。業界全体の導入率と断定しません。

会社負担のClaude有料導入は18.9%から71.0%、70.4%へ上がり、8月はClaude Code57.4%、NotebookLM53.7%、Codex25.9%です。これは有料導入の回答で、日常使用頻度や各製品による業績改善率ではありません。Level4の「自社データを学習」という分類も、全回答企業が同じfine-tuning構成を使うことを示していません。

課題は「何から始めるか」が50.9%から31.5%へ減る一方、人材不足は7.5%から20.4%、専門家・パートナー不足は11.3%から27.8%へ増えました。導入後の組織内支援が論点ですが、同じ標本での因果実験ではないため、ツール導入が不足を直接生んだとまでは言えません。

業績を変えたとする実感は9.4%→19.4%→25.9%。時間・工数の数字で効果を把握する回答は15.1%から24.1%、効果がまだなく把握できない回答は47.2%から20.4%です。数値で測っている割合と、利益としてのROIが確定した割合を混同しません。開発モニターへの前向きな87.0%も、29.6%の参加希望と57.4%の内容次第という意向の合計です。

面接では、導入レベルが変わると課題の優先順位も変わり得る点を説明できます。見積もりや設計など対象業務を定め、担当者育成、相談経路、時間短縮や手戻りを測る方法をセットにします。少数の経営者調査の傾向を、自社へそのまま移すことはできません。

**注目ポイント：★★★★★**

導入率、利用段階、業績実感、効果の計測を分けて読みます。

# B. 重要ポイントと面接で使える知識

## 1. GitHub Copilot Cloud Agent × Microsoft Teams

1. 会話参加者全員がコード変更を実行できるわけではありません。
2. sandboxの費用はAIクレジットとは別です。
3. 追加承認は管理者設定が条件です。

## 2. Liquid AI DSpark：Speculative Decoding

## C-3. JLPT文法

### 1. ～つつ
**Level：N1｜意味：** ある動作や状態と並行して別のことを行う。  
**形：** `動詞ます形から「ます」を取る + つつ`  
**使い方：** 自動化を進めながら必要な監督を残すことを述べます。

**補足：** 自動化を進めながら必要な監督を残すことを述べます。

### 2. ～に伴って
**Level：N1｜意味：** ある変化と一緒に別の変化が起こる。  
**形：** `名詞 + に伴って`  
**使い方：** AI利用の拡大と管理上の課題の関係を説明します。

**補足：** AI利用の拡大と管理上の課題の関係を説明します。

### 3. ～にとどまらず
**Level：N1｜意味：** ある範囲だけでなく、さらに広い範囲にも及ぶこと。  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 前の範囲から後ろへ話題を広げます。  
**例：** `AI ROIはModel Costにとどまらず、工数削減や障害復旧時間まで評価します。`  
**補足：** 前の範囲から後ろへ話題を広げます。

### 4. ～に応じて
**Level：N2｜意味：** 条件や変化に合わせて、対応を変えること。  
**形：** `名詞 + に応じて`  
**使い方：** 名詞に接続し、条件と対応の関係を示します。  
**例：** `Taskの専門性に応じて担当Agentを割り当てます。`  
**補足：** 名詞に接続し、条件と対応の関係を示します。

### 5. ～た上で
**Level：N2｜意味：** 先の行為を済ませ、それを前提として次を行う。  
**形：** `動詞た形 + 上で`  
**使い方：** 検証してから利用するという手順を述べます。  
**例：** `Riskと権限を確認した上で、自動復旧を許可します。`  
**補足：** 検証してから利用するという手順を述べます。

### 6. ～一方で
**Level：N2｜意味：** 同じ事柄の、対照的な二つの側面を述べること。  
**形：** `普通形 + 一方で`  
**使い方：** 前後は逆の評価や異なる側面でもつなげられます。  
**例：** `AIOpsは復旧を高速化できる一方で、誤操作Riskもあります。`  
**補足：** 前後は逆の評価や異なる側面でもつなげられます。

### 7. ～にかかわらず
**Level：N2｜意味：** ある条件が違っても、同じことが成り立つこと。  
**形：** `名詞 + にかかわらず`  
**使い方：** 後ろには条件に左右されない行動や規則を置きます。  
**例：** `Taskの長さにかかわらず、Agentの実行履歴を保存します。`  
**補足：** 後ろには条件に左右されない行動や規則を置きます。
