### ① DevinCon2026登壇報告 WINTICKETにおけるアラート対応自動化

**出典：CyberAgent Developers Blog｜2026年9月11日**  
**原文 URL：** https://developers.cyberagent.co.jp/blog/archives/65832/

WINTICKETでは2025年2月からDevinを利用し、記事公開時点までに **17,000件超のSession** が実行され、約1,800件がPRを作成、1,100件以上が実際にMergeされています。2025年12月～2026年1月に作られた36件の仕様書のうち33件、つまり92%もDevinとの共同作成でした。その延長でSRE領域へ導入した`Devin Auto-Triage`は、SlackのAlert Channelを常時監視し、PlaybookとSession間で共有するPersistent Memoryを使ってP1～P4に分類します。P1/P2ではHumanへMentionしてRoot Cause調査、P4は記録して終了、P3で改善可能なら修正PRまで作成します。Kubernetes PodのMemory使用量AlertではResource Limitの設定漏れを見つけ、土曜日の発生から約 **3分**でP3判定・Mention・修正PR提出まで進んだ事例が紹介されています。

一方、数か月運用したからこそ限界も具体的です。対応不要のAlertまで緊急と判定するFalse Positive、本番DBや`kubectl`を使えないContext制限、設計判断を伴うCode FixでのHarness不足、人間のPR Review内容がPersistent Memoryへ戻らない点が残っています。さらにDevin botのPRをSelf Mergeさせると事故時の「責任の所在」が曖昧になるため、LabelをTriggerに対象GitHub TeamからHuman Reviewerを割り当てています。Google SREのAutonomy Modelに当てはめると現状は **Level 1 Assisted** で、Monitor / Investigateは自動、Mitigate / ActuateはHumanです。

**Evidence Boundary：** ただし、3分の対応や17,000 SessionはWINTICKET固有のProduction Caseであり、一般的なSRE Agent性能Benchmarkではありません。Agent自身へのSLO、Error Budget、Circuit Breaker、Kill Switchは今後の展望として述べられており、全てが既に本番導入済みという意味でもありません。

**注目ポイント：★★★★★**  
「Agentを入れるか」ではなく、**Autonomy LevelごとにContext、Permission、Human Gate、Accountabilityを設計する**という面接回答へ発展させられます。

### ② GPT‑LiveをCodexで最速検証。iOSデモを数時間で作ってみた。

**出典：CyberAgent Developers Blog｜2026年9月11日**  
**原文 URL：** https://developers.cyberagent.co.jp/blog/archives/65204/

GPT-Liveは入力と出力を同時に扱う **full-duplex** Voice Modelで、Realtime APIはApplicationとModelの間でStateful Sessionを維持します。Mobile / BrowserはWebRTC、Server-side AudioはWebSocket、PhoneはSIPを用途に応じて使い分けます。Session中はAudio、Event、Instruction、Conversation Stateが双方向に流れ、UserのBarge-inやPauseを含む会話を一問一答ではなく継続したInteractionとして扱えます。Function CallingではModelからFunction NameとJSON Argsを受け取り、Application側が検証してから処理を実行します。著者はCodexを使い、要件定義とReviewを自分で行いながら、設計・実装・Debug・実機確認を進め、数時間でSwiftUI Prototypeを作りました。

安全性の設計が特に実践的です。標準API KeyはBackendに置き、iOSへは短命Client Credentialだけを渡します。Modelが返すのも「保存済みTask」ではなくTask Candidateで、ApplicationがArgsを検証し、重複を除外してConfirmation Queueへ入れ、**Userが承認したCandidateだけLocal Stateへ保存**します。50.7秒のDemoでは最初の発話から5件の買い物Candidateが生成され、その後の相談で実際に決めた「いちごを買う」だけが新規Candidateになりました。記事には24kHz PCM入力やQueue処理のSwift例もあり、仕様紹介だけではなくAuthor Experimentとして確認できます。

**Evidence Boundary：** ただし、数時間のPrototypeなので、本番品質のReliability評価ではありません。公開AppにはReconnect、Timeout、Interruption時のPlayback停止、Error Recovery、Credential Lifecycleが必要だと著者自身が明記しています。実機Demoで自然に割り込めたことを、多様なNetwork / Device条件へ一般化することはできません。

**注目ポイント：★★★★★**  
Voice Agentを作るとき、**Conversation ContextはModelへ任せても、Committed Application StateはValidationとHuman Confirmationを通す**という設計原則を学べます。

### ③ DeNA の大規模環境を MySQL 8.4 に移行する時に考えたこと[DeNA インフラ SRE]

**出典：DeNA Engineering｜2026年9月10日**  
**原文 URL：** https://engineering.dena.com/blog/2026/09/mysql84-migrate-research/

DeNAは15年以上にわたり大規模MySQLを運用してきましたが、長年HAに利用してきたMHAがMySQL 8.4以降に対応していません。さらにMySQL 8.0は2026年4月にEoLを迎えたため、Infrastructure側として8.4以降の方針を決める必要がありました。比較軸は「開発組織やSoftware Behaviorを含む信頼性・透明性」「System Complexityを不必要に増やさない」「既存の大規模環境を現実的に移行できる」の3点。MHA継続Maintenance、Orchestrator、Vitess、TiDB、Group Replication、Amazon Aurora / Google Cloud SQLを候補として比較しています。

Trade-offが具体的です。Vitessは実績がありCNCF Graduated Projectですが、HAだけを目的にVTGate / VTTabletを増やすとHop、Latency、運用対象が増えます。TiDBはMySQL Compatibilityが高い一方、既存ApplicationがSharding Logicを持つ今回のCaseでは変更が大きい。MySQL公式PluginのGroup ReplicationはMember Monitoring、自動Failover、Clone + binlog Recoveryを備え、Multi-primaryにも可能性がありますが、大規模運用の公開事例はまだ十分多いとは言えません。最終的には既にProduction Experienceがあり、構築・運用Costが低く、Distributed SQLほど変更量が大きくないAurora / Cloud SQL等のManaged Serviceを選択しました。

**Evidence Boundary：** ただし、調査自体は **2025年前半** に行われ、記事公開時点で1年以上経っているため、著者も最新状況を完全には反映しない可能性を明記しています。また多くの候補を本格導入まで検証した比較Experimentではありません。これはDeNA IT基盤部第二Groupの既存大規模MySQLに対するDecision Recordです。

**注目ポイント：★★★★★**  
SRE面接で「最新技術を選ぶ」のではなく、**Reliability、Operational Complexity、Migration Feasibility、Existing Experience、Cost、Portability**を比較してDecisionを説明する材料になります。

### ④ 従来の「AI－Readyデータ」だけでなく新たなアプローチを理解せよ：Gartner Insights Pickup（463）

**出典：＠IT｜2026年9月11日 05:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/11/news006.html

GartnerはDataとAIの関係を2つのAdoption Patternとして整理しています。1つ目は従来の **Project-led AI** で、Owner、Budget、Scope、Use Caseを定義した後、その目的へ適合するDataを準備・検証する「Data for AI」です。通常のAI-Ready Dataはこの文脈に属します。2つ目は **AI for Data** で、AIがData Platform、Tool、WorkflowのFeatureとして直接入り、正式なAI Projectや完全なRequirementが存在する前から、Data EngineerがExploration、Explanation、Pattern Suggestionに使う形です。

この2つは成熟度の前後ではありません。AI for DataではDocumentationが不完全、Requirementが流動的、Data Environmentの全体像が分からない状態でも作業を前へ進められる一方、Governance、Ownership、RiskがTool利用開始後に浮上しやすくなります。したがって「AIを使う前に全DataをAI-Readyにする」という単一Processだけでは、既に日常ToolへEmbedded AIが入る現実を管理できません。Project型とFeature型で、Inventory、Permission、Usage Logging、Ownerの置き方を分ける必要があります。

**Evidence Boundary：** ただし、これはGartnerが2026年6月に執筆し、＠ITが翻訳・紹介したAnalytical Frameworkです。AccuracyやROIを測ったControlled Benchmarkではないため、「AI for Dataの方が高生産性」といった定量結論には使えません。自社でTool Inventoryと利用実態を確認して初めてGovernance Designにつながります。

**注目ポイント：★★★★★**  
「AI-Ready Dataが必要」という正しいが単純な回答から一歩進み、**Data for AIとAI for Dataは別のAdoption PatternでGovernance入口も異なる**と説明できます。

### ⑤ 〖小ネタ〗Amazon QuickのAI推論はApp Storageのデータ分析は可能でダッシュボード分析は出来ませんでした

**出典：DevelopersIO｜2026年9月11日**  
**原文 URL：** https://dev.classmethod.jp/articles/amazon-quick-apps-ai-inference-dashboard/

著者がAmazon Quick AppへAI Inferenceを組み込んだHands-onでは、自由形式TextのSummaryに加え、ClassificationやJSON ExtractionなどStructured Outputも利用できました。しかし、AppにEmbedded Dashboardを表示した状態で「DashboardのScoreをAIで分析して傾向と対応案を出す」と依頼しても、AIは内部数値を直接取得できませんでした。ポイントはModel能力ではなく **Data Path** です。Embedded VisualはSandbox化されたiframeで表示され、App Codeが中のDatasetを自由に読み取れる構造ではありません。外部SystemとのCommunicationもBridge APIやAction Connector等の許可された経路に制約されます。

一方、実機でAI Inferenceへ渡せたのは、Viewerが手入力したScoreと **App Storage** に保存した対応MemoのTextでした。そのため「Scoreを手入力→App StorageのContextと合わせてAIが対応Memoの下書きを作る」は可能ですが、「画面に表示されているDashboardだからAIも読める」は成立しません。Cross-dataset Analysisをしたいなら、表示Layerとは別にModelへDataを届けるIntegrationを設計する必要があります。

**Evidence Boundary：** ただし、これは1つのApp構成に対するAuthor Hands-onです。AWS DocumentationはSandbox / Communicationの制約を説明していますが、「あらゆるEmbedded Dashboard Dataが将来もAI Inferenceから読めない」と断定する仕様書ではありません。現行挙動として扱い、Product Update時には再検証すべきです。

**注目ポイント：★★★★★**  
AI Applicationでは、**Visible UIとMachine-readable Dataを同一視しない**ことが重要です。Source → Storage / Connector → App → ModelのData Flowを先に設計する習慣につながります。

## 4. 今日の技術テーマ

# Autonomy Budget：AIの自律性をEvidence・Permission・Responsibilityで配分する

本日の5本は、次の共通Architectureで捉えられます。

```text
Context / Data
      ↓
AI Reasoning
      ↓
Capability Boundary
├─ Read Scope
├─ Write Scope
├─ Decision Scope
└─ Approval Scope
      ↓
Evidence / Observability
      ↓
Human or Policy Gate
      ↓
Committed State
```

WINTICKETではMonitor / Investigateを自動化しつつMitigate / ActuateをHumanへ残しています。GPT-Liveでは自然な会話を止めずにCandidateを作っても、保存直前にConfirmation Queueを通します。DeNAのDB選定も、Featureの多さではなく運用責任とMigration Riskを含むBoundary Decisionです。GartnerのAI for Dataは、正式Projectより前にCapabilityが現場へ入り込むためGovernanceの後追いが起きやすい。Amazon QuickではUI表示とData AccessのBoundaryが技術的に分離されています。

**メリット**は、Automationを一気に100%へ進めず、EvidenceとGuardrailが成熟した範囲からAutonomyを広げられることです。ModelやToolを交換しても、Read / Write / ApprovalのPolicyは再利用できます。

**制約**はBoundary設計そのものも間違える点です。Permissionが狭すぎれば調査不能、広すぎればBlast Radiusが増えます。False Positiveが多いAgentへ強いAction権限を与えると、人がAlertを無視するAutomation Fatigueにもつながり得ます。Data Pathを誤認すれば、UIには表示されているのにModelはDataを取得できません。

**国内企業導入時の注意点**として、各Agentに`Read Scope / Write Scope / Decision Scope / Evidence / Human Owner / Kill Switch`を持たせると運用しやすくなります。低いAutonomy LevelでSLOとReview結果が安定してから次の権限へ進めることが、単純な「完全自動化」より説明可能性と責任分担に優れます。

# B. 重要ポイントと面接で使える知識

## 1. WINTICKET SRE Agent
`Devin Auto-Triage`はSlack Alert、P1～P4 Playbook、Persistent Memory、PR作成を一つのLoopへつないでいます。3分でPRまで進んだCaseがある一方、False Positive、本番DB / kubectlを使えないContext、Human Review Feedbackの未統合が残ります。Self Mergeを禁止してHuman Reviewerを割り当てることが、AutonomyとAccountabilityのバランスです。

## 2. GPT-Live
Realtime APIはStateful full-duplex Sessionを維持し、Function CallingでStructured Actionを生成できます。ただしAction CandidateはApp側で検証し、Confirmation Queueを経てからCommitします。Standard API KeyをClientへ埋め込まず、短命Credentialを使う点もProduction Designの基本です。

## 3. DeNA MySQL 8.4
MHA非対応をきっかけに、Orchestrator、Vitess、TiDB、Group Replication、Managed Serviceを比較しています。最終選択は「一番新しい技術」ではなく、既存実績、変更量、運用Cost、Migration Feasibilityのバランスでした。調査時点が2025年前半であることもEvidence Boundaryです。

## 4. AI-Ready Data
Project-led AIではAI-Ready Dataが必要です。一方、AI for Dataは正式Use Caseが固まる前からData WorkflowへAIが入り、曖昧なRequirementでExplorationを支援します。後者ではGovernanceとOwnershipが後追いになりやすいため、Shadow AdoptionをInventoryする視点が必要です。

## 5. Amazon Quick
Embedded Dashboardを表示できても、AI Inferenceがその内部Dataを読めるとは限りません。Hands-onではManual ValueとApp Storage Textは渡せました。AI ApplicationではUI Layer、Storage、Connector、ModelのData Pathを分けて設計する必要があります。

## C-3. JLPT文法（7）

1. **～にとどまらず｜N1**：ある範囲だけでなくさらに広がる。例：`DevinはAlert分類にとどまらず、条件次第で修正PRまで作成します。`
2. **～を余儀なくされる｜N1**：External Constraintでやむを得ず行う。例：`MHAが8.4に対応しないため、HA方式の再検討を余儀なくされました。`
3. **～に応じて｜N2**：条件に合わせて変える。例：`AlertのPriorityに応じてEscalationを変えます。`
4. **～たうえで｜N2**：前の行為を完了して次へ進む。例：`互換性を確認したうえで、移行先を決めます。`
5. **～一方で｜N2**：別の側面・Trade-offを示す。例：`Agentは24時間調査できる一方で、誤判定も残ります。`
6. **～とは限らない｜N2**：常にそうとは言えない。例：`Dashboardが表示されても、AIが数値を読めるとは限りません。`
7. **～かねない｜N1**：望ましくない結果になる可能性。例：`Governanceを後回しにすると、利用実態を把握できなくなりかねません。`
