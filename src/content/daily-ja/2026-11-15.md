### 1. Undoした「水曜は出社」が、共有予定に残る理由

**原文：** https://zenn.dev/honabochi/articles/family-newspaper-shared-week-undo

**公開日時：** 2026-11-15 09:45:32 JST

家族新聞は日ごとの号と、次の号に引き継ぐ共有予定を持っています。新しい号には共有の週表をコピーしますが、号から週間予定を保存すると、共有側にも書き戻されます。例では月曜号から水曜の勤務が変わり、その後の火曜号で木曜の休みを追加して共有予定を採用しました。

月曜号の Undo は、まずその号の保存前の版を復元します。共有側を戻す条件は、現在の週表と採用フラグが、取り消す保存の直後を表す sharedAfter と両方一致することです。火曜号が作った C は月曜の B と異なります。週表を見るだけで、後から採用されたかどうかまで分かるとは限りません。採用状態だけが変わった場合にも共有側は残ります。

勤務欄二つに絞った公開モデルでの説明で、月曜号に別の保存を挟まない条件です。水曜だけを共有側から取り除けば、火曜に採用したことのない週表ができます。共有側の結果も通知する案と、新しい週表を見せて採用し直す案は未実装です。

**読む価値：** 後の操作を残す条件を、実際に比較する二つの値から説明できます。

### 2. 429 を受けてからでは遅い — 外部プロバイダへの送信レート制御を再試行の増幅率で比較する

**原文：** https://zenn.dev/kyrenzk/articles/messaging-send-rate-control-design

**公開日時：** 2026-11-15 08:57:42 JST

毎秒百リクエストの固定ウィンドウを持つプロバイダをモデル化し、五十の Worker で千件を送り切る実験です。Go の仮想時間で、十ミリ秒ごとの再試行、指数バックオフに Full Jitter を加えた方式、Retry-After、全 Worker で共有するトークンバケットを比べています。

固定間隔では一件当たりの要求が45.95回になりました。Retry-After のみなら1.45回で9秒、毎秒90件を通す共有トークンバケットでは一回となり、完了は11.06秒でした。増幅率はプロバイダへの全リクエスト数を送信件数で割った値です。

同じ乱数シードで結果は再現しています。ただし、これは Go 1.24.7 の固定ウィンドウ実験で、共有バケットの burst も5だけです。別の制限方式や複数プロセスの合算、実際のサービスでの遅延や料金は検証していません。

**読む価値：** 再試行の多さと配信完了までの時間を、同じ負荷条件で見比べられます。

### 3. TypeScriptのnoUncheckedIndexedAccessで配列・辞書のundefined事故を防ぐ

**原文：** https://zenn.dev/sponge841841/articles/2026-11-06-typescript-no-unchecked-indexed-access

**公開日時：** 2026-11-15 09:01:51 JST

未登録の商品コードを Record<string, number> で引いても、通常の strict 設定では number と扱われる例があります。実際には undefined が返るため、そのまま toFixed を呼べば例外になります。筆者は TypeScript 5.8.3 と Node.js 22.16.0 でサンプルを確かめています。

noUncheckedIndexedAccess を追加すると、任意キーで読み出した値に undefined が加わります。商品が見つからない場合を先に分ければ、在庫ゼロはそのまま数として扱えます。添字が不要な配列なら for...of を使い、必要な箇所では取り出した値を個別に確認します。

型に存在が明記された apiUrl には同じ変化は起きません。ただし、型検査だけでは実行時の入力や在庫の同時更新までは守れません。単一プロセスの例から本番の購入処理に進む場合は、別途データの検証と更新の条件が必要です。

**読む価値：** 値が見つからない場合の扱いを、型検査からAPIの応答まで考えられます。

### 4. 欠けている値は「捨てる」か「埋める」か：小さい町村だけ値がない持ち家率で、扱い方を比べたときに何を決めて何を確かめたか

**原文：** https://zenn.dev/takayuki0127/articles/7ee036279243fc

**公開日時：** 2026-11-15 07:31:56 JST

市区町村の持ち家率は、集計した千七百三十四自治体のうち小規模な六百十九町村で欠けていました。筆者は人口の対数を補助に補完を二十組作り、推定をまとめました。持ち家率十ポイント当たりの係数は、完全ケースでマイナス6.6、結果変数も使う多重代入でマイナス9.7でした。

値のそろう千百十五自治体を基準に、四通りの欠け方で約三十五パーセントを消し、百回の推定を比べています。小さい町ほど消す設定では、偏りは完全ケースのマイナス2.8に対して多重代入はマイナス4.2でした。町の大きさで関係が変わると、一つのモデルによる外挿でずれが増えます。

ただし、欠損している自治体の値は観測されていないため、実データの係数の正誤は決められません。補完値には百分率の範囲を超えたものがあり、モデルの点検に役立ちます。今回の比較は一時点の地域データで、因果関係を示すものでもありません。

**読む価値：** 欠け方と補完モデルの両方が推定に影響する場面を数字で追えます。

### 5. AI にコードを読ませて設計意図を推測させたら、3つ外れた

**原文：** https://zenn.dev/tomnotelog/articles/design-intent-guesses-missed-retrospective

**公開日時：** 2026-11-15 09:00:05 JST

授業ノートを整理するリポジトリで、Claude Code がコードと git log を読み、設計理由を推測しました。筆者は記録を、見た事実・仮説・確認の三行に分け、答えが違う箇所に仮説修正を追記しました。

原本と変換版と編集版を三層にした理由を、AIは編集の消失防止だと推測しました。筆者の都合は、穴を埋めた資料と余談まで加えた資料を両方残すことでした。公開用の別リポジトリは見やすさのためで、後からできた PDF ツールにも別の動機がありました。

ただし、一つのリポジトリの振り返りです。報告した三件は後で数え直せる性質の話で、すべての推測の正答率は測っていません。筆者の記憶にも後から整理した説明が混じり得るため、当時の記録を一緒に参照する価値があります。

**読む価値：** コードから読み取れる事実と、担当者に聞いて初めて分かる理由を区別できます。

### 2. 429 を受けてからでは遅い — 外部プロバイダへの送信レート制御を再試行の増幅率で比較する

**面接質問：**

> Retry-After と毎秒90件の共有トークンバケットを、なぜ別々に計測したのですか。

**約30秒回答：**

> Retry-After は拒否された後に待つ方法です。実験では再試行が四百五十回残りました。毎秒九十件の共有トークンバケットは先に流量を絞るので、千件を千回で送れました。一方で、完了に約二秒多くかかりました。ただし、固定ウィンドウでの結果なので、別の制限方式でも同じ比率になるとは限りません。

**関連プロジェクト例：** 仮想時計のテストで、送る前に待つ場合と拒否後に待つ場合を分けて測ります。

**キーワード：** Retry-After、共有トークンバケット、固定ウィンドウ

### 3. TypeScriptのnoUncheckedIndexedAccessで配列・辞書のundefined事故を防ぐ

**面接質問：**

> Record<string, number> の在庫で、noUncheckedIndexedAccess を加えたら何を確認しますか。

**約30秒回答：**

> Record で任意のキーを引くと、未登録でも number と扱われる場合があります。noUncheckedIndexedAccess を有効にすれば、読み出した値は undefined の可能性を持ちます。未登録だけを分けて、ゼロは有効な在庫として残します。添字が要らなければ、配列の要素を直接読みます。ただし、実行時の入力検証や、同時購入での在庫更新は別に確かめます。

**関連プロジェクト例：** 未登録、在庫ゼロ、在庫ありを別々のテストにして、APIの応答を確かめます。

**キーワード：** Record、noUncheckedIndexedAccess、undefined

### 4. 欠けている値は「捨てる」か「埋める」か：小さい町村だけ値がない持ち家率で、扱い方を比べたときに何を決めて何を確かめたか

**面接質問：**

> 小さい町ほど欠ける場合に、多重代入と完全ケースの結果が分かれたのはなぜですか。

**約30秒回答：**

> 記録のある町では、持ち家率との関係が町の規模で違っていました。一つのモデルで多重代入すると、大きい町の関係を小さい町に外挿します。この条件のシミュレーションでは、完全ケースより偏りが大きくなりました。ただし、実際の欠損値は分からないので、どちらの推定が正しいかまでは言えません。

**関連プロジェクト例：** 規模別に関係が違うデータを作り、欠損の割合を変えて推定の偏りを比べます。

**キーワード：** 欠損、多重代入、完全ケース、外挿

**関連プロジェクト例：** 身近な設計判断を二件選び、根拠のファイルと変更時に確認された理由を並べます。

## 4. 技術テーマ：処理の単位と検証方法を決める

比較に使う基準を先に決めます。Undoでは直前の保存結果、配信では元の件数、補完では値を消す前の係数が役立ちます。

扱う値が同じ形に見えるときは、どこから来たかを調べます。共有予定の採用は独自の履歴を持ち、値が欠けた地域と値がゼロの地域では意味が変わります。

最後に、確認できた範囲を記録します。固定ウィンドウ一条件のシミュレーションと、一人の記憶をもとにした振り返りでは、それぞれ言える範囲が違います。

# B. 重点まとめと面接で使える知識

### 1. Undoした「水曜は出社」が、共有予定に残る理由

1. 新しい号と保存済みの号では、週表を読む先が違います。

2. 後から採用したことも、残すべき変更として扱えます。

3. どちらが戻ったか分かる表示なら、履歴を調べる負担が減ります。

### 2. 429 を受けてからでは遅い — 外部プロバイダへの送信レート制御を再試行の増幅率で比較する

1. 同じ完了時間でも、相手に送った要求数は異なります。

2. 共有予算なら、複数の送信処理が一度に動くときの合計を抑えられます。

3. 複数プロセスに増やす場合には、別途全体の予算を考えます。

### 3. TypeScriptのnoUncheckedIndexedAccessで配列・辞書のundefined事故を防ぐ

1. 未登録キーの読み出しを、その値を使う前に処理します。

2. 配列の添字が不要なら、要素を直接読む形にできます。

3. DBの同時更新は型チェックと別の仕組みで扱います。

### 4. 欠けている値は「捨てる」か「埋める」か：小さい町村だけ値がない持ち家率で、扱い方を比べたときに何を決めて何を確かめたか

1. 欠損の手がかりを補完モデルに入れる発想を確認します。

2. 人口で分けた係数を見ると、一つのモデルの弱点が見えます。

3. 偏りの比較には、元の値を知っている検証が役立ちます。

### 5. AI にコードを読ませて設計意図を推測させたら、3つ外れた

1. 質問の前に根拠と仮説を置くと、何が修正されたか追えます。

2. 別の成果物が後に現れても、動機がつながるとは限りません。

3. 記憶による説明と作業当時の記録を突き合わせます。
