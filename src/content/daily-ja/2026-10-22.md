### 1. Nulab Backlogの検索をローカルAIで拡張した — Ollama・SQLiteで意味検索を実装する

**原文：** https://zenn.dev/hidetzu/articles/backlog-fzf-semantic-search-ollama

**公開時刻：** 2026-10-22 07:30:05 JST

Backlogの課題を探すCLI「bkfz」に、ローカルで動くOllamaを使った意味検索を追加した実装報告です。件名の言葉を忘れても症状を言い換えて探せるようにしつつ、課題キーや固有名詞に強い既存のキーワード検索は残しています。入力中はSQLiteの全文検索を使い、見つからないときだけCtrl-Sで意味検索へ切り替えます。入力のたびに文章をベクトルへ変換しないため、従来の操作の即応性を保てる設計です。既定の接続先をローカルにし、意味検索を設定した人だけが索引作成やモデル常駐の負担を持つ点も特徴です。

課題は件名と説明の先頭1,200字を一つのベクトルにし、文書は約1,000字ずつ、最大8個に分けて各断片へタイトルを添えます。状態や担当者、日付は埋め込まず、絞り込みなどに任せています。768次元の数値列を長さ1へ正規化し、SQLiteの通常テーブルにバイト列として保存します。検索時はGoで全件との内積を計算し、向きの近さで順位を付けます。一つの文書が複数の断片を持つ場合は、その中の最大スコアを文書のスコアにします。モデル名と次元数の食い違いは検索前に検出し、モデル名と本文を組み合わせたハッシュで変更分だけを埋め込み直します。

専用拡張を採用しなかった判断には測定があります。ランダムなベクトルを保存したDBを新しいプロセスで開き、上位50件を返すまでを3回測った中央値です。実データと同じ17,949本・768次元では、Ryzen 7 5700XのArch Linuxで総当たりが66ミリ秒、sqlite-vecが28ミリ秒でした。M2 Max側のGoはRosetta上なので、両環境をそのままCPU性能の比較にはできません。モデルが既にメモリにある場合の埋め込み27〜65ミリ秒と合わせ、検索全体は100〜140ミリ秒程度と見込んでいますが、これは操作全体を測った結果ではありません。初回約30分も、毎秒9.7件からの換算です。

検索品質は、実データの6問を目視した確認と、架空の課題19件・文書6件に対する22問の評価を分けて読む必要があります。後者では768次元の上位1件に正解が入る割合が0.95、上位5件では1.00でした。256次元は索引を約52MBから17MBへ減らせますが、架空データの上位5件の割合が0.95へ下がり、実データでも意図した課題を取りこぼしたため、既定を768次元へ戻しています。キーワードと意味検索の順位を融合する方法も実装しましたが、追加した12問では意味検索だけで全問1位となり、融合の優位性を判別できませんでした。

評価候補は25件しかなく、上位5件は全体の2割です。質問も正解を知る著者が作っており、この点数を一般的な検索精度とは呼べません。長い架空文書がないため、断片への分割や最大スコア採用の品質も未検証です。5万ベクトルを超えた場合などに専用拡張を見直す方針で、最初から複雑な構成にする必要があるとは結論付けていません。初回索引はバッチごとに保存して再開でき、2回目以降の同期でOllamaにつながらなくても、課題と文書の同期は成功させて警告を出します。検索機能の追加と、元の同期処理の可用性を切り分けた点も実務へ持ち帰れます。

**読む価値：** 意味検索を導入するだけでなく、既存の操作を保つ方法、測定から構成を選ぶ理由、小さな評価の限界を具体的に説明できます。

### 2. MapLibre React Native v11 入門：Expo で iOS / Android / Web に同じ地図を出す

**原文：** https://zenn.dev/sun_asterisk/articles/60d48ec339a739

**公開時刻：** 2026-10-21 14:03:07 JST

MapLibre React Native v11を使い、ExpoからiOS・Android・Webに地図を表示した入門記事です。v11はReact NativeのNew Architecture専用で、地図データや見た目の指定をWeb用のMapLibre GL JSへ近付けています。記事では共通の入力とGeoJSON、レイヤーの色などの定義を持ち、ネイティブ用とWeb用のファイルを拡張子で切り替えます。ただし、ネイティブはReactコンポーネントで宣言し、Webは地図のインスタンスを操作するため、イベント形式や生成・破棄の処理まで同一になるわけではありません。

動作確認は10月7日、Expo SDK 57.0.26、React Native 0.86.3、React 19.2.3、MapLibre React Native 11.5.0、Web側はMapLibre GL JS 5.22.0です。Android API 36のエミュレーター、iOS 27のシミュレーター、Chromiumで確認し、実機は未確認と明記しています。ネイティブモジュールを含むためExpo Goでは動かず、自前のDevelopment Buildが必要です。実行時にファイルを選ぶMetroとTypeScriptの既定の解決方法は違うので、型チェック用のファイルも用意しています。地図の描画ライブラリとは別に背景タイルやスタイルの提供元が必要なことも、導入前に分けて考えます。

共通化しても、単位と座標順の境界は残ります。アプリ内では緯度・経度を名前付きで持ち、地図へ渡す境界で経度・緯度の順の配列に変換します。地図上の円の半径を指定する描画設定はピクセル単位なので、半径1キロメートルの範囲を示す用途にはそのまま使えません。記事では球面上の64点から閉じた多角形を作り、GeoJSONとして描きます。また、プログラムでカメラを動かしても移動完了イベントは来るため、ネイティブではユーザー操作を示す値、Webでは元の操作イベントの有無を確認し、選択とカメラ移動が循環するのを避けています。

Reactの不具合として特に参考になるのは、カメラを範囲へ合わせるfitBoundsの戻り値です。v11.5.0の型はvoidでも、実装はネイティブ側のPromiseを返します。戻り値をそのまま返す省略形の関数をuseEffectへ渡すと、そのPromiseが後片付け用の戻り値になり、画面切替時に警告が出ます。関数をブロックで書き、何も返さない形へ直しています。回帰テストでも型だけをなぞらず、実装と同じくPromiseを返すカメラを用意し、更新とアンマウントで警告が出ないことを確かめます。型チェックの通過と実行時の振る舞いの確認を分ける好例です。

Webでは親要素の大きさの変化をResizeObserverで監視し、地図を再配置します。破棄時には監視と地図インスタンスを片付けます。自動テストでは背景色だけのスタイルを返してタイル取得を避けますが、それで確認できるのは操作やピン表示までです。実タイル、APIキー、出典表示は実サービスで別に確かめる必要があります。公開用環境変数の値はアプリへ埋め込まれるので、Gitに入れないだけで秘密にはなりません。キーの利用量や制限も確認し、住所検索をサーバー経由にする場合は利用者ごとの回数制限を設ける、という境界まで説明しています。

**読む価値：** Reactの型と実装のずれ、地図イベントの循環、実サービスと自動テストの確認範囲を、具体的な不具合から学べます。

### 3. Node.jsのfs.openAsBlob()で作成後にファイルを変更するとどうなるか

**原文：** https://zenn.dev/yukke_dev/articles/20261022-open-as-blob-file-change

**公開時刻：** 2026-10-22 09:53:17 JST

Node.jsでファイルをBlobとして扱った後、元のファイルを更新するとどうなるかを確かめた小さな実験です。Blobを作った時点の内容がメモリに固定されると思うと、後から読む処理を誤解します。記事が扱うopenAsBlobはファイルを基にしたBlobを返すため、作成時点と実際に読み取る時点を分ける必要があります。公式資料への参照と、自分の環境で観測した値を併記している点が読みどころです。

検証環境はmacOS arm64上のNode.js v26.0.0です。一時ディレクトリに架空のファイルを作り、最初に5バイトの文字列を保存してBlobを作成します。大きさと型、読み取った本文をassertで確認した後、同じパスへ14バイトの別の文字列を上書きします。業務データを使わず、最後に一時ファイルを削除する一連の順序で、変更前後の差を確かめています。

最初のBlobは変更前なら読み取れますが、上書きした後に同じBlobのtextを呼ぶと、DOMExceptionのNotReadableErrorで失敗しました。その後にopenAsBlobを呼び直すと、新しく作られたBlobは14バイトとなり、変更後の本文を読めました。ここで観測したのは「古い内容が残る」「自動で最新内容になる」という挙動ではなく、既存のBlobからの読み取りが失敗する挙動です。ファイルの内容を利用するタイミングまで含めて設計する理由が見えます。

原文は、ファイルを基にしたBlobの作成時と読み取り前に状態を調べるという公式資料の説明を紹介します。一方、今回の上書きは文字列の長さも変えています。同じ長さでの上書き、パスの名前変更、読み取り中の変更、別のOSは未検証です。変更の検出条件を全て調べた実験ではなく、あらゆる失敗で同じ例外名になるとも主張していません。小さなテストの結果を、そのまま全環境の仕様へ広げない区切り方が重要です。

元のファイルが更新される可能性があるなら、読み取り直前にBlobを作るか、処理中に更新されないファイルを用意する必要があります。呼び直して読めたのは今回の順序での結果であり、呼び直した後の読み取り中に再び更新されない保証ではありません。記事はNode.js 26.10.0の同期版追加にも触れますが、手元のv26.0.0では非同期版だけを実行しています。新しいAPIの紹介と自分が実際に試した範囲を分けて読むことで、ファイルの寿命や更新競合を説明する材料になります。

**読む価値：** 短いコードから、APIの名前だけでは分からないデータの寿命と更新競合を、観測条件を添えて説明できます。

### 4. データベースとコードの長期的なリファクタリングを安全に進めるための取り組み —— 従業員データの複雑さを解きほぐす

**原文：** https://tech.smarthr.jp/entry/2026/10/21/123725

**公開時刻：** 2026-10-21 12:37:25 JST

SmartHRは、従業員データを扱うRailsアプリケーションで、親子関係にある二つの履歴テーブルの統合を進めています。両方が、業務上いつ有効かと、システムにいつ記録したかを管理するバイテンポラル履歴のため、過去時点の参照や更新では二つの時間軸と親子間の期間をそろえる必要がありました。親側だけで1,000万件規模のレコードがあり、特別扱いするコードも各所に影響していました。現在の要件とPoCを確認し、外部の機能を変えず、親テーブルへ情報をまとめる方針です。

移行中はデータを一度に置き換えません。現在の更新と同時に統合先へ書くダブルライトと、過去分を移すバックフィルを併用し、新旧両方のデータを保ちます。現行処理が統合後のデータを参照しない段階では、新側への書き込みに失敗しても現行の動作へ影響しない構成です。新実装へ切り替えた後も旧側への書き込みを続けるため、問題があれば旧実装へ戻せます。

コード側ではBranch by Abstractionを使い、新旧実装を共通の抽象の内側へ隠します。利用側が従来と同じ方法で子データへアクセスすると、その抽象がフィーチャーフラグに応じた処理を選びます。各呼び出し元へ移行中という事情を広げず、旧実装でサービスを動かしたまま新実装を少しずつ追加する設計です。

移行用の処理も使い捨てにせず、通常のアプリケーションと同じようにモジュール、インターフェース、テストを整え、複数のツールで共有しています。その同じ判断基準を使い、前日以降の作成・更新分を調べる日次チェックと、並列処理で過去分も調べる全件チェック用CLIを運用します。履歴同士を対応付けにくいデータなどを早く見つけ、修正して再確認する循環を短くしています。

原文は運用中の設計と経過を報告した記事です。約半年の作業を進めた段階でも新実装への切り替え準備は続いており、旧実装の削除まで完了したという結果ではありません。処理速度の改善率や無停止移行の実測値も示されていません。面接では、大規模データの移行を、変更範囲の限定、切り戻し、継続的な整合性確認に分けて説明する材料になります。

**読む価値：** 履歴を持つ大規模データの変更で、互換性、切り戻し、移行検証をどう両立するかを具体的に説明できます。

### 5. ZKP・MPC・FHEを「学ぶ」から「作る」へ ――Advanced Cryptography Program 2026に参加して見えた、高機能暗号実装の難しさ

**原文：** https://gihyo.jp/article/2026/10/advanced-crypto-program-recap

**公開時刻：** 2026-10-22 09:34:00 JST

この記事は、7週間のAdvanced Cryptography Program 2026に参加した筆者による実装の振り返りです。複数者が秘密を明かさず共同計算するMPC、主張や計算の正しさを示すZKP、暗号化したまま計算するFHEを学び、最終週に成果物を発表しました。技術名を採用すること自体より、何を隠し、誰に何を検証してもらうかを先に整理する必要が見えてきたと報告しています。

特に区別すべきなのが、計算の正しさと情報の秘匿です。FHEで入力を隠せても、サーバーが指定どおりの計算をしたかは別途確認が必要で、講義では証明を組み合わせるVerifiable FHEを扱いました。一方、証明が正しくても、入力前に不都合なログが抜かれていれば現実の記録全体は保証できません。署名、改ざんに強い保存、時刻の証明、アクセス制御などを含め、信頼する範囲を決める課題です。

筆者の成果物AuditGuardは、監査ログの改ざん検出と、単独の管理者に開示権限を集中させないことを題材にしています。架空のログをそれぞれハッシュ化し、Merkle treeのルートへまとめ、保存後の書き換えを検出します。開示用の鍵はShamir秘密分散で五つに分け、三つがそろうと復元できる3-of-5構成にしました。さらにSchnorr型の知識証明で、対応する分散片を知っているかを簡易的に確認します。

デモでは、ログの変更でMerkle rootとの検証が失敗することと、三者分の分散片から鍵を復元する流れを確認しています。ただし三人が別の端末で承認したのではなく、一つのPythonプロセス内で三者の承認を模擬しています。小さな暗号パラメータと簡易な自作暗号化処理を使う学習用PoCで、企業データを保護できる完成品ではありません。実用化には暗号方式、鍵管理、証明方式、保存基盤などを実用的な実装へ置き換える必要があります。

したがって、ここでの成果は高機能暗号を組み合わせる役割分担を小さく確認したことであり、実運用の安全性や性能を実証した結果ではありません。面接では、改ざん検出、秘密の共同管理、計算の検証、入力の出所を別々の保証として説明できます。証明が通ることを、入力が現実の事実を漏れなく表すことや、本番運用に耐えることと混同しない点が重要です。

- 例文：同じ方式でも、必要な条件は一様ではありません。
- 例文の意味：技術名だけで全ケースを同じと判断しない意味です。
- ニュアンス：やや硬い言葉で、同じでないことと共通点が全くないことは別です。

## C-2. IT/AI専門用語

1. **embedding（埋め込み）**：文章を比較できる数値の列へ変換すること。 Backlogの文章をOllamaで768次元へ変換します。

2. **FTS5（SQLiteの全文検索機能）**：SQLiteで文章の索引を作り、検索する機能。 bigramで候補を絞り、元の語をLIKEで確かめる検索を残しています。

3. **GeoJSON（地理データのJSON形式）**：位置や形をJSONで表す形式。 地図との境界で経度、緯度の順へそろえます。

4. **New Architecture（React Nativeの新しい内部構造）**：Fabricなどを含むReact Nativeの新しい内部構造。 MapLibre React Native v11はこの構造を前提とします。

5. **fs.openAsBlob()（ファイルを基にしたBlobの作成）**：ファイルを基にBlobを作る機能で、その場で全内容を複製するものではありません。 作成後の変更による読取失敗と、再作成後の読取を分けています。

6. **Bitemporal Data Model（バイテンポラル履歴）**：有効な時点とシステムへ記録した時点の二つの軸で履歴を扱う方法。 SmartHRは二つの時間軸を持つ親子テーブルを統合しています。

7. **Branch by Abstraction（抽象化によるブランチ）**：共通の抽象の後ろに新旧実装を隠し、切り替える方法。 SmartHRは内部のフラグで実装を選び、呼出側へ変更途中の事情を広げません。

8. **Verifiable FHE（検証可能な完全準同型暗号）**：暗号化したままの計算に、その計算の正しさを確かめる仕組みを組み合わせる考え方。 秘匿と計算の検証を分け、入力が現実を正しく表すかは別の問題とします。

## C-3. 新規文法

本日の新規文法は1件です。「増やしていくわけにもいきません」を、事情や責任による制約を表す「～わけにはいかない」として扱います。過去71号の全履歴と照合し、既習の「わけではない」「ないわけではない」とは機能を区別しました。他の候補は既習や一般的な接続であり、新規5件にそろえるための追加はしていません。復習は当日の日本語用例から別に選びます。

### 1. ～わけにはいかない｜N2

- 意味：事情や責任があるため、そうすることはできない。
- 接続：動詞辞書形＋わけにはいかない／強調・追加の形では「わけにもいかない」
- 使い方：能力の不足ではなく、事情や責任を考えると実行できない時に使います。原文では、長期作業だからこそ移行用コードにも品質が必要だと述べています。
- 原文出現形：増やしていくわけにもいきません
- 原文根拠：[データ移行用とはいえ、書き捨てのコードを無秩序に増やしていくわけにもいきません。](https://tech.smarthr.jp/entry/2026/10/21/123725)
- 独自例文：旧実装へ戻す可能性があるので、今すぐ古いデータを消すわけにはいきません。
- 例文の意味：切り戻しに備える必要があるため、削除はまだできないという意味です。
- 注意：既習の「わけではない」は説明や主張を否定します。今回は事情により行為を避ける判断です。「にも」の形も同じ文型の中で扱います。
