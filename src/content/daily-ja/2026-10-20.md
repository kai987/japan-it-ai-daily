### 1. ブラウザだけで動くデータ分析AIエージェントを作ってみた

**原文：** https://zenn.dev/coji/articles/browser-only-data-analyst-agent

**公開時刻：** 2026-10-20 08:33:49 JST

CSVやParquetを読み、日本語の質問から集計と説明まで行うエージェントを、作者がブラウザ内に構築した報告です。Gemini NanoのPrompt APIがSQLと説明を作り、DuckDB-WASMが集計し、pi-durableが会話と実行記録をSQLite-WASMへ保存します。いずれも保存先はサイト単位のOPFSです。質問後の推論と集計に外部LLM APIは使いませんが、初回のモデル取得、起動時のエンジンや拡張の取得には通信があるため、常時オフラインという意味ではありません。

再開で重要なのは、途中だった操作の扱いです。pi-durableは呼び出し前に意図を、処理後に結果をコミットします。結果のない呼び出しは、安全に再試行できると指定したツールだけをやり直し、既定では中断エラーとして扱います。さらに、要約はSQL実行の内側から呼ばれるため、外側の再開にとどめると集計が重複します。そこで呼び出しIDに対応するSQL結果を保存し、既存の結果があればDuckDBを再実行せず要約を続けています。質問自体の二重送信も、同じ要求識別子で防いでいます。

画面側では、別タブが同じOPFSファイルを開く競合をWeb Locksで防ぎました。React StrictModeで初期化が二度走る問題には起動を一度に絞って対応し、開発時のHMRは全面再読み込みにしています。進行表示は別の状態として保存せず、コミット済みの記録から導きます。モデルのダウンロード完了を待ってから再開する点も、処理の失敗と準備不足を混同しない設計です。

作者はストレージの適合テスト24件、同じSQLiteファイルを別の実行本体で開くテスト、要約中の再読み込みをPlaywrightで確認しています。ただしブラウザ全体の強制終了や、書き込みツールの中断は未検証です。JSON Schemaで返答を絞っても、モデルはSQLの空白を落としたり、未実行のまま答えたりします。そのためコード側の補正と数値・名前の照合が必要でした。会話は最新の質問一つだけを渡し、応答は約15～20秒。Chrome155と実験的なpi-durable 1.3.0での実装であり、汎用的な正確性やクラッシュ耐性を示した結果ではありません。

**読む価値：** 画面の復帰と処理の二重実行防止を区別し、保存する結果と表示上の状態をどう分けるかを具体的に学べます。

### 2. Lambda Web Functions と従来の Lambda の実行環境と課金の違いを実測から確かめてみた

**原文：** https://zenn.dev/aws_japan/articles/lambda-web-functions-vs-event-functions

**公開時刻：** 2026-10-20 09:28:10 JST

HTTPサーバーをそのまま動かすLambda Web Functionsと、handlerでイベントを受けるEvent Functionsを、東京リージョンのNode.js24・arm64で比較した記事です。3秒待ちを300件同時に送る試験、200ms待ちを20並列で60秒続ける試験、1秒のCPUループを20件同時に動かす試験を用意し、Event側は256～2048MBも比較しています。レスポンスの環境識別子は応答した環境の数、初期化ログは起動の数を表し、同じ指標ではありません。

待ち時間主体の300件ではWeb Functionsは18環境で応答し、ログ上の初期化は19回、環境内の最大同時処理は23件でした。Eventの2048MBでは応答環境が299です。一方、CPU試験では20件がほぼ一つのNode.jsプロセスに集まり、直列処理によって最大20.6秒となりました。複数要求を同居させる仕組みと、JavaScriptの計算を並列化する仕組みは別です。環境内同時数の削減やworker_threadsは改善候補ですが、この記事では未検証です。

課金の比較には、呼び出し時間以外の情報も必要です。Eventは実行時間と割当メモリが基本で、凍結して残る間は課金されません。WebはCPU使用時間と環境存続中のメモリを分けて扱います。作者は終了ログとCost Explorerを照合し、寿命と最大使用メモリからの近似が一日・一アプリで約0.8%差になったと報告しています。ただし公式の計算式とはしていません。継続負荷では待機分を多くの要求で分担できましたが、3件だけのアクセスでは環境が347秒残り、256MB Eventとの定価比較で約260倍となりました。料金は環境が残っている限り発生するため、到着間隔が結論を変えます。

S3配布の読取権限、IAM認証の署名、ログ保持、監視拡張も移行時の確認点です。Webでは拡張登録APIが404、従来の環境変数の一部が存在しないこと、二つのロググループに同じ内容が保存されることも観測されています。各条件一回で、時刻や直前のウォーム状態は揃い切っていません。CPUループも仕事量固定ではないため、費用だけの優劣には使えません。環境の割当、課金対象、実際の到着間隔を分けて確かめるのが、この記事から得られる判断手順です。

**読む価値：** 同じLambdaという名前でも、同時処理・CPU・待機メモリの単位が異なることを、条件付きの実測で説明できます。

### 3. スピード10倍の開発を支える、AI活用基盤の開発に参戦（インターンレポート）

**原文：** https://techblog.lycorp.co.jp/ja/20261019b

**公開時刻：** 2026-10-19 11:00:00 JST

LINEギフトのSREチームで、2026年8月3日から9月11日まで行ったインターンの実装報告です。コードを書く速さが上がる一方、アラート調査やブランチ運用など周辺作業が詰まり始めていました。日付別のリリースブランチへmainの変更を戻すバックマージは、毎朝のGitHub Actionsで機械的なPR作成・マージを自動化し、重要な判断箇所には手作業を残しています。題名の「スピード10倍」は企業のバリューであり、十倍を測定した成果ではありません。

AIが作った変更を受け止める検査も整えています。E2Eにミューテーションテストを導入し、テストが変更や誤りを検出できるかを確認する方向です。OpenAPIの整備と、コミット・プッシュ前にLefthookで走るチェックを組み合わせました。高速に単一バイナリを配布したいCLIはGo、分析と柔軟なAI処理はPythonと、用途で言語を分けています。ただしテストの検出率がどれだけ改善したかという比較値は本文にありません。

自律調査の基盤にはflueを採用しました。既存CLIをそのまま起動する案、重いエージェントフレームワーク、公式SDKの直接利用を比べ、将来の変更に追従できる軽量な会話・状態管理を重視した選択です。処理はコンテナに隔離し、履歴や調査の文脈はDBへ保持します。実行ステップ数とタイムアウトを制限し、ログやメトリクスの参照と破壊的操作の権限を分けました。安全性をモデルの判断だけに預けない構成です。

監視アラートやE2E失敗を契機に、AIがコード、ログ、メトリクスを照合し、見立てと次の確認点をSlackへ返します。対応を決めるのは人間です。将来のリモートコーディング支援やPR・課題の自動起票は構想として区別する必要があります。バックマージ自体を減らすブランチ戦略も今後の課題です。定型化できる処理と判断を伴う調査を分けた実践として読み、修復率や事故削減率まで示した事例とは扱いません。

**読む価値：** 日本の現場で、定型処理の自動化、テストの検出力、AIの調査権限をどう組み合わせたかを説明できます。

### 4. Claude Code で CI 待ち時間を 18 分から 4 分台に短縮する【GitHub Actions】

**原文：** https://zenn.dev/edash_tech_blog/articles/5b90aa33bd8d49

**公開時刻：** 2026-10-20 08:00:05 JST

e-dashがNext.js・TypeScriptのPR CIを改善した報告です。Vitest4.1を使う私有リポジトリのubuntu-latestは2CPUで、テストの増加に伴い中央値が約15分、長い時は18分を超えていました。Claude Codeで内訳を測ると、400秒のうちテスト本体は57秒にすぎず、jsdomの起動には224秒を使っていました。さらに既定のワーカー数がCPU数から一つ減るため、この実行環境では直列になっていました。

まず、DOM不要のテストをnode環境へ、画面描画のテストをjsdomへ分け、低CPU環境ではワーカーを二つへ増やしました。PostgreSQLの準備は、移行済みDBをpg_dumpで保存し、マイグレーションファイルのハッシュをキーに復元しました。共有したいキャッシュはmainで作る必要があり、PRで保存したものを他のPRが読めると考えてはいけません。DB準備は約5分から2分15秒へ縮みました。

次に単体テストとDBを使うテストを別ジョブへ分け、単体テストを分片化しました。blobレポートを最後に合算してからカバレッジを判定し、検査基準は維持しています。node_modulesの復元ではOS・アーキテクチャ・Node版とパッケージ定義をキーに含めていますが、インストールスクリプトを使わないという当該プロジェクトの前提があります。キャッシュ命中で整合性チェックまで飛ぶ点を見落とせません。

直近20本の中央値は約4分45秒となり、約15分から約69%の削減でした。ただし複数施策を組み合わせた同社の実運用値です。キャッシュが合計11.9GBとなって既定上限を超え、古いDBキャッシュも消える問題があり、Dockerの保存範囲やPlaywrightの保存元、重複するnpmキャッシュを見直しています。PRごとの使用量は推定約1.7GBから673MBへ減りました。今後のDOM実装変更やテスト整理は候補であり、実施済みの効果には含めていません。

**読む価値：** フロントエンドの面接で、待ち時間の内訳、キャッシュの失効、分割後の検査維持を実数とともに説明できます。

### 5. Cloudflare CLIで公式ドキュメントを検索し、Markdownで取得する

**原文：** https://dev.classmethod.jp/articles/cloudflare-cf-docs-search/

**公開時刻：** 2026-10-19 15:50:10 JST

Cloudflare CLIで公式資料を探し、選んだページをMarkdownで取得する手順です。公開資料の検索にはログインが不要ですが、インターネット接続は要ります。返るのは本文ではなく、タイトル・説明・URLを持つ順位付き候補です。公式説明は最大5件で、記事のDNS検索でも5件でした。公開文書を探せることと、アカウント内の変更操作を認証なしで行えることは別です。

候補を読んで採用するURLを決めた後、Markdownを要求するHTTPヘッダーを付けて本文を取ります。jqでURLを抽出しcurlへ渡す例は、前段が成功した時だけ進む構成です。空の結果なら抽出が非ゼロ終了するため、不明なURLの取得に進みません。取得した文書にはタイトル等のfrontmatterがあり、応答の種類もMarkdownでした。検索の成功だけを根拠にせず、選択と本文確認を別の工程にできる点が実用的です。

検証はUbuntu24.04.5 LTSのARM64、Node.js24.21.0、cf 1.0.0-beta.18です。ただしCLIはベータ段階で、出力やオプションは変わる可能性があります。同じページの異なる見出しが候補に混じり、定期実行を尋ねた日本語検索でも目的のScheduled Handlerは三番目でした。五件を五つの独立資料と数えたり、先頭を無条件に渡したりしない判断が必要です。検索順位の評価実験ではなく手順の確認であり、検索語にはトークンや個人・組織を特定する情報を含めないという注意も残します。

**読む価値：** 検索候補と本文の根拠を分けて、必要な公式資料を選んでから開発エージェントへ渡す手順を学べます。

## C-2. IT/AI専門用語

1. **durable execution（中断から再開できる実行）**：呼び出しと結果の記録を使って処理を再開する仕組み。 ブラウザの例では再実行を読み取りに限定し、入れ子のSQL結果も再利用します。

2. **OPFS（オリジン専用ファイルシステム）**：ブラウザがオリジンごとに管理する専用ファイル領域。 本記事ではWeb Locksで複数タブによる同時利用を制限します。

3. **Lambda Web Functions（HTTPサーバー型のLambda）**：一つの実行環境に複数のHTTP要求を載せる方式。 Node.jsの一プロセスでのCPU処理と、I/O待ちの並行処理を分けて考えます。

4. **flue（軽量エージェントフレームワーク）**：エージェントの会話や状態、道具を組み立てるための枠組み。 LINEの事例では制限付きの調査に使い、対応の最終判断は人に残します。

5. **mutation testing（ミューテーションテスト）**：小さな誤りを加え、テストが検出できるかを調べる方法。 LINEの報告では、AIの実装を検査するテストの検出力を見る観点です。

6. **Vitest projects（テスト構成の分離）**：テストのグループごとに実行環境などを分ける設定。 e-dashはDOM不要のテストを分離し、全体のワーカー数も管理します。

7. **blob report（統合用テストレポート）**：分けて実行したテストの結果を後でまとめるためのレポート。 分片ごとの合格だけで終えず、全結果を合算してカバレッジを判定します。

8. **Markdown content negotiation（Markdownでの応答形式指定）**：HTTPヘッダーでMarkdown形式の本文を求めること。 Cloudflareの検索候補を選んだ後、本文を別に取得して確かめます。
