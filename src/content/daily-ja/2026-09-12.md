### ② レガシーコード500本からSQLを自動抽出できるのか試してみた 〜Claude Codeのヘッドレス実行とHaiku/Sonnet/Opusの比較〜

**出典：DevelopersIO｜2026年9月11日**  
**原文 URL：** https://dev.classmethod.jp/articles/claude-code-headless-legacy-code-sql-extraction/

SQL Server 2008 R2以前から2019/2022へ移行する際、Application側で実行されるSQLを全て洗い出すImpact Analysisは、数千File規模になると大きな負担になる。この記事では、LLMにRepository探索を自由にさせず、外部Scriptから `claude -p` をHeadless実行し、さらに `--tools ""` でTool利用を止める構成を採っている。最初の検証Dataは500 File（Java 300 / VB.NET 200）、SQL 440件、Shift_JIS 208 File、UTF-8 292 File、SQLなし127 Fileで、branch、proc、literal、concat、dynamic、builderなど8 Patternを埋め込んだ。Migrationでの取りこぼしは本番障害につながり得るため、主指標をRecallにした点も明確である。

Haiku 4.5による500 File Testは500/500を完走し、Costは **$3.14（$0.0063/file）**、所要時間は102.1分（batch=5 / workers=4）。当初Recallは98.9%（435/440）と表示されたが、原因はLLMではなく評価側Source Codeの誤りで、修正後は100%になった。ここは非常に重要で、Evaluatorが間違えばModel評価も間違うことを実例で示している。次のTestでは、100 Fileに866 SQLを埋め込み、83 Fileに2カ所以上のSQL、1 File 4～8 Location、中央値185行という難しい条件に変え、同一Data / Prompt / Schema / BatchでHaiku 4.5、Sonnet 5.0、Opus 5.0を比較した。

実測結果はRecallがHaiku 99.9%、Sonnet 99.8%、Opus 100%。見逃し・想定外抽出・未照合が全て0だったのはOpusだけで、Costは **$4.25 / $7.07 / $9.04**、所要時間は **21.0 / 7.4 / 6.7分**だった。安いHaikuが最も遅かった点も単純なModel Tierの直感と一致しない。**一方で、Ground Truth付きDataは著者が生成したSampleであり、実際のLegacy Systemにあるさらに複雑なLogicへの一般化は未検証である。** したがって100%という数字より、Headless Batch、Ground Truth、Recall、False Positive、Cost、Time、Evaluator Testを同じ実験設計に入れたことを学ぶべき記事である。

**注目ポイント：★★★★★**  
AI EvaluationはModel Scoreを出して終わりではない。**何を見逃すとBusiness Riskになるかを決め、Evaluator自身までTestする**という実務的な設計がそのまま面接回答に使える。

### ③ 「危険コマンド停止率、AIは89％、人間だと14％」　Claude Codeが「自動モード」をデフォルトにした理由：「有害な操作」の承認は、手動の方が2倍多い

**出典：＠IT｜2026年9月11日**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/spv/2609/11/news018.html

Claude Codeの `auto mode` はPermissionをなくす機能ではない。Tool CallをClassifierへ通し、元に戻せない操作、破壊的操作、User Environment外へ影響する操作をBlockする。既存Permission RuleはClassifierより先に評価されるが、`python:*` のように任意Codeを実行できる広いAllow Ruleはauto mode中だけ無効になる。Classifierが3回連続でBlockするか、1 Sessionで20回Blockして前進できなくなった場合はManual Approvalへ切り替わる。狙いはHuman Gateを排除することではなく、同じPermission Promptを何度も見ることで起きる承認疲労を減らすことにある。

Anthropicが調査会社経由で集めた **1,053人**の有償TesterによるBlind Controlled Experimentでは、Permission Promptの1つを明らかに危険なCommandの表示へ置き換えた。実際の危険処理は実行されない条件で、人が止めた割合は13.6%（143/1053）、auto modeは89%（937/1053）。Human DetectionはSession序盤の約17%から、50回以上Promptを経験した後は約5%まで低下した。別のMay–JuneのFlagged Session再評価では、Severity 7以上でUserが明示的に要求していない有害操作を含む割合がManual 6.3%、auto mode 2.4%と報告されている。

Apollo Researchとの2週間のSynthetic Red Teamでは、RepoのPublic / Private、Git State、Data Handling RuleなどをClassifier Contextへ追加した後、Adversarial SetのMiss Rateが12%から7%へ下がった。**ただし、この7%はClassifierの穴を探すために作ったSynthetic Attack Setでの値で、Real TrafficのMiss Rateではない。1,053人Testも危険Commandの表示を差し替えたControlled Experimentであり、本当にDamageを発生させた実験ではない。** つまりEvidenceごとの母集団と条件を分けて読む必要がある。

**注目ポイント：★★★★★**  
「Human-in-the-loopなら安全」という前提自体を測り直している点が重要である。Security GateもUXと同じく、**疲労、Fallback、Context、実TrafficでのCalibration**まで含めて設計する必要がある。

### ④ AI開発を「マルチプレイ」に　対話とコードを複数人でリアルタイム共有する「Delta」：「なぜこんなコードに？」の疑問を解消

**出典：＠IT｜2026年9月11日 08:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/11/news033.html

Zed IndustriesのDeltaは、AI Codingの共同作業単位をGit Diffだけでなく **Conversation Thread + Worktree**へ広げる。基盤の `DeltaDB` はAIとの会話とWorktreeをまとめてThread参加者へRealtime Replicateする。既存Git Repositoryはそのまま使え、Commit / Pushも従来通りなので、Deltaを使わないMemberからは普通のRepoに見える。一方、Deltaを使うReviewerは最終Diffだけから意図を推測せず、Code生成に至ったAgentとの会話をContextとして参照できる。

Review Commentの扱いも特徴的だ。一般的なPR CommentはCommit Snapshotへ固定され、Codeが変わると文脈が古くなることがある。DeltaではWorktree内のCode Lineへ直接Commentでき、そのCommentがCode変更へ追随する。MemberはThreadへ招待されればRealtimeで会話とCodeを確認でき、後から作業を引き継げる。Cloud Runnerへ移せばPCを閉じてもAgentは継続し、Browser版Delta.devはRust ApplicationをWebAssemblyへCompileし、WebGLで描画する。Claude Codeなど外部AgentのTerminal SessionもThreadへLive Syncできる。

**ただし、Deltaは現時点でPrivate Betaである。** Realtime Sync、Cloud Runner、WASM/WebGLといった内容はZed IndustriesのProduct Design / Announcementであり、Team Productivityや大規模Repoでの信頼性を示す独立Benchmarkではない。Production利用ではAccess Control、Secretの扱い、Sync Conflict、Large Worktree Performance、History Retention、Conversationをどこまで保存するかを確認する必要がある。

**注目ポイント：★★★★★**  
AI CodingのReviewでは「何が変わったか」だけでなく「なぜそのCodeになったか」が重要になる。Deltaは**Reasoning ContextをTeam Artifactとして残す**という新しいDeveloper Experienceを提示している。

### ⑤ ANAがネットワーク構築を「数カ月→数週間」に短縮　“システムごとに回線追加”からどう脱却した？：事業拡大に伴うネットワーク複雑化をどう抑えるか

**出典：＠IT｜2026年9月11日 11:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/11/news036.html

ANAは約280機の航空機、200路線以上を持ち、予約、搭乗、顧客Communication、運航管理など多くのSystemを運用している。従来はSystemごとに専用回線を用意していたため、新System追加や既存System拡張のたびに回線・設備も増え、Network構成とCostが複雑化した。そこで「専用回線をもっと効率よく増やす」のではなく、CloudへのConnectivity自体を共有CapabilityにするCloud Network HubへArchitectureを変えた。

採用したのはNaaSの `Equinix Fabric`。AWS、Microsoft Azure、Google Cloudへの接続を一元的に管理し、System追加のたびに物理回線を敷設せず、Private Connectionと集中Policy ManagementでSecurity / Complianceも扱う。記事で報告された結果はNetwork構築期間 **約80%短縮**で、従来数カ月だったものを数週間へ短縮した。Application開発・Testに必要なResourceを早く使えるため、Business Agilityの向上にもつながるとしている。

Costについては **5年間TCOを30%削減することを目標**としている。ここはMeasurementとTargetを分ける必要がある。約80%はCaseで報告された構築期間の短縮結果だが、30%は将来目標であり実績ではない。**また、ANA / EquinixのCustomer Caseなので、全てのMulti-cloudで同じArchitectureが最適とは限らない。** Private Connection Cost、Latency、HA / Redundancy、Failure Domain、Route Policy、Hub集中によるBlast Radiusは自社Topologyで検証する必要がある。

**注目ポイント：★★★★★**  
Cloud / SREで大切なのはService名よりArchitecture Signalである。**Applicationが増えるたび同じNetwork Decisionを繰り返しているなら、そのConnectivityをPlatform化できないか**と考える視点が得られる。

## 4. 今日の技術テーマ

### Observable Automation Contract —— 自動化が強くなるほど、結果・Context・責任を観測可能にする

今日の5本は異なるLayerを扱っているが、構造は共通している。

```text
Business / Engineering Intent
          ↓
Observable Contract
├─ Business KPI / RBAC / Quota
├─ Ground Truth / Recall / Evaluator
├─ Action Risk / Classifier / Fallback
├─ Conversation / Worktree / Review Context
└─ Lead Time / TCO / Network Policy
          ↓
Automation
          ↓
Evidence + Human Decision
```

SnowflakeではBusiness KPI、Usage Log、RBAC、CostがAgentic EnterpriseのContractになる。SQL抽出では「見逃さないこと」をRecallとして測り、Ground Truthで検証する。Claude auto modeはHuman Approval自体を劣化し得るComponentとして測定した。DeltaはConversation Contextを個人のChatからTeam Artifactへ移し、ANAはSystemごとの暗黙Network Costを共通HubのLead Time / TCOへ変換した。

**メリット**は、AutomationをDemoではなくEvidenceで評価できることだ。ModelやToolを交換してもBusiness Contractを再利用でき、Human Reviewを不確実性が高い箇所へ集中できる。毎回安全Commandを承認するより、Classifierの不確実性、Domain Ruleの変更、Evaluatorの破綻、Architecture変更に人を置く方が価値を出しやすい。

**制約**として、ObservableであることとCorrectであることは同じではない。Usage Logが増えてもROIが上がるとは限らない。Synthetic Ground Truthは実Legacyを十分に表現しない可能性があり、7%のRed Team Miss RateもProduction Trafficには一般化できない。Conversationを全保存すればPrivacy / Retention Costが増え、共通Network Hubは新しい集中Failure Domainにもなる。

**国内企業での導入時の注意点：** AI / Automationごとに `Owner / Business KPI / Permission Boundary / Evidence Source / Failure Metric / Cost Metric / Escalation / Rollback` を明記する。Human Approvalも「人がいるから安全」で終わらせず、実際のReject Rateや疲労を測る。Vendor Caseの倍率・Cost・%は原条件と一緒に残し、自社ROIへそのまま転用しない。

面接では次のようにまとめられる。

> **AIや自動化を本番導入する場合、処理を自動化するだけでなく、KPI、権限、品質指標、失敗条件、CostをObservable Contractとして先に定義し、結果とContextを後から追跡できるようにすることが重要だと考えています。**

**exampleJa：** `Systemごとに回線を追加し続ければ、Network Architectureの見直しを余儀なくされます。`  
**exampleMeaning：** 個別回線の増殖により、Architecture変更が避けられなくなる。  
**note：** Top 5のNetwork複雑化の背景と対応する。

### 3. ～に至るまで
**level：** N1  
**meaning：** 起点からかなり広い終点まで、範囲が及ぶこと。  
**structure：** `名詞 + に至るまで`  
**usage：** Test Coverageの広さを説明する場合に有効。  
**exampleJa：** `単純なLiteralから複数Methodに分散したSQLに至るまで抽出精度を検証します。`  
**exampleMeaning：** Simple CaseからComplex Caseまで広くTestする。  
**note：** Top 2の複数SQL Patternに対応する。

### 4. ～たうえで
**level：** N2  
**meaning：** 前のActionを完了し、その結果を条件として次へ進む。  
**structure：** `動詞た形 + 上で / 名詞 + の上で`  
**usage：** Architecture Decision前のVerificationを表しやすい。  
**exampleJa：** `Private接続のLatencyと冗長性を確認したうえで、Network Hubへ移行します。`  
**exampleMeaning：** Network品質を確認してからMigration Decisionを行う。  
**note：** Top 5のProduction Validationに対応する。

### 5. ～に応じて
**level：** N2  
**meaning：** 条件や程度が変わるのに合わせ、Actionや選択を変える。  
**structure：** `名詞 + に応じて / 名詞 + に応じた + 名詞`  
**usage：** Model RoutingやPermission Policyの説明で頻出する。  
**exampleJa：** `Taskの難易度とCostに応じて利用するModelを切り替えます。`  
**exampleMeaning：** Task条件に合わせModelを選択する。  
**note：** Top 1のCortex AI Gatewayと対応する。

### 6. ～一方で
**level：** N2  
**meaning：** 一つの性質と同時に存在する、別の側面を示す。  
**structure：** `普通形 + 一方で / 名詞・な形容詞 + である一方で`  
**usage：** Cost・Speed・AccuracyのTrade-off説明に向く。  
**exampleJa：** `HaikuはCostが低い一方で、この検証では3Modelの中で最も時間がかかりました。`  
**exampleMeaning：** 安さと処理時間のTrade-offを示す。  
**note：** Top 2のAuthor Measurementに直接対応する。

### 7. ～とは限らない
**level：** N2  
**meaning：** 一般化できないこと、必ずそうなるわけではないことを示す。  
**structure：** `普通形 + とは限らない`  
**usage：** BenchmarkやCase StudyのEvidence Boundaryを述べるときに有効。  
**exampleJa：** `Synthetic DataでRecallが100％でも、実Legacy Codeで同じ結果になるとは限りません。`  
**exampleMeaning：** Test Dataでの成功をReal Systemへそのまま一般化できない。  
**note：** Top 2を中心に、今日の全Top 5へ応用できる。
