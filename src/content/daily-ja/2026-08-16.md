### ① Kiro IDE、サブディレクトリのAGENTS.mdをサポート

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/kiro-ide-subdirectry-agentsmd/

**Kiro IDE 1.0.309** はサブディレクトリの **AGENTS.md** を読み込めるようになりました。従来のIDEはルート直下や `~/.kiro/steering/` が中心で、CLIに先にあった階層別の対応がIDEにも加わった変更です。複数の技術スタックを持つモノレポで、全体の共通規約と各サービスの規約を分ける用途を想定しています。

著者はルートにTypeScriptのstrict modeやコミット規約を置き、API側にPrisma・zod・async/await、画面側にTailwind CSS・関数コンポーネント・named exportの指示を置きました。新しい会話ではルートが **Included Steering** として読み込まれます。一方、下位のAGENTS.mdは最初から全部ではなく、対象ディレクトリのファイルへアクセスした時点で追加されました。

APIのファイル作成ではraw SQLを使わず、画面側ではTailwind、named export、aria-labelなど、対象側の規約に沿う出力を確認しています。**読み取りだけでも下位ルールが追加される**点も試しました。ファイルの読み書きをきっかけに必要な指示を渡す動作であり、毎回依頼文に全規約を再掲しなくて済みます。

ただしこれは1.0.309での限定した動作確認です。あらゆる階層、矛盾するルール、別ツール経由のアクセスまで検証した記事ではありません。AGENTS.mdを読めたことと、すべての生成物が規約に従うことも別です。自分のリポジトリで読み込み表示と成果物を両方確かめ、型検査やレビューにつなげる材料になります。

**注目ポイント：★★★★★**

ルートの常時読み込みと、アクセス時の下位ルール追加を分け、モノレポの指示設計を具体的に説明できます。

### ② AI時代は「Go言語」が理想の言語に？ Googleが解説する「Goの価値」

**出典：＠IT**

**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2608/15/news013.html

＠ITはGoogleの見解として、AIが大量にコードを書く時代は、人が書く速さより **読む・検証する・保守する費用** が重要になると紹介しています。2ページにわたり、Goの構文だけでなく、統一された道具とチームで長く維持するための設計を論じています。言語間の同一課題による成功率や費用の比較実験ではありません。

一つ目の軸は静的型とコンパイルです。存在しないメソッドや型の不一致などを早く検出し、エージェントが修正して再検査する周期を短くする考え方です。**コンパイルに通ることは業務ロジックが正しい証明ではありません。** 境界条件や要求への適合は、別のテストと人の判断を必要とします。

二つ目は **gofmtによる表記の統一** と、単純で明示的な記述を重視する言語設計です。レビュー担当が個人ごとの書式を読み解く負担を減らし、意味を確認しやすくします。ただしgofmtは整形の道具で、複雑な設計や誤ったロジックを自動的に除くものではありません。原文の利点は、道具と設計思想を合わせた主張として読みます。

三つ目は標準ライブラリと **govulncheckなどの検証ツール** です。不要な外部依存を増やさず、既知の脆弱性に関係する利用箇所を調べる考え方で、あらゆる未知の欠陥を防ぐ保証ではありません。2ページ目は、一つの実装を動かす行為と、チームで長期間システムを維持する活動を分け、共通のツールチェーンと後方互換性の方針を重視しています。

面接では「AIにはGoが常に最適」と断定するより、生成コードの確認に必要なコンパイラ、整形、テスト、依存関係の検査が揃うかを説明できます。既存資産やチームの技術、配備先との適合を確かめることは応用上の判断で、この記事がすべての用途での優位を測ったという意味ではありません。[Googleの説明](https://developers.googleblog.com/why-go-is-an-ideal-language-for-ai-assisted-software-engineering/)も、数値比較とは区別して参照します。

**注目ポイント：★★★★★**

言語の選定を生成速度だけで考えず、型・整形・依存関係と保守を含む検証費用として説明できます。

### ③ AWS DevOps Agent Guardrail、ReadOnlyAccessをサポート

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/devops-agent-readonlyaccess-permission-guardrail/

**AWS DevOps Agent** の8月5日更新で、権限ガードレールが **ReadOnlyAccess** の全アクションに加え、Athenaの開始・停止と `kms:Decrypt` を許容できるようになりました。以前の8サービス別の追加権限表から整理された変更です。ここで重要なのは、**ガードレールが許す上限と、実行ロールに実際に付けた権限は別**という点です。

既定の **AIDevOpsAgentAccessPolicy** は許容範囲の一部のみを付与します。追加操作は明示的に有効化する必要があり、原文の引用仕様では、既定ポリシー外の許容操作は同じように検証済みではありません。利用者が対象リソースと適切な操作を評価し、範囲を絞る責任が残ります。ReadOnlyAccessという名前だけで、すべてのデータを見せてよいとは判断できません。

既定ポリシーも8月12日の **v10** で更新されました。削除なしで34アクションが追加され、内訳はCodeCommit25、Config2、Glue1、KMS6です。これはガードレールの拡張とは別の、既定で与える権限の変更です。新たに許容された操作すべてが既定ポリシーへ入ったわけではありません。

著者はReadOnlyAccessとAthenaのクエリ実行権限を付け、**Managed query results** を有効にしたワークグループでCloudTrailログを数えました。開始、SUCCEEDEDまでの確認、結果取得を経て **28,127,791件** を得ています。既定ポリシーにはないGetQueryExecutionやGetQueryResultsが使えた点を確認し、Bedrock AgentCoreの参照も追加前後で試しています。

この数値は対象テーブルの件数で、性能や精度の指標ではありません。実験条件はその権限と保存先設定に限定され、すべてのデータ取得を検証したわけではありません。実務では必要なアクションとリソースを個別に選び、クエリ開始だけでなく結果取得・復号まで通るか、見せてはいけないデータへ届かないかを確かめます。

**注目ポイント：★★★★★**

許容できる権限、既定の付与、明示的な追加を分け、Athenaの開始から結果取得まで追えます。

### ④ Claude Code Remote ControlのServer mode

**出典：Zenn**

**原文：** https://zenn.dev/0msys/articles/486b44b3af083d

著者はMac miniで作業し、iPhoneからClaude Codeを操作しています。既存の会話を `/remote-control` で公開する使い方では、別の作業を始めるたびにMacで会話を準備していました。**`claude remote-control` のServer mode** は対話を開くのではなく、接続を待ち、スマートフォン側から新しい会話を作れるサーバーとして動きます。

既定の同時セッション上限は32と紹介され、著者はiPhoneのコードタブから新規作成を確認しました。`same-dir` は全会話で同じディレクトリを共有し、**同じファイルの編集が衝突し得ます**。`worktree` は新しい会話にGit worktreeを作りますが、同じリポジトリ内の分離です。単一会話の `--spawn=session` もあり、1サーバーで任意の別プロジェクトを開く機能ではありません。

iPhone側にフォルダの表示やグルーピングがなく、同じホスト上のプロジェクトを判別しにくい問題もありました。著者は `--name`、`--remote-control-session-name-prefix`、**SessionStart hook** で自動命名を試しましたが、追加会話の名前を統一できませんでした。名前のオプションは最初の会話にしか効かず、prefixは明示名がない場合の自動名に使われます。

同じ場所でサーバーを再起動すると、停止から約4時間は以前の会話を復元するため、新しく指定した名前が使われない場合があります。著者は未使用のディレクトリで作成と復元を分けて確認しました。hookの値はログで受信・キャッシュされたものの、一覧に反映されず、子プロセスのprint起動が関係するという説明は推測のままです。

検証条件は半日ほどの個人利用に限定され、すべての端末・バージョンの命名機能を否定するものではありません。新規作成はできた一方、作者が確かめた範囲では手動改名が残ります。**新規作成、復元、共有ディレクトリ、worktree** を区別して調べることが、遠隔操作の誤解と編集衝突を減らす学習点です。

**注目ポイント：★★★★★**

遠隔接続を既存会話の操作だけと考えず、作成・復元・作業ディレクトリの違いで問題を切り分けられます。

### ⑤ GLM-5.3：Post-trainingでLong-horizon Codingを強化

**出典：gihyo.jp**

**原文：** https://gihyo.jp/article/2026/08/glm-5.3

Z.aiは8月14日、**GLM-5.3** を発表しました。GLM-5.2と同じ **743B** の基盤を使い、事後学習の環境・課題・計算を増やして改善したという説明です。短い問題より、性能低下の原因調査から修正・正しさの確認まで続く長時間の開発課題を重視しています。課題の生成・検証にはエージェントも使いますが、人の作業も残るとしています。

強化学習基盤 **slime** の改良で学習全体のスループットが2.3倍以上になったと報告しています。これは利用時の推論速度ではありません。公表された旧版との比較は、Terminal-Bench 3.0が4.6から28.3、DeepSWE v1.1が46.2から66.9、Agents' Last Examが23.8から28.5です。最後の評価ではGPT-5.6 Solの28.6に近い一方、すべての評価で上回ったわけではありません。

非公開のZ.ai Code Benchで約50%改善という主張は、公開ベンチマークとは区別します。サイバー評価は **CyberGymが77.2%から84.5%、ExploitBenchが24.4%から54.4%**。共同調査では専門家の確認と重複除外後に269のOSSから2,436件、うち1,097件がCriticalまたはHighと報告されていますが、記事には全件の再現情報や独立した追試はありません。

発表時はGLM Coding PlanやZCodeなどで利用でき、**重みは安全性評価後、2週間後に公開する予定**でした。発表時点で配布済みの重みと扱わないことが重要です。利用枠は入力、キャッシュ済み入力、出力で計算するポイント制へ移り、平日14〜18時のUTC+8がピーク、それ以外は消費ポイント50%と説明しています。

APIの **`reasoning_effort` はlow・high・max、既定はmax** で、推論を無効にはできません。ベンダーの評価と提供予定を整理した記事であり、同一モデル規模でも事後学習で能力が変わることを学べます。ただし、学習効率、コード品質、脆弱性分析、利用料金は別の指標で、ひとつの改善率にまとめてはいけません。

**注目ポイント：★★★★★**

同じ基盤モデルでの事後学習の効果と、学習速度・推論設定・提供予定を分けて読み取れます。

## 4. 今日の技術テーマ

### 「対応している」と「この条件で使えた」を分ける

指示や権限は、設定を書くだけでは確認が終わりません。Kiroではファイルへのアクセス時に下位規約が読み込まれ、DevOps Agentではロールへの付与と結果保存先の設定が実行に影響します。Remote Controlでは新規作成と復元を混ぜると、命名オプションの効果を誤解します。

```text
仕様で可能な範囲 → 実際の設定 → 読み込み・実行の記録 → 成果物と結果の検証
```

GoのコンパイルやGLMの公表スコアも、それぞれが測る範囲を明確にします。型の整合、特定課題の成績、利用者の業務要件を一つの「品質」にまとめず、判断の根拠を説明できることが面接での強みになります。

## C-3. JLPT文法

### 1. ～にとどまらず
**Level：N1｜意味：** ある範囲だけでなく、さらに広い範囲にも及ぶこと。  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 前の範囲から後ろへ話題を広げます。  
**例：** `AGENTS.mdはCoding Styleにとどまらず、Validationや禁止事項まで定義できます。`  
**補足：** 前の範囲から後ろへ話題を広げます。

### 2. ～かねない
**Level：N1｜意味：** 望ましくない事態が起こる可能性があること。  
**形：** `動詞ます形から「ます」を取る + かねない`  
**使い方：** 動詞のます形から「ます」を除いて付けます。通常は悪い結果に使います。  
**例：** `複数Agentが同じFileを同時に変更すると、大きな競合を招きかねません。`  
**補足：** 動詞のます形から「ます」を除いて付けます。通常は悪い結果に使います。

### 3. ～なくしては
**Level：N1｜意味：** ある条件がなければ、後のことは実現しない。  
**形：** `名詞 + なくしては`  
**使い方：** 検証や権限確認を、必要な前提として強調する表現です。  
**例：** `DeterministicなValidationなくしては、AI Codingの品質を安定させるのは難しいです。`  
**補足：** 検証や権限確認を、必要な前提として強調する表現です。

### 4. ～に応じて
**Level：N2｜意味：** 条件や変化に合わせて、対応を変えること。  
**形：** `名詞 + に応じて`  
**使い方：** 名詞に接続し、条件と対応の関係を示します。
