### ① Claude Code × Slack：allow / ask / denyによるPermission Design

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/obsidian-claude-code-slack-permission-guardrails/

ObsidianとClaude Codeの連携記事は、Slackの会話をKanbanへ反映するためにMCPを接続した個人環境の設計です。情報収集が目的でも送信、予約投稿、canvas、下書き作成までツールが存在し、毎回の承認だけでは誤操作や確認疲れが残ることが背景です。著者は組織内の利用規則を踏まえ、取り消せるか、影響が広がるか、知識の保管方針と矛盾しないかで分類します。

**allow・ask・deny** の三層に分け、検索や読み取りはallow、送信やリアクションは確認、予約投稿・canvas・下書きはdenyとします。削除できるメッセージでも通知は取り消せないため、可逆と単純に扱いません。`settings.json` のpermissionsが実行可否を制御し、**CLAUDE.mdは理由と方針を伝える**役割です。文章で禁止を書くことだけを技術的な制限と同一視しません。

記事では評価順をdeny、ask、allowとし、ツール全体のdenyは一覧から外し、引数条件付きdenyはツールを残して該当呼び出しを止めると区別します。ただしツール名は接続方法で変わるため `/mcp` で実名を確認します。`.env`へのRead禁止や `Bash(rm *)` も例示されますが、個別の呼び出し規則を全ファイルアクセス経路の隔離保証へ拡張してはいけません。

重要なのは承認モードです。未指定ツールが通常モードで確認になる観察を、確認省略モードへそのまま持ち込めません。必ず確認したいツールはaskへ明示し、著者は `disableAutoMode` と `disableBypassPermissionsMode` も設定しています。`acceptEdits` はMCPの自動承認とは別ですが、ローカル編集や一部ファイル操作を許すため、自動実行されるフックの編集も考慮する必要があります。

同じ分類をBacklogにも適用し、読み取り35、削除等の禁止3、変更の確認20として棚卸ししています。接続日、範囲、権限と解除条件は `.claude/audit/` へ記録します。これは著者の構成例で、会社ごとの情報や方針に合わせた設計が必要です。承認回数を減らした実感は述べていますが、事故率を比較測定した記事ではありません。

**注目ポイント：★★★★★**

指示、実行権限、承認モードを分けて説明できます。

### ② Slack Code：Team DiscussionをCoding AgentのContextへ

**出典：Publickey**

**原文：** https://www.publickey1.jp/blog/26/slackaislack_code.html

Publickeyが紹介する **Slack Code** は、開発チームの会話にAIエージェントが加わり、議論を背景として実装を進める機能です。指示、途中の判断、進捗、結果を同じチームで共有し、担当者が会話を別の開発ツールへ手作業で転記する負担を減らす狙いがあります。

デモではダークモードに合わない購入ボタンの画像を投稿し、エージェントを呼ぶと作業用の **Code Channel** が作られます。元の会話を保ちながら修正を進め、色の判断が必要な場面でデザイナーを呼び、具体的な色の指示を受けてコードを変えます。Canvasに作業文書が作られ、ViewとCodeで表示結果とコードを確認する流れです。

記事時点の対応先はClaude Code、Claude Tag、Devin、GitHub Copilot、Vercel Agentで、ChatGPTは予定として区別されています。これは公開デモと製品発表であり、全員に同じ接続権限があることや、どのリポジトリでも同じ手順で公開できることを実測していません。

面接では、共有された会話から要求を受け取れても、デザイン判断や完成物の承認には人の役割が残る点を説明できます。チャンネルで見える進捗を、差分レビュー・テスト・公開判断と結び付ける運用が必要です。会話を理解する機能だけで品質やリリース権限が保証されるわけではありません。

**注目ポイント：★★★★★**

チームで共有する文脈と、人が決める設計判断をつなげて話せます。

### ③ Bun 1.4：Claude CodeがZig → Rust大規模Migrationに参加

**出典：Publickey**

**原文：** https://www.publickey1.jp/blog/26/rustbun_14nodejsplaywrightvitestcpu.html

**Bun 1.4** は、ZigからRustへの移植後の正式リリースとして紹介されています。重要なのは言語変更だけでなく、Node.js互換性、メモリ管理、起動、観測ツールの動作が改善された点です。公式はNode.js由来のテスト1,517件追加と2,900件超のissue修正を報告しますが、Node.jsと完全互換ではないことも明記しています。

Playwright、vitest、OpenTelemetryが動作するようになり、公式説明ではブラウザー操作、テストとcoverage、HTTP/fsのspan出力が具体例です。Next.js App RouterのSSRでfetchを使う際のGC保持循環も修正対象です。既存の開発・試験・監視を残したまま置換できるかが採用判断になります。

CPUの5分の1という値は、公式では小さなhello worldのアイドル負荷の条件です。メモリはPublickey本文の最大32%と埋め込み発表・公式冒頭の35%に差があり、一律の削減率にはできません。公式のHTTP試験でも64接続、通常100万リクエスト、Next.js/Viteは10万という条件で、サーバーごとに削減幅が異なります。アロケーターをmimallocへ揃え、アイドル中の回収等を改善した機構も説明されています。

原記事は正規表現最大281倍と起動4.8msも紹介しますが、短い記事には詳細な入力・環境条件がありません。再確認した正式資料のLinux hello.jsは5.1msで、異なる観測を同じ値に統合しません。これらをアプリ全体の速度保証にせず、自社の正規表現、起動処理、SSRの長時間メモリとテストを比較する必要があります。

補足確認：[Bun 1.4公式リリース](https://bun.com/blog/bun-v1.4)。数値の不一致と条件不足を明記したうえで、互換性と性能を別々に評価します。

**注目ポイント：★★★★★**

ランタイム移行を、互換性と条件付きの性能比較で説明できます。

### ⑤ 日本企業のAI投資は拡大、全社的な継続成果はなお限定的

**出典：＠IT**

**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2608/24/news047.html

＠ITは、アクセンチュアの **Pulse of Change** で、日本の投資意欲と成果実感に差があると報じました。一次発表の調査条件は2026年4～6月、20か国・19業種、経営層3,000人と従業員3,000人、日本は各100人です。経営層と従業員の回答は別の標本であり、日本企業すべての監査済み収益率ではありません。

日本の経営層で今後12か月のAI投資拡大は78%、世界82%。全社的かつ持続的な成果を既に得た回答は13%、世界23%です。従業員の生産性向上は57%対81%、満足度向上は48%対71%、日本の37%は生産性に変化なしと答えています。投資意欲、全社成果、個人の実感を同じ指標として足し合わせません。

リスキリングを自力で行う必要がある回答は日本50%・世界45%。経営層がAI人材の獲得・育成を難しいとする割合は64%対62%です。若手に求める技能の変化は87%対85%と近い一方、新しい若手職種を作る可能性は60%対73%、若手採用増の意向は41%対52%でした。認識と組織の具体的な対応を分ける必要があります。

アクセンチュアは、システムだけでなく仕事、人の役割、学習環境を一体で変える必要があると解釈しています。ただし自己申告の横断調査から、研修不足だけが成果差の原因だと証明したわけではありません。面接では、個人任せにせず業務の役割と支援を設計し、導入前後の成果と現場負担を測る方針へつなげられます。

調査条件の補足：[アクセンチュアの一次発表](https://prtimes.jp/main/html/rd/p/000000481.000019290.html)。

**注目ポイント：★★★★★**

投資意向と自己申告の成果を、調査の母数を残して読み分けられます。

1. Code Channelは作業を共有する場です。
2. デザインの決定を人へ戻す例があります。
3. 対応予定と提供済みのエージェントを分けます。

1. 言語の移植とアプリ互換性は別の証拠が必要です。
2. 小さなアイドル試験を本番CPUへ一般化しません。
3. 性能値の不一致は条件ごと残します。

## 4. Codex Usage過剰消費とMetering Reliability

1. リセットは原因修正と別の対応です。
2. 三パターンの具体的な内訳は原文にありません。
3. 過去の予定から現在の残量は判断できません。

## 5. 日本企業のAI投資は拡大、全社的な継続成果はなお限定的

1. 日本の経営層と従業員は各100人です。
2. 全社成果と個人の生産性実感は別設問です。
3. 調査の解釈を因果関係の証明にしません。

**文脈：** 「付与する」は権限を与えること、「制限する」は範囲を狭めることです。  
**例：** `Commandごとに必要な権限を設定します。`  
**ニュアンス：** 「付与する」は権限を与えること、「制限する」は範囲を狭めることです。

### 2. 利用量（りようりょう）
**品詞：** 名詞｜**意味：** サービスなどをどれだけ使ったかを示す量。｜**目安：N2**  
**コロケーション：** 利用量を集計する / 利用量を可視化する / 月間利用量

**例：** `Team別の利用量をDashboardで可視化します。`  
**ニュアンス：** 利用量のリセットと過剰消費の原因修正を分けます。

### 3. 生産性（せいさんせい）
**品詞：** 名詞｜**意味：** 投入した時間や資源に対して得られる成果の程度。｜**目安：N1**  
**コロケーション：** 開発生産性 / 生産性を高める / 生産性向上

## C-3. JLPT文法

### 1. ～に伴って
**Level：N1｜意味：** ある変化と一緒に別の変化が起こる。  
**形：** `名詞 + に伴って`  
**使い方：** AI利用の拡大と管理上の課題の関係を説明します。  
**例：** `Agent利用の普及に伴って、Meteringと監査の重要性も高まります。`  
**補足：** AI利用の拡大と管理上の課題の関係を説明します。

### 2. ～にとどまらず
**Level：N1｜意味：** ある範囲だけでなく、さらに広い範囲にも及ぶこと。  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 前の範囲から後ろへ話題を広げます。  
**例：** `AI TransformationはTool導入にとどまらず、業務Processや組織文化の変革まで含みます。`  
**補足：** 前の範囲から後ろへ話題を広げます。

### 3. ～なくしては
**Level：N1｜意味：** ある条件がなければ、後のことは実現しない。  
**形：** `名詞 + なくしては`  
**使い方：** 検証や権限確認を、必要な前提として強調する表現です。  
**例：** `継続的なTrainingなくしては、Agent利用を組織に定着させるのは難しいです。`  
**補足：** 検証や権限確認を、必要な前提として強調する表現です。

### 4. ～に応じて
**Level：N2｜意味：** 条件や変化に合わせて、対応を変えること。  
**形：** `名詞 + に応じて`  
**使い方：** 名詞に接続し、条件と対応の関係を示します。  
**例：** `利用量に応じてCostをTeamへ配賦します。`  
**補足：** 名詞に接続し、条件と対応の関係を示します。

### 5. ～一方で
**Level：N2｜意味：** 同じ事柄の、対照的な二つの側面を述べること。  
**形：** `普通形 + 一方で`  
**使い方：** 前後は逆の評価や異なる側面でもつなげられます。  
**例：** `自動許可は開発速度を上げる一方で、誤操作Riskも高めます。`  
**補足：** 前後は逆の評価や異なる側面でもつなげられます。

### 6. ～た上で
**Level：N2｜意味：** 先の行為を済ませ、それを前提として次を行う。  
**形：** `動詞た形 + 上で`  
**使い方：** 検証してから利用するという手順を述べます。  
**例：** `互換性とPerformanceを確認した上でBunへ移行します。`  
**補足：** 検証してから利用するという手順を述べます。

### 7. ～につれて
**Level：N2｜意味：** 一つの変化とともに、別の変化が進む。  
**形：** `動詞辞書形 / 名詞 + につれて`  
**使い方：** 利用する会話や機能が増え、管理の負担も変わることを述べます。  
**例：** `利用者が増えるにつれて、Permission管理も複雑になります。`  
**補足：** 利用する会話や機能が増え、管理の負担も変わることを述べます。
