### ① AIとGrafana Foundation SDKで進めるGrafanaダッシュボードのIaC化

**出典：DeNA Engineering｜2026年9月14日**  
**原文 URL：** https://engineering.dena.com/blog/2026/09/grafana-dashboard-iac-with-ai-typescript/

GrafanaのWeb UIはDashboardを素早く試作するには便利ですが、AIを継続的に活用する場合、変更を画面内だけに残すとReview、再利用、環境間の再現が難しくなります。DeNAはそこで **Grafana Foundation SDKのTypeScript版** を採用し、Dashboardを型付きCodeとして管理する形へ移行しました。基本FlowはTypeScript定義を変更し、`npm run build`でGit Sync向けJSONを作り、`npm run validate`とCIで検証し、PR Review後にmainへMergeしてGit Syncから反映するものです。CIではUID不足、空Panel、`gridPos`欠落、Git Sync必須Field、旧Data Source UID、`editable`設定など、TypeScript Compileだけでは拾えない生成物も確認します。

AI活用は2系統です。1つはMCPからGrafanaのData Source、Metric、既存Dashboardを参照し、PromQLやGrafana SDK Code案を作るFlow。もう1つはWeb UIでPrototypeを作ってJSONをExportし、AIにTypeScriptへ変換させるFlowです。本番の`mcp-grafana`へは直接公開せず、前段の`mcp-auth-proxy`でGitHub認証・認可を行います。Grafana側も用途別Service Accountを使い、通常の調査は **read-only** に限定します。AIの調査とDeployは別経路で、Production変更はBuild、Validation、PR、Git Syncを必須にしています。

**Evidence / Measurement：** 本記事はDeNAのRepository構成、Command、CI Rule、MCP Auth、Migration手順を具体的に示すImplementation Reportです。一方、開発時間が何％短縮したといったControlled Benchmarkはありません。TypeScriptもGoと厳密に性能比較した結果ではなく、既存JSONを扱う際のObject / Array表現との親和性から選ばれています。

**Evidence Boundary：ただし、** Type Checkで分かるのは型やPropertyの整合性までで、Metricの実在、PromQLの意図、Panelの見やすさは保証できません。Grafana上での表示確認が残ります。Git Syncの正式Supportはv13以降で、v12はexperimentalです。複雑な`gridPos`は手作業調整が必要な場合があり、新UIDで並行展開すると旧UID / Panel IDに紐づく手動Annotationも自動では引き継がれません。

**注目ポイント：★★★★★**  
AIへProduction DataのReadを許しながら、WriteをTyped IaC、CI、Human Review、Git Syncの後ろへ置く構成は、ObservabilityだけでなくTerraformやKubernetesのAgent設計にも応用できます。

### ② Anthropic、Claude Codeのプラグイン評価コマンド「claude plugin eval」を紹介

**出典：gihyo.jp｜2026年9月14日**  
**原文 URL：** https://gihyo.jp/article/2026/09/claude-plugin-eval

Claude Code **2.1.269以降**では、PluginやSkillが本当に付加価値を出しているかを測る`claude plugin eval`が利用できます。Pluginを入れた状態でTaskが成功しても、Model単体でも同じ結果を出せるなら、その成功をPlugin効果とは言えません。対象Folderで`claude plugin eval init`を実行すると、望ましいOutput、避けたいOutput、Sample PromptをClaudeと整理し、Test CaseとCriterionを作れます。Pattern Match、特定Tool Callの有無、別AI ModelによるGradingなどをCriterionにでき、Full EvalのCost見積もりも支援します。

`claude plugin eval`を実行すると、同一CaseをPluginあり・なしで比較します。Defaultではそれぞれ **3回ずつ**実行して平均Scoreを比較し、詳細はHTML Reportで確認できます。Quick Checkなら`--runs 1`、claude.aiへReportを保存せずLocalだけにしたい場合は`--no-publish`を指定できます。Plugin内のMCP Serverは自動起動されず、Real Serverを使うときは`--allow-real-servers`、Tool利用は`--allow-tools`で明示的に許可します。

**Evidence / Measurement：** ここでのEvidenceはVendor Benchmarkではなく、同一Test DistributionでのControl比較です。3回の反復はSampling Varianceを意識した設計で、PluginなしのBaselineを持つことでModel本来の能力とPlugin寄与を切り分けます。

**Evidence Boundary：ただし、** High Scoreは用意したTest Case内での結果です。未観測RepositoryやPromptへ自動的に一般化できません。Eval自体がToken / Plan Usage / API Costを消費し、HookやMCPはUser Permissionで動きます。そのためTrusted Plugin、Minimal Permission、Baseline、Multiple RunsをEval Harness側にも設計する必要があります。

**注目ポイント：★★★★★**  
Claude Code Skillを「作った」で終わらせず、**Control Groupを持つRegression Evalとして運用する**考え方を学べます。AI Coding Toolの品質管理として面接でも使いやすい題材です。

### ③ Amazon S3で「ストレージコスト80％削減」――たった6カ月で成功した“再現性のある方法”とは？

**出典：＠IT｜2026年9月14日**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/spv/2609/14/news027.html

WeatherBugはMulti-account AWS環境で数百のS3 Bucketを運用し、Data増加とともにStorage Costが上昇していました。課題は単に高価なStorage Classを使っていることではなく、支出要因を細かく把握できていなかったことです。S3 Storage Lensで調べると、Versioningを有効にしたBucketの半数超にLifecycle Policyがない、参照頻度の低いLogがS3 Standardに残る、Landing ZoneにExpiration Ruleがない、非Critical Dataに重複やCross-Region Replicationがある、といったSystemicな無駄が見つかりました。

Optimizationは **Visibility and Assessment → Quick Wins → Strategic Optimization** の3段階です。最初にS3 Storage Lensで利用実態を可視化し、Kiro CLIでAccess PatternとLifecycle候補の分析を支援させます。その後、不要DataのCleanupやAccess Patternに合わせたLifecycle管理へ進みます。WeatherBugはこの取組で **6カ月以内にStorage Costを80％削減** し、Data AccessibilityとOperational Stabilityは維持したと報告しています。AI Agentを直接Cleanup権限へ接続するのではなく、先にManual ReviewとVisibilityを作った点が重要です。

**Evidence / Measurement：** 80％はWeatherBug/AWSが公開したCustomer Case Resultです。元々Lifecycle未設定BucketやCold Log、Expiration不足、不要Replicationが存在していたという具体的なInitial Conditionがあります。したがって学ぶべきなのは数字そのものより、Visibility → Prioritization → Lifecycle → VerificationというProcessです。

**Evidence Boundary：ただし、** 単一企業Caseであり、全てのS3利用者が80％削減できるBenchmarkではありません。Retention、Compliance、Recovery、Access Frequency、Replication Requirementによって最適Policyは変わります。KiroがLifecycleを提案しても、Data OwnerとRecovery Requirementを確認せず自動適用するべきではありません。

**注目ポイント：★★★★★**  
FinOpsを「安いStorage Classへ移す作業」ではなく、**ObservabilityとAI RecommendationをPolicy / Verificationへ接続する継続Loop**として説明できます。

### ④ 「FDE」「ハーネス」「オープンウェイト」って何？　AI時代に現場で飛び交う10用語をGitHubが整理

**出典：＠IT｜2026年9月14日**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/spv/2609/14/news037.html

GitHubはAI開発で増えた用語を、単なるBuzzwordではなく実務Patternとして整理しています。特に **Harness** は、Modelの生成Textそのものではなく、その外側にあるTool、Permission、Memory、Context、Orchestrationなど、ModelをWorkflowの中で安全かつ有用に動かすSystemを指します。GitHub Copilotを例にすれば、ModelだけでなくCodebase、Editor、PR、Terminalへ接続する仕組みまでHarnessの一部です。Harness Engineeringは、この周辺Systemを設計・改善する仕事です。

**Loop Engineering** はAgentへ同じPromptを毎回手で投げるのではなく、Work取得 → Agent実行 → Output Validation → Stuck時にHuman Escalation、という反復可能なProcessを組む考え方です。GitHubはこれをAI-nativeなcron jobに近い例で説明しています。**Hill Climbing** はEvalを使い、例えばPR Review Agentが意味のあるBugを見つけられるか、RecommendationがUsefulかを測りながらHarnessを改善します。FDEはCustomer現場に入り、AI Tool、Automation、Agentを既存SystemとDelivery Flowへ統合するRoleです。

**Evidence / Measurement：** この記事は10用語のConceptual Guideであり、具体的な生産性Percentを競うBenchmarkではありません。ただ、従来「Prompt Engineering」と一括されていた仕事を、Loop、Harness、Eval、Role、Model Opennessへ分解するためのVocabularyとして有用です。

**Evidence Boundary：ただし、** GitHub自身も用語は進化中だと説明しており、一部は新しいPattern、一部は既存概念の言い換えです。Harnessという名前を付けただけでReliabilityが上がるわけではありません。ProductionではEval Metric、Permission Boundary、Failure Condition、Checkpoint、Escalation Ownerを別途定義する必要があります。

**注目ポイント：★★★★★**  
Agent Engineeringを説明するとき、Promptの巧拙ではなく、**Model外部Systemをどのように再現可能・観測可能・制御可能にするか**へ話を広げられます。

### ⑤ 「禁止したらシャドーITがなくなる」は幻想？　まん延するシンプルな理由

**出典：＠IT｜2026年9月15日 05:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/15/news010.html

Serviceを禁止して相談が来なくなっても、Usageまで消えたとは限りません。大容量File送信や外出先での資料確認など、現場の仕事は翌日も続きます。Approved Serviceの申請に2週間かかり、締切が明後日なら、現場は代替を自分で探します。一度「ダメ」とだけ言われると再相談の心理Costも上がり、結果として企業が失うのはShadow ITではなく **相談とUsage Visibility** になり得ます。

記事が引用するCybersecurity Cloudの調査は、業務で生成AIを使う会社員 **360人**が対象です。勤務先で生成AIを禁止された場合、**19.2％**が個人的に使い続ける、**18.6％**が会社へ利用継続を訴えると回答しました。記事が提案する改善は具体的で、禁止通知に「Approved Alternative」と「相談先」を加え、Consultation Countではなく実際に公認Serviceへ乗り換えた件数を測り、相談から回答まで何日かかったかも確認します。Formal Adoptionが後日でも、Case限定の暫定回答を早く返すことがShadow Usage抑止につながるという考えです。

**Evidence / Measurement：** SurveyはBan-only Policy下でも一部UserがUsageを続ける可能性を示すSignalで、運用側ではAlternative、Consultation Route、Response Timeという測定可能なControlへ落としています。Security Ruleを「周知したか」ではなく「Approved Routeへ移行できたか」で見る点が重要です。

**Evidence Boundary：ただし、** 母集団は既に生成AIを業務利用する360人であり、日本の全Employeeや全CompanyのShadow AI Rateを表すものではありません。Alternative + Consultationという施策もControlled Experimentで効果量を測定したものではなくPractitioner Guidanceです。実際の組織ではSSO、Proxy、CASB、AI GatewayなどのLogと合わせてAdoptionを確認する必要があります。

**注目ポイント：★★★★★**  
Security Governanceの目的を「禁止を守らせる」から、**安全な正規Routeを業務の時間軸で使える状態にする**へ置き換える視点が得られます。

## 4. 今日の技術テーマ

### Verifiable AI Execution Path —— AIが能力を持つことと、変更権限を持つことを分ける

本日の5記事は次のFlowでまとめられます。

```text
Observation / Context
        ↓
AI Proposal / Reasoning
        ↓
Harness
├─ Tool & Data Access
├─ Permission
├─ Baseline / Eval
├─ Validation
└─ Escalation
        ↓
Controlled Change Path
        ↓
Evidence / Cost / Adoption Metric
```

**仕組み：** AIは許可されたContextを読み、Proposalを作ります。そのProposalは直接Committed Stateにはせず、Type / Schema、Eval、CI、Human Review、Policy Gateなどを通します。DeNAのread-only MCP + Git Sync、Claude Plugin EvalのBaseline、S3のStorage Lens → Kiro → Lifecycle、Shadow AIのAlternative → Consultation → Migration Metricは、対象は違っても同じControl Patternです。

**メリット：** ModelやToolを入れ替えてもValidation Logicを再利用できます。Agentが高性能になってもWrite Scopeを無制限に広げる必要がありません。Failureが起きたときModel、Tool、Data、Policy、Human Processのどこが原因か分けやすくなります。

**制約：** Validationは定義した範囲しか守れません。Type CheckはPromQL Semanticを保証せず、Plugin EvalはTest Set外を保証せず、Storage Visibilityがあっても安全にDeleteできるとは限りません。実FailureとHuman FeedbackをEvalへ戻すContinuous Improvementが必要です。

**国内企業導入時の注意：** Agent / AI Workflowごとに `Read Scope / Write Scope / Validation / Human Owner / Evidence / Rollback` を明文化し、まずProposal-onlyまたはread-onlyでEvidenceを集めてからAction Scopeを広げるのが安全です。

# B. 重点サマリーと面接で使える知識

## 1. DeNA Grafana IaC
`mcp-grafana`でReal Metricを調査してもProduction Writeは許可せず、Grafana Foundation SDK TypeScript → Build → Validate → PR → Git Syncを正規Pathにする。Type SafetyとSemantic Validationを分けることが重要です。

## 2. Claude Code Plugin Eval
Pluginあり/なしを同じCaseで比較し、Default 3 runsでAverage Scoreを見る。MCPには`--allow-real-servers`と`--allow-tools`が必要。Eval Harness自身にもCostとPermissionがあります。

## 3. WeatherBug S3 FinOps
S3 Storage LensでVisibilityを作り、Kiro CLIでPatternを分析し、Lifecycleへ反映する。6カ月80％削減はCase Resultであり、再現すべきはPercentではなくProcessです。

## 4. Harness / Loop Engineering
HarnessはTool / Permission / Memory / Context / Orchestration、Loop EngineeringはFetch / Execute / Validate / Escalateを反復可能にする設計。Prompt単体よりSystem Boundaryを扱います。

## 5. Shadow AI
Ban-only PolicyはConsultationを減らす可能性がある。Alternative、相談先、Migration Count、Response DaysをGovernance KPIにして、Approved Routeを現場の時間軸で利用可能にする必要があります。

## C-3. JLPT文法（7）

1. **～にとどまらず｜N1**：ある範囲だけでなくさらに広がる。例：`AIはCode生成にとどまらず、実Dataの調査にも使われています。`
2. **～たうえで｜N2**：前Actionを完了・確認した後。例：`生成物を検証したうえで、Git Syncから本番へ反映します。`
3. **～に応じて｜N2**：条件に合わせて。例：`Access Patternに応じてStorage ClassとLifecycleを選びます。`
4. **～とは限らない｜N2**：必ずそうとは言えない。例：`ある企業で80％削減できても、自社で同じ効果が出るとは限りません。`
5. **～を踏まえて｜N1**：FactやResultを根拠にして。例：`Pluginあり・なしのScore差を踏まえて、改善点を決めます。`
6. **～かねない｜N1**：望ましくない結果になる可能性がある。例：`代替手段を示さず禁止すると、利用が見えない場所へ移りかねません。`
7. **～一方で｜N2**：対照的な別側面を示す。例：`Agentは反復作業を減らせる一方で、Permission設計が不十分だとRiskが増えます。`
