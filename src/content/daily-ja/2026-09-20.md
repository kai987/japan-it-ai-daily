### 1. [アップデート] Amazon Quick で画像やプロンプトからBI画面を自動生成できるようになったので試してみた

**出典：DevelopersIO｜2026年9月20日**  
**原文 URL：** https://dev.classmethod.jp/articles/20260919-amazon-quick-generate-sheets-and-analysis-from-an-image/

Amazon Quickの`Generate Sheet`は、既存Analysisを作り直さずにSheetを1枚追加します。Prompt上限は **280文字**で、完全な`Generate Analysis`の **1,400文字**より短く、要件を絞る必要があります。作者はSuperstore注文Dataを東京とバージニア北部で検証しました。What's Newでは利用可能Region全体でGAとされていた一方、観測時の東京ではGenerate Sheetの入口が見えず、北バージニアでは表示されました。画像を添付する`Add image`は東京でも確認されています。

日本語Promptでは5 Visualを作れたものの、Sales $23.14MとProfit $3.68Mから **529.43%** を算出してYoYのように説明し、Average Profitの軸をProfit MarginとするSemanticなずれがありました。明示したFilter ControlとCalculated Fieldは日本語・英語とも **0件**です。一方、1600×1000のLegacy BI風画像からは **9 Visual・5 Control** と`profit_ratio`を生成しましたが、3 Tabは1 Sheetへ集約され、2本のYoY Lineは1本になり、KPIの集計範囲も元画像と一致しませんでした。

**Evidenceは作者のHands-onです。** UI自身も「Generated analyses should be reviewed before publishing」と案内しています。**ただし、** Superstoreを使った少数の生成であり、一般的なAccuracy Benchmarkではありません。業務利用では見た目ではなくMeasure、Aggregation、Filter、Calculated Field、Date Grain、Sheet構成を元仕様と照合してから公開する必要があります。

**注目ポイント：★★★★★**  
生成BIは「Screenshotを似せるAI」ではなく、**設定と意味を復元するMigration Tool**として評価すると設計判断が明確になります。

### 2. NemoHermes の LLM ルーティングに使っている NeMo Switchyard の Classifier を TypeSafe の Jev に替えて計測してみた

**出典：DevelopersIO｜2026年9月20日**  
**原文 URL：** https://dev.classmethod.jp/articles/reona-dgx-spark-switchyard-jev-classifier/

NemoHermesではNeMo SwitchyardのLLM JudgeがRequestをWeak/Strong Modelへ振り分けていましたが、ProductionではJudge 1回のMedianが約1.8秒で、1つのSlack Messageに3～4回の判定が走ります。そこで`type_safe_classifier`を使い、TypeSafeの **Jev** へ置換しました。13 Scenario×3回では、従来Judgeが期待どおり **36/39**、Jevは **39/39**。Executor生成時間を差し引いた「判定＋変換」のMedianは1.55秒から、Strong 0.27秒、Weak 0.42秒へ短縮しました。

Direct APIでも13×10＝130回を測り、全て期待一致、Median 0.514秒、p95 0.576秒でした。ただしDirect Pythonは呼ぶたびTLS接続を張り直す一方、SwitchyardはConnectionを再利用するため、両者のLatencyを同列には置けません。Jevは画像内容を見られず、画像は`(image)`へ置換されます。またRouting JSONLには選択ModelとToken数が残りますが、Label/ConfidenceはServer INFO Logだけで、判断理由を完全に追うには追加のLog設計が必要です。

**Evidenceは作者による小規模比較実測です。** **ただし、** 13 Scenarioは実Traffic全体を代表するBenchmarkではなく、Jevはearly accessでPriceやLimitが変わる可能性があります。実導入ではAccuracyにとどまらずP95/P99、Cost、External Data Boundary、Image Request、Auditabilityを評価し、Criteria変更時は同じEval SetでRegressionを取るべきです。

**注目ポイント：★★★★★**  
Routerの狭いDecisionを専用Classifierへ分離すると、Model能力の議論から **SLOを持てるComponent設計**へ進めます。

### 3. AI攻撃は「調べて対応」では間に合わない　ゼットスケーラーがSOCをAIエージェント化

**出典：キーマンズネット｜2026年9月20日**  
**原文 URL：** https://kn.itmedia.co.jp/kn/article/2609/20/2000001661/

Zscalerが打ち出すAgentic SOCは、Alert要約だけでなく **Triage → Root Cause Investigation → Judgment → Response Workflow** をAgentで接続します。Zero Trust Telemetryと第三者Security Dataを相関し、侵害Userの隔離、攻撃通信のBlock、Lateral Movementの抑止といったInline Controlまで対象です。同社はNetwork、Identity、Endpoint、Cloud、AIを横断する **1日7500億件規模**のZero Trust Transaction Telemetryを活用すると説明しています。

一方、自動Responseは調査支援とはRiskが違います。誤検知によって正当なUserやSystemを隔離すれば、そのAction自体がIncidentになります。まずEvidence GatheringとRoot Cause候補を自動化し、ActionのSeverityや可逆性に応じてHuman Approvalを残す設計が必要です。重大なActionほど、Evidence、Confidence、実行内容、Rollback、OwnerをAuditできる状態にします。

**EvidenceはVendor/Product発表を報じたものです。** **ただし、** 7500億件という規模はFalse Positive RateやMTTR改善を証明するBenchmarkではなく、記事にもAIが判断を誤る可能性が示されています。自治範囲は一律に広げず、実運用の誤検知率とRollback成功率に応じて段階的に広げるのが妥当です。

**注目ポイント：★★★★★**  
Security Agentでは「できるAction」より、**どのEvidenceでどこまで任せるか**が本番設計の中心です。

### 4. Amazon Bedrock AgentCore Runtime V2 の課金メモリがピーク後に縮小する挙動を USAGE_LOGS で観測してみた

**出典：DevelopersIO｜2026年9月19日（日付境界の補完）**  
**原文 URL：** https://dev.classmethod.jp/articles/amazon-bedrock-agentcore-runtime-v2-memory-usage-logs/

AgentCore Runtime V2のMemory Billingを理解するため、作者はOSのRSSではなく **USAGE_LOGS** の`agent.runtime.memory.gb_hours.used`を1秒粒度で記録しました。`ap-northeast-1`の同一V2 Imageで0/100/500/1000MBを確保し、GB-hoursをMB相当へ換算しています。1000MB確保後の課金換算Peakは約 **2839MB**。解放後は67秒で約1138MB、100秒で1027MB、300秒で876MB、**667秒後でも約796MB**でした。

Application側のVmRSSはBaseline約33MBで、667秒後の課金Memory約796MBとは約24倍の差があります。3 Sessionの`total mem_gb_hours`は **0.469416**。seq Sessionは実作業約15秒でも667秒の観測区間で課金Memoryが残り、Idle TailがCostへ効くことが分かります。Process RSSやTask実行秒数をBillingのProxyにすると、FinOps判断を誤る可能性があります。

**Evidenceは3 SessionのControlled Hands-onです。** **ただし、** 1つのImageと限定的なPatternなので24倍という比率を一般化できず、USAGE_LOGSの到着にも遅れがあります。本番ではSession長、同時実行、Peak Allocation、Idle Patternを再現したうえでGB-hoursを積算し、Task単位Costを求める必要があります。

**注目ポイント：★★★★★**  
Agent Runtimeでは内部Memoryより **Billing TelemetryをSource of Truthにする**というFinOpsの基本を具体的に学べます。

### 5. Claude Code v2.1.277〜v2.1.278 の主要アップデート - 待望の AGENTS.md 対応と TaskOutput ツールの削除

**出典：DevelopersIO｜2026年9月19日（日付境界の補完）**  
**原文 URL：** https://dev.classmethod.jp/articles/20260919-cc-updates-v2-1-278/

Claude Code v2.1.277は、Current/Parent DirectoryにCLAUDE.mdがない場合、 **AGENTS.md** をProject Instructionとして読むFallbackを追加しました。作者の一時Directory実測ではAGENTS.mdだけならInstructionが効き、Fileを退避すると効かなくなりました。さらにParentにCLAUDE.mdがある場合はChildのAGENTS.mdよりParentが優先され、`git init`でも上位探索は止まりません。**Bedrock・Vertex・Foundryでは当時未対応**というProvider Boundaryもあります。

同Versionでは`TaskOutput` Toolが削除され、Task結果は`Read`で扱う形へ移行しました。v2.1.278ではClaude API/EnterpriseとBedrock・Vertex・Foundry・GatewayでAuto mode classifierがServer-side既定になり、対象環境では`CLAUDE_CODE_AUTO_MODE_SERVER=0`でOpt-outできます。GatewayをEgress Boundaryとして扱う`CLAUDE_GATEWAY_PROXY_IS_EGRESS_BOUNDARY=1`やSandbox関連Security Fixも含まれるため、Upgradeは単一Feature追加ではなくBehavior Contract変更です。

**EvidenceはChangelogと作者Hands-onです。** **ただし、** Productivityを測った記事ではなく、ProviderとSettingによってFeature Availabilityも異なります。Team展開前に`/config`、`/status`、Instruction precedence、Removed Tool、Gateway、Sandboxを実環境でRegression Testしたうえで更新する必要があります。

**注目ポイント：★★★★★**  
Coding Agentを組織利用するなら、Version UpもApplication Runtimeと同じく **Behavior Regression**として扱うべきです。

## 4. 今日の技術テーマ：Evidence Before Commit

AIの能力をBusiness Actionへ直結させず、間にEvidence Layerを置くのが今日の共通設計です。Amazon QuickはGenerated Config、JevはRouting Decision、SOCはResponse Candidate、AgentCoreはCost Evidence、Claude CodeはRuntime Policyを扱います。それぞれに必要なValidationを定義したうえでCommit Authorityを分離します。

```text
Input / Context
      ↓
AI / Agent Execution
      ↓
Candidate Output
      ↓
Evidence Layer
├─ Semantic / Aggregation check
├─ Router accuracy + latency
├─ Security evidence + rollback
├─ Billing telemetry
└─ Runtime regression
      ↓
Commit Authority
      ↓
Business State
```

**メリット**は、ModelやProviderを変更してもEvidence Contractを再利用できることです。Action Riskに応じてHuman Gateを残せます。**一方で、** Evidenceも万能ではありません。単発生成、13 Scenario、Vendor Telemetry規模、3 Session、Changelogはいずれも特定条件のEvidenceです。日本企業で導入するなら、`Candidate Output / Independent Evidence / Side Effect / Rollback / Human Owner / Commit Condition`をWorkflowごとに明示したうえで、実測に応じて自治範囲を拡大します。

# B. 重要ポイントと面接で使える知識

## B-1. Amazon Quick生成BI
- Generate Sheetは280文字、画像Analysisは1,400文字で、入力経路と処理が異なります。
- 本Hands-onではText生成のFilter/Calculated Fieldが0件、画像生成は5 Control＋1 Calculated Fieldでした。
- 見た目が近くてもAggregation意味が違うため、MigrationはSemantic Reviewまで含めます。

## B-2. Jev Routing Classifier
- Narrow DecisionをGenerative LLM JudgeからDedicated Classifierへ分けるとLatency/CostをSLO化しやすくなります。
- 39/39は13 Scenario×3の範囲であり、Traffic全体のAccuracyではありません。
- JSONLにReasonが残らない制約があるため、MonitoringとAuditを別途設計します。

## B-3. Zscaler Agentic SOC
- Investigation AutomationとResponse Authorityは同じLevelで扱わないことが重要です。
- User隔離や通信遮断はSide Effectが大きく、Evidence・Rollback・Human Ownerが必要です。
- 7500億件/日というTelemetry規模とDetection Qualityは別指標です。

## B-4. AgentCore Runtime V2
- Billing Source of TruthはUSAGE_LOGSで、Process RSSをそのままProxyにできません。
- Peak後もIdle Billing Tailが残るため、Task処理時間だけでCostを見積もると過小評価し得ます。
- 実WorkloadでGB-hoursを計測したうえでCost per Taskへ落とし込みます。

## B-5. Claude Code v2.1.277–278
- AGENTS.mdはCLAUDE.mdが無い場合のFallbackであり、Parent CLAUDE.mdが優先されます。
- TaskOutput削除やAuto mode server-side DefaultはAutomation Behaviorを変えます。
