### 1. OpenAI、「GPT-6 Sol」と「GPT-6 Luna」公開　API料金は前世代の半額に

**出典：ITmedia NEWS｜2026年9月23日 09:12**  
**原文 URL：** https://www.itmedia.co.jp/news/article/2609/23/2000001674/

今回の発表で重要なのは、単に新Modelが2種類増えたことではなく、**GPT-6 Sol** と **GPT-6 Luna** のTask Envelopeを明確に分けた点である。Solは複雑なCoding、Agentic Workflow、難しいKnowledge Workを主対象とし、Lunaは高頻度で範囲の狭いFocused Taskを重視する。標準の短Context料金は100万Token当たりSolが入力**2ドル**・出力**10ドル**、Lunaが入力**0.10ドル**・出力**0.50ドル**。さらにCached Input readは**90％割引**になる。したがって、「最も賢いModelを全Taskへ固定する」のではなく、Taskの難易度と頻度に応じてRoutingする設計が現実的になる。

ただし、Prompt Cacheは安定したSystem Prompt、Tool Definition、長い共通Contextの再利用Costを下げる仕組みであり、Agent全体のCostを自動的に90％削減するわけではない。Tool Call、失敗Retry、長いOutput、Human Reviewは別のCostとして残る。Context Windowが大きいことに加えて、必要な情報だけをRetrievalし、古いContextを整理し、失敗時のFallback先を決める必要がある。Web/AI Appで使うなら、複雑なRepository変更はSol、高頻度の分類や整形はLunaから検証し、同じHarnessでTask Success、Latency、Cost-per-successを記録するのがよい。

**Evidence：** ITmedia NEWSとOpenAI公式発表で料金、Cache割引、役割分担を確認した。**一方で、公開BenchmarkはVendor Evaluationであり、自社Workloadの保証ではない。** 処理TierやContext条件で料金も変わり得るため、Production導入では同じTask Setを使って再測定する必要がある。

**注目ポイント：★★★★★**  
LLM選定を「Model名の比較」から「Task RoutingとEnd-to-End Costの設計」へ引き上げられる。

### 2. AIは新規開発より既存改修が苦手？より得意？　Android開発の実力を測る「Android Bench 2.0」が公開

**出典：窓の杜｜2026年9月22日 11:45**  
**原文 URL：** https://forest.watch.impress.co.jp/docs/news/2142521.html

Android Bench 2.0は、Coding Agentを短いBug fixだけで評価する方法では不十分になったことを受けて、**Long-Horizon Task（LHT）** を導入した。30件のTaskは、新規App、Dependency Upgrade、既存Appへの新機能追加、Cross-platformからAndroidへの移植を含む。上流のAndroid Developers Blogでは、Engineerなら数日から一週間かかるTaskを想定すると説明している。Pass/Failだけでなく **Continuous Scoring** を使うことで、一部Requirementを満たした実装やUIの達成度も評価できるようにした。

当時の最高組合せでもPass率は**28％**にとどまった。ここで注意すべきなのは、LeaderboardがBase Model単独ではなく、**ModelとProvider Agent/Harnessの組合せ**を測っていることである。Toolの設計、Prompt Cache、Context Windowing、実行環境がToken量や成功率に影響し得るため、Model名だけを抜き出して優劣を断定できない。新規開発より既存改修や移植で状態理解とRegression対応が増えることから、Long-Horizon Agentでは「途中でどこまで壊さずに進められるか」も重要になる。

**Evidence：** 窓の杜とAndroid Developers公式Blogで、30 Task、4カテゴリ、Continuous Scoring、28％という結果を確認した。**ただしAndroid特化のBenchmarkであり、Software Engineering全体を代表するわけではない。** 社内評価ではRepository固有の長期間Task、Human Handoff、Regression、Requirement Coverageを測る必要がある。

**注目ポイント：★★★★★**  
Coding Agent評価を「一発のCode生成」ではなく、数日規模の継続作業とHarness設計として説明できる。

### 3. たった1つの拡張機能で5つのWebブラウザーのAIを乗っ取れちゃう!?　「BragJack」脆弱性

**出典：窓の杜｜2026年9月22日 17:45**  
**原文 URL：** https://forest.watch.impress.co.jp/docs/serial/yajiuma/2142598.html

BragJackが示すのは、Browser AgentのTrust BoundaryがModelへのPromptだけでは完結しないことである。Forever Securityの研究では、1つの悪意あるChromium ExtensionからChrome Gemini Live、Perplexity Comet、Edge、Opera Neon、Claude in Chromeなど5種類のAgent surfaceを狙うChainを示した。**declarativeNetRequest** などのExtension機能を利用してResponse Securityの条件へ介入し、Trusted ContextへJavaScriptを持ち込んだ上で、Agentへ **Prompt Forcing** を行うという発想である。

Productごとに到達できるActionは異なり、History、Local File、Screenshot、さらに一部ではCamera/Microphoneまで含まれる。ChromeのCVE-2026-0628、EdgeのCVE-2026-55945は公開され、該当経路は修正済みと報告されている。ここで「Browser AIは全部危険」と一般化してはいけない。Demoは**悪意あるExtensionがInstallされ、必要な権限を与えられていること**が前提であり、修正状況もProductごとに違うためである。

**Evidence：** 窓の杜の記事とForever SecurityのCoordinated Disclosureを確認した。**実際の大規模侵害を示す統計ではなく、Security ResearchとしてのAttack Chainである。** 導入側はExtension Allowlist、Host/Network Permission、高Risk Actionの再認可、AgentがFile/History/Deviceへアクセスできる範囲を監査する必要がある。

**注目ポイント：★★★★★**  
Prompt Injection対策だけでなく、Browser PermissionとAction AuthorizationまでThreat Modelへ入れる理由を説明できる。

### 4. OpenAI、数学者の独立諮問グループと連携　内部モデルは「100件超の未解決問題を解決」

**出典：ITmedia NEWS｜2026年9月22日 11:49**  
**原文 URL：** https://www.itmedia.co.jp/news/article/2609/22/2000001671/

OpenAIは、8月28日にTrainingを開始した内部Modelが**100件超**の長年の未解決数学問題を解いたと主張している。技術的に重要なのは数字そのものより、その数字をどのEvidence Layerで扱うかである。未解決問題の「解決」は、ModelがProofらしいTextを生成しただけでは成立しない。既知Resultの引用、論理Gap、Attribution、専門家Review、形式検証、Independent Reproductionを段階的に確認する必要がある。

OpenAIはIASを拠点とする **Advisory Group on Mathematics and Artificial Intelligence（AGMAI）** と連携し、成果の意義、公表方法、研究Standardについて助言を受ける。MemberはOpenAIから報酬を受けず、自主的な提言や公開反論もできる一方で、OpenAI内部の数学研究Paceを指揮する役割ではない。このGovernanceは、強いClaimを出す際のAttributionやNegative Externalityへ対応する枠組みとして意義がある。しかし、独立Groupが存在することと、100件超の各Proofが独立に再現済みであることは同じではない。

**Evidence：** ITmedia NEWSとOpenAI公式発表を確認した。**「100件超」はOpenAIによる内部ModelのClaimで、独立Benchmarkの再現結果ではない。** 研究成果を評価するときは、Governance助言とProof Verificationを別のGateにするべきである。

**注目ポイント：★★★★☆**  
AI for Scienceで「成果が大きいほどValidationを弱めるのではなく、むしろ強くする」考え方を学べる。

### 5. ネットワーク障害による残業が「ほぼゼロ」に　情シス担当“実質2人”の病院は何を変えた？

**出典：＠IT｜2026年9月22日 11:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/22/news012.html

公立小浜病院では約**500台の電子カルテ端末**を運用する一方、Networkを実質的に支える情シスは約**2人**だった。従来は障害時に現場へ出向き、Switchや無線状況を逐一確認する必要があり、原因の切り分けと復旧が時間外まで続くことがあった。刷新では単にSwitchを交換するだけでなく、冗長化、Auto Recovery、無線最適化、24/365 Monitoring、Topology可視化を一体化し、少人数でも安定運用できるようにした。

具体的には **AT-SBx908 GEN2のVCS** でCoreを冗長化し、**AMF** で機器の集中管理と設定復旧、**AWC** で無線Channel/Powerを自動調整する。さらに **Net.Monitor 24/365** と **Vista Manager EX** を組み合わせて状態を遠隔から把握できるようにした。その結果、病院は原因特定時間が従来の**10分の1以下**になり、時間外の復旧作業も「ほぼゼロ」になったと報告している。複数VendorのRemote Maintenance回線も集約の方向で見直している。

**Evidence：** ＠ITのCustomer Caseであり、約500台、実質2人、10分の1以下、時間外復旧ほぼゼロという運用結果を確認した。**一方で、Control Studyではない。** Hardware Refresh、VCS、AMF、AWC、Monitoring、運用Serviceが同時に変わっており、一つのFeatureだけへ効果を帰属させることはできない。

**注目ポイント：★★★★★**  
日本企業の情シス・Infra面接で、少人数運用を人海戦術ではなくObservabilityとAutomationで改善する例として使える。

## 2. 今日の横断テーマ：CapabilityとProduction Readinessを分ける

5本に共通するのは、**能力が高いことと、安全かつ安定して運用できることは別である**という点だ。GPT-6のBenchmarkに加えて実TaskでCostを測る必要があり、Android Bench 2.0ではHarnessが成績へ影響する。BragJackはModelの外側にあるExtension Permissionを攻撃面として示し、数学AIは生成結果と独立検証を分ける必要性を示す。病院Networkでは、復旧Outcomeが複数の運用要素を組み合わせた結果として現れている。

Production Readinessを整理するなら、**Model / Algorithm → Harness / Runtime → Permission / Ownership → Evidence / Validation → Observability / Recovery** の順で確認すると分かりやすい。Modelが変わったとしても、Task Success、権限境界、Evidence、Rollbackという設計資産はそのまま再利用し得る。このように層を分けることで、Vendorの新発表へ過度に振り回されず、自社要件に応じて採用判断できる。

## 4. 今日の技術テーマ：Verified Execution Boundary

~~~text
Task / User Intent
      ↓
Model Selection
      ↓
Agent Harness / Runtime
      ↓
Permission & Ownership Boundary
      ↓
Validation / Independent Evidence
      ↓
Observability / Recovery
~~~

GPT-6はModel SelectionとCost、Android Bench 2.0はHarnessとLong-Horizon Evaluation、BragJackはPermission Boundary、数学AIはIndependent Evidence、病院NetworkはObservability/Recoveryを代表している。これらを一つのStackとして捉えると、AI Systemの失敗を「Modelが弱かった」で片付けず、どの層でContractが破れたかを切り分けられる。

この設計に加えて、各層へOwner、Metric、Rollback条件を定義することが重要である。例えばModel RouterはCost-per-success、Browser AgentはHigh-risk Actionの再認可、Research AIはIndependent Review、NetworkはMTTRを持つ。一方で、すべてのSystemへ同じMetricを適用するわけではない。Workloadに応じてGateを変えつつ、Evidenceの種類を明示する必要がある。

- ModelとHarnessの組合せ評価なので、Tool、Cache、Context処理を分離して分析する。

## B-3. BragJack
- Browser AgentではPromptだけでなくExtension PermissionとTrusted ContextがAttack Surfaceになる。
- Demoは悪意あるExtensionのInstallと権限付与が前提で、Productごとの修正状況も異なる。
- Security説明では「何が必要条件か」「どこまで修正済みか」を残し、過度な一般化を避ける。

## B-4. AI for Mathematics
- 「100件超」はOpenAIの内部Modelに関するClaimであり、独立再現済みBenchmarkとは別である。
- AGMAIの独立助言はAttributionや公表Normを改善するが、各ProofのValidationを代替しない。
- 生成結果、Expert Review、Formal Verification、Independent Reproductionを別々のGateとして扱う。

## B-5. Hospital Network
- VCS、AMF、AWC、24/365 Monitoring、Vista Manager EXを組み合わせ、少人数運用の復旧負荷を下げた。
- 原因特定10分の1以下、時間外復旧ほぼゼロは一つのCustomer Caseで、単一Featureの効果ではない。
- 情シス面接では、障害後の人手対応より「見える・切り分けられる・自動復旧できる」構成を優先する。
