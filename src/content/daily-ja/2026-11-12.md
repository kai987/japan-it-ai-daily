### 1. AIの望まない動作を減らしたのは、禁止でも依頼でもなく「していい範囲」を決める1文だった。Claude Codeの返事が英語になる問題で検証

**原文：** https://zenn.dev/murooka_az/articles/claude-reply-switches-to-english

**公開時刻：** 2026-11-12 09:13:04 JST

利用者には日本語で返す設定でも、作業ログや担当への指示が英語の会話では、短い進捗や長い報告まで英語になることがありました。記事はClaude Code 2.1.318とOpus 5.5のmedium設定で、実際の会話を英語の返事の直前まで戻し、CLAUDE.mdの一文を変えたときの返答を数えています。元の記録は保持し、コピーから同じ場面を各条件で100回再生しました。

元の文は英語を許す項目を列挙しており、100回のうち15回が英語でした。英語に引きずられないよう注意を足す条件は19回、許可の文を削る条件は7回でした。利用者が読む本文と、担当への指示やコードなどの成果物を読み手で区別する条件では1回でした。短い経過報告も利用者向けの範囲に含めるため、報告の長さに左右されにくい指示になります。

著者は両側のFisherの正確検定でも差を調べました。ただし、測定は主に一つの会話の一地点と一つのモデルに限られ、再生時には元のツールや思考過程の一部もありません。もう一つの場面では10回の再生で英語の返事自体を再現できず、条件の比較には使っていません。自分の運用では進捗と最終報告を別に観測し、言語設定を変えるたびに失敗例を同じ条件で比較する設計が考えられます。

### 2. Worker の結果を transfer で返したら写すより遅かった（Chromium で小さな配列 30 万個）

**原文：** https://zenn.dev/openedfile/articles/worker-transfer-small-buffers

**公開時刻：** 2026-11-12 08:00:06 JST

DXFビューアーは図面をWeb Workerで組み立て、座標などの型付き配列をpostMessageで描画側へ返します。記事が測った6.4 MBの図面には10万の画層があり、各描画単位に三つの配列があるため、受け渡す配列は30万個になりました。合計は2.4 MBでも、16、8、0バイトの小さい配列が大量に並ぶ形です。

Chromium 151で開いて描き終わるまでを測ると、すべてを転送リストに入れる方式の中央値は13.6秒でした。64 KB以上だけを移し、残りをコピーする方式は2.8秒でした。別の測定では64バイトの配列30万個を移すと約10.7秒、コピーでは約0.41秒で、移す場合の大半はWorker側でpostMessageを呼んでいる間にかかりました。転送すると送り手はそのArrayBufferを使えなくなるため、所有権も設計に関わります。

64 KBの分け目は、転送するオブジェクト数を上限付きにする判断です。64 MBを16 KBずつに分けた別条件では、むしろ転送の方が速く、同じ設定が最速とは限りません。WebKit 26.5では図面の両方式が約1.7秒で、測定機も別です。ただし原因となるChromium内部の処理は特定していません。採用時はデータの総量に加えて、バッファ数と大きさの分布を測ります。

**読む価値：** 転送リストの費用を総バイト数だけで見積もると外れる例として説明できます。

### 3. 【CSSだけ】スクロールでふわっと表示するアニメーションを作る

**原文：** https://zenn.dev/h_aso/articles/css-scroll-driven-animations-baseline

**公開時刻：** 2026-11-12 08:00:06 JST

カフェのサンプルページでは、要素が画面に入るとカードが見える演出や、ページの進捗を示すバーをCSSで組んでいます。animation-timelineにview()を指定すると要素と表示領域の位置関係で進み、scroll()ならスクロール位置に連動します。カードの開始と終了はanimation-rangeで指定します。Chrome 157で位置を変えると、透明度は0から中間値を経て1まで変わりました。

記事では、animationの一括指定より先にanimation-timelineを書いたとき、Chromeの実測でViewTimelineが時間基準のDocumentTimelineに戻りました。後から適用される一括指定がタイムラインもリセットするためです。また、背景を切り取る親にoverflow: hiddenを付けると、view()がその親を最寄りのスクロールコンテナとして参照しました。overflow: clipにした例ではページが基準になりました。

著者は通常の見た目を読みやすい白背景や表示済みのカードにして、@supportsと動きを減らす設定の条件を通った場合に演出を足しています。Firefox 149で未対応時の表示を、Chromeでは動きを減らす設定を確認しました。ただし、これは一つのデモの確認です。入れ子のスクロール領域、端末ごとの対応、実ページの負荷までは別に検証する必要があります。

**読む価値：** 演出の成立条件をCSSの宣言順とスクロール領域まで追い、見えない状態が残る失敗を説明できます。

### 4. Python 3.15の新プロファイラーTachyonの紹介

**原文：** https://gihyo.jp/article/2026/11/monthly-python-2611

**公開時刻：** 2026-11-12 09:00:00 JST

Python 3.15のTachyonは、実行中のコールスタックを外部から一定の間隔で採取する統計プロファイラーです。周期的に採れたスタックの分布から時間を使っている場所を推定します。profiling.samplingのrunは新たにスクリプトを実行し、attachはすでに動いているプロセスを計測します。

記事は素数判定と2秒の待機を同じスクリプトに置いて比較しました。ウォールクロックでは待機の行が約61％のサンプルを占め、CPUモードではその行が集計から外れて素数判定が上位になりました。pstatsのdirectはその行を実行していたサンプルを、cumulativeは呼び出し先を含むサンプルを示します。待ち時間を含む割合と、CPU実行中だけの割合は分母が異なります。

出力にはフレームグラフや行単位のヒートマップがあり、バイナリで保存した計測結果をreplayで別形式にできます。ただし、attachには対象と同じPythonマイナーバージョン、通常版とfree-threaded版の一致、OSの権限が必要です。短く終わる処理ではサンプルが足りず、記事の比率も実行ごとに変わるため、代表的な時間を確保して測定を繰り返します。

**読む価値：** 遅い処理が待ち時間かCPU負荷かを、同じプログラムを二通りに観測して説明できます。

### 5. 【日本株分析プラットフォーム】過去の株価の自動修正が、出来高の1株の違いで止まった話(前半): 四捨五入と切り捨て(2026-11-12)

**原文：** https://zenn.dev/stagea_tech/articles/20261112-pj8-devlog

**公開時刻：** 2026-11-12 09:21:24 JST

過去の株価を保守する自動処理では、訂正計画を反映する前に、参照データから期待値を計算し直して比較していました。11月9日の処理で147社2643行の計画ができましたが、同じ銘柄の七行で出来高が1株ずつ合わず、書き込み前に停止しました。始値、高値、安値、終値は一致していました。

株式併合と分割を考慮した当該銘柄の履歴では、参照値の出来高を10で割って今の基準へそろえます。計画作成は四捨五入、点検と保存済みデータは切り捨てでした。端数が0.5未満なら両方の結果は同じです。例えば23,113.5を整数にすると、前者は23,114、後者は23,113になり、端数が0.5以上の七行だけ差が表れました。

チームは計画側の規則をそろえ、点検の許容は広げませんでした。保存済みの入力で再実行したところ、2643行のうち差分は該当七行の出来高に限られ、反映後の確認と判定110項目、処理全体53項目の試験も通りました。ただし、この丸め規則は記事の参照データと既存履歴を照合した結果です。別のデータ源では定義を読み直し、境界値と更新範囲を独立に確かめます。

- 例文の意味：前に採ってから決まった時間が過ぎるたびに、実行中の呼び出しの流れを記録します。

### 2. 増える（ふえる）｜N5/N4
