### 1. キユーピー、AIで工場シミュレーションモデルの開発工数を8割削減　3つの壁をどう乗り越えた？

**出典：＠IT｜2026年9月22日 08:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/22/news009.html

対象は一般的なWeb開発ではなく、Siemensの **Tecnomatix Plant Simulation** と専用言語 **SimTalk** である。SimTalkは汎用的なProgramming LanguageではなくDomain Knowledgeが必要で、Plant Simulation自体もLocal GUI前提のため、Cloud上のAIがCodeを出すだけでは実行・検証・修正Loopを閉じられない。さらに専門TeamへKnowledgeが偏りやすく、組織展開の道筋も見えにくいという3つの課題があった。そこでキユーピーはCognition AIの **Devin** を採用し、DeNA AI Linkとともに「自然言語からSimulation Modelを構築できる状態」を目指した。

実装上の要点はCloud/Localの役割分離にある。Cloud版DevinへRule、専門用語辞書、手順Documentを蓄積し、つまずいた点をLearning Asset化する。一方、Plant Simulation上でしかできない実行と修正は **Devin CLI** へ切り出し、Error自動検出とTask別 **Playbook** を組み合わせることで、実行から修正までを一気通貫で回せる形にした。最新の小規模Modelでは、手作業なら8.5人日想定だった工数を**1.8人日**にし、**78.8％削減**したと報告されている。

**Evidence：** ＠ITによるキユーピー／DeNA AI Link事例の報道で、PoC条件と工数値が示されている。**ただし、制約は明確である。** 78.8％は現時点で**小規模な1シミュレーションModel**の実績であり、複数工場・大規模Model・異なる工程で再現された統計ではない。また、Local環境ではEngineerの関与も残る。本番展開では成功率、作り直し回数、Engineer介入時間、Model規模別の再現性を別KPIとして測る必要がある。

**注目ポイント：★★★★★**  
Agent Engineeringを「Promptの工夫」で終わらせず、GUIしかないTargetに対してCLI Boundary、Playbook、Knowledge Asset、Verification Loopをどう作るかという設計問題として話せる。

### 2. SpaceXAI、「Grok 4.7」発表　コーディングと知識労働向けで同社最高性能、価格は据え置き

**出典：ITmedia NEWS｜2026年9月22日 08:46**  
**原文 URL：** https://www.itmedia.co.jp/news/article/2609/22/2000001668/

Grok 4.7はGrok 4.6より大きなBase Modelを採用し、数時間かかる難しいTaskを多く含むMixで強化学習を長く回したと説明されている。Self VerificationやLong Contextの扱いを改善し、さらに **Grok Bot Harness** をNativeに理解するよう学習させた点が特徴である。提供面では同日からCursor、Grok Build、Grok APIに加え、第三者のCoding Harness、Model Router、Cloud Platformでも利用可能。API価格は100万Tokenあたり**入力2ドル・出力6ドルから**で、4.6と同価格・同速度を維持するとしている。

一方、Benchmarkは一枚岩ではない。CursorBench 4.0はGrok 4.7 xHighが**46.3％**でGrok 4.6の40.4％、GPT-5.6 Solの41.7％を上回るが、Fable 5.1の51.8％には届かない。Terminal-Bench 4.0は**38.0％**でFable 5.1の57.9％を下回り、HealthBench Professionalも最上位ではない。反対にEEBench 64.0％、Harvey Legal Agent Benchmark 19.6％は比較4 Modelで最高。安全性についてもHackerBench v0.3のRisky Dual-use Prompt通過率3.3％などが示された。

**Evidence：** ITmediaがSpaceXAIの公式発表・Benchmark表を整理したVendor発表ベースの情報。**ただし、Vendor Benchmarkをそのまま自社採用判断には使えない。** Effort設定、Harness、Task分布が異なり、Terminal/Health系では優位でない。自社Repositoryの長時間Coding Taskを固定Datasetにし、Task Success、人工修正、Latency、Cost-per-successを測る必要がある。

**注目ポイント：★★★★★**  
「新Modelが出たら切り替えるか」という面接質問に対し、総合順位ではなくBenchmark Conditionと自社Workloadを結ぶ評価設計を説明できる。

### 3. 【TypeSafe】出力を絞ればLLMも速くなる？ Gemini 3.8 Flash と Jev で同じ107ケースの速度・コストを比較してみた

**出典：DevelopersIO｜2026年9月21日（日付境界補完）**  
**原文 URL：** https://dev.classmethod.jp/articles/jev-vs-gemini-flash-cross-match/

検証した仮説は「Jevが速く安いのは文章を生成しないからで、生成LLMも出力を極小化すればいい勝負になるのではないか」である。前回と同じ架空値の**107ケース**、同じ英語Question、exact/semanticの2軸、閾値0.8、逐次実行を揃え、Gemini 3.8 Flash側はStructured Outputで2つの確率値だけ返すようにした。さらにGemini 3.8 FlashはThinkingを完全Offにできず、最小の **low** を指定。Network条件ではGeminiだけkeepaliveを使っており、Jevの前回測定よりむしろ有利な条件になっている。

結果は、精度だけ見ればGeminiに強みがある。ExactはJev **106/107（99.1％）**に対しGemini **107/107（100.0％）**、SemanticはJev **96/106（90.6％）**に対しGemini **101/106（95.3％）**。しかしLatency中央値は約**0.71秒 vs 1.64秒**、107ケース合計75.1秒 vs 200.8秒、Costは約**0.35円 vs 6.4円**だった。GeminiはVisible Outputが平均15.4 Tokenでも、Thinking Tokenを平均42.4消費している。つまり「出力を短くすれば内部処理もほぼ消える」という予想は外れた。

**Evidence：** Dataset・Question・閾値・実行方式・接続条件を公開した作者Hands-on比較。**ただし、107件の文字列照合Taskという限定Workloadであり、一般的LLM能力の順位ではない。** Geminiの確率はModel自身がTextとして出したSelf-reported値でCalibration保証もない。Semantic Accuracyを優先するならGeminiの方が良かったため、結論は勝者選定ではなくTask別Routingである。

**注目ポイント：★★★★★**  
「すべて生成LLMに寄せる」設計ではなく、判定・分類のTask Shapeに専用Modelを当てる理由を、Accuracy/Latency/Costの3軸で説明できる。

### 4. Amazon Bedrock で一般提供になった Moonshot AI の Kimi K3 を試してみた

**出典：DevelopersIO｜2026年9月21日（日付境界補完）**  
**原文 URL：** https://dev.classmethod.jp/articles/moonshot-ai-kimi-k3-bedrock/

Moonshot AIの **Kimi K3** はAmazon BedrockでGAとなり、2.8兆Parameter、Image Input、**100万Token Context Window**に対応する。Bedrock上ではOn-demandの裸Model IDでは呼べず、**Inference Profile**が必要。us-east-1ではglobalとUS Profileが見えるが、ap-northeast-1ではglobalだけが返るため、東京からは “global.moonshotai.kimi-k3” を指定する。Converseでは特に設定しなくてもReasoningが有効で、短い “Say ok” でもOutputの大半をReasoningが占めた。maxTokensを64に絞るとReasoningだけで上限へ達する例もあり、Token Budget設計が必要になる。

Explicit Prompt CacheはResponses / Chat Completions APIで利用でき、Checkpointは最低**1024 Token**、保持期間は最低**30分**。作者のSystem Prompt実測では2997 Input Token中2972 Tokenが1回目にCache Writeされ、2回目は同じ2972 TokenがCached Tokenとして読まれた。読み取り単価は通常Inputの1/10。ただし2回目はReasoning Tokenが163から463へ増えたためResponse Timeはむしろ長く、CacheによるLatency改善はこの測定では判断できない。

**Evidence：** DevelopersIOの実機Hands-onとAWS Model Card／Launch Blogの照合。**ただし、公式が記載するConverse多TurnのKnown Limitationは作者の単純な2 Turnでは再現しなかっただけで、解消を意味しない。** Agent Frameworkで使う場合はOpenAI互換API、Reasoning Block処理、Profile Routing、Cache Hit率を別々に検証すべきである。

**注目ポイント：★★★★★**  
Managed Modelを「呼べた」で終わらせず、API Surface、Region Routing、Reasoning Cost、Cache Policy、Known Limitationまで運用Contractへ落とす視点が得られる。

### 5. [アップデート] AWS Glue zero-ETL integration で同じテーブルへの二重書き込みが ConflictException で止まるようになったので試してみた

**出典：DevelopersIO｜2026年9月21日（日付境界補完）**  
**原文 URL：** https://dev.classmethod.jp/articles/20260921-aws-glue-zero-etl-ownership-conflicts/

AWS Glue zero-ETL integrationでは、Target Table Propertiesに「どのIntegrationが所有しているか」を記録するようになった。Ownership Keyは **Target Resource ARN × Source Table Name** で、同じ組み合わせを同時に所有できるIntegrationは1本だけ。作者はap-northeast-1でDynamoDB単一TableをSource、S3 Bucketに紐づくGlue DatabaseをTargetとして検証し、Table Properties作成直後にはなかった “IntegrationArn” が、最初のIntegrationを作成してStatusがまだ **CREATING** の段階ですでに付与されることを確認した。

同一DynamoDB Tableから同一Glue Databaseへ2本目をcreate-integrationすると **ConflictException** で拒否され、Error MessageにはOwner Integration ARNが含まれた。ARNをdescribe-integrationsへ渡せば、競合相手のNameやCreated Timeまで追跡できる。新しいIntegrationArn FieldやListIntegrationTablePropertiesを扱うには **AWS CLI 2.36.45以降またはbotocore 1.43.94以降**が必要である。この変更は、実行後に二重書込みを観測するのではなく、Resource作成時に不正TopologyをBlockするControl Plane設計といえる。

**Evidence：** 作者Hands-onとAWS公式Document。**ただし、制約単位はあくまで同じTarget Resource ARN × Source Table Nameであり、Targetが違えば別組み合わせになる。** また同時変更の検出はCreate Conflictと同じ扱いではなく、すべてのConcurrency問題を解決する機能ではない。複数Team運用ではOwner Inventoryと更新手順を別途持つ必要がある。

**注目ポイント：★★★★★**  
Reliabilityを「Alertで早く気付く」だけでなく、Control PlaneのConstraintでInvalid Configurationを作れなくする設計として学べる。

## 4. 今日の技術テーマ：Execution Contract

5本を共通化すると、Agent/LLM/Data Pipelineの本番化では次のContractが必要になる。

~~~text
Task / Intent
    ↓
Execution Harness
├─ Runtime / CLI / Tool
├─ Model / API / Routing
├─ State / Ownership
└─ Domain Knowledge
    ↓
Preflight & Constraint
├─ Validation / Playbook
├─ Benchmark condition
├─ Cache / Token budget
└─ Conflict rejection
    ↓
Execution
    ↓
Evidence
    ↓
Commit / Scale
~~~

Harnessは「どう実行するか」、Constraintは「何を許さないか」、Evidenceは「本当に成立したか」を分ける。キユーピーはGUI実行をDevin CLIへ切り出し、Jev/Geminiは同一DatasetでRouting判断を作り、Kimi K3はAPI/Cache/ReasoningをContract化し、GlueはOwnershipをControl PlaneのConstraintへ昇格させた。

メリットはModelを差し替えてもDeterministicな運用Assetを残せる点にある。一方で、小規模PoC、Vendor Benchmark、単発Cache計測、限定的Ownership KeyのようにContractの前提自体が狭い場合もある。国内企業ではOwner、更新条件、Metric、Exception、Rollbackまで明文化して初めてScaleできる。

## B-5. Glue zero-ETL
- Target Resource ARN×Source Table NameがOwnership Keyとなり、2本目を作成時に拒否する。
