# A. 詳細版

トレースの取り込み、データ基盤の意味と権限、推論設定、会話の管理、エージェントのIDを扱います。運用上の改善では、変更を成立させる前提条件まで残します。

## 1. 今日読むべき5本

### ① Langfuse トレース取り込み処理の改善による ClickHouse の負荷低減

**出典：LayerX Engineering Blog**

**原文：** https://tech.layerx.co.jp/entry/langfuse-clickhouse-read-skip

LayerXはセルフホストの **LangfuseとClickHouse** で、トレース反映がピーク時に1日近く遅れる問題を調べました。顧客の操作へ直接影響する障害ではありませんが、プロンプト変更後の観測と改善が遅れます。Redisの待ち行列が増える一方、workerのCPUは30%台、ClickHouseは約60%で頭打ちで、**書き込み処理なのにEFSのDataReadIOBytesが増える**ことが手がかりでした。

取り込みではイベントをS3に保存してRedisへジョブを積み、workerが同じトレースのS3イベントを集めてマージします。さらにClickHouseの既存行を `project_id` と `id` で検索し、再度マージして書き込みます。**イベントごとのSELECTに `use_query_cache = false`** が付いており、集計を得意とするClickHouseに大量の一点検索が集中していました。

対策は **`LANGFUSE_SKIP_INGESTION_CLICKHOUSE_READ_MIN_PROJECT_CREATE_DATE`** に日付を設定し、それ以降に作られたプロジェクトの既存行読み取りを省くことです。成立条件は履歴をS3から再構成できること。v2から移行した環境では古いイベントがS3にないため、ClickHouseの既存行とのマージが必要です。LayerXは最初からv3を使い、S3オブジェクトを削除するライフサイクルルールも置いていないので、運用開始前の日付を指定できました。

変更後はRedisの滞留とメモリ使用が減り、workerは滞留を処理した後に以前の半分以下の負荷、ClickHouseのCPUは **一桁台** になりました。EFS読み取りも閑散時並みに落ち、その後にタスクを縮小しています。ただし削減額や普遍的な処理速度の倍率は示していません。これは一社の構成での前後観測で、全Langfuse環境へ同じ日付を入れてよいという話ではありません。

面接ではCPUの余裕だけで増強を決めず、待ち行列、ストレージI/O、実際のクエリを追った点を説明できます。不要な読み取りを除く前に、履歴の出どころと保持期間を確認することが、この改善を安全に適用する条件です。

**注目ポイント：★★★★★**

不要なSELECTを省ける履歴条件と、待ち行列・I/O・CPUのつながりを具体的に説明できます。

### ② Snowflake Cortex AI Gateway：Dynamic Model Routing

**出典：CodeZine**

**原文：** https://dev.classmethod.jp/articles/modern-data-stack-info-summary-20260819/

DevelopersIOの隔週まとめは、**Modern Data Stack** の製品発表と論考を選んで紹介する記事です。網羅的な調査や同条件の製品比較ではありません。共通する問題は、エージェントへ大量のデータを渡すだけでなく、意味、権限、変更履歴、実行の責任をどう整理するかです。

冒頭の4論考は、オントロジーを用語集だけでなく検証・版管理を持つ仕組みにすること、エージェントの名前よりスキル・ツール・認証情報などの構成を管理すること、既存データ基盤の統制を再利用すること、**「売上」「顧客」の意味をセマンティックレイヤーで明示すること**を扱います。これらは論者の提案であり、外部APIの実行認可までデータ基盤だけで解決できるという主張にはしません。

Snowflakeでは **Cortex AI GatewayのDynamic Model Routing** と利用計量・予算管理の強化、DeepSeekやGLMの追加予定を紹介しています。一方、Native AppsでのCortex Agents/MCPと、**S3 TablesへのIceberg REST接続**はGAとして区別します。後者はGlue統合を経由せずSigV4で接続し、catalog-linked databaseやプライベート接続を使う構成です。社内コンテキスト層の事例も、データ量より指標の意味を揃える必要性を示しています。

BigQueryは **AI.SEARCH()と自動埋め込み管理がGA、Hybrid SearchはPublic Preview**。最大133倍は紹介元のスロット効率の主張で、すべての検索が133倍速いという測定ではありません。Databricksの **Smart RoutingはBetaで主にコード課題**を対象とし、30%以上の費用削減は提供者の評価です。モデルだけでなくハーネスを選ぶ話は将来構想です。Genie OneのSheets/Excel連携と、管理Icebergテーブルの外部共有GAは別の更新です。

DuckDB 2.0は秋の正式版に向けたプレビューで、サーバー利用、トリガー、VARIANT、非同期I/O、パーサーや保存形式がテーマです。MotherDuckは **Signup APIとFlights** によるアカウント準備・Python実行を紹介し、Dataformのremote MCPはリポジトリや変換処理を扱うGA機能として紹介されています。アカウント作成ができることを、無制限の課金権限と同一視しません。

BIではSigma Tenantsが組織単位の利用者・データ・コンテンツを分け、親側で管理するGA機能です。SigmaのWebhookはPublic Beta、MCPからワークブックを作る機能は予定です。**Omni Apps** は既存のセマンティックモデル、権限、行制御を引き継ぎ、外部通信を既定で制限する設計です。OpenMetadata 2.0.0-rc2はDEV/TESTでの検証募集で、本番用GAではありません。

面接で使う際は、一つの「データ基盤の進化」にまとめず、意味の共通化、接続、実行、課金、提供段階を分けます。数値の実験条件がこのまとめだけでは十分に示されないため、個別製品の採用には元の発表と自社の対象処理を追加確認する必要があります。

**注目ポイント：★★★★★**

GA・Beta・予定を区別し、意味の定義と実行権限が異なる設計課題だと話せます。

### ③ Claude Code effort：1 Requestあたりの推論量を制御

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/claude-code-effort-202608/

DevelopersIOは8月20日時点の公式資料を基に、Claude Codeの **effort** を整理しています。モデルを変えることは重みと単価の選択、effortは一つの応答へどれだけ処理をかけるかの調整です。対象は思考だけでなく、**説明文、ツール呼び出しと引数、thinking** を含みます。`/effort` やDesktopの画面から変更できると紹介しています。

段階はlow、medium、high、xhigh、max。lowは速度・費用を重視し、highは複雑な処理、xhighは長く続くエージェント課題、maxは最大限の分析という整理です。ただし対応する段階はモデルによって異なり、記事ではxhighとmaxの対象モデルを分けています。maxを選べば出力枠などすべてのサービス上限が消えるという意味ではありません。

**`output_config.effort` は要求単位**の設定です。会話途中で次の要求から変更できますが、一つの要求の前半だけlow、後半だけhighという部分指定ではありません。原文が参照する説明では、変更によってプロンプトの形が変わり、前のターンのキャッシュ接頭部を引き継げなくなります。長い会話で頻繁に切り替える場合は、キャッシュの効率も含めて考えます。

**thinking** は回答前に思考ブロックを使うかを制御し、adaptiveではeffortが思考の頻度や深さも含む全体の処理量を調整します。記事時点では新しいモデル群の既定オンと、旧モデルでadaptive指定する場合を分けています。これをeffortの別名や、モデルの置き換えと説明しません。

同じ依頼で約7倍のトークン差という値はAnthropicブログの例で、著者自身の多課題実測ではありません。トークン量が増えれば必ず正しいとも限らず、最小のeffortで要件を満たすか、待ち時間・利用量・成功条件を比較する材料です。対応表は記事の時点情報として扱います。

**注目ポイント：★★★★★**

モデル・effort・thinkingを分け、会話途中の変更とキャッシュの関係を説明できます。

### ④ Kiro IDEのAgent Focusモードでセッションのピン留めとCloud Sessionsが使えるようになったので確認してみた

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/kiro-agentfocus-pinning-cloudsession/

著者は **Kiro IDEのAgent Focus** で多数のプロジェクトを管理すると、重要な会話が一覧の下へ埋もれる問題を挙げます。v1.0.288の **Pin Session** と、v1.0.293の **Cloud Sessions Preview** を操作して改善を確認した記事です。画面上の動作確認であり、並行作業の生産性を量的に比較した実験ではありません。

セッションのメニューからPin Sessionを選ぶと、プロジェクトの折りたたみグループから外れ、レール上部へ固定されます。見つけやすくなる一方、**プロジェクト名が表示されなくなる**ため、名前だけでは出どころを判断しにくい場合があります。著者はRename Sessionで識別しやすい名を付けることを勧めています。

Cloud Sessionsではリポジトリを選び、Kiro Webのクラウド側の会話をIDEから管理・操作できます。ローカルと同様のエージェント・モデル選択欄があり、画面の行き来が減ります。ただし検証した範囲では**トリガー設定は管理できず**、すべてのWeb機能がIDEへ移ったわけではありません。

クラウド側もピン留めできますが、ローカルの固定会話へ混ざらず、それぞれの区画内で上部に置かれます。Previewと個人の操作確認という制約を残し、固定された位置だけで実行場所やプロジェクトを判断しないことが実務の学習点です。状態を見つけやすくするUIと、成果物の確認は別に行います。

**注目ポイント：★★★★★**

ピン留めで失われるプロジェクト表示と、ローカル・クラウドの区分を具体的に話せます。

### ⑤ AI Agent Identity：Agentを普通のBotとして扱えない理由

**出典：＠IT**

**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2608/20/news017.html

＠ITはSailPointのフィールドCTOに、**AIエージェントのID管理**を取材しています。定義済みの手順を動かすbotやRPAと違い、エージェントは与えられた権限から次の操作を選びます。そのため、人の資格情報をそのまま渡し、人と同じ自制を期待する管理では不十分という見解です。見出しの「良心」はこの運用リスクを表す比喩で、意識を実験で判定したものではありません。

一工程95%でも20工程では約35%になるという説明は、**各工程が独立に95%成功し、全工程成功を必要とする場合の例**です。`0.95^20` は約35.8%になります。原文は単純化した例で、実際のエージェントを20工程走らせた測定ではありません。相関、再試行、部分回復がある処理へ同じ比率を当てはめません。

取材では、多くの端末で使われるクライアント側と、業務処理を担うサーバー側を区別します。前者は人の作業を広げ、入力情報やプロンプト注入の管理が重要です。後者は業務の労働力として動き、**どの権限で何へアクセスしたか、目的どおりの行動か**を追います。まず役割と用途を可視化・分類してレジストリへ登録し、追加時に適した方針を適用することを提案しています。

ただし、クライアント側のリスクが高いという判断も、利用者が可能な操作や情報の扱いを理解しない場合があるという取材相手の見解で、全製品の比較順位ではありません。監督責任と継続的な観測を残す必要性が論点です。企業面接では、人のアカウントの延長として扱わず、役割、実行範囲、管理者、停止や見直しの責任を整理する設計へつなげられます。

**注目ポイント：★★★★★**

役割別のID管理と、工程成功率の計算例に必要な仮定を説明できます。

## 3. 面接で使えるポイント

### 話題1：LLMOps / Evaluation

**質問：**

> 書き込みが遅いのにCPUに余裕がある場合、何を調べますか。

**30秒回答：**

> 待ち行列と、裏で発生する読み取りを調べます。Langfuseの例はRedisが滞留し、ClickHouseへイベントごとにSELECTしていました。S3に全履歴がある条件で読み取りを省き、負荷を下げています。v2からの移行では古いイベントがない場合があるので、設定をまねる前に履歴の保存先と保持期間を確認します。EFSの読み取りが手がかりでした。

**関連Project（学習用）：** テスト用トレースの保存経路を図にし、S3と既存行で欠ける履歴がないかを比べる。

**キーワード：** `Langfuse` / `Redis` / `SELECT`

### 話題2：Model Routing / Cost

**質問：**

> エージェント向けのデータ基盤では、データ量以外に何を整えますか。

**30秒回答：**

> 指標の意味と、使ってよい範囲を整えます。記事のOmni Appsはセマンティックモデルと行レベルの権限を引き継ぎ、外部通信も制限する設計です。一方で、データの定義だけでは外部APIの実行認可は解決しません。売上や顧客の定義を揃えたうえで、接続先の操作権限と、各機能がGAかプレビューかを確認します。公開段階も判断に含めます。

**関連Project（学習用）：** 同じ指標の定義、データソース、権限、変更履歴を一枚の仕様にまとめる。

**キーワード：** `Omni Apps` / `セマンティックモデル` / `GA`

### 話題3：Claude Code / Cost

**質問：**

> 推論のeffortは、難しい場面ごとに細かく切り替えますか。

**30秒回答：**

> 必要な品質と、切り替えの費用を見て決めます。Claudeのoutput_config.effortは要求単位で、説明やツール引数にも影響します。会話の次の要求で変えられますが、記事ではキャッシュの接頭部を引き継げない点に注意しています。長い会話は設定を安定させ、同じ課題で成功率と待ち時間を比べます。同じ課題で費用と回答品質の両方を確かめます。

**関連Project（学習用）：** 同じ課題でeffortとキャッシュ条件を固定し、正しさと待ち時間を比較する。

**キーワード：** `output_config.effort` / `キャッシュ` / `ツール引数`

### 話題4：Multi-agent / Session

**質問：**

> 複数プロジェクトの会話を管理するとき、見落としをどう減らしますか。

**30秒回答：**

> 注目する会話を固定し、実行場所が分かる名前を付けます。KiroのPin Sessionは一覧上部に置けますが、プロジェクト名が消えるので改名が役立ちます。Cloud Sessionsは別の区画に固定され、Previewではトリガー管理も対象外です。表示位置だけで判断せず、対象のリポジトリと完了した成果物を確認します。表示順の固定と実行場所は別です。

**関連Project（学習用）：** 複数の検証会話にプロジェクトと実行場所が分かる名前を付け、状態を追う。

**キーワード：** `Kiro` / `Pin Session` / `Cloud Sessions`

### 話題5：Identity / Governance

**質問：**

> エージェントには、人と同じアカウント権限を渡してよいですか。

**30秒回答：**

> 役割と実行する操作に合わせて権限を分けます。SailPointの取材では、クライアント側とサーバー側を分類し、レジストリで把握する考え方を示しています。ただし、登録だけで安全になるわけではありません。誰の権限で何にアクセスしたかを追い、利用者が代理の行動を監督できる範囲かを継続して確認します。成功率の計算には、各工程が独立という仮定もあります。

**関連Project（学習用）：** 架空の代理を役割で分類し、所有者、必要権限、アクセス記録を整理する。

**キーワード：** `SailPoint` / `クライアント側` / `レジストリ`

## 4. 今日の技術テーマ

### 状態を引き継ぐ場所を確認する

LangfuseはS3の履歴から状態を再構成できたため、ClickHouseの読み取りを省けました。effortは変更するとキャッシュの前提が変わり、Kiroはピン留めするとプロジェクト名の表示が変わります。どれも「設定を変えた後も、必要な情報が残るか」が共通の確認点です。

```text
保存・表示される情報 → 変更する設定 → 引き継げる情報 → 失われる情報と補完方法
```

エージェントのIDやデータの意味も、名前があるだけでは十分ではありません。所有者、権限、定義、履歴がどこにあり、変更後もたどれるかを説明できることが運用判断につながります。

# B. 重要ポイントと面接で使える知識

## 1. Langfuse トレース取り込み処理の改善による ClickHouse の負荷低減

1. 書き込み経路の裏で既存行の読み取りが繰り返されていました。
2. S3に全履歴があることが省略の前提です。
3. CPU低下は観測結果で、全構成への適用や費用倍率は保証されません。

## C-3. JLPT文法

### 1. ～にとどまらず
**Level：N1｜意味：** ある範囲だけでなく、さらに広い範囲にも及ぶこと。  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 前の範囲から後ろへ話題を広げます。  
**例：** `LLMOpsはPrompt管理にとどまらず、TraceやEvaluationの運用まで含みます。`  
**補足：** 前の範囲から後ろへ話題を広げます。

### 2. ～かねない
**Level：N1｜意味：** 望ましくない事態が起こる可能性があること。  
**形：** `動詞ます形から「ます」を取る + かねない`  
**使い方：** 動詞のます形から「ます」を除いて付けます。通常は悪い結果に使います。  
**例：** `Agent Identityを記録しないと、責任の所在が不明確になりかねません。`  
**補足：** 動詞のます形から「ます」を除いて付けます。通常は悪い結果に使います。

### 3. ～なくしては
**Level：N1｜意味：** ある条件がなければ、後のことは実現しない。  
**形：** `名詞 + なくしては`  
**使い方：** 検証や権限確認を、必要な前提として強調する表現です。  
**例：** `Traceと継続的なEvaluationなくしては、LLM品質の改善は難しいです。`  
**補足：** 検証や権限確認を、必要な前提として強調する表現です。

### 4. ～に応じて
**Level：N2｜意味：** 条件や変化に合わせて、対応を変えること。  
**形：** `名詞 + に応じて`  
**使い方：** 名詞に接続し、条件と対応の関係を示します。  
**例：** `Taskの難易度に応じてModelとEffortを切り替えます。`  
**補足：** 名詞に接続し、条件と対応の関係を示します。

### 5. ～たうえで
**Level：N2｜意味：** 前のことを済ませ、それを前提として次の行動をすること。  
**形：** `動詞た形 + 上で`  
**使い方：** 単なる順序だけでなく、必要な準備・確認の意味を含みます。  
**例：** `複数Versionを評価したうえで、本番Promptを選択します。`  
**補足：** 単なる順序だけでなく、必要な準備・確認の意味を含みます。

### 6. ～一方で
**Level：N2｜意味：** 同じ事柄の、対照的な二つの側面を述べること。  
**形：** `普通形 + 一方で`  
**使い方：** 前後は逆の評価や異なる側面でもつなげられます。  
**例：** `高性能Modelは品質が高い一方で、CostとLatencyも大きくなります。`  
**補足：** 前後は逆の評価や異なる側面でもつなげられます。

### 7. ～につれて
**Level：N2｜意味：** 一つの変化とともに、別の変化が進む。  
**形：** `動詞辞書形 / 名詞 + につれて`  
**使い方：** 利用する会話や機能が増え、管理の負担も変わることを述べます。  
**例：** `Agent数が増えるにつれて、IdentityとSession Managementも複雑になります。`  
**補足：** 利用する会話や機能が増え、管理の負担も変わることを述べます。
