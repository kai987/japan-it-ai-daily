### 1. Claude Code のスキルを、Figma エージェントの中で動かせるか試した

**原文：** https://zenn.dev/akaringo1109/articles/figma-agent-skill-external-library

**公開時刻：** 2026-11-03 09:01:42 JST

デザイナーの普段の作業場所はFigmaであり、端末を開いてGitからスキルを更新すること自体が導入の壁になります。著者は、手順書・規則・Pythonをまとめた既存のClaude Codeスキルを、Figma内のエージェントへ移す実験をしました。確認期間は10月23〜25日で、業務での判定精度そのものは非公開です。「同じ手順を最後まで動かせた」という実装報告と、業務品質の評価を分けて読みます。

大きなスキルを単一Markdownへ詰めると、登録できる文字数と、最初にエージェントへ届くバイト数が別の制約になります。著者の観察では登録上限は65,536字、初期に届く量は約51,000バイトでした。そこで約6,500字の起動役だけを登録し、本体はキャンバスのテキストノードへ配置しました。最初のライブラリは7枠、43枚のカードと2表、388個のテキストノード、約27万字です。ここでいうライブラリは独自の資料置き場であり、Figma標準のコンポーネント共有機能ではありません。

起動役はPlugin APIでノードの名前・文字・順序を読み、実行環境で元のファイルを組み直してPythonを起動します。長い道具の戻り値は画面では省略されるため、AIに全文を書き写させず、Pythonが保存された戻り値を直接読みます。テキストの件数とFNV-1aという照合用ハッシュを両側で計算し、不一致なら停止します。ハッシュは転送された文字の一致を調べるもので、誰が書いたか、今回の最新読み取りかまで証明するものではありません。

手順を一度に全部渡す代わりに、Pythonが検査済みの成果物を見て次の一手だけを返します。実行環境が入れ替わったときはライブラリを読み直して再開する設計で、13分46秒後の再開例も報告されています。一方、戻り値の内部保存先は非公開仕様で、同じチャットに古い読み取りが残る場合も注意が必要です。ライブラリの編集者は実行コードを書き換えられ、記事のパス検査にも弱さが残るため、編集権限を保守担当へ絞る前提です。

実行時間は1回11〜27分で、圧縮して一つのスキルへ収めた版は約6分でした。ただし処理別の測定はなく、方式だけが遅延の原因だとは断定できません。モデルを利用者が選べないこと、本番の配置先と編集者が未確定であることも残る課題です。面接では、利用者の作業場所へ機能を移す利点と、再現性・更新管理・実行権限の負担を合わせて説明できます。

**読む価値：** スキルの移植を、入口の使いやすさだけでなく、読み取りの完全性・再開・保守権限まで含めて考えられます。

### 2. Claude Code で Haiku・Sonnet・Opus とエフォートを変えて22課題を解かせたら、差が出たのは実装より上流だった

**原文：** https://zenn.dev/okzaq/articles/claude-code-model-effort-bench

**公開時刻：** 2026-11-03 07:30:05 JST

著者は、架空の業務システムと部品資料を用いた22課題で、Claude Codeのモデルと推論に割く設定を比較しました。2026年10月、Windows、Claude Code 2.1.308、Max 5xでの測定です。Haiku・Sonnet・Opus 5.5と五つのエフォートを使い、長い四工程の比較だけは五設定へ絞っています。費用はCLIが出すAPI換算額で、定額プランの実支払額ではありません。

小さな実装9題では、medium以上の全モデルが満点でした。Haiku mediumの費用平均は0.10ドル、Opus highは1.18ドルですが、各設定の実行は1回です。実装は作業場所の外に置いた隠しテストで採点し、生成されたテストの力は、正しい実装を意図的に壊す変異テストでも調べています。単にエージェント自身のテストが緑になったかだけを見る評価ではありません。

大きい題材は、既存テストを含め約1.3万行の会員管理システムです。曖昧な要求と、要求書にない16個の業務規則を用意し、古い値の文書も混ぜています。文書三工程は各3回で、計画・仕様書・試験仕様の得点率はHaiku mediumが72・83・85%、Sonnet highが91・96・99%でした。各工程には著者が確定した入力を与えているため、上流の欠落が下流へ連鎖する量を測った実験ではありません。

詳しい仕様と220項目の試験仕様を渡した実装では、全設定が隠しテスト152件に合格しました。ただし変異体42個のうちOpus highが検出したのは39個で、ほかは42個です。これを「全工程で同じ品質」とは読めません。文書は別起動のOpusが採点し、45回分の再採点では項目一致率が96.0〜99.6%だった一方、計画の単回得点は最大8ポイント動きました。

別の18課題・設定ごと23回の集計では、SonnetとOpusをmaxにしてもxhighより満点率は上がらず、時間の中央値は2.5〜2.9倍でした。差は少数回なので「maxが悪い」とまでは言えず、xhighを大きい四工程で測ってもいません。架空の自作課題、少ない反復、共有Python環境の影響、採点基準の偏りも限界です。工程別に期待する成果と採点を先に決め、人の仕様レビューを残す、という使い方へつなげられます。

**読む価値：** 実装のテスト合格と、上流の仕様漏れを分けて評価するための具体的な比較条件を学べます。

### 3. Projectionという発想。WebViewの中にNative UIを投影して共存させる方法にたどり着いた

**原文：** https://zenn.dev/rdlabo/articles/webview-native-ui-projection

**公開時刻：** 2026-11-03 08:58:35 JST

WebViewの上に置いたネイティブUIは、CSSの重なり順やスクロールを共有しません。Webのモーダルで覆いたくても、z-indexを大きくするだけでは別レイヤーのネイティブビューを覆えない、というのが出発点です。著者は、iOSのUIKitによる本物のタブバーとWeb画面を共存させるProjectionという方式を示しています。

操作できるときはLive Native UIとして本物を表示し、モーダルの背後など操作できないときには、その画像をWeb ProjectionとしてDOM内へ置きます。画像を用意できない場合はWeb Fallbackへ切り替えます。ネイティブUI自体をDOMへ移すのではなく、操作不能な間の見た目を投影するため、画像の間はタップできないという境界が重要です。

切り替え前に撮影とWeb側の画像デコードを済ませます。iOSでは約60fpsの一フレーム間隔を目安に位置とサイズを観測し、3回続けて変わらなくなってから撮影します。ネイティブ側に同じ画像をつなぎとして置き、本物を隠す処理と合わせて行い、その後Web側で画像を表示します。requestAnimationFrameのタイミングで通知し、つなぎの画像を外すことで、空白フレームと半透明UIの二重表示を避ける設計です。

記事はiOS・Androidの広告追随やヘッダー下のクリッピングも示し、共通部分をMITライセンスのWebView Native UI Engineとして公開しています。対象はCapacitorとCordovaのプラグイン作者で、既存プラグインのAPIや業務処理を保った導入を意図しています。ただし著者のデモと実装説明であり、全端末での応答時間、アクセシビリティ、電力消費の比較結果は示されていません。自分のUIでは、画像化できる状態と操作を戻す条件を先に定義して確かめます。

**読む価値：** CSSで解ける範囲と、OSの描画・操作レイヤーを調整すべき範囲を説明できるフロントエンドの題材です。

### 4. Amazon Data FirehoseのLambda変換で、失敗・破棄したレコードがどこへ行くのか確かめてみた

**原文：** https://dev.classmethod.jp/articles/202611-mitsuguchi-firehose-to-lambda-kensho/

**公開時刻：** 2026-11-02 18:20:43 JST

Firehoseへ送信できても、Lambda変換後にどこへ残るかは結果によって違います。著者は東京リージョンの検証構成で、正常・意図的な破棄・レコードの変換失敗・関数の例外を分けて送りました。Python 3.12のLambdaは128MB、タイムアウト60秒で、Lambda向けとS3向けのバッファはそれぞれ1MB・60秒、呼び出し再試行は3回、変換前のバックアップは有効です。

正常なOkは変換後の保存先へJSON Linesで届きました。Droppedは正常先にもエラー先にも出ず、今回の設定では変換前のバックアップにだけ残りました。バックアップ無効時は未検証です。ProcessingFailedと不正なJSONは、元データをBase64で持つrawData付きのエラーファイルになり、どちらもLambda.ProcessingFailedStatus、試行回数は1でした。このコードだけでは二つの原因を区別できません。

一件だけ関数例外を起こしたバッチでは、正常な二件も含む三件すべてがエラー側へ入りました。エラーコードはLambda.FunctionErrorで、CloudWatch Logsでも初回と再試行3回、合計4回の呼び出しを確認しています。例外の詳しい内容はエラーファイルではなくLambdaのログで見る必要があります。レコードごとに失敗を返す設計と、関数を落として同じバッチを巻き込む設計の違いが見えます。

送信からS3への配信は、三回の検証で約80秒、126秒、139秒でした。各条件一回ずつの実測であり、バッファやバッチの大きさに依存するため、配信時間の保証には使えません。変換前バックアップも単純に連結され、変換後と同じJSON Linesではありません。再処理側で保存形式まで確かめる必要があります。

エラー先とバックアップには元データが残り、Base64は暗号化ではありません。アクセス権と保存期間、失敗の通知、再処理を本番設計として別に考えます。記事の例は、その検討のための故障注入実験であって、運用設計が完成したという証拠ではありません。

**読む価値：** レコード単位の失敗とバッチ全体の例外、受け付け成功と最終保存を分ける説明を練習できます。

### 5. GitHub ActionsのSHAピン留めを設定で強制する。何が止まるか、lockfileならタグのまま通せるかを試す

**原文：** https://dev.classmethod.jp/articles/github-actions-require-sha-pinning/

**公開時刻：** 2026-11-02 22:20:23 JST

レビューだけでアクションの参照漏れを防ぐのは難しいため、著者はGitHubのSHA固定を強制する設定を実験しました。11月2日のFreeアカウントの非公開リポジトリ、GitHubホストのubuntu-latest、pushでの結果です。タグとブランチ参照はジョブの準備段階で止まり、40桁のフルSHAは通りました。短縮SHAは、強制を無効にしていても使えないため、ポリシーだけの効果と混同しません。

外側のcomposite actionをフルSHAで指定しても、その内部のタグ参照は止まりました。再利用ワークフローの呼び出し自体はタグで通りましたが、呼ばれる内部のアクションにタグがあると失敗します。一方、同じリポジトリのローカルアクションやdocker形式のステップは対象外でした。「この設定で実行されるコードが全部固定される」という理解にはならない結果です。

gh actions-lock 0.4.0で対象ワークフローの依存をactions.lockへ登録すると、タグのままでもcomposite action内部を含めて通りました。これは実行時にロックしたコミットを取得するためで、未登録の別ワークフローは失敗したままです。古い0.2.0で作ったロックでは、内部が参照するタグと記録されたタグが食い違う問題があり、検査で不完全と判定され、ロックを作り直すと通ったと報告されています。

強制設定は違反を止めるもので、新しい版へ自動更新するものではありません。Dependabotが更新するのも登録済みワークフローの依存です。新規ワークフローの登録、更新差分のレビュー、組織ポリシーとの組み合わせは別に管理します。組織・Enterprise、一部の許可リスト、外部の再利用ワークフロー、セルフホスト環境などは今回未検証です。既存のフルSHA運用を捨てず、小さな範囲で適用境界を確認する判断につなげます。

**読む価値：** 依存固定の宣言、入れ子の実行依存、ポリシーの適用範囲を分けて説明できます。

### 4. Amazon Data FirehoseのLambda変換で、失敗・破棄したレコードがどこへ行くのか確かめてみた

**面接質問：**

> ストリーム変換の失敗を、どの単位で扱うか説明してください。

**約30秒回答：**

> レコードごとの失敗と、関数全体の例外を分けます。Firehoseの検証では、ProcessingFailedは該当データをエラー側へ残しましたが、Lambdaが例外で落ちると同じバッチの正常データも巻き込まれ、初回と再試行で4回呼ばれました。Droppedは今回の有効なバックアップにだけ残っています。ただし各条件一回の結果なので、保存設定と再処理の単位を自分の構成でも確かめます。
