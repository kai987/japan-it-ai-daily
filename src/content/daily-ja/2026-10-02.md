### 1. Claude Code v2.1.286 の主要アップデート - --bare の変更とプラグインの npm ソース制限

**原文：** https://dev.classmethod.jp/articles/20261001-cc-updates-v2-1-286/

**公開時刻：** 2026-10-01 19:03:20 JST

Claude Code v2.1.286の変更点を整理し、プラグインの取得方法を試した記事です。88件の変更の内訳は筆者の分類で、互換性全体を測った数字ではありません。--bareではコマンドラインに指定したMCPサーバーだけへ接続し、system remindersとバックグラウンドタスクを使わなくなります。タイムアウトしたshellも停止します。以前の暗黙の接続やバックグラウンド化に頼るCIは、起動条件の見直しが必要です。

実測はCLAUDE_CONFIG_DIRを一時ディレクトリへ向け、同じmarketplaceに三つの取得方法を登録して行っています。claude plugin validateは通過しましたが、npmソースのfile:とgithub:はインストール時に終了コード1で拒否され、相対パスは成功しました。git+https:も拒否されたと報告しています。ただし、これはすべてのローカル・Gitプラグインを禁止する意味ではありません。エラーにはregistry packageとtarballのリンクが挙がり、Git取得用の別のsource種別も案内されています。

verifyスキルの実行指示、セッション履歴の修復、同じtierの前モデルへの一度のリトライ、認証情報のマスキング修正も紹介されています。これらは変更履歴に基づく説明で、すべてを筆者が実測したわけではありません。依存関係をregistryからだけ取得する制限は今回未検証です。面接では、構文の検証、実際のインストール、既存スクリプトの動作を別の証拠として扱う理由を、この事例から具体的に説明できます。

### 2. DevOps AgentにMCPサーバーを追加してEC2のOS調査をしてみた

**原文：** https://dev.classmethod.jp/articles/devops-agent-mcp-ec2-os-investigation/

**公開時刻：** 2026-10-01 14:21:12 JST

DevOps AgentのInvestigationは、環境を変えないためにEC2内の任意のコマンドを実行できません。OSのプロセスやログをCloudWatchへ送っていない場合、調査の材料が不足します。Directed ActionsはSSM Documentを使えますが、操作ごとの承認が必要です。筆者はMCPを追加し、調べる種類とインスタンスだけをAgentに選ばせる形を試しました。

MCPサーバーはAWS_IAM認証のLambda Function URLで公開し、SigV4で接続します。LambdaだけがSSM Run Commandを呼び、SSM Documentに固定した処理をEC2で実行します。AgentへSSM権限を直接渡さず、Lambdaの実行ロールも対象Documentへ限定しています。七つの調査をallowedValuesで選び、targetとlimitにはallowedPatternを設けます。READ_ONLYへの分類は利用者の責務で、名前だけで任意実行を安全にする仕組みではありません。

実験はAmazon Linux 2023上でyesをreport-batchという名前にして二本動かし、CPU負荷を作っています。MCPなしの調査では今回取得したOS情報から原因を特定できず、以前の調査に由来する仮説と事実を区別しています。MCPを追加するとプロセスを特定でき、Run Commandの履歴も残りました。その後の停止とCPU回復は別のエージェントアクションです。参照ツールが停止まで行ったと説明すると、権限の境界を取り違えます。

ただし、結果は人工的な一障害の確認です。Windowsへの拡張、一般的な原因特定率、応答時間は検証していません。実務での確認事項として、対象インスタンス、引数、ログに含まれる情報を整理できます。観測は限定したツール、変更は別の承認という構成を説明できることが、面接での学習価値です。

**読む価値：** 情報収集と環境変更の権限を分け、推測と実際に取得したOS情報の違いを説明できます。

### 3. AI に伴走してもらうチームマネジメントの試み

**原文：** https://tech.layerx.co.jp/entry/ai-empowered-team-management

**公開時刻：** 2026-10-01 11:00:05 JST

一人のEngineering ManagerがAIとともにチームを見渡した半年の実践報告です。前後の半期でPRマージは1,982から5,326へ増えていますが、これは活動量の記録です。AIだけの因果効果を測った比較ではありません。対象となる4〜9月のチームは13〜20人で、メンバーの参加時期や並行するプロジェクトの増加も、観測すべき情報を増やしています。

個人アプリはObsidianの専用Vaultへ.mdを集め、Claude Codeなどから読み取る構成です。収集はskillとtool、定期実行はClaude CodeやShepherdのroutineを使い、1on1のaction itemはローカルのTodoへ登録します。Webのviewerも会話の参考に使います。狙いは判断を丸ごと任せることではなく、日々の活動を整理して、OKRやアサイン、称賛を話すきっかけを増やすことです。

一方で、機密の会議や会話は対象外で、収集が失敗して気づかないこともあります。不定期の1on1が一か月空く場合や、プロジェクトの理解が粗くなる課題も残りました。AIの提示は本人に確認する仮説として扱い、心理状態や負荷を確定したり、そのまま評価へ使ったりしません。metricsとalertの強化は改善案で、改善後の効果を実測した数字は示されていません。

データが作者のローカルだけにあることと、組織利用に適した基盤であることも別です。展開時には閲覧権限と常時稼働する収集基盤が必要になります。本稿の設計上の提案は、取得時刻と欠落を活動ビューへ示し、要約への信頼を観測の範囲に合わせることです。これは原文の既存機能だと断言するものではなく、面接で改善の理由を説明するための整理です。

**読む価値：** 情報を集める自動化と人事上の判断を分け、欠落した観測の扱いを具体的に説明できます。

### 4. TORCSのレースAIを122秒から106秒台へ：区間ごとの切り替え、衝突区間の特定、補正ネットワーク

**原文：** https://zenn.dev/sean_from_japan/articles/torcs-racing-ai-106s

**公開時刻：** 2026-10-01 21:03:47 JST

TORCSの特定コースを122秒台から106秒台へ詰めた開発記録です。全周を一組の定数で走ると、長い直線に合う速度と最終コーナーの減速が衝突します。筆者は単周の位置で速度の係数を切り替え、最終コーナーの後の直線では元へ戻し、最後は全開にしています。局所的な変更なら一つずつ外して比較できます。春のプロジェクトの振り返りで、汎用の運転能力を示すベンチマークではありません。

衝突した場所は、66区間の種類・半径・長さ・距離の表とdistRacedを照合して特定しました。急カーブを覆う2,339〜2,510mだけに71.4km/hの天井を置くと、108.692秒になっています。CMA-ESが探索したこの値は目標速度ではなく上限で、元の規則がもっと遅ければそのままです。全周を遅くするのではなく、壊れる帯の原因と対策を対応させています。

残差ネットワークは操舵を変えず、規則のアクセル・ブレーキへ最大0.2の補正を重ねます。23入力、32・32の中間層、1出力を使い、前回0.7と今回0.3でならします。出力層をゼロで初期化し、中間層は91,329件の模倣学習後に固定、ARSで出力層の33個だけを探索しています。約6.6時間・72回の評価で最良が106.630秒です。ただし、補正を小さくしたことは、未知の条件でも安全だという保証ではありません。

提出時は重みの.ptがGitの対象外で、TORCSやレース設定、gym_torcsの変更も環境ごとに違っていました。別PCでは約112秒で、原因のすべては切り分けていません。後からイメージを固定したDocker環境と九か所の変更をそろえると、Apple SiliconのMacで規則のみ108.538秒、補正あり107.082秒でした。106.63秒は最速の一回で、同じ値の再現でも平均でもありません。公開コードにはライセンスがないという注意も残し、重み・環境・繰り返し測定の必要性を面接で説明できます。

**読む価値：** 局所的な故障診断、制御則を残す学習、再現に必要な重みと環境をまとめて説明できます。

### 5. vCPUを減らせばVMが速くなる！？ Linux 7.4でマージが期待される“Steal Governor”

**原文：** https://gihyo.jp/article/2026/10/daily-linux-261001

**公開時刻：** 2026-10-01 11:41:00 JST

仮想環境では、割り当てたvCPUの数がそのまま実効性能になるとは限りません。ロックを保持したvCPUがhypervisorに奪われると、その処理だけでなく、待ち合わせる他のvCPUも進めなくなります。記事はOLTPとOLAPが混在するような、ロックやスレッドの依存が大きい処理を例に、二次的な損失を説明しています。

Steal Governorは各VMのsteal timeを調べ、長い場合にPreferred CPUの数を動的に減らすしくみです。優先して使うvCPUを絞り、競合や待ち合わせを抑えます。他のVMと直接通信する方式でも、クラウドの契約CPU数を減らす操作でもありません。IBM Power向けから始まり、x86やs390でも効果が確認されたという説明がありますが、記事は測定条件と改善率を一覧で示していません。

開発者のコメントでは全VMへの協調的な展開が効果を引き出し、明示的なモジュール読み込みを求めています。一方で、単純にCPU時間を使う負荷には軽いリグレッションの可能性があります。CASとの比較は、実行環境の特徴をスケジューリングへ反映する考え方の整理で、両者を同じ条件で測った順位ではありません。

9月28日にtipツリーへキューイングされ、Linux 7.4のマージウィンドウへ提出される見込みという段階です。提供済み・標準有効だと説明しないことが重要です。本稿が提案する評価は、ロック依存の強い負荷と独立したCPU負荷を分け、steal time、待ち時間、処理量を比較することです。対象kernelとhypervisorも確かめ、記事にない改善率を付け足さず、面接ではCPU数と処理の進み方を分けて説明します。

**読む価値：** vCPUの割り当て数と実効性能を分け、ロック依存による二次的な損失を説明できます。

## C-2. IT/AI専門用語

1. **--bare（ベアモード）**：暗黙の接続やバックグラウンド処理を制限する実行形態。 既存CIの起動条件を照合する。

2. **SSM Document（エスエスエム・ドキュメント）**：インスタンスで実行する処理の定義。 本例ではコマンドを固定しIAMも限定する。

3. **Obsidian Vault（オブシディアン・ボルト）**：ノートを保存するまとまり。 本例はローカルのMarkdown資料。

4. **Residual Network（残差ネットワーク）**：基準出力への補正を学ぶネットワーク。 本例はアクセルだけを補正し操舵は変えない。

5. **Steal Time（スティールタイム）**：vCPUが実行可能でもホスト上で走れなかった時間。 ホストの過負荷を考える指標。

6. **Preferred CPU（優先CPU数）**：ゲスト内で優先して動かすCPUの数。 VMの契約スペックの変更ではない。

## C-3. 新規文法

過去51期の四表現と95文法identityを照合しました。原文にある新規は論理的前提を表す以上（は）の1件です。数値の以上とは区別します。既習文型は共有の復習層で補い、例文を替えて新規件数を増やしません。

### 1. ～以上（は）｜N2

- 意味：ある前提が成立するので、それに伴う判断や責任を示す。
- 接続：普通形＋以上（は）／名詞・な形容詞＋である以上（は）
- 使い方：前提を受けて義務や判断を続ける。数値の「以上」とは区別する。
- 原文出現形：実行する以上
- 原文根拠：[OS上でコマンドを実行する以上](https://dev.classmethod.jp/articles/devops-agent-mcp-ec2-os-investigation/)
- 独自例文：OS上で処理する以上、実行権限を限定します。
- 例文の意味：OSでの処理には権限を限定する責任が伴う。
- 注意：例文は独自の学習用文。READ_ONLYという分類だけで安全を保証しない。
