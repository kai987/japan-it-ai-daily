# A. 詳細版

指標の意味、既存仕様の網羅性、設定ファイルの管理、業務の自動化、Gitの整合性を扱います。AIに任せる前に、何を正しい状態とするかを明文化する一日です。

## 1. 今日読むべき5本

### ① SnowflakeにおけるAIエージェント向けの内部コンテキストレイヤーの構築

**出典：Snowflake**

**原文：** https://www.snowflake.com/ja/blog/snowflake-internal-context-layer-for-ai-agents/

Snowflakeの社内事例は、大量のテレメトリーがあっても、AIが業務上の意味を選べなければ正しいSQLにならないという問題から始まります。「アクティブ顧客」でも、30日以内のログイン、試用を除くクレジット消費、地域を考慮しないアカウント数では答えが変わります。原文はこれを単なるプロンプト不足ではなく、共通の定義を持たないデータ利用の問題として扱います。

**Semantic Views** は物理テーブルと利用者の間に、論理的な事実、ディメンション、指標、関係を定義します。説明、同義語、検証済みクエリも添えることで、エージェントが列を探してサンプルを読む探索を減らします。定義はdbtで版管理し、レビューとCI/CDを通し、よく使うダッシュボードや質問ログから評価問題を作ります。運用後の問い合わせも収集して定義を修正するため、最初にYAMLを書けば完成する設計ではありません。

性能面では、意味を整理しても数十億行の結合が自動で軽くなるわけではありません。個別の事前集計やDynamic Tablesを管理する負担に対し、**Semantic Materialization** で必要なディメンションと指標を宣言し、裏側で集計を維持します。例は地域別の `compute_spend` を `AGG(compute_spend)` で参照し、`MAX_STALENESS = '1 hour'` を許容します。鮮度と計算負荷の条件をセットで説明する必要があります。

原文の表記では2025年7月、データサイエンス向けエージェントは400人超・5,400件超の質問、広い社内コンテキスト層は5,600人超・32万件超のクエリに利用されました。これは利用規模で、正答率ではありません。紹介されるAtScaleのTPC-DSの40問で約20%から90%以上という結果は外部ベンチマークであり、この社内基盤の実測と混同できません。Apache Ossieによる定義交換も紹介されていますが、全クライアントの互換性を保証する話ではありません。

面接では、指標の定義を共通化する仕組みと、鮮度を許容して集計を速くする仕組みを分けて説明できます。利用者数だけで品質を判断せず、業務の正解を持つ評価問題と、集計の更新条件を確認するのが重要です。

**注目ポイント：★★★★★**

意味の正しさと集計の速さを、別々の設計条件として説明できます。

### ② Legacy Modernization：AIが「読んでいないもの」が最も危険

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/legacy-modernization-ai-spec-gap/

DevelopersIOのレガシー移行記事は、AIが作った新システムのテストに合格しても、元システムの機能が抜け落ちる問題を扱います。著者が整理するのは、原コードを読み落とす、仕様へ反映し損ねる、新実装とテストの両方から機能が消えるという連続した欠落です。新コードだけを分母にすると、未実装の機能はカバレッジに現れません。

具体例には、クラス名だけ残ってCSSやアイコンがない画面、呼び出されないAPI、編集URLは動くが一覧の編集ボタンがない状態があります。テストが編集URLへ直接遷移すれば、利用者がそこに到達できない不具合を見逃します。モーダル、ドロワー、条件分岐するフォーム、ウィザードの各段階も、画面一枚を一行とする一覧では十分に扱えません。

原文は、AIが読んだ範囲を人が把握しにくい点も問題にします。ファイルの選別で重要な処理が外れたり、Readの部分取得、WebFetchの要約、別エージェントに渡った情報の違いで欠落したりします。「資料がない」と「未読」を区別し、ファイルと読み取り範囲、仕様項目、実装、テストを結び付けて追跡する必要があります。

対策は、旧システムの機能を分母にした細かな仕様台帳を作ることです。既存テストがある場合も移植数だけでなく内容を照合し、ない場合は原コードと資料から利用経路まで列挙します。ただし既存テスト自体が完全とは限りません。これは著者の開発経験に基づく注意点で、全モデルの欠落率を測った比較実験ではありません。

**注目ポイント：★★★★★**

テスト合格と移行の完全性が別問題であることを具体例で示せます。

### ③ CyberAgent：chezmoiでClaude Code / Codex設定を管理

**出典：CyberAgent Developers Blog**

**原文：** https://developers.cyberagent.co.jp/blog/archives/65099/

CyberAgentのエンジニアは、Claude CodeとCodexで重複する個人設定を **chezmoi** で管理する構成を試しています。共通指示を `.chezmoitemplates/agent-instructions/base.md.tmpl` に置き、各ツールのCLAUDE.mdやAGENTS.md用テンプレートから読み込みます。`agent_home` を渡して配置先の差を吸収し、共通内容と製品ごとの差を分けています。

chezmoiはGitで管理するsource stateから実際のホームディレクトリのtarget stateを生成します。`diff`、`apply --dry-run`、`execute-template`、`cat` で変更内容を確認してから適用できます。共通SKILL.mdをシンボリックリンクで配る案もありますが、メタデータや利用可能ツールの差まで解消されるわけではありません。

**APM** はパッケージの導入・更新を担当させ、ホーム全体やマシン差分を扱うchezmoiと役割を分けます。`install --global` と `compile --global` は別操作で、同じ生成済みルートファイルを両方に管理させると競合します。適用後のスクリプトでAPMを動かす構成も示されます。秘密情報は `.chezmoiignore` だけでは暗号化されないため、ageやGPG、パスワード管理との連携、秘密の検査を別途扱います。

著者はAPM 0.8.12が実際のホームで停止したようになる問題も調べました。小さなホームでは約1.7、4.1、3.3秒で動き、実環境では `Path.home()` 以下の再帰探索が原因でした。探索起点だけを `~/.apm` に絞り、別用途の `PackageInfo.install_path` はホームのままにして、二重の `.apm/.apm` を防ぎます。issue 830とPR 850を経て、修正は0.9.3に入りました。

ただし、これは個人環境の試行と不具合調査であり、社内全体への導入効果の実測ではありません。面接では設定の所有者を一つにする判断と、同じパス変数でも意味が違うため最小範囲で直した点を説明できます。

**注目ポイント：★★★★★**

共通化、ファイルの所有権、パスの不具合を一つの実例から学べます。

### ④ 生成AI活用企業の67.1％が、いまだ「人が起動」──「Japan AI Operations Report 2026 Summer」を公開

**出典：Mer**

**原文：** https://www.merinc.co.jp/news/japan-ai-operations-report-2026-summer

Merの **Japan AI Operations Report 2026 Summer** は、従業員100人以上の企業で生成AIを業務利用し、AI活用・業務改善・情報システムに関わる責任者や担当者548人への調査です。2026年6月24～25日のインターネット調査で、公開日は8月6日です。AI未利用企業や小規模企業を含む日本企業全体の比率ではない点が条件です。

回答では起動の67.1%が人の入力や定型プロンプト実行で、スケジュール・システムの変化をきっかけとするものは29.3%でした。社内で最も進む利用でも、条件内の処理・反映を自動化し例外だけ人が見る状態は2.9%です。出力の自動反映は27.2%、参考にした手作業やコピー転記は67.4%で、AIの回答生成と業務処理の完了が分かれていることを示します。

組織横断で利用記録を追跡できる回答は13.0%、事業指標に結び付けて把握する回答は14.8%でした。社内データが整っていない回答は50.7%。今後一年のAI投資拡大は67.2%なのに対し、業務フロー・起動条件の再設計への投資は18.4%です。設問が異なる比率を足し合わせたり、投資拡大が成果を生む因果関係と解釈したりできません。

Merは **「起動・接続・反映・ログ」** の四要件と、任意・スケジュール・条件という起動方式を整理します。これは同社の運営設計の提案であり、自動化率を上げれば必ず良いという比較実験ではありません。面接では、チャットの利用回数に加え、転記が残る場所、例外の担当者、後から結果を追える記録を確認する話へつなげられます。

**注目ポイント：★★★★★**

調査の母集団を残したまま、AI利用と業務運用の違いを説明できます。

### ⑤ Cursor：大規模Gitホスティング向けStorage Architecture「Continuity」

**出典：Cursor**

**原文：** https://prod.cursor.com/blog/git-at-any-scale

Cursorの **Continuity** は、エージェントが大量にGitを使う状況に向け、普通のGitリポジトリをローカルNVMeに置きながら、永続化とレプリカ数を切り離す設計です。GitのオブジェクトはDAGをたどり、packfile内でも差分を追います。オブジェクトごとの遠隔取得やネットワークファイルシステムでは往復が積み重なるため、ローカルの通常形式を維持します。

記事が比較するSpokesは、packfileを各ノードへ配り、小さい参照更新を3段階コミットで同期します。参照が更新されるまでコミットが公開されないGitの性質を利用できますが、レプリカが多いと遅いノードの影響が増え、ほぼ使われないリポジトリにも複数コピーが必要です。ディスク上のコピーが正本なので、配置表、チェックサム、修復も継続して管理します。

Continuityは **S3上のWAL** を正本とし、ディスク上の通常リポジトリを再生成可能なキャッシュにします。packfileの保存とローカル処理を並行し、参照トランザクションの準備後、WALの索引ポインタを **CAS** で更新して公開します。永続化前にpush成功を返しません。通常はrendezvous hashingで選ぶprimaryへ送りますが、別サーバーもCASの競合を解決しながら書けます。索引更新はまとめて処理し、pushごとにS3書き込みを一対一で増やす構成にはしません。

UDP gossipは更新通知を速めますが、通知を正しさの根拠にはしません。読み取り前にS3へ **ETagの条件付きGET** を行い、304なら最新、200なら索引と不足データを取得してから返します。レプリカがゼロのアイドル状態からもWALで復元できます。圧縮整理はprimaryで行い、他は新packfileを取得し、帯域を使ってCPUの重複作業を減らします。

提供者の合成負荷試験では100レプリカまで読み取りがほぼ線形に伸び、pushの悪化を観測しなかったと報告しています。圧縮整理を含め、S3 Standardで毎秒120回、S3 Express One Zoneで300回超のpushという結果です。ただしリポジトリや操作条件の異なる実運用へそのまま倍率を移せません。ETag確認が平均10ms未満という値も、その観測環境でのメタデータ確認です。基盤選択では単一ゾーンの構成条件や費用も別に評価する必要があります。

**注目ポイント：★★★★★**

永続ログ、CAS、読み取り時の鮮度確認が整合性をどう支えるかを説明できます。

## 4. 今日の技術テーマ

**正しい状態の定義を、実行結果までつなぐ。**

`原システム・業務定義 → 共有する仕様 → 実行 → 永続記録・結果 → 定義との照合`

同じ顧客数でも定義が違えば不一致になります。テストが通っても入口がなければ移行は未完了です。Gitの通知が届いても索引が古ければ正しい読み取りになりません。各領域で何を正本とするかを決め、確認する位置を具体化します。

## C-3. JLPT文法

### 1. ～にわたって
**Level：N1｜意味：** 期間や場所などの範囲全体に及ぶこと。  
**形：** `名詞 + にわたって`  
**使い方：** 組織全体にわたって記録を追跡できるかを説明します。  
**例：** `複数のBusiness Unitにわたって共通AI基盤を展開します。`  
**補足：** 組織全体にわたって記録を追跡できるかを説明します。

### 2. ～にとどまらず
**Level：N1｜意味：** ある範囲だけでなく、さらに広い範囲にも及ぶこと。  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 前の範囲から後ろへ話題を広げます。  
**例：** `CoverageはFile数にとどまらず、Error CaseやData条件まで確認します。`  
**補足：** 前の範囲から後ろへ話題を広げます。

### 3. ～なくしては
**Level：N1｜意味：** ある条件がなければ、後のことは実現しない。  
**形：** `名詞 + なくしては`  
**使い方：** 検証や権限確認を、必要な前提として強調する表現です。  
**例：** `明確なInput Universeなくしては、Coverageの抜けを正しく検出できません。`  
**補足：** 検証や権限確認を、必要な前提として強調する表現です。

### 4. ～に基づいて
**Level：N2｜意味：** 情報や規則などを根拠として行動・判断すること。  
**形：** `名詞 + に基づいて`  
**使い方：** 何を判断の土台にしたのかを明確にします。  
**例：** `対象一覧に基づいてMigrationの進捗を確認します。`  
**補足：** 何を判断の土台にしたのかを明確にします。

### 5. ～た上で
**Level：N2｜意味：** 先の行為を済ませ、それを前提として次を行う。  
**形：** `動詞た形 + 上で`  
**使い方：** 検証してから利用するという手順を述べます。  
**例：** `Data Ownerを明確にした上で、AI連携を設計します。`  
**補足：** 検証してから利用するという手順を述べます。

### 6. ～一方で
**Level：N2｜意味：** 同じ事柄の、対照的な二つの側面を述べること。  
**形：** `普通形 + 一方で`  
**使い方：** 前後は逆の評価や異なる側面でもつなげられます。  
**例：** `SSOTはConfig Driftを減らせる一方で、移行時の調整が必要です。`  
**補足：** 前後は逆の評価や異なる側面でもつなげられます。

### 7. ～にかかわらず
**Level：N2｜意味：** ある条件が違っても、同じことが成り立つこと。  
**形：** `名詞 + にかかわらず`  
**使い方：** 後ろには条件に左右されない行動や規則を置きます。  
**例：** `Teamにかかわらず、同じSchema Registryを参照します。`  
**補足：** 後ろには条件に左右されない行動や規則を置きます。
