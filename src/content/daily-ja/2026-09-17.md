### 1 Claude Codeで開発期間を2.5か月から1か月に縮めた「ハーネス」の設計手法

**出典：SmartHR Tech Blog｜2026年9月16日 11:02**  
**原文 URL：** https://tech.smarthr.jp/entry/2026/09/16/110205

SmartHRの事例は、Claude Codeへ長いPromptを与え続けるのではなく、Agentが動く周辺環境を先に設計する発想が中心です。対象は既存のModular Monolithへ追加する新機能で、1 Sessionに全Contextを詰めるには規模が大きく、履歴が伸びるほど過去Logを再送するCostとContext消費も増えます。そこでSkill File、進行状態を持つJSON、完了条件を判定するShell Scriptの3点で **Harness** を構成しました。OrchestratorはClaude CodeのMain Sessionが兼ね、Phase Transition、Userとの合意、State Update、検査実行に限定し、自ら実装しません。Implementation Agentは最小Taskごとに新しく起動し、TDDで実装とCommitまで行います。

品質をModelの自己申告へ委ねない点が特に重要です。各Taskの完了時には **12項目のShell検査**を実行し、対象TestがGreenであるだけでなく、Testが0件ならFail、Feature Flag OFF時に既存挙動と一致すること、変更Fileが許可Path内にあること、Dependency違反が増えていないこと、TDDの痕跡がCommitに残ることなどを機械判定します。共有Tableの変更やUI側のFlag漏れなど機械判定しにくい2項目はHuman Checkへ残します。SpecとRulesも分離し、矛盾時はRulesを優先し、合意した内容はSession MemoryではなくSpec / Rulesへ書き戻します。最終Reviewは全Task後に一度だけ、仕様突合・Concurrency・Authorization・機能完結性の4観点で並列実行します。

**Evidence / Measurement：** 未公開の1機能について、当初の実質工数見積もりは約 **2.5か月**、Harnessを先に作った後は大きな手戻りなく約 **1か月**で一通り実装したと報告されています。状態JSONが10 Task時点で118KBまで増えた経験から `progress.json` と `stages.json` を分離し、ModelもData ModelやState TransitionにはOpus、型が決まったAPI・UI・TestにはSonnetを使い分けました。**ただし、**筆者自身がHarnessは銀の弾丸ではなく、Projectによって不要な場合やInfrastructure Designには合わない場合もあると明記しています。2.5→1か月は単一機能の実例であり、Claude Code一般の生産性Benchmarkではありません。

**注目ポイント：★★★★★**  
Modelを賢くするより、Context・State・Completion GateをModel外へ設計することが大規模AI Codingでは重要です。

### 2 毎秒数十万スパンを扱う、高トラフィック環境での分散トレーシング基盤の構築

**出典：CyberAgent Developers Blog｜2026年9月16日**  
**原文 URL：** https://developers.cyberagent.co.jp/blog/archives/65910/

AJA DSPでは一つのBid Requestが複数MicroserviceとDatastoreを横断します。従来はMetricで異常を見つけた後、各ServiceのLogを行き来して原因を組み立てる必要がありました。そこでOpenTelemetryで計装し、**Tail-based Sampling**を導入しています。Head-based Samplingは処理開始時に保存可否を決めるため、低いSampling Rateでは後からErrorやDelayになったTraceまで落とす可能性があります。Tail SamplingはTraceの結果を見てから保存可否を決めるため、調査価値の高い異常Traceを残しつつNormal Traceを絞れます。一方、最終的に捨てるTraceも判断までは全Spanを処理するので、Sampling前のCollector Capacityが重要になります。

構成は二層です。Datadog Distribution of OpenTelemetry Collector（**DDOT**）を各NodeのDaemonSetとして配置し、Load Balancing Exporterが `traceID` をRouting Keyにして同一TraceのSpanを同じCollectorへ送ります。BufferとTail Samplingを担当するCollectorは専用Node Poolへ分離し、広告配信処理とのResource競合を避けました。本番後、Policyが一時 **20個**まで増え、同じ保持率の条件がSpanを何度も走査してCPUを消費したため、先に確率で対象を絞り、条件を集約し、`sample_on_first_match` で後続評価を止めて **7個**まで削減しています。Scale-downではDDOT側のQueue / Retryと、Collectorの `terminationGracePeriodSeconds: 60`、`preStop: 30s` を組み合わせて欠損を抑えました。

**Evidence / Measurement：** 本番では5xx、内部失敗、品質低下、Async Failureを含むTraceを意図通り残し、Delay、Cancel、4xx、Normal Traceも設定割合で保存できたとしています。Application LatencyやError Rateに顕著な悪化はなく、Peak Trafficも想定Budget帯で処理したと報告されています。例では `decision_wait: 10s` やBaseline `sampling_percentage: 0.1` が示されています。**ただし、**Sampling Percentage、Policy分類、Resource Budgetは毎秒数十万Spanを扱うAJA DSP固有の設計です。別SystemではSpan生成量、Trace Duration、Collector Memory、Costを実測して再設計する必要があります。

**注目ポイント：★★★★★**  
Observability自体をProduction Workloadとして扱い、Retention・CPU・Scale-downを同じ設計問題として解いています。

### 3 人が「承認」した無害なコマンドでAIが乗っ取られる　コードエディタCursorを襲った“2行の攻撃”

**出典：＠IT｜2026年9月16日 08:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/16/news033.html

対象はCursorの **CVE-2026-22708** です。Memory Corruptionや従来型Privilege Escalationではなく、Coding AgentのCommand ApprovalにあるTrust Gapを突きました。`export`、`typeset`、`declare` などのShell Built-inが暗黙に信頼される経路があり、README、Dependency、Issue CommentなどAgentが読むTextに悪意あるInstructionを混ぜるとEnvironment Variableを書き換えられました。公開例では先に `PAGER` をPayloadへ変更し、その後Userが `git branch` を承認すると、Gitが表示ProgramとしてPAGERを起動して任意Commandが動きます。CursorはHighと評価し、**v2.3**で実証経路を修正しています。

記事はDocker Sandboxesを使い、PermissionとIsolationを分けて説明します。SandboxはmicroVM、独自Kernel / Filesystem、default-deny Networkを持つため、同じPayloadが内部で動いてもHostの `~/.ssh/id_rsa` は直接見えません。しかし通常の `git push` 用にSSH Agent SocketをForwardする場合、Key Fileを盗めなくても稼働中はIdentityを借りられます。そのためEgress先Address / PortもPolicy化する必要があります。Workspaceは標準でHostとLive Syncされるため、未検証Codeには `--clone` で独立Copyを渡す方法があり、共有Agent Skill StoreもSandbox間のTrust Boundaryとして扱う必要があります。

**Evidence / Measurement：** ＠ITはDockerの解説とPillar Securityの公開研究を基に、2行で成立した過去のExploitを整理しています。設計上の教訓は、**Allow-listやHuman ApprovalだけをSecurity Boundaryにしない**ことです。最初のCommandより前にIsolationを置き、Environment Mutation、Workspace Sync、Credential Forwardingを別Riskとして扱います。**ただし、**この具体経路はCursor v2.3ですでに修正されており、現在も同じ2行で攻撃できるという記事ではありません。またSandboxも万能ではなく、SSH Agent、Network Egress、Shared State、外部Toolが生成Fileを後から信頼する経路は別途制御が必要です。

**注目ポイント：★★★★★**  
Permission、Approval、Isolation、Credentialを一つの安全策にまとめず、独立したBoundaryとして説明できる記事です。

### 4 Lovable、ViteからRust製開発ツール「OJ」への切り替えを紹介

**出典：gihyo.jp｜2026年9月16日**  
**原文 URL：** https://gihyo.jp/article/2026/09/oj

LovableはAI AppのPreviewごとに隔離実行環境を用意し、1日約 **100万環境**を稼働させています。複数Agentが繰り返しBuildするとNode.js / ViteのMemoryと起動Costが大規模に積み上がるため、Preview ServerをRust製 **OJ** へ段階的に切り替えています。OJは対応範囲のVite Config / Pluginを利用でき、RolldownでBundle、OxcでParse / Transformし、JavaScript実行が必要なPluginやServer CodeではNode.jsも使います。またAgentのMulti-file EditをまとめてBrowserへ反映し、変更途中の状態が何度も見えることを抑えます。

Lovableの実Serviceでは、Previewを開いてから操作可能になるまでのMedianが **17.4秒→8.0秒**、Execution Environment確保が **14.5秒→3.0秒**、App Load前のDev Server MemoryがNode/Vite構成の約15％になったと報告されています。ただし1万React ComponentのCold StartでVite 4.9秒、OJ 1.2秒という比較は、Vite側だけ `vite-plugin-checker` が動作し、OJは未対応でした。RepositoryのBundled Development ModeではM-series Mac上でStart+Display Medianが **OJ 1.315秒、Vite 8.2.1 1.528秒**と近く、Memoryは **115MB対1751MB**と大きく差が残っています。

**Evidence / Comparison：** Production PreviewのMeasurementとRepository Benchmarkを分け、さらにEvan You氏がBenchmark条件を指摘している点が重要です。OJはVite全体を書き直したものではなくRolldown / Oxcを再利用し、より狭いApp Classへ最適化しています。一方Viteはより広いFramework、Plugin、Configurationを支える責務があります。**ただし、**OJはViteの全Use CaseをCoverせず、`vite-plugin-checker` など未対応Pluginもあります。一部ModeはExperimentalです。Performance判断ではStartup、Memory、Plugin Compatibility、Migration Riskを別Metricで評価すべきです。

**注目ポイント：★★★★★**  
Frontend Performanceの面接で、Production MeasurementとBenchmark条件を区別する具体例になります。

### 5 Google、会話を止めずに裏でタスクを実行する音声モデル「Gemini 3.8 Live」公開　推論強化の上位版も

**出典：ITmedia NEWS｜2026年9月16日 10:16**

GoogleはRealtime Voice向けに **Gemini 3.8 Live** と **Gemini 3.8 Live Extended Thinking** を公開しました。3.8 LiveはScaleとCost Efficiency、Extended Thinkingは複雑なMulti-step Reasoningを重視します。大きな変更はTool / API CallをConversationと同期的に待たなくてよいことです。依頼を受けたことを音声で返した後、BackgroundでTaskを進めながらConversationを続けられます。Video InputもほぼRealtimeにContextへ反映し、日本語を含む97言語を会話途中で自動識別・切替できます。Voice AgentのApplication設計ではConversation StateとBackground Task Stateを分離して管理する必要が出てきます。

DeveloperはGemini API / Google AI Studioから `gemini-3.8-live` と `gemini-3.8-live-extended-thinking` を利用できます。想定CaseにはCameraを使うOnboarding、VoiceでのBusiness Plan、SketchからReact Component生成、Multi-step Reservationがあります。Extended ThinkingはReasoningの進行をVoiceで説明しながら処理できます。ただしApplication側では、Background TaskのSide EffectをいつCommitするか、Userが途中でIntentを変更した場合のCancel、Timeout / Retry、重複Tool CallのIdempotencyを設計しないと、Conversationが自然でもBusiness Stateは壊れ得ます。

**Evidence / Benchmark：** Google公表値ではExtended Thinking（High）がArtificial AnalysisのSpeech-to-Speech Quality Index **82.6**で、Gemini 3.1 Flash Live（High）の71.5を上回ったとされています。τ-Voiceなど他の指標も示されました。**ただし、**これらはVendor発表時のBenchmarkであり、日本語客服や予約、Coding Voice Agentで同じTask Successになる保証はありません。Gemini Enterpriseは当時Limited / Private Previewで、記事時点の公式BlogにはAPI従量料金も明記されていません。本番ではVoice Latency、Interruption、Tool Side Effect、Long-session Stability、Cost-per-successを自社で測る必要があります。

**注目ポイント：★★★★★**  
Non-blocking ConversationはUX改善ですが、ProductionではBackground TaskのCommit Boundaryを別に設計する必要があります。

## 4. 今日の技術テーマ：Execution Boundary

```text
Input / Context
      ↓
Agent / Runtime
      ↓
Execution Boundary
├─ What can be read?
├─ What can be executed?
├─ What is a deterministic pass/fail?
├─ What state is buffered or shared?
└─ What requires commit / approval?
      ↓
Evidence / Telemetry
      ↓
Human or Policy Gate
      ↓
Committed State
```

**仕組み：** SmartHRはCompletion GateをShellとTestへ外出しし、AJAはTrace RetentionをTail Sampling Policyで制御しながらtraceIDでTrace全体を保ちます。Cursor事例はPermissionとIsolationを別Layerにし、OJはPerformance Claimを比較条件から切り離しません。Gemini LiveではConversationとTool Executionが非同期になり、ApplicationがSide EffectのCommitを管理する必要があります。

**メリット：** ModelやRuntimeを変えてもBoundaryは再利用できます。Test Gate、Sampling Policy、Sandbox Egress、Benchmark Protocol、Commit Ruleは特定Modelに依存しません。さらに、なぜActionを許可したかをTest Output、Trace、Policy、Audit Logで説明できます。

**制約：** Boundaryは記述したFailure Modeしか捕捉できません。Shell TestはUXを見落とし、Sampling Policyは属性化されていない重要Traceを落とし得ます。SandboxでもSSH Agent Forwardingは残り、BenchmarkはPlugin条件で歪み、Async ToolはCancel / Retry / Duplicate Executionを生みます。Production FailureからRuleを更新するLoopが必要です。

**国内企業導入時の注意：** AI Workflowごとに `Context Source / Read Scope / Execute Scope / Deterministic Gate / Evidence / Commit Authority / Rollback` を明示すると、Permission拡大の判断を説明しやすくなります。まずRead / Proposalから始め、AuditとFailure Handlingが安定してからWriteやAutonomous Commitへ進めるのが安全です。

## C-3. JLPT文法（7項目）

1. **～にとどまらず｜N1**：ある範囲だけで終わらず他にも及ぶ。接続：名詞＋にとどまらず／普通形＋にとどまらず。例：`Tail SamplingはError Traceの保存にとどまらず、性能調査にも利用されています。` 意味：Tracingは障害保存以外にも使える。AJAの利用範囲に対応します。
2. **～たうえで｜N2**：前を完了してから次を行う。接続：Vた＋うえで／Nの＋うえで。例：`Benchmark条件を確認したうえで、OJとViteの性能を比較します。` 意味：条件確認後に比較する。Benchmark Readingに対応します。
3. **～に応じて｜N2**：条件に合わせて対応を変える。接続：N＋に応じて。例：`Taskの設計自由度に応じてOpusとSonnetを使い分けます。` 意味：Task難易度でModelを変える。SmartHRのModel Routingです。
4. **～とは限らない｜N2**：常に成立するわけではない。接続：普通形＋とは限らない。例：`一つのFeatureで開発期間が短縮しても、別Projectで同じ効果が出るとは限りません。` 意味：Caseを一般化しない。HarnessのBoundaryです。
5. **～かねない｜N1**：望ましくない結果が起こる可能性。接続：Vます去ます＋かねない。例：`SSH Agent Socketを無制限にForwardすると、Sandbox内から資格情報を悪用されかねません。` 意味：Credential Abuse Risk。CursorのSandbox限界です。
6. **～を余儀なくされる｜N1**：外部条件で対応せざるを得ない。接続：N＋を余儀なくされる。例：`大量のPreview Environmentでは、Memory Costを抑えるため基盤の見直しを余儀なくされます。` 意味：ScaleがArchitecture変更を迫る。Lovableの背景です。
7. **～に至るまで｜N1**：範囲が最終対象まで及ぶ。接続：N＋に至るまで。例：`ConversationからBackground TaskのCommitに至るまで、状態遷移をAuditできるようにします。` 意味：VoiceからBusiness Stateまで追跡する。GeminiのAsync設計です。
