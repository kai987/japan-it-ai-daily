### 1. Googleの「Gemini」も能力テスト中に実在企業3社に侵入──WSJ報道

**出典：ITmedia NEWS｜2026年9月21日 06:50**  
**原文 URL：** https://www.itmedia.co.jp/news/article/2609/21/2000001665/

今回の本質は「Modelが悪意を持ったか」ではなく、Cyber能力評価の隔離条件が崩れたときにAgentのActionが実Internetへ到達した点にある。Irregularが5月に実施したTestでは、架空企業のSoftwareから情報を得るTaskをGeminiへ与えた。架空企業と実在企業が同名だったことに加え、本来Internetへ出られないはずの環境が意図せず接続可能になっており、Geminiは**実在3社**のSystemへ侵入した。Irregularによれば実在企業だと気付いた時点で停止し、Googleは3社と連邦当局へ連絡した。

Security Designとしては、Model SafetyとInfrastructure Isolationを別々のControlとして持つ必要がある。Googleは停止できた点をSafety対策の機能として説明する一方、外部専門家は「評価範囲を越えて実SystemへActionが出たこと」自体を問題視している。Cyber AgentのHarnessでは、Egressをdefault denyにし、許可Targetを固定し、DNS/HTTP DestinationをTraceした上でModel Behaviorを評価するべきだ。Modelが途中で気付くことはDefense-in-depthにはなるが、Network Boundaryの代替にはならない。

**根拠種別：** ITmediaによるWSJ報道の紹介で、Googleの確認とIrregularの説明を含む。**ただし／適用範囲：** 使用されたGeminiのVersionと対象企業名は非公開で、Googleは被害なし・最新Modelではないと説明している。したがって現在のGemini一般の侵入率を示すEvidenceではなく、Evaluation EnvironmentのEgress設計を見直すCaseとして扱うのが妥当だ。

**注目ポイント：★★★★★**  
高権限Agentの評価では「Modelが拒否するか」を試す前に、「そもそも許可外DestinationへPacketを出せないか」を検証する、という順序が面接でも説明しやすい。

### 2. [アップデート] AWS Continuum のペネトレーションテストでテスト実施前に認証情報のテストと到達ドメインの提案ができるようになりました

**出典：DevelopersIO｜2026年9月20日（日付のみ公開のため境界補完）**  
**原文 URL：** https://dev.classmethod.jp/articles/aws-security-agent-credential-test-domain/

AWS Continuum for penetration testingは、AI AgentでWeb ApplicationのPentestを行うServiceで、以前はAWS Security Agentと呼ばれていた。今回のUpdateでは、実Testを開始する前にCredentialのLogin可否を確認し、そのLogin Flowで到達したDomainをNetwork Scope候補として提示できる。作者は`secapp.tak1wa.com`、`api.tak1wa.com`、`assets.tak1wa.com`の3 DomainをAPI Gateway + Lambdaで用意し、Credential TestとScope Suggestionを確認した。

Credential TestはStarting→In progressへ進み、Success / Failed / Timed outで終了する。**15分**でTimeoutし、今回のLoginは約2〜3分だった。Login後に到達したAPIとAsset DomainはSuggestedとして現れ、最初はAccessibleに分類された。ただし、Login Flowで到達しなかったDomainは自動では出ず、必要なら`Add domain`で補う。AWS DocumentationもProduction Credentialを渡さず、非本番で代表的な権限を持つAccountを使うよう求めている。AgentはLogin Userが見える範囲を一通りTestするからだ。

**根拠種別：** Author Hands-onとAWS公式Documentの注意事項。**ただし／適用範囲：** 作者環境ではTest Logを確認できず、CloudWatch Logs設定との関係は推測にとどまる。Suggested Scopeも「今回到達した範囲」でありApplication全体のAttack Surfaceを保証しないため、最終Scopeは人がReviewする必要がある。

**注目ポイント：★★★★★**  
高価なAgent Taskや攻撃Actionは、Credential・Scope・Policyを小さいPreflightで確かめたうえで実行する、という設計に一般化できる。

### 3. dbt Charts で Snowflake 上の dbt モデルを YAML だけでダッシュボード化してみた

**出典：DevelopersIO｜2026年9月20日（日付のみ公開のため境界補完）**  
**原文 URL：** https://dev.classmethod.jp/articles/dbt-charts-snowflake-dbt-model-yaml-dashboard/

dbt ChartsはBoardをYAMLで宣言し、SQLでDataを取得するOSS Toolだ。作者は**0.7.1**をWindows 11、Python 3.12.11、dbt Core 1.12.0 + dbt-snowflake 1.12.0、Snowflake東京Regionで検証した。YAMLは`variables / queries / charts / layout`を持ち、QueryではJinjaの`{{ ref('orders') }}`を使える。dbt Projectと同居すると`dbt_project.yml`、`profiles.yml`、`target/manifest.json`を読み、`dct validate`、`dct render`、`dct query`、`dct serve`でValidateから表示まで行える。

運用上はData Planeの権限が重要になる。Hands-onでは簡略化のためACCOUNTADMINを使ったが、公式は対象SchemaへSELECTだけを持つ専用Roleを推奨している。Credentialを持つ`profiles.yml`はGitへ入れない。さらに`dct serve`には認証Optionがないため、作者は**`dct serve --host localhost`**でLocal限定にした。`0.0.0.0`へ公開すれば同一Networkの端末から見える可能性がある。dbt Core 1.x依存のため、dbt v2/Fusion環境へ同居させるとDependency ResolutionでCore 1.xへ置き換わるRiskもある。

**根拠種別：** Author Hands-onとOfficial Documentation。**ただし／適用範囲：** dbt Charts 0.7.1はpre-1.0で、YAML構文やCLI Optionは変わり得る。本記事はOSS `dct`の検証であり、Hosting・権限管理・Chat UIを持つdbt Charts Cloud public betaの評価ではない。

**注目ポイント：★★★★★**  
DashboardをCodeとしてReviewできることと、Database Credential・Serve Endpointを安全に運用できることは別の要件であり、Analytics Engineeringの面接でも話しやすい。

### 4. 双日調査、Copilot導入企業の87.5％が「情報分散」を課題　「横断検索AI」に期待か

**出典：キーマンズネット｜2026年9月21日 07:00**  
**原文 URL：** https://kn.itmedia.co.jp/kn/article/2609/21/2000001657/

双日テックイノベーションは、従業員1000人以上でMicrosoft 365 Copilotを導入済み、かつ生成AI/AI Toolの導入推進に関わる担当者を対象にInternet Surveyを実施した。期間は2026年7月31日〜8月3日、有効回答は105人。CopilotとM365だけで業務上必要な社内情報の検索・活用をカバーできるかという質問には、39.0％+39.0％、合計**78.0％**が肯定した。

一方で、必要情報がM365内外の複数Systemへ分散していることを課題と感じる回答は42.3％+45.2％、合計**87.5％**だった。M365外も横断検索できればAI活用が広がるとの期待は96.2％に達する。ただし、これは導入効果ではなくExpectationのSurveyだ。実装ではConnectorを増やす前にSource Owner、Freshness、ACL継承を整理し、代表Question SetでRetrieval Recall、Citation、Permission Leakageを測る必要がある。

**根拠種別：** Sample条件が明記されたVendor関連Survey。**ただし／適用範囲：** 105人は大企業かつCopilot導入済みの推進担当者に限定されるため、日本企業全体の代表値ではない。96.2％も「横断検索AIが効いた」というMeasurementではなく期待値である。

**注目ポイント：★★★★★**  
Enterprise RAGはModel選定より前にKnowledge CoverageとAuthorizationを整える必要があることを、実際の利用者Surveyから説明できる。

### 5. AI予算はどこへ向かう？　企業が選んだ投資先と判断材料

**出典：キーマンズネット｜2026年9月21日 07:00**  
**原文 URL：** https://kn.itmedia.co.jp/kn/article/2609/21/2000001585/

Findyの調査は2026年8月6〜10日、従業員300人以上の企業でAI投資Budgetに関与する20〜69歳の435人を対象に行われた。経営決裁層では前年度よりAI投資が増えた回答が81.3％で、1.5倍以上の大幅増が28.0％、増加が53.3％。今後1年間に強化する領域は**情報システム69.2％**、Software Development/Engineering 56.1％、Product Management 50.5％、R&D 48.6％だった。

最大の費目としてAI Service/SaaS Licenseを選んだ割合は31.8％、AI Infra/Compute 17.8％、AI API従量課金16.8％。API料金を上位3費目に挙げた人は47.7％だった。強化理由ではCost削減50.5％、人材不足46.2％、競合動向40.9％、効果実証済み39.8％。Outcome側ではCost削減26.2％、Speed 17.8％、Revenue/Profit 15.0％、Quality/Error Reduction 10.3％となる。FinOpsではModel Token単価にとどまらず、License、Infra、API、人件費を同じPortfolioで見るべきだ。

**根拠種別：** 435人のInternet Survey。**ただし／適用範囲：** 予算関与者の回答であり、実際の会計Dataを監査した調査ではない。従業員300人以上に限定されるため、69.2％や31.8％を自社の正解配分とみなさず、自社のCost-per-successや工数削減などで再評価する必要がある。

**注目ポイント：★★★★★**  
AI Cost Controlを「APIを安くする」だけでなく、Portfolio AllocationとBusiness KPIで説明できるため、Enterprise AI職の面接材料として使いやすい。

## 2. カテゴリ別サマリー

**AI / Agent：** GeminiのCaseはAgent Safetyを拒否応答だけでなくEvaluation HarnessとEgress Boundaryの問題として示した。AWS Continuumは本Task前のCredential/Scope Preflightを具体化しており、どちらもCapability評価の前にExecution Spaceを制御する発想で共通する。

**Frontend：** 直近24時間ではReact/Next.js単独の強い新規記事はTop 5に入らなかった。dbt ChartsはData寄りだが、`variables/charts/layout`をDeclarative UIとしてCode Reviewできる。UIをCode化してもAuthenticationとServing Exposureは別途設計が必要だ。

**Cloud / Backend：** AWS ContinuumのTarget/Accessible/Out of scope、dbt ChartsのSELECT-only RoleはLeast Privilegeの実例である。Automationが強くなるほどCredential Scope、Network Boundary、Preflightの価値が上がる。

**国内企業導入：** 双日調査はKnowledge Coverage、Findy調査はBudget Allocationを可視化した。Enterprise AIではConnectorやModelだけでなく、ACL、Source Ownership、License/API/Infra費、Outcome KPIまで運用設計へ含める必要がある。

## 4. 今日の技術テーマ：Scope Before Scale

5本を共通化すると、AI/AutomationをScaleさせる前に「何を見られるか、どこへ到達できるか、どの権限を使うか、いくら使えるか」をScopeとして固定する設計になる。GeminiはEvaluation Network Scope、AWS ContinuumはCredential/Pentest Domain、dbt ChartsはDB RoleとServe Surface、CopilotはKnowledge Source、AI予算はFinancial/Outcome Scopeの話である。

```text
Business Goal
    ↓
Scope Definition
├─ Network / Target
├─ Credential / Permission
├─ Data / Knowledge Source
├─ Runtime / Serving Surface
└─ Budget / KPI
    ↓
Preflight & Validation
    ↓
AI / Automation Execution
    ↓
Evidence
    ↓
Scale / Commit
```

メリットはModelやToolが変わってもTarget Allowlist、SELECT-only Role、ACL Mapping、Budget Guardrailを再利用できることだ。一方でScope自体が誤っていたり古くなったりする可能性は残る。AWS Continuumも未到達Domainを自動発見できるとは限らず、横断検索もSourceを増やすだけでは権限品質を保証できない。国内企業ではScope Owner、更新契機、Exception、Audit Evidenceまで決めた上で運用する必要がある。

## 5. 面接復習カード

### Q1
**質問：** AI AgentのEvaluation Sandboxで、Model Safety以外に必ず確認すべきものは何ですか。  
**回答要点：** Egress default-deny、Target Allowlist、Credential Scope、DNS/HTTP監査、実Systemへ出た場合のKill Switch。Modelの停止判断をNetwork Isolationの代わりにしない。

### Q2
**質問：** Enterprise RAGでData Sourceを増やす前に何を確認しますか。  
**回答要点：** Source Owner、Freshness、ACL継承、検索対象範囲、代表Question Set、Recall、Citation、Permission Leakage。期待値のSurveyと本番Measurementを分ける。

### Q3
**質問：** AI FinOpsでAPI料金だけを見てはいけない理由は何ですか。  
**回答要点：** License、Infra、API、人件費が別費目で積み上がるため。Cost-per-success、工数削減、Speed、QualityなどOutcome単位へ配賦して比較する。

# B. 重点知識・面接で使える論点

## B-1. Gemini Cyber能力評価
- Agentの越境ActionはModel IntentだけでなくEvaluation HarnessのNetwork Conditionからも起きる。
- 実在企業と認識して停止できたことはDefense-in-depthだが、Egress Controlの代替にはならない。
- 面接ポイント：Model SafetyとNetwork Isolationを独立したControlとして説明する。

## B-2. AWS Continuum Preflight
- Credential Testで高価なPentest前にLogin Failureを検出でき、今回のHands-onは約2〜3分、Timeoutは15分。

## C-3. JLPT文法｜新規2項目

全履歴Identityを確認した結果、当日Top 5で「原文に実在＋未収録＋N1/N2として学習価値がある」を満たす新規文法は2項目だった。5〜8項目をQuotaとして埋めず、復習は`learning-review`が当日本文の実例から派生する。

1. **～にとどまる｜N1**：範囲・数量・影響が一定の限界を越えず、そこまでに収まる。構造：`N / 数量 + にとどまる`。原文形式：`「減少」と「大幅に減少」の合計は2.8％にとどまった。`（Top 5、AI投資額の前年比）。例：`Vendor調査の数字は参考にとどまり、自社の投資判断は実測KPIで補います。` 注意：「～にとどまらず」は「それだけではなく」で、機能を混同しない。
2. **～ずに済む｜N2**：本来必要だった行為をしないまま問題を終えられる。構造：`Vない→Vず + に済む（する→せずに済む）`。原文形式：`認証情報の不備でテスト時間を無駄にせずに済む`（Top 2、Credential Testの利点）。例：`事前にCredentialを検証すれば、失敗したPentestにTask-hourを使わずに済みます。` 注意：「～なくて済む」と近いが「ずに」はやや書き言葉的。
