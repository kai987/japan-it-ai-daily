### ① なぜ経営陣に危機感が伝わらない？　CISOの半数以上が苦悩する「AIエージェント制御」のリアル：人間のアカウント管理の流用にシャドーAIの横行　従来の対策は限界

**出典：＠IT**

**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2609/04/news042.html

OktaのGlobal CISO Insights 2026は、六月に六か国のCISOやセキュリティ責任者306人へ行った調査です。英国33％、日本24.8％など国別構成に偏りがあり、全世界の企業を同じ比率で代表する統計ではありません。所在を把握できると答えた人は47％、接続先を一元管理できる人は46％、個別のツール呼び出しを認可できる人は45％でした。

見えることと制御できることは別です。全Agentの所在を把握する回答者でも約八割が過剰権限を心配しています。成熟度は高度26％、定義済み34％、発展途上31％、受動的9％でした。「定義済み」には既知ツールのSSO/MFAがあっても、未承認AIや下流の権限を制御できない状態が含まれます。ログインの保護だけで、Agentの個々の操作が認可されたことにはなりません。

人間と同様のID管理が25％、広い権限を持つ共有資格情報やサービスアカウントが21％、展開チームごとの臨時管理が20％です。Oktaの提案はAgent自身をディレクトリへ登録し、責任者、対象データ、操作範囲を結び付けることです。高度な組織の50％が数分以内に不正Agentのアクセスを取り消せると回答した一方、全体では26％でした。これは自己申告の関連で、成熟度を上げた結果として停止時間が短縮した因果実験ではありません。

受動的な組織の61％が安全性より革新を優先し、全体の48％を上回りました。全体の68％が未承認AI利用を認識し、日本では予算・人員不足47％が最大の障壁です。経営層とリスク許容度が完全に合うとの回答は全体31％にとどまります。面接では棚卸しに加えて、呼び出しごとの認可と資格情報の失効を誰が担当するかを説明できます。ただし調査値は侵害の実測件数や特定製品の防御率ではありません。

**注目ポイント：★★★★★**

IDの可視化、認証、操作の認可を区別して話せます。

### ② Amazon Bedrock AgentCore Memory、きめ細かなアクセス制御をサポート

**出典：CodeZine**

**原文：** https://codezine.jp/news/detail/29562

Agentが複数利用者の記憶を保存するとき、検索条件の付け忘れが別の利用者のデータへつながることがあります。八月28日のAgentCore Memory更新は、この分離をアプリの独自ロジックだけへ任せず、Gateway側のポリシーで適用する仕組みです。[AWSの発表](https://aws.amazon.com/jp/about-aws/whats-new/2026/08/agentcorememory-fine-grained-access-control/)とCodeZineの説明を照合しました。

前提はOAuthのJWT認証を設定したAgentCore Gatewayです。検証した呼び出し元のidentityにCedarの条件を結び付け、自分のactorに限定したアクセス、token claim由来のnamespaceへの制限、Memory操作ごとの許可・拒否を表します。利用者が本文に書いた自己申告のuser IDを、そのまま信頼する設計とは区別します。

マネージドMemoryコネクタがGateway targetとMemoryのdata planeを接続し、十二のMemory操作をCedar actionとして公開します。request属性を条件にできるため、同じ認証済みユーザーでも読み取りと別の操作を分けられます。「認証済みだから全記憶を読める」という粗い管理から、identity・対象・操作を結び付ける方向です。

ただし記事は機能発表で、攻撃試験や遅延測定はありません。Gatewayを経由しない経路まで自動的に守るという保証も読み取れません。面接への応用として、別tenantのnamespace、偽のclaim、許可しない操作で拒否されることを確かめ、直接アクセスの権限も点検する方法を説明できます。

**注目ポイント：★★★★★**

記憶の分離を認証済みidentityとCedar条件で説明できます。

### ③ GitHub Copilot Enterpriseでデフォルトモデル設定機能を提供開始

**出典：CodeZine**

**原文：** https://codezine.jp/news/detail/29564

GitHubは九月二日、Copilot Business/Enterpriseの企業管理設定で、新規会話の既定モデルを指定する機能を一般提供しました。CodeZineの見出しはEnterpriseですが、本文と[公式変更履歴](https://github.blog/changelog/2026-09-02-enterprise-managed-settings-support-any-default-model/)ではBusinessも対象です。対象クライアントはCopilotアプリ、CLI、VS Codeです。

全社の既定値に加え、企業teamの所属に応じて違う既定値を使えます。`model`を`overridable`にし、`team-mappings.json`からteam構成を対応付けることが条件です。該当しない利用者は全社設定を継承します。既定値と例外の関係が明示されるので、個人ごとの設定のばらつきを抑えながら用途差を残せます。

ただし対象は新規会話の初期モデルであり、他モデルの全面禁止や、進行中会話の一括切替を示す発表ではありません。モデルの応答品質や費用が改善したという比較実験もありません。面接では、全社標準、team例外、継承先を決め、各クライアントで新規会話を開いて期待した設定になるかを確認する説明へつなげます。

**注目ポイント：★★★★★**

既定値、上書き可能な例外、利用禁止を分けます。

### ④ 要求が桁違いに上がるAIエージェント時代。スピード、スケール、コストを満たすデータ基盤とは

**出典：DeveloperZine**

**原文：** https://codezine.jp/article/detail/29184

ClickHouseの講演レポートは、Text-to-SQLの動的なSQL、Agentの多数の並列照会、AI SREの事前分析によって、予測できる人間の利用を前提にしたDB設計が変わると説明します。三ページ全ての公開本文を確認しました。広告企画の講演であり、他社DBに対する「一億行から遅い」などの整理は講演者の一般化で、全構成に共通する上限としては採用しません。

高速化の説明は四点です。列指向で必要列だけを読み、同種データを圧縮します。INSERTがimmutableなPartsを作り、SELECTがその時点のPartsを読むことで、取り込みと参照の競合を抑えます。さらにサーバー間とCPUコア間へscanを分散し、SIMDとJITで処理を効率化します。Cloud版は計算と保存を分離し、複数zoneやScale-to-Zeroを組み合わせますが、全workloadで必ずミリ秒になるという保証ではありません。

CostBenchの43queryによる23～101倍の費用効率はClickHouse自身の比較です。Netflixの一日5PB、毎秒1,250万件、500～1,000QPSと最適化4.3倍、eBayの一分十億件以上、圧縮30倍、費用90％減は別々の顧客事例です。データ、比較前の構成、算出方法が同じでないため、自社の削減率へ転用しません。

Agentic Data Stackは中央のClickHouseへ、PostgresのCDCやClickPipesからデータを集めます。LibreChat系のAgentはMCPを介してDBのユーザー権限内で分析し、ClickStackはOpenTelemetryとAI Notebooksで障害を調査し、Langfuseは会話・費用・遅延・prompt版・回帰評価を扱います。五分のdashboardデモは講演の事例で、導入全工程の所要時間ではありません。

自社基盤の説明では四十以上のsource、十四兆行、10PB超を集め、Airflow、S3、dbtで取り込みと変換を行います。dbtの表・列の説明を意味情報へ使い、結合関係をSkillにまとめ、Langfuseの観測を改善へ返す点が重要です。面接では高速なDBだけでなく、指標の定義と権限を渡し、生成SQLの正しさを確認する設計まで話せます。全データ統合や高圧縮が、自動的に全回答の正しさを保証するわけではありません。

**注目ポイント：★★★★★**

DBの速度を、意味情報と評価を含む全体設計へ結び付けます。

### ⑤ Microsoft Agent Frameworkの新機能「チャネル」リリース

**出典：CodeZine**

**原文：** https://codezine.jp/news/detail/29554

Microsoft Agent Frameworkのchannelsは、Pythonの同じAgentやworkflowを複数の入口へ公開するための更新です。共有の`agent-framework-hosting`と、Responses、Telegram、A2A、MCP別のpackageで構成します。Agent本体を各SDKに作り直すのではなく、境界で要求と結果を変換します。

[Microsoftの元記事](https://devblogs.microsoft.com/agent-framework/introducing-agent-and-workflow-channels/)では、AgentStateがtargetとsessionを、WorkflowStateがworkflowの解決を扱います。Responsesは入出力変換、Telegramはupdateと送信操作、A2Aはnative SDK型、MCPはtool公開を担当します。既存のweb frameworkやSDKを使い続けられます。

ただしrouting、認証・認可、保存、background処理、配備はアプリの責任です。同じ会話を複数channelで続けるには、認証済みの利用者を同じsession IDへ結び付ける処理が要ります。原文の`resolve_session_id`は説明用のアプリ関数で、frameworkに付属するAPIではありません。workflowのcheckpoint対応付けや同時更新の制御もアプリ側に残ります。

発表とsampleであり、複数channelの遅延や障害回復の比較実験ではありません。面接では入口追加による再実装の削減と、identityを誤結合すると他人の履歴を共有する危険を同時に説明できます。channel間で意図的に履歴を分ける設計も選べます。

**注目ポイント：★★★★★**

プロトコル変換と、identity・session管理の責任を分けます。

## 3. 面接で使えるポイント

### 話題1：AI Agent / Identity / Security Governance

**質問：**

> AIエージェントの所在を把握した後、何を管理しますか。

**30秒回答：**

> 接続先と、実行できる操作を管理します。Oktaの調査では、所在が見えても約八割が過剰権限を心配しています。SSOやMFAは入口の保護で、下流のツール操作まで認めるものではありません。Agentごとに責任者と利用範囲を決め、不要な権限を外します。ただし棚卸しだけで終えず、不正な操作を見つけたときに、誰がいつアクセスを止められるか確認します。

**関連Project（学習用）：** Agent台帳と失効手順の演習

**キーワード：** `Agent Identity` / `SSO` / `MFA` / `権限失効`

### 話題2：AWS / Agent Memory / Access Control

**質問：**

> 複数利用者のAIメモリを、どう分離しますか。

**30秒回答：**

> 認証した利用者と、読める記憶を結び付けます。AgentCore Memoryでは、JWTの情報からnamespaceを決め、Cedarで操作を制限できます。アプリが毎回検索条件を付ける方法より、共通の境界で確認しやすくなります。ただしGatewayを通らない経路も確認が必要です。別の利用者の記憶や、許可していない操作を要求して、正しく拒否されることを確かめます。

**関連Project（学習用）：** 二つの利用者の記憶分離試験

**キーワード：** `AgentCore Memory` / `JWT` / `Cedar` / `namespace`

### 話題3：GitHub Copilot / Enterprise Governance / Model Policy

**質問：**

> 開発チームごとに、AIの既定モデルを変えるならどう管理しますか。

**30秒回答：**

> 全社の標準と、チームの例外を分けます。Copilotではmodelを上書き可能にし、team-mappings.jsonで所属に応じた設定を渡せます。対象外の利用者は全社の既定値を継承します。ただしこれは新しい会話の初期値で、他モデルの禁止とは別です。チームを移った場合も含め、アプリ、CLI、VS Codeで期待したモデルが選ばれるかを確かめます。

**関連Project（学習用）：** team別既定値の確認表

**キーワード：** `Copilot` / `model` / `overridable` / `team-mappings.json`

### 話題4：AI Agent / Data Platform / SRE

**質問：**

> AIが分析するデータ基盤で、DBの速度以外に何を整えますか。

**30秒回答：**

> データの意味と、利用範囲を整えます。ClickHouseの事例では、dbtの表や列の説明を辞書にし、結合関係をSkillへまとめています。Langfuseで実行を観測し、不足情報を基盤へ戻す流れです。ただし高速なSQLでも、集計の粒度が違えば答えは誤ります。生成したSQLを既知の値と比べ、MCP経由でも利用者の権限内で読んでいるかを確かめます。

**関連Project（学習用）：** dbt辞書付き集計の評価

**キーワード：** `ClickHouse` / `dbt` / `Skill` / `Langfuse`

### 話題5：Agent Framework / A2A / MCP / Hosting

**質問：**

> 同じAIを複数の窓口へ公開するとき、何を共通化しますか。

**30秒回答：**

> Agent本体を共通にし、入口の変換を分けます。Agent Frameworkのchannelsは、ResponsesやTelegram、MCPへの入出力を変換します。ただし認証とsessionの対応付けはアプリ側です。同じ利用者なら会話を続けられますが、別の人の履歴を結び付けてはいけません。利用者の確認、同時更新、保存先を決め、窓口を変えても正しい履歴が見えるか試します。

**関連Project（学習用）：** 二つの入口のsession隔離試験

**キーワード：** `Agent Framework` / `channels` / `AgentState` / `session ID`

## 4. 今日の技術テーマ

```text
認証したidentity → 操作の認可 → 読める記憶・データ → 結果の評価
                 ↘ sessionの対応付け ↗
```
既定値は使い始める選択、認可は実行してよい範囲です。共有化する場所が増えるほど、この二つとidentityの対応を明確にします。
