### ① AI Gateway「Bifrost」の本番導入で、Technical Project Manager が担ったこと

**出典：LayerX Engineering Blog**

**原文：** https://tech.layerx.co.jp/entry/2026/08/28/180027

LayerXのAi Workforceは、テナントごとに異なるデータ処理地域、LLM障害への対応、利用状況の観測を共通化するためBifrostを導入しました。呼び出しの各所へ地域判定や再試行を実装すると抜けや差が生まれます。TPMは課題を三つに整理し、選択肢と不採用理由をADRへ残しました。

比較はアプリ内実装、Azure API Management、LiteLLM、Bifrostです。Bifrostのコアは外部middlewareなしで動きますが、本番ではAzure Container AppsとPostgreSQLを使い、設定、監査ログ、Virtual Keyを永続化します。Redisが不要という評価を「本番もDB不要」と書き換えません。自前運用の費用見込みも今回の規模での比較です。

アプリはテナントの地域条件に合うVirtual Keyを選び、Gatewayは `provider_configs` の `allowed_keys` で利用先を制限します。USの例ではglobal用へ結び付けず、将来の切り替え先にも地域条件を保つ構成です。具体的な認証情報はKey Vaultへ寄せ、Azure OpenAIへはManaged Identityを使います。互換APIで変更を抑えつつ、直接呼び出しへの迂回を開発工程でも検査します。

`gen_ai.*` のトレースとメトリクスをCollectorからDatadogへ送り、プロンプトや応答の本文は監視SaaSへ送らないよう処理します。メトリクスの属性は種類が少ないものへ絞ります。SLOと監視を整え、バーンレートアラートは整備を進めている段階です。Gateway自体の停止が広く影響するリスクもADRへ含めています。

本番同等のネットワーク制限でリハーサルし、SRE、SWE、TPM、顧客対応側の役割も分担しました。公式5,000req/sはモックOpenAIを用いた参考値で、自社本番の処理実績ではありません。複数プロバイダーへのfailover、端点別流量制限、設定検証の自動化は今後の課題です。面接では地域制約を保つ切り替えと、単一の制御点を運用する責任を説明できます。

**注目ポイント：★★★★★**

地域条件と可用性を同時に守る経路設計を、実装と運用の両面から話せます。

### ② AWS DevOps Agentがリソースを更新できるようになったので試してみた

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/devops-agent-directed-actions/

AWS DevOps AgentのDirected actionsは、調査や提案に加えてリソースを変更する機能です。既定は無効で、Agent Spaceの有効化、アカウントごとのaction role、実行時の承認が必要です。第三者ツールでは分類も独立した層です。権限を登録しただけで以後の変更を包括的に任せる構成ではありません。

信頼ポリシーには `sts:AssumeRole`、`sts:SetSourceIdentity`、`sts:TagSession` が必要です。SourceAccountとSourceArnで引き受け元を限定し、承認者をCloudTrailに結び付けます。roleのpolicyは最大範囲で、実際の一操作は承認されたactionとresourceへsession policyでさらに狭まります。

広いAWS管理policyには削除系も含まれますが、Agentは独立に削除、permissions boundary変更、PassRoleを必要とする操作を拒否します。[公式説明](https://docs.aws.amazon.com/devopsagent/latest/userguide/working-with-devops-agent-working-with-directed-actions.html)でも承認はこの制約を上書きしません。アプリ側の拒否とIAMの権限を同一視せず、role自体を狭くする設計を考えます。

著者は八月28日、primary accountの検証用Lambdaで `tag_resource` を試しました。テンプレートによるrole保存はSTS検証で失敗し、原因は未特定です。自動作成へ変えると進み、Agent Space IDを含むタグ値、ARN、role、APIパラメータを承認画面で確認できました。承認前は実行されず、承認後の空レスポンスだけでなくコンソールでタグを確認しています。

タグ一件の確認は、障害復旧全体やsecondary accountの実証ではありません。Athenaの結果保存への適用も原文では可能性です。面接では設定・承認・一時権限・実状態の読み直しをつなぎ、Agentの成功説明だけで完了にしない手順を話せます。

**注目ポイント：★★★★★**

権限の上限と一回の許可、実行結果の確認を分けて説明できます。

### ③ Claude Code v2.1.248 の主要アップデート - ツールを制限する --restricted の追加

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/20260828-cc-updates-v2-1-248/

Claude Code v2.1.248の `--restricted` は、明示的に `--tools` で指定しない限りコード実行系の組み込みツールやWebFetchを外し、ファイル操作を作業ディレクトリへ限定します。bypassPermissionsを拒否し、ユーザー・プロジェクト・ローカル設定を無視します。ただしファイル操作を範囲内へ制限することは、すべての書き込みを禁止することと同じではありません。

著者は一時ディレクトリで両条件に `--strict-mcp-config` を付け、stream-jsonの `system/init` を比較しました。Bash、CronCreate、Monitor、RemoteTrigger、WebFetch、Workflowが外れ、permissionModeはauto→default、pluginsは6→0、skillsは91→17でした。Glob/Grepの表示差は通常側の遅延読み込みが理由と考察され、新機能の追加とは扱っていません。

重要な反例は、`--restricted` だけではclaude.aiコネクタのMCPが残ったことです。外部接続も絞るならstrict MCP設定を合わせ、管理設定と `--settings` は引き続き適用される点を確認します。この測定は一環境の初期イベント比較で、全操作の禁止を証明した侵入試験ではありません。

更新はOAuth更新によるツール定義の再描画が約一時間ごとのcache missを起こす問題や、background worktreeのロック保持も修正します。Workflowの説明約5.7k→1kは参照資料をskillへ移した結果で、全会話の入力が同率で減るわけではありません。`headersHelper` の401再試行や、hookのJSON不正をエラーとして返す変更もあります。

未コミットの資格情報関連ファイルをクラウドへ送る問題、Desktop/Coworkの保存期間、dispatchのshift+enter改行・ctrl+enter送信も変更対象です。面接では制限フラグの名前で安心せず、残るツールと設定源を観測して読み取り用途の条件を作れます。

**注目ポイント：★★★★★**

制限の名前と実効権限を分け、残った外部接続を確認できます。

### ④ Batch APIと同じ料金で使えるOpenAI APIのFlex processingを試してみる

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/openai-flex-processing/

Flex processingは、ResponsesまたはChat Completionsの通常要求に `service_tier: "flex"` を加え、待ち時間と一時的な資源不足を許容して低料金で結果を受け取る方式です。JSONLを提出するBatchと違い、同じ要求で返ります。記事時点のterra短文脈では百万token当たり入力2→1ドル、出力12→6ドルなどBatchと同単価でした。対応モデルや現行料金は別途確認する条件です。

著者の実験はgpt-5.6-terra、各100回・最大20並列、二文以内の日本語判断と要約、平均入力約190・出力約65、effort none、cacheなし、再試行なしです。完了までのp50はStandard1.77秒/Flex1.68秒、p95は2.62/2.22秒、最大3.28/2.99秒で、双方100件成功しました。

料金計算は実際のtoken量からStandard0.1162ドル、Flex0.0590ドルです。出力数が6,516対6,660と異なるため厳密な半額ではありません。同じtoken数の単価比較と、生成が変わる実際の総額を区別しています。今回Flexが少し速くても、著者は別の利用で混雑時の失敗や再試行を経験しており、速度保証にはできません。

[公式ガイド](https://developers.openai.com/api/docs/guides/flex-processing)は429 Resource Unavailable時は課金されず、指数バックオフまたは通常処理への切り替えを説明します。十五分timeoutの例は完了保証ではありません。SDKの自動再試行設定も実験条件とそろえる必要があります。面接では期限、再実行の安全性、切り替え後の料金まで見て、評価や後処理への適用を判断できます。

**注目ポイント：★★★★★**

再試行なしの実験と本番の再試行込みの費用・期限を分けて説明できます。

### ⑤ GitHub Copilot、エンタープライズ向けにプラグイン自動更新機能を追加

**出典：CodeZine**

**原文：** https://codezine.jp/news/detail/29479

GitHubの八月26日の発表は、Enterprise managed settingsからマーケットプレイス単位の自動更新を指定できる機能です。`extraKnownMarketplaces` の各項目で `autoUpdate: true` を設定すると、対応クライアントがそこを確認し、その配布元から入れたプラグインを更新します。

自動更新を許可することと、導入元を許可することは別です。実効 `strictKnownMarketplaces` に認められた配布元である必要があり、autoUpdateで許可リストを迂回しません。公式参照ではfalseは自動更新の無効を強制し、省略時は既存の既定・ユーザー設定へ従います。

[原発表](https://github.blog/changelog/2026-08-26-enterprise-managed-settings-now-support-autoupdate-for-plugin-marketplaces/)はCopilot Business/EnterpriseのApp、CLI、VS CodeでGAとしています。全IDEや全プラグインの同時更新保証ではなく、具体的な更新間隔や不具合減少率は示していません。

面接では許可済み配布元を選び、対象クライアントで更新後の版と代表的なスキルの動作を確認する運用を説明できます。更新作業の削減と、内容の正しさの検証は別の責任です。昨日のOpenAIの提出時snapshotとは別製品・別方式で、混同しません。

**注目ポイント：★★★★★**

自動更新と許可リスト、導入後の検証を分けられます。

### 話題1：AI Gateway / LLMOps / SRE

**質問：**

> AI Gatewayで障害時に接続先を変える場合、何を守りますか。

**30秒回答：**

> 切り替え先でも、テナントの処理地域を守ります。LayerXのBifrost構成はVirtual Keyごとに使えるprovider keyを絞り、US用がglobalへ流れないようにしています。ただし接続できるだけでは十分でなく、モデルの品質やツール互換性も確認が必要です。Gateway自体の障害も監視し、本番と同じネットワーク条件で、許可した経路だけが使われるかを検証します。

### 話題2：AI Agent / AWS / Security

**質問：**

> 運用エージェントへリソース変更を任せるとき、どう確認しますか。

**30秒回答：**

> ロールの上限と、一回の承認を分けます。DevOps AgentのDirected actionsは、Spaceの有効化とアカウント別ロールが必要で、実行時は承認した操作と資源に権限が絞られます。ただし削除などは承認しても実行できません。Lambdaのタグ更新例のように、APIパラメータを確認し、成功の返答だけで終えず、変更後の資源とCloudTrailまで照合します。

**関連Project（学習用）：** 承認と監査を結ぶ運用変更

**30秒回答：**

**関連Project（学習用）：** 残存ツールを確認するレビュー環境

## C-3. JLPT文法

### 1. ～に応じて
**Level：N2｜意味：** 条件や変化に合わせて、対応を変えること。  
**形：** `名詞 + に応じて / 名詞 + に応じた + 名詞`  
**使い方：** 名詞に接続し、条件と対応の関係を示します。  
**例：** `TenantのData Residency要件に応じて、利用するVirtual Keyを切り替えます。`  
**補足：** 名詞に接続し、条件と対応の関係を示します。

### 2. ～一方で
**Level：N2｜意味：** 同じ事柄の、対照的な二つの側面を述べること。  
**形：** `普通形 + 一方で / 名詞・な形容詞 + である + 一方で`  
**使い方：** 前後は逆の評価や異なる側面でもつなげられます。  
**例：** `Flex processingはコストを抑えられる一方で、Latencyの変動や一時的なResource不足を考慮する必要があります。`  
**補足：** 前後は逆の評価や異なる側面でもつなげられます。

### 3. ～たうえで
**Level：N2｜意味：** 前のことを済ませ、それを前提として次の行動をすること。  
**形：** `動詞た形 + 上で / 名詞 + の上で`  
**使い方：** 単なる順序だけでなく、必要な準備・確認の意味を含みます。  
**例：** `実際のUsageとRetry率を計測したうえで、Flexへ切り替えるTaskを決めます。`  
**補足：** 単なる順序だけでなく、必要な準備・確認の意味を含みます。

### 4. ～かねない
**Level：N2｜意味：** 望ましくない事態が起こる可能性があること。  
**形：** `動詞ます形から「ます」を取る + かねない`  
**使い方：** 動詞のます形から「ます」を除いて付けます。通常は悪い結果に使います。  
**例：** `Pluginを無条件に自動更新すると、不具合のあるVersionを組織全体へ広げかねません。`  
**補足：** 動詞のます形から「ます」を除いて付けます。通常は悪い結果に使います。

### 5. ～にとどまらず
**Level：N1｜意味：** ある範囲だけでなく、さらに広い範囲にも及ぶこと。  
**形：** `名詞 + にとどまらず / 普通形 + にとどまらず`  
**使い方：** 前の範囲から後ろへ話題を広げます。  
**例：** `AI Gatewayの役割はModel Routingにとどまらず、Secret管理やObservability、Data Residencyにも及びます。`  
**補足：** 前の範囲から後ろへ話題を広げます。

### 6. ～を余儀なくされる
**Level：N1｜意味：** 外部の事情で、望まない行動や変更をせざるを得なくなる。  
**形：** `名詞 + を余儀なくされる`  
**使い方：** 名詞につなげる硬い表現です。資源不足で切り替えが必要になる状況などを述べます。  
**例：** `Resource不足が長時間続けば、一部TaskをStandardへ戻す対応を余儀なくされる可能性があります。`  
**補足：** 名詞につなげる硬い表現です。資源不足で切り替えが必要になる状況などを述べます。

### 7. ～に至るまで
**Level：N1｜意味：** 範囲が最後の細かな対象まで広がることを強調する。  
**形：** `名詞 + に至るまで`  
**使い方：** 「～から～に至るまで」の形で、接続から監視までの広い責任を示せます。  
**例：** `AI Gatewayでは、Provider接続からSecret管理、SLO設計に至るまで一貫して運用方針を整える必要があります。`  
**補足：** 「～から～に至るまで」の形で、接続から監視までの広い責任を示せます。
