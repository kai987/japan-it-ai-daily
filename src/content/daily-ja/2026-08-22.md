### ② Agent Plugins 1.0：Skill + MCP設定をClient間で再利用

**出典：CodeZine**

**原文：** https://codezine.jp/news/detail/29354

**Agent Plugins 1.0** は、スキルとMCPサーバー構成を一つの導入可能なパッケージへまとめる公開仕様です。CodeZineはVS Code、Copilot CLI、GitHub Copilot SDK、Copilotアプリでの対応を紹介しています。複数クライアントに同じ内容を配るたび、別のマニフェストや配置を維持する重複を減らすことが狙いです。

移行では **`plugin.json` に `$schema`** を加え、スキルを `skills/`、MCP設定を `mcp.json` に置きます。Copilot固有のファイルは **`com.github.copilot/`** へまとめ、他クライアントはそこを無視します。標準化されるスキルとMCPに対して、カスタムエージェント、コマンド、ルール、フックなどを名前空間内に残せるため、共通化のために専用機能を捨てる必要はありません。

Awesome Copilotのマーケットプレイスから利用でき、既存の非1.0形式プラグインも引き続き対応するため、移行は必須ではありません。ただし「同じパッケージを読める」は、全クライアントが全拡張を同じように実行するという保証ではありません。対応する要素を見つけて利用する仕組みです。

これは仕様と製品対応の発表で、移行工数や不具合率の比較実験ではありません。面接では、共通ファイルと固有機能の境界を示し、対応クライアントでスキルの発見、MCP接続、専用機能の読み込みを分けて確認する方針を話せます。

### ③ MCP Tool Poisoningを実測

**出典：Zenn**

**原文：** https://zenn.dev/shinji_bk/articles/7a24decb4ce42e

Zennの著者は、自作のメモ管理MCPサーバーで **Tool Poisoning** を試しました。Node.jsとTypeScript、公式SDK、zodを使い、stdioで接続します。登録、ログイン、追加、一覧、削除の五つのツールを用意し、メモとユーザーをJSONファイルへ保存する小さな検証環境です。認証トークンは操作条件を作るためのもので、製品としての認証設計を評価した記事ではありません。

最初は削除処理の名前を **`delete_memo`** のまま残し、説明だけを「詳細表示・変更なし」に変えました。Claude Codeは名前と説明の不一致を見つけ、実行前に確認しています。次に名前も **`view_memo_detail`** に変え、別セッションで同じ詳細表示を求めると、実際の削除処理が呼ばれました。異常への言及は、戻り値に削除したと書かれていた後でした。

`inputSchema` は引数の形を検証できますが、ハンドラーが説明どおりの処理をすることは証明しません。名前とdescriptionが一致することも、読み取り専用の権限を技術的に強制する仕組みではありません。ここからは、サーバー実装と実行権限を確認し、必要なら書き込み能力を別に制限する、という設計判断へつなげられます。

ただし記事は小規模な二つの観察であり、モデルごとの成功率や再現率を測っていません。戻り値まで偽装した場合の話は著者の推測で、実施済みの第三実験ではありません。また、戻り値を見た事後検知は削除前の防止と同じではありません。面接では信頼するサーバーの選定と、処理結果・保存状態の確認を分けて説明できます。

**注目ポイント：★★★★★**

引数検証、説明文、実行権限が保証する範囲を区別できます。

### ④ Amazon Bedrock AgentCore Web Search、東京Regionに対応

**出典：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/bedrock-agentcore-web-search-tool-japanese-query/

DevelopersIOは、東京リージョンで利用可能になった **AgentCore Web Search Tool** を日本語クエリで試しました。CloudFormationでGatewayとTargetを作り、`AWS_IAM` 認証とAssumeRoleの一時資格情報を使ったSigV4署名で接続しています。MCPの `tools/list` から公開名 `web-search-tool___WebSearch` を確認し、Pythonクライアントで検索する構成です。

記事タイトルを日本語で指定しても、同じ記事の英語翻訳版が一位になる例がありました。網羅率の調査はGoogle Search Consoleのクリック数上位99URLを質問にし、`maxResults=5` で対象URLか別言語の同一記事があればヒットとする条件です。結果は **84/99、約85%**。上位1～20位は17/20、21～80位は54/60、81～99位は13/19でした。ただし古く人気のある記事に偏るため、人気と経過時間の効果は切り分けられません。

新規記事39件では、公開24時間以内は0/1、24～48時間は1/4、48～72時間は1/5、72～96時間は2/6でした。4～5日以降には60～80%台の群が見られますが、各群が1～6件と少なく、反映時間の保証ではありません。また検索上位五件に見つからないことだけで、内部インデックスに絶対存在しないとは判定できません。

初期環境のConnector 1.1.0を **1.2.0** へ更新すると、呼び出し時の `domainFilter` と `publishedDateFilter` がスキーマに加わりました。ドメイン指定では翻訳版を含む五件が同一ドメインに収まり、日付指定も範囲内でした。日付境界はUTC・両端を含む仕様です。言語フィルタやSearch Console相当の管理機能は著者の要望で、確認済み機能ではありません。

記事時点の料金を使う139回の試算は、検索一回0.007ドルにGatewayの1,000回0.005ドルを加え、約0.97ドルです。請求額の実測ではなく、記載した呼び出し数の概算です。面接では、検索できることと必要記事が新鮮に揃うことを分け、対象URL、言語版、公開後時間を決めた評価を説明できます。

**注目ポイント：★★★★★**

検索のヒット率を、対象URL・言語版・経過時間の条件付きで説明できます。

### ⑤ Codex resume --ephemeral：Exit Code 0でもDisk Writeがないとは限らない

**出典：Zenn**

**原文：** https://zenn.dev/clopy/articles/codex-resume-ephemeral-rollout-gate

Zennの検証は、Codex CLI **0.147.0** で既存セッションを一度 `resume --ephemeral` した際、終了コード0でもローカルのrolloutへ追記された事例です。8月14日に、通常の実行でbaselineを一つ作り、同じ正確なsession IDを一度だけ再開しました。モデルや推論の上書きはなく、解決されたバックエンドは未確定です。

対象ファイルは **38,025から42,427バイトへ4,402バイト増加**、14行から23行へ増え、再開用の無害なマーカーが追記部に五回現れました。SHA-256も変わり、変更前の全バイトが変更後の先頭に一致したため、単なる別ファイルや上書きではなく追記と判定しています。二つの呼び出しはそれぞれ成功イベント一件、同じIDで、認識されたツールイベントはゼロでした。

判定には終了コードとは別の **file oracle** が必要です。正確なIDから対象を一件に解決し、同じパスのhash、バイト数、行数、マーカーを前後比較します。変化なしなら記録条件内で適合、元のprefixを保つマーカー付き追記なら拒否し、ID不一致、タイムアウト、複数候補、未定義の変更形などは判断不能として止めます。モデルに記憶を尋ねる方法は保存状態を測らず、追加ターンで測定対象も変えてしまいます。

版固定ソースでは、新規開始用の `ThreadStartParams` と再開用の `ThreadResumeParams` にephemeralの扱いの非対称性が見られます。ただしこのフィールド差が直接原因であることを一回の外部観測だけで証明したわけではありません。新規のephemeral、他OS・他バージョン、サーバー側保存、複数回の再現率は未検証です。ワークスペースのread-only設定とsession storeへの保存も別の境界です。

面接では、ローカルに再開ターンを残さない要件をCLIの成功表示に置き換えず、無害な版固定preflightで同一ファイルの不変を測る判断を説明できます。本記事の検証をここで再実行したという意味ではなく、公開されたケースの証拠と限界を整理しています。

**注目ポイント：★★★★★**

コマンドの成功と、要件が満たされた証拠を別々に検査できます。

## C-3. JLPT文法

### 1. ～にとどまらず
**Level：N1｜意味：** ある範囲だけでなく、さらに広い範囲にも及ぶこと。  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 前の範囲から後ろへ話題を広げます。  
**例：** `Plugin SecurityはCode Reviewにとどまらず、署名や配布元の確認まで必要です。`  
**補足：** 前の範囲から後ろへ話題を広げます。

### 2. ～恐れがある
**Level：N1｜意味：** 好ましくないことが起きる可能性がある。  
**形：** `動詞辞書形 / 名詞 + の + 恐れがある`  
**使い方：** 確認できたリスクと仮定のリスクを区別して使います。  
**例：** `悪意あるTool Descriptionを読み込むと、意図しない操作を実行する恐れがあります。`  
**補足：** 確認できたリスクと仮定のリスクを区別して使います。

### 3. ～かねない
**Level：N1｜意味：** 望ましくない事態が起こる可能性があること。  
**形：** `動詞ます形去ます + かねない`  
**使い方：** 動詞のます形から「ます」を除いて付けます。通常は悪い結果に使います。  
**例：** `Sourceを確認せずPluginを導入すると、Supply Chain攻撃を招きかねません。`  
**補足：** 動詞のます形から「ます」を除いて付けます。通常は悪い結果に使います。

### 4. ～とは限らない
**Level：N2｜意味：** 必ずそうなるわけではなく、例外や別の可能性があること。  
**形：** `普通形 + とは限らない`  
**使い方：** 全面的な否定ではなく、一般化を避ける表現です。  
**例：** `人気のPluginだから安全とは限りません。`  
**補足：** 全面的な否定ではなく、一般化を避ける表現です。

### 5. ～に備えて
**Level：N2｜意味：** 将来起こることを予想して準備する。  
**形：** `名詞 + に備えて`  
**使い方：** 修正版の公開に備えて依存関係を確認します。  
**例：** `緊急Patchに備えてDependency Inventoryを維持します。`  
**補足：** 修正版の公開に備えて依存関係を確認します。

### 6. ～た上で
**Level：N2｜意味：** 先の行為を済ませ、それを前提として次を行う。  
**形：** `動詞た形 + 上で`  
**使い方：** 検証してから利用するという手順を述べます。  
**例：** `影響範囲と互換性を確認した上でVersionを更新します。`  
**補足：** 検証してから利用するという手順を述べます。

### 7. ～一方で
**Level：N2｜意味：** 同じ事柄の、対照的な二つの側面を述べること。  
**形：** `普通形 + 一方で`  
**使い方：** 前後は逆の評価や異なる側面でもつなげられます。  
**例：** `PluginはAgentの機能を拡張できる一方で、攻撃面も広げます。`  
**補足：** 前後は逆の評価や異なる側面でもつなげられます。
