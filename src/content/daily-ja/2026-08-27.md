### ① LINEヤフー Agent i：Agent BuilderとAgent Runtimeで「作りやすさ」と本番安全性を両立

**出典：LINEヤフー Tech Blog**

**原文：** https://techblog.lycorp.co.jp/ja/20260826a

LINEヤフーのAgent i基盤は、最初のマルチエージェント構想から、一つのエージェントを作る難しさへ課題を捉え直しました。企画や営業が業務知識を試せるよう、用途を絞ったノーコードの **Agent Builder** と本番処理の **Agent Runtime** を内製しています。高度な制御まで全員が画面だけで作れるという設計ではありません。

BuilderはReact Flowでノード・エッジを編集し、共通の中間表現IRを生成します。公開前に到達可能性や接続関係を検証して構造の誤りを返します。Structured Outputsでは入力項目からJSON Schemaを作り、利用者に専門記法を直接要求しません。Runtimeは検証済みIRをLangGraphへ変換・コンパイルし、分岐、繰り返し、状態を処理します。

Kubernetes Namespaceを環境別に分けた論理サンドボックスへネットワークACLを組み合わせ、MCP、文書、内部APIへのアクセスを実行時にも確認します。認証情報はワークフローに埋め込まず必要時に取得します。環境別の負荷を局所化できますが、Namespaceという名前だけで通信の隔離まで成立すると読みません。

負荷試験ではCPU・メモリを調整した後、レプリカを増やすと帯域が次のボトルネックになりました。著者はメトリクスと再現条件を絞り、エージェントにスタブ、ログ調査、テスト観点を任せ、人が方針と最終確認を担ったと説明しています。具体的な最大同時数や短縮率は公開されていません。

Gatewayは認証と共通部分の変換を受け持ち、画面用のカード・フォーム定義は利用サービスへそのまま渡します。現在は独自プロトコルで、A2AやMCPによる外部からの接続は将来方針です。社内データへMCPでアクセスする現行機能とは区別します。面接では編集UI、実行、接続互換性の責任分担と、スケール後の別の詰まりを説明できます。

**注目ポイント：★★★★★**

Reactの編集画面から実行グラフまで、変換と検証の責任を具体的に説明できます。

### ② LINEヤフー：AI活用率100％のQA組織をつくるまで

**出典：LINEヤフー Tech Blog**

**原文：** https://techblog.lycorp.co.jp/ja/20260826b

約二十人のLINEヤフーのプロダクトQAユニットは、情報収集や成果物作成のAI活用を、得意な個人だけに依存しない形へ移しました。QAAPはCodex CLI/Appと使うGitテンプレートで、専門スキル、社内MCP、設定用スクリプトを共有します。利用者はForkし、Upstreamの対策をSyncしてそろえます。

秘密情報は暗号化ストレージで管理し、入力直前のパターン検出、実行ポリシーによる直接読み取り制限、PR前の静的検査という三層を置きます。ブロック理由と直し方もその場で示します。npmの社内レジストリとインストールスクリプトの抑止、復元可能な削除操作も標準化しています。これは報告された防御設計で、すべての侵入を防いだ実験結果ではありません。

配布だけでは定着しませんでした。成熟度アンケートで半数以上が補助的利用のLv1〜2と分かり、二月に全員で一日のハンズオンを行い、各自の実業務へ適用しました。その後は一つの利用アンケートを、隔週の全員会議、推進チーム、リーダー会議へ流し、横展開、基盤改善、個別支援を同時に進めました。

社内測定は **テスト実行を除くQA業務** が対象で、作業時間49.4%削減、成果物数1.54倍、AI代替率68.1%です。利用率100%は当該ユニットの指標で、会社全体でも品質正答率でもありません。発表名の10xを測定済みの全業務十倍と読み替えず、観測期間や対照群が示されていない制約も残します。

面接では導入率だけでなく、共通環境が他者の工夫の再現性を上げたこと、利用者の障壁を調べ続ける仕組みを説明できます。QAスキルの詳細は原文で割愛されており、本文で推測して補いません。

**注目ポイント：★★★★★**

利用率と成果指標を分け、共通基盤と学習支援の両方を説明できます。

### ③ GitHub EnterpriseにおけるCopilot統制：AI ControlsとManaged Settings

**出典：Zenn**

**原文：** https://zenn.dev/microsoft/articles/copilot-enterprise-managed-settings0827

Zennの記事はCopilotのAI ControlsとEnterprise managed settingsを分けています。前者は機能・エージェント・モデルを誰に利用させるか、後者は利用時の権限、プラグイン、通信やサンドボックスなどの条件です。モデル有効化のOrganization単位とEnterprise team単位は、原文では選択式で同時併用ではありません。

`.github-private/copilot/managed-settings.json` では `permissions.disableBypassPermissionsMode` の `"disable"` で承認省略を禁止できます。`model: "auto"` は新しい会話の既定値で、ユーザーが会話ごとに別のモデルを選ぶことまで禁止しません。プラグインの有効化と、`strictKnownMarketplaces` による導入元制限も別です。

`allowedMcpServers` を省略すれば拒否以外は許可され、空配列なら組み込み既定サーバーを除きブロックされます。`deniedMcpServers` が許可より優先し、複数の許可リストは共通部分になります。名前・URL・コマンドの一致条件を具体的に試す必要があります。通常の優先順位はMDM、サーバー、ファイル、ユーザーで、CLIのsandboxは厳しい方向に統合する例外です。

テレメトリは送信先とプロンプト・応答を含むかを決め、remoteControlはその端末でホストする会話への操作を制御します。teamの上書きは指定可能なキーと `overridable` に限定され、pluginなどは追加統合です。現行[公式参照](https://docs.github.com/en/enterprise-cloud@latest/copilot/reference/enterprise-administrators/enterprise-managed-settings)には詳細なpermissions規則もあるため、八月の列挙を永久に完全なschemaとは扱いません。

証拠は文書整理と著者の構成画面で、未知の全クライアントへの適用試験ではありません。AI Controls側のMCP許可リストが消えるという原文の予想は未確定のため採用しません。面接では「未指定」「空」「明示拒否」と配布方式を分け、期待した操作が本当に止まるかを確認できます。

**注目ポイント：★★★★★**

設定値の存在だけでなく、空値・優先順位・クライアント対応を確認できます。

### ④ LayerX：TypeSpec × Schema-driven Development × Coding Agent

**出典：LayerX Engineering Blog**

**原文：** https://tech.layerx.co.jp/entry/typespec-in-aiworkforce

LayerXのAi Workforceでは、FastAPIからOpenAPIを出しクライアント生成していたため、サーバー実装を待ってから画面を作る状態でした。そこで実装前にTypeSpecでREST契約をレビューし、両側が並行する流れへ移しました。TypeScriptに慣れたチームでの型表現と読みやすさが選定理由です。

既存九エンドポイントを四方式でエージェントに記述させた比較では、TypeSpec410行、Fern437行、Smithy673行、OpenAPI直書き771行でした。これはこのAPI群と生成条件の比較で、全プロジェクトの生産性やtoken削減率ではありません。OpenAPI出力はemitterに依存し、独自構文や周辺ツールの学習も必要です。

レビュー後はOpenAPI YAMLからOrvalでMSWのモックとSWRクライアントを生成し、バックエンドは契約を満たす実装を並行します。実装側が生成したOpenAPIとスキーマを自作CIスクリプトで比較し、食い違いを検出します。実APIができれば接続を切り替え、モックはテストやStorybookにも残せます。

Discriminated Unionでは `scope` を `workspace` または `groups` とし、後者のときだけ `groupIds` が必要な構造を表します。ただしJSON自体に型はないため、識別プロパティを実際の要求・応答へ含めます。エラーも型として定義し、画面側の処理漏れを減らす材料にします。

著者は並行開発とレビューの改善を実感していますが、MSWモックは想定ほど使われませんでした。バックエンドがエージェントで速くなった可能性は仮説です。API増加後のファイル配置も未標準化で、契約導入だけで保守の課題が消えたわけではありません。面接では型生成に加え、契約レビューとCI差分検出の役割を説明できます。

**注目ポイント：★★★★★**

SWR・MSW・CIを含む、フロントエンドとAPI契約の具体的な連携を話せます。

### ⑤ JetBrains Junie Local：Local Coding Agentをより簡単に導入

**出典：CodeZine**

**原文：** https://codezine.jp/news/detail/29461

CodeZineが紹介するJunie Localは、従来のOllamaなどへの手動接続と違い、選定・調整済みモデルと実行設定をまとめています。`/local` でモデルを取得し、サーバーを起動して切り替えます。発表時はQwen3.6-27Bの4bit、約20GBのダウンロード、M5 Macと64GB RAMという条件です。

[JetBrainsの原発表](https://blog.jetbrains.com/junie/2026/08/junie-local-launch/)では、生成速度だけでなくファイルを読むprefillが大きな負担だと説明します。M5向けの8bit演算によるprefill約40%改善、KVキャッシュ再利用と投機的デコードを挙げています。新しいQwen3.8は安定動作に推論が必要で課題が約四倍遅くなるとして、3.6を選びました。これらはベンダー環境の結果です。

非公開の自社テストでは、推論を無効にした3.6が推論上限一万tokenのSonnet 4.5と同程度で、GPT-5 mediumは少し上でした。テスト集合の全条件が公開されていないため、すべての開発能力の同等性を保証しません。複雑なアーキテクチャ推論では差があると公式も認めています。

重み取得後はオフラインで使え、登録やクレジットは不要ですが、端末・電力・実行時間の負担は残ります。既存skillsやPlan modeを使えることと、外部ツールが通信しないことは別に確認します。ほかのGPUは試作や検討段階で、発表時の一般対応とは扱いません。面接では局所的な推論、ハードウェア条件、課題完了までの時間をそろえて比較できます。

**注目ポイント：★★★★★**

ローカル推論の選定を、生成速度だけでなくprefillと課題の品質で説明できます。
