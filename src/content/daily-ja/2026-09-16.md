### ① AIが書くコード「エラー率はJavaがPythonの6.7倍」　150万「会話」データで分かったAIコーディングの盲点

**出典：＠IT｜2026年9月15日 11:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/15/news047.html

AWSは、**2026年1～6月にKiro IDEで発生した約150万件の会話**と、そこに含まれる**40万6000件の静的解析Tool Call**を分析し、Coding AgentがCode生成中に自分の出力をどこまで検査しているかを調べました。Kiroの `diagnostics` は独自Analyzerだけで完結するものではなく、TypeScript / JavaScriptの `tsserver`、Javaの `jdtls`、Pythonの `Pyright`、Rustの `rust-analyzer`、Goの `gopls`、C/C++の `clangd` など既存のLanguage Serverを利用します。つまり、この分析は最終Codeの品質だけでなく、AgentがStatic Analysisを生成Loopへ自発的に組み込む行動そのものを見ています。

結果として、Coding会話中に `diagnostics` を少なくとも1回呼んだ割合はSonnet 4.5の **2.74％** からOpus 4.6の **22.26％** にとどまりました。Toolが利用可能でも、Modelが自動的に「検査してから完了する」とは限りません。Opus 4.6の言語別ファイルError率はJavaScript 1.6％、Python 4.0％、TypeScript 8.6％、TSX（React）11.2％、Java 26.7％でした。また、Test FileはSource Fileより平均Errorが3～4倍多い傾向も報告されています。Workflowで静的解析を完了条件に組み込み、Errorが残る間は完了をBlockする発想が重要になります。

**Evidence / Measurement：** 約150万会話という実利用Telemetryに基づく点は強い一方、測っているのは `diagnostics` で検出可能な静的問題です。**ただし、**JavaScriptやPythonの低いError率はStatic Analysisが弱いことの影響もあり、CodeがJavaより正しいことを意味しません。`diagnostics` がCleanでもRuntime Error、Logic Bug、Performance劣化は残り得ますし、AWSも改善をModel更新だけに帰属できないと説明しています。Prompt、Hook、Sub-agentなどOrchestration Layerも結果へ影響します。

**注目ポイント：★★★★★**  
AI Codingで重要なのは「Modelが賢くなれば自分で検査する」と期待することではなく、`diagnostics / typecheck / lint / test / review` を**deterministicなCompletion Gate**としてHarness側へ入れることです。React / TypeScript面接でも、TSX 11.2％という数字を単純な言語比較にせず、Static Analysisの検出範囲とTest Harnessの必要性まで説明できると強いです。

### ② GitHub Copilot、モデル自動選択「Auto」に3つのティアを追加 ——コストと品質の重視度を調整可能に

**出典：gihyo.jp｜2026年9月15日**  
**原文 URL：** https://gihyo.jp/article/2026/09/github-copilot-auto-model-selection

GitHub CopilotのModel自動選択 `Auto` に、Cost・Quality・Response Timeの優先度を表す3つのTierが追加されました。**Efficiency** はCostを優先し単純Task向け、**Balance** はCost・Quality・応答時間を総合的に扱い、**Intelligence** はQualityを優先して複雑Taskを想定します。AutoはPrompt単位でModelを判断し、有料Planでは実際に選ばれたModelの料金から **10％引き**で計算されます。Developerが毎回Model名を指定するのではなく、Team PolicyとしてRoutingのIntentを指定する方向に一歩進んだと言えます。

重要なのは、Intelligenceが「必ず最大Modelを使うMode」ではないことです。docstring追加のような単純Taskでは、Intelligenceを選んでいても小型で効率の高いModelが選択される場合があります。また2026年9月15日時点では、VS CodeのCopilot Chat、Copilot CLI、GitHub Copilot Appで候補Modelが一部異なり、Cloud AgentはAutoに対応していても今回の3 Tier対象外です。PlanやAdmin Policyによって利用可能Modelも制限されます。

**Evidence / Measurement：** 今回の記事はGitHubのProduct Specification / Changelogを基にしたもので、TierごとのTask Successや実Cost削減率を比較するBenchmarkではありません。**ただし、**候補ModelはProductやPolicyで変化し、今後追加・削除される可能性もあります。Enterprise導入ではTier名だけをPolicyにせず、`selected model / task category / success / latency / cost` をTelemetryとして残し、自社のRepositoryとWorkloadでRoutingが妥当かを評価すべきです。

**注目ポイント：★★★★★**  
面接では「Autoが便利」ではなく、**Policy-based Model Routing**として説明できます。低Risk・定型TaskはEfficiency、通常作業はBalance、高Risk・複雑TaskはIntelligenceという初期Policyを置き、結果を見ながらCost-per-successで調整する、という設計が実務的です。

AnthropicでMCPを共同設計したDavid Soria Parra氏は、東京で開催された `AGNTCon＋MCPCon Japan 2026` のKeynoteで、MCPの次の重点領域を説明しました。Coding Agentが早期にProduction利用へ進めた理由の一つとして、CompilerやUnit Testのような自動FeedbackでModelを正しい方向へ導けた点を挙げています。一方、Knowledge Worker向けAgentではMicrosoft 365、Google Workspace、Task Managementなど多様な業務SystemとのConnectivityが重要になり、単純なTool Call以上のProtocol設計が必要になります。

講演では、Claude上のMCP経由Tool Callが累計約 **10億件**、MCP SDK Downloadが**月間5億件超**になったと説明されました。MCPはRemote Connection、Authorization、MCP Appsを追加し、2026年7月28日版ではStateless Connectionが正式な方向として強化されています。今後12カ月では、数分・数時間・数週間・数カ月にわたる処理を扱う **MCP Tasks**、ToolとSkillをPackageしてMCP Serverから配布する **Skills over MCP**、さらにAgent自身と「誰の代理で動くか」を識別するIdentity / Authorizationが重点です。

**Evidence / Measurement：** 10億Tool Callや月5億DownloadはKeynoteで示されたAnthropic / MCP Ecosystem側の利用規模であり、独立したMarket Share調査ではありません。**ただし、** `MCP Tasks` や `Skills over MCP` には今後のRoadmap要素が含まれ、現時点で全てが安定したGA仕様という意味ではありません。企業ではCurrent SpecとRoadmapを分け、Long-running TaskのCancellation、Timeout、Retry、Auditと、Agentが誰を代理しているかを確認できるIdentity設計を先に固める必要があります。

**注目ポイント：★★★★★**  
MCP学習を「Serverを増やす」だけで終わらせず、**Task Lifecycle、Skill Registry、Delegated Identity**まで広げるべきだと分かる記事です。Enterprise Agent Platformでは、接続性そのものより「接続した後に誰が何を実行できるか」が次の設計課題になります。

### ④ AIの「脱クラウド・オンプレミス回帰」が66％、「AI案件の中止」も多数――その原因は？

**出典：＠IT｜2026年9月15日**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/spv/2609/15/news031.html

Clouderaの調査「The Great AI Re-Architecture」は、AIがPoCから本格利用へ移るにつれ、Workload配置とData Architectureを企業が見直している状況を示しています。調査は2026年6月5～22日、9市場の **1500人のEnterprise Architect、Cloud Infrastructure責任者、Data Architect**を対象に行われ、日本Sampleは100人です。77％がAIを積極利用している一方、95％は過去1年にData Governance、Compliance、Regulation上の課題を理由としてAI Projectを延期または中止したと回答しました。

特に、**66％** が過去1年にAI WorkloadをPublic CloudからPrivate CloudまたはOn-premへ移したと回答しています。日本では今後の投資先としてOn-prem拡大35％、Cloud拡大31％、Hybrid-first 22％、Edge 12％が示され、Infrastructure Costが増えたという回答は **86％** でした。さらに73％がAIによってData Governanceが複雑化したと回答し、97％は少なくとも月1回、異なる環境間でDataを移動しています。これは「CloudかOn-premか」の二択より、Data LocationとGovernanceを複数環境で一貫させる課題が大きくなっていることを示します。

**Evidence / Measurement：** Sample数、実施期間、対象Roleが公開されたSurveyであり、Enterprise Architecture担当者の認識を読む材料になります。**ただし、**Clouderaが公表したVendor Surveyの自己申告値で、実際のCloud BillやOn-prem TCOを監査した結果ではありません。66％を「AIはOn-premへ戻すべき」と一般化できず、Private環境にはCapacity、GPU Utilization、Patch、Availability、人材Costが新たに発生します。Workload単位で **TCO + Governance + Data Gravity + SLO** を比較すべきです。

**注目ポイント：★★★★★**  
日本企業のAI Infra面接で使いやすい記事です。Cloud信仰・On-prem回帰のどちらかに寄せるのではなく、Data Sensitivity、Regulation、Latency、Utilization、Ops Costごとに配置し、Hybrid環境でも同じPolicyとAuditを適用するという回答につなげられます。

### ⑤ アイカ工業が「AI活用を阻む“表記揺れ”問題」解消へ　データ品質を高める具体策とは？

**出典：＠IT｜2026年9月15日 11:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/15/news040.html

アイカ工業では、生成AIやBI活用を進める前段でMaster Data品質が課題になっていました。顧客・販売Dataが部門や拠点ごとに管理され、表記揺れ、重複、更新漏れがあるため、同じ企業や事業所でもSystemが違うと同一Entityとして扱いにくい状態でした。ModelやEmbeddingを改善しても、Source Dataが不整合ならRetrieval、Aggregation、Answerへその問題が引き継がれます。

同社は `Sansan Data Intelligence` と `Sansan` を導入し、得意先・仕入先などのMasterへ **Sansan Organization Code（SOC）**を付与しました。SOCによって異なるSystem上の同一企業・事業所を関連付け、自動Data Cleansingで表記揺れと重複を解消し、より正確で新しい状態を維持します。加えてSansanで名刺、Email、商談HistoryなどCustomer Touchpointを一元管理し、今後は基幹SystemのMasterと横断利用して営業や経営判断へつなげる方針です。

**Evidence / Measurement：** 記事は、分散Masterという課題、採用したProduct、SOCによるEntity統一、Cleansingの仕組みを具体的に説明しています。**ただし、**「生成AIの回答精度が何％改善した」「重複率が何％下がった」といった定量Outcomeは示されていません。導入後は `duplicate rate / entity match accuracy / freshness / retrieval precision / answer accuracy` を自社KPIとして測り、Master Data Ownerと更新SLAも明確にする必要があります。

**注目ポイント：★★★★★**  
RAGやBIの品質問題をModelだけで解決しようとしない視点が重要です。**Entity統一、Source of Truth、Master Owner、Freshness**を先に整えることがAI Engineeringの一部であり、日本企業のDX・AI導入面接でも非常に実践的な論点です。

## 4. 今日の技術テーマ

# Execution Preconditions：AIが「完了」と言う前に満たす条件を設計する

今日の5本は次のFlowで整理できます。

```text
Task / Business Goal
        ↓
Execution Context
├─ Model / Tier
├─ Tool / MCP
├─ Data / Master
└─ Runtime Location
        ↓
Preconditions
├─ Static Analysis / Test
├─ Identity / Authorization
├─ Governance / Compliance
├─ Cost / SLO
└─ Source Data Quality
        ↓
AI / Agent Execution
        ↓
Evidence
        ↓
Commit / Rollout / Human Gate
```

Top 1が示す通り、`diagnostics`が利用可能でもModelは自発的に呼ぶとは限りません。つまり **Tool AvailabilityはControlではありません**。Completion条件としてHarness側に組み込む必要があります。Top 2ではModel Selection自体がEfficiency / Balance / IntelligenceというPolicyになり、Top 3ではLong-running MCP TaskにIdentity、Delegation、Auditが必要になります。Top 4ではPublic / Private / On-premをExecution Locationとして選び、Top 5ではその前提となるMaster DataのEntityとFreshnessを整えます。

この設計のメリットは、ModelやCloud、Toolを変更してもVerification、Identity、Evidence、Data Qualityの基準を再利用できることです。**ただし、**Preconditionも完全ではありません。Static AnalysisはRuntime Bugを見つけず、Surveyは自社TCOを証明せず、Entity Codeを付けてもAnswer Accuracyは自動では上がりません。Production FailureとBusiness OutcomeからGate自体を更新する必要があります。

国内企業でAgent Workflowを設計するなら、`Input Source / Model or Runtime / Required Checks / Identity & Permission / Evidence / Commit Authority` の6項目を固定しておくと実用的です。Autonomyを一度に最大化するのではなく、Evidenceが揃ったActionだけ次のStageへ進める設計にします。

# B. 重点まとめ・面接で使える知識

## 1. Kiro：AI CodingのSelf-checkをModel任せにしない
- 約150万件のKiro IDE会話で、`diagnostics`を自発的に呼んだ割合は2.74％～22.26％でした。
- Java 26.7％、Python 4.0％などはStatic Error率であり、言語やCode全体の正確性Rankingではありません。
- Test FileのErrorがSource Fileより多い傾向から、Test Code自体もQuality Gate対象にする必要があります。
- Completion GateはPromptのお願いではなくWorkflowで強制します。

**面接ポイント：** `Toolが使える`ことと`Toolを必ず使う`ことは別です。Static Analysis、Test、ReviewをHarness側の完了条件にします。

## 2. GitHub Copilot Auto：Model RoutingをTeam Policyとして扱う
- Efficiency / Balance / IntelligenceはCost・総合Balance・Qualityという優先度を表します。
- Intelligenceでも単純Taskでは小型Modelを選ぶ場合があります。
- 有料Planでは選択Model料金から10％引きですが、重要なのはCost-per-successです。
- Product、Plan、Admin Policyで候補Modelが変わるため、実Routingを観測します。

**面接ポイント：** `selected model / task / success / cost`をTelemetry化し、自社WorkloadでRouting Policyを検証します。

## 3. MCP：ConnectivityからTask LifecycleとIdentityへ
- 講演ではClaude上の累計約10億MCP Tool Call、SDK月間5億Download超が紹介されました。
- 次の重点はMCP Tasks、Skills over MCP、Identity / Authorizationです。
- Long-running TaskではCancellation、Timeout、Retry、Auditが必要です。
- RoadmapとCurrent Specを混同しないことが重要です。

**面接ポイント：** MCPの次の設計課題はTool数ではなく、Task LifecycleとDelegated Identityです。

## 4. AI Infra：脱CloudではなくPlacementの再設計
- 1500人Surveyの66％がAI WorkloadをPublic CloudからPrivate / On-premへ移したと回答しました。
- 95％がGovernance / Compliance理由でAI Projectの延期・中止を経験しています。
- Vendor Surveyは自社のTCOやSLO測定の代替にはなりません。
- Hybrid化するほど環境横断のPolicyとAuditが重要です。

**面接ポイント：** Cloud / On-premは思想ではなくPlacement Optionです。Data、Cost、Governance、SLOでWorkload単位に選びます。

## 5. アイカ工業：AI利用前にEntityを統一する
- 表記揺れ、重複、更新漏れは生成AI / BIのSource Qualityを下げます。
- Sansan Organization Codeで異なるSystem上の同一企業・事業所を関連付けます。
- Data CleansingはAI EngineeringのFoundationです。
- 定量的なAI精度改善は未提示なので、導入後KPIで検証します。

**面接ポイント：** Model改善の前にMaster DataのEntity、Owner、Freshness、Source of Truthを確認します。

## C-3. JLPT文法｜7項目

### C-3-1. ～にとどまらず｜N1
**意味：** ある範囲だけで終わらず、さらに広い範囲へ及ぶことを示す。  
**接続：** 名詞 + にとどまらず / 動詞普通形 + にとどまらず  
**使い方：** 影響・能力・対象範囲の拡張を説明するときに使います。  
**例文：** MCPはTool接続にとどまらず、長期TaskやIdentityの設計へ広がっています。  
**例文の意味：** MCPの対象が単純なTool接続より広くなっていることを示します。  
**今日の記事での位置付け：** Top 3のMCP進化を説明するのに適しています。

### C-3-2. ～に応じて｜N2
**意味：** 条件や状況に合わせて方法・程度を変えることを示す。  
**接続：** 名詞 + に応じて  
**使い方：** RoutingやPolicyなど、条件依存の選択を説明するときに使います。  
**例文：** Taskの複雑さに応じてCopilotのAuto Tierを選びます。  
**例文の意味：** Taskの難しさに合わせてTierを変えるという意味です。  
**今日の記事での位置付け：** Model Routingの説明で使いやすい表現です。

### C-3-3. ～たうえで｜N2
**意味：** 前提となる確認・行為を完了してから次の判断を行うことを示す。  
**接続：** 動詞た形 + うえで / 名詞 + のうえで  
**使い方：** Verification後のDecisionを強調するときに使います。  
**例文：** Dataの所在と規制要件を確認したうえで、AI Workloadの配置を決めます。  
**例文の意味：** 必要条件を確認してから配置を判断するという意味です。  
**今日の記事での位置付け：** Enterprise Architecture面接でも有用です。

### C-3-4. ～とは限らない｜N2
**意味：** ある条件から必ずその結論になるわけではないことを示す。  
**接続：** 普通形 + とは限らない  
**使い方：** Evidenceを過度に一般化しないために使います。  
**例文：** 静的Error率が低くても、Code全体が正しいとは限りません。  
**例文の意味：** Static Analysisの結果だけで全体品質を断定できないことを示します。  
**今日の記事での位置付け：** Top 1のEvidence Boundaryそのものです。

### C-3-5. ～一方で｜N2
**意味：** 一つの側面と対照的・補足的な別の側面を示す。  
**接続：** 普通形 + 一方で / 名詞である + 一方で  
**使い方：** メリットと制約、傾向とRiskを同時に説明するときに使います。  
**例文：** Hybrid構成は柔軟な一方で、Governanceを複雑にする可能性があります。  
**例文の意味：** 柔軟性と管理ComplexityのTrade-offを示しています。  
**今日の記事での位置付け：** Architecture Discussionで便利です。

### C-3-6. ～ざるを得ない｜N1
**意味：** 客観的な事情により、そうするしかないことを示す。  
**接続：** 動詞ない形から「ない」を取る + ざるを得ない（する→せざるを得ない）  
**使い方：** 規制・Cost・技術制約で選択肢が限定される場面に使います。  
**例文：** 規制上Public Cloudへ置けないDataは、別環境を選ばざるを得ません。  
**例文の意味：** Compliance上の理由で別環境を選ぶ必要があるという意味です。  
**今日の記事での位置付け：** 企業ITの制約説明に向きます。

### C-3-7. ～に伴って｜N2
**意味：** 一つの変化に連動して別の変化が起きることを示す。  
**接続：** 名詞 + に伴って / 動詞辞書形 + のに伴って  
**使い方：** AI利用拡大とGovernance・Infra・Data品質の変化を説明できます。  
**例文：** AI利用の拡大に伴って、Master Dataの品質管理も重要になります。  
**例文の意味：** AI利用が広がるほどData品質管理の重要性も増すという意味です。  
**今日の記事での位置付け：** Top 4・Top 5の企業導入文脈に合います。
