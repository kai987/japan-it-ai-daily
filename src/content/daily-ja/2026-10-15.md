### 1. Claude Code on Bedrock：アカウント単位のガードレールで入力側の攻撃を検証

**原文：** https://dev.classmethod.jp/articles/claude-code-bedrock-account-level-guardrail-prompt-attack/

**公開時刻：** 2026-10-15 00:51:17 JST

ガードレールを指定したことと、実際の入力が検査されることは同じではありません。本記事はClaude CodeからBedrockを使う際、アカウント単位での強制適用、未設定、settings.jsonのヘッダー指定という三つの経路を比較しています。モデルが自分で不適切な指示を断る場面もあるため、応答だけを見てガードレールが働いたと判定しないことが出発点です。

試したのはWindowsとWSL2のUbuntu、Claude Code v2.1.285、東京リージョン、jp.anthropic.claude-opus-5-5という組み合わせです。プロンプト攻撃だけをBlock・高強度にし、ほかのフィルターを無効にしています。APACのクロスリージョン設定でStandardを選び、指示の上書き、別人格への変更、システムプロンプトの取り出しを求める三例を使いました。質問の題材自体は無害にし、まずコンソール、次にクライアントから同じ文を送っています。

入力の評価範囲を決めるのがタグとSelective guardingです。通常のInvokeModel系APIではユーザー入力のタグが必要だとAWS資料に記載されています。今回、アカウント単位のUser promptsをComprehensiveにすると、タグの有無に依存せずユーザー入力が対象になります。System promptsはSelectiveにし、正規のツール説明まで誤って検出しないよう、今回の比較範囲をユーザー入力へ絞りました。この選択でシステム側の内容まで検証できたわけではありません。

Comprehensiveでは三例とも入力側のブロック表示になりました。一方、未設定とヘッダー指定では、同じ入力側の検出は確認できませんでした。入力用と出力用の拒否文を変えた点が、どこで止まったかの判別に役立っています。モデルが別人格への変更を拒んでも、それだけではガードレールの検出結果とは呼べません。また、ヘッダー方式で返った機密指示の具体的な内容は公開されておらず、読者がその内容まで確認できる資料ではありません。

三種類を止められた結果は、あらゆる攻撃への保証ではありません。Claude Codeがタグを付けないという説明も、公式仕様で確定した事実ではなく、実験とIssueからの見立てです。ブロック後の通常会話が続く場合と続かない場合の違いも未解明でした。導入判断では、実際のクライアント版と入口を固定し、通常の作業を妨げないか、拒否が入力側か、次の会話へ影響するかを別々に確かめる必要があります。

**読む価値：** 設定の有無と実際の検査範囲を分け、モデル自身の拒否まで混同せず説明する練習になります。

### 2. React Native：TextDecoderによるタッチ停止を実機で切り分ける

**原文：** https://zenn.dev/yskms/articles/5b1090cfa1a51e

**公開時刻：** 2026-10-15 07:21:05 JST

RSSアプリの初期案内でボタンが反応しなくなり、著者は最初、初期フィード登録と同期の同時実行を疑いました。しかし構造を変えて実機で調べると、その仮説では説明できませんでした。Expo ManagedとHermesの環境で大きなUTF-8を一括デコードする処理が、JSスレッドを長く止めていたのです。取得を十並列にしても、返ってきたデータを同期的に処理する部分まで並列になるわけではありません。

測定には50ms間隔のタイマーを使い、予定より遅れた時間からブロックを推定しました。20msを超えるずれを拾う補助的な方法であり、ほかの遅延も含む近似です。さらに、フィード別の時間を記録する共有オブジェクトが、awaitの間に別workerから上書きされる不具合も見つかりました。関数の戻り値に各処理の計測情報を含めたことで、どのフィードの値かを取り違えず確認できるようになっています。計測対象だけでなく、計測器の実装も調べた点が重要です。

内訳を直して測ると、3.2MBのフィードは一括デコードだけで1379ms、別の1.7MBと1.4MBは709msと603msでした。対策はUTF-8のバイト列を64KBで区切り、TextDecoderにstreamを指定して文字の途中を保持させる方法です。チャンク間だけでなく、デコード前、パース前、各フィードの終了時にもsetTimeoutで処理を譲りました。Promiseの微小タスクだけでは改善せず、後続のタスクへ継続を回すことで、操作を処理する機会を作っています。

Pixel 11の実機でアプリのデータを消した同条件の比較では、連続ブロック最大値が1793msから227msへ下がり、300ms超は七回からゼロになりました。同期全体も12.5秒から10.2秒になりましたが、総時間が縮んだ直接の理由までは切り分けていません。別途、一括と分割のデコード結果を照合し、Android実機75件とiOSシミュレーター78件で不一致がないことを確認しています。速さだけでなく文字列の正しさも検証した結果です。

約87%という改善率はこのAndroid比較の値です。iOSシミュレーターでは最大546ms、300ms超が二回残り、同じ割合の改善とは言えません。iPhone 8での体感確認もありますが、同じ形式の数値は公開されていません。対象は巨大なUTF-8に限定され、ほかの文字コードの分割は見送られました。端末を固定した計測、戻り値による記録の対応付け、文字列一致の確認をそろえることが、この事例から持ち帰れる手順です。

**読む価値：** 非同期なら軽いという思い込みを避け、実機と計測コードの両方で原因を確かめる説明に使えます。

### 3. dbtとSnowflake：PrivateLinkの接続経路と公開側の制限を確かめる

**原文：** https://dev.classmethod.jp/articles/dbt-platform-snowflake-aws-privatelink-network-policy/

**公開時刻：** 2026-10-15 09:43:26 JST

dbtからSnowflakeへ接続できても、公開経路を禁止できたとは限りません。本記事ではAWSのEnterprise+を使うdbt platformと、Business CriticalのSnowflakeをPrivateLinkで結んでいます。dbtはus-east-1、Snowflakeは東京で、同じAWS内の異なるリージョンです。共有アカウント全体を変更せず、作業用ユーザーDBT_PL_SVCだけに制限を掛けた検証です。操作は14日、遅れて反映される履歴の確認は15日に行われました。

最初にSnowflake SupportへSaaS側のAWSアカウントを許可してもらい、管理者がSYSTEM$GET_PRIVATELINK_CONFIG()を取得します。その結果でdbtのPrivate endpointを作り、Connectionに割り当てます。実際に使ったのはself-serveとRegionlessのURLです。Support-ledの手順も載っていますが、こちらは公式資料の整理であって実施結果ではありません。また、当時のself-serveはbetaであり、Internal Stage用の別endpointは今回の対象外でした。

接続の証拠には、ジョブとStudioで別ユーザーを使ったことが効いています。ジョブでsession_idなどをテーブルに残し、LOGIN_HISTORYのCLIENT_PRIVATE_LINK_IDがdbt側のEndpoint identifierと一致するか確認しました。設定情報に出るSnowflake側のサービス識別子を、そのままNetwork Ruleへ入れない点も重要です。IPアドレスが私有範囲に見えるだけで判定せず、使った端点をログで特定しています。

次に、許可するAWSVPCEIDの規則と、公開IPv4全体を拒否する規則をNetwork Policyにまとめました。私有端点の規則だけでは公開側を閉じられないためです。対象ユーザーに適用して再実行するとジョブは通り、同じユーザーで手元PCから公開接続すると拒否されました。さらにセッションとログインを結び、REQUEST_AUTHORITYで接続先ホストも確認しています。SESSIONSは最大三時間、入口履歴は最大四時間の反映遅延があり、表示を待つ必要があります。

確認したのはユーザー単位の鍵ペア接続と公開IPv4の対照です。アカウント全体の公開接続を無効化した結果ではありません。OAuthのトークン要求、Internal Stage、開発者の本番認証には別の確認が残ります。検証用の暗号化しない秘密鍵も、本番の保管・暗号化・更新方針を代替しません。接続できる経路と拒否する経路を両方試し、ログの識別子で設定と実態を結び付けることが、この例の要点です。

**読む価値：** 接続成功に加えて拒否側も試し、設定した端点を履歴で説明する考え方を学べます。

### 4. LINEヤフー：VM Live MigrationのTLS化と鍵更新の不具合を調べる

**原文：** https://techblog.lycorp.co.jp/ja/20261014b

**公開時刻：** 2026-10-14 11:00:00 JST

Live Migrationは動作中のVMを別の物理ホストへ移す技術ですが、最後まで一切停止しないという意味ではありません。まず状態を送り、書き換わった部分を繰り返し送り、残りを移す間だけ短く止めます。転送にはメモリやディスクなどの内容が含まれるため、盗み見られるとVMの情報が露出します。LINEヤフーのFlavaでは、QEMUが張るホスト間のTCPをTLS化し、信頼すべき範囲を送信元と送信先へ絞ろうとしました。

上位のOpenStack、そのドライバーとして使うlibvirt、実際のVMを動かすQEMUという層をまたぐ作業です。各ホストの証明書を署名する仕組みがなかったため、CAと管理クライアントを実装しています。CAは有効なKeystoneトークンを持つ依頼を認証して署名し、クライアントが鍵と証明書を管理します。そのうえでAnsibleから設定を反映しました。通信の暗号化に加え、相手の確認と完全性の保護に必要な準備をした例です。

数百MBの小さなVMは移動でき、キャプチャでTLSのHelloも見えました。しかしメモリとディスクがそれぞれ100GiBのVMでは、移行に失敗してロールバックもできず、ERRORになりました。複数のログを照合すると送信元QEMUがSIGSEGVで終了しており、gdbのバックトレースでGnuTLS内部まで追えました。大きいVMで確実に再現する条件が、下位層の調査につながっています。

原因はTLS 1.3の鍵更新に関するGnuTLSの既存の不具合でした。記事の説明では、一方向ずつ扱うべき鍵の更新を両方向へ行う実装が問題でした。引用されたQEMUのIssueでは約32GBの転送で更新が起きるとされ、短い検証では通らなかった処理に大きなVMが到達したと理解できます。関連パッチの適用後は、大きなVMでもTLS付きの移行が成功しました。ただし、約32GBをすべてのTLS環境に共通の境目として使うことはできません。

別の比較では、TLSによる転送速度の低下がディスクで平均25.9%、メモリで78.9%でした。速度、総所要時間、最後にVMを止める時間は別の指標です。QEMUがTLSを単一コアで処理することを著者は疑っていますが、原因を確定した性能分析ではありません。この試験の割合をそのまま本番予測へ使わず、長時間転送と鍵更新、失敗時の復旧、大きなVMの性能まで段階を分けて検証する考え方が参考になります。

**読む価値：** 上位のERRORからTLS実装まで調べる道筋と、短い成功だけでは見つからない境界を学べます。

### 5. TypeScriptのunknown：実行時ガードとSchema Libraryを使い分ける

**原文：** https://zenn.dev/nyaomaru/articles/validate-unknown-without-schema-library

**公開時刻：** 2026-10-15 00:36:45 JST

外から届いた値をUserとして使いたくても、型アサーションだけでは値は検査されません。記事はunknownから始め、コンパイラーへの説明と実行時の確認を分けています。nameが数値でもas Userは書けてしまい、後で文字列のメソッドを呼べば失敗します。ここで必要なのは、データが本当に条件を満たすかを実行時に調べ、その結果を型の絞り込みへつなぐことです。

Schema Libraryなしという題名ですが、依存を一切使わない方法ではありません。著者のis-kitを使い、isString、oneOfValues、structなどの小さなガードを組み合わせます。成功すれば条件分岐の中で値の型が狭まり、同じガードを別の場所でも使えます。optionalKeyはキー自体の省略、nullableはnullという値の許可です。配列の要素や入れ子も、どの値を許すかという小さい判定を組み合わせて表します。

safeParseは判定済みの結果をほかの処理へ渡すための形を追加します。validがtrueならvalueを持ち、falseなら失敗を表すため、普通の分岐で扱えます。値の複製や型変換、補正は行わず、受け入れた元の値を返します。したがって検証した瞬間の複製や不変化を保証するものではありません。safeJsonParseはJSONの読み込みとガードを一つの入口にまとめ、不正なJSONと条件不一致を失敗として扱います。

余分なキーをどう扱うかも、境界の契約で決めます。structは標準では追加キーを許し、exact:trueなら宣言外のキーを拒否します。APIの項目追加を許したいクライアントと、決めた形だけを受けたい入力では、選ぶ設定が違います。ただし、認証用データの形が通ることと本人確認や権限の承認は別です。記事の構造チェックに、実装されていない認証機能まで読み込むことはできません。

一方、複数の検証エラーやフィールドの場所を返したい、既定値や変換を入れたい、フォームなどと深く連携したい場合はSchema Libraryが向いていると著者も述べています。この説明はライブラリーをなくす主張ではなく、必要な検証の大きさを選ぶ提案です。速度や容量の比較値は示されておらず、あらゆる用途で優れるという結論にはしていません。

**読む価値：** 型アサーションと実行時の検証を分け、キーの省略・null・追加キーを具体的に説明できます。

### 3. dbt platform から Snowflake へ AWS PrivateLink で接続し、Network Policy で経路を制限してみた

**面接質問：**

> 私有接続を設定したあと、経路制限をどう検証しますか。
