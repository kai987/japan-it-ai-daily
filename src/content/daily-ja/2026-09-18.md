## 1. 今日読むべき5本

### 1. Claude Code v2.1.274 の主要アップデート - type: sdk の MCP 設定廃止と MCP 接続の安定化

**出典：DevelopersIO｜2026年9月17日**  
**原文 URL：** https://dev.classmethod.jp/articles/20260917-cc-updates-v2-1-274/

v2.1.274は108件の変更を含み、特にMCPを利用するHeadless Sessionの起動制御が実務的だ。`CLAUDE_CODE_MCP_STARTUP_WAIT_MS` で最初のTurnがMCP Serverを待つ上限を指定できる。記事では、60秒sleepするだけでMCP Protocolを話さないstdio Serverを用意し、`--strict-mcp-config` で検証条件を固定した。4回平均はMCPなし3.6秒、接続しないMCPあり33.4秒、待機上限0で3.5秒だった。Model ResponseではなくStartup Waitが約30秒を占めた最悪Caseを切り分けている。

同ReleaseではStreamable HTTP MCP Toolが約5分で切れる不具合、`${VAR}` から解決したSecretがError表示へ出る問題、Bash権限Checkなども修正された。`claude_code.managed_settings_resolved` EventやLLM Requestの `effort` 属性も追加された。**ただし、**33.4秒から3.5秒という差は接続が成立しないServerを置いた実験で、通常のServerすべてに約30秒の短縮が出るわけではない。また `0` では最初のTurnにMCP Toolがそろわない可能性があるため、CIでは実測から上限を決める必要がある。

**注目ポイント：★★★★★**  
MCP運用をTool接続だけでなく、Startup Budget、Timeout、Secret、Telemetryとして扱える。

### 2. 自作RAGニュース検索をMCPサーバー化し、全記事再embedをChromaDBの差分更新に直した

**出典：Zenn｜2026年9月17日**  
**原文 URL：** https://zenn.dev/satoru_o/articles/014317b053f0aa

`info-rag` はAWS、Snowflake、dbt、FivetranなどのRSSを収集し、Claude Codeから呼べるMCP Serverとして実装されている。初期版はServer起動時に全記事を取得し、毎回Bedrockで全件Embedしていたため、Sourceが7、8個へ増えるにつれて同じ記事への呼び出しが繰り返された。改善版では `chromadb.PersistentClient(path="./chroma_data")` を採用し、URLをDocument IDにする。`_collection.get(ids=ids)` で既存IDを確認し、未登録のDocumentだけ `embed()` と `add()` を行い、検索は `_collection.query()` で返す。

Data Qualityの失敗も興味深い。`dbt-fivetran-blog` というSource名なのにURLはdbt側だけを指しており、Fivetranを取得しているつもりになっていた。実URL確認をRuleにし、Fivetran RSSを別Sourceとして追加した。**ただし、**URL IDで新規追加だけを見る方式では、同一URL本文の更新、削除、Canonical URL変更、Embedding Model更新を検出できない。個人Toolの実装事例であり、大規模ConcurrencyやRecall、SLOまで検証したBenchmarkではない。

**注目ポイント：★★★★★**  
RAGのCost最適化とDocument Lifecycleを同時に考える具体例である。

### 3. 「AIがログを取りに行く」時代、SIEMは何のためにある？　Splunkの答え

**出典：＠IT｜2026年9月17日 15:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/17/news045.html

`.conf26` でCisco/Splunkが示した構想では、Agentは新しい監視対象であると同時に、SOCの調査・一次対応を実行する主体にもなる。`Cisco Data Fabric powered by Splunk` がInfrastructure、Application、AIのTelemetryを横断して扱い、`Cisco Security Cloud Control` がそのDataを使って運用Actionへつなぐ。DemoではAnalystがConsoleを開く前にAgentが複数Data Lakeと第三者ToolをQueryし、関連情報を照合していた。その後、侵害されたIdentity Sessionを切断し、露出TokenをRotationし、新しいControl Policyを提案した。

Policyの適用はHuman Approval後に行われ、直後のAttack Testで遮断を確認した。記事はAgentのData参照、API Call、Action自体を追跡対象にする必要性を示している。CiscoはAgentが同じTaskを行うと人より約450%多くNetwork Bandwidthを消費するという見積もりも紹介した。**ただし、**これらはConference KeynoteとDemoのEvidenceであり、独立したProduction Benchmarkではない。実環境ではFalse Positive、Least Privilege、Audit、Rollback、誤った自動ActionのBlast Radiusを別途評価する必要がある。

**注目ポイント：★★★★★**  
Agentic SOCを「自動化率」ではなく、Data→Decision→Action→Approvalの監査可能性で考えられる。

### 4. AI学習は拒否、検索クロールは維持……Cloudflareの新機能「AI学習の不許可」　Google、Apple、Microsoftが対応

**出典：ITmedia AI＋｜2026年9月17日 15:19**  
**原文 URL：** https://www.itmedia.co.jp/aiplus/article/2609/17/2000001584/

Cloudflareの `Disallow AI Training` は、Search IndexとAI Trainingを同じCrawlerがまかなうときのPolicy衝突を解く設定だ。従来はmixed-use crawlerを拒否すると検索露出まで失う可能性があった。新設定ではCloudflareが `robots.txt` にTrainingを認めないRuleを記載し、対応CrawlerはSearchのためのCrawlingを継続しながらAI Trainingには利用しないという扱いになる。AppleとGoogleは対応済みで、Microsoftは2027年初頭までの対応方針を示している。

OpenAI、Anthropic、Meta、Amazonは検索CrawlerとTraining Crawlerを分けているため、Training側だけBlockできる。Microsoft対応前のBingでは `NOARCHIVE` など別手段も必要になる。**ただし、**robots.txtは宣言的なPolicyであり、全Crawlerへの強制的・暗号学的なEnforcementではない。Site OwnerはCrawler Identity、Access Log、Vendorの実装状況を確認し、「Ruleを書いた」ことと「全AIが学習していない」ことを同一視しない方がよい。

**注目ポイント：★★★★★**  
Web Content GovernanceをSearch、Training、Agent利用の目的別に分ける考え方が重要になる。

### 5. PlanetScale、PostgreSQLのシャーディングを自動化して1億1800万QPSを達成。新DBサービス「Neki」をプレビュー公開

**出典：Publickey｜2026年9月18日**  
**原文 URL：** https://www.publickey1.jp/blog/26/planetscalepostgresql11800qpsdbneki.html

PlanetScaleのPreview Service `Neki` は、標準Postgres Protocolを保ったままShardingを自動化する。Clientは既存DriverやToolを利用でき、入口の `Neki Router` がPostgres Query Parser、Distributed Query Planner、Query Bufferingを持つ。RouterはQueryを解析し、対象Shardへ実行を指示し、結果を集約する。Router自身もScale-outする。各ShardはPostgreSQLで、1 Primaryと少なくとも2 Replicaを異なるAvailability Zoneへ配置するほか、Connection Pooling Sidecar、Re-shardingやSchema Change、Failoverを担うControl Planeがある。

最初はShardingせずSingle Primary/Replicaで始め、必要時にShardingへ移行できる。PlanetScaleは約1.4PBを512 Shardへ分け、最大1億1875万QPSを達成し、Shard増加に対しほぼLinearに伸びたと発表した。**ただし、**NekiはPreviewで、この数値はVendor Benchmarkである。Cross-shard Query、Transaction、P99 Latency、Re-sharding時のSLO、実際のTCOは企業のSchemaとQuery Patternで測る必要がある。

**注目ポイント：★★★★★**  
「最初から分散」ではなく、単一構成から必要時にShardingへ移る設計判断を学べる。

## 3. 面接で使えるポイント

### 1. Claude Code v2.1.274

**面接質問：**

> Claude CodeをCIからHeadless実行するとき、MCPの起動待ちをどう設計しますか。

**約30秒回答：**

> 非対話のClaude Codeでは、MCP接続待ちを固定の前提にしません。v2.1.274ではCLAUDE_CODE_MCP_STARTUP_WAIT_MSが追加され、記事の4回平均では接続しないMCPありで33.4秒、0指定で3.5秒でした。ただし0では最初のTurnにToolが揃わないため、CIでは実測して必要な上限値を置きます。

**関連プロジェクト：** Claude Code / CI / MCP Platform  
**技術キーワード：** 起動待ち / 非対話Session / 実測上限

### 2. ChromaDB差分RAG

**面接質問：**

> RSS型RAGをMCP化するとき、Embeddingの更新をどう設計しますか。

**約30秒回答：**

> RAGの更新単位を記事ごとにします。記事ではURLをIDにし、ChromaDBのPersistentClientで既存IDをgetし、新規記事だけBedrockでembedしてaddしました。これで起動ごとの全件再embedを避けられます。ただしURLが変わらない本文更新や削除はこの方式だけでは拾えないので、更新検知を別に設計します。

**関連プロジェクト：** RAG / MCP / Vector Database  
**技術キーワード：** 差分同期 / Document Identity / 更新検知

### 3. Agentic SOC

**面接質問：**

> AIエージェントをSOCへ組み込む場合、どこまで自動化しますか。

**約30秒回答：**

> AIエージェントをSOCへ入れるなら、判断だけでなく行動のTraceを残します。.conf26のDemoではCisco Data Fabricから複数Data Lakeを照合し、侵害Sessionの切断とToken RotationまでAgentが一次対応しました。ただしConference Demoなので効果を一般化せず、Policy適用はApprovalとAudit LogをGateにします。

**関連プロジェクト：** SIEM / SOC / AI Agent / Security  
**技術キーワード：** 一次対応 / 監査証跡 / Policy適用

### 4. Cloudflare AI Training Policy

**面接質問：**

> 検索Crawlerを残しながらAI学習を拒否したい場合、何を確認しますか。

**約30秒回答：**

> Webの検索流入とAI学習の許可を同じ設定にしません。CloudflareのDisallow AI Trainingはrobots.txtへ学習拒否Ruleを書き、対応するmixed-use crawlerでは検索を継続できます。GoogleとAppleは対応済みですが、Microsoftは2027年初頭予定なので、Crawlerごとの対応状況とNOARCHIVEなどの補助手段を確認します。

**関連プロジェクト：** Web Governance / Cloudflare / SEO  
**技術キーワード：** mixed-use crawler / 学習拒否 / 対応状況

### 5. PlanetScale Neki

**面接質問：**

> PostgreSQLのSharding基盤を採用するとき、Benchmarkをどう評価しますか。

**約30秒回答：**

> PostgreSQLをShardingするなら、互換性と運用面を分けて評価します。Nekiは標準Postgres ProtocolのままNeki RouterがQueryを各Shardへ分配し、512 Shard・約1.4PBで最大1億1875万QPSを公表しました。ただしPreviewのVendor Benchmarkなので、実WorkloadではCross-shard Query、Failover、Costを別に測ります。

**関連プロジェクト：** PostgreSQL / Distributed Database / Cloud  
**技術キーワード：** Sharding / Query Router / Vendor Benchmark

## 4. 今日の技術テーマ：Operational Contract

```text
Capability
   ↓
Operational Contract
├─ Startup / Timeout
├─ Identity / Freshness
├─ Permission / Approval
├─ Policy / Consent
└─ Scale / Failure Boundary
   ↓
Evidence & Telemetry
   ↓
Commit / Action
```

Claude CodeではMCP待機、RAGではDocument Identity、SOCではAction権限、Cloudflareでは用途別Consent、NekiではScale条件がContractになる。このContractが明示されれば、ModelやToolを変更しても運用判断の基準を残しやすい。

一方で、Contractは完全ではない。0ms待機ではToolが間に合わず、URL IDでは本文更新を検出せず、robots.txtは対応Crawlerの遵守に依存する。国内企業で使うなら **Source of Truth / Timeout / Permission / State Transition / Evidence / Rollback Owner** をWorkflowごとに残し、本番障害から継続的に更新するのがよい。

## 5. 面接復習カード

**Q1：** Claude CodeのMCP起動待ちを0にすれば常に速くなりますか。  
回答要点：Headless限定 / `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` / 33.4秒→3.5秒は最悪Case / Tool ReadyとのTrade-off / 自社CIで実測。

**Q2：** RAGの差分更新でURLをIDにする場合、どんな更新を取りこぼしますか。  
回答要点：同URL本文更新 / Delete / Canonical変更 / Embedding Model更新 / Hash・Updated-at・Re-indexが必要。

**Q3：** Agentic SOCでHuman Approvalを残すべき箇所はどこですか。  
回答要点：調査とEvidence収集 / Session・Credential処置のPolicy / 新Control Policy適用 / Audit / Rollback。

# B. 重要ポイントと面接で使える知識

### 1. Claude Code v2.1.274
MCP Startup WaitはBatch AgentのLatency Budgetであり、0msにすること自体が目的ではない。Security修正とOpenTelemetry Eventも含め、Effective Runtimeを観測する。

### 2. ChromaDB差分RAG
URL IDとPersistentClientで全件Embedを避けられるが、Update/Delete Lifecycleは別途必要になる。Source名と実URLの一致もRetrieval Qualityの一部である。

### 3. Splunk / Cisco Agentic SOC
Agentが参照Data、API Call、Actionを残し、HumanがCommit Authorityを持つ形が重要だ。Conference DemoとProduction Evidenceは分けて読む。

### 4. Cloudflare Disallow AI Training
SearchとTrainingを用途別に制御する。robots.txtを書くだけでなく、Vendor SupportとAccess Logで実効性を見る。

### 5. PlanetScale Neki
Postgres互換のClient Experienceと、Router/Shard/Control PlaneのDistributed Complexityは別物である。Vendor QPSは実SchemaのSLOではない。
