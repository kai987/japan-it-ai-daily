## 1. 今日読むべき5本

### ① AI に実装を任せるための仕様と検証ループ 〜ProxySQL に足りない機能を実装で埋めた〜 [DeNA インフラ SRE]

**出典：DeNA Engineering｜2026年9月9日**  
**原文 URL：** https://engineering.dena.com/blog/2026/09/spec-and-verify-loop-proxysql-eks/

DeNAのインフラSREが扱ったのは、2022年からEC2上で運用していたProxySQLをEKSへ載せ替える案件だ。最初はProxySQL組み込みの`mysql_aws_aurora_hostgroups`でAurora Writer / Readerをauto-discoveryする前提だったが、EKSとAuroraがVPC PeeringをまたぐTopologyでは`check_timeout_ms`超過が頻発し、正常なReaderが`SHUNNED`から戻らないケースや、想定外Hostがhostgroupへ入る挙動が出た。そのためGoでKubernetes Controller「Manager」を実装し、周辺実装は約**1万行、145 commits、約2.5カ月**。AIには実装とTest実行を任せ、人は「何を正解とするか」と、結果から次の仕様を決める役割を持った。

検証基盤は実装より先に作っている。`k6 + xk6-sql + MySQL driver`のLoad Test Imageを用意し、**Argo Workflows**からCluster内で実行。3 AZへ同時に負荷をかけたままReader追加、Failover、Pod停止を発火させ、**接続エラー率5％未満、Queryエラー率1％未満**を合否条件にした。Query DurationとError RateはAZ別にPrometheusへ送る。ManagerはRDS APIでInstanceを検出し、ProxySQL Admin APIで`mysql_servers`を更新する。全体同期は10秒周期、Writer判定だけは2秒周期、新Readerはweight 0から開始して60秒ごとに5ずつ増やす。

本番前には3 AZ構成でProduction Peakの**2倍以上**のQueryを流し、Route53 Weighted Routingを**1％→10％→50％→100％**と段階的に切り替えた。移行後、Instance Costは月額で約**80％**低下し、DB Readのcross-AZ比率は**65％から31.5％**へ減った。Leader Electionは通常約1秒、Crash時は約15秒で引き継いだ。これはDeNA自身の本番Migrationと実測に基づくEvidenceである。**ただし**、必要な仕様の粒度はModelやEnvironmentに依存し一般解ではない。後から見つかったKernel Table使用率90％近辺の問題を発見したのもAIではなくMonitoringであり、自作Controllerには保守責任が残る。

**注目ポイント：★★★★★**  
AIへ安全に実装を委譲できる範囲は、Code生成能力ではなくRequirements、Failure Injection、Pass / Fail Threshold、段階Rolloutをどこまで先に定義できるかで決まる、という実務的な結論が得られる。

### ② AWS、AIがフルスタックAWSアプリの基本コードを、セキュリティ、可観測性、インフラまで一気通貫で生成する「Nx Plugin for AWS 1.0」、オープンソースで公開

**出典：Publickey｜2026年9月10日**  
**原文 URL：** https://www.publickey1.jp/blog/26/awsaiawsnx_plugin_for_aws_10.html

AWSがOpen Sourceで公開した`Nx Plugin for AWS 1.0`は、AIにApplication Requirementsを渡すと、**AWS CDKまたはTerraform**によるInfrastructure CodeとBackend / FrontendのApplication Scaffoldをまとめて生成する。Publickeyが紹介した公式DemoではWorkspaceを作成し、React Web、AI AgentとFrontendを接続する**AG-UI**、MCP Server、DynamoDBを指定してCodeを生成している。X-Ray、CloudWatch、FirewallなどのSecurity / Observability要件や、Amazon Bedrock AgentCore、TypeScript / Python FrameworkとAPIまで同じ設計対象に含められる。

重要なのは、Frontendだけ・IaCだけを別々に作るのではなく、ApplicationとInfrastructureの初期構成を同じContextでScaffoldする点だ。生成されたCodeにはその後**Nx Plugin for AWSへの依存が残らず**、Developerが自由に編集できるため、継続RuntimeというよりBootstrap Toolに近い。React / TypeScript Engineerにとっても、UIとMCP / Agent、Data Store、Telemetry、IaCを一つのInitial Architectureとして扱う発想につながる。

**ただし**、公開されているEvidenceはAWSのAnnouncement / Demoを基にしたものであり、「数分で生成」はScaffold生成時間を示すものでProduction品質のBenchmarkではない。複雑なMonorepo、既存System Migration、IAM Least Privilegeの正確性、長期TCOまでは判断できない。実運用ではIAM、Network Boundary、X-Ray / CloudWatch、Terraform / CDK State、Test Strategyを別途Reviewする必要がある。

**注目ポイント：★★★★★**  
AI Full-stack Developmentを「Component生成」ではなく、Application + IaC + Observability + Agent Integrationの共同Scaffoldとして捉え、その後のEngineering Gateへ品質責任を渡す考え方を学べる。

### ③ NEC、社内の“AIトークン節約”に注力　「同じ使われ方なら10分の1に」と小玉CAXO

**出典：ITmedia AI＋｜2026年9月10日 06:55**  
**原文 URL：** https://www.itmedia.co.jp/aiplus/article/2609/10/2000001333/

NECの小玉浩CAXOは9月9日の説明会で、社内AI利用にかかる「実質的なToken Cost」について、2026年4月の利用状況を基準に、**同じ使われ方なら上期中に5分の1、下期中に10分の1**へ下げる目標を示した。絶対利用額を90％削減すると言っているのではない。AIの利用量自体は今後も増える見通しであり、NECは利用効率を高めながら、増加分をPerformance / Output向上で回収する考えを示している。

具体策は、Task別に最適なModelへ処理を**振り分けるModel Routing**、Frontier ModelとOpen-weight Modelの使い分け、過去Inputの一部を再利用する**Cache**、Task実行時に参照する**Context Data**の整備、さらに固定料金型Serviceの検討まで含む。AI FinOpsを単なるToken集計ではなく、Routing、Caching、Context Engineering、Pricing Modelの組み合わせとして扱うアプローチだ。組織面では8月1日に「コーポレートAI・Workforce部門」を設置し、AI Native Companyへの移行を進めている。

**ただし**、5分の1・10分の1は現時点の実績ではなく**Target**であり、4月と同じ利用Patternを仮定した比較である。AI Usageが増える前提なので、月額請求だけをKPIにすると施策を誤読しやすい。Task Success、Output、Human Time、Quality、Latencyまで含めたCost-per-Outcomeで評価する必要がある。

**注目ポイント：★★★★★**  
「安いModelへ置き換える」だけでなく、Model Routing、Open-weight、Cache、Context Dataを組み合わせてEnterprise AI Costを最適化する具体的な論点を持てる。

### ④ 電通など3社、広告コピーをAIが自動評価　コピーライター64人・11万件超の評価データを構築

**出典：Ledge.ai｜2026年9月9日**  
**原文 URL：** https://ledge.ai/articles/dentsu_ai_ad_copy_evaluation

電通、電通デジタル、SB Intuitionsの3社は、日本語広告Copyを専門家基準で評価するDataを構築した。電通のコピーライター**64名**がAI生成Copyを共通基準で評価し、計**116,532件**の評価Dataを作成。Expert Interviewから「ファースト・インパクト」「インサイトの深さ」「言葉選びの妥当性」など、Copywriterが見ている観点を体系化し、LLMが参照できるJudge Criteriaへ落とし込んだ。研究ではSB Intuitionsの日本語Native Model `Sarashina`も活用している。

自動評価は、Dataの一部とCopywriterの基準をPromptへ組み込む**LLM-as-a-Judge**として検証した。学習・最適化を行った業種・商材ではHuman Evaluationと**一定程度の正の相関**を確認した一方、未学習の業種・商材では相関が低下した。つまり「Judgeが人に近い点数を出すか」だけでなく、どのDomainでCalibrationしたか、Domain Shift後も相関が維持されるかが実運用の中心課題になる。

**ただし**、116,532件はEvaluation Recordsの件数であり、同数の完全独立Creativeを意味するとは限らない。公式発表は全業種で使える固定Correlationを提示しておらず、未学習Domainで低下する課題を明示している。LLM-as-a-JudgeをProduction GateにするならHuman Calibration Set、業種別Slice、定期的なRe-score、Judge Version変更時のRegressionが必要だ。

**注目ポイント：★★★★★**  
日本語Creative Evaluationで、Domain Expertの暗黙基準をRubric / Labelへ変え、LLM-as-a-Judgeを未学習Domainまで評価する流れが具体的に見える。

### ⑤ 「四半期ごとのパッチ適用」はもう許されない　AWSが「フロンティアAI対策9項目」のポイントを解説：「能動的なサービス停止」の基準を明確化する

**出典：＠IT｜2026年9月9日 11:30**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/09/news043.html

金融庁と日本銀行は2026年5月22日、Frontier AIによるCyber Threat変化を踏まえた**9項目**の短期対応を金融機関へ求めた。AWSの解説では、2025年に公開されたCVEは**48,185件**で前年比約20％増。Anthropic `Project Glasswing`ではClaude Mythos Previewを使ったPartner組織が1カ月でHigh / Critical Vulnerabilityを1万件超発見し、Amazon Threat Intelligenceは公開Exploitが開示後**数時間～数日**で攻撃へ転用される状況を観測している。一方、英国AISIは十分に防御されたIT SystemをFrontier AIが必ず突破できるとは限らないとしており、基本的なSecurity Hygieneの重要性は変わらない。

AWSは対応をExecutive Governance / External Collaboration、Asset VisibilityとTechnical Debt、Patch AutomationとRisk Prioritization、Assume-breachとBCPなどに整理する。Patchは四半期固定ではなく、CISA **KEV**や**EPSS**を使って日常的に優先度を付ける。WAF / IPSのVirtual Patchは**暫定的な**緩和策であり根本修正ではない。`AWS Continuum`はDiscover → Prioritize → Validate → Remediateを継続し、SandboxでExploitを検証できる。導入初期は**learnモード**でHuman Approvalを挟み、成熟度に応じて徐々に**enforce**へ進める。

**ただし**、AWS自身も「AWS Serviceを導入すれば9項目への対応が完了するわけではない」と明記している。最終的なRisk Evaluation、Control、Decisionは金融機関側の責任であり、能動的なService Stopを行うなら停止基準、Communication、Fallback、BCP、Air-gapped Backupまで事前に定義する必要がある。AIで攻撃速度が上がるからこそ、Tool導入よりDecision Latencyを短くするOperating Modelが重要になる。

**注目ポイント：★★★★★**  
Calendar-based Patchから、KEV / EPSS、Continuum learn→enforce、Human Approval、停止基準、BCPをつないだRisk-based Continuous Remediationへ移る考え方を整理できる。

## 4. 今日の技術テーマ

### Verification Contract：AIへ任せる範囲を「検証可能性」から決める

今日の5本を横断すると、AI Engineeringに必要なのは出力の豪華さではなく、**何を正解とするかを機械・人の両方が確認できるContractへ変えること**だと分かる。

```text
Requirement / Risk
        ↓
Observable Contract
├─ Pass / Fail Threshold
├─ Test / Failure Injection
├─ Cost / Quality Metric
├─ Domain Boundary
└─ Rollout / Stop Rule
        ↓
AI Implementation / Evaluation
        ↓
Evidence
        ↓
Human / Policy Decision
```

DeNAは接続Error Rate 5％未満、Query Error Rate 1％未満、3 AZ Failure Injection、Route53 1→10→50→100％をGateにした。Nx Plugin for AWSではScaffold生成後のIAM / Test / TelemetryがContractになる。NECの10分の1も「4月と同じ使われ方」という条件があって初めて比較できる。電通のJudgeはHuman Evaluationとunseen DomainでBoundaryを確認し、AWS SecurityはKEV / EPSS、learn→enforce、Service Stop CriteriaをOperational Gateへ落としている。

**メリット：** AI Outputを感覚ではなく再現可能なEvidenceで評価できる。Model / Toolを交換しても同じGateを再実行できる。Human ReviewはSpecification、Domain Shift、Service Stopなど自動判定しにくい場所へ集中でき、CostやSecurityもFunctional Testと同じRelease Decisionへ接続できる。

**制約：** Contractに書かなかったRiskは自動的には見つからない。DeNAでKernel Table使用率が90％近くまで上がった問題を発見したのはAIではなくMonitoringだった。LLM-as-a-Judgeもseen Domainの結果をunseen Domainへ一般化できない。Verification Set、Observability、Risk ModelはProduction Failureから継続更新する必要がある。

**国内企業での導入時の注意点：** 最初に一つのWorkflowを選び、Owner、Source of Truth、Pass / Fail、Failure Injection、Cost KPI、Human Approval、Rollbackを明文化する。PoCから本番へはStaged Rolloutを使う。AI Costは絶対請求額とCost-per-Outcomeを分け、JudgeにはHuman Calibrationを残す。Security Automationはlearnモードから始め、停止基準とBCPを先に決めてからenforceを広げる。

面接では次のようにまとめられる。

> AIに実装や評価を任せる場合、Modelの能力だけでなく、何を正解とするかをPass / Fail条件として先に定義し、実測・Failure Injection・段階Rolloutで検証できるContractを作ることが重要だと考えています。

# B. 重要ポイントと面接で使える知識

## 1. AI に実装を任せるための仕様と検証ループ
- AIへ実装を委譲する前にRequirementと「確かめ方」を同じ仕様へ書く。
- xk6-sql / Argo Workflowsで3 AZ Failure InjectionとError Rate Thresholdを繰り返す。
- 本番はRoute53 1％→10％→50％→100％で段階移行し、Costとcross-AZ Trafficも実測する。
- AIが発見しないRiskを前提に、Node-level ResourceまでObservabilityを持つ。

## 2. Nx Plugin for AWS 1.0
- React、AG-UI、MCP、DynamoDB、AWS CDK / Terraform、Observabilityを同じFull-stack Scaffoldに含める。
- 生成後にPlugin依存が残らないため編集自由度は高いが、Quality ResponsibilityはTeamへ戻る。
- 「数分」はScaffold生成速度であり、IAMやTCOを含むProduction Benchmarkではない。

## 3. NECのAI Token Cost最適化
- 5分の1・10分の1は4月と同じ利用Patternを仮定したEfficiency Target。
- Model Routing、Frontier / Open-weight、Cache、Context Dataを組み合わせる。
- Usage自体は増えるため、請求額だけでなくOutput、Human Time、QualityをCost-per-Outcomeで評価する。

## 4. 電通など3社のLLM-as-a-Judge
- 64名・116,532件の評価DataでDomain Expertの暗黙基準をRubricへ変換した。
- 「ファースト・インパクト」「インサイトの深さ」「言葉選びの妥当性」をJudge Criteriaとして利用した。
- 学習済みDomainでは正の相関を確認した一方、未学習Domainでは低下し、Generalization Limitが明確になった。

## 5. フロンティアAI対策9項目
- Quarterly PatchからKEV / EPSSを使うRisk-based Continuous Operationへ移行する。
- Virtual PatchはTemporary MitigationでありRoot Cause Fixの代替ではない。
- AWS Continuumはlearn + Human Approvalから徐々にenforceへ進める。
- AWS Serviceだけで対応は完了せず、Stop CriteriaやBCPは金融機関自身が決める。

**意味：** 二つの側面や対照的な事実を並べる。  
**接続：** `普通形 + 一方で`  
**使い方：** Top 3のUsage増加とEfficiency向上を同時に説明できる。  
**例文：** AI利用量は増える一方で、同じ使い方なら実質Token Costを下げる目標です。  
**例文の意味：** AI UsageとCost Efficiencyを同時に見る例。  
**ポイント：** Trade-off説明の基本。

### 7. ～とは限らない
**学習目安：** N2  
**意味：** 一般化を避け、例外や条件差があることを示す。  
**接続：** `普通形 + とは限らない`  
**使い方：** Top 4のDomain Generalizationを慎重に述べる。  
**例文：** 学習済み業種で相関が高くても、未学習業種で同じ結果になるとは限りません。  
**例文の意味：** Seen Domainの結果をUnseen Domainへ一般化しない例。  
**ポイント：** Evidence Boundaryを口頭で示すのに有効。
