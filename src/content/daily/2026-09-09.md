# A. 详细文字版

今天优先筛选 2026 年 9 月 8 日上午至 9 月 9 日上午的新内容，并避开昨天已重点汇总的 Identity-Aware AI Gateway、AI Coding Supply Chain、Memory Lifecycle、Figma Make→Claude Code 与富士通 AI-driven Work Redesign。今天的共同主线是：**当 AI Agent 能真正迁移系统、调用Cloud、执行Shell、发送邮件和完成购买以后，企业工程的重点会从“模型会不会做”转向“在哪个执行边界内做、谁能授权、结果怎样验证”。**

### ① COBOL、VMware、.NETまで――AWS「45億行に及ぶコード処理」で見えたAIレガシー刷新の現状：「数年→6週間」「8カ月→数日」の事例に学ぶ「4つの知見」

**来源：＠IT｜2026年9月9日 08:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/09/news027.html

AWS 总结了 `AWS Transform` GA 一年来的 Legacy Modernization 实践：累计处理超过 **45 亿行 Source Code**、迁移数十万台 VM。具体案例里，一个约 **25 万行**的 Mainframe Application 从过去需要数年的 Code Conversion + Test 缩短到 **6 周**；CSL 针对数千台 VMware Server 的 Migration Planning 提速约 10 倍；Signaturit Group 原估 6～8 个月的 .NET Modernization 被压缩到数日。AWS 汇总客户评价还给出 Cloud Migration 计算成本平均下降 35%、License Cost 下降 45%、整体 Migration Cost 最多约下降 60% 等数字。这里的 Evidence 主要来自 AWS 官方及客户案例，属于 Vendor / Customer Report，并不是统一条件下的独立 Benchmark。

比数字更值得学习的是 AWS 从大量项目中归纳出的“四个知见”。第一，Migration Tool 不能只活在专用 UI 里，因此 AWS Transform 通过 **MCP Server** 让 Kiro、Claude Code、Cursor、Codex 直接调用其能力。第二，开放 Extension 的同时需要共享基盘，防止 Team / Partner 各自扩展后产生 Quality Drift。第三，Modernization 不是单人 Coding Task，需要 Architect、Developer、Reviewer、Approver 的 Handoff 和 Change Tracking。第四，复杂系统不能全部交给概率性 AI；用户明确要求在精度与再现性重要的处理上保留**決定論的な手法**和 Human Intervention。**限制：** 文章中的时间与成本缩短来自不同客户与不同系统，不能把“6周”或“60%”直接当成你的系统可复现结果；迁移前仍要评估业务规则、依赖关系、测试覆盖和Rollback。

**为什么值得看：★★★★★**  
它把 AI Modernization 从“Code Translation”提升到 Workflow / MCP / Human Review / Deterministic Control 的系统工程问题。面试里可以用来回答“AI 如何真正进入 Legacy Migration，而不是只生成代码”。

### ② LLM乗っ取りでサイバー攻撃者がコスト節約　知財流出の危険性も高まる「LLMジャッキング」の深刻度

**来源：＠IT｜2026年9月8日 21:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/08/news083.html

Google Threat Intelligence Group（GTIG）指出，`LLM Jacking` 正把 AI Account、API Quota 和 GPU 变成新的 Cloud Abuse Target。2026 年其监测的 Dark Web 中 Claude、Gemini、Cursor Pro、Devin 等账号交易需求上升，平均交易价格相比年初上涨 2 倍以上；LUMMAC.V2、ACRSTEALER 等 Infostealer 也开始直接读取 Developer PC 中 AI Tool 的 Local Config，因为 API Key 与自定义 Model Routing 信息经常以明文存在。风险不止是“别人替你花 Token”：企业自有 Model、Fine-tuning Skill、Prompt、Training Data、RAG Knowledge Base 也可能被窃取或利用。

报告中的 2026 年 4 月 Incident 展示了完整 Attack Chain：攻击者先取得误暴露的 **GitHub PAT**，侵入 Google Cloud；随后开启 Gemini Enterprise、启动 HPC Instance，在 Artifact Registry 建立自定义 Docker Repository，将 LiteLLM 与 Manus 部署到对公网开放的 Cloud Run；又建立恶意 Editor Service Account、导出 Key，通过 **BigQuery** 搜索 Environment Variable / API Key，并利用受害组织 Data 运行 AI Workbench RAG。最后还滥用 **Cloud Quotas API** 申请增加 `NVIDIA RTX 6000 GPU` 配额，并启动多台 48 vCPU Instance。**Evidence Boundary：** 这是 GTIG / Mandiant 调查的具体事件，不代表所有 AI Account Compromise 都会发展成同样路径；真正可迁移的是监控点——Credential、Quota、Service Account、Public Exposure、BigQuery Scan 与异常 GPU Consumption 应关联分析。

**为什么值得看：★★★★★**  
它说明 AI Security 已经和 Cloud FinOps、IAM、Developer Endpoint、RAG Data Protection 合并成同一个 Incident Surface；对 AWS / Cloud / Security / AI Platform 面试非常实用。

### ③ Claude Codeを安全に使い倒すための、実行環境の隔離 はじめの一歩

**来源：DevelopersIO｜2026年9月8日**  
**原文 URL：** https://dev.classmethod.jp/articles/claude-code-isolation-20260901/

作者先把问题 Scope 缩小：不是试图一次解决 Claude Code 的所有风险，而是针对“Software Supply Chain Attack 进入开发机后，如何缩小机密信息泄漏的 Blast Radius”。AI Coding 会让 `npm install`、`npx` 等操作频率提高，人类很难审查所有 Transitive Dependency，因此单靠 Permission Prompt 或“我只装知名Package”不够。文章比较三层执行边界。第一层是 Claude Code 的 **Bash sandbox**，可通过 `/sandbox` 限制 Command 及 Child Process 的写入位置与 Network；但默认可能在 Sandbox 失败后走 Unsandboxed Retry，因此要用 `sandbox.allowUnsandboxedCommands: false` 关闭绕过路径。

第二层 **Dev Container** 能把 IDE Extension、Dependency、Test、以及人自己启动的 `npm run dev` 一起包进 Container，比 Command-level Sandbox 覆盖更广；但 Mount 进去的目录、Environment Secret、Git Credential 与开放 Network 仍然在攻击范围内，Docker-out-of-Docker（DooD）甚至可能把 Host Docker 权限带进去。第三层 **Claude Code on the Web** 把执行环境移到 Anthropic 管理的外部环境，可进一步远离 Local Secret，但文章标注它仍是 **Research Preview**，并且 Bedrock / Vertex AI 路径、内部 Network、硬件依赖、复杂环境准备等场景有适用限制。核心原则是：Isolation 只能保护“墙外的秘密”，所以要减少带入 Container / Remote Runtime 的 Credential。

**为什么值得看：★★★★★**  
这是 Coding Agent Security 中非常实战的一篇：不是问“有没有 Sandbox”，而是问**Sandbox 在哪一层、保护什么、哪些 Secret 仍被带进去了、有没有 Bypass Path**。

### ④ Meta、パーソナルAIエージェント「Muse」発表　メール送信や買い物も代行（まずは米国で無料提供開始）

**来源：ITmedia NEWS｜2026年9月9日 06:41**  
**原文 URL：** https://www.itmedia.co.jp/news/article/2609/09/2000001294/

Meta 的 `Muse` 已先在美国推出 iOS、Android 与 Web 版，基础 Model 为 **Muse Spark 1.3**。它不是单纯 Chat：可以发送邮件、预订旅行、Browser Form Fill、代用户谈判，并且在 App 关闭后继续运行长时间 Task；需要用户决定时再通知。Payment 可使用 Stripe Link 的一次性 Card Number，未来还计划接入 Shop Pay 与 1Password。这意味着 Personal Agent 已直接拥有 External Side Effect，Security 模型必须覆盖“执行什么、谁批准、Credential 在哪里”。

Meta 的关键设计是把 Intelligence 与 Authorization 分开。Muse 在专用 **Muse Secure VM** 内运行；VM 中还有与主 Agent 在系统级分离的 `Sentinel`，所有对 External Service 的操作与 Network Communication 都必须经过 Sentinel，Muse 无法自行关闭。主 Agent 看不到真实 Password / Payment Credential，只使用 Proxy Token，在 Network Egress 才替换成真实值；发送 Email、Purchase 等高影响操作前还要求 User Confirmation，并支持按 App 设置 Read-only / Send 权限。**限制：** Meta 明确承认 Prompt Injection 仍是行业未解决问题，Muse 也可能犯错，因此它采用 Untrusted Input、Classifier、Human Approval 等多层防御。Bug Bounty 对有效报告最高 30 万美元，影响单一用户的成功 Prompt Injection 最高 13 万美元；这些奖励金额是安全计划，不代表漏洞发生概率。

**为什么值得看：★★★★★**  
Muse 给出了高自治 Agent 的一个清晰 Runtime Pattern：`Agent ≠ Credential Owner ≠ Policy Enforcer`。这个分层很适合迁移到企业 Browser Agent、Payment Agent、Ops Agent。

### ⑤ Amazon Linuxが4年ぶりにメジャーバージョンアップ、「Amazon Linux 2027」パブリックプレビュー。SELinuxがデフォルトで強制モードに

**来源：Publickey｜2026年9月9日**  
**原文 URL：** https://www.publickey1.jp/blog/26/amazon_linux4amazon_linux_2027selinux.html

AWS 发布 **Amazon Linux 2027 Public Preview**，这是 Amazon Linux 2023 以来约四年的 Major Version Update。它仍部分基于 Fedora 生态但维持 AWS 自己的 Release / Support Cycle；Kernel 升到 **7.1 以上**，继续使用 RPM / `dnf`，支持 x86-64 与 ARM，并包含 AWS Neuron 等 Accelerator Driver。对多数 Cloud / SRE Team 真正需要提前验证的变化并不是版本号，而是 Security Default。

Amazon Linux 2023 默认启用 SELinux 但为 **Permissive**；2027 Preview 改成默认 **Enforcing Mode**。这意味着即使 Process 具有管理员 / root 权限，只要 Access 违反 SELinux Policy 也会被拒绝。对现有 EC2、Container Host、Monitoring Agent、Security Agent、Custom Daemon 来说，过去“能运行”不代表在 Enforcing 下仍能运行。**限制：** 当前是 Public Preview，而不是 GA；Publickey 文章没有给出生产性能 Benchmark 或确定 GA Date。迁移时应该分别验证 SELinux Audit Log、Custom Policy、Kernel / Driver、Container Runtime、x86-64 / ARM Compatibility，再决定 Rollout。

**为什么值得看：★★★★★**  
这是一条很适合日本 Cloud / SRE 面试的更新：Security Baseline 的默认值改变，会直接改变 Migration Risk 和 Incident Diagnosis 方法。

## 4. 今日の技術テーマ

### Agent Execution Boundary：模型越强，越不能直接拥有全部执行权

今天 Top 5 可以统一成一个结构：

```text
Identity / Source
      ↓
AI Reasoning
      ↓
Execution Boundary
├─ Deterministic Migration Step
├─ Sandbox / Container
├─ Sentinel / Policy Agent
├─ SELinux / Host Policy
└─ Human Approval
      ↓
Real Side Effect
      ↓
Audit / Verification
```

AWS Transform 说明，AI 可以大幅加快 Legacy Analysis / Conversion，但复杂 Migration 仍需要 Deterministic Step 与 Human Review。LLM Jacking 说明，一旦 Credential 与 Model / Cloud Resource 没有足够边界，攻击者可以把受害企业的 AI 与 GPU 直接变成自己的执行平台。Claude Code 文章说明 Sandbox 不只是一个开关，而是多个不同 Trust Boundary；Muse 更进一步把 Agent、Credential、External Action Authorization 拆到不同主体；Amazon Linux 2027 则在 OS 层用 SELinux Enforcing 强制 Policy。

**优点：** 第一，错误或 Prompt Injection 不会自动变成无限制 Side Effect；第二，权限可以和 Model Version 解耦，换模型不必重做所有 Security Rule；第三，Incident 后可以明确定位是 Reasoning Error、Credential Compromise、Sandbox Bypass 还是 Host Policy；第四，更容易逐步开放 Read → Write → External Action。

**局限：** Isolation 会增加 Developer Experience 与 Environment Maintenance 成本；Container 并不天然安全，Mount、Network、DooD、Credential 都可能穿透边界；Policy 太严格还可能让正常 Agent Task 频繁失败。另一方面，SELinux / Sentinel / Human Approval 只能控制“能不能做”，并不能保证 AI 的业务判断一定正确，所以还需要 Test、Evaluation 与 Domain Rule。

**日本企业落地注意点：** 建议把 Agent Action 按 Risk 分级：Read / Analyze 可自动；Code Write / Sandbox Command 受 Policy；Production Change / Payment / External Message 要求更强 Gate。Credential 尽量 Short-lived，不直接放进 Agent Context；同时记录 Owner、Tool、Resource、Approval、Result。对于 Legacy Migration，要保留旧系统与新系统的 Diff、Test Evidence 与 Rollback Plan，而不是把“AI 完成转换”视为 Done Definition。

面试可总结为：

> AI Agentを本番利用する場合、Modelの判断能力と実行権限を分離し、Sandbox、Policy Engine、OS Control、Human Approvalなど複数のExecution BoundaryでSide Effectを制御することが重要だと考えています。

## 1. AWS TransformとAIレガシー刷新

**中文知识点总结：**
1. AI Modernization 的价值不只在 Code Generation，还包括 Dependency Analysis、Migration Planning、Change Tracking 与 Workflow Handoff。
2. AWS 报告 1 年处理超 45 亿行代码、25 万行 Mainframe Conversion + Test 六周完成，但这是 Vendor / Customer Case，不能直接泛化。
3. MCP 让 AWS Transform 可以从 Claude Code、Cursor、Codex、Kiro 等开发入口调用，说明 Migration Capability 正从独立 UI 变为 Agent Tool。
4. 精度与可复现性重要的环节应保留 Deterministic Method 与 Human Intervention。

**日本語の知識ポイント：**
- AWS TransformはCode変換だけでなく、依存関係分析、移行計画、変更追跡、Team間Handoffまで含むModernization Workflowとして考える必要があります。
- 45億行超や6週間という数字はAWSと顧客の事例であり、自社Systemで同じ効果を保証するものではありません。
- MCP経由でClaude CodeやCodexから利用できる一方、精度が必要な処理は決定論的にし、人が介入できる設計を残します。

## 2. LLMジャッキング

**中文知识点总结：**
1. AI Credential 的价值已经从“调用 Model”扩展到 Cloud Quota、GPU、RAG 与企业 IP。
2. 2026 年 4 月 Case 中，GitHub PAT → Google Cloud → Cloud Run / BigQuery / Service Account / RAG / GPU Quota 构成完整 Attack Chain。
3. Endpoint Infostealer 正直接瞄准 AI Tool Local Config，因此 Developer Workstation 也属于 AI Security Boundary。
4. Cost Anomaly 应与 Identity / Quota / Resource Creation / Public Exposure 联动，而不是只看月末账单。

**日本語の知識ポイント：**
- LLM JackingではAPI利用料だけでなく、GPU、RAG、企業Data、Model資産まで攻撃対象になり得ます。
- GitHub PATからCloud Run、BigQuery、Cloud Quotas APIへ広がった実例は、Developer CredentialとCloud Monitoringを分離できないことを示しています。
- Cost Spike、Service Account作成、Quota変更、Public Exposureを同じIncident Contextで相関分析することが重要です。

## 3. Claude Codeの実行環境隔離

**中文知识点总结：**
1. Bash sandbox、Dev Container、Web Runtime 保护的层次不同，不能把“Sandbox Enabled”当成完整结论。
2. `sandbox.allowUnsandboxedCommands: false` 用于关闭 Sandbox 失败后的绕过执行。
3. Dev Container 仍可能暴露 Mount、Env Secret、Git Credential、Network，DooD 甚至扩大 Host Access。
4. 隔离只保护墙外的 Secret，因此最重要原则之一是“不要把不需要的 Credential 带进去”。

**日本語の知識ポイント：**
- Bash sandbox、Dev Container、Claude Code on the Webでは隔離するScopeが異なります。
- `/sandbox`だけでなく、unsandboxed retryを止める設定まで確認する必要があります。
- Containerを使ってもMount、Git Credential、Network、DooDが残ればHost側のRiskは消えません。

## 4. Meta Muse

**中文知识点总结：**
1. Muse 能发送邮件、购买、填表等，属于有真实 Side Effect 的 Personal Agent。
2. `Muse Secure VM` 与独立 `Sentinel` 将 Model 与 External Action Authorization 分离。
3. Agent 只看到 Proxy Token，真实 Credential 在 Network Egress 替换；高影响动作还要求 User Confirmation。
4. Prompt Injection 仍未解决，因此 Runtime Boundary 只能降低 Blast Radius，不能消灭输入风险。

**日本語の知識ポイント：**
- MuseはMuse Secure VM内で動き、外部ActionとNetwork通信は独立したSentinelの許可を通ります。
- CredentialをMain Agentへ直接見せず、Proxy TokenをEgressで差し替える設計が重要です。
- Prompt Injectionは未解決のため、購入やMail送信にはHuman Confirmationを残しています。

## 5. Amazon Linux 2027

**中文知识点总结：**
1. Amazon Linux 2027 是 Public Preview，Kernel 7.1+，继续 RPM / dnf，支持 x86-64 与 ARM。
2. 最大 Migration Point 是 SELinux 默认从 Permissive 改为 Enforcing。
3. Enforcing 下即使 root 也不能执行违反 Policy 的访问，因此 Agent / Daemon / Container 需要重新验证。
4. Preview 并没有生产 SLA / Benchmark 保证，应先看 Audit Log、Custom Policy 与 Driver Compatibility。

**日本語の知識ポイント：**
- Amazon Linux 2027ではSELinuxがDefault Enforcingとなり、rootでもPolicy違反Accessが拒否されます。
- Kernel 7.1以上やNeuron DriverなどRuntime側の変更もあるため、ApplicationとContainerを実環境で検証する必要があります。
- Public Previewなので、Production MigrationはGA条件やCompatibilityを確認してから判断します。

## C-3. JLPT语法（7个）

1. **～にとどまらず｜N1**：不止于……。结构：`名詞 + にとどまらず / 動詞辞書形 + にとどまらず`。例：`LLMジャッキングは利用料の不正消費にとどまらず、ModelやRAG資産の流出につながる可能性があります。` 中文：不止造成费用滥用，也可能导致 Model / RAG 资产流出。用于 Top 2 风险范围扩展。
2. **～かねない｜N1**：恐怕会……、有风险导致……。结构：`動詞ます形去ます + かねない`。例：`AI ToolのLocal Configを平文で残すと、Cloud全体の乗っ取りにつながりかねません。` 中文：明文保存可能导致整个 Cloud 被劫持。
3. **～に至るまで｜N1**：从……一直到……。结构：`名詞 + に至るまで`。例：`MuseはWeb操作からメール送信、購入に至るまで複数のActionを実行します。` 中文：Muse 的 Action 范围从 Web 操作一直到邮件、购买。
4. **～たうえで｜N2**：在……基础上再……。结构：`動詞た形 + 上で / 名詞 + の上で`。例：`SELinux Policyを確認したうえで、Amazon Linux 2027への移行範囲を決めます。` 中文：确认 Policy 后决定 Migration Scope。
5. **～に応じて｜N2**：根据……相应调整。结构：`名詞 + に応じて`。例：`開発TaskのRiskに応じてBash sandbox、Dev Container、Web実行を使い分けます。` 中文：根据 Risk 选择不同隔离层。
6. **～一方で｜N2**：另一方面……。结构：`普通形 + 一方で`。例：`Museは長時間Taskを自律実行できる一方で、Prompt Injectionは未解決の課題です。` 中文：能执行长任务，但 Prompt Injection 未解决。
7. **～とは限らない｜N2**：不一定……。结构：`普通形 + とは限らない`。例：`AWSの顧客事例で期間が短縮されても、自社Systemで同じ結果になるとは限りません。` 中文：AWS 客户案例提速并不保证自家系统同样结果。用于 Top 1 Evidence Boundary。

**5语法：** `～にとどまらず・～かねない・～に至るまで・～たうえで・～に応じて`
