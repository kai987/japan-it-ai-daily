### 1. [アップデート] AgentCore GatewayがBedrockのInvokeModel APIとモデルのフォールバックに対応したので試してみた

**原文：** https://dev.classmethod.jp/articles/agentcore-gateway-model-fallback/

**发布时间：** 2026-10-25 01:51:41 JST

LLM 主供应端出错后，是否重试、等待多久、切换到哪个模型，往往散落在不同应用中。DevelopersIO 的神野雄大以实际配置和故障注入说明，AgentCore Gateway 新增的 Bedrock Runtime 连接器与模型回退规则，可以把这些决定收拢到共同入口。普通调用使用 InvokeModel，流式调用使用 InvokeModelWithResponseStream；规则按模型名称匹配请求，并可替换送往目标端的模型标识。回退的前提仍是副模型能够接受相同的请求格式，不能把任意两种接口直接互换。

作者在 us-east-1 建立实验，主端是能分别返回正常结果、503 错误或等待10秒的 Lambda，副端是 Bedrock Mantle 上的 gpt-oss-120b；另用 Bedrock Runtime 和 Claude Haiku 4.5 检查普通与流式调用。Python 为3.14。由于当时镜像尚未提供完整的新 SDK，作者把1.43.118的 API 模型叠加在 boto3 1.43.115上使用。控制台中也尚未看到 Runtime 连接器选项，目标通过 SDK 创建。这些是当次实验成立的环境条件，不能省去后写成所有控制台和安装环境都已一致支持。

没有回退规则时，主端的503直接返回应用；加入规则后，副端返回200。让主端延迟10秒，再设置首个响应字节等待上限为3秒后，总体约4.7秒获得副端回复。作者又在相同迟延故障下各连续调用20次：关闭熔断器时累计93.5秒、主端调用20次；启用后累计70.1秒、主端调用12次。熔断器在连续失败后暂时跳过主端，减少重复等待。文章没有确认一个可配置的固定开启阈值，因此不能把本次大约第10～11次的现象写成产品契约，也不能把单环境20次比较当作一般性能保证。

可用性还有边界。流式输出尚未开始时可以回退，开始返回正文后再中断，则不会由另一模型续接未完的句子。网关自身限流产生的429、Policy拒绝产生的403，也不会因为列入回退条件就绕过限制。每一次尝试均计入网关调用费用；实际由哪个目标应答，需要看路由日志，不能仅凭调用成功就确认主端恢复。原文还报告 Converse 经该网关得到400。对于日本企业面试，可据此讨论入口统一、故障分类、部分回复如何展示、授权边界和重试费用，而不是笼统回答“准备备用模型即可”。

**阅读价值：** 适合把 AI 应用的故障处理讲到调用接口、首字节等待、熔断、流式中断以及授权边界，并清楚交代实验条件。

### 2. 同じ段落を10言語で送ってみた: 日本語は英語の何倍トークンを払っているのか（オープンモデル4種で実測）

**原文：** https://zenn.dev/runcrate/articles/0ce2f3c0b25a38

**发布时间：** 2026-10-25 09:05:05 JST

按字符数估算日语 LLM 费用容易出错：日语文字较短，不代表编码后的 Token 更少。Runcrate 团队使用自家推理 API，对一段英文技术说明及其9种译文进行测量，覆盖4种开放模型。英文原段落630字符，内容是租用一块 GPU 微调小模型的流程；GLM-5.3一次性翻译成各语言，日文为344字符。输入测量把输出上限设为1 Token，并读取 API 报告的输入使用量，不使用本地分词器估计来冒充账单数据。

由于聊天请求还带有模板开销，作者先发送一个字符作为基线，从段落请求中减去该使用量，再补回一个字符对应的份额。在这个口径下，日文段落在 Qwen3.8-Flash 上为165 Token、相对该模型英文1.26倍；gpt-oss-120b为243 Token、1.85倍；DeepSeek-V4.1-Flash为223，GLM-5.3-Flash为219。字符数近乎英文一半，输入用量却都更高。同一段日文的编码效率，也会随模型改变。这是一次特定段落的 API 记录，不是“所有日文固定多付某个倍数”的规律。

费用排名还需再乘单位价格。作者按测量时从 Runcrate 模型列表读取的价格计算，243 Token 的 gpt-oss-120b反而比165 Token 的 Qwen更便宜，约为 DeepSeek费用的3.5分之1。这里是特定推理服务的当时价格，不代表模型原厂统一报价，更不是未来价格承诺。对业务系统，应分别保存输入用量、计价来源及时间、总费用，避免把 Token 倍率直接解释成账单倍率。

输出侧也有隐藏差异：要求把同一日文段落概括成两句话，记录到的输出用量从141到780 Token，相差约5.5倍，而可见摘要长度没有相同幅度的差别。推理过程消耗会进入输出计费；GLM虽报告推理 Token 为0，却对233字符摘要计上780输出 Token，因此作者把内部分解不充分保留为不确定性，没有把0解释成已经证明完全没有推理开销。实验只有一个段落、每种语言一次机器翻译，也没有衡量摘要准确性。分领域的文体、译文信息量、模型质量与稳定延迟都尚未被控制，应拿自己的日语文档另外验证。

**阅读价值：** 可以向面试官解释日语场景中的分词、计费与质量为什么必须分开测量，并避免用一次单段实验替代模型选择。

### 3. localStorageの複数タブ競合で学習記録を消さない――Web Locksと更新検知で古いタブを止める

**原文：** https://zenn.dev/c_a_p_engineer/articles/localstorage-multitab-guard-20261025

**发布时间：** 2026-10-25 01:40:29 JST

同一个浏览器应用的两个标签页，各自保存着过去读取的状态；后开的保存动作可能覆盖先前已经完成的学习。文章以本地保存经验值、答题履历和复习计划的学习游戏为例：A与B都从100 XP开始，A保存120，B再保存130，并不等于两个会话已经合并。若整个 JSON 被旧副本覆盖，回滚的不只是总分，还包括奖励去重和复习期限。问题属于状态并发与持久化，不是 React 画面有没有刷新。

实现先记住读取时的原始 JSON 字符串，在写入前重新读取当前值并比较，不一致就停止保存。增加版本号、写入标签页标识和时间可帮助追踪，但版本号本身不是锁：比较完成与实际写入之间，仍可能插入另一个标签页。作者因此用 Web Locks 的同名独占锁包住“再读取—比较—写入”，让合作遵守同一锁的写入依次进行。旧格式数据即使没有这些辅助字段，仍可读取，避免为了加保护而重置既有进度。

storage事件负责尽早发现别页变化，但不会通知发出写入的那个页面，也不会把收到通知变成排他操作。检测到冲突后，应用停止答题和自动保存，进入恢复画面：既可导出尚未保存的内存进度、期待值和当前值作为诊断材料，也可重新读取已保存的最新状态。作者没有自动相加两份经验值，因为同一题的奖励可能被重复计入，答题与复习事件也需要明确的合并规则。诊断导出和普通备份格式不同，且包含学习履历，不能当成可直接公开的错误日志。

保护仅覆盖同一来源下、都遵守相同锁的操作；其他代码直接写入仍可越过这个约定。不支持 Web Locks 时，检查只能尽力而为，不能保证比较与写入原子化，也不能把多项 localStorage 更新变成数据库事务。原文的测试使用模拟锁，并包含检查 React 源码条件的测试；真正两标签页同时操作的 E2E、Android和Brave实机尚未执行，写作时也没有重新跑一次CI。这些限制要一并保留，才能准确区分“代码具有防护结构”“单元测试有对应案例”与“真实浏览器并发已经被证明安全”。

**阅读价值：** 适合 React／前端面试中的本地持久化、跨标签页冲突和恢复设计，能讲清通知、锁与数据合并各自负责什么。

### 4. DB更新とメッセージ送信の不可逆性 — Transactional Outbox で「消えるイベント」を直す

**原文：** https://zenn.dev/kyrenzk/articles/transactional-outbox-event-consistency

**发布时间：** 2026-10-25 09:45:45 JST

数据库已经保存订单，队列事件却发送失败，后续通知与库存处理就可能永远没有起点；反过来先发事件，也可能在数据库提交失败后留下一个不存在订单的通知。文章用 Transactional Outbox 解释跨系统双重写入的缺口：把业务行和待发事件行一起放进同一数据库事务，实际投递由独立的 relay 处理。它不是让数据库与外部队列瞬间变成一个事务，而是先可靠记录“有一件事应当被发送”，接受后续再达成一致。

实验采用 Linux x86_64、Go 1.26.0及 modernc.org/sqlite 1.61.0，数据库位于内存中，连接数限制为1；消息端则是能按指定次数失败的自制桩，并非实际SQS或Kafka。直接投递的案例显示：订单留下1条，投递为0。使用Outbox后，前两次投递失败仍保留待发记录，第三次轮询成功，发送1条、待发0条。这个结果验证的是保留待办事实有助于恢复，而不是已经在真实消息服务中验证了整套系统。

若消息发送成功后、数据库写入发送完成标记前崩溃，下次relay还会重新投递。作者演示收到2次、按事件标识去重后只有1件，说明Outbox并不自动带来“恰好一次”。消费端仍需要幂等保护；文章中的去重只是最小模型，没有实现生产环境下消费结果和去重记录如何共同持久化。回滚案例也有明确范围：第二次业务写入先触发订单主键冲突，因此不能把它说成另外验证了“Outbox追记单独失败时，业务更新也会回滚”的路径。

轮询方式容易起步，但扫描未发送行会产生数据库负载，等待时间也受轮询间隔影响；CDC读取变更日志，可降低应用查询侧负担，却需要额外的权限和连接器运维。原文只运行了轮询模型，没有测试CDC。多relay抢同一行、并行发送破坏顺序、已发送行不断增多后的清理或归档，都需要另行设计。内存SQLite也不能证明进程重启后的真实持久性或PostgreSQL/MySQL的隔离与锁行为。面试中的重点是指出提交边界、重试留下的事实和接收方的去重责任，而不是把任何失败都简化为“再试一次”。

**阅读价值：** 为后端与分布式系统面试提供可画出故障时序的案例，能准确说明丢失、重复、幂等和异步一致性之间的关系。

### 5. 「AI音声の読みが間違ってる」を公開前に見つけたい。日本語TTS点検Skillを作りました

**原文：** https://zenn.dev/chitoku/articles/d02d7611901d1f

**发布时间：** 2026-10-25 09:45:48 JST

日语语音自然、停顿顺畅，并不证明汉字读音正确。Chitoku公开的日本语TTS检查工具由Python CLI和Agent操作用Skill组成，目标是从台本和既有录音中找出需要聆听的候选位置。它先把台本变成假名读音，再使用从Whisper large-v3-turbo追加训练的kana-whisper识别音频，比较两侧假名。为了不让识别器迎合预期答案，台本和期待读音不会作为识别输入。这样得到的是独立音频识别与台本读音的差异，而非再让同一个提示复述原句。

候选在带波形、台本和识别文字的时间线上呈现，使用者一边播放一边选择无问题、需要修正或保留判断。ASR识别出的读音与人实际听到的读音分开保存；即使机器没有报出差异，也可手动圈出可疑部分。判断通过本地确认服务器自动写入JSON，后续Agent读取的是已经保存的审阅记录。这个流程缩小人工寻找问题的位置，但没有取消听音，也不会把“识别一致”直接当成“读音一定正确”。

原文用VOICEVOX演示按句修复：只有“脇本陣”读错的那一句，把合成输入改为假名“わきほんじん”再生成，原台本本身保持不动。其余两句的录音、审阅判断和采用版本均未变化。修正版的采用依据是机器对比已无差异，作者明确将它与人工重新听过区分。版本设计同样区分导入新录音、检查、批准和正式采用，导入不会立即替换正在使用的版本，旧录音也能回退。

当前公开的是试用范围：真实音频检查在Apple Silicon Mac上进行，但检出率、准确率尚未量化；即使没有候选，仍可能漏掉误读，时间戳也是估计值。免费演示可复用保存的识别结果；首次真正识别音频则需下载约3.24GB模型。Skill文件和Python运行环境是两个安装层，ASR本地执行不等于后续TTS重新合成一定没有服务费用。今天只核对了文章中公开的设计和记录，没有安装这个Skill、下载模型或复现其识别效果。对日本语学习产品而言，最可迁移的是把机器筛选、人的听音、单句修复与采用版管理拆开，避免一个“完成”状态掩盖不同证据。

**阅读价值：** 适合讨论日语AI产品的音频质量、人工确认和增量修复，尤其能保留采用依据及不受影响录音的边界。

### 1. [アップデート] AgentCore GatewayがBedrockのInvokeModel APIとモデルのフォールバックに対応したので試してみた

**面试问题：**

> 生成AIの応答先を自動で切り替える場合、どこまで継続できるかをどう考えますか。

**约30秒回答：**

## 4. 技术主题：把“完成”拆成可核对的状态

综合这五篇原文，可以得到一个设计上的判断：把“完成”拆成不同状态，会比只保留一个成功标记更容易恢复。HTTP 200只说明某次路由得到了响应，数据库提交只说明本地事实已经确定，ASR与台本一致也只说明机器比较结果一致。它们分别还需要目标日志、外部投递记录或人的听取判断，不能互相代替。这里是跨案例的分析，不表示五种技术具有同一种原子性保证。

浏览器保存与Outbox尤其适合画成两种时序。Web Locks保护合作标签页的重新读取、期待值比较和写入，发现旧副本后停止；Outbox则把业务变更与待发事实放进同一DB事务，随后才对外投递。后者在发送与登记完成之间仍有缝隙，所以需要幂等消费。恢复动作必须依据留下来的状态选择，不能遇到异常就从头重做全部步骤。

逐句TTS修复提供了另一个例子：原台本、用于合成的读音输入、候选录音、听取结论与采用版分别保存，才能只替换确有问题的一句，同时保留其他句子的证据。模型回退也要保留边界：开始输出后的断开不由备用模型无缝续接，换模型更不自动证明语义质量相同。减少等待或减少重生成是收益，状态变多、审阅和日志维护是代价。

在日本企业落地时，可将这些边界变成受入条件：日语业务材料的实际用量与准确性、跨标签页的用户操作、重复事件是否造成二次业务效果、音频采用是否经过相应判断。原文中的模拟锁、桩队列、单段翻译和20次调用，各自证明的范围不同。应在实际环境中逐项补验，并保留同一输入、配置与结果的对应关系，不能把某一条绿色检查扩写成系统整体可靠。

### 1. 台本（だいほん）｜N1

## C-2. IT/AI专业词汇

1. **First-byte timeout（最初の応答の待ち時間上限）**：收到第一个响应字节之前允许等待的时限。 原文把主端延迟设为10秒、首字节上限设为3秒，之后切至副端。

2. **Circuit breaker（サーキットブレーカー）**：失败持续后暂时跳过故障目标的机制。 20次对比中主端调用20次变12次，但开启阈值没有被确认为固定规格。

3. **Chat template（チャット形式のテンプレート）**：把消息角色和正文包装为模型输入时增加的格式。 测量用一字符请求作基线，区分正文用量和模板开销。

4. **Web Locks（同一オリジン内の名前付きロック）**：让同一来源的标签页和Worker协作串行处理共享资源的锁。 读、比、写需共同遵守同一独占锁；直接绕开锁的写入不受保护。

5. **storage event（別のタブへの保存領域変更通知）**：保存区变化后通知共享该区的其他页面的事件。 写入页面自身不会收到该通知，它也不能代替排他锁。

6. **Transactional Outbox（業務更新と送信待ち記録の同時確定）**：将业务更新和待发送事件一并写入同一数据库事务的模式。 投递由relay另行处理，发送后标记前故障仍会导致重复。

7. **Idempotency（同じ処理を繰り返しても結果を重ねない性質）**：相同请求或事件重复到达时，不让业务效果重复增加的性质。 原文只用事件ID集合演示去重，生产中的业务结果与去重记录仍需共同设计。

8. **CDC（データベースの変更ログを捉える方式）**：从数据库变更日志捕捉更新，用于向下游传递变化的方式。 是轮询以外的选择，但原文没有运行CDC，也未验证连接器。

9. **ASR（音声からの自動認識）**：从录音中识别说话内容或读音的自动处理。 本例将识别读音与台本读音比较，但ASR本身也可能错。

10. **kana-whisper（音声をカナとして認識するモデル）**：以假名读音呈现音频识别结果的模型。 文章不向识别模型输入期望台本，以减少答案诱导。
