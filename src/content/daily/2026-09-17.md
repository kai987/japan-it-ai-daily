### 1 Claude Codeで開発期間を2.5か月から1か月に縮めた「ハーネス」の設計手法

**来源：SmartHR Tech Blog｜2026年9月16日 11:02**  
**原文 URL：** https://tech.smarthr.jp/entry/2026/09/16/110205

SmartHR面对的是一个无法放进单一Claude Code Context的新功能：它要进入既有Modular Monolith，Regression会影响其他团队；长Session又会不断携带历史，使API Cost和可用Context持续膨胀。作者没有继续堆Prompt，而是先构造 **Harness**：Skill文件定义流程，JSON保存进行状态，Shell Script判定Completion Gate。Orchestrator由Claude Code主Session兼任，只负责Phase Transition、User Dialogue、State Update与检查，不直接实现；每个最小Task则启动一个新的Implementation Agent，用TDD完成并Commit，避免上一Task的Conversation Noise污染后续Context。

这个Harness最有工程价值的部分，是把“AI说自己完成了”变成机械事实。每个Task执行 **12项Shell检查**：目标Test必须green，而且Test数量为0也Fail；Feature Flag关闭时保持既有行为；所有Changed File必须位于Allowed Path；不能增加Package Dependency违规；TDD痕迹要能从Commit看到。机器无法可靠判断的共享Table Change与UI Flag遗漏则明确留给Human Review。Spec与Rules分开，冲突时Rules优先；用户确认后的决定写回Spec / Rules，而不是只留在Session Memory。最终Review只在全部Task结束后执行一次，并从Spec、Concurrency、Authorization、Feature Completeness四个角度并行检查。

**Evidence / Measurement：** 作者称这个尚未发布的单一功能原先有效工期估算约 **2.5个月**，先做Harness后，大体实现约 **1个月**完成；状态文件曾在10个Task时增长到118KB，因此拆为 `progress.json` 和 `stages.json`。Model也按设计自由度分工：Data Model / State Transition等高自由度Task用Opus，API、UI、Test等路径明确的Task可用Sonnet。**但是，**作者明确写道Harness不是银弹，并不适合所有Project，Infrastructure Design等工作也不一定能复用；2.5→1个月只是一个团队、一个功能的经验，不能当成Claude Code的一般Productivity Benchmark。

**为什么值得看：★★★★★**  
重点不是“Claude Code快了一倍”，而是怎样把Context切分、Spec回写、TDD与Deterministic Gate组合成可审计的AI开发流程。

### 2 毎秒数十万スパンを扱う、高トラフィック環境での分散トレーシング基盤の構築

**来源：CyberAgent Developers Blog｜2026年9月16日**  
**原文 URL：** https://developers.cyberagent.co.jp/blog/archives/65910/

AJA DSP的广告投放链路中，一个Bid Request会横跨多个Microservice和Datastore。过去只能从Metric发现异常，再到多个Log中拼原因，无法用一个Trace看清请求经过哪里、在哪耗时、在哪里失败。团队因此引入OpenTelemetry Instrumentation与 **Tail-based Sampling**。Head Sampling在请求开始时就决定是否保存，低采样率可能把最终发生Error或Delay的Trace一起丢掉；Tail Sampling则等Trace接近完成后再按结果判断，能保留调查价值高的异常，同时只抽取部分Normal Traffic。代价是即使最后不保存，也必须先处理全量Span，因此Sampling前的Collector Capacity成为核心约束。

架构上，Datadog Distribution of OpenTelemetry Collector（**DDOT**）以DaemonSet部署在每个Node，先收Span，再用Load Balancing Exporter按 `traceID` 把同一Trace送进同一个Sampling Collector；负责Buffer与Tail Sampling的Collector放到独立Node Pool，避免和广告处理争CPU / Memory。Production后Sampling Policy一度增到 **20个**，同保留率条件重复扫描Span导致CPU过高。团队先按Probability缩小待检查对象，再合并相同保留率条件并启用 `sample_on_first_match`，在不改变Retention条件和Rate的前提下把Policy从20个压到 **7个**。Scale-down时又用Queue / Retry重新分配未送Span，并给Collector `terminationGracePeriodSeconds: 60` 与 `preStop: 30s`，让Buffer中的Trace有时间完成判断。

**Evidence / Measurement：** 文章来自AJA DSP的Production Experience。上线后5xx、内部失败、质量下降、Async Failure等Trace能按意图完整保存，Delay、Cancel、4xx、Normal Trace按各自比例保留；团队报告Application Latency / Error Rate没有明显恶化，Peak Traffic也能在预期Budget区间运行。示例中 `decision_wait: 10s`、Baseline `sampling_percentage: 0.1` 用来说明机制。**但是，**具体Sampling Percentage、Policy分类和Resource Budget来自每秒数十万Span的AJA DSP，并非所有Kubernetes / Datadog环境的通用参数；迁移到别的服务仍要重新测Span Generation、Trace Duration、Collector Memory与Cost。

**为什么值得看：★★★★★**  
这篇把Observability当成真正的Production Workload来设计，而不是“接上Tracing就结束”。

### 3 人が「承認」した無害なコマンドでAIが乗っ取られる　コードエディタCursorを襲った“2行の攻撃”

**来源：＠IT｜2026年9月16日 08:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/16/news033.html

文章分析Cursor的 **CVE-2026-22708**。问题不在Memory Corruption或传统Privilege Escalation，而在AI Coding Agent的Command Approval模型：`export`、`typeset`、`declare` 等Shell Built-in曾可能被隐式信任，不出现在Allow-list Approval中。恶意Instruction如果藏在README、Dependency、Issue Comment等Agent会读到的Text里，就可能先静默改写Environment Variable，再等待用户批准看似无害的Command。公开示例只有两步：先把 `PAGER` 改成Payload，再让用户批准 `git branch`；Git为显示Branch List会调用PAGER，于是用户批准的只是Trigger，而不是最终执行内容。Cursor将其评为High，并在 **v2.3** 修复已知路径。

Docker Sandboxes说明“隔离”和“许可列表”解决的是不同问题。Sandbox给Agent一个microVM、独立Kernel / Filesystem与default-deny Network；即使Payload在Sandbox内成功执行，Host的 `~/.ssh/id_rsa` 也不直接存在。但Credential Risk并没有消失：为 `git push` 转发的SSH Agent Socket能让内部Process在运行期间“借用”身份，因此还需要Network Policy限制目标Address / Port。Workspace默认与Host Live Sync，未验证Code更适合用 `--clone` 提供独立Copy；共享Agent Skill Store也形成Sandbox之间的新Trust Boundary。

**Evidence / Measurement：** 报道基于Docker对已公开Cursor Vulnerability的复盘，并引用Pillar Security的研究。最重要的工程判断是：**Allow-list与Human Approval都不应被当成唯一Security Boundary**，Isolation应在First Command之前建立，Environment Mutation、Workspace Sync、Credential Forwarding要分别建模。**但是，**这条具体Exploit Route已经在Cursor v2.3修复，不能把文章理解成“当前Cursor仍能被相同两行攻击”；Docker Sandbox也不是万能防线，它缩小Blast Radius，却仍需要处理SSH Agent、Network Egress、Shared State与Host-side Tool后续信任。

**为什么值得看：★★★★★**  
它给Coding Agent Security一个很清晰的面试框架：Permission、Approval、Isolation和Credential不是同一个Boundary。

### 4 Lovable、ViteからRust製開発ツール「OJ」への切り替えを紹介

**来源：gihyo.jp｜2026年9月16日**  
**原文 URL：** https://gihyo.jp/article/2026/09/oj

Lovable的AI App Platform每天运行约 **100万个隔离执行环境**，每个Preview都要启动Development Server。多个AI Agent反复修改与Build时，Node.js / Vite的Memory与Startup Cost会在大规模Sandbox中累积。因此Lovable逐步把Preview Server从Vite切换到Rust实现的 **OJ**。OJ兼容一部分Vite Config / Plugin，以Rolldown负责Bundle、Oxc负责Parsing / Transform；需要JavaScript Plugin或Server Code时仍使用Node.js。它还会把Agent的Multi-file Edit批量反映到页面，减少中间状态被频繁显示。

真实服务数据中，Lovable报告从打开Preview到可交互的Median从 **17.4s降到8.0s**，Environment Allocation从 **14.5s降到3.0s**，App Load前Dev Server Process Memory约降到Node/Vite的15%。但另一组“1万React Component”Cold Start Benchmark必须谨慎读：Vite 4.9s、OJ 1.2s的比较里，只有Vite侧运行 `vite-plugin-checker`，OJ当时不支持这个Plugin，因此不是等价条件。Repository中较公平的Bundled Development Mode在M-series Mac上的Start+Display Median是 **OJ 1.315s vs Vite 8.2.1 1.528s**，时间很接近；Memory则是 **115MB vs 1751MB**，差距依然明显。

**Evidence / Comparison：** 这篇同时给Production Preview Measurement与Repository Benchmark，还引用Vite作者Evan You对比较条件的说明。OJ并不是Vite整体重写，而是复用Rolldown / Oxc并聚焦更窄的App Class；Vite则必须覆盖更多Framework、Plugin和Configuration。**但是，**OJ不覆盖全部Vite Use Case，`vite-plugin-checker` 等Plugin Compatibility有限，部分Mode也处于Experimental。选型时应把Cold Start、Memory、Plugin Coverage、Migration Risk拆开，而不是把一个Benchmark倍数一般化。

**为什么值得看：★★★★★**  
非常适合Frontend面试：既能讲React Preview架构，也能讲如何识别“不公平Benchmark”。

### 5 Google、会話を止めずに裏でタスクを実行する音声モデル「Gemini 3.8 Live」公開　推論強化の上位版も

**来源：ITmedia NEWS｜2026年9月16日 10:16**  
**原文 URL：** https://www.itmedia.co.jp/news/article/2609/16/2000001524/

Google发布 **Gemini 3.8 Live** 与 **Gemini 3.8 Live Extended Thinking**。3.8 Live强调大规模Realtime Conversation与Cost Efficiency，Extended Thinking面向复杂Multi-step Reasoning。关键变化是Execution Path：Tool / API Call可以在Conversation背后继续运行，Model可以先口头确认收到请求，再在不等待Tool完成的情况下继续对话；Video Input能近实时进入Context，并支持包含日语在内的97种语言在会话中自动识别切换。对Voice Agent来说，这意味着Conversation State与Background Task State必须分开管理。

开发者可从Gemini API / Google AI Studio使用 `gemini-3.8-live` 与 `gemini-3.8-live-extended-thinking`。Google列出的场景包括Camera辅助Onboarding、Voice Business Plan、从手绘Sketch生成可运行的React Component，以及Multi-step Reservation。Extended Thinking还能边推理边用语音说明进度。对企业工程而言，新增难点不是“Tool能不能调用”，而是Background Task完成后何时Commit Side Effect、用户中途改变Intent如何Cancel、Timeout / Retry如何恢复、重复Tool Call如何做到Idempotent；这些需要Application Layer明确State Machine与Audit。

**Evidence / Benchmark：** Google公表数据显示Extended Thinking（High）在Artificial Analysis Speech-to-Speech Quality Index为 **82.6**，前代Gemini 3.1 Flash Live（High）为71.5；报道还给出τ-Voice等指标。**但是，**这些是Vendor发布Benchmark，不等于日语客服、预约或Coding Voice Workload的实际成功率；Gemini Enterprise当时仍是Limited / Private Preview，报道也指出官方Blog没有明示API按量计费体系。Production采用前仍应实测Voice Latency、Interruption、Tool Side Effect、Long-session Stability与Cost-per-success。

**为什么值得看：★★★★★**  
它把Voice Agent从同步问答升级成并发系统问题：对话继续，并不等于后台Business Action已经安全完成。

## 4. 今日の技術テーマ：Execution Boundary

```text
Input / Context
      ↓
Agent / Runtime
      ↓
Execution Boundary
├─ What can be read?
├─ What can be executed?
├─ What is a deterministic pass/fail?
├─ What state is buffered or shared?
└─ What requires commit / approval?
      ↓
Evidence / Telemetry
      ↓
Human or Policy Gate
      ↓
Committed State
```

**机制：** SmartHR把Completion Gate外置到Shell与Test；AJA把Trace保存决策放到Tail Sampling Policy并用traceID保持完整Trace；Cursor案例把Permission与Isolation分离；OJ要求Performance Decision携带比较条件；Gemini Live让Conversation和Tool Execution并行后，Application必须显式管理Commit。Agent Capability越强，外部Boundary越不能含糊。

**优点：** Boundary可以跨Model复用。明天Claude、Gemini或Runtime换掉，Test Gate、Sampling Policy、Sandbox Egress、Benchmark Protocol、Side-effect Commit Rule仍有效，而且“为什么允许这次动作”可以用Test Output、Trace、Policy或Audit Log解释。

**局限：** Boundary只能覆盖被写出来的Failure Mode。Shell Test可能漏掉UX，Sampling可能漏掉未被属性化的重要Trace，Sandbox仍可能转发SSH Agent，Benchmark也可能因Plugin差异失真，Async Voice Task会遇到中断、重试和重复执行。因此Rule本身也必须从Production Failure持续更新。

**日本企业落地注意点：** 建议每个AI Workflow固定记录 `Context Source / Read Scope / Execute Scope / Deterministic Gate / Evidence / Commit Authority / Rollback`。低Risk阶段先自动化Read与Proposal，只有当Failure Mode和Audit稳定后，再扩大Write或Autonomous Commit权限。

# B. 重点总结和面试可用知识点

## B-1. SmartHR Claude Code Harness
**中文总结：** 2.5→1个月是单一功能Case，真正可复用的是Skill + 状态外置 + 12项机械Gate + TDD；Test为0也Fail、Feature Flag OFF回归、Allowed Path等规则让“完成”成为Deterministic Evidence。

## B-2. AJA DSP Tail Sampling
**中文总结：** Sampling前仍处理全量Span，traceID必须保持Trace完整；Policy从20→7解决CPU，preStop 30s处理Scale-down时Buffer欠损。  
**日本語の知識ポイント：** Tail SamplingはRetention Policyだけでなく、Sampling前Capacityと縮退時のTrace欠損まで含めて設計します。

## B-3. Cursor CVE / Sandbox
**中文总结：** CVE-2026-22708说明批准git branch也可能触发被Environment Variable改写的Payload；具体路径已修复，但Permission≠Isolation的原则仍有效。  
**日本語の知識ポイント：** Allow-listやHuman ApprovalをTrust Boundaryにせず、microVM、Network Policy、Credential Forwardingを別Layerで扱います。

## B-4. Lovable OJ
**中文总结：** 真实Preview 17.4→8.0s与Memory下降有价值，但1万React Component的4.9→1.2s对比存在vite-plugin-checker不对称；Bundled Mode时间接近而Memory差依然巨大。  
**日本語の知識ポイント：** Performanceは一つの倍率で語らず、Startup、Memory、Plugin条件、実Service値を分けて比較します。

## B-5. Gemini 3.8 Live
**中文总结：** Background Tool不阻塞对话让Voice UX更自然，同时引入Conversation/Task状态分离、取消、重试、幂等与Side Effect Commit；82.6是Vendor Benchmark。  
**日本語の知識ポイント：** Non-blocking Tool Executionでは、自然な会話よりBackground TaskのStateとCommit Boundaryを設計することが重要です。

### 1. ～ない限り
**学习参考：** N2  
**含义：** 除非……，否则……；只要不……就……。  
**接续：** `動詞ない形＋限り／かぎり`  
**使用说明：** 原文说明共享技能存储默认挂载，除非主动停用；突出改变默认状态的必要条件。  
**例句：** `共有設定を無効にしない限り、同じ保存先が使われます。`  
**译文：** 除非停用共享设置，否则会使用同一保存位置。  
**辨析与注意：** 不同于「に限って」的范围限定；本项表达条件不改变时结果持续。 当天Top 3原文形式：ない限り。例句为学习用原创。
