### 1. Cloudflare AI Searchで日本語のキーワード検索を使うなら、trigramトークナイザを作成時に選ぼう

**原文：** https://dev.classmethod.jp/articles/cloudflare-ai-search-cjk-keyword-tokenizer/

**发布时间：** 2026-11-05 23:35:32 JST

日文检索没有返回本来存在的文档时，问题可能出在查询词怎样被切分，而不在生成模型。原文比较了 Cloudflare AI Search 的 porter 与 trigram。前者按空白和标点分隔并做词干处理，后者使用连续三字符片段。作者把检索方式限定为关键词检索，以免向量检索返回的内容掩盖关键词一侧的失败。

实验使用 Workers Free 账户、两篇关于报销和休假的文档，保持 AND 模式与默认0.4阈值。创建时选择 trigram 的实例能用日语自然问句检出报销文档，porter 则为0条。三字符词「締め日」能命中，两字符词「経費」即使把阈值降为0仍无结果。作者还观察到，并不是问句里的每个三字符片段都必须存在，因此不能把界面的 AND 标签直接解释成自己想象的严格交集规则。

更换已有实例的分词器后，设置与重建索引任务都更新了，但约9分钟内的查询仍表现为原先的分词方式，反向切换也出现类似现象。这是特定日期、少量文件和控制台操作下的观察，作者没有判定它究竟是规格、缺陷还是尚未生效，也没有验证API切换。对工程实践有价值的是把配置保存、任务结束和实际查询分别验收，而不是把配置显示正确当成检索已经改变。

**阅读价值：** 能把日文召回问题缩小到关键词通道，并检查配置变更是否真正反映到查询。

### 2. 【MLflow 3.18】Skill Registryでスキル管理してみた

**原文：** https://zenn.dev/rrioh/articles/c0d66deddddafe

**发布时间：** 2026-11-06 00:24:47 JST

团队把代理指令复制到不同项目后，常常难以确认究竟哪一版在生效。原文实践了 MLflow 3.18.0 的实验性 Skill Registry，把技能正文与辅助文件共同登记。同名再次登记会增加版本，原版保留，也可以先标为草稿，确认后转成有效状态，再让 production 别名指向它。

作者分别用固定版本和别名取回文件，并确认辅助检查清单与原文件一致。固定版本适合复现实验，别名适合分配当前采用的版本，但记录运行时仍应保留实际解析出的版本。取回目标必须为空或尚不存在，重复写入已有目标会报错。文章也区分了已登记技能的搜索与产品自带技能的列表，避免把不同目录混在一起。

第二个实验使用 compare_evaluations()，对相同12个整数样本比较两个函数。正解率从0.5到1.0，平均绝对误差从0.5到0，输出还包含差值、置信区间和0.03125的p值。不过基准函数被人为设置为只在偶数上正确，这是接口演示数据，不构成大模型在业务上取得提升的证据。可复用的方法是保持输入配对、确认指标好坏方向，并同时查看差值与不确定性。

**阅读价值：** 把代理技能的版本分配和相同样本的结果比较联系起来，适合说明可复现的发布判断。

### 3. 非同期の操作が競合して更新が消える問題を、小さなキューで直す

**原文：** https://zenn.dev/carecraft/articles/react-action-queue-lost-update

**发布时间：** 2026-11-06 09:00:11 JST

一个报销演示在操作后马上切换使用者时出现更新丢失和画面回退。它用浏览器 Web Worker 模拟API，由客户端把当前状态连同操作发出去。如果两个操作都拿旧状态出发，后返回的结果就可能覆盖先完成的更新。React 的事件闭包还会保留创建它时那次渲染的状态，等待异步响应不会自动让运行中的函数读到新值。

作者用 useActionQueue 把 Promise 连接成顺序执行的队列，前一操作失败后仍允许后续操作执行，同时把原始 Promise 返回给调用者以便接收错误。真正执行任务时，从 useRef 读取最新状态。但是操作者身份必须在点击时固定，否则等待期间切换了人，旧操作就会被归到新人名下。这里的核心不是一律读取最新值，而是根据每个值的业务含义确定读取时点。

切换使用者时取得画面的动作和清空保存数据的动作也进入同一队列，避免旧任务在重置后又把数据写回。作者通过 Playwright 在同一段页面操作中连续点击并切换，再反复运行以重现竞争。不过这只是单个客户端的顺序控制。真实服务面对多个客户端并发更新时，仍需事务或版本检查等服务端措施，不能把浏览器队列当成跨用户一致性的保证。

**阅读价值：** 展示了最新业务状态与点击时操作者这两类时间语义不同的数据。

### 4. Database Insights のスタンダードモードで、Amazon RDS for PostgreSQL のロック待ちとブロック元を確かめてみた

**原文：** https://dev.classmethod.jp/articles/rds-postgresql-lock-wait-database-insights-standard-mode/

**发布时间：** 2026-11-05 11:30:24 JST

RDS 的负载图能显示等待，并不意味着它一定显示制造等待的连接。原文使用东京区域的 PostgreSQL 18.3、db.t4g.micro，让一个未提交的行更新挡住另外四个更新同一行的会话。实例默认是 Database Insights 标准模式，但通过CLI创建时 Performance Insights 仍未启用，作者在实验中另外打开了它。

标准模式图表出现 Lock:transactionid 和 Lock:tuple。持锁者却处于 idle in transaction，等待客户端下一条指令，没有正在执行的查询，因此没有作为负载显示。作者每60秒记录 pg_stat_activity 与 pg_blocking_pids()，发现排头的等待者直接等原因事务，后面三个等待者则等元组锁。看到哪类等待，与找出谁在挡住谁，是两个不同层次的证据。

释放原因会话后，等待中的更新在725.5～725.7秒返回，随后所有实验更新均回滚，在库数量保持原值。实测时长比指定的720秒更长，需要结合监控轮询间隔和开始时点解释。不过这个结果没有让标准模式获得付费模式的SQL锁分析能力，也只覆盖了一个行竞争场景。面试中可以用它说明，排查锁阻塞时只追高负载SQL，可能漏掉没有结束事务的空闲连接。

**阅读价值：** 提供了从等待事件走到阻塞关系和根因会话的具体调查路径。

### 5. Vite+ 1.5 がリリースされたので、vp migrate は ts-node をどこまで移行してくれるのか試してみた

**原文：** https://dev.classmethod.jp/articles/hasuto-vite-plus-1-5-migrate-ts-node/

**发布时间：** 2026-11-05 21:58:57 JST

升级 TypeScript 执行工具时，脚本输出没变不等于原有检查也被保留下来。原文在 Node.js 26.13.0 上，用带枚举计算逻辑的小型ESM项目测试 Vite+ 1.5.0 的 vp migrate。枚举用于区分真正的转换与仅删除类型注解的执行路径。

首次迁移保留了三条脚本。补上明确配置文件的 TS_NODE_PROJECT 后，不做类型检查的运行脚本才被改写成 Node.js 预加载转换。测试脚本则在把 node:assert/strict 的默认导入改为具名导入后迁移成功。原先包含类型检查的脚本继续保留警告，需要手动拆为先执行 vp check、成功后再运行。

作者故意把价格写成字符串，发现新的执行路径仍会算出相同的结果，因为乘法发生了数字转换，而类型检查能够指出错误。把检查失败与停止执行连起来，才能保住原先的约束，之后才移除 ts-node。限制也很明确，同一实验的 CommonJS 版本仍因互操作警告而保留原脚本，旧版Node也有兼容条件。文章的价值在于用错误输入验收迁移承诺，而不只比较正常输出。

**阅读价值：** 用类型错误的反例揭示工具升级中可能丢失的质量保证。

## 4. 技术主题：按各项保证分别验收自动化结果

今天的共同问题是，自动化步骤报告完成，能否证明它原本要守住的性质。重建索引结束还要检查查得到什么，操作排队还要检查身份归属，脚本迁移成功还要检查错误能否阻止运行。验收的对象是业务性质，状态标签只是其中一份证据。

可以为每个性质构造一个有区分力的小反例。日语搜索用三字符词和两字符词，异步界面用点击后立刻切换操作者，类型工具迁移用故意写错的价格类型。排查数据库等待则加入处于空闲状态却仍持锁的原因会话。这些例子不共享一套实现，却都要求从自动化步骤之外核验结果。

版本登记和成对评价让这种核验更容易复现。技能正文与辅助文件共同固定为版本，比较时让同一输入对应两边结果。但12个人工样本的p值和少量文档的检索行为都有适用边界，代表性、数据量和真实并发条件仍需另行评估。

用于日本企业项目时，可以把审批身份、日语制度文档和已有Node脚本等具体约束转为验收用例。这是基于本文实验提出的工程应用思路，不代表文章已经证明各企业的生产效果。

**回答要点：** 业务状态要包含先行操作的结果，所以执行时读取；操作者属于点击事件，所以入队前固定。

**回答要点：** 相同输出可能隐藏类型检查的丢失；负载图可能遗漏持锁但空闲的未完成事务。

# B. 重点总结与可用于面试的知识

### 1. Cloudflare AI Searchで日本語のキーワード検索を使うなら、trigramトークナイザを作成時に選ぼう

1. **中文：** 单独比较关键词检索，避免向量结果掩盖关键词通道的0命中。
   **日本語：** キーワード検索だけにして、ベクトル検索の結果と混ぜずにトークナイザを比較します。

2. **中文：** 三字符分词的收益与两字符词的限制需要一起验证。
   **日本語：** 三文字以上の部分一致と二文字語の検索は、同じ設定でも結果が異なります。

3. **中文：** 变更设置、索引任务成功与查询结果改变是三个需要分别观测的事件。

### 1. 現れる（あらわれる）｜N3

- 词性：動詞・下一段
- 含义：出现在可观察的位置，显现出来。
- 搭配：画面に現れる / グラフに現れる / 差が現れる
- 文章语境：持锁但未执行查询的连接没有出现在数据库负载图里。

- 例句含义：导致问题的连接也可能不显示在负载图中。
- 辨析：本例是显现、被观察到的含义，不是到场或出现人物。

### 2. 吐く（はく）｜N3

- 词性：動詞・五段
- 含义：技术口语中指程序抛出异常或输出错误。
- 搭配：例外を吐く / エラーを吐く / メッセージを吐く
- 文章语境：MLflow原文使用「AssertionErrorを吐きます」描述未达到改善条件时的行为。
- 例句：改善の条件を満たさなければ、検査は例外を吐きます。
- 例句含义：如果不满足改善条件，检查会抛出异常。
- 辨析：属于技术交流中的口语，正式文档可写「例外を送出する」。

### 3. 分ける（わける）｜N3

- 词性：動詞・下一段
- 含义：把不同对象或职责分别处理。
- 搭配：役割を分ける / 処理を分ける / 実行と検査を分ける
- 文章语境：原文分别讨论把执行与类型检查拆开，以及把状态读取和身份捕获的时点分开。
- 例句：実行と型検査を分けても、検査が先に終わる順序は守ります。
- 例句含义：即使把执行与类型检查分开，也要保持先完成检查的顺序。
- 辨析：不同于「切り分ける」强调排查原因，这里指划分职责。

### 4. 並べる（ならべる）｜N5/N4

- 词性：動詞・下一段
- 含义：把对象排列起来，使其便于比较或查看。
- 搭配：結果を並べる / 同じ入力を並べる / 指標を並べる
- 文章语境：MLflow把同一数据的两次评价结果并列显示，进一步计算差值。 学习参考等级为N4。
- 例句：同じ入力に対する結果を並べて、差を確認します。
- 例句含义：把相同输入对应的结果并排比较，确认差异。
- 辨析：排列只是观察方式，不能单凭并列就证明改进。

### 5. 外す（はずす）｜N3

- 词性：動詞・五段
- 含义：把某物从原来附属或包含的范围中移除。
- 搭配：依存から外す / 対象から外す / 設定を外す
- 文章语境：Vite+案例先验证运行与检查职责，再从依赖中移除ts-node。

### 6. いずれ（いずれ）｜N2

- 词性：副詞
- 含义：表示将来的某个时候，迟早会发生。
- 搭配：いずれ移行する / いずれ必要になる / いずれ確認する
