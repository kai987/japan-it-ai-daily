### 1. Amazon BedrockとSageMakerのAIエージェントでOpenTelemetryの自動計装が行われる範囲

**原文：** https://zenn.dev/ymotongpoo/articles/20261014-bedrock-sagemaker-otel

**发布时间：** 2026-10-14 09:00:08 JST

AI 代理的可观测性，首先要分清调用的是模型、托管推理端点，还是代理运行时。原文使用 Python boto3，分别考察 Bedrock Runtime 的四种模型 API、SageMaker InvokeEndpoint 和 AgentCore InvokeAgentRuntime。三者自动生成的记录不同；一条 AWS 客户端调用记录，并不等于已经掌握模型、工具和容器内部的整条处理链。作者核查的是 10 月 13 日的源码、官方资料与部分实际调用，GenAI 语义规范仍处于 Development 阶段。

在 us-east-1 调用 Nova Micro 的实验中，botocore 的 Bedrock 扩展确实生成了跨度和指标，但 0.66b1 仍使用 gen_ai.system 等旧属性。另一个 genai-bedrock 1.2b0 的源码已采用 gen_ai.provider.name，本文没有实际运行这一库，不能把源码比较说成双库实测。两者都包装 BaseClient._make_api_call，同时启用可能重复计装，亦未做并用验证。instrument() 只是安装钩子，仍须正确设置 TracerProvider、MeterProvider 与导出器。

SageMaker 的关键断点在服务边界。作者在 us-east-2 的 ml.t2.medium 端点比较后确认，直接发送的 traceparent HTTP 头不会原样进入模型容器。可用 CustomAttributes 携带上下文：版本 00 的 traceparent 为 55 字符，参数上限为 1024 个可打印 US-ASCII 字符。最小方案只注入 traceparent；若混合 tracestate、baggage，不宜简单用逗号拼接，因为值本身可能含逗号。多字段应约定 JSON 编解码并检查总长度，容器显式提取后再建立子跨度。实验由此连上了相同 Trace ID 与父子关系。

AgentCore 的官方观测接入路径要求 ADOT SDK 直接向 OTLP 端点发送；文中所说的 Collector 不受支持，指官方 Agent Observability 路径，不能推导为所有自定义中转都不可实现。会话 baggage 也要在处理结束时解除上下文，避免复用线程串入前一会话。另一个容易误读的开关是 AWS_GENAI_CONTENT_EXTRACTION_OPT_OUT=true：它停止把正文从跨度抽到日志，正文会留在跨度中，并不是禁止采集提示词。因此必须分别审查日志与跨度的访问权限、保留期和敏感信息处理。

CloudWatch 的接收、索引和展示是不同阶段。OTLP 采用 HTTP；Transaction Search 的账号与区域设置会改变 X-Ray 跨度的存储路径，默认仅索引 1%。作者的小样本约十分钟后在 Transaction Search 出现，不能因某个界面暂时空白就断言导出失败，应先查看导出器的发送与失败计数。按键名脱敏只覆盖指定属性，未必覆盖事件或已搬到日志的正文；每个字符串截断至 4096 字节，也不能保证整个跨度符合 200 KB 上限。

费用判断同样有边界：当前自动指标主要区分输入与输出 token，缓存读取可能只有跨度属性，没有自动生成对应的费用指标。不能直接把聚合 token 直方图当成精确账单；需要价格表、缓存类别的计量或使用明细核对。本文没有给出所有模型、地区和库版本通用的端到端保证，其价值是把自动覆盖、手工补齐、正文治理和计费依据逐项拆开。

**阅读价值：** 适合练习回答“自动计装到底覆盖了什么”：既能解释 SageMaker 的传递断点，也能说明提示词治理和计费为何需要另行验证。

### 2. LINEスキマニのトップページにおけるパフォーマンス改善（インターンレポート）

**原文：** https://techblog.lycorp.co.jp/ja/20261013a

**发布时间：** 2026-10-13 11:00:00 JST

LINE スキマニ的职位列表最初依靠 CSR，首批职位信息约 3500 ms 才出现。作者明确指出，这个业务可见时间不直接体现在 Core Web Vitals 中。六周实习期间的改动限定于未登录用户的初始显示，沿用已有 SSR 基础设施，而非改写所有登录、搜索与无限滚动行为。

第一步是稳定数据身份。TanStack Query 的 queryKey 只应由影响检索结果的条件构成；把界面状态参数一起放进去，会使同一查询难以命中缓存。实现先校验条件，再去重、排序、省略默认值。例如 prefectureIds 的 47,13,1 归一为 1,13,47，occupationIds 的 3,1,3 归一为 1,3。统一 URL 也使 canonical 与 meta 标签整理成为可能，但原文没有给出搜索排名提升的测量。

服务端预取职位信息，hydrate 后继承为初始数据；用户信息和检索条件就绪后，再转入通常的客户端查询。这让首屏不再等待完整的客户端获取链条，但把 API 等待移到了服务端。一个本地请求的 TTFB 为 532 ms，其中 SSR 529 ms、API 等待 403 ms、renderToString 126 ms；序列化 4.9 ms、dehydrate 等不足 1 ms。另有约 100 ms 网络开销，不能将本地结果直接当作公网响应时间。

解决办法不是让所有请求共享 QueryClient。其缓存可能含个人信息，跨请求共享会增加隔离风险，且现有前后端同构代码不易改造。作者保留每个请求一个 QueryClient，在服务端请求函数外增加 Stale-While-Revalidate 装饰器缓存。命中时 API 等待缩到约 1 ms，说明应在真正瓶颈所在的层加缓存，而不是牺牲用户隔离来追求命中率。

开发环境部署后，一个请求的 LCP 为 387 ms，分解为 TTFB 226、资源等待 4、下载 46、渲染 111 ms；该时点已有职位信息。这里不能说“LCP 从 3500 降到 387”，因为两端不是同一指标。作者在正式用户验证前结束了实习，生产效果尚未核实。面试里应同时说明实现、缓存安全、测量口径和未完成的验收。

**阅读价值：** 这是与前端求职直接相关的完整案例：从 queryKey 与 hydration 讲到 TTFB 分解、跨用户隔离和上线前后的证据边界。

### 3. Lambda Web Functions と Lambda Web Adapter で、アセット数多めの Next.js（SSR）ページの配信性能を比べてみた

**原文：** https://dev.classmethod.jp/articles/lambda-web-functions-vs-lwa-nextjs-assets/

**发布时间：** 2026-10-14 00:57:27 JST

Lambda Web Functions 为 Web 请求提供原生 HTTP 执行环境，单环境并发上限可设为 1–128，默认 64，CPU 固定为 2 vCPU。原文将同一份 Next.js SSR 构建分别放到新功能和传统 Lambda Web Adapter（LWA），观察静态资源请求较多时的表现。比较的是交付形态和具体负载，不是所有 Lambda 应用的通用性能结论。

东京区环境使用 Next.js 16.4.0、React 19.3.0、Node.js 24，LWA 为 1.1.0。测试页含 150 个动态组件，但构建优化掉了大段未使用的文本；实际获取 HTML 1 份和 JavaScript 156 份，合计 157 次请求、246645 字节。不能按每组件 8000 字符推算出不存在的巨大下载量。两端构建相同，但 Web Functions 用 ZIP、固定 CPU，LWA 用容器与 2048 MB 内存；公开入口、资源配置也不完全一致。

k6 2.3.0 模拟 VU 10 与 20，每个虚拟用户用 HTTP/1.1 获取一整页，资源最多六个并发，不用缓存、不加思考时间。每次先替换环境并用 curl 预热一次，排除前五秒助跑，再统计三十秒；每个条件只跑一次，并在两组 VU 中交换运行顺序。页面完成时间止于最后一个资源下载，并未执行真实用户的完整渲染；也不是纯冷启动测试。

VU 10 时，Web Functions 为 22.9 页/秒、完成中位数 439 ms，LWA 为 17.4 页/秒、575 ms；VU 20 时分别为 44.9 与 34.7 页/秒，中位数 447 与 575 ms。四次实验的 429、5xx 和超时均为零。在这些条件下，吞吐约为 1.3 倍。VU 20 的统计段 LWA 有六次冷启动，而 VU 10 两者都为零仍有差异，因此不能把结果全部归因于消除冷启动。Web Functions 在 VU 20 也扩展到 83 个环境，默认并发 64 本身不证明收益来自多路复用。

日志模型还影响成本与排障。LWA 默认逐请求输出 START/END/REPORT，Web Functions 平台日志按环境和时间段汇总。没有应用访问日志的此次配置，日志量约为 LWA 的 1/200；该日志统计包括助跑，不能与仅三十秒的请求数直接混为同一口径。另一小型实验给 50 次请求加应用日志，响应 lambda-web-request-id 与日志 requestId、路径对应，说明需要逐请求追踪时应在应用层补齐。新增日志后的总体费用没有实测。

浏览器暖态截图的 Load 为 168 与 301 ms，但 Finish 为 1.41 与 1.43 秒，指标也不能互换。CPU、打包方式、公开路径、单次运行与缓存关闭共同限制了归因。采用时可借鉴同构建对照、完整资源集合、尾延迟与请求关联的测量设计；应再用自身缓存策略和多次重复实验验证，不能从这个样本给出普遍降本承诺。

**阅读价值：** 适合把 Next.js 的用户体验、服务器吞吐和逐请求可观测性分开解释，也能练习识别基准测试中的不等价条件。

### 4. [アップデート] AWS Glue でシステム管理型の Iceberg マテリアライズドビューが利用可能になったので、通常のマテリアライズドビューと書き込みを比べてみた

**原文：** https://dev.classmethod.jp/articles/20261013-aws-glue-system-managed-iceberg-mv/

**发布时间：** 2026-10-13 23:55:46 JST

普通 Iceberg 物化视图即使表达的是共享查询结果，拥有写权限的使用者仍可能直接插入或删除数据，使结果偏离定义。AWS Glue 的系统管理型将数据与定义的写入交给 Glue，仍以标准 Iceberg 形式供 Athena、EMR 等读取。作者不是只读产品公告，而是在同一 S3 Tables namespace 建两种同 SQL 视图，比较不同入口的写入。

实验在东京使用 Glue 6.0、Spark 4.1.1-amzn-0、两台 G.1X 与 Athena 3，分别使用作业角色和 Lake Formation 管理员测试角色。管理型需 spark.sql.mv.managed.enabled=true 和 CREATE MANAGED MATERIALIZED VIEW，存储仅支持 S3 Tables，普通 S3 bucket 不适用。创建会等待 Glue 初次计算；五行源数据生成三行汇总，普通创建 9.6 秒，管理型 211.9 秒。这个小样本不能推出大规模处理的固定速度。

状态判断要看实际字段。GetTable 的 ViewDefinition.IsManaged 才区分管理型，两者的类型标签均可显示 MANAGED。管理型 SELECT * 还带 __ivm_s_total_amount、__ivm_num_rec 内部列，应用最好明确列名。首次用三列 INSERT 的失败只说明列数不符；作者改为包含五列后，管理型仍因 S3 403 拒绝，而普通视图的 INSERT、DataFrame append、DELETE 和 Athena INSERT 能改变结果。这才形成了较公平的保护验证。

目录与存储层也有差异。将管理型 IsManaged 改为 false 被 API 拒绝；修改查询文本亦不能这样绕过保护。普通视图的 UpdateTableMetadataLocation 则接受了旧元数据指针，随后 Glue 目录版本不一致，Athena 与 Spark 读取失败。原文记录过一次旧内容 SELECT 成功，随后仍报错，原因未解，不能当成已经修复。管理型同类元数据操作被 ExplicitDeny 拒绝，但内部策略存放机制没有核实。

两行新增后，管理型变成 STALE；首次刷新缺 glue:StartMaterializedViewRefreshTaskRun 权限，补齐任务 API 权限才成功。七行数据的 FULL REFRESH SQL 等待 456.5 秒，而异步刷新任务约 223 秒、240.3 DPU 秒。SQL 等待、刷新任务与完整作业的计费范围不同。自动刷新也不能只看命令返回：文档支持的十分钟间隔在此 Spark 解析失败，一小时成功；DROP SCHEDULE 返回成功后 RefreshSeconds 仍为 3600，随后出现自动任务，作者再用停止 API 确认 STOPPED。

管理型保护并不代表所有管理操作不可变：读取、REFRESH、部分属性修改与删除仍可执行。定义和 schema 演进受限制，需删除重建。适合考虑它的场景，是给其他团队提供汇总结果且不希望对方直接改结果；仍需安排刷新、权限、费用和实际状态回读。本文没有证明所有版本都复现调度异常，也没有解释一次短暂读取成功的原因，保留这些未解部分比简单宣布“全面安全”更有价值。

**阅读价值：** 适合回答共享数据的写入边界，也提供了一个很具体的“命令成功不等于状态成立”的运维案例。

### 5. [アップデート] Kiro で管理者がサインイン方法を制限できるようになったので試してみた

**原文：** https://dev.classmethod.jp/articles/kiro-governance-sign-in-controls/

**发布时间：** 2026-10-14 06:57:20 JST

企业希望使用 IAM Identity Center 管理 Kiro，但允许个人 Google、GitHub 或 Builder ID 登录时，安装客户端可能绕开组织期望的账号路径。原文测试的是向受管端点分发 managed-settings.json 的控制方式。它要求 IDE 1.2 及以后、CLI 2.25.0 及以后，组织部署需要 MDM 等端点管理手段；不能把这一路径写成整个产品只存在一种控制入口。

macOS 文件放在 /Library/Application Support/Kiro/managed-settings.json。规则 capability 为 signin_method，effect 为 deny；match 的 ["*"] 先拒绝所有方式，再用 exclude 的 ["idc"] 保留 Identity Center。方法 ID 区分大小写，idc、builder_id 等才是规则使用的名称，不能拿界面文字或内部 awsidc 直接替代。settings 可预填组织 start URL、区域并加 HTTPS 帮助链接；只允许一种方式时直接进入组织表单。

作者不止查看按钮是否隐藏，还手改浏览器登录 URL 加上 Builder ID。浏览器仍能完成个人认证，但返回 IDE 后被拒绝。官方说明客户端会在结果返回时重新检查方式，在发放 token 前拒绝禁止方式。这证实了该正常配置下的客户端回查，不等于账号在所有入口都禁止登录。

适用范围是有配置文件、版本满足要求的安装客户端。Kiro Web、未分发文件的设备以及旧客户端不受此规则限制。文章没有测试损坏规则等异常配置，也没有证明失败时一定封闭。企业应用时应把端点覆盖、客户端版本、允许账号及回调拒绝一起验收；MDM 分发的难点不能仅靠设置文件本身解决。

**阅读价值：** 能把企业 AI 工具治理讲成可验证的端点控制，区分登录界面、认证回调与实际覆盖范围。

## 2. 四类速览

- 生成 AI 与追踪：Bedrock、SageMaker、AgentCore 的自动覆盖和跨服务上下文不同，提示词保存与费用指标需独立审查。
- 前端与 Web 配信：LINE 的 SSR 与两层缓存改善业务初屏；Lambda 对照则测资源获取吞吐，两篇指标不能混用。
- 数据平台：Glue 管理型 Iceberg 汇总将数据和定义写入交给服务，但刷新、权限和实际调度仍需要使用者检查。
- 开发与端点治理：Kiro 的安装客户端回查登录结果，策略覆盖依赖配置分发和版本，不包含所有入口。

**关键词：** managed-settings.json / signin_method / idc



## 4. 技术主题：让“成功”落到可观察的实际状态

今天五篇文章共有的不是某种产品，而是工程验收的方法。追踪导出成功不能代替确认父子关系；SSR 完成不能代替业务信息已经显示；基准更快也不能省略资源、缓存和测量次数。设计时先说清验收对象，再选对应的证据，避免用方便取得的信号替代真正目标。

Glue 的 DROP SCHEDULE 与 Kiro 的浏览器认证提供了更直接的反例。一个命令成功后，调度字段和任务仍可能存在；浏览器认证成功后，客户端仍可能拒绝结果。验收应沿着实际生效边界读回状态，而不是只看第一层返回值。这是从原文归纳的设计建议，不是在本日报中新增的产品实验。

可以把检查表写成四项：目标状态、观测位置、成立条件、未验证范围。例如“同一追踪链”看调用端和容器；“首屏改善”同时看业务内容与性能指标；“写保护”验证等价操作失败的真正原因；“受管登录”检查安装、配置和认证回调。日志更少或指标更好也有代价，应用时应明确记录敏感数据、排障粒度和费用口径。

## 5. 面试复习卡

### Q1

> SageMakerでtraceparentを渡す際、HTTPヘッダーとCustomAttributesはどう違いますか。

**回答要点：** 原文实测中普通 traceparent 头到不了容器；CustomAttributes 原样传递但有1024字符限制。双方须约定编码和提取，并验证同一 Trace ID 与父子关系。

**回答要点：** Glue 看 RefreshSeconds 与任务真实状态，Kiro 看安装客户端是否接受认证结果及配置、版本覆盖；不能用第一层成功推断最终生效。


# B. 重点总结与可迁移知识

### 1. Amazon BedrockとSageMakerのAIエージェントでOpenTelemetryの自動計装が行われる範囲

**知识点1：** 自动计装的覆盖取决于 API 与库版本；读源码得到的属性差异，不能冒充库的运行结果。

**日本語：** 計装の有無だけでなく、対象APIとライブラリーの版を確認します。ソース比較と実測を区別します。

**知识点2：** 上下文必须穿过实际服务边界。SageMaker 需要双方约定 CustomAttributes 的编码及提取方式。

**日本語：** サービス境界を越える伝播は実際の親子スパンで確認します。SageMakerではCustomAttributesの符号化・復号を双方でそろえます。

**知识点3：** 正文抽取 opt-out 不等于禁止采集；缓存 token 也不能仅凭输入输出指标换算成精确费用。

**日本語：** 本文抽出の停止と本文収集の停止は別です。キャッシュ料金も入力・出力メトリクスだけでは確定しません。

### 2. LINEスキマニのトップページにおけるパフォーマンス改善（インターンレポート）

**知识点1：** SSR 预取需要可重现的查询身份；无关参数、重复与顺序差异不应制造新的数据身份。

**日本語：** SSRのプリフェッチを生かすには、検索条件が同じならqueryKeyも同じになる正規化が必要です。

**知识点2：** 不要为缩短 TTFB 而全局共享可能含个人信息的 QueryClient，应分别设计缓存层与隔离范围。

**日本語：** TTFBの短縮とユーザーの隔離を両立させます。QueryClientとサーバー側のSWRキャッシュを区別します。

**知识点3：** 业务信息初次显示、LCP、TTFB 各有口径；开发请求的结果不能当成生产用户统计。

**日本語：** 求人初表示、LCP、TTFBは別の指標です。開発環境の一例を本番の利用者統計として説明しません。

### 3. Lambda Web Functions と Lambda Web Adapter で、アセット数多めの Next.js（SSR）ページの配信性能を比べてみた

**知识点1：** 先核对真实构建产物，再判断请求负载；源码中的未使用文本不能当作传输字节。

**日本語：** 負荷は実際のビルド成果物で定義します。使われないソース文字列の大きさから転送量を推計しません。

**知识点2：** 吞吐、完整资源获取、Load、Finish、LCP 分别定义，避免拿不同指标解释同一种改善。

**日本語：** スループット、全アセット取得、Load、Finish、LCPを区別し、単発の比較を一般化しません。

**知识点3：** 平台日志更少也意味着粒度不同。若业务需要逐请求追踪，补齐后再评价总成本。

**日本語：** ログ量の減少と観測粒度は一緒に評価します。逐次ログを加えた構成の費用は別途測定します。

### 4. [アップデート] AWS Glue でシステム管理型の Iceberg マテリアライズドビューが利用可能になったので、通常のマテリアライズドビューと書き込みを比べてみた

**知识点1：** 比较写保护前先排除列数不符等无关失败，确保两个对象收到等价操作。

**日本語：** 書き込み拒否を比較するときは、列数など別の失敗原因を先に除きます。

**知识点2：** 只读开放与写入封闭可以共存；管理型不代表 REFRESH、属性变更或删除一律禁止。

**日本語：** 標準Icebergでの読み取りと書き込み保護は両立します。刷新や削除まで禁止されるわけではありません。

**知识点3：** SQL 等待时间、异步任务时间、完整作业费用和实际调度状态必须分别观察。

**日本語：** SQLの待ち時間、非同期タスクの時間と費用、実際のスケジュール状態を分けて確認します。

### 5. [アップデート] Kiro で管理者がサインイン方法を制限できるようになったので試してみた

**知识点1：** 规则的方法 ID 与 UI 名称、内部 URL ID 不同，应按照配置协议精确填写。

**日本語：** 設定に使う方法IDと画面ラベル・内部URLのIDを区別します。

**知识点2：** 隐藏按钮不构成完整认证控制，需检查浏览器结果返回后的客户端拒绝。

**日本語：** 選択肢を隠すだけでなく、ブラウザーから戻る認証結果をクライアントが拒否することを確認します。

**知识点3：** 端点策略有效性依赖分发和版本；Web 与未配置端点是明确的覆盖缺口。

**日本語：** 端末ポリシーの効果は配布と対応版に依存します。Webや未配布端末は別に扱います。

### 1. 一括り（ひとくくり）｜N1

- 词性：名詞
- 含义：笼统归为一类
- 搭配：一括りにする / 一括りに呼ぶ

- 例句译文：设置后确认运行直到最终结果。
- 语感区别：比“一眼看到”更强调跟踪到结束。

### 14. 惜しむ（おしむ）｜N2

- 词性：動詞
- 含义：吝惜；觉得可惜
- 搭配：努力を惜しまない / 別れを惜しむ
- 文章语境：原文“努力を惜しまない”形容成员不吝付出努力。

### 15. 助走（じょそう）｜N1

### 16. 載せる（のせる）｜N2

### 17. 入れ替える（いれかえる）｜N2

### 18. 判別（はんべつ）｜N1

- 语感区别：与已学“見分ける”接近，但为不同汉字词；注意不是仅用同义换名重讲技术概念。

## C-2. IT/AI 专业词汇

1. **CustomAttributes（カスタム属性）**：SageMaker 推理时原样传递的附加信息参数。 用于上下文传播时，需要长度检查与双方编解码约定。

2. **traceparent（トレースペアレント）**：W3C Trace Context 中携带追踪与父跨度身份的字段。 HTTP头能否进入目标容器须实测，不能从名字推断。

3. **queryKey（クエリキー）**：TanStack Query 用来识别查询数据的键。 归一化查询条件，避免同一结果拥有不同缓存身份。

4. **hydration（ハイドレーション）**：在浏览器把服务端输出与客户端运行状态连接的过程。 本文将服务端预取数据继承到初始查询缓存。

5. **SWR（ステイル・ホワイル・リバリデート）**：返回已有缓存并在后台重新验证的缓存方式。 LINE 增加的是服务端请求装饰器缓存，与每请求 QueryClient 分开。

6. **k6（ケーシックス）**：用脚本模拟负载并测量请求行为的工具。 本实验模拟资源获取，不把该时间当作浏览器LCP。

7. **Iceberg materialized view（アイスバーグのマテリアライズドビュー）**：以 Iceberg 保存已计算查询结果的物化视图。 Glue 管理型将数据与定义写入交给服务，刷新与读取仍是独立操作。

8. **managed-settings.json（マネージド設定ファイル）**：Kiro 安装客户端读取的端点策略配置文件。 本文测试 signin_method deny 规则，覆盖取决于分发和版本。
