### ① 企業資産の「36％」が“脆弱性ゾーン”で放置　AI攻撃時代に旧来の防御モデルは限界か： 「重要資産を重点的に守る」は通用しない？　最新調査が明かす限界

**来源：＠IT｜2026年9月7日 08:00**  
**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2609/07/news017.html

EY 的 2026 年全球调查覆盖 840 名经营层与 Security 负责人。调查指出，企业资产平均 **36%** 落在“Vulnerability Zone”——即资产存在或依赖关系的可视性不足，同时 Security Coverage 也不到位。分类中，OT / 物理资产为 57%、Third-party / Ecosystem 为 49%、AI System / Tool 为 47%、Network Infrastructure 为 38%。

这篇文章真正重要的地方在于防御模型的变化：AI Agent 能帮助攻击者自动搜索“被遗忘的 Asset、旧 ID、弱配置”，因此只保护 Crown Jewel 已经不足。EY 把 Cyber Resilience 从“Incident 后迅速恢复”扩展为“持续发现死角、理解依赖关系、及时更新控制”。其所谓 Secure Creator 组织的 Vulnerability Zone 平均约 30%，低于其他企业的约 42%。

**为什么值得看：★★★★★**

面试里可以把 Security 说得更完整：**Asset Inventory → Dependency Visibility → Identity / Third-party → Continuous Control → Resilience**。AI 不是只增加一个新攻击面，它也会提高攻击者发现旧攻击面的速度。

### ② Claude Fable 5.1 + EFS で企業 AI を安全に実装 — ZDR ロードマップ

**来源：Zenn｜2026年9月6日**  
**原文：** https://zenn.dev/kashiwabaray/articles/25d934bfd1a5c9

文章整理 Claude Fable 5.1 与 Enterprise Frontier Safeguards（EFS）的企业采用视角。Fable 5.1 面向复杂推理和 Agent Workload；文中基于 AWS / Anthropic 公布信息指出 Cache Read 单价从 $1.00/M 降到 $0.25/M，而 EFS 尝试把 Frontier Model 的能力与 Customer-owned Storage、Customer-managed Encryption、Safety Monitoring 等控制结合起来，使高性能模型与 ZDR / Data Governance 不必简单二选一。

**为什么值得看：★★★★★**

企业采用新模型时更成熟的顺序是：**Data / Compliance Gate → Capability → Quality → Latency / Cost**。同时要区分厂商 Benchmark、单次实验与 Production Workload 的证据等级。

### ③ 三菱UFJグループ会社、DBコストを87％削減――なぜ「Aurora Serverless」ではなく「Aurora DSQL」を選んだ？：同じサーバレスでも何が違った？

**来源：＠IT｜2026年9月7日 08:00**  
**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2609/07/news026.html

MUFG 集团的 Japan Digital Design（JDD）在新建文档搜索系统时采用 Amazon Aurora DSQL。其负载很有代表性：夜间集中处理 PDF / Web 数据，约 **1800 个 ECS Task 并行**，一个晚上可处理超过 **10 万个 File / Record**；白天则主要是 Web App 的 Read。Production、Staging、Development 又同时存在，因此 Idle 环境的固定成本成为关键因素。

在与 Aurora Serverless 的特定配置比较中，如果为了避免 Cold Start 将最小 ACU 设为 0.5，多个环境会持续产生固定成本；Aurora DSQL 长时间不使用时可缩到接近零资源，重新连接时自动恢复。JDD 报告数据库成本约降低 **87%**，运维负担接近零；其后 Data 量扩大约 10 倍时，也没有做 DB 参数调整和性能调优。团队还明确确认了 Workload 不依赖同一 Record 的高频并发更新，也不是以分析聚合为主要目的。

**为什么值得看：★★★★★**

这是日本企业非常好的 Cloud Cost 面试案例：**Serverless 不是统一答案，Pricing Model 必须和负载形状匹配。** 选型要一起考虑 Idle Cost、Burst Concurrency、Data Model、团队 SQL 经验、未来 Scale 和运维工数。

### ④ Prometheusとの関係から整理、なぜGrafanaは「OpenTelemetry」を推進する？：オープンへ向かうオブザーバビリティー（1/2 ページ）

**来源：＠IT｜2026年9月7日 05:00**  
**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2609/07/news010.html

文章从 Grafana 与 Prometheus 的历史关系解释 OpenTelemetry 的意义。Grafana 最初主要负责 Visualization；随后 Grafana Labs 在 Metrics、Logs、Traces 分别发展出 Mimir、Loki、Tempo。与此同时，它并没有把 Prometheus 兼容性变成封闭的自家格式，而继续强调开放生态与迁移能力。

OpenTelemetry 的关键价值不是“又一个 Observability Tool”，而是让 Telemetry 的生成、收集、传输尽量不被特定 Vendor 固化。当企业开始同时使用 Cloud、Agent、Serverless、Kubernetes 与多个 Monitoring Backend 时，这种开放接口能降低迁移和组合成本。

**为什么值得看：★★★★★**

SRE 面试里很适合回答：为什么要 OpenTelemetry？不是因为 Grafana / Prometheus 不够用，而是因为 **Telemetry 是长期资产，采集层和存储 / 分析层应该尽量解耦。**

### ⑤ JavaScriptをC言語にコンパイルする「porffor」がアルファ版に到達。ネイティブやWASMを生成可能

**来源：Publickey｜2026年9月7日**  
**原文：** https://www.publickey1.jp/blog/26/javascriptcporfforwasm.html

Porffor 进入 Alpha。它尝试把 JavaScript / TypeScript **事前编译（AOT）**为中间表示，再转换成 C，最终生成 Native Binary 或 WebAssembly，从而减少传统 JavaScript Runtime 与大量库的运行时依赖。官方称生成 Binary 相比把 Node.js 等 Runtime 一起打包的方式，体积可缩小到最多约 **1/50**；还给出 1GB Memory 下 Node.js 可运行约 28 个 App、Porffor 可运行 1000+ 的说明。

这些数字属于项目官方给出的目标 / 测量，不能直接替代自己的 Workload Test；而作者也明确提醒 Alpha 阶段“很可能还不能直接跑你的 App”，Node Compatibility 仍是主要瓶颈。近期项目还展示了低于 1ms 的 Cold Start 和 Closure 性能 / 内存优化，但现阶段更适合作为 **Runtime Architecture 趋势**观察，而不是生产直接替换 Node.js。

**为什么值得看：★★★★☆**

Frontend / Node.js 工程师可以把它看成一个新的 Trade-off：**Runtime Compatibility ↔ Binary Size / Cold Start / Density**。如果 Serverless、Edge、CLI、Agent Tool 对启动时间和内存密度敏感，AOT JavaScript 值得关注。

### 🤖 AI / Agent

今天 AI 方向的核心不是新 Agent Feature，而是 **Enterprise Eligibility**。Top 1 提醒 AI Attack 会自动寻找旧 Asset；Top 2 则提醒 Frontier Model 即使性能更高，也可能因为 Data Retention Policy 不符合而被 Runtime 直接判为 unavailable。生产系统应把 Model Access 当成 Policy Decision，而不是“API Key 有效就能调用”。

Qiita 9 月 6 日还有一篇横向比较 14 种 AI Agent 的长文，从 UI / 部署形式、Rollback、Data Sovereignty、Autonomy、Cost 等角度对 Claude Code、Codex、Cursor、Devin、Manus 等进行对照。社区整理不应替代各产品的官方条款，但它提出的判断框架很实用：**不要只比较 Model IQ，要比较 Side Effect、Rollback、权限、费用和使用人群。**

### 💻 Frontend / Web

过去一天没有新的 React / Next.js 专文值得超过近期已重点跟踪的 Security / Runtime 更新，因此不拿旧文补位。

今天 Frontend 最值得看的反而是 Porffor。它挑战了“JavaScript 必须带着完整 JavaScript Runtime 执行”的常见假设。对于 Next.js / Node Backend、CLI、Serverless Function 等环境，未来可能出现更多 AOT / Native / WASM 方向；但 Alpha 阶段首先应该验证 Node API Compatibility、Native Addon、Dynamic Behavior、Debugging 和 Build Pipeline，而不是只看 Cold Start 数字。

### ☁️ Cloud / Backend

今天 Cloud / Backend 的两条主线非常明确：**Workload-aware Database** 与 **Vendor-neutral Telemetry**。

JDD 的 Aurora DSQL 案例说明，Database Cost 与“是否 Serverless”关系不够直接，更关键的是 Burst / Idle 比例、并发模式、环境数量与数据增长。OpenTelemetry 则解决另一类长期问题：即使 Backend 或 Monitoring Vendor 改变，也尽量保留统一的 Telemetry Instrumentation。

### 🏢 日本企业 Tech Blog

严格时间窗口内，CyberAgent、LINEヤフー、Mercari、SmartHR、LayerX、DeNA、Money Forward 等指定企业 Tech Blog 没有发现比今天 Top 5 更值得置顶的新技术稿，因此没有使用旧稿补位。

今天日本企业实践最值得记的是 JDD：**技术选型不是“最新服务优先”，而是把真实负载、团队能力和长期运营成本写成显式 Requirement，再比较候选。** 这套方法同样适用于 RAG Vector DB、AI Gateway、Model Provider 与 Observability Stack。

## 3. 面接で使えるポイント

### 话题 1：AI 攻击时代，为什么 Asset Inventory 更重要？

**面试问题：**

> AIを使う攻撃者が増えると、Asset Managementはどのように変わると思いますか。

**约 30 秒回答：**

> 重要Assetだけを重点的に守る方法では不十分になると思います。AI Agentは古いIDや未管理のSaaS、Third-party Connectionなど、人が見落としやすい弱点を大量に探索できます。そのためAssetと依存関係を継続的に可視化し、Owner、Identity、Security Coverageを確認して、死角を減らすことが重要だと考えています。

**可关联项目：** Cloud Security、Enterprise Agent、IAM、Asset Inventory  
**关键词：** `資産可視化` / `死角` / `継続的統制`

### 话题 2：Enterprise LLM 选型为什么先看 Data Retention？

**面试问题：**

> 高性能な新しいLLMが出た場合、まずBenchmarkを比較しますか。

**约 30 秒回答：**

> まずData Retention、Data Processor、Region、社内Complianceを確認します。これらの条件を満たさないModelは、性能が高くても本番候補にできません。その上でQuality、Latency、Cache、Costを自社Workloadで複数回測定します。Vendor Benchmarkと一回の実測を分けて扱うことが重要だと思います。

**可关联项目：** Bedrock、Enterprise RAG、AI Gateway、Model Router  
**关键词：** `データ保持` / `適格性` / `実Workload評価`

### 话题 3：Serverless Database 怎样选？

**面试问题：**

> Serverless Databaseを選ぶとき、どの指標を比較しますか。

**约 30 秒回答：**

> Peak性能だけでなく、Idle時間のCost、Burst Concurrency、Cold Start、Transaction Pattern、複数Environmentの固定費を確認します。例えば夜間だけ大量Writeがあり、日中はRead中心なら、常時Capacityを確保する方式より利用量に追従するPricingが有利な場合があります。TeamのSQL Skillと将来Scaleも含めて判断します。

**可关联项目：** AWS、Document Search、RAG Backend、Batch Processing  
**关键词：** `負荷特性` / `アイドルコスト` / `拡張性`

### 话题 4：为什么 Observability 要 OpenTelemetry？

**面试问题：**

> PrometheusやVendor製Monitoring Toolがあるのに、なぜOpenTelemetryが必要ですか。

**约 30 秒回答：**

> Monitoring BackendとTelemetry生成を分離するためだと考えています。Application側がVendor固有SDKへ強く依存すると、Backend変更時の移行Costが高くなります。OpenTelemetryでMetrics、Logs、Tracesの収集方式を標準化すると、複数Backendを組み合わせたり将来切り替えたりしやすくなります。

**可关联项目：** SRE、Microservices、AWS、Agent Observability  
**关键词：** `可観測性` / `標準化` / `ベンダーロックイン`

### 话题 5：AOT JavaScript 有什么价值和风险？

**面试问题：**

> JavaScriptをAOT CompileしてNativeやWASMにするメリットと注意点は何ですか。

**约 30 秒回答：**

> Runtimeを一緒に配布しない構成では、Binary Size、Cold Start、Memory Densityを改善できる可能性があります。一方でNode.js APIやDynamicなJavaScript機能とのCompatibilityが課題になります。Alpha段階のToolはBenchmarkだけで判断せず、実ApplicationのDependency、Debugging、Build Pipelineまで検証する必要があります。

**可关联项目：** Node.js、Serverless、Edge、CLI、Frontend Tooling  
**关键词：** `事前コンパイル` / `互換性` / `コールドスタート`

## 4. 今日の技術テーマ

### Workload Contract First —— 产品名之前，先写清“这个系统实际怎么运行”

今天 Top 5 表面上分别是 Security、LLM、Database、Observability、JavaScript Runtime，但它们都在提醒同一件事：**不要用产品标签代替 Requirement。**

可以把技术选型抽象成：

```text
Workload / Risk Contract
  ├─ Data / Identity / Compliance
  ├─ Traffic / Concurrency / Idle Pattern
  ├─ Latency / Cost / Scale
  ├─ Compatibility / Portability
  └─ Failure / Recovery / Observability
            ↓
     Candidate Technology
            ↓
        Real Validation
```

Top 1 中，“重要 Asset”这个标签并不能替代完整 Asset Visibility；攻击者会从你认为“不重要”的旧 ID 或 Third-party 进入。Top 2 中，“Frontier Model”也不能替代 Data Retention Requirement。Top 3 中，“Serverless DB”不是统一的成本模型，Aurora Serverless 与 Aurora DSQL 在 Idle / Scale 行为上不同。Top 4 中，“Observability Tool”不是数据标准，OpenTelemetry 的价值恰恰在于把 Telemetry 与 Backend 解耦。Top 5 中，“JavaScript”也不必天然等同于传统 Runtime，但 AOT 的收益必须和 Compatibility 一起验证。

**优点：** 更容易解释技术选择；可把 Cost / Security / Reliability 量化；新产品出现时不必推翻整个判断框架；适合 Model Router、Database Selection、Cloud Architecture Review。

**局限：** Requirement 写错一样会选错；真实 Workload 会变化；一些指标互相冲突，例如最低 Cost 与最高 Availability；社区 / Vendor Benchmark 不能代替 Production 数据。

**日本企业落地注意点：** 建议在 PoC 前就把 “Must / Should / Nice-to-have” 写清楚，并记录数据保留、权限、峰值并发、Idle 比例、恢复目标、成本预算和 Skill / Operation Ownership。选型后保留 ADR 与实测数据，3～6 个月后重新检查 Workload 是否变化。

面试可直接总结：

> **技術選定では製品カテゴリやBenchmarkを先に見るのではなく、Data、Security、Concurrency、Cost、Compatibilityを含むWorkload Contractを定義し、その条件に候補Serviceが適合するかを実測で確認することが重要だと考えています。**

# B. 重点总结和面试可用的知识点｜重要ポイントと面接で使える知識

## 1. 企業資産の「36％」が“脆弱性ゾーン”で放置　AI攻撃時代に旧来の防御モデルは限界か： 「重要資産を重点的に守る」は通用しない？　最新調査が明かす限界

### 中文知识点总结

1. **Asset Security 的核心正在从“重点保护”转向“全局可视化”。** 平均 36% Asset 处于 Visibility / Security Coverage 不足区域。
2. **AI 攻击提高的是弱点发现速度。** 被遗忘 Asset、旧 ID、Third-party Dependency 更容易被自动搜索并组合利用。
3. **Cyber Resilience 需要持续治理。** 不只是 Incident 后恢复，还要持续 Inventory、Dependency Mapping 和 Control Update。
4. **AI System 本身也是 Vulnerability Zone。** 调查中 AI System / Tool 落入该区域的比例约 47%。

### 日本語の知識ポイント

1. **AI時代のAsset Securityでは、重要Assetだけを守るのではなく、組織全体のAssetと依存関係を継続的に可視化する必要があります。**
2. **AIを使う攻撃者は、古いIDや未管理Assetを高速に探索できるため、見落としそのものがRiskになります。**
3. **Cyber Resilienceは復旧力だけでなく、継続的なInventory・Risk把握・Control改善を含む概念へ広がっています。**
4. **AI System / ToolもSecurity部門の管理対象として明示的にInventoryへ含める必要があります。**

## 2. Claude Fable 5.1 + EFS で企業 AI を安全に実装 — ZDR ロードマップ

### 中文知识点总结

1. **Model Performance 与 Enterprise Eligibility 是两件事。** Data Retention Policy 不满足时，即使账号有权限也可能无法调用。
2. **ZDR 不应只看 Provider 宣传。** 要确认 Storage Location、Retention Mode、Encryption、Human Review 与当前 Rollout 状态。
3. **单次 Benchmark 不能直接一般化。** 作者自己把 22.6% Latency 差明确限定为一次观测。
4. **Cost Optimization 要包含 Cache。** Cache Read 价格变化会影响长 Context / Agent Workload 的真实经济性。

### 日本語の知識ポイント

1. **Modelの性能とEnterpriseで利用可能かどうかは分けて判断し、Data RetentionやPolicy Eligibilityを先に確認する必要があります。**
2. **ZDRを評価するときは、保存先、暗号化、Review主体、Retention Mode、提供時期まで確認することが重要です。**
3. **一回のLatencyやToken差をModel固有の性能として一般化せず、複数回の実Workloadで検証します。**
4. **長いContextやAgent WorkloadではPrompt Cacheの単価とHit率もCost設計の一部になります。**

## 3. 三菱UFJグループ会社、DBコストを87％削減――なぜ「Aurora Serverless」ではなく「Aurora DSQL」を選んだ？：同じサーバレスでも何が違った？

### 中文知识点总结

1. **Database Selection 应按负载形状而不是产品类别。** 夜间高 Burst、白天 Read、多个环境带来独特 Cost Profile。
2. **87% 是特定比较条件下的结果。** 对比的是 Aurora Serverless 为避免 Cold Start 而把最低 ACU 设为 0.5 的场景。
3. **NoSQL 并非成本低就一定更合适。** 团队 SQL 经验、业务数据复杂度和 Query 灵活性也是设计条件。
4. **Scalability 也包括“无需持续调优”。** Data 约 10 倍扩大后没有重新调 DB 参数，是运维价值的一部分。

### 日本語の知識ポイント

1. **Databaseは“Serverlessかどうか”ではなく、Burst、Idle、Read/Write比率、Environment数などWorkload特性から選ぶ必要があります。**
2. **87%削減という数字は比較条件を明示して理解し、他Systemへそのまま一般化しないことが重要です。**
3. **DynamoDBよりSQLを選んだ理由には、Data構造の複雑性とTeamの既存Skillも含まれています。**
4. **Scale時に再設計やTuningが不要であることも、長期的な運用Cost削減につながります。**

## 4. Prometheusとの関係から整理、なぜGrafanaは「OpenTelemetry」を推進する？：オープンへ向かうオブザーバビリティー（1/2 ページ）

### 中文知识点总结

1. **Observability 的 Data Interface 应与 Backend 分离。** Telemetry 是长期资产，Vendor Tool 是可替换实现。
2. **Prometheus 与 OpenTelemetry 不是简单替代关系。** 前者在 Metrics 生态很强，后者覆盖更广的 Telemetry 标准化。
3. **Grafana 的价值从 Visualization 扩大到了 Mimir / Loki / Tempo，但仍强调开放兼容。**
4. **AI / Agent 时代更需要统一 Trace。** 多 Tool、Model、Cloud 组合后，Open Telemetry Format 更利于跨系统排障。

### 日本語の知識ポイント

1. **ObservabilityではTelemetry生成とBackendを分離し、Dataを特定Vendor形式へ閉じ込めない設計が重要です。**
2. **PrometheusとOpenTelemetryは単純な置き換えではなく、既存Metrics資産とOpenなTelemetry標準を組み合わせて考えます。**
3. **Grafana LabsはMimir、Loki、Tempoへ領域を広げながら、Openな互換性を重視しています。**
4. **AgentやMicroserviceが増えるほど、Metrics・Logs・Tracesを横断できる共通TelemetryがTroubleshootingに有効です。**

## 5. JavaScriptをC言語にコンパイルする「porffor」がアルファ版に到達。ネイティブやWASMを生成可能

### 中文知识点总结

1. **JavaScript Runtime 也可以走 AOT 路线。** Porffor 试图把 JS / TS 转换成 C，再生成 Native / WASM。
2. **Performance Claim 要看边界。** 官方给出体积、Cold Start 和 Memory Density 的亮眼数字，但项目仍处 Alpha。
3. **Node Compatibility 是主要瓶颈。** 真实 App 的 Dependency / Dynamic Feature 支持比 Microbenchmark 更重要。
4. **适用场景可能首先出现在 Serverless / CLI / Edge。** 这些环境更在意 Cold Start、Binary Size 和 Memory Density。

### 日本語の知識ポイント

1. **PorfforはJavaScript / TypeScriptをAOTし、Cを経由してNative BinaryやWASMへ変換するRuntime Approachです。**
2. **公式BenchmarkのBinary SizeやCold Startだけでなく、Alpha段階であることとCompatibility制約を同時に見る必要があります。**
3. **Node.js APIや実Application Dependencyが動くかどうかがProduction採用の大きな判断材料になります。**
4. **Cold StartとMemory Densityが重要なServerless、CLI、Edgeでは将来的な選択肢になり得ます。**

## C-2. IT/AI专业词汇

### 1. Vulnerability Zone｜脆弱性ゾーン

**中文：** 不只事故后恢复，也包括持续发现 Risk 并更新控制的能力。

### 5. Amazon Aurora DSQL
**中文：** AWS 的完全 Serverless 分布式 SQL Database。  
**当天语境：** JDD 在文档搜索系统中根据间歇高峰、多个环境和未来扩展选择 DSQL。

**中文：** 用统一开放方式生成、收集、传输 Metrics / Logs / Traces 的标准生态。

### 8. AOT Compilation｜事前コンパイル
**中文：** 运行前把 Source Code 编译到更接近机器执行形式。  
**当天语境：** Porffor 将 JS / TS 转到 C，再生成 Native / WASM。

**level：N1｜中文：** 可能会导致……、恐怕会……  
**接续：** `動詞ます形去ます + かねない`  
**用途：** Security / Cost 风险警示。  
**例句：** `忘れられたAssetを放置すると、AIを使う攻撃者の侵入口になりかねません。`  
**中文：** 放置遗忘 Asset 可能成为使用 AI 的攻击者入口。  
**注意：** 比简单“可能”更有警示意味。

### 3. ～に至るまで
**level：N1｜中文：** 从……一直到……、甚至包括……  
**接续：** `名詞 + に至るまで`  
**用途：** 强调需要覆盖的工程范围很广。  
**例句：** `ModelのData RetentionからDatabase Cost、Telemetry形式に至るまで、Workloadごとの条件を確認します。`  
**中文：** 从 Model Data Retention 到 DB Cost、Telemetry 格式都要确认。  
**注意：** 对应当天 Top 5 多层工程约束。

### 4. ～に応じて
**level：N2｜中文：** 根据……相应调整  
**接续：** `名詞 + に応じて / 名詞 + に応じた + 名詞`  
**用途：** 描述 Capacity / Policy 随负载变化。  
**例句：** `Applicationの負荷に応じてDatabaseの処理能力が自動的に調整されます。`  
**中文：** 数据库 Capacity 根据 Application 负载自动调整。  
**注意：** 对应 Serverless Scaling。

### 5. ～一方で
**level：N2｜中文：** 另一方面……  
**接续：** `普通形 + 一方で`  
**用途：** 表达 Architecture Trade-off。  
**例句：** `OpenTelemetryはVendor Lock-inを減らせる一方で、CollectorやSchemaの運用設計は必要です。`  
**中文：** OpenTelemetry 能降低 Vendor Lock-in，但仍需设计 Collector / Schema 运维。  
**注意：** 面试中讲优缺点很自然。

### 6. ～たうえで
**level：N2｜中文：** 在……之后、在……基础上  
**接续：** `動詞た形 + 上で / 名詞 + の上で`  
**用途：** 表示验证是选型前提。  
**例句：** `同時更新のPatternを確認したうえで、Aurora DSQLがWorkloadに適合するか判断します。`  
**中文：** 确认并发更新 Pattern 后再判断 DSQL 是否适合。  
**注意：** 对应 Top 3 的选型过程。

### 7. ～に伴って
**level：N2｜中文：** 随着……、伴随……  
**接续：** `名詞 + に伴って / 動詞辞書形 + のに伴って`  
**用途：** 描述 AI 规模扩大带来的治理需求同步增加。  
**例句：** `AI活用の拡大に伴って、Asset VisibilityとTelemetryの標準化も重要になります。`  
**中文：** 随着 AI 应用扩大，Asset Visibility 与 Telemetry 标准化也更重要。  
**注意：** 比「～につれて」更正式。
