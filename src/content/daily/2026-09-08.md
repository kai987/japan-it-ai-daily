# A. 详细文字版

今天优先筛选 2026 年 9 月 7 日上午至 9 月 8 日上午的新内容，并避开 9 月 7 日已经重点汇总的 Asset Visibility、Claude Fable 5.1 + EFS、Aurora DSQL、OpenTelemetry 与 Porffor。今天的共同主线是：**企业 AI 的下一阶段不是继续堆 Model，而是把 Identity、Supply Chain、Memory、Design Handoff 与 Data/KPI 变成可验证、可追踪的控制面。**

## 1. 今日最值得看的5篇

### ① 「AIの制限」でも「野放し」でも失敗する？　AI時代に“共有APIキー”は限界：「誰が使ったか分からない請求」におびえる現場からの脱却

**来源：＠IT｜2026年9月8日 08:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/08/news034.html

Cloudflare 的 **Identity-Aware AI Gateway** 直指企业 AI 使用进入规模化之后的两个治理盲区：费用突然上涨，以及敏感信息通过外部模型流出。传统共享 API Key 能告诉平台“这个 Key 花了多少钱”，却很难回答“实际是谁发起了 Request、哪个团队产生了异常、什么数据被送出去”。Cloudflare 将 AI Gateway 与 Zero Trust 产品 **Cloudflare Access** 结合，把经过身份提供商验证的用户或自动化系统身份绑定到每个 AI Request；官方说明 Request Metadata 中会加入 `cf.user_id`，因此 Log、Analytics 和 Spend 可以按真实主体过滤。`User Insights` 再利用已经过 Gateway 的 Traffic 建立每个用户 / Agent 的行为 Baseline，用于识别异常使用模式。

这套设计也把 FinOps 和 Security 放到同一个 Control Plane：身份明确后可以设置 per-user Spend Limit，达到上限时 Block 或切换到更便宜的 Model；Gateway 还可以配合 Cache、Rate Limit 与内容过滤减少重复费用和敏感数据外发。Cloudflare 官方建议先从 Monitoring Mode 学习 Baseline，再执行 Policy。**限制与证据边界：** ＠IT 本文主要基于 Cloudflare 的产品发布；Identity-Aware AI Gateway 当前是 Open Beta，而 User Insights 已 GA。行为异常检测的价值成立，并不意味着企业无需自己定义 Data Classification、预算阈值和 Model Allowlist。

**为什么值得看：★★★★★**  
把 AI Gateway 从“统一 API Endpoint”推进到“身份、预算、异常行为和数据治理的共同控制面”，很适合 Enterprise AI / Platform / Security 面试。

### ② AIが「クズコード」まで学習　“脆弱性の生まれ方”が変わったAIコーディング時代の「守り」の作法と始め方：レビュー時、どこを重点的に見るべきか（1/2 ページ）

**来源：＠IT｜2026年9月8日 05:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/08/news006.html

文章把 AI Coding 的风险分成了传统 Code Review 不容易覆盖的几类。第一类是 **slopsquatting**：模型幻觉出一个并不存在的 Package Name，攻击者提前在 Registry 注册同名恶意包；文中引用的 `huggingface-cli` 验证包在 3 个月里出现 1.5 万次以上下载。第二类是训练数据中的 Legacy Pattern 被重新生成。文中回顾 2021 年 NYU 对 GitHub Copilot 的研究：89 个 Scenario、1689 个程序中约 40% 含有漏洞；例如 MD5 密码 Hash 虽能通过功能 Test，却已经不符合现代安全要求。第三类是 Agent 会读取 README、Source Comment、Web、Issue、MCP 等外部内容，因此 Prompt Injection 直接变成 Execution Risk，文中列出 `CVE-2025-53773` 作为典型案例。

防守方式也不能停在“提醒 Developer 小心”。文章建议把 Package 是否真实存在、下载 / 维护历史、Known Vulnerability 等检查放进 CI 或 Proxy Repository；同时用 SAST / SCA 做机械检查，把 Prompt、Skill、Rule File 和 MCP Server 也当作版本化的 Software Supply Chain Asset。**限制与证据边界：** 2021 年 Copilot 的约 40% 是旧模型时代的研究结果，不能直接当作 2026 年 Coding Model 的当前漏洞率；真正可复用的是 Review 维度和团队化 Control。AI Coding 并非应该停止，而是安全基线必须从“只看生成代码”扩展到 Dependency、Context 与 Agent Extension。

**为什么值得看：★★★★★**  
把 AI Coding 的风险拆成 slopsquatting、旧弱实现再生产、Prompt Injection 与扩展生态攻击，并给出团队级 CI / SAST / SCA 治理方式。

### ③ AI エージェントの Memory を、訂正・検査・削除から考えてみた

**来源：DevelopersIO｜2026年9月7日**  
**原文 URL：** https://dev.classmethod.jp/articles/nemohermes-memory-lifecycle/

这篇最有价值的地方，是明确把 Long-term Memory 从“能不能记住更多”改成 **Memory Lifecycle** 问题。作者以 NVIDIA Memory-Driven Chief of Staff / `self model` 的思路为背景，区分原文证据、派生知识、业务判断 / 状态和执行权限；Memory 只是 Decision Material，真正的 Action Permission 仍由执行层控制。NVIDIA 原文使用 Nemotron 3 Ultra 做 186 问 Evaluation，报告 agentic RAG 82.8%、self model 90.9%，但也有单一信息检索下降的项目；作者明确强调这些不是自己的实测，也不意味着 Memory 越多越好。

作者自己的实验在隔离的 Synthetic Data 上进行，环境是 Python 3.13.12 与 SQLite 3.50.4。业务知识保存在 Markdown Memory，优先级和订正等状态写入 **SQLite Ledger**；重复发送相同 Human Correction 后得到 `changed: false`，说明保存层能保持 Idempotency。`memory_check.py` 能检测 `unindexed`、`broken-link`、`missing-field`、`unsourced`、`stale`、`bad-date` 六类结构异常，但在“结构不变、只把案件名改错”的情况下不会报警，因此 Structural Check ≠ Semantic Correctness。Retention 测试中以 7 天作为**测试条件而非推荐值**，8 条旧正文被删除、1 条新正文保留；而且这里只确认正文 Field 被清除，不代表 Storage Physical Deletion，Metadata、Audit Event、Derived Memory 仍可能保留。

**为什么值得看：★★★★★**  
不把长期 Memory 简化成“记得更多”，而是用订正、结构检查、Retention、Provenance 和删除边界来讨论可运营的 Memory Lifecycle。

### ④ Figma Make で作ったデザインを引き継いで Claude Code で開発する方法

**来源：Zenn｜2026年9月7日**  
**原文 URL：** https://zenn.dev/chooser/articles/series-007-product-story

文章给出了一个很贴近 AI×Frontend 的 Handoff 问题：Figma Make 可以很快生成“看起来完成”的 React / TypeScript UI，但后续 Claude Code 是否能稳定接手，取决于产物是否被整理成可读、可追踪、可继续维护的 Engineering Artifact。作者的流程是 **Figma Make → GitHub → Claude Code**，并不是把生成 Code 直接合并进主仓库；在一个 SEO 工具里，`design/prototype/` 保留 Figma Make Snapshot，`apps/seo-admin/` 再进行正式开发。作者要求 Figma Make 按 `atomic design` 组织 Component、从 Design 本身抽出 **Design Token**、保存原 Prompt 与 Guideline，并在 README 中增加 `Quick Summary for Claude Code` 和 **Ask Human**，把 Persistence、Authentication、Backend 等未决事项明确交还给人判断。

文章还强调“交接后的第一件事不是加功能，而是 DRY 化”：先合并重复 Component、把 Token 真正接到 UI、拆分巨大页面、恢复 Build / CI 的工程连接。作者用 Commit History 和 Config 文件回顾多个项目，其中一个 SEO 工具演进到约 180 个 Commit；另一方面，有的 App 虽然画面和导航完成，却停在 Auth / Persistence / Notification 尚未决定的阶段。**证据边界：** 这些是作者多个自研项目的 Case Study，不是独立 Benchmark；并且“atomic design 文件夹存在”不等于内部 Wiring 已正确。真正值得学习的是 Handoff Contract、Provenance 与“视觉完成 ≠ 产品完成”的边界。

**为什么值得看：★★★★★**  
从 Figma Make → GitHub → Claude Code 的真实多项目经验说明，AI 生成 UI 真正能交接需要 atomic design、Design Token、Snapshot、Ask Human 与 DRY 化。

### ⑤ 富士通の営業、個人の「勘や経験」を組織で再利用　データ、KPI、仕事を「AI前提」に変えた方法（1/2 ページ）

**来源：ITmedia ビジネスオンライン｜2026年9月8日 06:00**  
**原文 URL：** https://www.itmedia.co.jp/business/articles/2609/08/news027.html

富士通的案例把“AI 为先”的组织改造倒过来：不是先问 AI 能做什么，而是先决定 **工作要怎样改变**。古濱淑子氏负责的销售部门约 **5000 人**，连同关联部门约 **7300 人**。过去跨部门请求来自不同入口，谁在请求什么、哪里重复、哪里滞留并不清楚；团队先用 **Asana** 把请求一元化，让 Workflow 本身产生可分析 Data。“有事就放进 System”成为共同 Rule 后，重复任务与 Bottleneck 才有了可见性。

但“Data 已经收集”仍不等于“Data 可以给 AI”。文章特别指出 Priority 的定义如果因人而异，接收方就无法稳定解释，必须统一 Data 的粒度、格式与 Master。销售领域原本存在大量个人的“勘・経験・暗黙知”，富士通再利用 AI 整理客户对话和电话销售的**会话 Log**，沉淀行业销售 Know-how，并据此培养 Sales AI Agent。**证据边界：** 本文基于 8 月 26 日 Asana Japan Conference 的企业演讲，是组织实践报道，不是随机实验或因果研究；约5000人 / 約7300人、Asana 集约与会话 Log 属于公开案例事实，但“这样做一定能提高销售 KPI”仍需企业自己的 KPI Measurement 验证。

**为什么值得看：★★★★★**  
用约5000人的销售组织、约7300人的关联组织与 Asana 统一入口说明：AI 成果首先依赖工作可视化、数据定义、KPI 与知识循环，而不是先部署 Agent。

## 2. 分类速览

### 🤖 AI / Agent

Top 1、Top 3、Top 5 可以连成一条 Production AI 路线：请求进入系统时先绑定真实 Identity；Agent 的长期 Memory 要可订正、可检查、可过期；组织侧则要先把 Workflow 和 Data Definition 做成可复用资产。也就是说，Agent 的“聪明”只有在 Request、State 与 Organization Knowledge 都有 Owner 和 Provenance 时才容易进入生产。

### 💻 Frontend

今天 Frontend 最值得看的是 Top 4。Figma Make 可以快速给出 React / TypeScript 的视觉原型，但真正交给 Claude Code 后，第一优先级是 Component DRY、Design Token Wiring、Build/CI 与未决的 Authentication / Persistence，而不是继续堆页面。对于 Next.js / React 面试，这比只展示“AI 生成了 UI”更能体现 Product Engineering 能力。

### ☁️ Cloud-Backend

Top 1 的 Identity-Aware AI Gateway 展示了 Gateway 如何承担 AI Traffic 的身份、Spend、Behavior Baseline 与 Policy 入口；Top 3 则展示 Memory Storage 与 Lifecycle。二者共同说明 Cloud AI Platform 不只是 API Routing，还要管理谁在调用、状态保存在哪里、多久保留、怎样删除和怎样审计。

### 🏢 日本企业 Tech Blog

严格时间窗口内，指定的大型企业 Tech Blog 没有出现比今天 Top 5 更强的新稿；但 Top 5 的富士通企业实践非常值得与 Top 1 对照：前者解决“组织怎样生产可信 Data”，后者解决“AI Request 怎样绑定可信 Identity”。企业 AI 的价值与治理分别从 Work Plane 和 Control Plane 衔接起来。

### 话题 1：AI Gateway 为什么必须绑定身份而不是共享 API Key？

**面试问题：**

> 共有APIキーでAI Gatewayを運用する場合、どこに問題があると思いますか。

**约30秒回答：**

> 本番では共有APIキーのままAI Gatewayへ集約するだけでは不十分です。Identity-Aware AI GatewayでCloudflare Accessの確認済みIDを各Requestへひも付け、User Insightsで利用額の急増や通常パターンからの逸脱を追います。ただし全Trafficを一元化しても、Data分類やRate Limitの基準は自社Policyとして別に設計します。

**可关联项目：** Enterprise AI Gateway / Multi-model Platform / FinOps / Zero Trust  
**3个技术关键词：** `本人性確認` / `利用量統制` / `異常検知`

### 话题 2：AI 生成代码应该重点审查哪些新型风险？

**面试问题：**

> AI生成コードをSecurity Reviewするとき、通常のTest以外に何を確認しますか。

**约30秒回答：**

> AI生成Codeでは、Testが通るだけで安全とは判断しません。存在しないPackage名を先回り登録するslopsquattingや、CVE-2025-53773のようにREADMEやComment経由でAgentへPrompt Injectionする経路をReview対象にします。一方で2021年のCopilot調査は現行ModelのBenchmarkではないため、現在のCodeでSecurity Scanします。

**可关联项目：** Claude Code / GitHub Copilot / CI Security / DevSecOps  
**3个技术关键词：** `スロップスクワッティング` / `プロンプトインジェクション` / `依存関係検証`

**可关联项目：** Agent Memory / RAG / Personal Assistant / Enterprise Knowledge  
**3个技术关键词：** `訂正履歴` / `構造検査` / `保持期間`

## 4. 今日の技術テーマ

# Control Plane Before Intelligence

今天 5 篇文章表面上分别讨论 Gateway、AI Coding、Memory、Frontend Handoff 和企业销售，但它们实际上都在回答同一个问题：**哪些事实与边界不能交给概率模型临时决定？** 可以把企业 AI 系统拆成五层：`Identity Plane` 负责谁在调用；`Supply-chain Gate` 负责哪些 Code / Package / Context 值得信任；`Memory Lifecycle` 负责状态怎样被订正、检查和删除；`Artifact Contract` 负责 AI 生成物如何交给下一个 Agent / 人；`Data & KPI Plane` 负责组织知识是否具有统一定义。LLM 在这些边界内部做推理，而不是自己创建边界。

**机制：** Top 1 用 Cloudflare Access 把经过验证的 ID 写进 Gateway Request；Top 2 把 Package Verification、SAST/SCA 和 Prompt/Skill Versioning 变成 CI / Supply-chain Control；Top 3 把 Source、Derived Knowledge、Ledger State、Permission 分离；Top 4 通过 Snapshot、Design Token、Ask Human 保持 Handoff Provenance；Top 5 则先把跨部门 Request、Data 粒度、Master 和 KPI 标准化，再把 Conversation Log 交给 AI Agent。

**优点：** 第一，事故可追踪——能回答谁调用、用了什么 Context、基于什么 Source。第二，AI 输出更容易替换 Model，因为关键 Policy 不藏在 Prompt 里。第三，人类 Review 更聚焦：只需要处理 Ask Human、Semantic Check、High-risk Action 等真正需要判断的部分。第四，Cost 也更可治理，Identity 和 Work Unit 都可以成为归属单位。

**局限：** Control Plane 会增加 Engineering Complexity。Identity、Policy、Ledger、Evidence、Data Dictionary 都需要维护；而且结构检查通过不代表语义正确，统一 Data 定义也不代表 Agent 一定产生 Business Value。过强的 Control 还可能让 AI 使用变得煩雑并妨碍开发速度，因此需要按 Risk 分级，而不是“一律禁止”。

**日本企业落地注意点：** 建议先从一个 Workflow 建立 `Owner → Identity → Approved Tool / Package → Source / Memory → KPI → Audit` 的最小闭环，再扩展到全公司。尤其是日本企业中常见的个人 Excel、个人 Memo、共享 Account 与暗黙知，如果不先结构化，即使引入更强 Model，也只会把不可追踪状态放大。

面试可以这样总结：

> AIを本番導入する場合、Model Intelligenceだけを高めるのではなく、Identity、Supply Chain、Memory、Artifact、Data DefinitionをControl Planeとして分離し、LLMの確率的な判断が越えてはいけない境界をSystem側で管理することが重要だと考えています。

# B. 重点总结和面试可用的知识点｜重要ポイントと面接で使える知識

## 1. 「AIの制限」でも「野放し」でも失敗する？　AI時代に“共有APIキー”は限界

### 中文知识点总结

- 共享 API Key 的根本问题不是“Key 不安全”这么简单，而是 Cost、Log 与 Responsibility 无法落到真实主体。
- `Cloudflare Access → Identity-Aware AI Gateway → cf.user_id → User Insights` 形成从 Authentication 到 Behavior Baseline 的可追踪链。
- Identity 明确后才能做真正的 per-user Budget / Policy，但企业仍需自己定义 Data Classification 与 Rate Limit。

### 日本語の知識ポイント

- 共有APIキーではCostやRiskのOwnerを特定しにくく、Identity-awareなRequest Attributionが必要です。
- Cloudflare Accessの確認済みIdentityをAI Gatewayへ渡すことで、Log・Spend・User Insightsを利用主体単位で見られます。
- Identityを付けてもData分類やModel Policyが自動的に決まるわけではなく、組織Policyとして別に設計します。

## 2. AIが「クズコード」まで学習

### 中文知识点总结

- AI Coding Review 必须新增 Package Hallucination、Legacy Pattern 与外部 Context Injection 三个视角。
- slopsquatting 说明 Model Hallucination 会与公共 Package Registry 结合成为真实 Supply Chain Attack。
- SAST/SCA、Proxy Repository、Prompt/Skill Versioning 应从个人技巧升级成团队 Pipeline。

### 日本語の知識ポイント

- AI生成Codeでは、Package Hallucination、Legacy Pattern、外部ContextからのPrompt Injectionを分けて確認します。
- slopsquattingは、架空Package名の生成と公開Registryを組み合わせたSupply Chain Riskです。
- Package検証、SAST / SCA、Prompt・SkillのVersion管理をTeam Processへ組み込むことが重要です。

## 3. AI エージェントの Memory を、訂正・検査・削除から考えてみた

### 中文知识点总结

- Memory 不是 Permission；证据、派生知识、业务状态与执行权限应分层。
- `memory_check.py` 的 6 类检查只证明结构规则，没有证明内容与 Source 一致。
- Retention 也要区分“正文 Field 清除”“Derived Memory 保留”“Storage Physical Deletion”，不能把一个 Delete Command 当成完整删除证明。

### 日本語の知識ポイント

- Memoryは判断材料であり、外部ActionのPermissionとは分離して扱います。
- `memory_check.py`の6種類の検査はStructureを確認するもので、SourceとのSemantic Consistencyまでは保証しません。
- Retentionでは本文消去、Derived Memory、Audit Event、Physical Deletionを別のLifecycleとして定義する必要があります。

## 4. Figma Make で作ったデザインを引き継いで Claude Code で開発する方法

### 中文知识点总结

- AI 生成 UI 的可交接性来自 Artifact Contract，而不是“代码能跑”本身。
- `design/prototype/` Snapshot、atomic design、Design Token、Prompt / Guideline、Ask Human 让后续 Agent 能知道来源、规范和未决项。
- 视觉完成容易掩盖 Auth、Persistence、Notification 等产品基础未完成，因此交接后的首要任务是 DRY 与基础工程化。

### 日本語の知識ポイント

- Figma MakeのOutputを再利用可能な開発資産にするには、Snapshot、Design Token、Guideline、Ask Humanまで含むHandoffが必要です。
- `design/prototype/`を残すと、Designの出発点をMain Codeと分離して追跡できます。
- 見た目が完成してもAuthやPersistenceが未決ならProductは完成しておらず、Handoff直後はDRY化と基盤整理を優先します。

## 5. 富士通の営業、個人の「勘や経験」を組織で再利用

### 中文知识点总结

- Enterprise AI 的前置工程是 Workflow Visibility：Asana 先把跨部门请求变成可统计 Data。
- Data 可用性依赖粒度、格式、Master、Priority 等共同定义；“数据很多”与“AI 能可靠理解”不是同一件事。
- 销售会话 Log 与个人经验要进入组织知识循环，再由 AI Agent 使用，并用 KPI 验证是否真正改善业务。

### 日本語の知識ポイント

- AI Agent導入前に、Asanaのような共通SystemでWorkflowを可視化し、Dataを継続的に生み出せる状態を作ります。
- 粒度、Format、Master、Priorityの定義がそろって初めて、組織DataをAIが安定して利用できます。
- 会話Logや暗黙知を組織Knowledgeへ変え、KPIと共有Incentiveまで含むCycleを設計することが重要です。

### 4. Prompt Injection｜プロンプトインジェクション

### 6. Memory Ledger｜メモリ台帳

### 7. Design Handoff Contract｜デザイン引き継ぎ契約

## C-3. JLPT语法

今天共 **7 个语法**：N1 3 个、N2 4 个，全部对应当天 Top 5 的技术说明、风险、条件或 Evidence Boundary。

### 1. ～にとどまらず

**level：** N1  
**meaningZh：** 不止于……、不仅限于……  
**structure：** `名詞 + にとどまらず / 動詞辞書形 + にとどまらず`  
**usageZh：** 用于把讨论从单一功能扩展到更广的治理或风险范围。  
**exampleJa：** AI GatewayはTrafficの集約にとどまらず、Identityと予算管理にも使えます。  
**exampleZh：** AI Gateway 不止用于流量汇总，也可用于 Identity 与预算管理。  
**noteZh：** 对应 Top 1：企业需要的不只是统一 Endpoint，而是可追踪的治理层。

### 2. ～かねない

**level：** N1  
**meaningZh：** 有可能导致……、恐怕会……  
**structure：** `動詞ます形去ます + かねない`  
**usageZh：** 用于 Security、Supply Chain、Data Governance 等带警示语气的风险表达。  
**exampleJa：** 存在しないPackage名をそのまま採用すると、slopsquattingの被害につながりかねません。  
**exampleZh：** 如果原样采用不存在的 Package 名，可能导致 slopsquatting 攻击。  
**noteZh：** 对应 Top 2 的 Package Hallucination 风险。

### 3. ～に至るまで

**level：** N1  
**meaningZh：** 从……一直到……，甚至包括……  
**structure：** `名詞 + に至るまで`  
**usageZh：** 用于表示一个工程流程覆盖从上游到下游的广泛范围。  
**exampleJa：** Figma MakeのUI設計から認証・永続化に至るまで、未決事項を明示して引き継ぎます。  
**exampleZh：** 从 Figma Make 的 UI 设计直到认证、持久化，都明确未决事项后交接。  
**noteZh：** 对应 Top 4：视觉完成不等于产品开发已经完成。

### 4. ～一方で

**level：** N2  
**meaningZh：** 另一方面……、与此同时……  
**structure：** `普通形 + 一方で`  
**usageZh：** 用于技术面试中说明 Benefits 与 Risks 同时存在。  
**exampleJa：** Long-term Memoryは説明の手間を減らせる一方で、古い情報を残すRiskがあります。  
**exampleZh：** Long-term Memory 能减少重复说明，但也有保留旧信息的风险。  
**noteZh：** 对应 Top 3 的 Memory Utility 与 Staleness / Correction Trade-off。

### 5. ～たうえで

**level：** N2  
**meaningZh：** 在……之后；在……基础上再……  
**structure：** `動詞た形 + 上で / 名詞 + の上で`  
**usageZh：** 强调前一步分析或验证是后续采用、判断的必要依据。  
**exampleJa：** Dataの粒度とMasterをそろえたうえで、営業AI Agentへ利用させます。  
**exampleZh：** 统一数据粒度与 Master 后，再让 Sales AI Agent 使用。  
**noteZh：** 对应 Top 5：先整理工作与 Data，再做 Agent。

### 6. ～に応じて

**level：** N2  
**meaningZh：** 根据……相应调整  
**structure：** `名詞 + に応じて / 名詞 + に応じた + 名詞`  
**usageZh：** 用于 Permission、Retention、Risk 或业务条件变化时的动态策略。  
**exampleJa：** Memoryの種類に応じて、保持期間と訂正経路を分けます。  
**exampleZh：** 根据 Memory 类型区分保留期与订正路径。  
**noteZh：** 对应 Top 3：临时指令、派生知识、业务状态不应使用同一 Lifecycle。

### 7. ～とは限らない

**level：** N2  
**meaningZh：** 不一定……、不能断定……  
**structure：** `普通形 + とは限らない`  
**usageZh：** 用于限制过度一般化，特别适合 Evidence Boundary。  
**exampleJa：** 構造Checkに通ったMemoryが、Sourceと意味的に一致しているとは限りません。  
**exampleZh：** 通过结构检查的 Memory 不一定在语义上与 Source 一致。  
**noteZh：** 对应 Top 3 的实测限制：`memory_check.py` 检查结构，不保证语义正确。
