### ① AIとGrafana Foundation SDKで進めるGrafanaダッシュボードのIaC化

**来源：DeNA Engineering｜2026年9月14日**  
**原文 URL：** https://engineering.dena.com/blog/2026/09/grafana-dashboard-iac-with-ai-typescript/

DeNA面对的是一个很典型的AI工程化问题：Grafana Web UI适合快速试做Dashboard，但一旦希望AI持续参与PromQL、Panel和Dashboard生成，就必须把结果从“画面里的修改”变成可以Review、Validate、Reuse并跨环境一致发布的Artifact。团队因此采用 **Grafana Foundation SDK的TypeScript版**，让AI生成的Dashboard先成为TypeScript定义，再产出Git Sync所需JSON。基本路径是 `npm run build` → `npm run validate` / CI → PR Review → merge main → Git Sync。TypeScript类型检查可以提前发现不存在的Property或错误Value Type，CI还检查UID、空Panel、`gridPos`、Git Sync必需Field、旧Data Source UID、`editable`等生成物问题。

AI本身有两条工作流。其一是通过MCP读取Grafana的Data Source、Metric和既有Dashboard，再生成PromQL和SDK代码；其二是先在Web UI里完成Prototype、Export JSON，再让AI转换成Grafana SDK TypeScript。生产连接并不是把Grafana完全交给Agent：本地AI Editor先经过 `mcp-auth-proxy`，用GitHub做认证与授权，再转发到 `mcp-grafana`；Grafana侧使用按用途缩小权限的Service Account，常规调查保持 **read-only**。AI调查路径与发布路径被明确拆开，本番反映仍必须经过Build、Validation、PR和Git Sync。

**Evidence / Measurement：** 这是DeNA自己的Implementation Report，提供了Repository Layout、Command、Validation Rule、MCP Auth结构和Migration步骤，但**没有提供受控的开发效率Benchmark**。团队也明确说TypeScript并不是与Go严格比较后得出的“性能胜者”，而是因为对象/数组嵌套与现有JSON工作方式更自然。

**Evidence Boundary：但是，** 类型正确并不代表Dashboard语义正确。Type Check无法判断Metric是否真实存在、PromQL是否表达了想要的业务含义、Panel是否容易阅读，因此仍需实际Grafana显示确认。Git Sync正式支持以Grafana v13为前提，v12仍属experimental；复杂Layout的`gridPos`有时还要人工修正，新UID并行迁移时旧UID/Panel ID上的手工Annotation也不会自动继承。

**为什么值得看：★★★★★**  
这篇非常适合AI/Web/SRE面试。重点不是“AI会写Grafana”，而是：**让AI拥有Production Data的读取能力，同时把Production Write权限锁在Typed IaC + CI + Human Review + Git Sync后面。** 这是可直接迁移到Terraform、Kubernetes、Feature Flag甚至数据库Migration的Agent Guardrail设计。

### ② Anthropic、Claude Codeのプラグイン評価コマンド「claude plugin eval」を紹介

**来源：gihyo.jp｜2026年9月14日**  
**原文 URL：** https://gihyo.jp/article/2026/09/claude-plugin-eval

Claude Code **2.1.269以后**提供 `claude plugin eval`，解决的是一个很容易被忽略的问题：装了Plugin/Skill后任务成功，并不能证明成功来自Plugin，因为同一个Model不用Plugin可能也能完成。目标Plugin目录中运行 `claude plugin eval init`，Claude会通过对话收集“希望出现/不希望出现的输出”和Sample Prompt，生成Test Case与Criterion，还会试跑并估算完整Eval费用。Criterion不仅可以做Pattern Match，也能检查是否调用指定Tool，甚至让另一个AI Model充当Grader。

正式执行 `claude plugin eval` 时，同一Case会分别以Plugin开启与关闭运行；默认两边**各执行3次**并比较平均Score，详细结果可查看HTML Report。这种设计把“感觉Plugin有用”变成带Baseline的Comparison。若只想快速冒烟，可用 `--runs 1`；若不希望Report保存到claude.ai Artifact，可用 `--no-publish`。包含MCP的Plugin也不会默认启动真实Server，必须显式使用 `--allow-real-servers`，并用 `--allow-tools`允许具体Tool。

**Evidence / Measurement：** 文章描述的是Anthropic官方Eval Command和默认运行行为，核心证据是同一Test Set的Plugin on/off比较，而不是某个Vendor Benchmark分数。默认3次正是为了降低一次随机Sampling对结论的影响。

**Evidence Boundary：但是，** Eval只证明“在你写出的Test Distribution上”Plugin是否改善结果。它会消耗Token与Plan/API额度，而且Hook和MCP Server以用户权限运行，错误的Eval配置本身就可能产生Side Effect。因此Baseline、Multiple Runs、Trusted Plugin和最小Tool Permission缺一不可；不能把一组高分直接外推成所有Repository或所有Prompt都有效。

**为什么值得看：★★★★★**  
面试时可以把“我写了Claude Code Skill”升级成：**我会为Skill建立Control Group，比较Plugin on/off的成功率、Tool Use和Cost，再用Regression Eval避免后续修改把效果做坏。** 这比展示Prompt本身更接近AI工程化。

### ③ Amazon S3で「ストレージコスト80％削減」――たった6カ月で成功した“再現性のある方法”とは？

**来源：＠IT｜2026年9月14日**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/spv/2609/14/news027.html

WeatherBug在多Account AWS环境中管理数百个S3 Bucket，随着Data持续增长，问题并不是“找不到更便宜的Storage Class”，而是**不知道到底什么在推高费用**。调查发现，超过一半启用Versioning的Bucket没有Lifecycle Policy；很少访问的Log仍留在S3 Standard；Landing Zone旧数据没有Expiration；非关键Data还存在重复与Cross-Region Replication。团队因此先用 **S3 Storage Lens**跨Account观察实际使用，再决定优化优先级。

流程被拆成三个阶段：Visibility / Assessment、Quick Wins、Strategic Optimization。Kiro CLI被用于分析Access Pattern并辅助生成Lifecycle建议，真正的改变则围绕Storage Hygiene与按业务Access Pattern设计Lifecycle，而不是让Agent直接“自动删数据”。最终WeatherBug报告在**6个月以内把Storage Cost降低80%**，同时没有牺牲Data Accessibility和Operational Stability。值得注意的是，团队先做Manual Review，再让AI与Automation扩大处理规模，这和“先自动化再找证据”正好相反。

**Evidence / Measurement：** 80%是WeatherBug与AWS公开的Customer Case Result，适用条件包括其原本大量缺失Lifecycle、冷Log留在Standard、Landing Zone无Expiration以及非必要Replication等具体浪费结构。文章强调的是三阶段方法的可复用性，而不是承诺每个组织都得到80%。

**Evidence Boundary：但是，** 这是单一企业的Cloud FinOps案例，不是多公司Controlled Benchmark。Retention、Compliance、Recovery Point、Access Frequency、Replication价值不同，会直接改变Lifecycle最佳答案。尤其“AI建议可降本”不能等同于“可以自动Apply”；Production应该先确认Data Owner与恢复要求，再验证实际Billing/Access Metric后扩大范围。

**为什么值得看：★★★★★**  
这是AI × FinOps的好案例：**Agent负责Discovery / Recommendation，团队负责Policy / Risk，Cloud Metric负责验证。** 面试里比“把S3换成Glacier”更高级，因为它展示了可持续Cost Optimization Loop。

### ④ 「FDE」「ハーネス」「オープンウェイト」って何？　AI時代に現場で飛び交う10用語をGitHubが整理

**来源：＠IT｜2026年9月14日**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/spv/2609/14/news037.html

GitHub把近期开发现场常见的FDE、Harness Engineering、Loop Engineering、Hill Climbing、Squad/Fleet、Open Weights等词重新解释成工程实践。其中最重要的是 **Harness**：Model输出之外，Tool连接、Permission、Memory、Context、Orchestration等“让Model在真实Workflow里可控工作的外围系统”都属于Harness。GitHub Copilot本身就是一个直观例子——Model之外还有Codebase、Editor、PR、Terminal等大量Context与Action Surface。

**Loop Engineering**则强调不要每天手动发同一个Prompt，而要把Fetch Work → Agent Execute → Validate Output → Stuck时Escalate Human做成可重复Loop；GitHub甚至把它形容为AI-native cron job。**Hill Climbing**是在Loop上加Eval，通过“PR Review Agent到底能不能找到真实Bug、Recommendation有没有用”等Metric持续调整Harness。FDE则把工程师放到客户现场，把AI Tool、Automation Workflow、Agent接入既有System与Delivery Process。

**Evidence / Measurement：** 这篇的价值不是给出“效率提升X%”，而是提供了一套更精确的Architecture Vocabulary。它把原来都叫“Prompt Engineering”的工作拆成Loop、Harness、Eval、Role和Model Openness，有助于团队讨论Responsibility与System Boundary。

**Evidence Boundary：但是，** 这些术语本身仍在快速演化，GitHub也明确提醒有些词是有用的新Pattern，有些只是旧概念的新名字，还有些定义仍在形成。它不是性能Benchmark，也不能证明“做了Harness就自动更可靠”；真正落地仍要定义Eval Metric、Permission Boundary、Failure Condition、Checkpoint和Human Escalation。

**为什么值得看：★★★★★**  
以后面试被问“Agent工程和Prompt Engineering有什么区别”，可以回答：**Prompt只是Model输入；Harness Engineering负责Model外部的Context、Tool、Permission和Orchestration，Loop Engineering负责把工作变成可重复、可验证、可升级处理的System。**

### ⑤ 「禁止したらシャドーITがなくなる」は幻想？　まん延するシンプルな理由

**来源：＠IT｜2026年9月15日 05:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/15/news010.html

文章指出，企业禁止某个Online Service后“没人再来问”，并不代表Usage消失。实际问题是工作仍然存在：大文件仍要发给客户、出差仍要访问资料；如果Approved Tool的申请要两周，而业务后天就Deadline，现场就会寻找公司看不到的替代。一次简单的“禁止”还会降低再次咨询的意愿，于是企业失去的可能不是Shadow IT，而是**Usage Visibility与Consultation Channel**。

文章引用Cybersecurity Cloud对**360名已经在工作中使用生成AI的公司职员**的调查：若公司禁止生成AI，**19.2%**回答会“个人继续使用”，**18.6%**回答会“向公司争取继续使用”。作者据此提出很具体的治理改造：禁止通知至少补两行——“可以用什么Approved Alternative”和“其他Case到哪里咨询”；效果不要用Consultation Count衡量，而要看**实际迁移到公司公认Service的件数**；同时测从咨询到回复用了多少天。正式导入可能慢，但某个Case是否暂时允许可以更快回答。

**Evidence / Measurement：** 360人调查提供了“Ban后仍可能继续”的Signal，而文章的工程判断是：Policy必须同时设计Alternative、Consultation和Response Time。它把Security Governance从“规则有没有发”转成“员工能不能在Deadline内走正规Route”。

**Evidence Boundary：但是，** 调查对象是“已经在业务中使用生成AI的人”，并不是所有日本公司职员，因此19.2%和18.6%不能直接当作任何公司的Shadow AI发生率。文章给出的两行通知和Response-Time治理也属于Practitioner Guidance，不是Controlled Experiment。企业仍应结合Proxy/CASB/SSO/AI Gateway等自身Log观察真正的Tool Adoption与Migration。

**为什么值得看：★★★★★**  
对Security/AI Governance面试非常实用。核心不是“放松规则”，而是：**安全的正规路径必须在业务时间尺度上可用，否则Policy越强，实际行为可能越不可见。**

## 4. 今日の技術テーマ

### Verifiable AI Execution Path —— 把“AI会做”变成“AI只能沿可验证路径做”

今天五篇可以抽象成一条Production AI流水线：

```text
Observation / Context
        ↓
AI Proposal / Reasoning
        ↓
Harness
├─ Tool & Data Access
├─ Permission
├─ Baseline / Eval
├─ Validation
└─ Escalation
        ↓
Controlled Change Path
        ↓
Evidence / Cost / Adoption Metric
```

**机制：** AI首先读取被授权的Context，产生Proposal；Proposal不直接成为Committed State，而是进入类型、Schema、Eval、CI、Human Review或Policy Gate。DeNA的MCP read-only + Git Sync、Claude Plugin Eval的on/off Baseline、S3 Optimization的Storage Lens → Kiro → Lifecycle、Shadow AI的Approved Alternative → Consultation → Migration Metric，本质上都是这条路径的不同实现。

**优点：** Model和Tool可以更换，而验证逻辑能保留；Production权限不必随着Agent能力一起无限扩大；失败时能知道到底是Model、Tool、Policy、Data还是Human Process出问题；更容易把“AI采用率”变成更可信的Outcome Metric。

**局限：** 可验证路径只覆盖你定义出来的风险。Type Check抓不到PromQL语义，Plugin Eval抓不到Test Set之外的Distribution Shift，Storage Lens看见浪费也不代表能安全删除，Policy提供Alternative也不代表员工一定迁移。因此Production需要持续加入真实Failure和Human Feedback来扩充Eval与Guardrail。

**日本企业落地注意点：** 建议每个Agent/AI Workflow明确六栏：`Read Scope / Write Scope / Validation / Human Owner / Evidence / Rollback`。先让AI在Read-only或Proposal-only阶段积累Evidence，再逐步扩展Action。不要把“能调用Tool”误解成“应该拥有写权限”。

# B. 重点总结和面试可用知识点

## 1. DeNA Grafana IaC

**中文总结：** AI可通过MCP调查真实Metric与既有Dashboard，但常规访问使用read-only Service Account；AI输出必须转成Grafana Foundation SDK TypeScript，再走`build → validate → PR → Git Sync`。Type Safety只能验证结构，PromQL语义和Panel可读性仍要Runtime Review。

**日本語の知識ポイント：** `mcp-grafana`の調査経路とProduction Deploy経路を分離し、AIの提案をTyped IaCとしてReviewする。Git Syncはv13以降が正式Supportで、Migrationは旧版と新UID版を並行運用する。

## 2. Claude Code Plugin Eval

**中文总结：** Plugin价值不能靠“装上以后任务成功”判断；`claude plugin eval`用同一Test Case比较Plugin on/off，默认各3次，降低Sampling Variance。真实MCP需要显式`--allow-real-servers`与`--allow-tools`，Eval本身也是有Cost和Permission Risk的生产动作。

**日本語の知識ポイント：** Plugin EvaluationではBaseline、Multiple Runs、Test Distribution、Tool Permissionを分けて設計する。Score差はEvidenceだが、未テストPromptへのGeneralizationを保証しない。

## 3. WeatherBug S3 FinOps

**中文总结：** 先用S3 Storage Lens理解真实Footprint，再清理明显浪费，最后按Access Pattern设计Lifecycle；Kiro CLI用于分析和建议。6个月80%是WeatherBug Case，不是通用承诺。

**日本語の知識ポイント：** FinOpsは「安いClassへ移す」ことではなく、Visibility → Prioritization → Lifecycle → Verificationの継続Loopとして設計する。Customer Caseの削減率と自社の期待値を分ける。

## 4. Harness / Loop Engineering

**中文总结：** Harness是Model外部的Tool、Permission、Memory、Context、Orchestration；Loop Engineering把一次Prompt变成Fetch→Execute→Validate→Escalate的可重复系统；Hill Climbing再用Eval持续优化Harness。

**日本語の知識ポイント：** Prompt EngineeringとAgent Engineeringを分けるKeyはModel外部Systemにある。Harness自体のQualityはEval、Observability、Failure Conditionで測る必要がある。

## 5. Shadow AI

**中文总结：** Ban-only Policy可能让Usage转入不可见区域。调查中19.2%的既有生成AI业务用户称禁止后仍会个人使用，18.6%会向公司争取继续使用。治理应同时提供Alternative、Consultation Route并测Migration Count与Response Days。

**日本語の知識ポイント：** Security Policyの目的は「相談を減らす」ことではなく、Approved Routeへ実利用を移すこと。Survey母集団が生成AI既利用者であるEvidence Boundaryも忘れない。

## C-3. JLPT语法（7）

1. **～にとどまらず｜N1**：不止于。结构：`名詞 + にとどまらず / 動詞辞書形 + にとどまらず`。例：`AIはCode生成にとどまらず、実Dataの調査にも使われています。`
2. **～たうえで｜N2**：在完成/确认前项之后。结构：`動詞た形 + うえで / 名詞 + のうえで`。例：`生成物を検証したうえで、Git Syncから本番へ反映します。`
3. **～に応じて｜N2**：根据……。结构：`名詞 + に応じて`。例：`Access Patternに応じてStorage ClassとLifecycleを選びます。`
4. **～とは限らない｜N2**：不一定。例：`ある企業で80％削減できても、自社で同じ効果が出るとは限りません。`
5. **～を踏まえて｜N1**：基于……。结构：`名詞 + を踏まえて`。例：`Pluginあり・なしのScore差を踏まえて、改善点を決めます。`
6. **～かねない｜N1**：可能导致不良结果。结构：`動詞ます形語幹 + かねない`。例：`代替手段を示さず禁止すると、利用が見えない場所へ移りかねません。`
7. **～一方で｜N2**：另一方面。例：`Agentは反復作業を減らせる一方で、Permission設計が不十分だとRiskが増えます。`
