### 1. ブラウザだけで動くデータ分析AIエージェントを作ってみた

**原文：** https://zenn.dev/coji/articles/browser-only-data-analyst-agent

**发布时间：** 2026-10-20 08:33:49 JST

作者把数据分析代理做成了静态网页：Chrome 内置的 Gemini Nano 通过 Prompt API 编写 SQL 并组织说明，DuckDB-WASM 负责查询 CSV、Parquet，pi-durable 把会话、调用和结果写入 SQLite-WASM。数据库和运行记录都存放在 OPFS，也就是浏览器按站点隔离的文件空间。提问之后的推理和集计在标签页内进行；但首次模型下载、启动时加载数据库引擎与扩展仍会联网，不能把它说成整个使用周期完全没有网络。示例使用家庭支出数据，不是任意数据上都正确的通用分析产品。

恢复机制比“把聊天记录存起来”更细。pi-durable 在调用工具前保存调用意图，完成后再保存结果。缺少结果的中断调用按工具是否允许重放处理：作者把三个只读工具标为可安全重试；默认不安全的操作则不会自动重跑。要约工具嵌套在查询工具中，因此仅重试外层仍可能重复 SQL。实现进一步用调用 ID 保存查询结果，有结果时直接取回，再继续被中断的要约。输入也先记录请求标识，重送相同标识不会产生第二条问题。

前端还有独立的资源边界。OPFS 文件不能由第二个标签页同时打开，作者用 Web Locks 将执行限制在一个标签页；React StrictMode 的重复初始化曾占用自己刚取得的锁，因此启动只做一次，开发热更新改成完整重载。显示的“计划中、要约中、完成”由已提交的运行记录计算，不另外持久化一套容易过期的状态。Gemini Nano 可用之后才恢复任务，以免模型尚在下载时把恢复误判成失败。

验证包括存储适配器的24项适合性测试、重新打开同一 SQLite 文件的恢复测试，以及要约过程中重载页面的 Playwright 测试。文章没有测试强制结束整个浏览器，也没有验证写操作的安全重放。Prompt API 不直接提供这里需要的工具调用协议，作者用 JSON Schema 限制返回形式，并额外核对要约里的数字和名称。小模型仍会写错 SQL、跳过实际执行或改写姓名；当前只传最新一个问题，回答约需15～20秒，主要时间花在模型而非数据库。pi-durable 1.3.0 还是实验性接口，这些条件都是采用前需要保留的边界。

**阅读价值：** 把前端状态、模型能力和执行记录放在同一个故障场景下检查，适合解释“界面恢复”与“副作用没有重复”之间的区别。

### 2. Lambda Web Functions と従来の Lambda の実行環境と課金の違いを実測から確かめてみた

**原文：** https://zenn.dev/aws_japan/articles/lambda-web-functions-vs-event-functions

**发布时间：** 2026-10-20 09:28:10 JST

作者在东京区域用 Node.js 24、arm64 和相同业务逻辑，对比 Lambda Web Functions 与传统 Event Functions。前者运行监听端口的 HTTP 服务，后者由处理器接收事件；既有 Express、Hono 等 HTTP 应用迁移时是否需要适配层，是程序模型上的差异。试验覆盖3秒等待的300并发请求、200毫秒等待的20并发持续60秒，以及1秒 CPU 循环的20并发。Event 另外测了256、512、1024、2048MB。环境标识的数量表示实际响应过的环境，初始化日志才用于统计冷启动，两者并不必然相等。

在300请求的 I/O 突发中，Web Functions 用18个环境响应、记录19次初始化，每环境最多23个并发；2048MB 的 Event Functions 有299个响应环境。这个差异来自一个进程承载多个等待中的请求，不是单个计算自动并行。CPU 循环试验中，Web Functions 的20件几乎都进入一个 Node.js 进程，事件循环被计算占据，最大延迟20.6秒；Event 将请求分到不同环境。文章提出减小环境内并发或另用工作线程作为思路，但没有实测这两种改善。即使提供2个 vCPU，也不能把单线程 JavaScript 当成两路并行计算。

费用也不能只看请求执行时间。Event 按请求和执行时长乘分配内存收费，冻结等待复用时不计该时长；Web 分开计 CPU 使用与环境存活期间的内存。作者以结束日志里的寿命、CPU 时间、最大使用内存对照 Cost Explorer，某一天一个应用的内存计量近似值与账单相差约0.8%，但这不是官方确认的通用计算式。持续负载能分摊环境存活成本；只有3个散发请求时，Web 环境仍存活347秒，该示例定价费用约为256MB Event 的260倍。差别主要是空闲内存时间，不能据此说某一种形态永远更贵或更便宜。

运维迁移还包括 S3 代码对象的双方读取权限、IAM 认证入口的签名头、日志保持期和扩展接口。文章记录 Web 环境的扩展注册接口返回404、缺少若干传统环境变量，以及相同日志写入两个日志组；这些会影响既有监控假设。所有负载条件只测一次，不同形态和内存档位的时间与先前热状态不完全相同；CPU 试验按墙钟循环，完成的工作量也不同。采用时应以自己的到达间隔、同等工作量和延迟要求重测。原文已有明确说明的未验证事项不补写成服务保证。

**阅读价值：** 同一入口叫作 Lambda，也可能具有不同的并发、进程和计费单位；前端服务迁移前应先识别负载性质和空闲时间。

### 3. スピード10倍の開発を支える、AI活用基盤の開発に参戦（インターンレポート）

**原文：** https://techblog.lycorp.co.jp/ja/20261019b

**发布时间：** 2026-10-19 11:00:00 JST

这是 LINE ギフト SRE 团队2026年8月3日至9月11日的实习实践，出发点是代码生成变快之后，分支传播、告警初查和规范修正变成新的等待环节。“スピード10倍”是企业价值与目标，原文没有提供速度提高十倍的对照实测。团队按发布日期维护发布分支，主分支发布后需把改动传播给仍在使用的分支；作者用每天运行的 GitHub Actions 自动创建并合并机械性回合并请求，关键判断环节仍需人工确认。

自动化还依赖反馈质量。作者以变异测试检查现有 E2E 测试能否检测人工引入的错误，并整备 OpenAPI；“已有测试”与“测试真的有检测力”不是同一件事。Lefthook 在提交、推送前运行检查，CLI 改为方便以单个可执行文件分发的 Go，数据分析和 AI 周边处理选 Python。这里选择不同语言有具体交付原因，不能概括成统一一种语言就能解决可维护性。文章未给出变异分数的前后数值或误报、漏报统计。

在代理基础设施上，作者比较了直接运行现有 CLI、使用较重的框架，以及直接调用 LLM SDK。前者存在工具演进依赖，后两者分别面对框架负担与会话、状态逻辑膨胀，于是选择轻量描述代理流程的 flue。会话和调查上下文存入数据库，所有处理隔离到容器。执行步数与超时设上限，允许读取日志、指标，同时阻断破坏性写入；这类边界由运行环境和权限实现，不能只靠提示词要求“不要出错”。

当告警或 E2E 失败通知出现，代理会核对相关代码、日志和指标，把原因见解、检查点及建议动作回复到 Slack 线程，人负责核验结论和实际处置。远程编码、自动创建 PR 与工单被列为后续方向，不能写成已经上线的能力。作者也指出长期理想是减少需要回合并的分支策略，而非无限强化临时自动化。本文的价值是展示阶段性约束与职责划分；没有给出的修复成功率、事故率和成本收益，均不补成确定数字。

**阅读价值：** 可以从真实日本企业的分支运用、测试检测力和事件驱动调查三个层次，说明 AI 自动化为何需要运行边界与反馈。

### 4. Claude Code で CI 待ち時間を 18 分から 4 分台に短縮する【GitHub Actions】

**原文：** https://zenn.dev/edash_tech_blog/articles/5b90aa33bd8d49

**发布时间：** 2026-10-20 08:00:05 JST

e-dash 的 Next.js／TypeScript 项目使用 Vitest 4.1 与 GitHub Actions，私有仓库的 Ubuntu runner 只有2个 CPU。测试文件从7月初89个增加到10月初432个，PR CI 中位数从7月约7分钟升到9月约15分钟，较慢时超过18分钟。作者先让 Claude Code 统计同等2 CPU 环境的耗时：400秒中真正测试本体只有57秒，约14%；jsdom 启动占224秒。瓶颈首先是每个文件启动环境的开销，以及默认“CPU 数减1”使该机器只运行一个 worker。

第一步用 Vitest projects 把不需要 DOM 的 TypeScript 测试分到 node 环境，React JSX 测试留在 jsdom，并在根配置统一设置低 CPU 环境的2个 worker。其次把应用完迁移的 PostgreSQL 用 pg_dump 保存，依据迁移文件哈希复用，避免每次从零建库。PR 写出的 Actions 缓存不能供其他 PR 共享，因此共享缓存由 main 生成。数据库准备约从5分钟降至2分15秒，但这并不意味着缓存永远有效；键与分支范围都必须纳入设计。

随后将纯单元测试与数据库集成测试拆为不同作业，并将单元测试再分片。每个分片先输出 blob 报告，末端合并结果后才判定覆盖率门槛，没有通过降低阈值换时间。node_modules 直接复用时，缓存键包含系统、架构、Node 版本及两份包清单；该项目安装时忽略安装脚本，才有文中讨论的复用前提。作者特别提醒，命中缓存后不会再跑安装一致性检查，所以不能遗漏包清单更新。

最终直近20个 PR 的中位数约4分45秒，相对原约15分钟下降约69%；这属于多个措施累加的生产观察，不是 Claude Code 或某个选项的通用速度承诺。缓存总量一度达到11.9GB，超过默认10GB后，数据库缓存也会被逐出。团队减少 Docker 中间层导出、只从 main 保存 Playwright 浏览器缓存并取消重复 npm 下载缓存，把每 PR 估算约1.7GB压到673MB。后续候选方案如共享测试环境、换轻量 DOM 和清理低价值测试，仍需评估，不能列为已实现收益。

**阅读价值：** 前端面试中可以用具体耗时说明为什么先测关键路径，再优化测试环境、数据库准备和缓存失效，而不是一味增加并行数。

### 5. Cloudflare CLIで公式ドキュメントを検索し、Markdownで取得する

**原文：** https://dev.classmethod.jp/articles/cloudflare-cf-docs-search/

**发布时间：** 2026-10-19 15:50:10 JST

作者用 Cloudflare CLI 在终端寻找官方文档，再按所选 URL 取得 Markdown 正文。公开文档搜索不需登录，但仍需互联网；返回的是标题、说明、URL 组成的排序候选，而不是页面全文。官方说明上限5件，作者的 DNS 查询也返回5件。这里的便利是便于在命令行中选择资料和传给编码代理，不能扩大成 Cloudflare 的账户操作也都无需身份认证。

正文获取还要另一步：先读标题和说明确认相关性，再以要求 Markdown 的 HTTP 请求访问选定 URL。文章用 jq 从候选 JSON 提取 URL，再用 curl 获取正文，且让前一步成功才执行下一步；若结果为空，URL 提取返回非零状态，后续下载就不运行。取得的正文带有标题、说明的 frontmatter，响应类型是 Markdown。搜索命中与真正读到正确文档是两个验证点，不应只凭排序第一就替代理解。

环境为 Ubuntu 24.04.5 LTS ARM64、Node.js 24.21.0、cf 1.0.0-beta.18，文中提及安装要求 Node 22.18 以上。CLI 仍为 beta，参数和输出可能变化。作者看到同一页面的不同标题锚点混在候选里，所以5个候选并不等于5个独立来源；日语“定期运行 Worker”的查询中，定时处理器资料也不是第一项。排名只代表当时结果，没有报告大样本召回率。搜索词还应避免带入账号 ID、域名、邮箱或令牌等识别信息。

**阅读价值：** 给编码代理准备上下文时，先找候选再取官方正文；可以明确区分搜索结果、引用证据与需要认证的账户操作。

## 2. 四类速览

- 浏览器 AI：持久化调用与结果，并限定可安全重放的操作，不能用刷新测试代替崩溃安全证明。
- 云架构：Lambda 的请求并发、CPU 调度与环境存续费用需按流量形态分别观察。
- AI 辅助工程：运维代理应受限调查、由人决策；CI 优化从真实耗时与缓存失效入手。
- 资料准备：文档搜索先返候选，再读正式正文；数量、相关性和可追溯证据不能互相替代。

## 3. 面接で使えるポイント

### 1. ブラウザだけで動くデータ分析AIエージェントを作ってみた

**面试问题：**

> ブラウザ内AIの処理を、中断後に安全に再開するにはどう設計しますか。

**约30秒回答：**

> ブラウザ内で処理を再開させるときは、実行結果を先に記録し、再実行してよい操作を分けます。この記事ではpi-durableに呼び出しと結果を保存し、SQLの結果は呼び出しIDで再利用しています。OPFSはWeb Locksで一つのタブに限定します。ただし、ブラウザの強制終了や書き込み処理の安全性は未検証なので、同じ保証には広げません。

**相关项目：** 用只读 CSV 查询做恢复演练：分别在提交前、查询后和要约中重载，核对数据库实际执行次数与界面显示。写操作另行设计幂等性，不照搬只读策略。

**关键词：** pi-durable / OPFS / 冪等性

### 2. Lambda Web Functions と従来の Lambda の実行環境と課金の違いを実測から確かめてみた

**面试问题：**

> HTTPサービスをLambda Web Functionsへ移すか、何を見て判断しますか。

**约30秒回答：**

> まず、I/O待ちが多い処理か、CPUを使い続ける処理かで分けます。Web Functionsは一つのNode.jsプロセスに複数の要求を載せますが、今回のCPUループ20件では最大20.6秒かかりました。使ったCPU時間と環境が残る間のメモリも別に課金されます。ただし各条件一回の測定なので、実際の到着間隔と同じ仕事量で確かめます。

**相关项目：** 对同一 HTTP 功能分别设置突发、持续与稀疏到达，记录实际响应环境、冷启动、CPU 和空闲内存时间。比较 CPU 时固定工作量，保留热状态与时间差。

**关键词：** Web Functions / イベントループ / 環境の寿命

### 3. スピード10倍の開発を支える、AI活用基盤の開発に参戦（インターンレポート）

**面试问题：**

> 運用の一次調査をAIへ任せる場合、どこに安全性の境界を置きますか。

**约30秒回答：**

## 4. 技术主题：AI 工具加速之后，如何让处理仍然可验证

今天的5篇文章都不把“工具能运行”当作最终验收。浏览器代理要知道哪些调用可重放，Lambda 要说明为何同一进程中 I/O 等待可重叠而 CPU 忙循环排队，运维 AI 要区分检索调查与实际处置。可验证的单位应是某次调用、某个执行环境、一个事件的调查或某次测试报告，而不是泛泛的“AI 已成功”。

共同机制是保留能重建原因的中间结果：调用与 SQL 结果、环境生命周期与 CPU 时间、只读调查过程、分片测试的合并报告、被采用文档的正式正文。这些材料让失败能定位到恢复、资源竞争、权限、缓存或资料选择。并行与缓存会减少等待，但也会引入重复执行、单进程阻塞、旧数据库镜像和容量淘汰等新边界。

收益是可以解释加速到底来自哪里，并保持正确性检查。代价则是存储与失效管理、额外状态和测试设计。单次 Lambda 压测、浏览器原型、实习报告和20次 CI 中位数属于不同证据，不能合成一个共同改善率。没有测试的崩溃恢复、破坏性自动操作及后续计划均仍是待验证事项。

面向日本 IT 岗位，可以用当天的具体机制表达设计判断：前端讲 OPFS 的单标签占用或 Vitest 环境分离，云端讲常驻内存和稀疏流量，AI 运维讲受限调查与人工决定。以上是基于文章组织的面试练习，不是读者的实际履历，也不是日本企业采用率的统计。

### 1. 揺るぎない（ゆるぎない）｜N1

- 词性：形容詞
- 含义：坚定不移；不会轻易动摇
- 搭配：揺るぎない信頼 / 揺るぎないものにする
- 文章语境：LINE 的实习报告把建立稳固开发平台作为愿望；这不是已实现“10倍”的测量结论。

### 2. 物怖じする（ものおじする）｜N1

## C-2. IT/AI 专业词汇

1. **durable execution（中断から再開できる実行）**：保存调用和结果，恢复后可从记录重建处理。 浏览器案例的重放限于只读工具，嵌套 SQL 还需结果缓存。

2. **OPFS（オリジン専用ファイルシステム）**：浏览器按来源隔离的私有文件存储。 此案例用 Web Locks 防止多个标签同时占用数据库。

3. **Lambda Web Functions（HTTPサーバー型のLambda）**：一个服务环境中同时处理多个 HTTP 请求的执行形式。 Node.js 单进程的 CPU 串行和 I/O 等待并发必须分开评估。

4. **flue（軽量エージェントフレームワーク）**：用于组织代理会话、状态和工具的框架。 LINE 案例将其用于受限容器内的运维调查，不赋予实际处置的所有权。

5. **mutation testing（ミューテーションテスト）**：主动插入小错误，检查测试是否能发现它们的方法。 LINE 报告用它审视 AI 实现带来的测试质量，而不只看测试数量。

6. **Vitest projects（テスト構成の分離）**：让不同测试组使用各自执行环境的 Vitest 配置。 e-dash 将不需要 DOM 的测试与 jsdom 测试分开，再统一控制 worker。

7. **blob report（統合用テストレポート）**：可在分片测试后合并的中间测试报告。 覆盖率须在合并全部报告后判定，而非各片独立通过就结束。

8. **Markdown content negotiation（Markdownでの応答形式指定）**：通过 HTTP 头要求服务返回 Markdown 正文。 Cloudflare 的搜索只返候选，所选页面仍需单独取回并确认。

### 1. ～限り｜N2

- 含义：只要某状态仍持续，就在该条件下成立。
- 结构：動詞普通形＋限り／い形容詞＋限り／名詞・な形容詞＋である限り
- 用法：用状态持续划定结论范围。原文限定的是执行环境仍存在的期间，即使没有请求也继续产生内存费用。
- 原文形态：限り
- 原文依据：[メモリの課金はリクエストがなくても環境が残っている限り続きます。](https://zenn.dev/aws_japan/articles/lambda-web-functions-vs-event-functions)
- 独立例句：接続が続いている限り、同じ処理の結果を待ちます。
- 例句译文：只要连接还在持续，就等待同一处理的结果。
- 注意：区别既习的「～限りでは」（所知范围）与「～ない限り」（除非）。这里是肯定状态持续的条件；例句不是产品保证。
