### ① AIが書くコード「エラー率はJavaがPythonの6.7倍」　150万「会話」データで分かったAIコーディングの盲点

**来源：＠IT｜2026年9月15日 11:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/15/news047.html

AWS基于 **2026年1～6月Kiro IDE约150万次会话**与其中 **40.6万次静态分析工具调用**，观察Coding Agent在“写代码的过程中”会不会主动检查自己的输出。Kiro的 `diagnostics` 并不是另造一套Analyzer，而是连接各语言现有的Language Server / Linter，例如TypeScript / JavaScript使用 `tsserver`，Java使用 `jdtls`，Python使用 `Pyright`，Rust使用 `rust-analyzer`，Go使用 `gopls`，C/C++使用 `clangd`。它能发现缺失import、类型不一致、未定义Symbol等问题，因此这里测量的是Agent是否会主动把Static Analysis纳入生成Loop，而不只是最终文件是否能Build。

结果很值得警惕：至少主动调用过一次 `diagnostics` 的Coding会话比例，最低的Sonnet 4.5只有 **2.74％**，最高的Opus 4.6也只有 **22.26％**。换句话说，即使Tool已经存在，Model也通常不会自动把“检查自己”变成完成条件。文章还引用实验说明，如果Workflow在错误未解决前阻止Agent完成，错误代码被接受的比例可从约90％降到约8％。语言间也存在明显差异：在Opus 4.6样本中JavaScript文件静态错误率1.6％、Python 4.0％、TypeScript 8.6％、TSX（React）11.2％、Java 26.7％；测试文件的平均Error又大约是Source File的3～4倍。

**Evidence / Measurement：** 这些数字来自AWS对Kiro真实使用Telemetry的分析，而不是单一Toy Benchmark；它同时说明了Model版本、语言与Test Code上的差异。不过这个数据只覆盖Agent实际调用了diagnostics后能被静态分析捕捉的问题。**但是，**低静态错误率并不等于代码更正确：JavaScript / Python的静态检查本来就比强类型语言弱，`diagnostics` Clean也无法证明Runtime Error、Logic Bug或Performance没有问题；AWS也明确表示，观察到的改善不能只归因于Model升级，因为Prompt、Hook、Sub-agent等Orchestration也会影响结果。

**为什么值得看：★★★★★**  
这篇非常适合回答“AI Coding如何进CI”。真正的做法不是希望Model“自觉检查”，而是把 `diagnostics / typecheck / lint / test / review` 变成 **deterministic completion gate**。对React / TypeScript工程师尤其有用：TSX的11.2％并不是“React质量差”的结论，而是在提醒你，AI生成UI Code仍需要Type System和Test Harness主动兜底。

### ② GitHub Copilot、モデル自動選択「Auto」に3つのティアを追加 ——コストと品質の重視度を調整可能に

**来源：gihyo.jp｜2026年9月15日**  
**原文 URL：** https://gihyo.jp/article/2026/09/github-copilot-auto-model-selection

GitHub Copilot的Model自动选择 `Auto` 现在不再只是一个黑盒开关。GitHub在9月14日宣布新增三种Tier：**Efficiency** 优先低成本、适合快速简单Task；**Balance** 综合Cost、Quality与Response Time；**Intelligence** 优先Quality、面向复杂Task。Auto会按每个Prompt单独判断Model，有料Plan的计费按实际被选中的Model计算，并在该价格基础上 **10％折扣**。这说明Developer Platform正在把“选哪个模型”从个人习惯转成可以显式表达的Routing Policy。

一个容易误解的点是：Intelligence并不意味着每个请求都强制用最大Model。官方说明中，即使选择Intelligence，如果只是给现有函数补docstring这种简单工作，Auto仍可能选择小型高效Model。2026年9月15日的候选池也会因Product不同而变化：VS Code Copilot Chat、Copilot CLI、GitHub Copilot App有一组共同候选，同时部分产品还包含Claude Opus 4.8、Gemini 3.6 / 3.7 Flash或GPT-5.3-Codex等。Cloud Agent虽然支持Auto，但暂不包含这三个Tier。

**Evidence / Measurement：** 这是GitHub产品规格/Changelog性质的信息，不是“Efficiency一定节省多少”“Intelligence一定提高多少成功率”的Benchmark。**但是，**实际可选Model还受Copilot Plan、管理员Policy和产品端支持范围制约，候选名单也会变化。因此企业不能只记录“我们开启了Auto”，而应把 `selected model / task type / success / latency / cost` 纳入Telemetry，验证不同Tier是否真的符合自己的Repository与Task分布。

**为什么值得看：★★★★★**  
面试里可以把“自动选模型很方便”升级成 **Policy-based Model Routing**：简单Task优先Efficiency，普通开发走Balance，高风险或复杂Task才提高Intelligence，并用实际Task Success与Cost-per-success检查Routing是否合理。

### ③ AnthropicのMCP共同作者が来日、基調講演で語るこれからのMCP注力領域。AGNTCon＋MCPCon Japan 2026

**来源：Publickey｜2026年9月15日**  
**原文 URL：** https://www.publickey1.jp/blog/26/anthropicmcpmcpagntconmcpcon_japan_2026.html

MCP共同作者、Anthropic的David Soria Parra在东京 `AGNTCon＋MCPCon Japan 2026` 的Keynote中，把MCP下一阶段的重点从“Tool能不能连上”推进到了 **Long-horizon Agent、Skill Distribution、Identity / Authorization**。他解释，Coding Agent之所以较早进入Production，一个重要原因是Compiler和Unit Test可以持续给Model反馈；当Agent扩展到知识工作时，关键反而变成它怎样连接Microsoft 365、Google Workspace、Task System等组织系统，以及谁允许它代表谁采取行动。

演讲给出的生态规模也非常大：Claude上经MCP的Tool Call累计约 **10亿次**，MCP SDK Download超过 **每月5亿次**。同时，MCP已经加入Remote Connection、Authorization、MCP Apps，并在2026年7月28日规格中正式强化Stateless Connection。未来12个月的重点之一是 **MCP Tasks**：让MCP Server承担数分钟、数小时、数周甚至数月的Long-running处理；另一个是 **Skills over MCP**，把Tool与Skill一起Package，通过MCP Server提供，并为企业内部建立统一Skill Registry。最后一块是Agent Identity：不仅知道“哪个Agent”，还要知道它“代表谁”行动，以便做Observability、Policy和Authorization。

**Evidence / Measurement：** 10亿Tool Call和月5亿SDK Download来自Keynote中的Anthropic / MCP生态指标，适合证明采用规模，但不是独立市场占有率调查。**但是，** `MCP Tasks`、`Skills over MCP` 等内容包含今后12个月Roadmap方向，不能把演讲中的愿景当成今天已经全面GA的规格。企业设计时必须区分Current Spec与Future Capability，并优先把Identity、Delegation、Audit Trail和Cancellation/Timeout等Long-running Task控制做好。

**为什么值得看：★★★★★**  
如果面试被问“MCP之后还要学什么”，今天最好的答案不是更多MCP Server，而是：**Long-running Task Lifecycle + Skill Registry + Agent Identity / Delegation**。这已经从Integration问题进入企业级Agent Governance。

### ④ AIの「脱クラウド・オンプレミス回帰」が66％、「AI案件の中止」も多数――その原因は？

**来源：＠IT｜2026年9月15日**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/spv/2609/15/news031.html

Cloudera的《The Great AI Re-Architecture》调查显示，AI从PoC走向本格利用后，企业开始重新分配AI Workload，而不是简单把一切继续堆到Public Cloud。调查覆盖9个市场的 **1500名Enterprise Architect / Cloud Infrastructure负责人 / Data Architect**，其中日本100人。结果中，77％表示积极使用AI；但95％在过去一年因Data Governance、Compliance或Regulation问题延期或取消过AI Project。72％认为Data Architecture需要大幅重新设计，日本为69％。

最醒目的数字是 **66％** 的受访企业称过去一年把AI Workload从Public Cloud移到Private Cloud或On-prem。日本受访者未来投资方向中，On-prem扩大35％、Cloud扩大31％、Hybrid-first 22％、Edge 12％；同时全球73％认为AI让Data Governance更复杂，97％至少每月一次在不同环境间移动Data。报道还指出日本有 **86％** 受访者感到Infrastructure Cost上升。真正的趋势不是“Cloud失败”，而是Data Location、Cost、Performance、Security与Regulation开始共同决定每个Workload应该放在哪里。

**Evidence / Measurement：** 调查时间为2026年6月5～22日，样本主体是较大企业的架构与基础设施相关角色，因此它很好地反映了这一类决策者的自我报告。**但是，**这仍是Cloudera发布的Vendor Survey，不是对实际Cloud Bill、Latency或On-prem TCO的独立审计；66％也不能理解为“所有AI都应该回On-prem”。Private环境会带来GPU利用率、Capacity Planning、Patch、人才和Availability的新成本，真正应比较的是Workload级 **TCO + Governance + Data Gravity + SLO**。

**为什么值得看：★★★★★**  
日本AI岗位面试常被问Cloud / On-prem怎么选。好的回答不是站队，而是按Data Sensitivity、Regulation、Model/Compute需求、Latency、Utilization、Ops Cost分层，然后把Hybrid环境中的Policy和Audit尽量统一。

### ⑤ アイカ工業が「AI活用を阻む“表記揺れ”問題」解消へ　データ品質を高める具体策とは？

**来源：＠IT｜2026年9月15日 11:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/15/news040.html

アイカ工業在推进生成AI与BI之前遇到的不是Model问题，而是 **Master Data本身不可稳定使用**：客户与销售相关Data由不同部门、据点分别管理，存在表记摇摆、重复、更新遗漏，导致同一企业在不同System里无法可靠地被识别为同一个Entity。这样的Source Data即使交给更强LLM，也只会把不一致带进Retrieval、Aggregation和Answer。

其做法是引入 `Sansan Data Intelligence` 与 `Sansan`。核心Anchor是 **Sansan Organization Code（SOC）**：给得意先、仕入先等多个Master Data分配统一识别Code，让不同System里的同一企业 / 事业所可以关联管理；再通过自动Data Cleansing解决表记摇摆与重复，并保持较新的状态。Sansan侧则把名片、Email、商谈History等Customer Touchpoint集中管理。企业希望在此基础上把Master与生成AI/BI、销售活动和经营判断连接起来。

**Evidence / Measurement：** 这是企业导入Case，文章明确说明了问题、选择的产品能力和未来利用方向。**但是，**报道没有给出“生成AI回答精度提升X％”“重复率下降Y％”之类的量化结果，所以不能把“引入SOC和Cleansing”直接等同于AI效果已经被证明。后续仍应测 `duplicate rate / entity match accuracy / freshness / retrieval precision / answer accuracy`，并设置Master Data Owner和更新SLA。

**为什么值得看：★★★★★**  
这是很典型的日本企业AI落地题：当RAG或BI效果不稳定时，不要第一反应就换Embedding或Model。先问 **Entity是否统一、Master谁负责、版本是否新、Source of Truth是什么**。Data Quality通常是AI工程的一部分，而不是“业务部门以后再整理”的前置杂务。

## 2. 分类速览

### 🤖 AI / Agent
今天的重点不是新Model本身，而是Agent外层的控制。Kiro告诉我们Static Analysis必须成为Workflow Gate；MCP则把治理扩展到Long-running Task、Skills和Identity。Agent Engineering正在从Prompt层进入Execution Contract层。

### 💻 Frontend
过去24小时没有一篇新的React / Next.js专文强到足以进入Top 5，但Top 1与Frontend直接相关：Opus 4.6样本中TypeScript文件静态Error率8.6％、TSX（React）11.2％。这不能解释为React“更差”，但非常适合提醒Frontend团队把`tsc`、ESLint、Component Test与Review设为AI生成Code的强制Gate。

### ☁️ Cloud / Backend
Copilot Auto展示的是Model层Routing；Cloudera调查展示的是Infrastructure层Routing。二者本质相似：不是选一个永远最强的对象，而是根据Task / Data / Cost / Governance选择合适执行位置，并保留实际Telemetry验证选择是否合理。

### 🏢 日本企业 Tech / AI导入
アイカ工業案例把AI导入的起点拉回Master Data。不同System中的企业实体如果没有统一Key，RAG、BI和AI分析都会继承Source的不一致。日本企业AI岗位中，“Data Quality / Master Owner / Source of Truth”会越来越像基础能力，而不是附加话题。

### 1. Kiro diagnosticsとCompletion Gate

**質問：**

AIコーディングAgentの品質Gateを設計するなら、何を必須にしますか。

**約30秒回答：**

生成後の静的解析を任意ではなく完了条件にします。Kiro IDEの約150万会話ではdiagnosticsを自発的に呼んだ割合が2.74％から22.26％にとどまり、Opus 4.6ではJavaの静的エラー率が26.7％、Pythonは4.0％でした。ただしdiagnosticsがCleanでもRuntimeやLogicの正しさは保証しないため、TestとReviewを別Gateにします。

**関連プロジェクト：** AI Coding / CI Gate / Static Analysis  
**技術キーワード：** 完了条件 / 静的解析 / 多層検証

### 2. GitHub Copilot AutoのModel Routing

**質問：**

GitHub CopilotのAutoモデル選択をTeamで使うなら、どうPolicyを決めますか。

**約30秒回答：**

TaskのRiskとCostに合わせてEfficiency、Balance、Intelligenceを使い分けます。AutoはPromptごとにModelを選び、有料Planでは選択Modelの料金から10％引きです。ただしVS Code、Copilot CLI、GitHub Copilot Appで候補Modelが一部異なり、Admin Policyでも制約されるため、Tier名だけでなく実際の選択履歴とTask成功率を確認します。

**関連プロジェクト：** GitHub Copilot / Model Routing / Developer Platform  
**技術キーワード：** モデル選択 / コスト最適化 / 管理者ポリシー

### 3. MCP Tasks・Skills・Identity

**質問：**

MCPを社内Agent基盤へ広げるとき、次に何を設計しますか。

**約30秒回答：**

Tool接続だけでなく長期TaskとIdentityを設計します。講演ではClaude上のMCP Tool Callが累計約10億件、SDK Downloadが月間5億件超とされ、今後はMCP Tasks、Skills over MCP、認可とIdentityが重点です。ただしRoadmap要素も含むため、現行仕様と分け、誰の代理で動くAgentかをAuditできる構成にします。

**関連プロジェクト：** MCP Platform / Long-running Agent / Identity  
**技術キーワード：** 長期タスク / エージェントID / 認可

### 4. Hybrid AI Infrastructure

**質問：**

AI WorkloadのCloudとOn-premを選ぶとき、何を基準にしますか。

**約30秒回答：**

Cloud回帰論ではなくData Governance、Cost、Performanceで配置を決めます。Clouderaの1500人調査では66％がAI WorkloadをPublic CloudからPrivate CloudまたはOn-premへ移し、日本では86％がInfra Cost増を回答しました。ただし自己申告のVendor調査なので、自社ではData移動、Compliance、運用人件費を含むTCOで比較します。

**関連プロジェクト：** AI Infrastructure / Hybrid Cloud / FinOps  
**技術キーワード：** 配置判断 / データガバナンス / TCO

### 5. Master Data Quality

**質問：**

生成AIやBIの前にMaster Data品質をどう整えますか。

**約30秒回答：**

まず同一企業を同一Entityとして扱えるKeyとCleansingを整えます。アイカ工業はSansan Data IntelligenceのSansan Organization Code、SOCで複数SystemのMasterを関連付け、表記揺れと重複を自動Cleansingしました。ただしAI精度向上率は未提示なので、導入後は重複率、更新鮮度、検索・回答精度を自社KPIで測ります。

**関連プロジェクト：** Enterprise Data / RAG / BI / Master Data  
**技術キーワード：** 名寄せ / 表記揺れ / データクレンジング

# Execution Preconditions：先定义“什么条件满足后，AI才算完成”

```text
Task / Business Goal
        ↓
Execution Context
├─ Model / Tier
├─ Tool / MCP
├─ Data / Master
└─ Runtime Location
        ↓
Preconditions
├─ Static Analysis / Test
├─ Identity / Authorization
├─ Governance / Compliance
├─ Cost / SLO
└─ Source Data Quality
        ↓
AI / Agent Execution
        ↓
Evidence
        ↓
Commit / Rollout / Human Gate
```

Top 1说明最直接：即使`diagnostics`已经存在，Model也很少主动调用，所以**Tool Availability不等于Control**；必须把它放进Completion Gate。Top 2进一步把Model Selection从“开发者临时选择”变成Efficiency / Balance / Intelligence这样的Policy。Top 3则说明MCP发展到Long-running Task后，仅有Tool Schema远远不够，必须知道Agent是谁、代表谁、Task多久结束、如何Cancel和Audit。Top 4把相同思想放到Infra：Public Cloud、Private Cloud、On-prem都只是可选执行环境，实际选择要受Data Governance与TCO约束。Top 5最后补上最底层前提：如果Master Data连同一企业都无法稳定识别，AI再强也无法凭空制造可靠Source of Truth。

**优点**是Model、Cloud或Tool都可以替换，而Completion Gate、Identity、Evidence与Data Quality标准可以继续复用。**局限**是Precondition本身也可能设计错：Static Analysis抓不到Runtime Bug，Survey不能替代自己的TCO，统一Entity Code也不能自动证明Answer Quality。因此这些Gate必须由Production Failure与Business Outcome持续更新。

日本企业落地时，可以给每个AI Workflow固定记录六项：`Input Source / Model or Runtime / Required Checks / Identity & Permission / Evidence / Commit Authority`。这样“AI自动化”不再是把更多权限一次性交给Agent，而是明确**满足什么证据后，哪些动作才允许进入下一阶段**。

# B. 重点总结和面试可用知识点

## 1. Kiro：AI Coding的自我检查不能靠自觉
**中文总结：**
- 约150万Kiro IDE会话显示，Model主动调用`diagnostics`的比例只有2.74％～22.26％。
- Java 26.7％、Python 4.0％等数字是**静态Error Rate**，不能直接当语言或Code正确率排名。
- Test File Error高于Source File，说明AI Coding Quality Gate必须覆盖测试代码本身。
- Completion Gate应该由Workflow强制，而不是写一句“请检查代码”后相信Agent会执行。

**日本語の知識ポイント：** `Toolが使える`ことと`Toolを必ず使う`ことは別です。Static Analysis、Test、ReviewをHarness側の完了条件にします。

## 2. GitHub Copilot Auto：Model Routing开始变成Team Policy
**中文总结：**
- Efficiency / Balance / Intelligence分别表达成本、综合平衡与质量优先。
- Auto仍按Prompt动态选Model，Intelligence也可能给简单Task选小Model。
- 有料Plan为所选Model价格的10％折扣，但企业真正要看的是Cost-per-success。
- 产品、Plan和Admin Policy会改变候选Model，需要记录实际Routing结果。

**日本語の知識ポイント：** Tier名だけでなく、`selected model / task / success / cost`をTelemetry化し、自社WorkloadでRouting Policyを検証します。

## 3. MCP：从Tool连接走向Long-running Task与Identity
**中文总结：**
- Keynote给出Claude累计约10亿MCP Tool Call、SDK月下载超5亿的生态规模。
- 下一阶段包括MCP Tasks、Skills over MCP、Identity / Authorization。
- Long-running Agent需要Cancellation、Timeout、Retry、Audit，不只是一次RPC。
- Roadmap内容必须和Current Spec分开管理。

**日本語の知識ポイント：** MCPの次の論点はConnectivityだけではなく、Task LifecycleとDelegated Identityです。

## 4. AI Infra：不是“脱Cloud”，而是Workload重新分配
**中文总结：**
- 1500人Survey中66％称把部分AI Workload从Public Cloud转到Private/On-prem。
- 95％经历过Governance/Compliance相关延期或取消，说明Data Architecture是AI落地瓶颈。
- Vendor Survey不能替代自己的TCO与SLO测量。
- Hybrid越普遍，跨环境一致Policy与Audit越重要。

**日本語の知識ポイント：** Cloud / On-premは思想ではなく配置Optionです。Data、Cost、Governance、SLOでWorkload単位に決めます。

## 5. アイカ工業：AI之前先统一企业Entity
**中文总结：**
- 表记摇摆、重复和更新遗漏会直接污染生成AI/BI的Source Data。
- Sansan Organization Code把不同System中的同一企业/事业所关联起来。
- Data Cleansing是AI Engineering的一部分，而非“以后业务再整理”。
- 当前Case没有量化AI精度提升，因此后续要测Entity Match、Freshness、Retrieval/Answer Quality。

**日本語の知識ポイント：** Model改善の前にMaster DataのEntity、Owner、Freshness、Source of Truthを確認します。

**当天语境：** MCP共同作者把它列为今后12个月的重点之一，用于让MCP Server作为长任务执行主体。

### C-2-6. Skills over MCP
**日本語：** MCP経由のSkill配布  
**中文：** 把Tool与Agent Skill打包并通过MCP Server提供的扩展方向。  
**当天语境：** 目标之一是建立统一的内部Skill Registry，而不依赖分散Marketplace；仍包含Roadmap性质。

### C-2-7. Hybrid-first architecture
**日本語：** ハイブリッド優先アーキテクチャ  
**中文：** 根据数据、成本、性能、合规把AI Workload分配到多种环境。  
**当天语境：** Cloudera调查显示企业并非简单全面回到On-prem，而是更重视跨Public/Private/On-prem的一致治理。

### C-2-8. Sansan Organization Code (SOC)
**日本語：** Sansan Organization Code  
**中文：** 为企业/事业所实体赋予统一识别码的机制。  
**当天语境：** Aica用SOC关联不同系统中的得意先/仕入先Master，减少表记摇摆带来的实体不一致。

### C-2-9. Data Cleansing
**日本語：** データクレンジング  
**中文：** 发现并修正重复、表记不一致、过期等数据质量问题。  
**当天语境：** Top 5把它作为生成AI/BI之前的基础工程，而不是把低质量Master直接交给模型补救。

## C-3. JLPT语法｜7个

### C-3-1. ～にとどまらず｜N1
**中文：** 不仅限于……，还扩展到更广范围。  
**接续：** 名詞 + にとどまらず / 動詞普通形 + にとどまらず  
**用法：** 用于说明能力、影响或课题超出原先范围。  
**例句：** MCPはTool接続にとどまらず、長期TaskやIdentityの設計へ広がっています。  
**中文例句：** MCP不仅限于工具连接，也正在扩展到长期任务和身份设计。  
**当天语境：** 适合今天Top 3的MCP演进语境。

### C-3-2. ～に応じて｜N2
**中文：** 根据条件或情况进行相应调整。  
**接续：** 名詞 + に応じて  
**用法：** 说明选择、配置、处理方式随条件变化。  
**例句：** Taskの複雑さに応じてCopilotのAuto Tierを選びます。  
**中文例句：** 根据任务复杂度选择Copilot Auto档位。  
**当天语境：** Model Routing面试高频表达。

### C-3-3. ～たうえで｜N2
**中文：** 在完成前项、确认前提后再进行后项。  
**接续：** 動詞た形 + うえで / 名詞 + のうえで  
**用法：** 强调先验证/确认，再做决策或执行。  
**例句：** Dataの所在と規制要件を確認したうえで、AI Workloadの配置を決めます。  
**中文例句：** 在确认数据位置和监管要求后，再决定AI负载部署。  
**当天语境：** 适合Enterprise Architecture判断。

### C-3-4. ～とは限らない｜N2
**中文：** 不一定……，用于限制过度一般化。  
**接续：** 普通形 + とは限らない  
**用法：** 指出某个观察结果不能无条件推广。  
**例句：** 静的Error率が低くても、Code全体が正しいとは限りません。  
**中文例句：** 即使静态错误率低，也不一定表示代码整体正确。  
**当天语境：** Top 1的重要Evidence Boundary。

### C-3-5. ～一方で｜N2
**中文：** 另一方面，用来并列相反或补充的情况。  
**接续：** 普通形 + 一方で / 名詞である + 一方で  
**用法：** 在技术说明中表达收益与代价、趋势与风险并存。  
**例句：** Hybrid構成は柔軟な一方で、Governanceを複雑にする可能性があります。  
**中文例句：** Hybrid架构很灵活，但另一方面也可能让治理更复杂。  
**当天语境：** 适合平衡架构讨论。

### C-3-6. ～ざるを得ない｜N1
**中文：** 由于客观条件不得不……。  
**接续：** 動詞ない形去ない + ざるを得ない（する→せざるを得ない）  
**用法：** 说明受成本、法规或系统限制而被迫选择某方案。  
**例句：** 規制上Public Cloudへ置けないDataは、別環境を選ばざるを得ません。  
**中文例句：** 因监管不能放到公有云的数据，不得不选择其他环境。  
**当天语境：** 企业合规语境常用。

### C-3-7. ～に伴って｜N2
**中文：** 随着某种变化，另一变化也随之发生。  
**接续：** 名詞 + に伴って / 動詞辞書形 + のに伴って  
**用法：** 描述AI利用扩大与治理、成本、基础设施变化之间的联动。  
**例句：** AI利用の拡大に伴って、Master Dataの品質管理も重要になります。  
**中文例句：** 随着AI使用扩大，主数据质量管理也变得重要。  
**当天语境：** 适合今天Top 4、Top 5的企业语境。
