# 🇯🇵 日本 IT / AI 日报｜2026年9月18日

本期以 **2026年9月17日10:00～9月18日10:00（日本时间）** 的新内容为中心。9月17日已经重点汇总的SmartHR Claude Code Harness、CyberAgent OpenTelemetry Tail Sampling、Cursor CVE、Lovable OJ与Gemini 3.8 Live均已排除。

今天五篇可以用一个词串起来：**Operational Contract**。Claude Code的MCP等待上限、RAG的增量索引规则、SOC Agent的调查与处置权限、Crawler的训练同意、分布式数据库的Router/Shard协议，都说明“能工作”之外还需要明确超时、身份、状态、证据与适用边界。

## 1. 今日最值得看的5篇

### 1. Claude Code v2.1.274 の主要アップデート - type: sdk の MCP 設定廃止と MCP 接続の安定化

**来源：DevelopersIO｜2026年9月17日**  
**原文 URL：** https://dev.classmethod.jp/articles/20260917-cc-updates-v2-1-274/

v2.1.274一共包含108项变化，其中MCP相关的启动等待与稳定性特别值得做CI/Batch Agent的人看。新环境变量 `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` 可以限制非交互Session第一轮等待MCP连接的时间；作者用一个启动后 `sleep 60`、实际上不说MCP协议的stdio Server做实验，再用 `--strict-mcp-config` 隔离自己的日常配置。4次平均结果是：没有MCP Server时3.6秒；有一个永远连不上的Server、未改默认值时33.4秒；把等待设为0时3.5秒。也就是说，最坏路径中约30秒来自连接等待，而不是Model本身。

版本还修复了Streamable HTTP MCP Tool即使配置较长timeout仍约5分钟中止的问题，以及MCP `${VAR}` Secret曾出现在连接错误/登录说明中的泄露路径；同时新增 `claude_code.managed_settings_resolved` OpenTelemetry Event与 `claude_code.llm_request` 的 `effort` 属性。**但是，**作者明确说明33.4→3.5秒是一个“连接永不完成”的最坏Case，不是所有MCP都能节省30秒；而且设置 `0` 可能使第一轮尚未拿到Tool。对于真实CI，更合理的是测自己的冷启动分布，再设数百毫秒或合适上限，而不是机械复制0。

**为什么值得看：★★★★★**  
它把MCP从“接上Tool”提升到Startup Budget、Timeout、Secret Handling与Telemetry的运行治理问题。

### 2. 自作RAGニュース検索をMCPサーバー化し、全記事再embedをChromaDBの差分更新に直した

**来源：Zenn｜2026年9月17日**  
**原文 URL：** https://zenn.dev/satoru_o/articles/014317b053f0aa

作者把AWS、Snowflake、dbt、Fivetran等RSS聚合成 `info-rag` MCP Server，供Claude Code自然语言检索。早期实现会在Server每次启动时抓取全部文章，再逐条调用Bedrock做Embedding；Source增加到7、8个后，同样几十篇文章会被反复Embed，启动越来越慢。后来改用 `chromadb.PersistentClient(path="./chroma_data")`，以文章URL为唯一ID，先 `_collection.get(ids=ids)` 取得已存在集合，只对新ID执行 `embed()` 后 `add()`，查询则使用 `_collection.query(..., n_results=top_k)`。这样Embedding成本与等待从“全部历史”缩成“自上次启动以来新增文章”。

这篇还有一个比Vector DB更值得注意的数据治理Bug：配置项叫 `dbt-fivetran-blog`，但实际URL只指向dbt Blog，让人误以为Fivetran Source已覆盖。作者后来把Fivetran RSS独立加入，并规定每加Feed都打开实际URL确认。**但是，**“URL作为ID + 只Add新ID”本身只能解决新增文章：同一URL的正文更新、Source删除、Canonical URL变化、Embedding Model换版都需要额外的Update/Delete/Re-index策略。文章是个人RAG工具的实现经验，没有给出并发写入、大规模Recall或Production SLO Benchmark。

**为什么值得看：★★★★★**  
这是一个很适合面试的RAG问题：优化Embedding调用之前，先定义Document Identity、Freshness、Update/Delete语义与Source of Truth。

### 3. 「AIがログを取りに行く」時代、SIEMは何のためにある？　Splunkの答え

**来源：＠IT｜2026年9月17日 15:00**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/17/news045.html

Cisco/Splunk在 `.conf26` 讨论的不是“AI替SOC写摘要”，而是Agent既成为新的监控对象，也进入调查和一次响应链。`Cisco Data Fabric powered by Splunk` 负责横跨Infrastructure、Application、AI的Telemetry/Data层，`Cisco Security Cloud Control` 则在其上把AI用于IT/Security操作。Demo中，SOC Analyst打开Console时，初动Agent已经查询不同Data Lake与第三方Tool并完成关联；Incident Response Agent继续切断被侵害的Identity Session、Rotation暴露Token，最后生成新的Control Policy，在Human Approval后应用，并用后续攻击测试验证阻断。

文章也提出一个重要变化：需要追踪Agent“参考了什么Data、调用了什么API、执行了什么Action”，而不只是传统Host/Network Log。Cisco还宣称Agent执行同样任务时可能使用比人多约450%的Network Bandwidth，2026年2月Agent Token Consumption超过人类并以约5倍速度增长。**但是，**这些数字与几分钟完成处置都来自Cisco/Splunk Keynote或Conference Demo，不是独立生产基准；企业落地时仍要验证False Positive、权限最小化、Policy Rollback、Audit Trail以及错误自动化造成的Blast Radius。

**为什么值得看：★★★★★**  
Agentic SOC的关键不是“更自动”，而是把Data、Decision、Action与Approval串成可审计的闭环。

### 4. AI学習は拒否、検索クロールは維持……Cloudflareの新機能「AI学習の不許可」　Google、Apple、Microsoftが対応

**来源：ITmedia AI＋｜2026年9月17日 15:19**  
**原文 URL：** https://www.itmedia.co.jp/aiplus/article/2609/17/2000001584/

Cloudflare推出 `Disallow AI Training`，目标是解决mixed-use crawler的Policy耦合：同一个Crawler同时承担Search Index与AI Training时，站点Owner过去若直接Block它，可能同时损失搜索流入。启用新设置后，Cloudflare会在站点 `robots.txt` 中写入“不允许训练”的规则；已经支持该约定的mixed-use crawler仍可为了Search继续抓取，但不应把内容用于AI Training。Apple和Google已经支持，Microsoft表示计划在2027年初前支持。

这里的核心不是“robots.txt突然变成强制法律边界”，而是用途级Consent能否被Crawler实现方遵守。OpenAI、Anthropic、Meta、Amazon因为搜索与训练Crawler本来就分开，可以只Block训练Crawler；Microsoft完全支持前，Bing相关场景仍可能需要HTML `NOARCHIVE` 等补充办法。**但是，**这是声明式Policy与合作方支持机制，不是Cryptographic Enforcement；站点Owner仍要检查实际Bot行为、Crawler Identity、日志与各Vendor支持状态，不能把“写了规则”直接等同于“所有AI系统都没有训练”。

**为什么值得看：★★★★★**  
它把Web数据治理从“允许/拒绝一个Bot”细化为Search、Training、Agent三类用途的Policy设计。

### 5. PlanetScale、PostgreSQLのシャーディングを自動化して1億1800万QPSを達成。新DBサービス「Neki」をプレビュー公開

**来源：Publickey｜2026年9月18日**  
**原文 URL：** https://www.publickey1.jp/blog/26/planetscalepostgresql11800qpsdbneki.html

PlanetScale预览的新服务 `Neki` 试图把Vitess式Scale-out思路带到PostgreSQL。Client继续使用标准Postgres Protocol和已有Driver/Tool，但连接入口变成可水平扩展的 `Neki Router`；Router包含Postgres Query Parser、Distributed Query Planner和Query Buffering，决定Query去哪个Shard执行，再聚合结果返回。每个Shard本身仍是PostgreSQL，配置一个Primary和至少两个Replica并分布在不同Availability Zone；旁边还有Connection Pooling Sidecar与负责Node State、Re-sharding、Schema Change、Failover的Control Plane。系统可以先从单Primary/Replica开始，真正需要时再进入Sharding。

PlanetScale公布的Benchmark是约 **1.4PB、512 Shard、最大1亿1875万QPS（118,538,803 QPS）**，并称随Shard增加性能接近线性提升。这个数字非常醒目，但**但是，**Neki目前仍是Preview，而且这是Vendor Benchmark；文章没有给出你自己的Join/Transaction分布、Cross-shard Query代价、P99 Latency、Re-sharding期间的SLO或TCO。因此架构选择不能只看QPS峰值，还要用实际Schema与Query Pattern测试兼容性、Failure Recovery和Cost。

**为什么值得看：★★★★★**  
它适合用来回答“什么时候才值得Sharding”：应从单库开始，把Router/Control Plane的复杂度留到容量与业务真正需要时再引入。

### 🤖 AI / Agent
Claude Code与Splunk的共同点是：Agent运行时必须有明确的等待上限、可观察事件、身份与处置边界。Agent能力越大，越不能只观察最终文本。

### 💻 Frontend / Web
今天没有React/Next.js专文进入Top 5，但Cloudflare的Crawler Policy直接影响Web内容如何被Search和AI Training使用。Frontend/Web工程师也需要理解robots.txt、Crawler用途与声明式Policy的边界。

### ☁️ Cloud / Backend
Zenn的RAG差分Index与Neki的Sharding都在解决“规模增长后不能继续全量处理”的问题：一个把Embedding从全量变增量，一个把单Postgres扩成Router+Shard+Control Plane。

### 🏢 日本企业 Tech / Security
＠IT的Splunk现场报道显示，日本企业面试里讨论Agentic Security时，值得说清楚的不是“AI会查Log”，而是Data Fabric、Agent Action、Approval、Audit与Rollback如何组成闭环。

## 3. 面接で使えるポイント

### 1. Claude Code v2.1.274

**面试问题：**

> Claude CodeをCIからHeadless実行するとき、MCPの起動待ちをどう設計しますか。

**约30秒回答：**

> 非対話のClaude Codeでは、MCP接続待ちを固定の前提にしません。v2.1.274ではCLAUDE_CODE_MCP_STARTUP_WAIT_MSが追加され、記事の4回平均では接続しないMCPありで33.4秒、0指定で3.5秒でした。ただし0では最初のTurnにToolが揃わないため、CIでは実測して必要な上限値を置きます。

**可关联项目：** Claude Code / CI / MCP Platform  
**日语技术关键词：** 起動待ち / 非対話Session / 実測上限

### 2. ChromaDB差分RAG

**面试问题：**

> RSS型RAGをMCP化するとき、Embeddingの更新をどう設計しますか。

**约30秒回答：**

> RAGの更新単位を記事ごとにします。記事ではURLをIDにし、ChromaDBのPersistentClientで既存IDをgetし、新規記事だけBedrockでembedしてaddしました。これで起動ごとの全件再embedを避けられます。ただしURLが変わらない本文更新や削除はこの方式だけでは拾えないので、更新検知を別に設計します。

**可关联项目：** RAG / MCP / Vector Database  
**日语技术关键词：** 差分同期 / Document Identity / 更新検知

### 3. Agentic SOC

**面试问题：**

> AIエージェントをSOCへ組み込む場合、どこまで自動化しますか。

**约30秒回答：**

> AIエージェントをSOCへ入れるなら、判断だけでなく行動のTraceを残します。.conf26のDemoではCisco Data Fabricから複数Data Lakeを照合し、侵害Sessionの切断とToken RotationまでAgentが一次対応しました。ただしConference Demoなので効果を一般化せず、Policy適用はApprovalとAudit LogをGateにします。

**可关联项目：** SIEM / SOC / AI Agent / Security  
**日语技术关键词：** 一次対応 / 監査証跡 / Policy適用

### 4. Cloudflare AI Training Policy

**面试问题：**

> 検索Crawlerを残しながらAI学習を拒否したい場合、何を確認しますか。

**约30秒回答：**

> Webの検索流入とAI学習の許可を同じ設定にしません。CloudflareのDisallow AI Trainingはrobots.txtへ学習拒否Ruleを書き、対応するmixed-use crawlerでは検索を継続できます。GoogleとAppleは対応済みですが、Microsoftは2027年初頭予定なので、Crawlerごとの対応状況とNOARCHIVEなどの補助手段を確認します。

**可关联项目：** Web Governance / Cloudflare / SEO  
**日语技术关键词：** mixed-use crawler / 学習拒否 / 対応状況

### 5. PlanetScale Neki

**面试问题：**

> PostgreSQLのSharding基盤を採用するとき、Benchmarkをどう評価しますか。

**约30秒回答：**

> PostgreSQLをShardingするなら、互換性と運用面を分けて評価します。Nekiは標準Postgres ProtocolのままNeki RouterがQueryを各Shardへ分配し、512 Shard・約1.4PBで最大1億1875万QPSを公表しました。ただしPreviewのVendor Benchmarkなので、実WorkloadではCross-shard Query、Failover、Costを別に測ります。

**可关联项目：** PostgreSQL / Distributed Database / Cloud  
**日语技术关键词：** Sharding / Query Router / Vendor Benchmark

## 4. 今日の技術テーマ：Operational Contract

今天五篇的共同结构是：

```text
Capability
   ↓
Operational Contract
├─ Startup / Timeout
├─ Identity / Freshness
├─ Permission / Approval
├─ Policy / Consent
└─ Scale / Failure Boundary
   ↓
Evidence & Telemetry
   ↓
Commit / Action
```

Claude Code需要定义“最多等MCP多久”；RAG需要定义“什么算同一Document、什么时候重新Embed”；Agentic SOC需要定义“Agent可以调查到哪里、哪一步必须Human Approval”；Cloudflare需要定义“Search和Training是否分别授权”；Neki则需要定义“什么时候从单库升级到Sharding，以及Benchmark在哪些条件下成立”。这类Contract的优点是Model或Tool可替换后，运行边界仍能保留。

局限在于Contract本身也可能过时或漏项。`WAIT_MS=0`会让Tool尚未就绪，URL ID无法发现同URL内容改变，robots.txt依赖Crawler遵守，Vendor Benchmark无法代表企业Query Pattern。因此日本企业落地时，建议给每个AI/Cloud Workflow记录 **Source of Truth、Timeout、Permission、State Transition、Evidence、Rollback Owner**，并让Production Failure持续反哺Contract。

## 5. 面试复习卡

**Q1：** Claude CodeのMCP起動待ちを0にすれば常に速くなりますか。  
回答要点：Headless限定 / `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` / 33.4秒→3.5秒是最坏Case实测 / Tool可能首轮未就绪 / 应按自家CI测分布。

**Q2：** RAGの差分更新でURLをIDにする場合、どんな更新を取りこぼしますか。  
回答要点：同URL正文变更 / 删除 / Canonical变化 / Embedding Model版本 / 需要Hash或Updated-at与Delete/Re-index策略。

**Q3：** Agentic SOCでHuman Approvalを残すべき箇所はどこですか。  
回答要点：调查与Evidence收集可自动化 / Credential或Session处置需Policy / 新Control Policy应用要Approval、Audit、Rollback。

# B. 重点总结和面试可用知识点

### 1. Claude Code v2.1.274
**中文总结：** MCP Startup Wait已经成为Batch Agent的Latency Budget；v2.1.274还把Secret泄露、长MCP Tool Timeout和Managed Settings Telemetry一起补强。  
**日本語の知識ポイント：** `CLAUDE_CODE_MCP_STARTUP_WAIT_MS=0` は万能ではなく、最初のTurnでToolが揃う必要があるかを基準に上限を決めます。

### 2. ChromaDB差分RAG
**中文总结：** URL ID + PersistentClient + get/add把全量Embedding改为增量，但Document Update/Delete必须单独建模；Source名称与实际Feed URL也属于RAG Quality。  
**日本語の知識ポイント：** Vector DB導入より先に、Document IdentityとFreshness、Delete/Re-indexの条件を決めます。

### 3. Splunk / Cisco Agentic SOC
**中文总结：** AI Agent既是监控对象，也是SOC执行者；要记录其Data Reference、API Call和Action。Conference Demo展示了跨Data Lake调查、Session切断、Token Rotation与Policy Proposal。  
**日本語の知識ポイント：** 自動化範囲を「調査」「一次対応」「Policy変更」に分け、最後のCommit権限とAuditを別に設計します。

### 4. Cloudflare Disallow AI Training
**中文总结：** Search与Training Consent可分离，但效果依赖Crawler Vendor支持；Google/Apple已支持，Microsoft存在到2027年初的过渡期。  
**日本語の知識ポイント：** robots.txtは宣言的Policyなので、Crawler Identityと実際のAccess Logも確認します。

### 5. PlanetScale Neki
**中文总结：** Postgres兼容入口后面加入可扩展Router、Shard Replica、Sidecar与Control Plane；512 Shard的1.4PB/1.1875亿QPS是Vendor Benchmark而非业务SLO。  
**日本語の知識ポイント：** ShardingはQPSだけでなくCross-shard Query、Failover、Re-sharding、Costを実Schemaで評価します。
