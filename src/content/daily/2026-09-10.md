### ① AI に実装を任せるための仕様と検証ループ 〜ProxySQL に足りない機能を実装で埋めた〜 [DeNA インフラ SRE]

**来源：DeNA Engineering｜2026年9月9日**  
**原文 URL：** https://engineering.dena.com/blog/2026/09/spec-and-verify-loop-proxysql-eks/

DeNA 的基础设施 SRE 团队把 2022 年运行在 EC2 上的 ProxySQL 迁到 EKS。原本希望直接使用 ProxySQL 的 `mysql_aws_aurora_hostgroups` 自动发现 Aurora Writer / Reader，但 EKS 与 Aurora 跨 VPC Peering 时，`check_timeout_ms` 频繁超时，健康 Reader 会长期停在 `SHUNNED`，甚至有非预期 Host 进入 hostgroup。团队于是用 Go 自己实现 Kubernetes Controller“Manager”，周边实现约 **1 万行、145 commits、约 2.5 个月**。AI 负责实现和 Test 执行，人负责决定“什么是正确”、解释结果，再把结果写回下一版规格。这里的关键不是 AI 写了多少 Code，而是把 AI 的职责限定在可验证实现上。 

验证系统比实现更有价值。团队先做 `k6 + xk6-sql + MySQL driver` 的负载 Image，再通过 **Argo Workflows** 在 Cluster 内启动；Scenario 可同时对 3 个 AZ 加压，并触发 Reader 新增、Failover、Pod Stop。合格阈值写成 **连接错误率 <5%、Query 错误率 <1%**，Query Duration / Error Rate 按 AZ 送进 Prometheus。Manager 用 RDS API 发现实例，通过 ProxySQL Admin API 更新 `mysql_servers`；全量同步 10 秒一次，Writer 判定单独 2 秒一次，新 Reader 则先以 weight 0 加入，再每 60 秒加 5。也就是说，Specification 本身同时定义了 Implementation 与 Verification Contract。 

Production 前又在 3 AZ 下施加超过生产 Peak **2 倍**的 Query，并通过 Route53 Weighted Routing 按 **1%→10%→50%→100%** 切流。迁移后 Instance Cost 月度约降低 **80%**，DB Read 的 cross-AZ 比例从 **65% 降到 31.5%**；Leader Election 正常交接约 1 秒，Crash 场景约 15 秒。**限制 / Evidence Boundary：** 这些是 DeNA 自己这个 ProxySQL / Aurora / EKS Workload 的实测，并非通用 Benchmark；作者也明确说明规格要写到多细取决于 Model 与环境。后来 Node Kernel Table 使用率接近 90% 的问题也不是 AI 发现的，而是 Monitoring 暴露的，自研 Controller 还意味着长期维护责任留在团队。 

**为什么值得看：★★★★★**  
它把“AI Coding”升级成了 **Specification → Implementation → Failure Injection → Measurement → Next Specification** 的闭环。日本 SRE / AI Engineering 面试里，这比“我会用 Claude Code”更能体现工程能力。 

### ② AWS、AIがフルスタックAWSアプリの基本コードを、セキュリティ、可観測性、インフラまで一気通貫で生成する「Nx Plugin for AWS 1.0」、オープンソースで公開

**来源：Publickey｜2026年9月10日**  
**原文 URL：** https://www.publickey1.jp/blog/26/awsaiawsnx_plugin_for_aws_10.html

AWS 开源了 `Nx Plugin for AWS 1.0`。给出 Application Requirement 后，AI 可以组合合适的 AWS Service，生成 **AWS CDK 或 Terraform** 的 Infrastructure Code，同时生成 Backend / Frontend 的 Application Scaffold。Publickey 转述的官方 Demo 中，先建立 Workspace，再指定 **React Web、AG-UI、MCP Server、DynamoDB**，随后工具生成对应代码。文章还把 X-Ray、CloudWatch、Firewall、Amazon Bedrock AgentCore、TypeScript / Python Framework 与 API 放在可生成的同一 Full-stack Context 中。 

它的工程意义不是“一次多生成几个文件”，而是让 Application、Infrastructure、Security 与 Observability 从同一个 Requirement 出发，减少 Full-stack Bootstrap 阶段跨 IaC、Backend、Frontend 的人工拼接。生成后的 Scaffold **不再依赖 Nx Plugin for AWS**，可以自由修改，因此更像 Architecture Bootstrap，而不是一个必须长期驻留的 Runtime。对 React / TypeScript 工程师来说，这意味着 AI-assisted Frontend 已开始和 Agent Protocol、Data Store、IaC、Telemetry 一起初始化。 

**限制 / Evidence Boundary：** 当前证据是 AWS 官方 Announcement / Demo 经 Publickey 报道。“数分钟生成”是 Scaffold 生成速度，不是 Production TCO、IAM 正确率、复杂 Monorepo 迁移或长期维护性的 Benchmark。Production 使用前仍要 Review IAM Least Privilege、Network Boundary、X-Ray / CloudWatch Telemetry、Terraform / CDK State、Test Strategy 与 Environment Difference。 

**为什么值得看：★★★★★**  
它适合回答“AI 怎样帮助 React / AWS 全栈开发”：不是把 AI 当 Component Generator，而是**建立 Application + IaC + Observability + Agent Integration 的共同 Scaffold，再由 Engineering Gate 接管质量责任。**

### ③ NEC、社内の“AIトークン節約”に注力　「同じ使われ方なら10分の1に」と小玉CAXO

**来源：ITmedia AI＋｜2026年9月10日 06:55**  
**原文 URL：** https://www.itmedia.co.jp/aiplus/article/2609/10/2000001333/

NEC CAXO 小玉浩在 9 月 9 日说明会中给出了一个很容易被误读的目标：以 2026 年 4 月内部 AI 利用状况为基准，如果“使用方式相同”，希望上半年把**实质 Token Cost 降至 1/5**，下半年降至 **1/10**。NEC 同时预计 AI 利用量本身还会增长，所以这并不是“公司绝对 AI 账单下降 90%”的承诺，而是在同等使用模式下提高单位效率。小玉氏的逻辑是，只要 AI 使用增加带来的 Performance / Output 能够回收成本，绝对使用量增长本身不是问题。 

具体手段不是单纯压缩 Prompt。NEC 正在做 Task-based **Model Routing**，把处理振り分け到更合适的 Model；区分 Frontier Model 与 Open-weight Model；对部分过去输入使用 **Cache**；同时整理 Task 执行时参考的 **Context Data**，也考虑固定收费型 Service。这里已经是 Routing + Caching + Context Engineering + Pricing Model 的组合式 AI FinOps。组织上，NEC 在 8 月 1 日设立 Corporate AI・Workforce 部门，目标是向 AI Native Company 迁移。 

**限制 / Evidence Boundary：** 1/5 与 1/10 是公开的**目标值**，不是已经完成的实测 Cost Reduction；Comparison 还带有“4 月相同使用方式”的条件。因为 Usage 本身预计增长，所以评价时需要同时看 Task Success、Output / Productivity、Quality、Latency、Human Time 与 Cost-per-Outcome，不能只看总 Token Spend。 

**为什么值得看：★★★★★**  
面试中可把“AI 成本优化”从“选择便宜模型”提升为 **Model Routing + Cache + Context Quality + Open-weight + Business Outcome** 的系统问题。

### ④ 電通など3社、広告コピーをAIが自動評価　コピーライター64人・11万件超の評価データを構築

**来源：Ledge.ai｜2026年9月9日**  
**原文 URL：** https://ledge.ai/articles/dentsu_ai_ad_copy_evaluation

Ledge.ai 报道了电通、电通 Digital 与 SB Intuitions 的共同研究。三家公司让电通 **64 名 Copywriter** 按统一标准评价 AI 生成的日文广告 Copy，累计构建 **116,532 件**评价数据；同时通过 Expert Interview 把资深 Copywriter 的判断过程显式化，整理成「ファースト・インパクト」「インサイトの深さ」「言葉選びの妥当性」等评价维度。这一步非常关键：不是先让 LLM 自己发明 Rubric，而是先把 Domain Expert 的隐性标准变成结构化 Evaluation Asset。 

研究再使用部分专家评价数据，并把 Copywriter Criteria 编进 Prompt，验证 **LLM-as-a-Judge**。电通与 SB Intuitions 的一次资料显示，在参与学习 / 优化的行业与商品类别上，AI Judge 与 Human Evaluation 出现“一定程度的正相关”；但对**未学习的行业 / 商品**，相关性会下降。研究还使用 SB Intuitions 的日本语 Native Model `Sarashina`。这意味着 Judge 不能只问“整体相关性高不高”，还要问“在哪个 Domain 校准、换 Domain 后是否仍可靠”。 

**限制 / Evidence Boundary：** 116,532 是 Evaluation Records 数量，不等于 116,532 个完全独立创意；公开资料也没有给出跨全部行业都稳定的统一 Correlation。相反，unseen Domain 相关性下降正是研究明确暴露的限制，因此 Production LLM-as-a-Judge 需要 Human Calibration Set、Domain Slice、定期 Re-score 与 Judge Version Regression。 

**为什么值得看：★★★★★**  
这是日本企业中很具体的 Domain-specific Evaluation 案例：**专家 Rubric → Label Data → LLM Judge → unseen Domain 验证**，比单纯使用通用 Judge 分数更接近真正 LLMOps。

### ⑤ 「四半期ごとのパッチ適用」はもう許されない　AWSが「フロンティアAI対策9項目」のポイントを解説：「能動的なサービス停止」の基準を明確化する

**来源：＠IT｜2026年9月9日 11:30**  
**原文 URL：** https://atmarkit.itmedia.co.jp/ait/articles/2609/09/news043.html

金融厅与日本银行在 2026 年 5 月 22 日提出 Frontier AI 威胁变化下的 9 项短期应对，AWS 随后整理了自家 Service 可以怎样支撑。背景数字很强：2025 年公开 CVE **48,185 件**，同比约 +20%；Anthropic `Project Glasswing` 合作组织使用 Claude Mythos Preview，一个月发现超过 **10,000 个 High / Critical Vulnerabilities**；Amazon Threat Intelligence 观察到公开 Exploit 从 Disclosure 到 Weaponization 已缩短到**数小时～数日**。不过英国 AISI 同时指出，Frontier AI 不一定能突破防御充分的 IT System，所以基本 Security Hygiene 并没有失效。 

AWS 把动作归纳为 Governance / External Collaboration、Asset Visibility / Technical Debt、Patch Automation / Risk Prioritization、Assume-breach / BCP 等。Patch 不能继续只按季度批处理，而应结合 CISA **KEV** 与 **EPSS** 动态决定 Priority；WAF / IPS Virtual Patch 只适合临时缓解。`AWS Continuum` 则持续执行 Discover → Prioritize → Validate → Remediate，在 Sandbox 中验证 Exploit；文章建议从 **learn mode + Human Approval** 起步，再逐步进入 **enforce**。AWS Security Agent 也已成为 Continuum 的一部分。 

**限制 / Evidence Boundary：** AWS 自己明确强调，**采用 AWS Service 并不等于自动满足金融厅 / 日银的 9 项要求**，最终风险评价、控制、停服判断仍由金融机构自己承担。若要“主动停止服务”，组织还必须预先定义 Shutdown Criteria、Communication、Fallback、BCP，并准备 Air-gapped Backup 等恢复措施。因此真正要改变的是 Decision Latency 与 Operating Model，而不是把 Security Responsibility 外包给 AI Tool。 

**为什么值得看：★★★★★**  
非常适合 Security / SRE 面试：从 Calendar-based Patch 转成 **KEV/EPSS 驱动的 Risk-based Continuous Remediation**，再把 Human Approval、learn→enforce、主动停服标准和 BCP 连成 Operational Loop。

## 4. 今日の技術テーマ

### Verification Contract：AI 能做多少，取决于你能验证多少

今天最值得带进面试的核心主题是 **Verification Contract**：不是某个 Vendor Feature，而是把“AI 看起来能做”变成“AI 的结果可验收”的方式。

```text
Requirement / Risk
        ↓
Observable Contract
├─ Pass / Fail Threshold
├─ Test / Failure Injection
├─ Cost / Quality Metric
├─ Domain Boundary
└─ Rollout / Stop Rule
        ↓
AI Implementation / Evaluation
        ↓
Evidence
        ↓
Human / Policy Decision
```

DeNA 把连接错误率 <5%、Query 错误率 <1%、3 AZ Failure Injection 和 Route53 1→10→50→100% 切流写成 Contract；Nx Plugin for AWS 生成 Scaffold 后，真正 Contract 来自 IAM、Test、Telemetry 与 IaC Review；NEC 的 1/10 只有放在“同样使用方式”的 Comparison Condition 下才有意义；电通用专家 Label 与 unseen Domain 检查 Judge 边界；AWS Security 则把 KEV / EPSS、learn→enforce 与 Service Stop Criteria 变成 Operational Gate。

**优点：** 可以把主观的“AI 输出不错”转换成重复可跑的 Evidence；Model / Tool 更换后仍能重跑同一 Gate；Human Review 集中在规格、Domain Shift、停服等难以自动判断的边界；Cost 与 Security 也能像 Functional Test 一样进入 Release Decision。

**局限：** Contract 只验证你写进去的东西。DeNA 后来接近 90% 的 Kernel Table 使用率就是典型反例：原来的 App 指标正常，如果没有 Node-level Monitoring，既有测试不会主动发现。LLM-as-a-Judge 也会出现 seen Domain 很好、unseen Domain 下降。因此 Verification Set、Observability 与 Risk Model 要从 Production Failure 持续更新，不能一次写完就冻结。

**日本企业落地注意点：** 建议先挑一个可量化 Workflow，明确 Owner、Source of Truth、Pass / Fail、异常注入方式、Cost KPI、Human Approval 与 Rollback。PoC 后用 Staged Rollout；AI Cost 同时看绝对费用与 Cost-per-Outcome；Judge 保留 Human Calibration；Security Automation 从 learn 起步，并先写清主动停服权限与 BCP。

面试可总结为：

> AIに実装や評価を任せる場合、Modelの能力だけでなく、何を正解とするかをPass / Fail条件として先に定義し、実測・Failure Injection・段階Rolloutで検証できるContractを作ることが重要だと考えています。

# B. 重点总结和面试可用知识点｜重要ポイントと面接で使える知識

## 1. AI に実装を任せるための仕様と検証ループ
**中文知识点总结：** AI 最适合接手“合格条件写得清楚”的实现；`xk6-sql + Argo Workflows` 把 3 AZ Failure Injection 与 Error Threshold 变成可重复测试；Route53 1%→10%→50%→100% 是 Production Gate；自研 Controller 降低既有功能不确定性，却增加维护责任。

**日本語の知識ポイント：** AIへ実装を委譲する前に、要件と確かめ方を同じ仕様へ書きます。xk6-sql / Argo WorkflowsでFailure InjectionとError Rateを再現し、本番では段階Routingで切り替えます。AIが見つけないRiskを前提にObservabilityも別Layerで持ちます。

## 2. Nx Plugin for AWS 1.0
**中文知识点总结：** Scaffold 已扩展到 React、AG-UI、MCP、DynamoDB、AWS CDK / Terraform 与 Observability；生成后不依赖 Plugin，意味着自由度和团队责任同时增加；“数分钟”是 Bootstrap Speed，不是 Production Benchmark。

**日本語の知識ポイント：** Full-stack ScaffoldはFrontendだけでなくIaC、Agent Integration、Observabilityまで含みます。生成後にPlugin依存が残らない一方、IAMやState、TestのReview責任はDeveloper側へ戻ります。

## 3. NEC、社内の“AIトークン節約”
**中文知识点总结：** 1/5、1/10 都是在“4 月同等使用方式”前提下的效率目标；手段包括 Model Routing、Frontier / Open-weight、Cache、Context Data；Usage 预计增长，因此应评价 Cost-per-Outcome 而非只看账单。

**日本語の知識ポイント：** 5分の1・10分の1は4月と同じ利用Patternを仮定したEfficiency Targetです。Model Routing、Open-weight、Cache、Context Dataを組み合わせ、請求額だけでなくOutputやHuman Timeも見ます。

## 4. 電通など3社、広告コピーをAIが自動評価
**中文知识点总结：** 64 名专家与 116,532 条评价把隐性创意标准结构化；Rubric 包括 First Impact、Insight Depth、Word Choice Validity；已学习 Domain 相关性较好但 unseen Domain 下降，Judge 必须重新 Calibration。

**日本語の知識ポイント：** 64名・116,532件の評価DataでCopywriterの暗黙基準をRubricへ変換しました。学習済みDomainでは一定の相関が出ても、未学習Domainでは低下するためHuman Calibrationを残します。

## 5. フロンティアAI対策9項目
**中文知识点总结：** Exploit 速度进入小时～天级后，季度 Patch 会形成过长 Exposure Window；KEV / EPSS 用于 Risk-based Prioritization；AWS Continuum 从 learn + Human Approval 逐步到 enforce；AWS Service 不替代金融机构自己的停服与 BCP 决策。

**日本語の知識ポイント：** Vulnerability対応はQuarterly BatchからKEV / EPSSを使うRisk-based Operationへ変えます。Virtual Patchは暫定策で、ContinuumはlearnからHuman Approvalを挟み徐々にenforceへ進めます。Stop CriteriaとBCPは組織が決めます。

**用法：** 强调验证 Scenario 范围。  
**例句：** Reader追加からFailover、Pod停止に至るまで同じScenarioで検証します。  
**中文：** 从 Reader 新增到 Failover、Pod Stop 都在同一 Scenario 验证。  
**语境：** 对应 Top 1。

### 4. ～たうえで
**参考等级：** N2  
**中文：** 做完……并以此为基础再……  
**结构：** `動詞た形 + 上で / 名詞 + の上で`  
**用法：** 先验证再做技术决策。  
**例句：** Human Evaluationとの相関を確認したうえで、LLM-as-a-Judgeを運用Gateに使います。  
**中文：** 确认与 Human Evaluation 的相关性后再使用 Judge。  
**语境：** 对应 Top 4。

### 5. ～に応じて
**参考等级：** N2  
**中文：** 根据……相应调整  
**结构：** `名詞 + に応じて`  
**用法：** Routing / Policy 的动态选择。  
**例句：** Taskの難易度に応じてFrontier ModelとOpen-weight Modelを使い分けます。  
**中文：** 根据 Task 难度区分 Model。  
**语境：** 对应 Top 3。

### 6. ～一方で
**参考等级：** N2  
**中文：** 另一方面……  
**结构：** `普通形 + 一方で`  
**用法：** 表达 Usage Growth 与 Efficiency 的两面性。  
**例句：** AI利用量は増える一方で、同じ使い方なら実質Token Costを下げる目標です。  
**中文：** AI 用量会增加，但同等用法下目标是降低实质成本。  
**语境：** 对应 Top 3 的 Evidence Boundary。

### 7. ～とは限らない
**参考等级：** N2  
**中文：** 不一定……  
**结构：** `普通形 + とは限らない`  
**用法：** 限制过度一般化。  
**例句：** 学習済み業種で相関が高くても、未学習業種で同じ結果になるとは限りません。  
**中文：** 已学习行业相关性高，也不表示未学习行业相同。  
**语境：** 对应 Top 4。
