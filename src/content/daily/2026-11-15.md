### 1. Undoした「水曜は出社」が、共有予定に残る理由

**原文：** https://zenn.dev/honabochi/articles/family-newspaper-shared-week-undo

**发布时间：** 2026-11-15 09:45:32 JST

家庭报纸的编辑器保存两套状态：每期拥有一份周计划副本，新一期从共享计划复制初始值，日别编辑保存时也能改写共享计划。场景中周一把星期三改为出社，经过周二另一次编辑并采纳后，共享计划还加入了星期四休息。

撤销先把周一期恢复到原先版本。共享侧只有当前周表和采纳标志都等于这笔操作写入后的 sharedAfter 时，才会回到 sharedBefore。周二已把状态从 B、未采纳改成 C、已采纳，因此周四休息和周三出社都保留在共享侧。即使周表仍是 B，后来单独完成采纳也会阻止回滚。

作者用公开 JavaScript 模型演示，条件是两个虚构的排班字段，周一没有插入别的保存。把周三单独改回去会产生一个未取得采纳的新组合，可能还涉及午餐人数。提示用户共享状态仍保留、让用户重新采纳变更等都是改进提案，尚未实现。

**阅读价值：** 把撤销的影响范围落实到状态比较，可以判断是否会误删另一个用户随后确认的操作。

### 2. 429 を受けてからでは遅い — 外部プロバイダへの送信レート制御を再試行の増幅率で比較する

**原文：** https://zenn.dev/kyrenzk/articles/messaging-send-rate-control-design

**发布时间：** 2026-11-15 08:57:42 JST

作者用 Go 1.24.7 和 Linux x86_64 上的虚拟时钟模拟并发发送。50 个串行处理各自任务的工作单元合计送 1,000 件，模拟服务在每秒固定窗口内放行 100 个请求。比较固定十毫秒重试、带 Full Jitter 的指数退避、遵循 Retry-After，以及共享令牌桶。

固定间隔共发出 45,950 次请求，按虚拟时钟计算，9.01 秒送完。只按 Retry-After 等待共发出 1,450 次；每秒放行 90 次、突发容量为 5 的共享令牌桶只发出 1,000 次，完成用时 11.06 秒。作者以实际请求总数除以消息数来量化重试放大。

实验条件只有一组工作单元和速率参数，固定随机种子能复现输出。模拟没有触达真实供应商。滑动窗口、多进程配额和不同突发容量均未测量；真实应用还应测量端到端延迟和丢弃，并遵守供应商容量约定。

**阅读价值：** 把 429 数量与完成时间并列，显示发送前节流能换来多少请求量的减少。

### 3. TypeScriptのnoUncheckedIndexedAccessで配列・辞書のundefined事故を防ぐ

**原文：** https://zenn.dev/sponge841841/articles/2026-11-06-typescript-no-unchecked-indexed-access

**发布时间：** 2026-11-15 09:01:51 JST

在 TypeScript 里，库存若声明成 Record<string, number>，任意字符串下标看起来都能返回数字。JavaScript 读取未登记的商品键时却会给 undefined，直接调用 toFixed 会异常。作者在 TypeScript 5.8.3 与 Node.js 22.16.0 上检查这一差异。

给 strict 配置加上 noUncheckedIndexedAccess，字典任意键的读取就会带上 undefined。先检查缺失，再处理价格为零或库存数量为零的合法值。数组若只需要元素，可以直接用 for...of 避免下标；确实需要下标时，可在读取后确定值是否存在。

显式声明的必填属性仍维持其类型。但选项提供的是编译期提示，无法替代请求输入校验或数据库并发控制。原文展示的是单进程库存样例；对价格不明的商品补成零会改变业务含义。

**阅读价值：** 从字典类型提示追到业务分支，能说清楚“缺失”和“有值为零”的区别。

### 4. 欠けている値は「捨てる」か「埋める」か：小さい町村だけ値がない持ち家率で、扱い方を比べたときに何を決めて何を確かめたか

**原文：** https://zenn.dev/takayuki0127/articles/7ee036279243fc

**发布时间：** 2026-11-15 07:31:56 JST

作者比较市区町村的住房自有率和儿童妇女比。1,734 个地区中有 619 个缺失住房自有率，集中在小人口地区。以人口的对数帮助插补，作者生成 20 组填补数据再合并估计。自有率每增加十个百分点，对应的回归系数在完整样本是 −6.6，含结果变量的多重插补是 −9.7。

模拟用 1,115 个记录完整的地区作参照，按四种机制删除约 35% 的记录，重复 100 次。小地区更容易缺失时，完整案例偏差为 −2.8，多重插补为 −4.2。小地区与大地区的拟合关系不同，而统一模型会把有观测的关系外推给缺少观测的小地区。

比较的局限是，原始资料中缺失地区的真值未知，部分填补得到超过 100% 的比例，可作为模型外推的诊断信号。模拟以原本完整的地区作为参照，不能验证真正缺失的地区。研究只比较同一时点的地区，不能用来断言住房拥有率导致儿童数量变化。

**阅读价值：** 用参照真值的模拟拆解模型偏差，并说明为何真实缺失样本无法给出同样的证明。

### 1. Undoした「水曜は出社」が、共有予定に残る理由

**面试问题：**

> 月曜号を Undo しても共有予定の水曜が戻らないのはなぜですか。

**约30秒回答：**

> 月曜号は保存前に戻しますが、共有側は週表と採用フラグの両方を sharedAfter と比べます。火曜号が木曜の休みを追加して採用した後は、条件が合わないので共有予定を残します。水曜だけを戻すと、まだ誰も採用していない組合せになります。その案を見せて採用し直す操作は、記事では未実装です。

**相关项目例：** 构造两期的保存记录，分别测试后续修改内容和仅修改采纳标记的情形。

**关键词：** Undo、sharedAfter、採用フラグ

### 2. 429 を受けてからでは遅い — 外部プロバイダへの送信レート制御を再試行の増幅率で比較する

**面试问题：**

> Retry-After と毎秒90件の共有トークンバケットを、なぜ別々に計測したのですか。

**约30秒回答：**

> Retry-After は拒否された後に待つ方法です。実験では再試行が四百五十回残りました。毎秒九十件の共有トークンバケットは先に流量を絞るので、千件を千回で送れました。一方で、完了に約二秒多くかかりました。ただし、固定ウィンドウでの結果なので、別の制限方式でも同じ比率になるとは限りません。

**相关项目例：** 用本机模拟服务比较发送前排队和拒绝后退避，记录 429、放大率和所有任务完成时间。

**关键词：** Retry-After、共有トークンバケット、固定ウィンドウ

### 3. TypeScriptのnoUncheckedIndexedAccessで配列・辞書のundefined事故を防ぐ

**面试问题：**

> Record<string, number> の在庫で、noUncheckedIndexedAccess を加えたら何を確認しますか。

**约30秒回答：**

> Record で任意のキーを引くと、未登録でも number と扱われる場合があります。noUncheckedIndexedAccess を有効にすれば、読み出した値は undefined の可能性を持ちます。未登録だけを分けて、ゼロは有効な在庫として残します。添字が要らなければ、配列の要素を直接読みます。ただし、実行時の入力検証や、同時購入での在庫更新は別に確かめます。

**相关项目例：** 为库存接口准备不存在、零库存和正数三种测试数据，明确每种响应。

**关键词：** Record、noUncheckedIndexedAccess、undefined

### 4. 欠けている値は「捨てる」か「埋める」か：小さい町村だけ値がない持ち家率で、扱い方を比べたときに何を決めて何を確かめたか

**面试问题：**

> 小さい町ほど欠ける場合に、多重代入と完全ケースの結果が分かれたのはなぜですか。

**约30秒回答：**

> 記録のある町では、持ち家率との関係が町の規模で違っていました。一つのモデルで多重代入すると、大きい町の関係を小さい町に外挿します。この条件のシミュレーションでは、完全ケースより偏りが大きくなりました。ただし、実際の欠損値は分からないので、どちらの推定が正しいかまでは言えません。

**相关项目例：** 对合成分组数据按规模遮蔽记录，比较删除与多重插补相对已知参照的偏差。

**关键词：** 欠損、多重代入、完全ケース、外挿

### 5. AI にコードを読ませて設計意図を推測させたら、3つ外れた

**面试问题：**

> git log から推測した3層構成や公開用リポジトリの理由を、どう確かめましたか。

**约30秒回答：**

**相关项目例：** 选两个内部设计决策，分别记录代码证据、可能的解释和负责人可确认的原因。

**关键词：** git log、設計理由、仮説修正

## 4. 技术主题：明确处理边界和校验依据

状态、请求与估计都依赖于可追踪的比较基准。撤销时对照操作后状态，限流时记录每条消息的总请求数，模拟插补时以清除数据之前的系数作参照。

同一种表象可能来自不同机制。共享周表保留是因为后续操作通过了采纳；库存的零值应当单独解释；小地区缺失会把模型带到训练中缺少观察的范围。

把边界写进交付。日志记录请求次数与完成时间，统计报告并列呈现不同估计，设计文档并列放代码所见和负责人确认的理由。

1. **中文：** 退避减少竞争，发送前的共享预算减少进入竞争的请求。
   **日本語：** 拒否後に待つ方式と送信前に絞る方式を分けます。

2. **中文：** 放大率的分母是消息数，分子包括失败重试。
   **日本語：** 増幅率は失敗した要求も含めて計算します。

3. **中文：** 11.06 秒只适用于原文设定的负载与限流算法。
   **日本語：** 秒数は固定した負荷と制限方式に依存します。

### 3. TypeScriptのnoUncheckedIndexedAccessで配列・辞書のundefined事故を防ぐ

1. **中文：** strict 本身不会为任意索引补上缺失类型。
   **日本語：** strict だけでは添字で読んだ値をすべて検査できません。

2. **中文：** 在类型收窄时保留业务允许的零值。
   **日本語：** 値の有無と、値がゼロであることを分けます。

3. **中文：** 索引检查和运行时校验可以覆盖不同的问题。
   **日本語：** 型で表す条件と実行時に確認する条件を持ちます。

### 4. 欠けている値は「捨てる」か「埋める」か：小さい町村だけ値がない持ち家率で、扱い方を比べたときに何を決めて何を確かめたか

1. **中文：** 先检查缺失记录集中在哪些群体。
   **日本語：** どの集団で値が欠けるかを最初に見ます。

2. **中文：** 同时检查插补后的数值范围和模型是否外推。
   **日本語：** 補完した値の範囲と外挿の有無を点検します。

3. **中文：** 模拟可比较方法，真实未观测值仍是未知量。
   **日本語：** 模擬データでの優劣は実データの真値を決めません。

### 5. AI にコードを読ませて設計意図を推測させたら、3つ外れた

- 含义：情况、安排或实际限制。
- 搭配：日程の都合 / 業務上の都合 / 都合がつく
- 文章语境：原作者因内容用途的实际需要，保留填空与加笔记的不同版本。
- 例句：検証環境の都合で、二つの条件を別々に試します。
- 例句含义：受测试环境条件所限，我们分别试验两个条件。
- 辨析：「～の都合で」常指受安排或条件影响；「事情」更广泛地指背景。Bunpro 的参考等级为 N4。

## C-2. IT/AI专业词汇

1. **sharedAfter（シェアードアフター）**：被撤销操作写入后的共享状态。 对照当前周计划和采纳标志。

2. **Retry-After（リトライアフター）**：要求客户端等待再请求的提示。 固定窗口模型返回可重试的等待时间。

3. **token bucket（トークンバケット）**：按补充速率与容量控制发送。 各 Worker 共享发送额度。

4. **noUncheckedIndexedAccess（添字アクセスの未定義チェック）**：为可能不存在的索引结果添加 undefined 类型。 库存读取先处理未登记键。

5. **multiple imputation（多重代入）**：构造多份插补数据，再合并各次估计。 实验插补人口较小地区缺失的住房自有率。

6. **design hypothesis（設計の仮説）**：根据结构或历史推断设计动机。 与项目作者的实际说明并列。
