### 1. Claude Code のスキルを、Figma エージェントの中で動かせるか試した

**原文：** https://zenn.dev/akaringo1109/articles/figma-agent-skill-external-library

**发布时间：** 2026-11-03 09:01:42 JST

这篇文章从设计师的使用门槛出发：他们熟悉Figma，却未必愿意每次打开终端、通过Git更新技能。作者在10月23～25日将原有的Claude Code技能移到Figma代理中执行，技能既有操作说明和规则，也带Python脚本。文章公开的是运行与维护方式，没有公开具体业务判定逻辑及准确率，因此“完整走完既定步骤”不能替代质量验收。

第一道障碍是载入单位。Figma技能以单个Markdown注册，作者观察到65,536字符的注册限制，以及初始送达约51,000字节的另一道限制；字符和UTF-8字节不能混为一谈。压缩文件虽然能运行，却让后续规则扩充变得困难。作者最终只注册约6,500字符的启动部分，把主要内容放进画布文本节点。初版包含7个分区、43张卡片和2张表，共388个文本节点、约27万字；这是自建资料库，并非Figma原生组件库。

启动过程通过Plugin API读取节点名称、文本和排列顺序，在执行环境中恢复出原来的文件，再启动Python。大体量工具返回在界面上会被省略，于是作者不让代理重新抄写，而由程序直接读取执行环境保存的完整返回。两侧核对文本数和FNV-1a校验哈希，以便发现传输缺失。这只能回答内容是否对应，不能证明编辑者可信，也不能证明读到的一定是本次最新版本。

执行流程也由程序逐步驱动：Python根据已经产生且通过检查的成果物，决定下一步，减少代理跳步或自行合并步骤。作者报告了等待13分46秒后执行环境更换、重新载入并继续完成的案例。但工具返回的内部保存路径并非公开接口，同一会话残留旧返回也有误用风险。更关键的是，资料库编辑者能修改随后执行的代码，示例对路径名称的检查又不严格，所以编辑权需要限制在维护者范围内。

这种方案的运行时间为11～27分钟，压缩成单技能的旧版约6分钟；文章没有按步骤隔离测量，不能断言资料库方式本身造成了全部延迟。模型不可由使用者选择、本番资料库归属及维护人尚未确定，也都限制了直接推广。面试可以围绕“把工具放到用户熟悉的工作面”展开，再具体解释版本、新鲜度、恢复点和执行权限怎样影响落地。

**阅读价值：** 把代理功能移进使用者的日常工具时，如何同时处理资料分发、恢复执行与可执行内容的编辑权限。

### 2. Claude Code で Haiku・Sonnet・Opus とエフォートを変えて22課題を解かせたら、差が出たのは実装より上流だった

**原文：** https://zenn.dev/okzaq/articles/claude-code-model-effort-bench

**发布时间：** 2026-11-03 07:30:05 JST

作者在2026年10月用22道自建题比较Claude Code模型和推理投入设置。环境是Windows、Claude Code 2.1.308与Max 5x，模型为Haiku、Sonnet、Opus 5.5，通常覆盖五档effort；耗时较长的四阶段任务仅比较五种组合。题材是虚构业务系统与零件资料，CLI提供的是API换算费用，不是订阅用户真实付费金额。

在9道小型实现题中，medium及以上的所有模型均取得满分；Haiku medium的平均换算费用为0.10美元，Opus high为1.18美元。不过每种设置只跑了一次。实现由工作目录外的隐藏测试评分，生成测试还要经过变异测试，即故意破坏正确实现，检查这些测试能否抓住破坏；这比单纯相信代理声称“测试通过”更严格。

大型题材是含既有测试约1.3万行的会员管理系统，要求故意写得含糊，代码中藏有16项未写入要求书的业务规则，两项文档数值又已经过时。计划、规格、测试规格各重复3次，Haiku medium得分为72%、83%、85%，Sonnet high为91%、96%、99%。但每阶段使用作者准备的确定输入，前一阶段的模型输出不会直接传给下一阶段，因此没有测量规格遗漏向实现连锁传播的程度。

当实现阶段拿到详细规格和220项测试规格时，五种组合全部通过152项隐藏测试。42个变异体中，Opus high生成的测试抓到39个，其余组合抓到42个，因而不能把隐藏测试全绿说成测试能力完全相同。文档则由单独启动的Opus评分；对45次文档结果复评，条目一致率为96.0%～99.6%，但计划任务的一次总分最多改变8个百分点，小样本仍有明显波动。

在另一组18题、每设置23次运行的汇总里，Sonnet与Opus的max档并未比xhigh提高满分率，耗时中位数却为2.5～2.9倍。这不等于已证明max更差，而且大型四阶段没有测xhigh。题目自建、重复次数有限、共享Python环境可能影响后续运行、裁判评分口径有偏向，均应保留。可迁移的判断是：按工程阶段先定义成功标准，并继续由人检查规格中所有模型都会遗漏的决策。

**阅读价值：** 展示如何把模型比较转成工程阶段的验收问题，而不是只用一次编码成功决定全流程选型。

### 3. Projectionという発想。WebViewの中にNative UIを投影して共存させる方法にたどり着いた

**原文：** https://zenn.dev/rdlabo/articles/webview-native-ui-projection

**发布时间：** 2026-11-03 08:58:35 JST

WebView中的HTML与外部原生视图不共享绘制层级和滚动系统，因此提高z-index并不能让Web模态窗盖住上方的原生标签栏。作者此前用Web技术接近原生外观，却仍难复现iOS 26 Liquid Glass的折射和触摸效果，于是转向保留真正的UIKit视图，再解决它与Web内容的协作问题。

Projection利用“暂时不能操作”这一状态：可交互时显示Live Native UI；在模态窗后方或特定滚动期间，把原生视图的截图置于DOM容器，称为Web Projection；图片不可用时采用Web Fallback替代显示。原生组件并没有变成DOM节点，图片阶段也不能交互，所以切入和退出图片状态的时机是整个方案成立的前提。

为避免先隐藏后显示出现空白，以及反过来操作造成半透明图层双重叠加，作者在切换前完成截图与Web图片解码。iOS按约60fps的一帧间隔检查位置、尺寸，连续3次稳定才截图。交接时先在原生侧放同一张临时图片，并在同一处理内隐藏真实视图；待Web侧图片显示，在requestAnimationFrame时通知原生侧移除过渡图片，使外观保持一致、承载位置发生交接。

文章展示了iOS与Android中的滚动追随、广告被页头遮挡的裁切，并把公共部分提取为MIT许可的WebView Native UI Engine，供Capacitor、Cordova插件作者使用；已有两个具体插件采用。证据属于作者的演示和实现说明，没有提供全机型性能、能耗或无障碍对照测试。工程应用仍需逐项检查状态切换、图片准备失败、恢复触摸及滚动裁切，不能把“看起来连续”推广成所有用户体验均无损。

**阅读价值：** 有助于说明混合应用中CSS、系统视图、图片状态与可交互性之间的边界，适合前端面试。

### 4. Amazon Data FirehoseのLambda変換で、失敗・破棄したレコードがどこへ行くのか確かめてみた

**原文：** https://dev.classmethod.jp/articles/202611-mitsuguchi-firehose-to-lambda-kensho/

**发布时间：** 2026-11-02 18:20:43 JST

作者在东京区域搭建Direct PUT → Firehose → Lambda → S3的验证链路，故意制造四种变换结果。Lambda为Python 3.12、128MB、60秒超时，Lambda与S3两段缓冲均设1MB／60秒，调用重试数为3，并启用变换前数据备份。文章要解决的不是如何发送数据，而是入口受理后，成功、丢弃和失败究竟如何落盘。

Ok记录以变换后的JSON Lines进入正常保存区。Dropped不进入正常区或错误区，但在这次已启用的原始备份中仍存在；备份关闭时没有实测。ProcessingFailed及不合法JSON则进入错误区，rawData保存Base64编码的原始内容，两类都返回Lambda.ProcessingFailedStatus，尝试次数为1，所以错误码本身不能说明具体根因。

当三个记录中的一个让Lambda抛出函数异常时，同批两个正常记录也被一起送往错误区，正常区没有输出。错误码改为Lambda.FunctionError，尝试次数为4，CloudWatch日志进一步证明初次调用及3次重试。异常详情要去函数日志看，错误文件没有包含它。这说明逐条返回处理失败与直接终止函数，影响范围显著不同。

三次单独验证从发送到S3分别约80秒、126秒和139秒，属于各条件一次的观察，受缓冲、批量和当时情况影响，不能当作延迟保证。原始备份还是无换行的直接拼接，并不与正常输出一样都是JSON Lines，重处理时需要识别真实保存格式。

错误区和备份区都可能保留完整原始数据，Base64只是编码，并不提供保密性。生产设计还需限制访问和保存期，准备告警与重处理。面试时可以先讲清楚失败单位，再说明从入口响应、落盘内容和调用日志三处核对，而不是仅凭发送接口的成功计数就宣称数据已交付。

**阅读价值：** 用故障注入区分记录级失败、整批失败和最终保存，比只看入口成功响应更适合解释可靠性。

### 5. GitHub ActionsのSHAピン留めを設定で強制する。何が止まるか、lockfileならタグのまま通せるかを試す

**原文：** https://dev.classmethod.jp/articles/github-actions-require-sha-pinning/

**发布时间：** 2026-11-02 22:20:23 JST

作者在11月2日以Free账户的私有仓库、GitHub托管ubuntu-latest和push事件验证SHA固定强制策略。标签和分支引用在作业准备阶段被阻止，40位完整提交SHA通过；短SHA即使不启用策略也不能用。实验把不同引用方式分别放入工作流，避免把既有限制误认为这次策略新增的效果。

最容易遗漏的是内层依赖：即使外层composite action已经固定SHA，内部的标签引用仍会让作业失败；可复用工作流的调用本身可以用标签，但被调用内部的action仍受检查。同仓库本地action及docker形式步骤属于此次策略的例外。因而“启用后所有运行代码都固定”并不是实验支持的结论。

将工作流通过gh actions-lock 0.4.0注册后，actions.lock记录直接及内层依赖的提交，标签写法可以保持，运行仍取得锁定提交。但未注册的其他工作流继续失败。作者还重现旧0.2.0锁文件把内层标签记录成另一标签、导致运行缺项的问题；新版检查识别其不完整，重新锁定后通过。因此锁文件存在不等于依赖闭包完整。

强制策略负责拒绝违规，并不自动重写引用或升级依赖；Dependabot也只更新已经注册的工作流。新增注册、更新审查和策略适用范围仍要分别维护。组织和Enterprise、允许列表组合、跨仓库可复用工作流、自托管执行器等均不在此次实测范围内。文章给出的渐进判断是保留已稳定运作的完整SHA流程，再按工作流小批量迁移和验证。

**阅读价值：** 能够具体解释供应链依赖固定的覆盖边界，以及强制、注册和升级为何是三个不同环节。

### 1. Claude Code のスキルを、Figma エージェントの中で動かせるか試した

**面试问题：**

> 大きなAIスキルを、非エンジニアが使う画面へ移すとき、何を設計しますか。

**约30秒回答：**

> 大きなスキルは起動部分とライブラリに分け、Figmaのテキストノードから元のファイルを復元します。長い戻り値をAIに書き写させず、Pythonが保存された全文を直接読み、件数とハッシュを照合する点が大切です。ただし、実行環境の入れ替わりや古い読み取りは別の問題なので、実行単位の確認と再開手順を用意し、ライブラリの編集権限も絞ります。

**相关项目例：** 在设计稿旁呈现检查结果的企业内部制作辅助工具。

**关键词：** テキストノード / Python / 再開

### 2. Claude Code で Haiku・Sonnet・Opus とエフォートを変えて22課題を解かせたら、差が出たのは実装より上流だった

**面试问题：**

> 開発工程ごとにAIモデルを選ぶなら、どのように比較しますか。

**约30秒回答：**

> 実装と上流の文書作成を分けて比べます。記事では、小さな実装9題はmedium以上で満点でしたが、大きな既存コードの計画や仕様では差が出ました。隠しテストと変異テストを使い、文書は採点表で複数回確認しています。ただし、各工程の入力は著者の確定版なので、AIが書いた仕様の漏れが実装へ及ぼす影響までは測れていません。

**相关项目例：** 分别评价需求澄清、规格、测试规格及实现的AI辅助开发基准。

**关键词：** 隠しテスト / 変異テスト / 確定版の入力

### 3. Projectionという発想。WebViewの中にNative UIを投影して共存させる方法にたどり着いた

**面试问题：**

> WebViewのモーダルとネイティブUIが重なる問題を、どう解決しますか。

**约30秒回答：**

> CSSの重なり順だけでは、別レイヤーのUIKitのタブバーを覆えません。記事のProjectionは、操作できない間だけネイティブUIの画像をDOMへ置き、操作可能になったら本物へ戻します。撮影とデコードを先に済ませ、つなぎ画像を使って空白や二重表示を防ぎます。ただし画像の間は操作できないので、切り替え条件とタップの復帰を実機で確認します。

**相关项目例：** 让Web模态窗与原生标签栏共存的Capacitor混合应用。

**关键词：** Web Projection / UIKit / requestAnimationFrame

### 4. Amazon Data FirehoseのLambda変換で、失敗・破棄したレコードがどこへ行くのか確かめてみた

**面试问题：**

> ストリーム変換の失敗を、どの単位で扱うか説明してください。

**约30秒回答：**

> レコードごとの失敗と、関数全体の例外を分けます。Firehoseの検証では、ProcessingFailedは該当データをエラー側へ残しましたが、Lambdaが例外で落ちると同じバッチの正常データも巻き込まれ、初回と再試行で4回呼ばれました。Droppedは今回の有効なバックアップにだけ残っています。ただし各条件一回の結果なので、保存設定と再処理の単位を自分の構成でも確かめます。

**相关项目例：** 把正常、丢弃、变换失败和函数异常送入同一数据链路，核对日志、备份和重处理。

**关键词：** Dropped / ProcessingFailed / NumberOfRetries

### 5. GitHub ActionsのSHAピン留めを設定で強制する。何が止まるか、lockfileならタグのまま通せるかを試す

**面试问题：**

> CIで依存アクションのSHA固定を強制すれば、十分でしょうか。

**约30秒回答：**

> 強制が届く範囲と、依存を更新する仕組みを分けて考えます。記事では、外側をSHA固定したcomposite actionでも、内部のタグ参照で止まりました。actions.lockへ依存を登録したワークフローは内部も通りましたが、未登録のものは失敗したままです。ただし組織や外部の再利用ワークフローは未検証なので、自分の依存関係で確認し、新規登録と更新のレビューも続けます。

**相关项目例：** 在保留现有完整SHA固定的基础上，分批试用workflow依赖锁定。

**关键词：** sha_pinning_required / composite action / actions.lock

## 4. 技术主题：分别确认显示、评分与保存的成功条件

以下是基于五篇文章的教学归纳：先为不同层次定义可观察的成功。Figma的长返回要检查保存内容与恢复成果物，不能只看界面有没有显示；混合UI则要分别验证图像连续和交互恢复。把“显示出来”“内容完整”“能够操作”拆成独立验收问题，更容易定位异常。

评价模型时，隐藏测试通过、变异体被检出、文档规则覆盖率也衡量不同能力。Firehose的入口受理、逐条转换、整批异常和S3落盘，进一步展示了完成状态的层次。将输入、处理单位及最终证据对应起来，有助于明确失败范围，而不是把多种成功折叠成一个绿色状态。

CI依赖固定同样需要列出覆盖边界：外层SHA、composite action内层，以及哪些工作流已登记进锁文件。内容一致或依赖固定都不能自动证明其内容正确、编辑者可信或权限合适。资料库编辑权、原始数据读取权与评分标准，需要分别检查，这是采用这些机制时的限制。

面向日本企业的落地练习，可以从较小对象开始，由业务负责人确认输入与合格条件；例如设计检查明确脚本维护人与使用者，会员计费把月末、闰年等边界纳入测试。这是教学建议，五篇文章不提供日本整体采用率或统一收益。实际推广仍要在本企业资料、设备、依赖和保存政策下验证。

### 1. ～さえ～ば｜N2

- 含义：只要具备某个最低条件就可以……
- 接续：名詞＋さえ＋あれば／名詞＋さえ＋動詞のば形
- 用法：突出说话人认为足够的条件。原作者把读取外部文件的工具与运行代码的环境视为向其他代理迁移的必要支撑，是可行性判断而非已经逐个平台验证。
- 原文依据：外のファイルを読む道具とコードを動かす場所さえあれば、同じ形は使えるはずです。 https://zenn.dev/akaringo1109/articles/figma-agent-skill-external-library
- 学习例句：資料さえそろえば比較を始められますが、結論には測定結果も必要です。
- 例句含义：只要资料齐备就能开始比较，但得出结论还需要测量结果。
- 注意：不同于已学「すら」的极端举例强调；此处与条件形ば组合。学习例句不是原文引语。
