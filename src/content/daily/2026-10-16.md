### 1. 生成しない拡散モデル Nemotron Deciffusion 8B を DGX Spark で試してみた

**原文：** https://dev.classmethod.jp/articles/nemotron-deciffusion-8b-decision-model-dgx-spark/

**发布时间：** 2026-10-15 16:55:57 JST

这篇实测讨论的是把拡散语言模型用作“判定部件”，而非让它持续生成回答。Nemotron Deciffusion 8B v2 基于 Nemotron-Labs-Diffusion-8B，把答案压成一个掩码位置，读取候选符号的概率。它由 NVIDIA 员工以个人账号和专用组织公开，原文明确说明这不是 NVIDIA 官方产品发布。POST /v1/systemone 提供 choice、noul、score 三类结果，可在一个请求中放入多项问题；概率、是非和有序评分也不应混成同一种精度指标。

与自回归模型只根据左侧上下文预测下一个符号不同，这个判定位置读取整段上下文和选项。固定选项顺序、不使用随机采样，使相同输入能得到相同概率；代价是不能像文中比较的 CLM 那样复用前缀读取结果。作者用 DGX Spark 的 GB10，容器以 FP8 加载，模型常驻约9.03GiB；这与公开材料中的 GB200、NVFP4、较短输入条件不同，不能把双方延迟当成同场排名。

评价沿用已冻结的528条路由输入，分别考察真实任务、实现题、设计咨询、困难题、环境差异与未见样本。日本语问题的 zero-shot 结果在未见237条上有10条误送，AUC为0.858；14道需要更强模型的困难题中，10道被高置信度送给较弱模型。因此，“实运用样本误送为0”无法推出难题可靠。对照的 Jev 1.13、CLM 和现行判定器主要是9/27记录，后来另外复测了 Jev 1.14；重复次数和阈值规则也有差异，原文并未把它包装成严格统一条件的通用排行榜。

速度试验使用同机客户端，真实输入的中位长度为961 token。顺序发送时客户端p50为137.6ms，第二轮137.8ms，87条输入的概率均一致；同时8路则p50增至2728.5ms，整体吞吐也低于顺序发送。文中提出整批双向读取给GB10带来负担的解释，但没有单独定位原因。把三个问题合并到一次情境中约336.6ms，说明“一个情境多问”与“许多情境并发”是不同的性能问题。

可迁移的设计判断是把路由误送的损失、阈值校准、输入语言和并发量一起评估。此次只有一次 Deciffusion 测量，尚未完成适应该代理能力的再训练，NVFP4也未验证。作者没有替换现行生产判定器：模型能判断任务外形，并不等于了解某个代理的工具、权限与能力边界。后续学习项目可以复用公开评价方法，不能声称本日报重新运行了528条试验。

**阅读价值：** 适合说明“判定概率可重复”与“困难任务可安全路由”的差别，并练习分层评价和阈值取舍。

### 2. Chrome 155でJPEG XLを表示する。picture要素のフォールバックとJPEGからの可逆変換を確かめた

**原文：** https://dev.classmethod.jp/articles/chrome-jpeg-xl-decode/

**发布时间：** 2026-10-16 01:57:34 JST

JPEG XL 的上线不能只理解为把图片后缀换成 .jxl。文章实际验证 Chrome 155 的解码、旧版浏览器的退回路径，以及已有JPEG无损转码后的可恢复性。Chrome引入以Rust实现的jxl-rs解码器，原文转述了官方对内存安全的考虑；浏览器能解码并不代表也能制作这种文件，编码仍依赖独立工具。官方列出的压缩效率与作者对一张图片的测量，也属于不同证据。

实测环境为macOS上的Chrome 155.0.8059.79，以及Linux容器内的Chromium 156与153。新版本中，img.decode()成功，naturalWidth/naturalHeight为768×512，picture的currentSrc指向JXL；旧版153直接加载JXL失败、尺寸为0×0，而picture中的JPEG退回路径仍能显示。作者还在本地服务端记录到155/156的Accept包含image/jxl，153没有。它说明可以据此设计服务端协商，并没有证明某个CDN已正确配置了分流。

压缩试验把一张CC0照片缩成768×512，再以quality 85制作JPEG，之后用libjxl 0.12.0的cjxl可逆转码。96,118 bytes变为74,816 bytes，约减少22%；用djxl返回JPEG后，cmp和SHA-256均确认原文件字节一致。这是对已有JPEG的无损重打包，不能拿来直接验证官方“30～50%”的其他编码条件。另一次PNG到无损JXL的约62%缩减，还受到照片大面积平滑背景的影响。

可落地的前端判断包括：用picture保留旧格式；核对实际选中的资源、解码是否成功和返回字节；再用目标图片集评估容量。原文未测试Firefox、Safari、移动平台、HDR、动画、CSS背景图、CDN协商以及等画质AVIF比较，因此不能宣称全面兼容或容量领先。对React/Next.js项目，也应将这些浏览器层面的验收带入组件和图片流水线，而不是只在构建成功时结束。

**阅读价值：** 适合前端面试中的兼容性、渐进增强、图片流水线和可回滚验收。

### 3. Lambda Web FunctionsのNode.jsでCPUバウンドな処理をすると、ほかのリクエストは待たされるか？

**原文：** https://dev.classmethod.jp/articles/shuntaka-lambda-web-functions-nodejs-cpu-bound/

**发布时间：** 2026-10-15 16:40:20 JST

Lambda Web Functions允许一个执行环境同时处理多条请求；与每个环境一次处理一条的Event Functions相比，Node.js同步CPU计算会影响同环境的其他请求。文章不是只复述单线程常识，而是进一步问：平台是否会把后来的请求送往空闲环境，从而掩盖这种阻塞？为比较运行时机制，作者也从Node.js启动Go二进制，由Go直接处理HTTP；这不是宣布Web Functions新增原生Go运行时。

实验使用nodejs24.x、maxEnvironments=2、每环境两个CPU。/cpu以循环占用500ms，再按15ms间隔送/ping；两条CPU请求的启动错开50ms，每种模式20次。环境身份由envId和lambda-web-logstream交叉确认，“等待”则比较同一进程中/ping.receivedAt与/cpu.finishedAt，避免只用含网络抖动的端到端耗时推断阻塞。配置最小环境数为2，不能把它当成固定单环境的云端实验。

本地单进程对照中，Node.js处理一条CPU任务时/ping的p50约490ms，两条时约941ms；Go相应约4ms与18ms。Go一方面可在两个CPU上运行goroutine，另一方面运行时能切换长时间计算的goroutine；Node.js的JavaScript同步循环不会自动让出事件循环。这里比较的是文章指定的循环负载，不能把所有Node.js异步API一并归为同步阻塞。

云端经CloudFront发送时，有空闲环境的模式中两种实现的/ping都在20次试验中避开了正在计算的环境。两环境被占用后，Node.js的/ping有16次进入正在计算的环境且全部等到CPU任务结束，表中该模式p50为513ms；Go未出现同样的结束等待，p50为47ms。另有CPU请求碰到同一环境的试次，这时剩余环境仍空闲，因此不能说调度器永远按直觉平均分配，也不能只凭一次“没有延迟”判断代码安全。

动态并发上限与语言运行时的抢占机制是两层问题。原文指出maxConcurrencyPerEnvironment默认64、可设1～128，平台动态值不会超过该上限；但分配算法没有完整公开。异步内置API、worker_threads、降低每环境并发都是可研究方案，本文并未测量这些对策的收益。真实服务还需以CPU/I/O比例、冷启动和容量成本验证，不应把这个人为CPU压力试验概括成所有Web请求的常态。

**阅读价值：** 适合后端面试中区分运行时并发、平台调度、观测口径与尚未实测的优化方案。

### 4. アプリとDBの間の往復遅延が応答時間に与える影響を TiDB Cloud Starterで計測した

**原文：** https://dev.classmethod.jp/articles/tidb-cloud-network-latency-app-response/

**发布时间：** 2026-10-15 11:46:08 JST

当云数据库访问变慢，先搬服务器未必是最直接的解决路径。作者以TiDB Cloud Starter东京实例中的订单历史为题，查询最新5条订单及25条明细，对比“订单一次＋逐条明细五次”的六次SQL和“订单一次＋IN批量明细一次”的两次SQL。两种实现的返回结果每轮都做一致性检查，因此减少往返并非省略业务数据。测试数据含10,000条订单和50,000条明细。

环境为TiDB v8.5.3、macOS、Python 3.13、PyMySQL 2.2.8与Toxiproxy 2.12.0，测量于10/14实施、10/15发表。代理分别给上下行加入一半延迟，总新增往返设为0、20、80ms；SELECT 1前后探测对应实际约15、38、100ms。这里是同一路径加人工延迟，并非实地迁到三个不同地区。主试验复用一条连接，每种条件先暖机3次、各实现测30次，交替顺序并分组轮换延迟，以中位数和四分位呈现。

新增80ms时，六次SQL的中位响应为625.7ms，两次为206.8ms，缩短66.9%；未新增延迟时也从117.2ms到40.5ms。相比基线，六次实现多约508.5ms，两次多约166.2ms，接近“新增往返×逐次往返次数”。这解释为何单条SQL看起来很快，页面仍会受N+1影响。原文的近似关系针对增量，不能把它误写成所有请求总耗时的精确公式。

连接重建另作独立对照：新增80ms时，每请求新建连接的中位数721.0ms，复用为210.4ms，约缩短70.8%；新增0ms时约缩短79.5%。TCP、TLS握手和认证本身会产生多次往返，因此“只优化SQL两次”仍可能被建连占主导。主查询试验的206.8ms和建连试验的210.4ms来自两组测量，不应强行拼成一条同轮数据。

证据边界是轻量读取、一条连接逐次SQL、受控人工延迟，不含高并发写入、复杂聚合、真实跨区抖动或自动扩容。先数往返并检验结果，再考虑批量获取与连接池；若这些都无法满足目标，再评估布局或接入方案。原文列出PrivateLink等配置选项，但没有本次私网快于公网的实测，不应把建议写成已验证的加速结果。

**阅读价值：** 适合Web性能面试：把N+1、连接池、网络延迟和计时口径串成可验证的因果链。

### 5. Amazon Bedrock AgentCore IdentityのOn-Behalf-Of（OBO）トークン交換機能を実際に試して理解を深めてみた

**原文：** https://dev.classmethod.jp/articles/agentcore-identity-obo-entra-id/

**发布时间：** 2026-10-15 11:44:23 JST

AgentCore Identity的OBO（On-Behalf-Of）解决的不是让代理拥有更大的应用权限，而是把用户委任关系传到下游正确的API。Entra ID发给代理应用的令牌带有aud和scp；直接拿它访问Microsoft Graph的/me，文章得到401 Invalid audience。反过来把Graph令牌送到代理入口，原文也观察到Runtime的iss不匹配401、Gateway的insufficient_scope 403。这些是不同入口的具体错误，不能统一概括成“都是aud校验失败”。

正确链路先由Runtime或Gateway验证发给自己的用户令牌，再由Identity向Entra请求Graph用途的令牌。Runtime代码用requires_access_token和ON_BEHALF_OF_TOKEN_EXCHANGE，scope指定User.Read；Gateway的目标出站配置用TOKEN_EXCHANGE。Microsoft专用provider管理交换参数，秘密放入Token Vault，调用代码不必自行持有客户端秘密。减少交换代码并不免除令牌存储、IAM以及权限同意的配置责任。

前置条件包含单租户应用、公开access_as_user、事先同意Graph的委任User.Read、令牌版本2与客户端秘密。示例用Azure CLI作为已获准客户端，生产SPA则应有自己的客户端注册。交换发生在后端，不能在交换现场临时弹出用户同意，因此需要提前完成适当同意。User.Read的委任授权并不是给应用开放所有员工资料，仍应区分本人范围与应用级权限。

原文既测了Runtime中的工具调用，也测了Gateway上的OpenAPI工具。两条路径都从/me获得了当前登录者的资料；交换后Graph成为aud，User.Read进入scp，而用户身份仍保留。运行时角色和Gateway服务角色还要拥有获取工作负载令牌、资源令牌及相应秘密的权限；文中特别补上了CLI在外部创建provider后未自动配置的权限。这些结果验证了示例链路，没有给出吞吐、交换延迟或所有Graph权限的测试。

适用边界是同一Entra身份体系中的委任链。若入口身份来自Cognito等其他IdP，原文把3LO作为候选，而非宣称任意令牌都能OBO。对于MCP工具，文章引用规范中禁止把收到的令牌原样透传给上游的原则：每个资源接受自己的令牌，下游使用另外获得的正确用途令牌。可迁移到面试的问题是“谁替谁、向哪个API、凭哪项同意、在什么IAM范围内访问”，而不是一句“用了OAuth就安全”。

**阅读价值：** 适合AI Agent架构面试：用真实失败与成功路径解释aud、委任、身份保持和权限边界。

### 3. Lambda Web FunctionsのNode.jsでCPUバウンドな処理をすると、ほかのリクエストは待たされるか？

## 4. 技术主题：先固定比较单位，再解释性能与访问结果

以下是基于五篇原文的技术整理，不是新增实测。测量的单位不同，同一个“快”可能指模型单次判断、浏览器显示、进程内等待或数据库整页响应。Deciffusion的同机137.6ms不能与含回线的远程API值直接排序；Lambda的等待判定又依赖同一进程的时刻。先画出被测链路，再声明从哪一步计时，才能保留比较的意义。

优化也必须保留原任务。TiDB将六次SQL变为两次，前提是订单和明细返回一致；JPEG可逆转码检查返回原JPEG后的字节一致。两者的“一致”对象不同，不能拿文件哈希方法直接验证模型判断正确。Deciffusion恰好说明：相同输入给出相同概率，只证明确定性，仍可能稳定地把难题送错。

身份链路还需要另一类边界。OBO不是把用户凭据送遍每个工具，而是让每个资源验证对自己有效的令牌，交换后保持委任关系。一次Graph本人信息调用成功，没有证明所有目录权限都可访问；拒绝错误也需按真实入口区分。把“收到HTTP成功”与“完成业务目标和授权约束”分开，是本日报从原文提炼的验收方法。

若在日本企业项目中尝试，可先选一条已有业务链：图片组件保留旧格式；订单API记录SQL次数和连接时间；代理工具列出用户、aud、scope及同意。把实验条件、真实结果和未测范围写在同一份评审记录中，再决定要不要扩大使用。这里提出的是可验证的实施步骤，不是对日本企业采用率、成本收益或生产安全性的统计结论。

## C-2. IT/AI 专业词汇

1. **masked decision（マスク位置による判定）**：从单个掩码位置读取候选概率 Deciffusion不输出长篇回答，判定位置和普通next token不同。

2. **lossless transcoding（可逆トランスコード）**：可完整返回原文件的转码 JPEG转JXL后用djxl还原，并以cmp及SHA-256核对。

3. **picture / currentSrc（画像候補と選択済みURL）**：浏览器候选图片与实际资源的区分 旧浏览器落到JPEG，不能只核对HTML里写了JXL。

4. **event loop（イベントループ）**：Node.js处理任务和回调的执行循环 同步CPU循环会阻塞同环境内其他请求。

5. **maxConcurrencyPerEnvironment（環境ごとの同時要求数の上限）**：每执行环境并发请求的上限 不能直接等同于环境数或进程内部CPU并行度。

6. **N+1（エヌプラスワン）**：列表获取后逐条追加查询导致的往返增加 订单5件形成6次SQL，IN批量后变2次。

7. **round-trip time（往復時間）**：请求与响应走完整个来回所需时间 额外往返与逐次次数用于估算增量，不能直接当总耗时。

8. **OBO token exchange（本人に代わるトークン交換）**：保留用户委任关系而取得下游用途令牌 AgentCore Identity把代理用途令牌换成Graph用途。

9. **aud / scope（宛先と権限範囲）**：令牌给谁使用与允许做什么 aud正确不等于具有全部Graph权限。
