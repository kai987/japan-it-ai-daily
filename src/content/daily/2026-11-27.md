# 日本 IT/AI 日报｜2026年11月27日（第108号）

指标能告诉我们改动发生了什么，前提是先交代指标覆盖的过程。五篇原文分别从小样本实验和生产记录切入，展示如何拆开测量、解释异常值，再决定哪一步值得改。

# A. 详细文字版

## 1. 今日推荐的五篇原文

### 1. vLLM の /v1/decisions は同じ質問に同じ確率を返すか NVIDIA DGX Spark で確かめてみた

**原文：** https://dev.classmethod.jp/articles/dgx-spark-vllm-decisions-first-touch/

**发布时间：** 2026-11-26 11:36:30 JST

文章在 DGX Spark（GB10）上运行 Qwen3-0.6B，研究 vLLM 提供的 /v1/decisions。接口把问题和候选项变成带字母标签的提示，从首个输出 token 的 logprobs 取出各标签的值，再在标签之间做 softmax。判断可以由这些概率得到，应用不必解析自由文本。

作者分别改变 prefix cache 与并发背景流量，每个条件重复提交同一问题三十次。接近五五开的题，在混入其它流量且使用 cache_salt 的条件下，vLLM 0.33.0 和 0.34.0 都出现了正负各十五次。标签打成平手时，排序靠前的一项被选中，选项排列因此也需要纳入测试。

开启 VLLM_BATCH_INVARIANT 后，边界问题在四种条件合计一百二十次都选 negative，表中概率固定在 0.5。这个可复现的值与默认路径不同。即使改用 float32 令概率波动变小，默认执行路径仍可能在边界题上翻转。

本文只测了一台机器和一个小模型，未验证分类正确率或概率校准。部署者可以把环境版本、选项顺序和并发条件随判定一起存档，再用带标签的业务数据决定何时置信、何时保留。

**推荐理由：** 能把接口返回得稳定、判断选得正确和概率适合定门槛这三个问题分开检验。

### 2. Customer-managed runtimesでコールドスタートは速くなる?サイズの大きなライブラリをZIPにパッケージングする場合と比較してみた

**原文：** https://dev.classmethod.jp/articles/lambda-cmr-vs-zip-coldstart/

**发布时间：** 2026-11-26 16:16:53 JST

作者比较 Lambda 的两种部署方式。一边使用 AWS 管理的 Python 运行时，在 ZIP 里携带 botocore、numpy、pandas 和 scipy。另一边把依赖装进自管运行时镜像，在 ECR 发布运行时，让函数包只留自己的代码。

文章通过 API Gateway 产生调用，再在 X-Ray 的 Transaction Search 按 traceId 对齐服务跨度与初始化跨度。用 Init 开始时间减去 Invoke 对应服务跨度的起点，估算开始初始化之前的等待。所用跨度没有分别显示镜像读取、下载和运行时启动，指标无法区分这些环节。

这次比较中，ZIP 样本 108 次、估算中位数约 525 ms，自管运行时样本 105 次、中位数约 186 ms。自管运行时的最大值约 10.58 秒，原文在相应 trace 看到一次 Init 超过 10 秒后重试，并查到第二次 Init 约 4.82 秒。

镜像与 ZIP 的大小不一致，且平台底层实现未公开。文章用分块按需加载和缓存未命中解释长尾，属于根据 trace 提出的推测。仅凭一次实验，无法推导另一个地区或依赖集合的收益，也不能把这段时间当成端到端响应。

**推荐理由：** 同一改动改善了典型启动，却出现罕见的长等待，正适合讨论尾延迟与首次部署体验。

### 3. 型チェックが重かったので、クエリの型推論を手放してみた

**原文：** https://zenn.dev/dress_code/articles/88b55221eea4e0

**发布时间：** 2026-11-26 11:15:05 JST

团队在一台 24 GB Mac 遇到 TypeScript 检查挤占内存和磁盘。排查发现 Prisma 生成文件虽然大，转换为声明文件只少了十二次实例化。更大的消耗集中在旧 Kysely 查询的一条长表达式，这条查询包含五十多次 join。

给公开方法写清返回行类型以后，调用侧增量检查确实变轻。不过 SameRow 需要由编译器同时得到推断类型和手写类型，检查查询文件时仍会展开长表达式。作者把推断限制在迁移中的旧类，移除一致检查，再以显式行型维持调用接口。

在 TypeScript 7.0.2、单 checker、关闭增量的全库测试中，Instantiations 从约 3373 万降到 2268 万。Check time 从约 90.5 秒降到 46.4 秒。解析和绑定时间也同时显著降低，因此不能把所有墙钟时间改善都归给这次改动。检查结束后的堆数据也不能代替峰值内存。

文章用 query.compile() 对比变更前后的 SQL 文本和类型化参数，得到相同输出。现有数据库测试只覆盖若干列，选列变更后的整行一致保证随 SameRow 一同移除。这个取舍与该类已标记弃用、正在迁移的处境有关。

**推荐理由：** 既有清晰的诊断量，也交代了移除静态保障后还剩哪些证据，方便评估同类取舍。

### 4. Vercel Audit Log Drainsでチームの操作記録をHTTPSで受け取ってみた

**原文：** https://dev.classmethod.jp/articles/vercel-audit-log-drains/

**发布时间：** 2026-11-26 13:10:01 JST

作者在 Vercel Enterprise 团队里把 Audit Log Drain 指向自己的 HTTPS 函数。这里的输入是团队在平台上的操作审计，接收方在运行时记录里查看事件，不是用应用代码产生的普通日志替代审计。

接收端用 x-vercel-signature 核验请求。创建 Drain 时的确认请求也签名，所以如果启用验证，作者先在函数配置里准备好相匹配的密钥，再完成创建。这样建立的是一次特定的 Custom Endpoint 接入测试。

收到的 action 中包含 aliases-assigned、project-paused 和 project-unpaused。前者体现生产 URL 绑定新部署，后者在实验中带有 userAgent 与 ipAddress，而 aliases-assigned 未携带这两项。统一收集时需要允许不同事件具有不同字段。

删除 Drain 后，作者没有在原 HTTPS 接收端收到这次删除事件。单一转发路径上的静默因此不足以说明团队没有操作。观察只覆盖这次 Enterprise 配置。独立检查平台审计视图或转发配置，是从现象得出的运维做法。

**推荐理由：** 实测展示了转发接收、字段变化到停止投递的一整条链路，便于区分投递与审计覆盖。

### 5. 自動運転の予測軌跡の可視化動画を誰でも高速に作れるようにする

**原文：** https://zenn.dev/turing_motors/articles/cbf9872ca90166

**发布时间：** 2026-11-26 17:00:08 JST

Turing 把自动驾驶模型的预测轨迹叠在道路视频上。原先得由掌握 AWS 环境和 GPU 的人跑脚本，改用 Step Functions 与 AWS Batch 后，团队可从行驶数据界面发起请求，让 Slack 收到结果。前期即使图像处理变快，等待上游数据集仍让端到端时间居高。

新路径用场景 ID 和连续区间直接定位 S3 的 HEVC 与 Databricks 的预测轨迹。调度器分别计算 Spot 等待和运行时间，只对未启动且等待达到五分钟的作业使用 CancelJob，再转按需队列。作业启动后的执行上限由 Batch 的 attemptDurationSeconds 单独负责。

长视频按目标片段前的 I 帧开始解码，用 Up 过滤与 ISA-L 压缩写 PNG。为了并行执行抽取、检测和绘制，生产者先写未来帧清单，再用临时文件完成后改名，让检测器知道哪些帧仍可能出现，并避免读取未写完的图像。

同一 L4 和 16 个场景，抽取到成品 GIF 从 9 分 11 秒降到 4 分 32 秒，原文还核对了结果一致。生产通知时间的中位数也下降，不过前后各期任务组合有差异，最后阶段仅九天，不能把生产期的全部变化归给某一项优化。

**推荐理由：** 例子把单个算子、队列等待和面向使用者的总耗时放在同一条工程链路上。

## 3. 面接で使えるポイント

### 1. vLLM の /v1/decisions は同じ質問に同じ確率を返すか NVIDIA DGX Spark で確かめてみた

**面试问题：**

> 分類APIを振り分けに使うなら、しきい値付近をどう扱いますか。

**约30秒回答：**

> 同じ質問でも、同時に流れるリクエストとキャッシュの条件を変えて試します。記事では、境界に近い質問を三十回流すと、判定が十五回ずつに割れました。バッチに依存しない設定では判定がそろいましたが、既定時の値をそのまま保つわけではありません。しかも一つのモデルの測定なので、私なら境界には保留を設け、別データで正答率も確認します。

**相关项目示例：** 为客服工单分流制作一套回归样本，记录混合流量下的翻转率，并为接近阈值的请求设置人工复核。

**关键词：** prefix cache、logprobs、VLLM_BATCH_INVARIANT

### 2. Customer-managed runtimesでコールドスタートは速くなる?サイズの大きなライブラリをZIPにパッケージングする場合と比較してみた

**面试问题：**

> Lambdaのランタイムを替える提案を、何の数値で判断しますか。

**约30秒回答：**

> X-Rayで呼び出しと初期化の開始時刻をそろえて、起動前の待ち時間を比べます。記事では、中央値が約五百二十五ミリ秒から百八十六ミリ秒に縮みましたが、新しい方式では十秒を超えて初期化をやり直した例もありました。ただしこの差は起動の近似値です。私なら初回と繰り返しの両方を測り、応答全体が要件に収まるかで選びます。

**相关项目示例：** 为分析函数建立两套依赖打包方式，在相同触发入口记录 Init 前等待、Init 时间和客户端响应分位数。

**关键词：** Customer-managed runtime、X-Ray、Transaction Search

**相关项目示例：** 对迁移中的报表接口保留生成 SQL 的差异检查，并用约定的字段集合补查运行时返回行。

**相关项目示例：** 为异步媒体作业记录排队、解码、检测、渲染和通知耗时，按短作业和长作业分别观察。

## 4. 今日技术主题

### 给每项改动画出测量边界

先按使用者看到的结果定义起止点。分类结果从请求送入到路由决策，视频从点击生成到收到通知。再按系统状态增加中间点，才能判断某一段节省的时间是否被其它等待吸收。

重复测量时保留输入、版本和负载条件。把同样输入下的结果与生产期汇总分开放，另外检查首次和极端样本。准备上线时，还要列出新方案撤掉了什么保障，以及留下了哪些独立证据。这样也便于出问题时从确切阶段恢复。

# B. 重点总结与可用于面试的知识

### 1. vLLM の /v1/decisions は同じ質問に同じ確率を返すか NVIDIA DGX Spark で確かめてみた

1. **中文：** 首个 token 的标签概率让接口输出可直接被规则消费。
   **日本語：** 回答用のラベルの間で正規化するので、自由文を解析しなくて済みます。

2. **中文：** 同一个问题应在单发、混合流量和缓存变化下分别重复。
   **日本語：** 単発と混在で同じ問いを送り、キャッシュ条件も記録します。

3. **中文：** 判定一致不证明概率已校准，版本升级后要重跑边界样本。
   **日本語：** 結果がそろっても正答率や校正が確認できたわけではありません。

### 2. Customer-managed runtimesでコールドスタートは速くなる?サイズの大きなライブラリをZIPにパッケージングする場合と比較してみた

1. **中文：** 保留调用与初始化跨度，并明确用哪个时间差作为代理指标。
   **日本語：** スパンの開始時刻の差で起動前を近似します。

2. **中文：** 中位数约 525 ms 对 186 ms，同时查看 10 秒以上的极端值。
   **日本語：** 約百八十六ミリ秒の中央値と十秒を超える最大値を両方確認します。

3. **中文：** 镜像体积与缓存状态不同，内部按需加载只是一种解释。
   **日本語：** 別の依存やリージョンに同じ効果があるかは実測が必要です。

### 3. 型チェックが重かったので、クエリの型推論を手放してみた

1. **中文：** 用冷执行和相同 checker 数量取得可比较的实例化统计。
   **日本語：** コールドかつ同じチェッカー数で回数を比較します。

2. **中文：** 手写返回类型与继续引用推断结果是两项不同的选择。
   **日本語：** 公開型を絞っても一致検査が推論を残す場合があります。

3. **中文：** 保留 SQL 与参数核对，明确仍然可能漏掉整行类型漂移。

### 1. 妙（みょう）｜N3

- 词性：形容動詞・名詞
- 含义：表示异常或出乎意料，此处为副词形式「妙に」。
- 搭配：妙に少ない / 妙な値 / 妙に静か
- 文章语境：作者注意到结果只有少数几种概率，进而检查精度与取整。
- 例句：収集できたログの種類が妙に少ないので、フィルターの条件を見直しました。
- 例句含义：采到的日志类型少得不寻常，我重新检查了过滤条件。
- 辨析：「微妙」也可表示差别细微或不好下判断。「妙に」侧重程度出人意料。

### 2. 手元（てもと）｜N1

- 词性：名詞
- 含义：自己身边能够取得、使用的东西或环境。
- 搭配：手元の資料 / 手元で再現する / 手元に残す
- 文章语境：原文在工程师自己的 Mac 上分析内存和类型检查。
- 例句：本番と同じ条件を手元に用意して、変更前後を比べました。
- 例句含义：我在手头可控的环境中复现生产条件，对比改动前后。
- 辨析：「現場」强调事情或工作的发生地，「手元」强调自己能立即使用。

### 3. 帯（おび）｜N3

- 词性：名詞
- 含义：此处指连续而有宽度的条带状图形。
- 搭配：半透明の帯 / 帯を重ねる / 帯状に表示する
- 文章语境：文章用表示车宽的半透明覆盖层呈现预测路线。
- 例句：地図の上に色の帯を重ね、走行した範囲を示します。
- 例句含义：在地图上叠加彩色条带，标出车辆经过的范围。
- 辨析：「線」常只强调路径或边界，「帯」还可以体现宽度。

1. **Batch invariance（バッチ条件からの独立性）**：关注请求的批处理组合变化时，返回结果是否一致。 本文同一边界输入开启设置后，四种条件得出相同判定。
