### 1. Claude CodeにMCP経由で複数のAWSアカウントを参照させてみる

**原文：** https://dev.classmethod.jp/articles/claude-code-aws-mcp-multi-account/

**发布时间：** 2026-10-12 02:03:36 JST

**背景与适用范围。** 跨账户调查需要分别登录安全账户和业务账户，手动切换容易遗漏目标。原文把 Claude Code、AWS MCP Server 与 AWS CLI 的角色配置连接起来，让一次会话中的工具调用选择不同账户。这里讨论的是 AWS MCP 的多账户访问，不是让任意 MCP 服务自动获得 AWS 权限，也没有测试自然语言调查的完整性或准确率。

**凭证链如何工作。** 作者以 `hub-account` 为起点，先通过 `aws login` 取得基础凭证；示例要求 AWS CLI 2.32.0 以上及 `uvx`。目标账户提前创建同名 `AIAgentReadOnlyRole`，本地目标 profile 以 `source_profile=hub-account`、`role_arn` 指向目标角色。源侧允许 `sts:AssumeRole`，目标角色的信任策略接受源主体，两侧配置缺一不可。`role_session_name=claude-code` 则为后续 CloudTrail 记录提供可辨认的会话名；它不代替完整审计。

**工具调用如何选账户。** 项目的 `.mcp.json` 用 `AWS_CONFIG_FILE` 指向专用配置文件，并以 `AWS_MCP_PROXY_PROFILES` 列举可用 profile。允许列表与实际 IAM 权限分别发挥作用：前者约束可以选哪些配置，后者决定选定角色后能执行什么 API。调用时提供 `aws_profile`，代理按该 profile 取得凭证并进行 SigV4 签名，不必重启 MCP。省略参数时使用列表中的第一个 profile，因此示例中的 hub 默认权限也必须单独检查。

**实验步骤与观察。** 作者先对 hub、security profile 分别运行 `sts get-caller-identity`，确认账户和角色；再在 Claude Code 中通过 `/mcp` 连接工具，查询 security 与 workload-prod 的 S3 公共访问情况。原文报告可以跨账户参照信息。这个结果证明所示配置下的调用路径可工作，并未证明代理已经找出所有暴露资源、拒绝了所有危险提示，或在其他组织结构中同样适用。

**认证方式的边界。** 原文和其引用的 [AWS 多账户说明](https://docs.aws.amazon.com/agent-toolkit/latest/userguide/multi-account-access.html) 都限定这种按调用切换 profile 的方式适用于 SigV4。OAuth 模式绑定授权时的 IAM 角色，不能把本例的动态切换结论直接套过去。使用 IAM Identity Center 时，基础登录可改为 SSO profile，后续角色链仍需正确配置；这也不意味着 SSO 已自动替用户创建目标角色或信任关系。

**只读权限仍有数据风险。** 作者以 ReadOnlyAccess 限制写入，并提到不想让代理读取 S3 内容时可考虑 ViewOnlyAccess。学习时要区分“不能修改资源”和“不能取得机密内容”：只读并不阻止读取权限内的数据。示例中的角色名约束也不能替代针对账户、资源和服务的最小授权审查。

**可迁移的判断。** 对企业调查工具，我会先固定目标账户、核对默认 profile，再把可选配置、角色信任、数据读取范围和日志关联逐层验证。这是基于原文的设计整理，不是原文提供的安全认证。原文没有延迟对比、覆盖率、注入攻击测试或完整生产运维数据，因此这些能力不作保证。

**阅读价值：** 把账户选择、角色权限与只读数据风险拆开，能具体说明企业 AI Agent 的授权边界。

### 2. OpenAI の Decisions API で書類の値の突合を試し、Jev・Clef と比べてみた

**原文：** https://dev.classmethod.jp/articles/openai-decisions-cross-match/

**发布时间：** 2026-10-12 08:58:09 JST

**背景与问题定义。** 发票与采购单中的值可能写法不同而含义相同，也可能数字相同但币种不同。原文用 Decisions API 的 predicate 功能判断两个文本值是否相同，分别问 exact 字符串一致与 semantic 含义一致。此次输入是文本对，并非前一天的图片文档分类；不能把两种任务的结果混用。

**实验条件。** 作者准备107个架空案例，覆盖日期、货币、公司名、地址、OCR 错字、缺失、合计及不可见 Unicode 等10类情况。Decisions 使用 gpt-6-luna，返回“条件成立”的概率，以0.8为匹配阈值；英文、日文指令分别测试。predicate 不能像分类任务那样另给 criteria，真假条件需写进 instructions。数值是当前谓词成立的概率，而不是对所有业务结论统一适用的可靠性证明。

**准确率要看分母。** exact 判断在英文、日文条件下均为106/107正确。semantic 因一例不能确定正确答案而按106例计算，英文90/106、日文91/106。对比的 Jev 为96/106与97/106，Clef 为91/106与76/106，flash 英文为57/106。原文沿用同一组案例和问题，但 Jev 测于9月20日、Clef 于10月4日，不能把这视为同一时段、相同服务负载下反复运行的受控实验。

**错误揭示了规则边界。** 数字1250未注明币种，与 USD 1250 本应不匹配，Decisions 却给约0.95、0.97；提高到0.8并未挡住这种错误。双方空白的案例预期为语义匹配，却得到约0.08、0.33。学习上的判断是先统一业务对“缺失”“双方为空”“币种不明”的定义，再讨论提示词和阈值；这是对案例的设计分析，不是证明模型在所有缺失场景都失败。

**OCR 情况也不能笼统归类。** 两个同样带 OCR 错字的字符串在 exact 问题下只给0.66–0.77，低于0.8，而干净字符串常在0.91以上。原文观察到文本看起来完全相同仍可能被判不匹配。对于确定的字符串相等判断，可考虑先使用可解释的本地规则，再把歧义值交给语义判断；这是读后整理，原文并未给出生产混合方案的验证结果。

**时延与费用。** 本次 Decisions 英文、日文往返时间中位数为0.270与0.264秒，平均输入 token 为496与557；107次费用分别为0.0053、0.0060美元。按作者采用的1美元150日元折算约0.80、0.89日元，这不是今日汇率。英文条件下，费用约为 Clef 的六成、Jev 的2.3倍；这些值仅对应本次文本长度和调用条件，不能当成固定预算或延迟承诺。

**如何用于项目评审。** 这个实验适合练习“同一任务、同一案例、明确正解”的评估思路，尤其要保留类别级错误、无法判定的样本和比较测量日期。原文没有重复运行方差、真实业务分布、整页 OCR 链路或上线误判损失。日报因此不把总体分数外推为自动批准发票的能力；需要人工确认的条件仍取决于业务风险。

**阅读价值：** 保留文本相等与语义相等的任务差异、106/107分母以及币种错误，能把 AI 评估讲成具体业务判断。

### 3. Cloudflare Workersのサイズ上限が全プラン一律・非圧縮64 MBになった件をwranglerで確認する

**原文：** https://dev.classmethod.jp/articles/cloudflare-workers-64mib-size-limit/

**发布时间：** 2026-10-11 13:29:13 JST

**变化与时间背景。** 本文在10月11日验证 [Cloudflare 9月4日公告](https://developers.cloudflare.com/changelog/post/2026-09-04-increased-worker-size-limit/)：Workers 的脚本大小限制从 Free 的压缩后3MB、Paid 的压缩后10MB，改为各方案统一的非压缩64MiB，即67,108,864字节。标题写 MB，但实验命令与容量判断采用 MiB。这是对既有变化的实测，不是10月11日再次发布的新额度。

**为什么要区分计量方式。** 高重复字符串的 gzip 文件可以很小，但解压后代码很大；随机数据则难压缩。新规则不再以 gzip 后的数值判断，所以只盯构建工具的压缩报告会误读余量。原文用 `wrangler deploy --dry-run` 查看 `Total Upload` 与 gzip 两个值，先在本地验证产物计量，再实际部署到 Free 账户。

**实验环境。** 作者使用 Ubuntu 24.04 arm64 的一次性容器、Node 24.21.0、Wrangler 4.149.0，并明确只测 Free。dry-run 不需要登录，但真实部署需要其 Cloudflare 账户。这些实验是作者的记录；日报没有执行部署命令，也没有把示例容器当成所有系统都适用的必要环境。

**压缩差异的对照。** 约200万字符的重复文本得到约2,000,212字节未压缩文件、2,159字节 gzip；工具显示1953.33KiB与2.10KiB。随后加入8MiB随机数据，得到8192.21KiB、gzip6170.27KiB，超过旧 Free 压缩额度，却部署成功，公开请求返回 `len=8388608`。这个实例支持“旧压缩上限已不再阻挡该产物”，而不是证明所有8MiB依赖都能迅速启动。

**超限测试。** 重复65MiB文本得到66560.21KiB、gzip仅64.91KiB，部署以10027拒绝。与随机样本一起看，极高压缩率无法绕过新的非压缩限制。作者没有给64MiB恰好边界的逐字节测试，不能把65MiB失败说成已经测定了所有边界细节。

**部署后的短暂异常。** 实验曾在刚部署时遇到1042，约5秒后再部署可以返回结果；约1KB的对照 Worker 也出现同类情况。作者推测是部署传播过程，但没有验证根因。因此不能断言异常由大文件引起，也不能保证等待固定5秒一定恢复。

**工程判断与限制。** 尺寸额度取消的是旧计量门槛，并没有提供性能结果。原文未实测 Paid，未验证1秒启动限制下的复杂初始化，也没有首请求时延、内存或依赖加载基准。项目中可把非压缩体积作为准入检查，再独立测初始化和真实请求；这是读后设计建议，不是本例给出的速度保证。

**阅读价值：** 通过随机与重复载荷，清楚区分构建体积、部署额度与未测性能，适合前端及边缘部署评审。

### 4. Capacitor の iOS アプリで音が鳴らない・途中から鳴らなくなる原因 3 つ

**原文：** https://zenn.dev/mohhh_ok/articles/2026-10-capacitor-ios-web-audio-silent

**发布时间：** 2026-10-11 23:31:01 JST

**不是一种故障。** 作者的 Capacitor 日语学习应用在 iPhone 12、实际 iOS 26.6.1 上出现媒体加载误判、锁屏后无声，以及部分页面空白三类问题。User-Agent 仍显示 iPhone OS 18_7，不能拿它推断真实系统版本。原文强调浏览器、模拟器和真机的行为不同；日报按取得字节、解码、音频时钟及构建产物分别解释。

**第一类：把本地媒体当 HTTP 失败。** 应用以 `capacitor://localhost` 读取打包 MP3。作者检查 WebViewAssetHandler.swift 后发现媒体扩展名返回普通 URLResponse，其他资源走 HTTPURLResponse。模拟器日志显示 fetch 的 status=0、ok=false、type=basic，同时得到4652字节，decodeAudioData 可以成功。旧代码只要 `!res.ok` 就抛错，因而在解码之前误拒合法的本地媒体。

**修复与适用边界。** 作者让本地媒体取得逻辑接受 `res.ok || res.status === 0`。关键是已确认自定义本地协议下有字节且可解码，不能把这个条件无差别应用到远程 API、CORS 失败或所有 status=0 请求。状态码是排查线索，而非证明文件正确；仍应验证字节、解码和实际播放。

**第二类：状态运行但时钟停止。** 锁屏约1–2分钟后，Debug 日志每15秒记录 AudioContext。解除锁屏后其 state 仍为 running，但 currentTime 固定在48.459，音频不响，onended 也不触发。只检查 suspended 或调用 resume 无法覆盖这个观测到的状态。作者用 visibility 标记离开前台，在下一次用户点击的同步事件处理中关闭并重建 AudioContext。

**重建对象的细节。** AudioBuffer 可复用，但 GainNode 属于创建它的 context，应检查 `node.context` 并重建与旧 context 绑定的节点。作者的 Debug 锁屏测试恢复了声音，不需重启应用；锁屏时 Mac 日志连接断开，没有直接记录整个重建过程，TestFlight 的复测还在进行。我们因此保留“Debug 中复旧”的条件，不声称正式发布版本已经全面解决。

**第三类：构建环境与页面空白。** 独立问题来自 git worktree 未带 `.env`。Bun 的 `env: "BUN_PUBLIC_*"` 需要构建时注入 RevenueCat 的公开客户端配置；缺少配置时，产物留下 `process.env.BUN_PUBLIC_REVENUECAT_APPLE_KEY` 表达式。作者观测 API 返回200而页面仍空白，补齐环境重新构建后真机恢复。模拟器的表现不同，精确异常链并未完全证实，所以不能认定所有页面空白都由该键造成。

**可复用的验证思路。** 构建时可检查必要公开配置为空或表达式残留，并对真机做锁屏恢复测试。这不授权把服务端机密嵌入前端；Debug 日志中的会话数据也不该提交到 Git。取得成功、decode 成功、context 状态和真实听见声音是不同证据。这个分层判断来自本文案例，不能扩大为所有 Capacitor 版本的通用缺陷。

**阅读价值：** 该案例同时记录本地媒体字节、音频时钟和构建配置，能形成真机音频排障的具体步骤。

### 5. Zed 1.23.2でJSONL / NDJSONのログをテーブル表示する

**原文：** https://dev.classmethod.jp/articles/zed-1-23-jsonl-ndjson-table-preview/

**发布时间：** 2026-10-12 03:06:45 JST

**功能的背景。** Zed 稳定版1.23.2于10月7日加入 JSONL / NDJSON 的表格预览，10月11日原文给出操作验证。原有 CSV / TSV 表格功能自1.17提供，此次扩展到一行一个 JSON 对象的日志文件。它主要改善人工查看平坦记录的体验，不等于提供完整日志数据库或复杂查询引擎。

**环境和入口。** 作者在 macOS 26.6.1、Apple Silicon、默认配置与快捷键下测试。macOS 用 cmd-k 后接 v 开启预览；官方给 Linux / Windows 的对应组合是 ctrl-k 后接 v，但原文只测 macOS。日报保留其他平台快捷键的说明，不把它说成跨平台实测结果。

**简单记录如何成表。** 三条日志分别有 id 1、2、3和 info、warn、error 级别。键名形成列；数值1与字符串内容的显示保留类型线索，字符串的引号也有助于区分。以相同列对齐记录，可以直接比较某一字段，而不用逐行在 JSON 文本中寻找位置。

**排序入口容易误解。** 点击列名只出现复制列名相关提示，并不排序；排序要用列的上下箭头图标。按 level 的 A–Z 排序后是 error、info、warn，左侧原行号仍为3、1、2。这既说明视觉顺序已改变，也提供回到原日志位置的线索，不应把显示位置当成新的事件时间顺序。

**过滤、缺失和嵌套。** 漏斗按钮列出字段值及计数，选 error 后只留下对应一行。不同记录的键不一致时，表格取所有键的并集，缺键处为空白，不能仅凭空白区分字段不存在、数据为空或上游采集失败。嵌套 detail 对象留在一个 JSON 字符串单元格中，不会展开子列。

- 词性：名詞
- 含义：一次性使用、用后丢弃
- 搭配：使い捨ての環境 / 使い捨ての容器
- 文章语境：Worker测试使用一次性Ubuntu容器。
- 例句：検証には使い捨ての環境を用意しました。
- 例句译文：为验证准备了用后丢弃的环境。
- 语感区别：技术语境强调环境生命周期，不是性能快慢。

### 13. 混み具合（こみぐあい）｜N2

- 词性：名詞
- 含义：拥挤程度、繁忙状况
- 搭配：サーバーの混み具合 / 時間帯による混み具合
- 文章语境：Decisions耗时受测量时服务器繁忙情况影响。
- 例句：応答時間はサーバーの混み具合によって変わります。
- 例句译文：响应时间随服务器繁忙程度而变化。
- 语感区别：不必引入更多英语术语也能口头说明负载状态。

### 14. 後述（こうじゅつ）｜N2

- 词性：名詞・サ変
- 含义：在后文说明
- 搭配：後述の手順 / 詳しくは後述する
- 文章语境：技术文章先给结论，稍后展开设置或限制。
- 例句：詳しい設定手順は後述します。
- 例句译文：详细配置步骤在后文说明。
- 语感区别：书面表达，不宜在口头回答中反复用来跳过说明。

### 15. 先頭（せんとう）｜N2

- 词性：名詞
- 含义：最前面的项目
- 搭配：先頭の項目 / 列の先頭
- 文章语境：AWS profile参数省略时采用列表首项。
- 例句：指定がなければ、先頭のプロファイルが使われます。
- 例句译文：未指定时使用首个profile。
- 语感区别：重点是顺序位置，不表示最重要或权限最小。

### 16. 伸びる（のびる）｜N3

- 词性：動詞・一段
- 含义：延伸、变长
- 搭配：線が伸びる / 期間が伸びる
- 文章语境：Zed发布说明提到行分隔线延伸到最后列之外的旧显示问题。
- 例句：行を増やすと、区切り線が下まで伸びました。
- 例句译文：增加行后，分隔线延伸到了下方。
- 语感区别：此处是长度变化；不是自动推断性能或业绩提升。

## C-2. IT/AI 专业词汇

1. **aws_profile（AWSプロファイルの指定）**：每次AWS MCP调用选择本地凭证配置的参数。 省略时使用允许列表先头配置，必须核实默认账户。

2. **AWS_MCP_PROXY_PROFILES（利用可能なプロファイルの一覧）**：代理允许选择的profile名称列表。 列表和IAM权限是不同约束。

3. **predicate（条件の判定）**：判断给定条件成立概率的接口功能。 Decisions照合需在instructions写真假条件。

4. **exact / semantic（文字列一致／意味の一致）**：分离字面相同与业务含义相同两种评价任务。 两种问题的有效分母不同，不能混报。

5. **Total Upload（非圧縮のアップロード量）**：Wrangler展示的上传产物大小。 Workers额度改按非压缩64MiB判断。

6. **AudioContext（音声処理のコンテキスト）**：Web Audio中管理音频节点及时间的对象。 running不代表currentTime必然在推进。

7. **URLResponse（URLの応答情報）**：原生端表示URL资源返回结果的对象。 Capacitor本地MP3路径并非HTTPURLResponse。

8. **JSONL / NDJSON（一行ごとのJSON）**：每行一个JSON值，本文日志每行为对象。 Zed形成列但不自动展开嵌套对象。
