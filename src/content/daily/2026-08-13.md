## 1. 今日最值得看的 5 篇

### ① Claude Team / ChatGPT Business / Gemini Enterpriseを企業統制の観点で比較

**来源：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/summer-project-2026-ai-plans-admin-governance-comparison/

企业选型首先要明确：管理员能限制哪些行为，使用者能否覆盖这些限制。作者实际购买 **Claude Team、ChatGPT Business 和 Gemini Enterprise Standard**，从管理界面比较组织治理。调查对象主要是中小规模组织套餐，并非对三家公司所有 Enterprise 功能进行完整测评。

Claude Team 的「组织指示」覆盖所有用户与会话，与个人指示冲突时优先采用组织指示。作者检查的 ChatGPT Business 与 Gemini Enterprise Standard 普通聊天界面中，没有找到同等的全组织强制指示设置，但可以给专用代理配置指示。Gemini 的 **Prompt Chips 是供用户选择的提示辅助**；Model Armor 则检测和阻断有问题的输入、输出，两者都不应与强制下发共同提示词混为一谈。

外部服务治理也有不同粒度：Claude 先由管理员添加允许使用的连接器，再由用户认证自己的账号，部分操作可设为允许、逐次确认或阻止。ChatGPT 的应用也可限制操作，但支持范围取决于应用实现。Gemini 按数据存储管理连接，对 Google 与 Google Cloud 服务划分较细。实际选型要分别确认**能否连接一个服务，以及连接后能否发送邮件、创建工单等写入操作**。

Claude Code 的 **Managed settings** 可通过组织配置或 MDM 分发 JSON。示例用 `permissions.deny` 禁止读取秘密文件或运行指定命令，并用 `allowManagedMcpServersOnly` 限定 MCP；还涉及管理 Hooks、沙箱与 OpenTelemetry 日志发送。作者检查的 ChatGPT Business 中，Codex 管理主要覆盖共同指示、云端容器、仓库权限及连接器；可比的细粒度强制策略需要 Enterprise 套餐。

Gemini Enterprise Standard 附带的 Antigravity 要求**使用开具账单的 Cloud Billing 账号**，普通在线自助付费账号不在该使用范围。把本地 `settings.json` 放到指定目录能配置行为，但启动参数可覆盖它，不能当作组织强制策略。原文证据来自界面与规格检查，没有攻击测试或审计合规实验；因此应核实套餐、策略优先级和操作权限，而不是直接给出某产品“最安全”的结论。

**关注点：★★★★★**

用具体管理选项说明提示词、操作权限和不可覆盖策略的区别，让企业治理判断落到实际可配置的边界。

### ② NVIDIA NeMo Switchyard：Taskに応じてLLMを動的Routing

**来源：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/nvidia-nemo-switchyard-v020-rust-first-touch/

NeMo Switchyard **v0.2.0** 把路由实现从 Python 重写为 Rust，提供独立的 `switchyard-server`，接收 OpenAI Chat Completions、Responses 和 Anthropic Messages 三种请求格式。旧 `route.yaml` 改为 **`routes.toml`**，按 `llm_clients`、`targets`、`routes` 分离连接、模型和路由。`--dry-run` 可在启动前发现未知字段。作者的容器构建总耗时84秒，其中 `cargo install` 70秒，镜像187MB；这是其本地构建结果。

capability 模式让判定模型估计轻量模型完成任务的概率 **`p_solve`**，再与阈值比较。作者设置 `base_threshold = 0.75`、`threshold_step = 0.1`，对应擅长、不确定、不擅长领域的0.75、0.85、0.95。校准集包括40个真实会话形态和47个单次提示：0.75时，13个深入讨论问题中12个进入上位模型，40个代码任务仍留在轻量侧；升到0.80后开始把日常代码工作也送到上位模型。**该数值取决于任务和模型组合，不能复制成通用最佳值。**

`recent_turn_window = 4` 把最近的工具结果等提供给判定模型。作者用40个代码会话案例，包含交换执行顺序后的复测，共做320次判定；路由差异在40件中不超过1件，思考 Token 从1,713降到254，判定耗时中位数从17.5秒降到3.1秒。但讨论型会话可能因轻量模型的回答看似合理而偏向轻量侧。另一项在同一87次判定集上的思考抑制比较，中位数由10.4秒降到2.2秒，P90由44.5秒降到4.4秒；文中列出的30个真实工作形态判定全部一致。

escalation 模式先用轻量模型，连续两次判为陷入困境后锁定到上位模型。作者构造重复 ImportError、无关修改和误报完成的轨迹，两轮后触发升级；持续做相关修复但测试仍失败的轨迹没有升级。代价是升级前要缓存整段回答，确认升级的那一轮还会支付两侧费用：固定轻量路线原本分361个流式片段返回，升级路线变成1个片段。因此便宜与交互顺畅并不总是同时改善。

| 路线 | 文中评分 | 每次费用 | 实际耗时中位数 |
| --- | --- | ---: | ---: |
| 固定 Kimi K3 | 满分 | $0.0352 | 49秒 |
| auto | 满分 | $0.0007 | 12秒 |
| auto-esc | 满分 | $0.0021 | 23秒 |
| 固定 DeepSeek V4 Flash | 满分 | $0.0008 | 12秒 |

表中每条路线运行10次代码修正与3次工具调用，共52次，全部完成。**auto 节省98%的前提是轻量模型单独也能满分，且没有一次调用上位模型**，所以只证明避免了不必要的升级，不能证明困难任务也保持质量。作者团队另一项实际工作验证为27%节省。文中引用的 LangChain 节省74%、上位调用7%，以及 Cognition 节省约28%、精度差不超过2.8个百分点，也分别属于其他评估。

判定模型小版本更新后，同样50段会话的轻量分配曾从39段降到1段；8个模型、2种提示和87个输入组成的1,392次判定，轻量分配比例更分散到0～100%。还有14个竞赛编程难题全部被分给轻量模型的反例。应使用 `/v1/stats` 和 `--routing-log-file` 观察分布，更新后重新校准，并保留人工切换强模型的路径。项目仍标为 pre-alpha，上述数据应按各自条件阅读。

**关注点：★★★★★**

把轻量模型基线、判定模型开销、版本漂移与流式体验一起纳入模型路由设计，而不是只记住一个节省百分比。

### ③ Claude Code Self-hosted Environment：EC2をAgent実行環境にする

**来源：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/claude-code-self-hosted-runner/

Claude Code on the Web 的自托管环境把任务执行部分移到企业自己的网络中。该功能在 v2.1.224 出现，按原文2026年8月12日的状态，属于 **Team 与 Enterprise 套餐的公开测试版**。它适合连接不对公网开放的内部服务、数据库或镜像仓库，也能预装公司所需的 SDK 和编译器；相应地，运行器、镜像和网络的维护成本由企业承担。

**Environment / Pool** 是一组运行器的逻辑目的地。运行器用环境密钥注册，轮询任务队列，领取会话后克隆仓库，再启动 Claude Code 子进程。通信由企业网络向外发起 HTTPS，不需要 Anthropic 入站连接。检出的代码和构建产物留在自有基础设施，然而**提示词、回答、工具执行结果仍发送到 Anthropic 用于推理，会话记录也保存在对方平台**。因此自托管执行不等于自托管模型、控制平面或全部数据。

作者在 Team 套餐下使用一台位于私有子网的 **EC2 `m8i-flex.large`，系统为 Ubuntu 24.04**，通过 NAT Gateway 出站，用 SSM Session Manager 管理，安全组没有入站规则。除了 API 所需的443端口，还因默认 apt 镜像使用 HTTP 而开放80端口。这是该实验系统安装软件的条件，不应写成所有运行器的固定网络要求。

首次执行 `claude self-hosted-runner` 后，任务因 GitHub 认证缺失而在 `git ls-remote` 失败。加入 **`--use-anthropic-git-proxy`**，借助会话创建者的认证通过代理克隆后，任务恢复并成功返回结果。这个过程说明环境注册和仓库访问认证是两件需要分别配置的事。

当前验证只有一台运行器，未设置 `--capacity`，所以默认并发为1。原文还保留了会话不能及时释放、新 SSM 会话未加载 PATH、没有配置 systemd 常驻服务等问题；管理会话一结束，运行器便不再被识别。**可启动不代表可稳定运营**。文章提供了部署实验与故障修复记录，没有压力测试或成本比较；企业应先确认内部访问需求和会话外发范围，再完成并发、常驻服务与退出清理设计。

**关注点：★★★★★**

用 EC2 部署中的实际失败说明执行环境、仓库认证和云端推理边界，避免把自托管误解为完全不出网。

### ④ Nemotron 3.5 Lightning：常駐Agent向けオープンモデル

**来源：ITmedia AI＋**

**原文：** https://www.itmedia.co.jp/aiplus/article/2608/12/2000000503/

NVIDIA 于8月11日发布面向常驻代理的 **Nemotron 3.5 Lightning**，报道列举 OpenClaw、Hermes Agent 等用途。模型总规模 **30B，推理时激活3B**，通过 MoE 按输入选择部分专家参与运算，减少每步计算。激活参数少说明计算路径较轻，并不能据此把整个模型的存储与内存占用也当成3B模型。

高速生成还采用**推测式解码与量化**：前者先生成候选再验证，后者用低比特表示权重。报道将保持精度同时提高生成速度作为提供者的主张呈现。这解释了优化机制，但没有证明读者自己的机器、推理软件和业务负载会得到同样收益。

报道援引 Artificial Analysis：Intelligence Index 为 **24分**，比 Nemotron 3 Nano 高9分，与 gpt-oss-120b 同分，输出速度约每秒670 Token。需要保留证据边界：此文没有完整列出硬件、并发、输入输出长度等复现速度所需条件；一个综合分数相同，也不代表所有工具调用、长期执行或行业任务都同等可靠。

模型权重、训练数据与配方按 **OpenMDW-1.1** 许可在 Hugging Face 等渠道提供。原文是发布报道，而非作者在本地运行的测试报告，没有长期代理成功率或总拥有成本实验。实际采用前应核实许可和内存需求，再用要长期重复执行的工作测量错误与速度；这些属于应用验证建议，不是文章已完成的结果。

**关注点：★★★★★**

区分总参数、激活参数与部署资源，把第三方综合评分和实际代理任务能力分开判断。

### ⑤ Grok Bot：Agentが実際の業務アプリを操作

**来源：ITmedia AI＋**

**原文：** https://www.itmedia.co.jp/aiplus/article/2608/12/2000000505/

SpaceXAI 于8月11日公布 **Grok Bot 早期测试版**，在云端电脑中登录 Gmail、CRM 等业务应用，按画面操作推进工作。用户可从手机或电脑发消息委托任务，需要批准时由 Bot 请求确认。由于直接使用界面，发布方称它也能处理没有 API 或 MCP 的工具。

发布内容介绍了从演示中记住流程：观察用户操作，将步骤保存为例行程序，供以后执行；经过几次任务后，逐渐记住表达习惯和例外，判断何时询问用户。文章没有展开学习算法、记忆隔离或删除机制，因此“越来越聪明”属于发布方的产品描述，不能改写成错误率已下降的测量结论。

多个 Bot 可以互相发送消息、共享上下文、分配任务，并由一个统筹角色协调。举例包括根据通话记录更新 CRM 并起草后续联系、处理账单，以及在产品界面复现 Bug、建工单后交给修复 Bot。**这些是提供者内部使用案例，不是独立的成功率、误操作率或费用对比实验**，不能由此保证跨公司、跨应用稳定执行。

按报道时的条件，功能面向 **SuperGrok Heavy、Cursor Ultra、Cursor Teams Premium** 用户，支持 macOS、Windows、iOS，以及 Debian／Ubuntu 的 x64 `.deb`；Android 尚不支持。企业应核实哪些步骤可自动执行、哪些操作必须确认，并检查真实写入结果。操作后回读邮件或 CRM 状态是据此提出的验证建议，文章没有据此证实完整审计、回滚或故障恢复能力。

**关注点：★★★★★**

从界面操作、流程记忆与多 Bot 协作的具体机制出发，识别发布演示没有覆盖的批准与结果验证条件。

## 2. 分类摘要

### AI

Switchyard 选择调用哪个模型，Nemotron 的 MoE 选择模型内部的计算部分。两种节省机制处于不同层面。

### Frontend

Grok Bot 涉及业务界面操作，但今天的五篇中没有前端渲染性能对比文章。

### Cloud / Backend

EC2 运行器让任务访问内部资源，同时保留向云端推理和控制服务的通信。

### 日本企业 Tech Blog

DevelopersIO 的管理界面比较、路由测量和 EC2 故障修复分别提供不同性质的证据。

## 3. 面接で使えるポイント

### 話題1：AI Governance

**面试问题：**

> 生成AIを組織に導入するとき、管理機能をどう比較しますか。

**约 30 秒自然日语回答：**

> 管理者の設定が、利用者の操作で上書きできないかを確認します。Claude Teamでは、組織の指示に加え、Managed settingsでコマンドや接続先を制限できます。一方、Geminiのプロンプト チップは利用者が選ぶ仕組みです。接続と書き込みの許可も別に調べます。契約条件も含め、共通の指示と強制的な権限制御を分けて比較します。

**関連Project（学習用）：** 制作管理设置是否可被覆盖的检查表。

**キーワード：** `Managed settings` / `プロンプト チップ` / `Model Armor`

### 話題2：Model Routing

**面试问题：**

> モデルの自動振り分けで、費用と品質をどう確かめますか。

**约 30 秒自然日语回答：**

> 軽量モデルを単独で使う場合も基準に入れて比較します。Switchyardのcapabilityモードは、完遂確率を閾値と比べて振り分けます。判定にかかる時間も測ります。ただし、記事の98%削減は軽量側だけでも満点の課題でした。難しい問題を混ぜて品質を確かめ、判定モデルを更新した際には、振り分けの分布と閾値を測り直します。

**関連Project（学習用）：** 用同一组任务比较固定路线和自动路线。

**キーワード：** `p_solve` / `capability` / `routes.toml`

### 話題3：Claude Code / Runtime

**面试问题：**

> エージェントを自社サーバーで動かせば、情報は社外へ出ませんか。

**约 30 秒自然日语回答：**

> 実行場所と推論先を分けて確認します。Claude Codeのセルフホスト環境では、ランナーがキューを取得し、EC2上で作業します。ただし、会話やツール結果はAnthropicへ送信されます。記事ではGit認証も別途必要でした。常駐化や会話の保存先も確認します。内部サービスに接続できることと、情報が外へ出ないことは同じではありません。

**関連Project（学習用）：** 分别画出运行器注册与 Git 认证流程。

**キーワード：** `Environment / Pool` / `--use-anthropic-git-proxy` / `EC2`

### 話題4：Local LLM / Agent

**面试问题：**

> 小型のオープンモデルを選ぶとき、パラメータ数をどう読みますか。

**约 30 秒自然日语回答：**

> 総数と、推論時に動く部分を分けて見ます。Nemotron 3.5 Lightningは30Bですが、MoEで動くのは3Bです。計算を抑える仕組みがあっても、全体のメモリが同じだけ減るとは限りません。総合スコアだけでは決めません。公表された速度は測定条件にも依存するので、使う機器で必要なメモリと継続動作の正確さを確認します。

**関連Project（学習用）：** 在目标机器测量必要内存与业务执行速度。

**キーワード：** `MoE` / `30B / 3B` / `OpenMDW-1.1`

### 話題5：Computer-using Agent

**面试问题：**

> 画面を操作するエージェントを、業務でどう検証しますか。

**约 30 秒自然日语回答：**

> 実行できる範囲と、承認が必要な操作を先に決めます。Grok Botは画面を使うため、APIがない業務アプリも対象にできます。作業をルーティンとして覚える一方で、早期ベータで成功率は未公表です。契約プランと対応端末も確かめます。CRMの更新など一つの仕事で、例外時に止まれるかと、書き込み後の内容が正しいかを確認します。

**関連Project（学習用）：** 为 CRM 更新设计批准条件和完成检查。

**キーワード：** `Grok Bot` / `ルーティン` / `CRM`

## 4. 今日技术主题

### 分别设计代理的权限、模型分工和执行地点

先确定组织允许什么，再决定任务交给哪个模型、在哪个环境执行。Managed settings 管操作权限，Switchyard 管模型分流，自托管运行器管执行地点；MoE 则属于模型内部计算，Grok Bot 的界面操作属于业务应用交互。各层解决的问题不同，不能用一个功能替代所有边界设计。

```text
核实组织权限与套餐
    ↓
按任务选择模型
    ↓
确认执行环境与外发信息
    ↓
通过工具或界面完成业务
    ↓
检查成果物、费用与例外
```

**优点：** 管理比较可以落到强制策略，模型选择可以加入轻量基线，执行环境选择可以解释内部连接需求。

**限制与注意点：** 自托管仍有会话外发；轻量任务集上的98%节省，以及提供者描述的 Bot 案例，都不能直接推广到全部业务。

**日本企业应用：** 分别向管理员确认禁止操作，向开发者确认内部连接，向业务部门确认完成标准，再映射到套餐与实际配置项。这是基于今天文章提出的设计练习。

## 5. 面试复习卡

### Q1

> 組織の指示と権限制御は、何が違いますか。

**回答ポイント：** 組織の指示は回答の方針を与えます。権限制御は実際に許す操作を決めます。利用者が変更できる設定か、管理者が強制する設定かも確認します。

### Q2

> Switchyardの98%削減を、そのまま採用理由にできますか。

**回答ポイント：** 軽量モデル単独でも満点の課題での結果です。難問を含む評価と軽量固定の基準を加え、判定費用や振り分けの変動まで確認します。

### Q3

> セルフホスト環境で、どの情報がクラウド側に残りますか。

**回答ポイント：** 会話やツール結果は推論のため送信され、会話記録はAnthropic側に保存されます。自社側へ移るのはセッションの実行です。

# B. 重点知识与面试应用

## 1. Claude Team / ChatGPT Business / Gemini Enterpriseを企業統制の観点で比較

1. 组织提示词与输入输出检查解决不同问题。
2. 外部服务的连接权限和写入权限要分别检查。
3. 套餐与检查时点限制了这次比较的适用范围。

## 2. NVIDIA NeMo Switchyard：Taskに応じてLLMを動的Routing

1. 判定模型更新本身就可能改变分流比例。
2. escalation 为单向升级，需考虑升级前不能正常流式输出及确认轮双重费用。
3. 98%节省的测试中轻量模型单独也满分，不构成困难任务质量保障证据。

## 3. Claude Code Self-hosted Environment：EC2をAgent実行環境にする

1. 自托管迁移的是执行部分，推理和控制平面仍在云端。
2. 环境注册密钥与 Git 认证作用不同。
3. 单机启动验证之外，还要处理常驻服务、并发和会话释放。

## 4. Nemotron 3.5 Lightning：常駐Agent向けオープンモデル

1. 30B 指总参数，3B 指推理激活部分。
2. 24分与约670 Token/秒是报道引用的外部结果，不是本地性能保证。
3. 公开权重、数据和配方仍需核实相应许可条件。

## 5. Grok Bot：Agentが実際の業務アプリを操作

1. 直接操作界面扩展了 API 以外的应用范围，但可靠性仍需验证。
2. 流程记忆和多 Bot 协作属于提供者披露的机制及案例。
3. 套餐、操作系统支持和早期测试状态都是采用条件。

## C-3. JLPT文法

### 1. ～にとどまらず
**Level：N1｜意味：** 不仅限于……  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 说明 Agent Governance 不只管 Model，也要覆盖 Tool、Network 和 Runtime。  
**例：** `管理者は接続の許可にとどまらず、操作の範囲も確認します。`  
**補足：** 用于范围扩展。

### 2. ～かねない
**Level：N1｜意味：** 有可能导致不良结果  
**形：** `動詞ます形去ます + かねない`  
**使い方：** 警示过度授权或无隔离运行可能造成事故。  
**例：** `一つの削減率を一般化すると、導入判断を誤りかねません。`  
**補足：** 通常用于负面风险。

### 3. ～なくしては
**Level：N1｜意味：** 没有……就无法……  
**形：** `名詞 + なくしては`  
**使い方：** 强调 Audit、Policy Enforcement 等是企业 Agent 运用的基础条件。  
**例：** `条件の確認なくしては、測定結果を正しく比較できません。`  
**補足：** 语气较强，适合强调必要前提。

### 4. ～に応じて
**Level：N2｜意味：** 根据……相应调整  
**形：** `名詞 + に応じて`  
**使い方：** 用于按任务难度、风险和成本切换 Model 或权限。  
**例：** `タスクの種類に応じて、判定の閾値を変えます。`  
**補足：** 强调条件与对应措施。

### 5. ～一方で
**Level：N2｜意味：** 另一方面……  
**形：** `普通形 + 一方で`  
**使い方：** 说明 Agent 自动化带来的收益和风险。  
**例：** `軽量モデルは費用を抑える一方で、難問では確認が必要です。`  
**補足：** 适合说明 Trade-off。

### 6. ～に基づいて
**Level：N2｜意味：** 基于……  
**形：** `名詞 + に基づいて`  
**使い方：** 说明权限与 Routing 应依据 Policy 或数据。  
**例：** `実際の会話に基づいて、ルーターを較正します。`  
**補足：** 明确表示判断依据。

### 7. ～にかかわらず
**Level：N2｜意味：** 不论……都……  
**形：** `名詞 + にかかわらず`  
**使い方：** 表达所有 Agent / Environment 都必须遵守的共同安全规则。  
**例：** `実行場所にかかわらず、外部への送信内容を確認します。`  
**補足：** 适合说明与条件无关的统一规则。
