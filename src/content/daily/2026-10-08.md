### 1. Claude Code v2.1.292 の主要アップデート - stdio MCP のプロトコル既定化とサブエージェントの effort 指定

**原文：** https://dev.classmethod.jp/articles/20261007-cc-updates-v2-1-292/

**发布时间：** 2026-10-07 12:09:47 JST

v2.1.292 于 10 月 6 日发布，原文在 10 月 7 日整理 92 项变化，并实际检查子代理的 effort 参数。作者按自己的分类统计了修复、安全、改善等类别；这些数量代表变更条目，不能解释为错误率下降或性能提升幅度。Agent 工具现在可以在单次调用中指定 effort，与代理定义的 frontmatter 设置是不同入口；工具说明要求用户、CLAUDE.md 或技能明确指定时才传入，不能把文章示例当成任意扩大自主执行的授权。

作者尝试 low、medium、high、max、xhigh 等值，其中 ultra 返回 InputValidationError。部分子代理的自述与指定值不一致，文章因此同时查看调用记录和子代理元数据。这里核实的是参数接受与记录情况，不是相同任务下的质量、耗时或成本实验；不能从子代理说“我用了某个等级”推断其实际推理预算，更不能保证 high 的结果一定更正确。迁移到企业工作流时，可将委任参数和产物验收分别记录，这属于基于原文的设计整理。

兼容性变化集中在 stdio MCP：2026-07-28 协议协商成为所有安装的默认路径，范围包括 Bedrock、Vertex 和 Foundry。支持协商的服务器走新协议，不支持的服务器可退回旧握手；无响应的兼容性结果会记住 7 天。MCP_PROTOCOL_NEGOTIATION=legacy 提供回退入口，但已协商 v2 的通道不支持原有 channel messages，应分别检查服务器连接和通道行为。另一个执行生命周期变化是 claude -p / SDK 会等待后台命令及计划唤醒，不再在最终输出后按旧的约 5 秒行为结束，因此外层超时需要重新评估。

其他修复也有明确边界：超长工具名会从发送清单中排除；Grep/Glob 遇到读取权限失败会重试或报告，而不再把失败伪装成空结果；插件测试中 expect/stub hook 的失败也会让测试失败。Windows UNC 和 8.3 路径相关的权限修复说明升级涉及安全边界，不过原文并未对所有环境做独立安全审计。阅读价值在于把输入参数、协议协商、真实错误和最终产物串成检查链，而不是仅凭版本升级就断言全部风险消失。

**阅读价值：** 这篇文章把参数指定、协议兼容性和可观察结果分开，适合练习“配置已生效”与“产物已正确”的不同验收。

### 2. Amazon EC2 の AMI の新機能「共有タグ」を試してみた

**原文：** https://dev.classmethod.jp/articles/ec2-ami-shared-tags/

**发布时间：** 2026-10-07 14:41:21 JST

EC2 的共享标签把 AMI 元数据随镜像共享给其他账号。原文介绍 10 月 5 日发布的功能，并在东京区域用两个账号实测：复制 Amazon Linux 2023 x86_64 的 AMI，镜像来源通过 SSM 的 /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 获取。普通标签仍由各账号自行使用；所有者给标签键增加 ec2:SharedTag/ 前缀后，该键值才作为共享信息展示。官方能力范围包含指定账号、Organizations 和公开镜像，但本文的实际实验是两账号共享。

所有者添加 status=approved、os-version=2023.12.20260930.0 的共享标签，再以 modify-image-attribute 授予另一个账号启动权限。使用者通过 describe-images 可以看见共享标签，使用 executable-users self 和标签键过滤也可检索。这使镜像版本与生命周期状态能在所有者处统一维护，无需每个账号分别抄写。共享标签的可见性不替代 AMI 的启动授权，两者是独立设置。

权限测试分别尝试更新、删除和新建共享标签，使用者侧均返回 AccessDenied；CreateTags/DeleteTags 要求对镜像拥有所有权。使用者仍可添加自己的普通标签。所有者把 approved 改成 deprecated 后，使用者视角约 5 秒显示新值；这只是原文的一次观察，不是所有区域、账号或负载下的传播时限保证。本文也没有测试 Organizations 或公开共享的完整行为。

对 Golden AMI 管理而言，共享标签适合承载批准状态和版本信息，但状态变成 deprecated 并不意味着系统自动阻止实例启动。部署流程仍需读取标签、定义允许使用的状态并处理查询失败，这一建议是根据权限与可见性结果作出的设计判断。原文称功能覆盖全部区域且不额外收费，不能据此忽略 EC2、镜像存储或自建治理流程本身的成本。

**阅读价值：** 通过同一 AMI 的所有者与使用者视角，具体理解可见性、修改权限和部署策略的边界。

### 3. LTE ルーター Teltonika RUT956 を経由して配下のマシンへ WireGuard でリモートアクセスしてみた

**原文：** https://dev.classmethod.jp/articles/wireguard-remote-access-via-teltonika-rut956/

**发布时间：** 2026-10-07 14:48:23 JST

原文的场景是制造业 PoC：现场机器不能接入原有网络，LTE 又处于 CGNAT 后，外部不能直接向路由器发起连接。作者用带公网静态 IP 的 Lightsail 作为 WireGuard 中心，RUT956 和客户端主动连接到中心。这里减少的是现场侧公网入口需求；中心仍必须开放 UDP 51820，不能把结构描述成整个系统没有入站端口。实验使用东京区域 Ubuntu 24.04 LTS、512 MB Lightsail，RUT956 的 RutOS 固件 RUT9M_R_00.07.24.3 和 SORACOM plan01s。

地址分为 VPN 的 172.16.100.0/24 和现场 LAN 的 192.168.77.0/24。中心的路由器 peer 的 AllowedIPs 包含 172.16.100.2/32 与 LAN 网段，客户端也配置 VPN 和 LAN 两个范围。RUT956 启用 Route AllowedIPs，中心允许 IPv4 转发，PersistentKeepalive=25 用于维持 NAT 映射。密钥的生成和授受由自己负责；原文展示配置方法并不意味着可以公开私钥，也不替代对每个 peer 可访问网段的控制。

作者用 MacBook Air M4（macOS 26.6.2）检查握手、路由器与 Raspberry Pi 4 的 ping，并通过 IINA 查看 Tapo C210 的 RTSP 图像。三次 ping 的平均值分别约为中心 6.599 ms、路由器 13.667 ms、树莓派 15.356 ms，均无丢包；这是很小的样本，不能推广为 LTE 的长期延迟或可靠性指标。Android 用二维码导入配置后也能访问。成功标准由握手继续延伸到 LAN 终端和实际视频应用。

另一次本地 SSH 的 No route to host 并非隧道故障，而是 macOS 对终端应用的本地网络权限，开启权限后解决。这个例子提醒排查应分隧道、路由、转发和应用端权限。原文以 512 MB、每月 5 美元且包含 1 TB 流量的 Lightsail 方案比较托管 VPN，但它不是完整总成本分析：中心运维、补丁、密钥撤销、故障恢复仍由使用者承担。这些责任与原文实测连通性应分别判断。

**阅读价值：** 用具体拓扑说明 CGNAT、隧道、LAN 路由和应用访问不是同一层的成功条件。

### 4. Amazon Bedrock で Claude Haiku 5.5 が利用可能になりました

**原文：** https://dev.classmethod.jp/articles/bedrock-claude-haiku-5-5/

**发布时间：** 2026-10-08 07:28:33 JST

原文在 10 月 8 日早晨报告 Bedrock 支持 Claude Haiku 5.5，模型 ID 为 anthropic.claude-haiku-5-5，最大上下文从 Haiku 4.5 的 200K 增至 1M。可用推理配置包括 us、eu、au、jp 和 global。作者使用 IAM 角色会话和 AWS CLI 的 bedrock-runtime converse 在东京调用 JP 与 Global 配置，避免把长期 API key 作为实验前提。上下文容量是模型能力边界，不能直接当作低价计费范围或任务质量结论。

对同一句简短自我介绍提示，JP 返回 inputTokens=39、outputTokens=469、totalTokens=508，Global 是 39、335、374。被省略的 reasoningContent.text 为空，但输出 token 数仍比可见正文大；模型卡说明 adaptive thinking 默认启用。费用应依据 usage.outputTokens，不能只数最终答案字符。两次短提示响应并没有构成质量或延迟基准，也不能据 token 差异断言某条路由始终更优。

作者约 10 分钟后在 CloudTrail 中查到两条 Converse 事件，lookup-events 的 EventSource 使用 bedrock.amazonaws.com。requestParameters.modelId 记录模型，未展示输入 messages 正文；additionalEventData.inferenceRegion 表示实际执行区域，JP 是 ap-northeast-1，Global 是 us-east-1。两次 resources ARN 都含东京，所以调用区域或资源 ARN 不足以证明实际计算地域。若有数据处理地域要求，应核对配置能力与每次日志；这里的地域结果是两次真实观察，不是 Global 固定在某一个区域的保证。

价格快照取自 2026-10-07 18:37:33 UTC 的 Price API，按每百万 token 美元计：Global 在输入不超过 100K 时为输入 0.10／输出 0.50，超过 100K 变为 0.50／2.50；US 和 JP 分别是 0.11／0.55 与 0.55／2.75。换言之，长上下文档位是 5 倍，而地域档位约为 Global 的 1.1 倍。最大 1M 不等于整个容量都享受 100K 内的价格。原文同时列出缓存价格，但本文不把缓存命中或省钱效果当成实测；实际选择仍要满足地域要求、真实输入长度和账单输出量。

**阅读价值：** 这篇文章用实际 API 响应、CloudTrail 和价格快照说明，模型名、调用区域、执行区域与计费边界必须分别核实。

### 5. 「JSはオンデマンドで」 初期JSを2割削って高速化させる。

**原文：** https://zenn.dev/manay_kozokaai/articles/eab31670b285a7

**发布时间：** 2026-10-07 13:38:04 JST

作者在 Next.js 16／Turbopack 项目优化多个页面。会话日志列表初始 JS 从 1,223,409 B 降到 967,092 B，约 21% 是两次 PR 合起来的结果；其中按需加载那一次是 1,159,820→967,092 B，减少 192,728 B，约 16.62%。详情页这一轮降约 2.42%，词典页约 0.20%，61 条路由中 57 条基本不变。包体减少不等于用户等待时间同比减少，原文没有给出 21% 的真实延迟或 Lighthouse 提升。

第一层是缩小客户端边界。手册页原先通过客户端 usePathname 提取分类，作者改为将已等待的 params.category 作为属性传入服务器组件并移除 use client，使 markdown 渲染依赖留在服务器。highlight、remark/micromark 与 react-markdown 合计约 344,339 B 原始体积、98,805 B gzip，对四个相关路由有约 40%～46% 的削减。另一层才是 next/dynamic：组件即使 open=false，只要始终挂载仍会加载模块；因此动态分块并不自动等于真正按需。

直接 isOpen && 渲染虽然推迟初次挂载，却在关闭时立即卸载 DOM，截断 Radix 约 200 ms 的退出动画。useMountAfterFirstOpen 首次打开后保留挂载状态，兼顾初始不加载与关闭动画；作者核对 8 处组件、10 个触发器，并减少一个原本由关闭对话框发出的 useFolders 请求。Turbopack 的分析限制下，作者从 page_client-reference-manifest.js 的 clientModules[].chunks 收集并去重真实文件，比较原始字节；哈希文件名变化不能直接当成依赖新增，gzip 也受模块 ID 噪声影响。

延迟加载的代价必须单独处理：首次打开可能没有即时响应，加载提示延迟 150 ms 才显示以避免快连接时闪烁；部署后旧标签页可能请求不存在的哈希 chunk，React.lazy 抛错。作者在对话框范围设置 ErrorBoundary，保留外部表单输入，并提示重新加载，反复请求原来的 404 URL 不会解决版本错位。测试也可能因从未挂载而让 queryBy... 为 null 的断言“空真”，应在非懒加载的对照组件上验证原有分支。这里的优化既是减少初始代码，也是明确谁负责状态、错误和验收。

**阅读价值：** 把包体字节、组件挂载时机、关闭动画和旧页面故障一起检查，比笼统“用了动态导入就变快”更适合前端面试。

**相关项目：** LTE 现场设备的远程维护与分层诊断。

**关键词：** AllowedIPs / PersistentKeepalive / RUT956

### 4. Amazon Bedrock で Claude Haiku 5.5 が利用可能になりました

### 5. 「JSはオンデマンドで」 初期JSを2割削って高速化させる。

**面试问题：**

# C. 日语学习

## C-1. 新学 JLPT 词汇

本日保留原文中且全历史未学的 8 个新词。N1／N2 是学习难度目安，不声称官方单词表；其余目标由有当日例证的复习项补充，技术词另列。

### 1. 委任する（いにんする）｜N1

- 词性：サ変動詞
- 含义：把事项交给他人处理
- 搭配：作業を委任する / 権限を委任する / 委任先を確認する
- 文章语境：Claude Code 原文讨论按委任工作的特点选择 effort。
- 例句：調査を委任したうえで、実行記録と成果物を確認する。
- 例句译文：委任调查后，再核实执行记录和成果物。
- 语感区别：委任不等于放弃责任；技术任务委任后仍需验收。

### 2. 授受（じゅじゅ）｜N1

- 词性：名詞・サ変動詞
- 含义：给予与接收
- 搭配：鍵の授受 / 資料を授受する / 授受の方法
- 文章语境：WireGuard 原文说明密钥授受需要自行完成。
- 例句：鍵の授受に際して、相手と有効範囲を確かめる。
- 例句译文：交接密钥时核实对象与有效范围。
- 语感区别：强调双方交付接收，不只是发送；此处应避免把私钥当作共享资料。

### 3. 手当てする（てあてする）｜N2

- 词性：サ変動詞
- 含义：针对问题预先采取措施
- 搭配：不具合を手当てする / 先に手当てする / 必要な手当て
- 文章语境：Next.js 原文要求提前应对初次等待与旧 chunk 404。
- 例句：遅延読み込みの失敗を手当てしてから公開する。
- 例句译文：处理好延迟加载失败后再发布。
- 语感区别：这里不是津贴或医疗处理，而是针对具体问题补齐措施。

### 4. 叩く（たたく）｜N2

- 词性：五段動詞
- 含义：敲打；技术口语中发起 API 请求
- 搭配：APIを叩く / ドアを叩く / 何度も叩く
- 文章语境：Next.js 原文指出关闭对话框仍在请求文件夹 API。
- 例句：画面を開かない限り、一覧APIを叩かない。
- 例句译文：不开界面就不请求列表 API。
- 语感区别：APIを叩く 是口语，正式设计文档可写呼び出す；不表示攻击。

### 5. ちらつく（ちらつく）｜N2

- 词性：五段動詞
- 含义：短暂闪动而不稳定可见
- 搭配：表示がちらつく / 画面がちらつく / 一瞬ちらつく
- 文章语境：Next.js 原文用延迟 150 ms 的提示避免快连接上的短暂闪烁。
- 例句：すぐに読み込めるときは、待機表示がちらつかないようにする。
- 例句译文：很快加载完成时，应避免等待提示闪现。
- 语感区别：指短暂视觉不稳，与持续显示或加载很慢不同。

### 6. 貼る（はる）｜N2

- 词性：五段動詞
- 含义：粘贴；把标记或代码附到某处
- 搭配：ラベルを貼る / コードを貼る / 指定を貼る
- 文章语境：Next.js 原文说仅贴上 dynamic() 并不构成按需加载。
- 例句：指定を貼るだけでなく、マウント時期も確認する。
- 例句译文：不只加上指定，还要核实挂载时机。
- 语感区别：貼る 是附着；張る 多用于拉紧或铺开，同音而非此处同义。

### 7. 結局（けっきょく）｜N2

- 词性：副詞
- 含义：经过各种过程后最终
- 搭配：結局は自分で決める / 結局どうなったか / 結局こちらの仕事
- 文章语境：Next.js 作者认为代码可由 AI 写，但依赖放在哪里仍是人的判断。
- 例句：AIが実装を助けても、結局は測定条件を自分で確かめる。
- 例句译文：即使 AI 协助实现，最终仍须自己核实测量条件。
- 语感区别：强调经历过程后的落点，而非“目的上”或“一开始”。

### 8. 省略する（しょうりゃくする）｜N2

- 词性：サ変動詞
- 含义：省去不写或不展示的一部分
- 搭配：出力を省略する / 説明を省略する / 省略した部分
- 文章语境：Haiku 原文省略响应展示中的 reasoningContent 与 metrics，但费用仍看 usage。
- 例句：表示を省略しても、課金対象がないわけではない。
- 例句译文：省略显示并不意味着没有计费对象。
- 语感区别：是展示时省去，不意味着系统没有生成或计量该部分。

## C-2. IT/AI 专业词汇

1. **effort（処理の深さの指定）**：Agent 调用中的处理深度参数 参数记录与实际质量分别验收。

2. **ec2:SharedTag/（共有タグの接頭辞）**：AMI 所有者声明跨账号共享标签的前缀 使用者可读，不可改共享值。

3. **AllowedIPs（許可するIP範囲）**：WireGuard peer 的允许地址和选路范围 本文同时包含 VPN 与现场 LAN 网段。

4. **PersistentKeepalive（定期的な保活）**：持续发送小包以维持 NAT 状态的设置 原文取 25 秒，不是性能保证。

5. **inferenceRegion（実際の推論リージョン）**：CloudTrail 记录中的实际模型执行区域 不能只看东京 endpoint 或 ARN。

6. **useMountAfterFirstOpen（初回だけ待つマウント制御）**：首次打开后保留组件的挂载控制 兼顾按需下载和关闭动画。

7. **ErrorBoundary（エラー境界）**：把 React 渲染错误限制在组件范围内 原文用于旧 chunk 404 后保留调用者输入。

## C-3. 新学语法

本日新学语法仅 1 项。全历史排除重复后，只有原文“気づかないうちに”提供明确的新功能依据；其他既学表达进入独立复习层，不为达到 5 项编造新语法。

### 1. ～うちに｜N3

- 含义：趁某状态持续时；在持续过程中不知不觉发生变化
- 结构：動詞辞書形・ない形／い形容詞＋うちに；な形容詞＋なうちに；名詞＋のうちに
- 用法：本日原文用“気づかないうちに”说明未察觉时输入已经丢失，不是每次重复的“たびに”。
- 原文形态：気づかないうちに
- 原文依据：[気づかないうちに入力が欠ける](https://dev.classmethod.jp/articles/20261007-cc-updates-v2-1-292/)
- 独立例句：古いタブで作業しているうちに、新しい版が公開された。
- 例句译文：在旧标签页操作的过程中，新版本已经发布了。
- 注意：与“たびに”区分：うちに 是状态持续期间发生变化；不要把“ままでは”等已学形态当新语法。
