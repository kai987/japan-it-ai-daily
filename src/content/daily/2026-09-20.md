### 1. [アップデート] Amazon Quick で画像やプロンプトからBI画面を自動生成できるようになったので試してみた

**来源：DevelopersIO｜2026年9月20日**  
**原文 URL：** https://dev.classmethod.jp/articles/20260919-amazon-quick-generate-sheets-and-analysis-from-an-image/

Amazon Quick新增的`Generate Sheet`不是重建整个Analysis，而是在现有Analysis里增加一张Sheet。这个入口的Prompt上限只有 **280字符**，明显短于完整`Generate Analysis`的 **1,400字符**，因此需求必须更聚焦。作者用Superstore订单数据分别在东京和北弗吉尼亚验证：AWS What's New写的是Quick可用Region全面GA，但作者观察时东京没有Generate Sheet入口，北弗吉尼亚则有；另一方面，图片生成的`Add image`在东京已经能看到。这种Region落地差异本身就是企业上线时需要验证的条件，而不能只看Announcement。

更关键的是生成“成功”不等于语义正确。日文Prompt生成5个Visual，却把Sales $23.14M与Profit $3.68M的比例算成 **529.43%** 并包装成类似YoY的说明；`Average Profit`图的轴标题却写成Profit Margin。Prompt明确要求的Filter Control和Calculated Field，无论日文还是英文都生成 **0件**。相反，用1600×1000的Legacy BI截图生成时，Quick做出了 **9个Visual、5个Control** 和`profit_ratio`计算字段，但原图3个Tab被压成1张Sheet、两条YoY折线只剩一条，KPI聚合范围也和原图不同。

**证据类型是作者Hands-on。** Quick界面本身也写着“Generated analyses should be reviewed before publishing”。**限制与适用边界：** 这是Superstore上的少量生成，不是通用准确率Benchmark。企业迁移BI时不能只做Screenshot级比对，而要逐项核对Measure、Aggregation、Filter、Calculated Field、Date Grain和Sheet结构，最后再允许发布。

**为什么值得看：★★★★★**  
它把“AI生成Dashboard”从Demo问题变成了**Semantic Migration Verification**问题：外观只是候选结果，真正的验收对象是计算与聚合语义。

### 2. NemoHermes の LLM ルーティングに使っている NeMo Switchyard の Classifier を TypeSafe の Jev に替えて計測してみた

**来源：DevelopersIO｜2026年9月20日**  
**原文 URL：** https://dev.classmethod.jp/articles/reona-dgx-spark-switchyard-jev-classifier/

NemoHermes原来让NeMo Switchyard里的LLM Judge把请求路由到Weak/Strong模型。实际运行中，Judge一次判断的Median大约1.8秒，而一条Slack消息会触发3～4次判断，因此Router本身会形成明显等待。作者把路由改成`type_safe_classifier`，后端使用TypeSafe的专用分类模型 **Jev**。在同一组13 Scenario各跑3次的比较里，旧Judge按预期路由 **36/39**，Jev是 **39/39**；扣掉Executor生成时间后，“判断＋转换”的Median从1.55秒下降到Strong 0.27秒、Weak 0.42秒。

作者又直接调用TypeSafe API做13×10＝130次测量，全部符合预期，Median 0.514秒、p95 0.576秒。但这个数字不能和Switchyard内的0.27秒直接横比，因为Direct Python每次都会重新建立TLS连接，而Switchyard会复用Connection。Jev还有两个很实在的边界：图片内容不会被理解，只会替换为`(image)`；Routing JSONL会记Selected Model与Token，但Label/Confidence只在Server INFO Log，完整“为什么这样路由”的Audit Trail仍要自己补。

**证据类型是作者的小规模对照实测。** **限制与适用边界：** 13 Scenario不代表真实Traffic分布，而且Jev仍是early access，价格和限制可能变化。生产选择不能只看39/39，要一起测P95/P99、Cost、Criteria Drift、图片请求、外部数据发送边界与Auditability；Criteria变化时还应该用同一Eval Set做Regression。

**为什么值得看：★★★★★**  
它说明Model Router本身也可以拆成可管理Component：把狭窄Decision交给专用Classifier后，团队能为Router定义清晰的SLO，而不是把所有判断都塞给一个更大的生成模型。

### 3. AI攻撃は「調べて対応」では間に合わない　ゼットスケーラーがSOCをAIエージェント化

**来源：キーマンズネット｜2026年9月20日**  
**原文 URL：** https://kn.itmedia.co.jp/kn/article/2609/20/2000001661/

Zscaler提出的Agentic SOC不只做Alert Summary，而是把 **Triage → Root Cause Investigation → Judgment → Response Workflow** 串起来。它会把Zero Trust Telemetry与第三方Security Data关联，目标动作包括隔离被侵害User、阻断攻击通信、抑制Lateral Movement。Zscaler还强调其跨Network、Identity、Endpoint、Cloud与AI的Telemetry规模约为 **每天7500亿件Zero Trust Transaction**，希望用这个上下文减少人工在多个Console间来回调查的时间。

但“会调查”和“有权动作”必须拆开。若误报导致正常User或System被隔离，自动化本身就会成为Incident。因此比较稳妥的自治升级顺序是先让Agent做Evidence Gathering和Root Cause候选，再按Action的Severity、可逆性和Blast Radius决定是否保留Human Approval。对高风险动作，应能回看Evidence、Confidence、具体执行内容、Rollback与Human Owner。

**证据类型是Vendor/Product发布报道。** **限制与适用边界：** 每天7500亿件Telemetry只能说明数据规模，不能证明False Positive Rate、MTTR或Response正确率；报道本身也明确提到AI判断错误的风险。企业不能因为Telemetry大就直接开放更强权限，而要根据真实误报率、Rollback成功率与审计结果逐步扩大自治范围。

**为什么值得看：★★★★★**  
Security Agent最重要的面试视角不是“AI能自动封什么”，而是**什么Evidence足以授权什么Action**。

### 4. Amazon Bedrock AgentCore Runtime V2 の課金メモリがピーク後に縮小する挙動を USAGE_LOGS で観測してみた

**来源：DevelopersIO｜2026年9月19日（日期边界补充）**  
**原文 URL：** https://dev.classmethod.jp/articles/amazon-bedrock-agentcore-runtime-v2-memory-usage-logs/

作者为了理解AgentCore Runtime V2到底按什么Memory计费，没有用OS的RSS推算，而是直接观察 **USAGE_LOGS** 中的`agent.runtime.memory.gb_hours.used`。在`ap-northeast-1`同一个V2 Image里分别分配0/100/500/1000MB，并按1秒粒度把GB-hours换算成MB等价值。1000MB分配后的计费换算Peak约 **2839MB**；释放后67秒约1138MB、100秒1027MB、300秒876MB，到了 **667秒仍约796MB**。

与此同时，Application的VmRSS Baseline约33MB；667秒后的计费Memory约796MB，约相差24倍。三次Session的`total mem_gb_hours`合计 **0.469416**。其中seq Session实际工作约15秒，但在667秒观察区间里依然存在计费Memory的Idle Tail。这意味着“Process RSS”或“业务代码运行了几秒”都不能直接当Billing Proxy，否则Agent平台FinOps很容易低估成本。

**证据类型是3 Session Controlled Hands-on。** **限制与适用边界：** 只有一个Image和有限Allocation Pattern，24倍不能一般化；USAGE_LOGS本身也有到达延迟。企业应该按自己的Session Length、并发、Peak Allocation与Idle Pattern重放，再用GB-hours计算Cost per Task。

**为什么值得看：★★★★★**  
它把Agent成本分析从“看容器内存”提升为“以平台Billing Telemetry为Source of Truth”，非常适合AWS/FinOps面试。

### 5. Claude Code v2.1.277〜v2.1.278 の主要アップデート - 待望の AGENTS.md 対応と TaskOutput ツールの削除

**来源：DevelopersIO｜2026年9月19日（日期边界补充）**  
**原文 URL：** https://dev.classmethod.jp/articles/20260919-cc-updates-v2-1-278/

Claude Code v2.1.277新增了一个很影响团队规则分发的Fallback：Current/Parent Directory里没有CLAUDE.md时，会读取 **AGENTS.md** 作为Project Instruction。作者在临时Directory做了验证：只放AGENTS.md时Instruction生效，File退避后效果消失；如果Parent存在CLAUDE.md，则它优先于Child的AGENTS.md，而且`git init`不会阻止继续向上寻找。**Bedrock、Vertex、Foundry当时还不支持这个能力**，所以同一Version在不同Provider上并不是完全同一Behavior。

同一版本还移除了`TaskOutput` Tool，Task结果改为通过`Read`处理。v2.1.278又把Auto mode classifier在Claude API/Enterprise以及Bedrock、Vertex、Foundry、Gateway场景中改为Server-side默认，可用`CLAUDE_CODE_AUTO_MODE_SERVER=0`Opt-out；同时增加`CLAUDE_GATEWAY_PROXY_IS_EGRESS_BOUNDARY=1`以及Sandbox相关安全修复。这不是单纯“多了一个Feature”，而是Default、Tool surface和Network Boundary一起变化。

**证据类型是Changelog加作者Hands-on。** **限制与适用边界：** 这不是Productivity Benchmark，而且Feature Availability受Provider/Setting影响。企业升级前至少应回归`/config`、`/status`、Instruction precedence、Removed Tool、Gateway与Sandbox，确认实际Behavior Contract没有被版本默认值悄悄改掉。

**为什么值得看：★★★★★**  
Coding Agent的Upgrade也应该像Application Runtime升级一样做**Behavior Regression**，而不是只读Release Note后全员更新。

## 4. 今日の技術テーマ：Evidence Before Commit

今天的核心机制可以写成：AI先产生Candidate Output，然后经过独立Evidence Layer，最后才由Human或Policy授予Commit Authority。Amazon Quick的Evidence是Dashboard配置与聚合语义；Jev是同一Eval Set上的Routing Accuracy/Latency；SOC是Incident Evidence与Rollback；AgentCore是平台Billing Telemetry；Claude Code是Upgrade Regression。

```text
Input / Context
      ↓
AI / Agent Execution
      ↓
Candidate Output
      ↓
Evidence Layer
├─ Semantic / Aggregation check
├─ Router accuracy + latency
├─ Security evidence + rollback
├─ Billing telemetry
└─ Runtime regression
      ↓
Commit Authority
      ↓
Business State
```

优点是Model、Provider或具体Tool更换后，Evidence Contract仍可复用，而且可以根据Action Risk保留不同强度的Human Gate。**局限也必须保留：** 单次生成、13 Scenario、Vendor Telemetry规模、3 Session与Changelog都是特定条件的Evidence，不是万能真值。日本企业落地时，建议为每个AI Workflow明确`Candidate Output / Independent Evidence / Side Effect / Rollback / Human Owner / Commit Condition`，只有实测稳定后再扩大自治权限。

# B. 重点总结和面试可用知识点

- Generate Sheet只有280字符，而图片Analysis入口是1,400字符级输入，生成路径本身不同。
- 本次Hands-on中文本生成Filter/Calculated Field均为0；图片生成则得到5 Control和1个`profit_ratio`。

## C-1. JLPT词汇｜新学14词

1. **添付する（てんぷする）｜名词・サ变动词｜N2**：附加图片或文件。搭配：画像を添付する／Fileを添付する／資料を添付する。例：`Dashboard画像をPromptに添付して、再構成結果を比較します。` 中文：把Dashboard图片附加到Prompt后比较重建结果。Nuance：不限于邮件，也常用于AI输入。
2. **作り直す（つくりなおす）｜动词・五段｜N2**：重新制作既有对象。搭配：全体を作り直す／設計を作り直す／一から作り直す。例：`分析全体を作り直さず、必要なSheetだけを追加します。` 中文：不重做整个分析，只添加需要的Sheet。Nuance：比「直す」更接近再制作。
3. **読み取る（よみとる）｜动词・五段｜N2**：从文字、图像或情况中读取并理解信息。搭配：画像から読み取る／意図を読み取る／数値を読み取る。例：`AIが画像から読み取ったKPIと元Dashboardの定義を照合します。` 中文：核对AI从图片读取出的KPI与原Dashboard定义。Nuance：可包含语义理解，不只是OCR。
4. **書き写す（かきうつす）｜动词・五段｜N2**：把既有文字基本照抄到别处。搭配：内容を書き写す／指示を書き写す／ノートに書き写す。例：`共通指示をToolごとに書き写す運用は差分を生みやすいです。` 中文：把共同指令复制到每个Tool的运维方式容易产生差异。Nuance：强调复制，不是抽象复用。
5. **退避する（たいひする）｜名词・サ变动词｜N1**：为避免影响而临时移到别处。搭配：Fileを退避する／Dataを退避する／一時的に退避する。例：`検証ではAGENTS.mdを一度退避して読み込み差分を確認します。` 中文：验证时先临时移走AGENTS.md确认读取差异。Nuance：不是永久删除。
6. **縮小する（しゅくしょうする）｜名词・サ变动词｜N2**：缩小规模、范围或数值。搭配：規模を縮小する／Memory使用量を縮小する／影響範囲を縮小する。例：`Peak後に課金Memoryがどの速度で縮小するかを観測します。` 中文：观察峰值后计费Memory以怎样的速度缩小。Nuance：正式场合也用于Cost、组织和影响范围。
7. **確保する（かくほする）｜名词・サ变动词｜N2**：确保资源处于可用状态。搭配：Memoryを確保する／容量を確保する／人員を確保する。例：`Testでは1000MBを確保して課金側のPeakを測りました。` 中文：测试中分配1000MB并测量计费侧Peak。Nuance：也常用于人员、预算、时间。
8. **解放する（かいほうする）｜名词・サ变动词｜N1**：释放正在占用的资源。搭配：Memoryを解放する／Resourceを解放する／Lockを解放する。例：`Memoryを解放しても課金値が即時に同じ水準へ戻るとは限りません。` 中文：释放Memory后，计费值也不一定马上回到同一水平。Nuance：常见于Memory/Connection生命周期。
9. **回収する（かいしゅうする）｜名词・サ变动词｜N2**：回收已使用资源。搭配：Memoryを回収する／Resourceを回収する／Costを回収する。例：`Runtimeが解放済みMemoryを課金上どう回収するかを確認します。` 中文：确认Runtime在计费层如何回收已释放Memory。Nuance：商业语境也可表示回收成本。
10. **張り直す（はりなおす）｜动词・五段｜N1**：重新建立Connection或Session。搭配：接続を張り直す／Sessionを張り直す／Networkを張り直す。例：`APIを一回ずつ呼ぶ測定ではTLS接続を毎回張り直します。` 中文：逐次调用API的测量里每次都重新建立TLS连接。Nuance：IT实务表达。

14. **緩やかに（ゆるやかに）｜副词｜N2**：缓慢、非剧烈地变化。搭配：緩やかに低下する／緩やかに増える／緩やかに変化する。例：`課金MemoryはPeak後に緩やかに低下する区間がありました。` 中文：计费Memory在Peak后有一段缓慢下降区间。Nuance：也可描述规则松紧或变化速度。
