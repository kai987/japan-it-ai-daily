### 1. [アップデート] Amazon Quick で画像やプロンプトからBI画面を自動生成できるようになったので試してみた

**来源：DevelopersIO｜2026年9月20日**  
**原文 URL：** https://dev.classmethod.jp/articles/20260919-amazon-quick-generate-sheets-and-analysis-from-an-image/

Amazon Quick 新增两条生成路径。`Generate Sheet`在当前Analysis中根据自然语言追加一个Sheet，Prompt上限只有 **280字符**，而完整`Generate Analysis`可使用 **1,400字符**；图片模式还能把其他BI工具的Dashboard截图作为输入，重新构造成Amazon Quick支持的Visual。作者用Superstore订单数据同时在东京和北弗吉尼亚验证：What's New写着所有可用Region GA，但测试时东京没有看到Generate Sheet入口，北弗吉尼亚有；图片的`Add image`则在东京可见。也就是说，即使官方Announcement说GA，实际Console入口仍应按组织、Region和时间点核对。

更有价值的是作者没有把“生成成功”当作正确。日语Prompt生成5个Visual，却把Sales $23.14M与Profit $3.68M做成 **529.43%** 的比较，说明文案却写成YoY；Average Profit图的Axis又标成Profit Margin。Prompt里明确要求的Filter Control和Calculated Field都是 **0件**，改成英文Prompt并明示要求后仍为0。相反，输入一张1600×1000的模拟Legacy BI图片时，系统生成 **9个Visual、5个Control**，并自动建立`profit_ratio` Calculated Field；但3个Tab被压成1个Sheet，两条YoY Line只剩1条，KPI聚合范围也和原图不同。

**证据类型：作者实测。** 测试环境、Data、Prompt和生成结果都可追踪，而且UI本身明确写着“Generated analyses should be reviewed before publishing”。**但是，证据边界：** 这只是特定Superstore Dataset与单次/少量生成，不是Amazon Quick整体Accuracy Benchmark。适合企业的做法是把Migration定义成Config Reconstruction：逐项验证Measure、Aggregation、Filter、Calculated Field、Date Grain与Sheet结构，而不是只比较截图是否相似。

**为什么值得看：★★★★★**  
它把“AI生成BI”从Demo提升成了**可验证的配置迁移问题**：视觉相似只是第一层，真正决定能否上线的是语义与计算定义。

### 2. NemoHermes の LLM ルーティングに使っている NeMo Switchyard の Classifier を TypeSafe の Jev に替えて計測してみた

**来源：DevelopersIO｜2026年9月20日**  
**原文 URL：** https://dev.classmethod.jp/articles/reona-dgx-spark-switchyard-jev-classifier/

NemoHermes原先让NeMo Switchyard用一个LLM Judge判断Request应发给Weak还是Strong Model。这个方案可解释，但在作者环境中一次Judge通常要约1.8秒，而且一条Slack Message会触发3～4次判断。此次把Classifier替换成TypeSafe的 **Jev**：`type_safe_classifier`直接返回Choice与Confidence，不先生成自然语言。`routes.toml`把默认目标设为Strong、Threshold 0.6，Weak/Strong分别连接DeepSeek V4 Flash与Kimi K3。对 **13个Scenario×3次**的同条件比较，原Judge期望一致为 **36/39**，Jev为 **39/39**；扣除Executor生成后，判定+变换Median从 **1.55秒**降到Strong 0.27秒、Weak 0.42秒。

作者还直接调用TypeSafe API做13×10＝130次判断，全部符合预期，Median 0.514秒、p95 0.576秒；输入约500～692 Token，文章按当时Rate估算每次约$0.000023、130次约$0.003。但这个Direct Python测试每次会重新**張り直す**TLS连接，而Switchyard会复用Connection，所以不能把0.514秒直接当Production Router开销。更关键的是Audit边界：图片只被替换成`(image)`，Jev看不到图片内容；选中Model与Token会进JSONL，但Label/Confidence只在Server INFO Log，Routing理由不会完整留下。

**证据类型：作者小规模对照实测。** **但是，证据边界：** 13个Scenario不是广泛Routing Benchmark，Jev仍是early access，Price/Limit可变化；“39/39”只说明这些Criteria与这些Case匹配。真正上线需要同时测Classification Quality、P95/P99、Cost、External Data Boundary、Image Request策略与Audit Log。专用Classifier的价值不是“永远比LLM聪明”，而是把一个狭窄Decision变成更便宜、更快、更容易设SLO的独立Component。

**为什么值得看：★★★★★**  
这是很适合面试的 **Model Router Evaluation**：不仅比较Accuracy，还把Latency、Cost、Connection条件与Observability一起列入判断。

### 3. AI攻撃は「調べて対応」では間に合わない　ゼットスケーラーがSOCをAIエージェント化

**来源：キーマンズネット｜2026年9月20日**  
**原文 URL：** https://kn.itmedia.co.jp/kn/article/2609/20/2000001661/

Zscaler提出的Agentic SOC，不是只在SIEM Alert上附一段LLM摘要，而是把Detection之后的 **Triage → Root Cause调查 → 判断 → Response Workflow** 连成Agent流程。它把Zscaler Zero Trust Telemetry与第三方Security Data做Correlation，并可在判断后触发Inline Control，例如隔离受感染User、Block攻击通信、抑制Lateral Movement。Vendor说明其平台可利用每天约 **7500亿件** Zero Trust Transaction产生的Network、Identity、Endpoint、Cloud与AI Telemetry，同时结合Anthropic/OpenAI Model以及Red Canary的Security专家经验。

这类方案真正难的部分恰恰不是“查得快”，而是Action拥有实际业务后果。AI若把正常User误判成受攻击对象，自动隔离会立即造成业务中断；如果攻击判断漏掉，又会给攻击者横向移动时间。因此SOC Agent的Read Scope与Actuate Scope不能混成一层。对于高风险Action，应该记录Evidence Chain、Confidence、执行Action、Rollback路径与Human Escalation；严重度高但证据不足时，宁可把Agent输出作为调查叩き台，也不要直接把判断变成不可逆动作。

**证据类型：Vendor/Product报道。** **但是，证据边界：** “每天7500亿件Telemetry”证明的是可观测数据规模，不等于独立证明Detection Accuracy、False Positive Rate、MTTR或自动Response成功率。文章也明确承认AI判断可能出错。企业导入时应先把Triage与Evidence Gathering自动化，再按Action Risk逐步扩大权限，并对隔离/通信遮断准备快速Rollback。

**为什么值得看：★★★★★**  
Agentic Security最重要的面试点不是“AI比人快”，而是**自治级别必须跟证据强度和可逆性绑定**。

### 4. Amazon Bedrock AgentCore Runtime V2 の課金メモリがピーク後に縮小する挙動を USAGE_LOGS で観測してみた

**来源：DevelopersIO｜2026年9月19日（页面仅公开日期，作为窗口边界补充）**  
**原文 URL：** https://dev.classmethod.jp/articles/amazon-bedrock-agentcore-runtime-v2-memory-usage-logs/

AgentCore Runtime V2改变了Memory Billing后，作者没有用OS里的RSS猜费用，而是打开 **USAGE_LOGS**，读取1秒粒度的`agent.runtime.memory.gb_hours.used`再换算MB。测试在`ap-northeast-1`用同一V2 Image，依次分配0/100/500/1000MB。Application侧`VmRSS`会随着分配增长，Base约33MB；但Billing Memory的形态完全不同：1000MB分配后的换算Peak约 **2839MB**，释放后虽然下降，67秒约1138MB、100秒1027MB、300秒876MB，到 **667秒仍约796MB**。

这说明Process RSS不是Billing的代理指标。667秒时约796MB仍是Process RSS约33MB的约24倍。三个Session累计`total mem_gb_hours`为 **0.469416**；其中seq实际工作约15秒，但观察/计费轨迹持续667秒，Idle区间仍持续计入Memory。文章还记录到Log并非实时立刻出现，而是在测量后延迟到达。FinOps如果只看Task执行时间，容易低估长Session的Idle Billing Tail。

**证据类型：作者控制条件实测。** **但是，证据边界：** 只有3个Session与一套Image，不能推出所有Runtime Workload的固定“24倍”。AWS内部Billing Memory也不是公开等价于某个Linux RSS字段。真正上线应按真实Session Length、并发、Peak Allocation与Idle行为累计GB-hours，并把Cost per Successful Task而不是Process Memory作为SLO之一。

**为什么值得看：★★★★★**  
Agent Cost不能靠Application内部Metric猜；**Billing Telemetry本身就是Source of Truth**，这是非常实用的Agent FinOps思维。

### 5. Claude Code v2.1.277〜v2.1.278 の主要アップデート - 待望の AGENTS.md 対応と TaskOutput ツールの削除

**来源：DevelopersIO｜2026年9月19日（页面仅公开日期，作为窗口边界补充）**  
**原文 URL：** https://dev.classmethod.jp/articles/20260919-cc-updates-v2-1-278/

v2.1.277最醒目的变化是 **AGENTS.md**：当前/上级Directory没有CLAUDE.md时，Claude Code会把AGENTS.md作为Project Instruction Fallback，可在`/config`的Project instructions确认。作者用临时Directory实测：只有AGENTS.md时会读取；把它**退避する**后不再生效；如果上级Directory存在CLAUDE.md，则即使Child有AGENTS.md也优先读Parent CLAUDE.md，而且`git init`不会停止这个向上搜索。需要特别保留的兼容边界是：该AGENTS.md功能当时对Bedrock、Vertex、Foundry **未対応**。

同一批升级还改变了Runtime Contract。`TaskOutput` Tool被删除，Task结果改用`Read`读取，对应的`taskOutputMaxChars`/`TASK_MAX_OUTPUT_LENGTH`也失效。v2.1.278又把Claude API/Enterprise以及Bedrock、Vertex、Foundry、Gateway环境中的Auto mode classifier默认切到Server-side；特定环境可用`CLAUDE_CODE_AUTO_MODE_SERVER=0` Opt-out。此外还有`CLAUDE_GATEWAY_PROXY_IS_EGRESS_BOUNDARY=1`这类Gateway Egress设置、Sandbox compound Bash glob和不可见Unicode/Tag清理等Security Fix。

**证据类型：Changelog＋作者手动验证。** **但是，证据边界：** 这不是Productivity Benchmark，而且Feature Availability会随Provider与Setting变化。组织升级时不能只测“claude能启动”，而应回归 **Instruction Precedence、Removed Tool、Auto-mode Default、Gateway Egress、Sandbox和Billing Fallback**；尤其AGENTS.md与Parent CLAUDE.md优先级会直接改变Agent得到的Policy Context。

**为什么值得看：★★★★★**  
Coding Agent升级已经像Runtime升级一样，需要**Behavior Contract Regression**，而不仅是读Release Note后直接全员更新。

## 4. 今日の技術テーマ：Evidence Before Commit

今天五篇可以统一成一个很适合面试的设计：**AI输出先进入Evidence层，再决定是否Commit真实业务状态。** Amazon Quick生成的是Dashboard Config Candidate；Jev生成的是Route Decision；Agentic SOC生成的是Incident判断与Action Candidate；AgentCore USAGE_LOGS提供的是Cost Evidence；Claude Code的AGENTS.md、Auto mode和Gateway设置则定义Coding Agent Runtime的Policy Context。

```text
Input / Context
      ↓
AI / Agent Execution
      ↓
Candidate Output
      ↓
Evidence Layer
├─ Semantic / Aggregation check
├─ Router accuracy + latency
├─ Security evidence + rollback
├─ Billing telemetry
└─ Runtime regression
      ↓
Commit Authority
      ↓
Business State
```

**优点：** Model、Provider或Tool可以替换，但Evidence与Commit Gate可以复用；高风险Action可以要求更强证据；成本也能使用Billing Source of Truth而非内部Proxy。**局限：** Evidence本身也可能不完整——单次BI生成不代表长期Accuracy，13个Routing Case不代表真实分布，7500亿Telemetry不代表False Positive低，Process RSS不代表Billing，Changelog也不能代替组织自己的Regression。

日本企业落地时，可以给每个AI Workflow固定六栏：`Candidate Output / Independent Evidence / Side Effect / Rollback / Human Owner / Commit Condition`。这样AI的能力扩大时，治理不需要重新发明。
