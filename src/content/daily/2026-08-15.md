## 1. 今日最值得看的 5 篇

### ① DeepSeek Harness 0.1：「Everything is a Plugin」

**来源：gihyo.jp**

**原文：** https://gihyo.jp/article/2026/08/deepseek-harness-developer-preview

**DeepSeek Harness v0.1** 于8月13日以开发者预览发布，源码采用 MIT 许可。它把模型与工具、会话和运行环境结合成代理，并将模型、技能、文件系统、沙箱、代理循环、编排和 UI 等都设计为插件，而不是只提供一个模型调用接口。

插件底座 **Cordis** 管安装、卸载与依赖关系，插件通过服务和事件通信。启动时形成插件树，以配置档管理，因此无需改核心代码即可替换组件。`web` 和 `headless` 属于启动方式，后者处理一件任务后退出；标准、代码、最小构成、创建四种模式则属于代理能力配置，两个维度不能混淆。

标准模式含编辑、Shell、搜索、技能等；代码模式通过生成调用工具的代码合并多步操作；最小模式只保留有状态 bash 和文件编辑，便于评价模型；创建模式用于试验并组装代理预设。可配置 DeepSeek 以外的提供商、内部网关或自托管端点。调用已安装的 Codex CLI 或 Claude Code 进行委派**默认关闭**，需要开启及各 CLI 认证，父会话只收到最终回答。

追加式会话日志记录模型与工具输入输出、加入的上下文等，**Trajectory** 视图按输入、模型、工具分类展示；会话恢复、分支、搜索、重放也利用同一事件流。Web UI 可由 `npx @deepseek-ai/dsh web` 启动，默认地址为 `127.0.0.1:3080`。从源码开发要求22系且不低于22.19的 Node.js，或24系及以后，并使用 pnpm。

`dsh --profile headless` 无需启动服务器，处理任务后把最终响应写到标准输出；自定义扩展可写为 TypeScript Cordis 模块。原文证据是预览版本的功能与架构说明，没有测量插件替换后的性能、隔离程度或审计完整性。**可组合不代表组合后的权限与兼容性自动正确**，这些仍需要随具体配置验证。

**关注点：★★★★★**

分清启动配置与能力模式，并用插件依赖、事件流和权限说明模型外围执行框架的职责。

### ② Prompt Injection：AgentがWebを読むこと自体がAttack Surfaceになる

**来源：Zenn**

**原文：** https://zenn.dev/oubakiou/articles/ed98acbf4630b3

作者的 guarded 技能针对代理读取网页时接触未知指令和不可信内容的问题，组合**专用抓取子进程、最小权限与静态清理**，同时限制抓取过程能操作什么，以及父代理最终收到什么。允许抓取方使用不同模型，但这只是增加实现差异的一层防御，并非安全性证明。

子进程只保留网页获取、搜索类能力，并抑制 MCP、记忆和本地配置的自动加载；之后清除已知聊天标记和不可见 Unicode，整理成 JSON 再返回父代理。脚本使用 Node.js 标准功能，不增加 npm 依赖。限制必须保留：**清理器不识别普通自然语言中的恶意要求**，清理后的资料仍是数据，不能升级为可信操作指令。

| 抓取方 | 操作与输出控制 | 隔离条件 |
| --- | --- | --- |
| Claude | allowedTools、JSON Schema | 内置沙箱针对 Bash 路径 |
| Codex | 提示限制、read-only、输出 Schema | CLI 的只读沙箱 |
| Gemini | Policy Engine，输出形式靠提示 | x86_64 且可用 runsc 时启用 gVisor |

原文明确指出，Gemini 在 arm64 或缺少 runsc 时会**不启用沙箱而继续运行**。当前设计只把 Claude Code 作为父代理，Codex/Gemini 作为抓取进程。作者的网页搜索测量中，Claude 约23～26秒，Codex 约12～16秒，Gemini 波动较大。多出的启动、模型获取与清理步骤会降低实时性；文章没有给出完整试行数量或攻击成功率对照。

禁止 `WebFetch`、`WebSearch` 仍有 `gh`、curl、脚本和 git 等其他读取路径，CLAUDE.md 的工作约定也不具有强制力。作者因此建议在高隔离需求下进一步约束出站通信与执行环境。仅在工具名单中禁止两个入口，不能证明所有外部内容都经过清理路径。

文中引用的 **GHSA-wpqr-6v78-jr5g** 有 Gemini CLI headless、不可信输入及工具许可等前提；**ZDI-26-305** 描述的是 Codex 处理含恶意 JavaScript 仓库的路径，并没有验证这个网页获取技能。ZDI 原始公告还记录了提供者关于非默认产品范围的说明。因此**不保留“所有 read-only 沙箱都可由该漏洞突破”的泛化**，理由是适用范围无法得到证实。[Gemini CLI 原始公告](https://github.com/advisories/GHSA-wpqr-6v78-jr5g)、[ZDI 原始公告](https://www.zerodayinitiative.com/advisories/ZDI-26-305/)。

**关注点：★★★★★**

分开讨论文本清理、操作权限、系统隔离与父代理判断，准确描述每层能缓解什么、不能保证什么。

### ③ Claude Code 2.1.232：Sub-agent ForkとSessionをまたぐ協調

**来源：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/20260814-cc-updates-v2-1-232/

虽然标题包含 v2.1.230，原文实际覆盖8月13日的 **v2.1.231 与 v2.1.232**，并说明230未发布到 npm。共50项变化被归为17项修复、12项改进、12项安全、6项新功能、2项性能和1项破坏性变化。需要同时关注协作能力和权限边界，而不是只摘新功能。

**`subagent_type: "fork"`** 继承父代理完整会话与提示缓存，并使用同一模型；其他类型或省略类型仍是新代理，不代表所有子任务都会自动继承历史。对话模式中的 fork 默认启用与后台执行相联系，但作者检查 print 模式时，默认没有对应指示段，显式启用标志后才出现，因此应区分运行模式。

作者先只向父会话提供暗号，再启动 fork，子任务提示中不包含暗号，最终子代理答对。这证明了**会话继承的具体行为**，没有测量复杂任务成功率、缓存节省或性能提升比例。原文还给出 `CLAUDE_CODE_FORK_SUBAGENT=0` 以恢复旧行为。

新增通过 `@` 提及其他会话，并用 **`SendMessage`** 联系的能力。`/config` 可设接收、暂存或拒绝其他会话消息，同机会话名也会保持唯一。其他变化包括支持 GitLab 插件市场仓库、修复 MCP OAuth 重定向错误和探测阶段等待30秒的问题，以及 Bedrock、Vertex 流空闲超时后的恢复问题。

安全修复涉及 Windows 路径、PowerShell 权限绕过，以及嵌套 Git 仓库错误继承父目录信任等。现在嵌套仓库需要分别确认信任。**`sandbox.ripgrep` 不再接受项目级设置**，需移至用户、托管或 `--settings`；服务器托管的沙箱二进制覆盖也需要批准。已有项目不能仅升级版本而不检查配置来源。

证据是变更日志整理与部分动手实验，不是所有50项在各系统上的全面复测。应用时应检查 fork 的继承范围与运行模式、跨会话接收策略，以及破坏性配置的迁移位置，再验证自己实际依赖的权限行为。

**关注点：★★★★★**

用暗号实验说明会话继承的证据范围，同时保留运行模式和权限配置迁移的具体影响。

### ⑤ Amazon Bedrock AgentCore 入門 - AI エージェントを自作しながら「ハーネス」の仕組みを学んでみた

**来源：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/agentcore-hands-on-study-agent-harness/

作者用 **Amazon Bedrock AgentCore** 做了约30分钟的入门实验，让代理查询 CloudWatch 中处于 ALARM 的警报。目的在于理解 Runtime 执行环境、模型、工具、Gateway 入口与 Harness 的组合关系，并非生产系统压测。前提是**东京区域、相应服务操作权限，以及已开启 Bedrock 模型访问**。

CloudFormation 创建调用 `describe_alarms(StateValue="ALARM")` 的 Python Lambda、只读执行角色和 Gateway 调用 Lambda 的服务角色。函数返回 Metric 和 Composite 两类警报。Gateway 将 Lambda 作为 MCP 工具接入，实验为简化配置选择 IAM 而非 JWT；信任策略按账号和网关名称前缀约束，调用权限也限定到目标函数。

作者遇到的失败是 Gateway 自动创建角色后，后续工具目标未成功注册。该实验改为**预先创建服务角色，并让 Gateway 名称符合信任策略的前缀条件**。这是特定环境的故障及规避方式，不能写成所有自动角色创建都会失败。

Harness 使用 Bedrock 的 Claude Haiku 4.5 系列与已建网关，关闭记忆，不加存储、浏览器或代码解释器。测试警报用 **`TreatMissingData: breaching`** 把缺测视作违规，制造稳定的 ALARM 状态。第一次自然语言请求返回权限不足，没有走已连接的专用工具；在系统提示中明确什么时候使用 **`lambda-cwalarm-target`** 后，代理才按预期读取警报。

这说明连接工具和正确选用工具是两件事。遇到权限错误时，应先检查实际调用路径，而不是立即放宽 IAM。另一个代码层面的边界是，示例仅处理一次 `describe_alarms` 返回，没有展示分页遍历，因此大量警报场景的完整性尚未验证。

作者几次试运行的花费**低于$1**，条件是不额外启用记忆与存储，不能推广为生产成本。清理顺序依次是 Harness、Gateway 的工具目标、Gateway、CloudFormation 栈和自动角色，以解除依赖。实际使用仍需设置允许工具、迭代次数、超时、Token 上限和会话裁剪，并验证异常流程。

**关注点：★★★★★**

用实际工具选择失败说明接口接入、IAM 权限和提示中的调用条件是不同检查层次。

**関連Project（学習用）：** 检验子代理实际继承的父会话范围。

**キーワード：** `fork` / `SendMessage` / `print`

### 話題4：LLM / Evaluation

**约 30 秒自然日语回答：**

**関連Project（学習用）：** 以相同页面任务和推理设置比较模型。

**キーワード：** `Gemini 3.7 Flash` / `Terminal-bench` / `2026年末`

### 話題5：AWS / Agent Runtime

**面试问题：**

> 接続したツールをエージェントが使わないとき、どう調べますか。

**约 30 秒自然日语回答：**

> 権限を広げる前に、実際の呼び出し経路を確認します。AgentCoreの記事では、GatewayにLambdaを接続しても選ばれず、使う条件をシステムプロンプトに明示すると動きました。TreatMissingDataで異常状態も用意して検証しています。例は読み取り専用です。ただし小規模な確認なので、権限不足、対象なし、多数の結果も分けて試します。

**関連Project（学習用）：** 用已知 ALARM 与无结果场景检查工具选择。

**キーワード：** `Gateway` / `Lambda` / `TreatMissingData`

## 4. 今日技术主题

### 把代理的组成边界对应到具体运行检查

除了连接组件，还要检查继承哪些信息、允许哪些操作、实际调用了哪个工具。DeepSeek Harness 的事件流、fork 的会话继承和 AgentCore 的 Lambda 调用对应不同验证目标。网页内容即使被整理，也仍应保持不可信数据的身份。

```text
配置模型与执行组件
    ↓
明确信息、权限与发送目标
    ↓
用已知输入和预期结果测试
    ↓
核对实际工具路径
    ↓
记录限制与费用
```

**优点：** 暗号检查继承，已知 ALARM 检查工具读取，事件记录检查路径，让测试直接对应目标。

**限制与注意点：** 文本清理不能消除普通语言中的恶意内容；功能启用和基准分数也不能证明业务可靠性。

**日本企业应用：** 版本更新时同时验证工具选择、必须拒绝的操作和设置迁移，并把费用期限与外发信息纳入共同检查条件。

**回答ポイント：** 期待するGatewayのツールを選んだかを確認します。記事はツールを使う条件を明示して動作を直しており、権限の追加とは別の問題です。

**品詞：** 名詞｜**意味：** 权限｜**目安：N2**  
**コロケーション：** 権限を制限する / 実行権限 / 最小権限

**例：** `Sub-agentにはTaskに必要な権限だけを与えます。`

**ニュアンス：** 常与「～に対する耐性」搭配。

### 3. 侵入（しんにゅう）
**品詞：** 名詞｜**意味：** 侵入｜**目安：N2**  
**コロケーション：** 不正侵入 / 侵入経路 / 侵入を防ぐ

**例：** `AgentがTaskの目的から逸脱していないか評価します。`  
**中文：** 评估 Agent 是否偏离任务目标。

### 5. 監視（かんし）

**例：** `Long-running Agentの状態を監視基盤で追跡します。`  
**中文：** 通过监控平台追踪长期运行 Agent 的状态。  
**ニュアンス：** 比「見る」更强调持续观察。

### 6. 実行する（じっこうする）
**品詞：** 動詞・サ変｜**意味：** 执行｜**目安：N2**

**中文：** 危险命令在隔离的 Sandbox 中执行。  
**ニュアンス：** 与程序和命令真正执行的语感很强。

### 7. 防止する（ぼうしする）

**例：** `Toolの権限を絞って被害の拡大を防止します。`  
**中文：** 通过缩小 Tool 权限防止损害扩大。  
**ニュアンス：** 比「防ぐ」更书面、更偏制度性措施。

### 8. 評価する（ひょうかする）

**ニュアンス：** 技术报告中比「ずっと」正式。

### 19. 安易に（あんいに）

**ニュアンス：** 适合说明 Trade-off。

## C-3. JLPT文法

### 1. ～かねない
**Level：N1｜意味：** 有可能导致不良结果  
**形：** `動詞ます形去ます + かねない`  
**使い方：** 警示 Prompt Injection 或过度权限可能带来严重后果。  
**例：** `外部入力をそのまま実行すると、機密情報を送信しかねません。`  
**補足：** 通常用于负面风险。

### 2. ～にとどまらず
**Level：N1｜意味：** 不仅限于……  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 说明 Agent Evaluation 不只测 Model，也要测 Harness、Tool 与 Runtime。  
**例：** `Agent EvaluationはModel性能にとどまらず、HarnessやToolの安全性まで対象にします。`  
**補足：** 适合范围扩展。

### 3. ～なくしては
**Level：N1｜意味：** 没有……就无法……  
**形：** `名詞 + なくしては`  
**使い方：** 强调持续 Evaluation 与 Trace 是生产 Agent 的基础条件。  
**例：** `継続的なEvaluationなくしては、Agentの安全性を維持できません。`  
**補足：** 语气较强。

### 4. ～に応じて
**Level：N2｜意味：** 根据……相应调整  
**形：** `名詞 + に応じて`  
**使い方：** 按 Task Risk 决定权限、Sub-agent 和 Human Approval。  
**例：** `TaskのRiskに応じてHuman Approvalの要否を決めます。`  
**補足：** 强调条件和对应措施。

### 5. ～一方で
**Level：N2｜意味：** 另一方面……  
**形：** `普通形 + 一方で`  
**使い方：** 说明自主性与安全风险的 Trade-off。  
**例：** `Sub-agentは並列化に有効な一方で、Contextと権限の管理が複雑になります。`  
**補足：** 适合面试回答。

### 6. ～たうえで
**Level：N2｜意味：** 在……之后、在……基础上  
**形：** `動詞た形 + 上で`  
**使い方：** 先机器 Evaluation 再决定是否扩大 Agent 权限。  
**例：** `Production-like Taskで評価したうえで、利用範囲を拡大します。`  
**補足：** 强调前一步是决策依据。

### 7. ～にかかわらず
**Level：N2｜意味：** 不论……都……  
**形：** `名詞 + にかかわらず`  
**使い方：** 表达所有 Agent 都必须遵守的共同安全规则。  
**例：** `利用するModelにかかわらず、外部入力は信頼できないものとして扱います。`  
**補足：** 适合统一 Policy。
