### 1. Clef 单据核对：区分完全一致、语义和阈值

**原文：** https://dev.classmethod.jp/articles/cloudflare-clef-cross-match/

**发布时间：** 2026-10-05 08:00:00 JST

发票与采购单经常出现日期格式、币种记号和公司名称写法不同的问题。字符串不同未必代表业务值不同，但把所有差异都解释为格式变化，也可能放过金额或交易对象的实际差异。作者利用 Workers AI 的 Clef 与 Jev 的 API 兼容性，向它们提交同一组对照值和问题；接口可复用，并不意味着概率分布和判定行为可直接复用。

测试包含完全虚构的107组数据，覆盖日期、金额、交易方、地址、OCR 误读、缺失等10类。exact 判断字符是否完全相同，semantic 判断不同写法是否指向同一值，二者分别评分。语义评价排除了一个无法唯一判断的日期，分母是106。英语与日语只是指令和提问语言不同，待比较的数据始终是同一组日英混合值，不能把实验解释成两套不同语言的数据集。

原定阈值为 yes 概率不低于0.8；27B 的 clef 和9B 的 clef-flash，各以英日问题运行一次。Jev 对照来自9月20日的 jev-1.13.0，作者在修正3-6号样本真值后重新评分。它不是所有模型在同一时间、同一服务负载下的同步跑分，也不是实际客户单据的验证。

英语 Clef 的 exact 为107/107，但 semantic 仅91/106；日语问题分别为105/107与76/106。Jev 英语为106/107和96/106，日语为105/107和97/106。flash 英语为102/107和57/106，日语为104/107和65/106。这些结果说明“字符一致判断很好”不能替代“业务语义一致判断很好”，改成日语提问也没有统一改善。

不少错误来自真实相同的值所获概率低于0.8。英语 Clef 降至0.6后达到97/106，但错误判成一致的样本变成4个；Jev 英语在0.8下是96/106、误判一致3个。原文有一处把两者正答数概括为同等，日报保留表格中的97与96，不写成精确相等。降低阈值同时改变漏报和误报，不能只挑更高的总分。

英语条件下响应时间中位数为 Jev 0.709秒、Clef 0.499秒、flash 0.310秒。按作者1美元150日元的计算，107次的费用约0.34、1.40、0.53日元。尽管 Clef 系平均输入364 token，低于 Jev 的509，单价差仍使总费更高。这些是文章的测量与计价条件，不作为最新报价；网络和服务器混杂也可能改变速度顺序。

本文的工程应用建议是先定义币种缺失、OCR 的字母数字混淆及空值真值，再按误报损失决定自动处理与人工核对边界，并保存重新标注的记录。作者也没有确认 Jev 的日语官方支持。有限的虚构样本和单次运行不能证明生产环境的优劣，因此保留条件，避免把“更快”或“兼容”写成普遍保证。

**阅读价值：** 同时记录判定定义、阈值、误报与漏报，能避免把 API 兼容误当成模型行为相同。

### 2. Security Agent：按事件、分支和标签触发 PR 审查

**原文：** https://dev.classmethod.jp/articles/security-agent-pr-review-condition/

**发布时间：** 2026-10-04 19:49:55 JST

AWS Security Agent 可以对已连接仓库的 PR 进行自动安全审查并发表评论。本文原作者实测的是按目标分支、标签及 PR 事件过滤启动条件。文章以 AWS CLI 2.37.9 的变更记录介绍更新，但没有据此证明服务上线的精确日期；日报区分文章发布与产品更新。

作者起初连接公开仓库，发现代码审查评论显示不支持，触发配置也没有出现。原文及其核对的官方资料说明评论针对非公开 GitHub 仓库，因此实验改用非公开测试仓库。成功连接代码不等于所有审查功能都可用，不能照搬到公开项目后把没有评论当成配置失效。

实验设置两个组：第一组是“准备好审查”事件、目标 main；第二组是“新增标签”事件、标签 security-.*。每组内部条件必须全部满足，多个组之间任意一组成立即可。第二组并未附加 main 条件，所以 develop 的 PR 也能通过匹配标签触发。这一 AND/OR 关系是排查覆盖范围的关键。

条件使用匹配整个名称的正则表达式，并非 shell 通配符。官方说明采用 RE2 的完整名称匹配；security-.* 可以匹配 security-review。没有指定事件的组会覆盖创建、更新和准备完成，也包括草稿。要排除草稿，就需明确事件，不能只按分支筛选。[官方触发说明](https://docs.aws.amazon.com/securityagent/latest/userguide/configure-code-review-triggers.html)

作者给 main、develop 建分支，并加入含漏洞的 Python 文件。main 普通 PR 数十秒后出现开始评论，约两分半得到结果；main 草稿数分钟内未启动，转为 Ready for review 后启动。develop 普通 PR 约100秒内没有评论，在另一 develop PR 添加 security-review 后约20秒出现开始评论。报告这组观察时必须区分开始与审查完成，而不是把20秒当成完成速度。

配置过程中还遇到空目标分支条件无法保存、删行未解决，只能重建整个组的现象。这是单个作者的操作记录，并非全局已证实的故障。短时没有评论也不是永远不执行的证明；生产检查还要核对权限、事件和过滤结果。

文章注明 PR 审查额度按账户、区域为每月1000次，过滤可减少不必要消费。日报的应用判断是同时检测正例和反例，并确认筛选没有漏掉关键 PR。该实验验证的是触发行为，没有测漏洞检出率、漏检率或修复正确性；不能把启动成功解释成完整安全验收。

**阅读价值：** 触发器配置影响审查覆盖和额度消耗，适合练习正例、反例与状态切换的自动化验收。

### 3. Snowflake：为账户预算增加分级通知

**原文：** https://dev.classmethod.jp/articles/snowflake-set-notification-custom-actions-to-root-account-budget/

**发布时间：** 2026-10-04 11:03:49 JST

Snowflake 的账户预算监控账户内全部 credit 消耗，定制预算则可限定资源或标签。作者在自己的 Snowsight 界面只看到账户预算的上限通知，因此用 SQL 增加自定义动作。此处是界面能力与 SQL 能力的差别，不能把“界面没入口”写成服务不支持。

试验建立了1 credit 的账户预算，通过 ACCOUNT_ROOT_BUDGET 的 ACTIVATE 激活，SET_SPENDING_LIMIT 设置金额，SET_EMAIL_NOTIFICATIONS 设置邮箱。预算启用、邮箱配置和追加动作运行是三项不同检查，不能以其中任一项成功替代完整链路。

EMAIL 型通知 integration 设置启用和允许收件人。创建需要 CREATE INTEGRATION 权限，实际发送角色取得 USAGE，收件邮箱还须在账户中验证。示例分别使用 ACCOUNTADMIN 和 SYSADMIN，不证明普通用户或其他角色有同样访问权，也不建议直接复制示例地址。

发送动作由 Python 3.11 与 Snowpark 的存储过程完成，接收 integration 名、收件人、主题和正文，拒绝空参数后以参数绑定方式调用 SYSTEM$SEND_EMAIL。程序使用 EXECUTE AS OWNER，需关注所有者权限。作者对 SNOWFLAKE application 授予数据库、schema 和过程的 USAGE，并先手动 CALL 验证邮件确实收到，再连接预算。

登记时 ADD_CUSTOM_ACTION 使用 SYSTEM$REFERENCE 指向过程、ARRAY_CONSTRUCT 提供参数，最后明确传入 ACTUAL、75。真正执行含义是实际消耗达到预算75%，不是预测消耗。原文的 SQL 注释与邮件文案写着 projected，但执行参数和官方定义一致指向实际消费；日报据此解释，并说明差异，避免把文字标签当成运行语义。[官方参数定义](https://docs.snowflake.com/en/sql-reference/classes/budget/methods/add_custom_action)

作者增加使用量后收到75%与100%超额通知，但表示超额约发生在五小时前，两封邮件后来集中到达。他把现象解释为最长6.5小时的预算刷新周期造成；这是作者推断，文章没有提供能够排除其他延迟原因的独立追踪。保留小预算实测条件，而不保证实时送达或固定延迟。

本文的运用建议是依次验收收件人验证、手动发送、动作注册和真实收件时间，并评估生产业务对延迟的容忍度。即使多个阈值之间的金额较大，也不能自动认为延迟无影响。这段示例只有监测和通知，没有证据证明强制限额或即时停止；也不把服务支持的通用动作上限等同于此次实验登记数量。

**阅读价值：** 预算、通知权限和更新周期要分别验证，能区分成本预警与实时止损控制。

### 4. 通过 Slack 委托 AI：冻结指令，持续更新进度

**原文：** https://zenn.dev/ishizakahiroshi/articles/20261004-dots-slack-instruction

**发布时间：** 2026-10-04 14:17:23 JST

作者介绍从 ChatGPT、Claude Code、Claude.ai 进入，经 Slack 把开发工作交给 dots 的个人流程。入口增加时，如果每次只靠聊天推断任务和状态，会难以追踪。因此他把任务编号、固定 Git 指令书、最新进度和同一 Slack 线程串联。dots 是作者使用的另一执行环境里的工作者，文章没有提供可验证的内部架构或面向所有用户的供应条件。

编号先从本地台账取得；相同仓库和任务 key 维持同一编号，Issue 与 PR 的数字保持独立。README 指定范围、禁止事项、交付物和接受条件，REVIEW 保存独立检查项，再以带 commit 的 URL 交付。这使“原先约定的任务”可以回读，不会因分支文件更新而悄悄改变要求。

PROGRESS 则应放在成果分支，持续更新阶段、负责人、状态、产物和下一步。冻结的是任务含义，变化的是实际进度。若全冻结，进度会过时；若全可变，验收依据会漂移。这是日报基于作者操作的整理，不是原文声称的新协议。

Slack 的父 DM 写编号和题名，后续保持同一线程。发送成功或回读文本，只证明消息存在，不证明工作者理解或开始执行。作者还核对接受回复里的固定 commit、目标仓库、运行环境、依赖、浏览器能力、交付分支和阻碍因素；送达、接受与验证分别记状态，不能互相代替。

作者表示在三种入口确认发送，但连接可用性取决于账户和会话条件，Claude Code 的例子还包括重启后才可用。某个入口没有显示连接，不足以证明平台全面不支持。日报只记录作者体验，不替所有组织或未来界面保证操作步骤，也没有替他重新完成连接配置。

没有回复时，外部只读查看分支、PR、CI、Issue 和进度文档。60分钟无变化即标为停滞，是作者选定的运维值，不是服务超时保证；不能据此自动重派、结束或合并。原文包含下载依赖失败、在本机补救及超过两小时仍无 PR 的例子，因此建议把任务切到30至60分钟左右，但不保证这个时长必然交付。

有产物后冻结报告中的 commit，再在独立环境检查测试、UI 与线上结果，区分草稿、提交、验收、发布和在线确认。原文注明文章与图片由 dots 制作，日报按作者公开体验引用，而非独立性能测评。公开指令也不应包含密钥、cookie 或私有日志；阅读案例不意味着实际向其他人或服务发送任务。

**阅读价值：** 把编号、冻结合同、更新进度和独立验收放到明确位置，适合设计可追踪的代理交接。

### 5. Jeff 与 Kev 0.8B：核对速度、精度和比较条件

**原文：** https://zenn.dev/null_teck/articles/jeff-08b-vs-kev-08b-decision-models

**发布时间：** 2026-10-04 12:09:48 JST

作者比较以 Qwen3.5-0.8B-Base 为基础的 Jeff 与 Kev，它们主要返回类型化判断而不是长篇生成文字。文章讨论把小模型放在大模型前做快速判断，但相同0.8B并不表示训练、输出 head 或推理实现相同。日报将它作为比较证据的阅读练习，而不是直接沿用胜者结论。

环境是 RTX3090 24GB、Windows11 Pro/WSL2/Ubuntu24.04、CUDA12.6、PyTorch2.6.0+cu126 和 Python3.11。作者从同一客户端发 HTTP JSON 并测端到端响应。Jeff 配备按长度分桶的 CUDA Graphs，Kev 使用标准 PyTorch 实现；初始化的权重处理也不同。因而速度差包含运行时优化，不能单独归因于模型架构。

S1Bench 分成五类分类250题，以及加入 HelpSteer2 后的300题。分类结果为 Jeff 222/250、Kev 149/250；全体为230/300、162/300，p50 为15.7与150.4毫秒。Jeff 并未直接实现 score 回归，文章把概率最大索引近似映射成分值，得9/50，并指出严格要求该输出类型时是0分。18%不是正常实现 score 接口的质量。

Kev 用概率期望四舍五入得到13/50。原文称其26%显著超过随机20%，但没有统计检验或置信区间。日报仅保存观察比例，把统计显著性列为未核实，不把经验形容词转为统计结论。分类250题表现好，也不能证明包含数值评审的所有业务表现好。

童话边界13题中，旧问题 Jeff 9/13、Kev 11/13；把两种选择解释改为对称后，二者均11/13，但错误题不同，需要区分说谎与隐瞒身份。15道长合同题为15/15和8/15，20道语用及双重否定题为15/20和9/20。这些小型自制题的结果不保证法务、业务审核或安全系统正确。

语义 grep 涉及4988行猫正文加6条童话，共4994行。Jeff 并发4报告68.82行/秒、72.56秒全量完成。Kev 的5.82行/秒对应857秒和14.3分钟，表内注明是换算，所以不作为完整4994行实测。误报率也不同：Jeff 989/4988约19.8%，Kev 48/500为9.6%。母数差异和抽样限制使“误报减半”的直接公平全量比较无法成立，必须说明而非删除这个限制。

作者将速度差解释为 CUDA Graphs 等优化，但没有只切换该因素的控制实验。Kev 可优化到20至30毫秒、Jeff 推测的官方排名和分数、附录宣称某大模型具绝对精度，都不是这次实测能证实的结果，故不采纳为事实。文内1.69GB与1.65GB的显存数值也不一致，日报不据此下精确占用结论，并注明不保留的原因。

采用前应统一输出类型、负例、阈值、样本数、输入长度、预热和并发，再分别记录延迟、误报、漏报和未支持类型。必要时保留判断而非强行二选一。日报复核了原表分数与换算关系，没有独立跑模型；两项目当前官方说明可能对应新版本，也不能混进原实验数字。

**阅读价值：** 原文表格暴露样本量、任务类型和运行时差异，适合练习在采用小模型前审读证据，而不是记住排行榜结论。

### 1. Clef 单据核对：区分完全一致、语义和阈值

### 1. 確信度（かくしんど）｜N1

- 词性：名詞
- 含义：对判断有多大把握的程度
- 搭配：確信度が低い / 確信度を確認する / 確信度に差がある
- 文章语境：Clef 原文把低確信度数据转给人工核对。
- 例句：確信度が高くても、誤りがないとは限らない。
- 例句译文：即使置信程度高，也不一定没有错误。
- 语感区别：不同于统计的信頼区間；模型输出自信不等于校准后的正确概率。

### 2. 通貨（つうか）｜N2

- 词性：名詞
- 含义：货币、用于支付的货币单位
- 搭配：通貨を指定する / 通貨が異なる / 通貨の記号
- 文章语境：Clef 单据实验区分金额相同和币种相同。
- 例句：数字が同じでも、通貨が違えば同じ金額ではない。
- 例句译文：数字相同，但币种不同就不是同一金额。
- 语感区别：金额是数量，通貨是单位；两种概念不能省略其中一个。

### 3. 台帳（だいちょう）｜N1

- 词性：名詞
- 含义：登记事项并供持续核对的账册

### 4. 身分（みぶん）｜N2

- 词性：名詞
- 含义：个人在社会或组织中的身份
- 搭配：身分を隠す / 身分を明かす / 身分を確認する
- 文章语境：Jeff/Kev 童话题区分隐瞒身份和只说谎。

- 语感区别：不同于役割：役割是承担的任务，身分是本人或社会地位。

- 语感区别：切り上げ是始终向上，切り捨て始终向下，四捨五入有边界规则。

### 14. 受け取る（うけとる）｜N3

- 词性：動詞・五段
- 含义：接收交来的物品、消息或产物
- 搭配：成果を受け取る / 通知を受け取る / 資料を受け取る
- 文章语境：dots案例的独立受取是收到产物后另做检验，未等于认可。
- 例句：成果を受け取ってから、受入条件に沿って確認した。
- 例句译文：收到产物之后，再按接受标准检查。
- 语感区别：受け入れる是认可或接受安排；这里受け取る只指产物到手，不代表批准。

### 15. 控えめ（ひかえめ）｜N2

- 词性：形容動詞
- 含义：克制的、程度偏低的
- 搭配：控えめな値 / 控えめに出す / 控えめな表現
- 文章语境：Clef对同值也输出较保守概率，因此旧阈值漏掉匹配。
- 例句：控えめな確率だからといって、すべて正しいとは言えない。
- 例句译文：概率比较保守，也不能说判断全都正确。
- 语感区别：不同于慎重：控えめ描述表达或量的少，慎重描述做事谨慎。

### 16. 古風（こふう）｜N1

- 词性：形容動詞
- 含义：古雅的，带有旧时代的风格
- 搭配：古風な表現 / 古風な言葉 / 古風な言い回し
- 文章语境：Jeff/Kev对白雪姫“身をやつす”这种古风表达有不同反应。
- 例句：古風な言い回しも、評価用の文に含めた。
- 例句译文：评测句子也加入古雅的表达。
- 语感区别：与時代遅れ不同：古風可以赞许旧时风格，不表示功能已过时。

### 17. 不向き（ふむき）｜N2

- 词性：形容動詞
- 含义：不适合，不符合某用途的要求
- 搭配：大量走査には不向き / 不向きな用途 / 用途に不向きだ
- 文章语境：Jeff/Kev附录讨论不同用途的局限，不能直接当实测绝对结论。
- 例句：速い処理でも、数値の評価には不向きかもしれない。
- 例句译文：处理虽快，也可能不适合数值评价。
- 语感区别：不同于不能：不向き是适合度的判断，未必表示功能完全不可实现。

### 18. 意外と（いがいと）｜N2

- 词性：副詞
- 含义：出乎预料地
- 搭配：意外と少ない / 意外と難しい / 意外と見つからない
- 文章语境：Snowflake 作者说官方文字有说明，但具体账户示例意外地少。
- 例句：具体例が意外と少ないので、引数の定義も確認した。
- 例句译文：具体例出乎意料地少，所以也核对了参数定义。
- 语感区别：属于口头自然用语；意外に较书面，不等于“実は”纠正事实。

### 19. 対称（たいしょう）｜N2

- 词性：名詞
- 含义：对称，两侧具有对应结构
- 搭配：対称な説明 / 対称にそろえる / 対称性を確認する
- 文章语境：Jeff/Kev新命题把两个选项写成对称的身份描述。
- 例句：二つの選択肢を対称な説明にして、語彙の偏りを減らす。
- 例句译文：把两个选项改成对称描述，减少措辞偏差。
- 语感区别：与同率不同：対称是表述结构，同率是结果比例；结构对称不保证结果相同。

### 20. 一概に（いちがいに）｜N2

- 词性：副詞
- 含义：一概地、无视条件差异统一断定
- 搭配：一概には言えない / 一概に決める / 一概に否定しない
- 文章语境：Clef原文因混杂和网络差异，不一概说某模型总更快。
- 例句：一回の測定から、一概に優劣を決められない。
- 例句译文：不能凭一次测量一概断定优劣。
- 语感区别：不同于一律に：一律描述统一处理规则；一概强调省略差异的笼统论断。

1. **exact / semantic（完全一致／意味一致）**：分别检查字符相同与业务值相同。 Clef实验分母107与106，保留歧义日期。

### 1. ～か否か｜N1

- 含义：是否……，以正式方式提出二择判断
- 结构：普通形＋か否か（名詞・ナ形容詞の肯定現在は、だを省くことが多い）
- 用法：书面语和技术判定中明确“成立或不成立”。原文用它限定是否隐瞒身份，避免被“秘密”等关联词牵走。
- 原文形态：隠蔽しているか否か
- 原文依据：[身分を偽り隠蔽しているか否か](https://zenn.dev/null_teck/articles/jeff-08b-vs-kev-08b-decision-models)
- 独立例句：指定した出力型へ対応しているか否かを、速度とは別に確認する。
- 例句译文：是否支持指定输出类型，须与速度分开确认。
- 注意：比かどうか正式；它只设定二择问题，不保证模型知道答案，也不消除需保留的未知。
