# A. 详细文字版

今天重点核对指示适用范围、权限生效条件和远程会话的创建与恢复。语言及模型比较分别注明提供者观点、公表成绩和作者实际验证的边界。

## 1. 今日最值得看的 5 篇

### ① Kiro IDE、サブディレクトリのAGENTS.mdをサポート

**来源：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/kiro-ide-subdirectry-agentsmd/

**Kiro IDE 1.0.309** 新增读取子目录 **AGENTS.md** 的能力。此前 IDE 主要读取工作区根目录或 `~/.kiro/steering/` 的规则；CLI 较早支持的分层规则现在进入 IDE。针对单仓多服务项目，可以分别维护全局规范和服务特有要求。

作者在根目录设置 TypeScript strict mode、提交约定；API 目录规定 Prisma、zod 与 async/await；前端目录规定 Tailwind CSS、函数组件和 named export。新会话首先显示根规则已加入 **Included Steering**，子目录规则则在代理访问相应文件时动态进入上下文，而不是开始就一次加载全部目录规则。

实际创建 API 文件时，输出遵守不使用 raw SQL 等要求；前端文件采用目标目录的 Tailwind、named export 与 aria-label。作者还确认**只读文件也会触发对应子目录规则**。这种按访问加载的机制减少了每次把全部项目规范重复写入提示的必要。

限制是实验只覆盖1.0.309中的这些案例，没有全面测试更深嵌套、互相冲突的规则或所有读取工具。规则被读取也不等于生成代码必然全部合规。实际应用应同时检查加载记录和成果物，再结合类型检查与评审验证。

**关注点：★★★★★**

通过常驻根规则与按访问加载子规则的区别，解释单仓多服务的代理指示组织方式。

### ② AI時代は「Go言語」が理想の言語に？ Googleが解説する「Goの価値」

**来源：＠IT**

**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2608/15/news013.html

＠IT 用两页介绍 Google 的观点：AI 大量生成代码后，语言的价值不能只看手写速度，还要看**阅读、验证和长期维护的成本**。文章讨论统一工具及团队协作，而没有提供在同一任务上横向比较多种语言的成功率或费用实验。

第一条理由是静态类型与快速编译。不存在的方法、参数类型不一致等问题可尽早反馈给代理，形成修改后重新检查的循环。但**编译成功不能证明业务逻辑正确**，需求满足与边界行为仍由测试和人确认，不能写成编译器自动消除全部 Bug。

第二条是 **gofmt 的格式统一**，以及 Go 倡导的简单、明确的代码写法。减少风格差异后，评审者可以更集中地检查含义。需要区分工具与设计理念：gofmt 负责格式，不会自动删除复杂设计或纠正逻辑错误。

第三条是标准库与 **govulncheck 等验证工具**，用减少不必要依赖和检查已知漏洞相关调用来管理风险，并非保证没有未知漏洞。第二页进一步区分解决单个问题的编程，与团队长期设计、实现、运行系统的软件工程，强调共同工具链和向后兼容方针。

可迁移的面试判断是：语言及生态能否让生成结果被及时编译、整形、测试和检查依赖，再结合现有资产、团队能力与部署条件选择。不能由此认定所有 AI 项目都应改成 Go。[Google 原始说明](https://developers.googleblog.com/why-go-is-an-ideal-language-for-ai-assisted-software-engineering/)属于这些主张的依据，不是跨语言量化优越性的证明。

**关注点：★★★★★**

从验证链而不是“最适合 AI 的语言”口号切入，准确区分静态类型、格式化与安全扫描。

### ③ AWS DevOps Agent Guardrail、ReadOnlyAccessをサポート

**来源：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/devops-agent-readonlyaccess-permission-guardrail/

**AWS DevOps Agent** 的8月5日更新，让权限防线支持 **ReadOnlyAccess** 全部动作，另加 Athena 查询开始、停止以及 `kms:Decrypt`。此前按8种服务列出的额外动作因此被重新整理。关键是**防线允许的最大范围不等于执行角色已经获得的权限**。

默认 **AIDevOpsAgentAccessPolicy** 只授予其中一部分。额外权限必须显式加入；根据原文引用的说明，默认策略之外的可允许动作并未经过同等验证，使用者需要判断是否适合让代理针对自己的资源执行，并缩小范围。不能因为名称带 ReadOnly 就认定任何资料都可公开给代理。

默认策略在8月12日更新到 **v10**，没有删除动作，增加34个：CodeCommit25个、Config2个、Glue1个、KMS6个。这属于实际默认授权的演变，与防线扩大是不同变化，不代表支持的所有新动作都已默认授予。

作者附加 ReadOnlyAccess 和 Athena 查询执行权限，预先启用工作组的 **Managed query results**，让结果保存到 Athena 托管存储。随后依次启动查询、轮询到 SUCCEEDED、获取结果，读到 **28,127,791件** CloudTrail 事件。实验确认了默认策略不包含的 GetQueryExecution、GetQueryResults 可用，并比较了附加前后对 Bedrock AgentCore 的查询能力。

事件数量不是速度或精度指标；限制是实验仅对应这组角色权限与结果存储配置，不代表已验证全部数据操作。实际设计应选择必要动作和资源，并同时检查开始查询、获取结果、必要解密和不该被读取的数据范围。

**关注点：★★★★★**

分清权限上限、默认授权和主动扩展，用 Athena 完整调用链检验权限是否真正生效。

### ④ Claude Code Remote ControlのServer mode

**来源：Zenn**

**原文：** https://zenn.dev/0msys/articles/486b44b3af083d

作者在 Mac mini 开发，从 iPhone 操作 Claude Code。过去通过 `/remote-control` 接入已有会话，另开工作仍要在 Mac 端先准备。**`claude remote-control` 的 Server mode** 则作为等待连接的常驻服务，允许手机端新建会话，本地终端不再是可直接输入的交互会话。

文章介绍默认并发上限32，作者实际从 iPhone 的代码标签页创建了新会话。`same-dir` 让会话共用目录，**同时编辑相同文件可能冲突**；`worktree` 为后续会话建立 Git 工作树，但仍限定同一仓库；`--spawn=session` 只接收一个会话。服务的工作范围是启动目录，其他项目需要另起服务。

作者还遇到 iPhone 不显示工作目录、无法按文件夹分组的问题。试用 `--name`、`--remote-control-session-name-prefix` 和 **SessionStart hook** 后，仍没能让手机追加会话自动带项目名。名称参数只影响初始会话，prefix 用于没有显式名字时的自动命名，不能当作所有后续会话的统一前缀。

同目录重启还涉及恢复：停止约4小时内，会恢复原有会话，因此新的命名参数可能看似无效。作者改在未用过的目录验证。hook 的标题值虽被日志记录为收到并缓存，却未显示到列表；关于子进程采用 print 模式导致问题的解释，原文仍是推测，没有独立证明因果。

证据是约半天的个人试用，不代表所有终端或版本都不能自动命名。可以确认手机新建会话，而在作者检查范围内，名称区分仍靠手工调整。把**创建和恢复、共用目录和工作树**分开，才能准确判断参数作用与文件冲突风险。

**关注点：★★★★★**

从创建、恢复和工作目录三个维度理解远程会话，避免把名称恢复误判为参数失效。

### ⑤ GLM-5.3：Post-trainingでLong-horizon Codingを強化

**来源：gihyo.jp**

**原文：** https://gihyo.jp/article/2026/08/glm-5.3

Z.ai 于8月14日发布 **GLM-5.3**，沿用 GLM-5.2 的 **743B** 基础模型，通过扩大后训练的环境、任务和计算资源提高能力。训练重点转向长时间开发工作，例如定位机器学习系统性能瓶颈、实现修改并验证正确性，而不只是短题。任务生成和验证虽使用代理，仍需要较多人工参与。

提供者称改进 **slime** 后，强化学习整体吞吐提高2.3倍以上。这个数字描述训练流程，不是用户推理速度。公开旧版对比中，Terminal-Bench 3.0由4.6升到28.3，DeepSWE v1.1由46.2到66.9，Agents' Last Exam由23.8到28.5；后者接近 GPT-5.6 Sol 的28.6，但并非所有测评都超越它。

私有 Z.ai Code Bench 约50%的提升需要与公开基准分开。安全方面，**CyberGym 从77.2%升到84.5%，ExploitBench 从24.4%升到54.4%**。提供者还报告合作团队经专家确认和去重，从269个 OSS 项目发现2,436个漏洞，其中1,097个为 Critical/High；报道没有提供所有结果的复现证据或独立复测。

发布时可通过 GLM Coding Plan、ZCode 等使用，**模型权重计划在完成安全评估后两周公开**，不能写成发布日就已可下载。额度改为按输入、缓存输入和输出计算的积分，UTC+8 平日14～18时为高峰，其他时间含周末按50%积分消耗。

API 的 **`reasoning_effort` 提供 low、high、max，默认 max**，不能关闭推理。原文主要整理提供者成绩与计划，说明相同基础规模也能通过后训练改善能力；同时必须分开训练效率、代码评价、漏洞分析与使用价格，不能将它们合并成笼统的“性能提升”。

**关注点：★★★★★**

准确区分后训练提升、训练吞吐、推理配置与权重发布时间，避免不同指标互相替代。

## 3. 面接で使えるポイント

### 話題1：Context Scoping

**面试问题：**

> モノレポで、サービスごとに異なる開発規約をどう伝えますか。

**约 30 秒自然日语回答：**

> 共通の規約はルートに、固有の規約は各ディレクトリに置きます。Kiro IDEではAGENTS.mdを使い、対象ファイルにアクセスすると下位のルールが追加されます。読み取りだけでも適用される点が特徴です。ただし、読み込まれたことと規約を守れたことは別なので、Included Steeringの表示と生成コードの両方を確認します。APIと画面では指示も分けます。

**関連Project（学習用）：** 在小型单仓项目里拆分 API 和前端规则，对照加载记录与生成代码。

**キーワード：** `AGENTS.md` / `Included Steering` / `Kiro IDE`

### 話題2：AI Coding / Software Engineering

**面试问题：**

> AIがコードを書くなら、言語の選び方は変わりますか。

**约 30 秒自然日语回答：**

> 書く速さに加え、生成されたコードを確かめやすいかを重視します。Goは静的型で不一致を見つけ、gofmtで書式を揃え、govulncheckで既知の脆弱性を調べられます。ただし、コンパイルや整形だけで業務ロジックは保証できません。既存資産とチームの経験を踏まえ、テストと保守まで含めて選びます。記事は比較実験ではなく、Googleの見解です。

**関連Project（学習用）：** 对 Go 生成代码依次编译、格式化、测试及漏洞检查，记录每种工具实际发现的问题。

**キーワード：** `Go` / `gofmt` / `govulncheck`

### 話題3：AWS / Security

**面试问题：**

> ガードレールが読み取り権限に対応すれば、すぐ全データを調査できますか。

**约 30 秒自然日语回答：**

> 許容範囲と、ロールに付与した権限を分けて確認します。DevOps AgentはReadOnlyAccessに対応しても、既定で全部使えるわけではありません。記事のAthena検証は結果をAWS側に保存する設定で成功しました。ただし、追加権限は利用者が評価する必要があります。対象データを絞り、実行と結果取得の両方を試します。既定の付与は一部だけです。

**関連Project（学習用）：** 使用专门的测试数据，分别验证 Athena 启动与结果获取所需权限。

**キーワード：** `ReadOnlyAccess` / `Athena` / `Managed query results`

### 話題4：Claude Code / Multi-session

**面试问题：**

> 複数の遠隔セッションで、作業の衝突をどう避けますか。

**约 30 秒自然日语回答：**

> セッションが使うディレクトリを確認します。Remote ControlのServer modeでは、same-dirは共有、worktreeは同じGitリポジトリ内で作業場所を分けます。ただし、別プロジェクトには別のサーバーが必要です。また再起動は新規作成でなく復元の場合があります。名前だけで判断せず、対象の場所と未反映の変更を確かめて作業します。

**関連Project（学習用）：** 在临时仓库对照 same-dir 与 worktree，分别记录创建和恢复行为。

**キーワード：** `Server mode` / `same-dir` / `worktree`

### 話題5：Coding Model / Evaluation

**面试问题：**

> 同じ規模のモデルでも、性能が変わる理由をどう説明しますか。

**约 30 秒自然日语回答：**

> パラメータ数だけでなく、事後学習の課題と評価条件を見ます。GLM-5.3は743Bの基盤を変えず、長時間の開発課題を増やしています。slimeの2.3倍という値は学習の効率で、推論速度ではありません。ベンダーの成績を一般化せず、必要な作業と推論設定を揃え、正確さと実際の費用を確認します。

**関連Project（学習用）：** 固定任务与成功标准，记录 GLM-5.3 不同推理配置的结果、时间及点数消耗。

**キーワード：** `GLM-5.3` / `743B` / `slime`

## 4. 今日技术主题

### 区分“支持”与“在这些条件下验证成功”

指示和权限不能在配置完成后就视为验证结束。Kiro 随文件访问加载下级规则，DevOps Agent 的执行依赖角色授权及结果保存配置。Remote Control 若混淆新建和恢复，也会误判命名参数的作用。

```text
规格允许范围 → 实际配置 → 加载与执行记录 → 成果物及结果验证
```

Go 编译通过与 GLM 公表成绩同样各有边界。类型一致、特定任务分数与业务要求不能合并为一个含糊的“质量”；面试时需要说明每项判断的证据。

## 5. 面试复习卡

### Q1

> 指示の読み込みと、指示への適合は同じですか。

**回答ポイント：** KiroのIncluded Steeringで読み込みを確かめ、生成物は型検査やレビューで別に確認します。

### Q2

> 権限ガードレールの拡張だけでAthenaを実行できますか。

**回答ポイント：** 実行ロールへの付与と結果保存設定が必要です。開始、状態確認、結果取得を通して調べます。

### Q3

> 遠隔セッションの命名を調べるとき、何を分けますか。

**回答ポイント：** 新規作成と既存会話の復元、初期会話と追加会話を分けます。共有ディレクトリとworktreeの違いも確認します。

# B. 重点知识与面试应用

## 1. Kiro IDE、サブディレクトリのAGENTS.mdをサポート

1. 根规则在会话开始加载，子规则随目标访问加入。
2. 只读访问也会触发子目录 AGENTS.md。
3. 读取了指示与实际遵守指示需要分别验证。

## 2. AI時代は「Go言語」が理想の言語に？ Googleが解説する「Goの価値」

1. 生成与评审、验证、长期维护承担不同成本。
2. gofmt 统一格式，不验证业务逻辑。
3. 原文介绍 Google 观点，没有统一条件的跨语言对照实验。

## 3. AWS DevOps Agent Guardrail、ReadOnlyAccessをサポート

1. 防线许可与角色授权是不同层次。
2. 默认策略外的额外权限由使用者评估。
3. Athena 要同时核对开始、状态查询和结果获取的权限。

## 4. Claude Code Remote ControlのServer mode

1. Server mode 支持远程创建新会话。
2. same-dir 与 worktree 的文件共享边界不同。
3. 恢复既有会话时，新建用名称参数不一定生效。

## 5. GLM-5.3：Post-trainingでLong-horizon Codingを強化

1. 基础规模同为743B，改进集中在后训练。
2. slime 的2.3倍是训练吞吐。

## C-1. JLPT語彙

### 1. 範囲（はんい）
**品詞：** 名詞｜**意味：** 范围｜**目安：N3**  
**コロケーション：** 対象範囲 / 影響範囲 / 範囲を限定する  
**文脈：** Context Scoping 的核心就是控制每个 Agent 能看到和修改的范围。  
**例：** `Agentが参照できるContextの範囲をTaskごとに限定します。`  
**中文：** 按任务限定 Agent 可以参照的 Context 范围。  
**ニュアンス：** 技术说明中常与「限定・絞る・広げる」搭配。

### 2. 競合（きょうごう）
**品詞：** 名詞｜**意味：** 冲突、竞争｜**目安：N1**  
**コロケーション：** 変更競合 / 競合を解消する / Resource競合  
**文脈：** 多个 Coding Agent 并行修改代码时，Git 与文件层面的 conflict 是主要风险。  
**例：** `複数Agentの変更競合を減らすため、Working Treeを分けます。`  
**中文：** 为了减少多个 Agent 的修改冲突，分开 Working Tree。  
**ニュアンス：** 软件语境常对应 conflict；商业语境也可表示竞争。

### 3. 整合（せいごう）
**品詞：** 名詞｜**意味：** 一致、协调｜**目安：N1**  
**コロケーション：** 整合性を保つ / 仕様との整合 / データ整合性  
**文脈：** 自动验证要确认 Agent 生成代码与既有 Schema、Type 和接口保持一致。  
**例：** `生成Codeが既存Schemaと整合しているかTestで確認します。`  
**中文：** 通过测试确认生成代码是否与现有 Schema 一致。  
**ニュアンス：** 「整合性」常对应 consistency / integrity。

### 4. 保証（ほしょう）
**品詞：** 名詞｜**意味：** 保证、保障｜**目安：N2**  
**コロケーション：** 品質保証 / 互換性を保証する / 動作保証  
**文脈：** Deterministic Check 可以提高可靠性，但不能声称自动测试能保证所有质量。  
**例：** `自動Testだけで完全な品質を保証できるとは限りません。`  
**中文：** 仅靠自动测试未必能保证完整质量。  
**ニュアンス：** 工程语境应避免无依据的绝对保证。

### 5. 継承（けいしょう）
**品詞：** 名詞｜**意味：** 继承｜**目安：N1**  
**コロケーション：** 設定の継承 / Ruleを継承する / Class継承  
**文脈：** 目录级 AGENTS.md 会继承上层通用 Instruction，再由局部规则补充或覆盖。  
**例：** `子DirectoryはRootの共通Instructionを継承します。`  
**中文：** 子目录继承 Root 的通用 Instruction。  
**ニュアンス：** 既用于配置层级，也用于 OOP。

### 6. 優先する（ゆうせんする）
**品詞：** 動詞・サ変｜**意味：** 优先、优先考虑｜**目安：N3**  
**コロケーション：** 安全性を優先する / 近いRuleを優先する / 優先して処理する  
**文脈：** AGENTS.md 存在多层规则时，需要明确哪一级 Instruction 优先。  
**例：** `よりTaskに近いDirectoryのRuleを優先します。`  
**中文：** 优先采用更接近任务目录的规则。  
**ニュアンス：** 用于明确 precedence，比单纯「先にする」正式。

### 7. 適用する（てきようする）
**品詞：** 動詞・サ変｜**意味：** 适用、应用｜**目安：N2**  
**コロケーション：** Ruleを適用する / 設定を適用する / Patchを適用する

**例：** `Fileの位置に応じて適切なInstructionを適用します。`  
**中文：** 根据文件位置应用合适的 Instruction。  
**ニュアンス：** 「導入する」偏引入机制，「適用する」偏把已有规则用于对象。

### 8. 検証する（けんしょうする）
**品詞：** 動詞・サ変｜**意味：** 验证、检验｜**目安：N2**  
**コロケーション：** 変更を検証する / 結果を検証する / 自動的に検証する  
**文脈：** AI Coding 的不确定输出需要由 Test、Lint、Type Check 建立确定性边界。  
**例：** `Agentが生成したCodeをType CheckとTestで検証します。`  
**中文：** 通过 Type Check 和测试验证 Agent 生成代码。  
**ニュアンス：** 比「確認する」更强调可重复证据。

### 9. 実行する（じっこうする）
**品詞：** 動詞・サ変｜**意味：** 执行｜**目安：N2**  
**コロケーション：** Testを実行する / Commandを実行する / 並行して実行する

**例：** `独立したValidationを複数Sessionで並行して実行します。`  
**中文：** 在多个 Session 中并行执行独立的 Validation。  
**ニュアンス：** 程序和命令语境比「実施する」更自然。

### 10. 分離する（ぶんりする）
**品詞：** 動詞・サ変｜**意味：** 分离｜**目安：N2**  
**コロケーション：** Contextを分離する / 責務を分離する / 環境を分離する

**例：** `SessionごとにContextと作業Directoryを分離します。`  
**中文：** 按 Session 分离 Context 和工作目录。  
**ニュアンス：** 强调结构上独立开来。

### 11. 明示する（めいじする）
**品詞：** 動詞・サ変｜**意味：** 明确写出、明示｜**目安：N1**  
**コロケーション：** 条件を明示する / 禁止事項を明示する / 責任を明示する

**中文：** 在 AGENTS.md 中明确写出验证命令和禁止事项。  
**ニュアンス：** 比「書く」更强调清楚、无歧义地呈现。

### 12. 追跡する（ついせきする）
**品詞：** 動詞・サ変｜**意味：** 追踪、跟踪｜**目安：N1**  
**コロケーション：** 変更を追跡する / Sessionを追跡する / 履歴を追跡する

**例：** `AgentごとのCommitとValidation結果を追跡します。`  
**中文：** 追踪每个 Agent 的 Commit 和 Validation 结果。  
**ニュアンス：** 强调沿时间或链路持续跟踪。

### 13. 防ぐ（ふせぐ）

## C-2. IT/AI専門語彙

### 1. AGENTS.md｜AGENTS.md
**意味：** 给 Coding Agent 的仓库级说明文件  
**文脈：** 用于定义代码风格、命令、验证方式和目录级规则。

### 2. Context Scoping｜コンテキスト範囲制御
**意味：** 上下文范围控制  
**文脈：** 只向 Agent 提供完成当前任务所需的文件与说明。

### 3. Automated Validation｜自動検証
**意味：** 自动验证  
**文脈：** 通过 Test、Lint、Type Check、Schema Check 等机器规则确认结果。

### 4. Guardrail｜ガードレール
**意味：** 安全护栏  
**文脈：** 在 Agent 执行前后限制危险操作或不合规输出。

### 5. Parallel Session｜並行Session
**意味：** 并行会话  
**文脈：** 多个 Agent Session 同时处理独立任务，提高吞吐量。

### 6. Monorepo｜モノレポ
**意味：** 单体代码仓库  
**文脈：** 多个 Package/Service 共存在一个 Repository，需要清晰的规则作用域。

### 7. Deterministic Check｜決定論的チェック
**意味：** 确定性检查  
**文脈：** 用可重复的编译、测试和规则检查弥补 LLM 输出的不确定性。

### 8. Scoped Instruction｜スコープ付き指示
**意味：** 限定作用域的指令  
**文脈：** 让特定目录或模块使用自己的 Agent Rule，同时继承全局规则。

## C-3. JLPT文法

### 1. ～にとどまらず
**Level：N1｜意味：** 不仅限于……  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 说明 AGENTS.md 不只定义 Coding Style，也包含验证、命令与安全规则。  
**例：** `AGENTS.mdはCoding Styleにとどまらず、Validationや禁止事項まで定義できます。`  
**補足：** 适合范围扩展。

### 2. ～かねない
**Level：N1｜意味：** 有可能导致不良结果  
**形：** `動詞ます形去ます + かねない`  
**使い方：** 警示多个 Agent 共享同一 Working Tree 可能造成冲突。  
**例：** `複数Agentが同じFileを同時に変更すると、大きな競合を招きかねません。`  
**補足：** 通常用于负面风险。

### 3. ～なくしては
**Level：N1｜意味：** 没有……就无法……  
**形：** `名詞 + なくしては`  
**使い方：** 强调自动验证是 AI Coding 进入生产开发的重要前提。  
**例：** `DeterministicなValidationなくしては、AI Codingの品質を安定させるのは難しいです。`  
**補足：** 语气较强，适合强调必要前提。

### 4. ～に応じて
**Level：N2｜意味：** 根据……相应调整  
**形：** `名詞 + に応じて`  
**使い方：** 说明按目录、任务和风险应用不同 Instruction。  
**例：** `Directoryに応じて適用するInstructionを切り替えます。`  
**補足：** 强调条件和对应措施。

### 5. ～一方で
**Level：N2｜意味：** 另一方面……  
**形：** `普通形 + 一方で`  
**使い方：** 说明 Parallel Session 的速度收益与协调成本。  
**例：** `並行Sessionは開発を高速化できる一方で、競合管理が複雑になります。`  
**補足：** 适合说明 Trade-off。

### 6. ～たうえで
**Level：N2｜意味：** 在……之后、在……基础上  
**形：** `動詞た形 + 上で`  
**使い方：** 先通过 Test / Type Check，再决定是否接受 Agent 修改。  
**例：** `自動Validationを通したうえで、Agentの変更をMergeします。`  
**補足：** 强调前一步是后续判断依据。

### 7. ～に基づいて
**Level：N2｜意味：** 基于……  
**形：** `名詞 + に基づいて`  
**使い方：** 说明 Agent 行为依据 Repository Rule 与 Guardrail。  
**例：** `RepositoryのRuleに基づいてAgentのCommand実行を制御します。`  
**補足：** 明确表示依据。
