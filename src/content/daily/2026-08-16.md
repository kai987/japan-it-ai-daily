## 4. 今日の技術テーマ

# Agent Context Scoping

Context Scoping 的目标是控制“当前任务到底需要哪些规则”。分层 Context 可以降低 Token 消耗和规则冲突，也让团队规范跟随目录结构管理。局限是父子规则仍可能冲突，规则文件也会过时，因此应把 AGENTS.md 当作 Repository 工程规范的一部分纳入 Review。

```text
Repository Rule
  ↓
Directory Scope
  ↓
Task Context
  ↓
Agent Execution
  ↓
Review / Update
```

### 优点

**第一，减少无关复杂度。** 通过把职责拆成 `Repository Rule` 到 `Review / Update` 的明确层次，可以让模型只处理概率性判断，而把权限、验证和停止条件交给确定性系统。

**第二，更容易测量与回滚。** 每一层都能单独记录 Input / Output / Cost / Failure，出现异常时可以定位问题，而不是把所有错误都归因于“模型不够好”。

**第三，更适合团队规模化。** Context 设计需要同时管理相关性、访问范围、Token 成本与检索遗漏，并用真实任务做评价，因此可以把个人技巧转成可复用的 Platform Rule、CI Check 或 Governance Policy。

### 局限

**系统复杂度会上升。** 多一层 Router、Policy、Sandbox、Trace 或 Evaluation 都会带来开发和维护成本，需要确认它解决的是实际风险，而不是为了“架构完整”而堆层。

**确定性 Guardrail 也可能配置错误。** Policy、Test、Metric 与 Retrieval Rule 都需要版本管理和持续校准，不能因为“不是 LLM”就默认它绝对正确。

### 日本企业落地时的注意点

1. 先明确 **Owner、Data Boundary、Permission、Approval、Audit、Rollback**，再扩大 Agent 自治范围。  
2. 把现有的 **CI/CD、SRE、Security Review、Change Management** 继续保留，不因为接入 AI 就另建一套不可追踪的旁路。  
3. 用日本企业实际关心的 **品質、工数、Cost、Security Incident、Business Outcome** 评价，而不是只统计 AI 使用次数。

面试里可以这样总结：

> 必要な情報だけを渡すScope設計とAccess Controlを分けて考え、検索漏れ、Context Cost、回答品質を実Workloadで評価します。

3. **生产化要点：** 模型选择不能只看 Benchmark，应共同衡量任务成功率、延迟、成本与失败率。
4. **面试表达：** 说明技术价值时，同时给出适用条件、Trade-off 与验证方法，比只介绍“能做什么”更完整。

### 日本語の知識ポイント

1. **Coding Modelでは、短いCode Generationだけでなく、Long-horizon TaskやTerminal操作まで評価する必要があります。**
2. **Benchmarkだけで決めず、Task Quality、Latency、Cost、Failure Rateを同じ評価セットで比較し、必要なら弱いModelから強いModelへ段階的に切り替えます。**
3. **導入判断では、適用条件とTrade-offを明確にし、実際のWorkloadで評価することが重要です。**
4. **本番運用では、変更履歴、監査性、Rollback手段まで含めて設計する必要があります。**

### 1. 範囲（はんい）
**词性：** 名詞

**细微区别：** 技术说明中常与「限定・絞る・広げる」搭配。

**例句：** `複数Agentの変更競合を減らすため、Working Treeを分けます。`  
**中文：** 为了减少多个 Agent 的修改冲突，分开 Working Tree。  
**细微区别：** 软件语境常对应 conflict；商业语境也可表示竞争。

### 3. 整合（せいごう）

**中文：** 通过测试确认生成代码是否与现有 Schema 一致。  
**细微区别：** 「整合性」常对应 consistency / integrity。

### 4. 保証（ほしょう）
**词性：** 名詞

**例句：** `自動Testだけで完全な品質を保証できるとは限りません。`  
**中文：** 仅靠自动测试未必能保证完整质量。  
**细微区别：** 工程语境应避免无依据的绝对保证。

### 5. 継承（けいしょう）
**词性：** 名詞  
**中文：** 继承

**中文：** 子目录继承 Root 的通用 Instruction。  
**细微区别：** 既用于配置层级，也用于 OOP。

### 6. 優先する（ゆうせんする）
**词性：** 動詞・サ変

**中文：** 优先采用更接近任务目录的规则。  
**细微区别：** 用于明确 precedence，比单纯「先にする」正式。

## C-3. JLPT语法

### 1. ～にとどまらず
**参考：N1**  
**中文：** 不仅限于……  
**接续：** `名詞 / 普通形 + にとどまらず`  
**使用场景：** 说明 AGENTS.md 不只定义 Coding Style，也包含验证、命令与安全规则。  
**例句：** `AGENTS.mdはCoding Styleにとどまらず、Validationや禁止事項まで定義できます。`  
**中文：** AGENTS.md 不仅限于 Coding Style，也可定义 Validation 和禁止事项。  
**注意：** 适合范围扩展。

### 2. ～かねない
**参考：N1**  
**中文：** 有可能导致不良结果  
**接续：** `動詞ます形去ます + かねない`  
**使用场景：** 警示多个 Agent 共享同一 Working Tree 可能造成冲突。  
**例句：** `複数Agentが同じFileを同時に変更すると、大きな競合を招きかねません。`  
**中文：** 多个 Agent 同时修改同一文件可能造成严重冲突。  
**注意：** 通常用于负面风险。

### 3. ～なくしては
**参考：N1**  
**中文：** 没有……就无法……  
**接续：** `名詞 + なくしては`  
**使用场景：** 强调自动验证是 AI Coding 进入生产开发的重要前提。  
**例句：** `DeterministicなValidationなくしては、AI Codingの品質を安定させるのは難しいです。`  
**中文：** 没有确定性 Validation，就很难稳定 AI Coding 质量。  
**注意：** 语气较强，适合强调必要前提。

### 4. ～に応じて
**参考：N2**  
**中文：** 根据……相应调整  
**接续：** `名詞 + に応じて`  
**使用场景：** 说明按目录、任务和风险应用不同 Instruction。  
**例句：** `Directoryに応じて適用するInstructionを切り替えます。`  
**中文：** 根据目录切换适用的 Instruction。  
**注意：** 强调条件和对应措施。

### 5. ～一方で
**参考：N2**  
**中文：** 另一方面……  
**接续：** `普通形 + 一方で`  
**使用场景：** 说明 Parallel Session 的速度收益与协调成本。  
**例句：** `並行Sessionは開発を高速化できる一方で、競合管理が複雑になります。`  
**中文：** 并行 Session 能加快开发，但冲突管理会更复杂。  
**注意：** 适合说明 Trade-off。

### 6. ～たうえで
**参考：N2**  
**中文：** 在……之后、在……基础上  
**接续：** `動詞た形 + 上で`  
**使用场景：** 先通过 Test / Type Check，再决定是否接受 Agent 修改。  
**例句：** `自動Validationを通したうえで、Agentの変更をMergeします。`  
**中文：** 通过自动 Validation 后再合并 Agent 修改。  
**注意：** 强调前一步是后续判断依据。

### 7. ～に基づいて
**参考：N2**  
**中文：** 基于……  
**接续：** `名詞 + に基づいて`  
**使用场景：** 说明 Agent 行为依据 Repository Rule 与 Guardrail。  
**例句：** `RepositoryのRuleに基づいてAgentのCommand実行を制御します。`  
**中文：** 根据仓库规则控制 Agent 的命令执行。  
**注意：** 明确表示依据。
