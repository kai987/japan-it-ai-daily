# A. 详细文字版

从工事概算、外部AI误传、修复验证、开发工具更新和数据库会话权限，检查哪些工作交给AI、哪些规则必须由系统执行。

## 1. 今日最值得看的 5 篇

### ① 関電工が“AIありき”から脱却し、「1～2週間→数十分」に工事費計算を高速化　その方法は？：PoCを2回実施しても成果を得られず、発想を転換

**来源：＠IT**

**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2609/04/news038.html

关电工的设备工事概算依赖人工和熟练员工，提交报价原需一至两周，退休也带来知识流失风险。两次与 AI 服务商进行 PoC 后未达预期，ULS 分析现存数据，判断当前条件不适合把准确积算整体交给 AI。

最终把相似历史项目调用与各工事项金额计算交给确定性逻辑；AI 负责自然语言信息抽取、客户间术语和表单格式差异。不能把原文的相似案例调用改写成全由 AI 检索。系统同时继续整理未来 AI 积算需要的数据，以当前可验证的能力先解决业务问题。

开发先用原型对齐操作和精度认识，再结合 IT、积算、研究、销售等部门反馈，历时约一年半。发布方称完成系统中80～90%的算出方法沿袭传统逻辑，概算工作降到数十分钟，案例于7月30日公布。

限制是80～90%描述方法构成，不是准确率或 AI 自动化率；原文没有误差分布、样本数及例外处理工时，也不能保证所有报价整体都只需数十分钟。面试可解释抽取与计算分工，并用已知案例核对数值、规则和差额。

**关注点：★★★★★**

能具体说明AI与确定性程序各负责什么。

### ② RIZAP社員、私用AIに顧客の個人情報入力　氏名や疾患、保険証番号など……同社が謝罪

**来源：ITmedia NEWS**

**原文：** https://www.itmedia.co.jp/news/article/2609/04/2000001161/

ITmedia 9月4日报道 RIZAP 员工在集计时把特定保健指导客户资料误传给个人使用的外部 AI。数据来自1月1日至8月19日登记资料的一部分，包含姓名、出生日期、保险编号、联系方式及部分疾病信息；该时间段是资料登记范围，不是持续上传时长。数量及 AI 服务名并未公开。

当事人随后删去聊天并关闭训练利用。RIZAP 说经向服务商照会，含可识别个人信息的文件及24小时内删除的文件不用于训练，因此判断本次不会进入模型训练或经相关提问输出。这是公司基于个别答复的判断，不能扩展成所有 AI 产品的普遍条款。

限制是服务商员工是否可能阅览仍在核实。未训练、未保留、不可人工阅览是三个问题，不能相互替代。报道说已向个人信息保护委员会报告，通知受影响对象则仍需与数据提供方协调。

再发防止包括重申未批准 AI 禁止用于业务与持续培训，AIMS 是考虑导入而非已认证。面试可区分发送路径、数据选择、使用记录，以及事故后的保存、人工访问和删除确认；不能将阶段公告写成调查已完成或风险归零。

**关注点：★★★★★**

区分训练、保存与人工访问三类事实。

### ③ AI攻撃の脅威は「これから数カ月」で変わる　OpenAIらが共同声明：残された時間はわずか？

**来源：＠IT**

**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2609/04/news027.html

[8月27日公开信](https://openai.com/collective-cyberdefense/)呼吁多方强化网络防御，特别支持医院、水处理等重要基础设施。未来数月攻击扩大和复杂化是签署方判断，而非已观测到的未来攻击统计。

重点包括旧漏洞、过大权限、误配置、弱认证及未更新软件。修复高风险问题后要核实效果，并提高采购、开发和部署的安全标准，AI 生成代码同样接受检查。对无法停机打补丁的系统，应应用并验证补偿性控制，不能把“无法修补”当没有任何行动空间。

原文还提出低成本模型负责广覆盖，前沿模型解决难题，并分别安排企业、技术供应商、政府及 AI 公司在投入、支持、授权测试和成果共享中的职责。衡量应包括覆盖组织、封堵时间与修复是否有效，而非只数修复次数。

＠IT 将公开信与七月 Hugging Face 事件后的 OpenAI 环境隔离、联网、模型权重权限及推理监控措施联系起来。限制是另一事件报告中的应对，不等于签署公开信就已完成控制。面试可把修复交付与不影响核心业务的效果复验共同纳入流程。

**关注点：★★★★★**

可解释“已部署补丁”和“漏洞已被阻断”的差别。

### ④ Claude Code v2.1.259〜v2.1.260 の主要アップデート - 差分パネルの追加と権限ルールのセキュリティ修正

**来源：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/20260904-cc-updates-v2-1-260/

Claude Code2.1.259～260 的103项变更是作者整理数量，并非103项实测。实际演示为 fullscreen `/diff`：练习仓库编辑两个文件，确认未修改测试文件不出现、后续编辑实时更新、再次输入可关闭；需至少110列，作者使用144列。

`--permission-prompts none` 在无人值守时拒绝需要确认的动作，仍保留当前权限模式判断，不能理解为自动批准。无法解析管理配置时拒绝启动，同样是避免带着失效控制继续运行。`managedMcpServers` 面向 HTTP/SSE，指定本地 command 的条目会被跳过。

必须保留版本顺序：259将 Read 拒绝规则扩到 Bash 参数，260因误拦正常 build 等回退该改动，因此不能宣传260仍具该覆盖。括号路径规则、非法 pattern 与 zsh 特殊赋值的检查修复是其他独立事项。这里对照了[官方两版记录](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)。

迁移时 `allowedMcpServers` 仅约束用户新增服务器，原被过滤的管理服务器可能重新载入，继续禁用应使用 `deniedMcpServers`。人从 `!` 输入的命令改在沙箱外运行，不代表代理命令全部出沙箱。另修复备份不存在却声称 rewind 成功、多会话覆盖配置、系统证书库企业 CA 下 Bedrock 失败等。

cache miss 提示及 Fable 工具结果上下文缓存修复属于功能变化，正文没有总账单测量。限制是更新记录与局部 UI 演示；面试可从错误管理配置是否停止、正常与拒绝用例回归、恢复后文件是否正确三个角度验证，不能把差分可见当成变更安全证明。

**关注点：★★★★★**

用实际参数说明无人执行拒绝与版本回退。

### ⑤ [新機能]Snowflake の Restricted Session Scope が一般提供になったので CoCo 利用時だけ実効権限を狭めてみた

**来源：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/snowflake-restricted-session-scope-coco-permission-limit/

RSS 在不修改 RBAC 的情况下，对 agent-active 会话附加权限上限，最终操作必须同时被 RBAC 与 RSS 允许。`privilege_scopes` 描述动作及数据库范围，`role_scopes` 控制角色与切换，通过 session policy 的 `AGENT_RESTRICTED_SESSION_SCOPE` 应用。GA 指管理员策略机制，CLI/Desktop 用户自行管理仍是 private preview。

作者在 Enterprise、AWS 东京建立测试库和20条虚构资料，仅向自己用户附加策略。CoCo 与 worksheet 使用同用户、默认角色、warehouse及相同 SQL，并清空 secondary roles。无 RSS 时七条均成功；添加后代理对生产模拟库 INSERT、DDL 被拒，sandbox INSERT 和 program usage 成功，worksheet 则仍按原 RBAC 成功。

`data write` 不含 DDL：加上 sandbox 的 `object management` 并开启新会话后，只有 sandbox 建表改为成功。禁止角色切换后，即使在 CoCo 确认框点 Allow，切主角色及开启副角色仍被底层拒绝，当前角色未变。角色阻断按名称匹配，不会回收现有主角色已经继承的权限。

三个预设 scope 的 SELECT、SHOW 均成功，INSERT 均拒；仅 PROGRAM_USAGE 可调用 UDF/procedure。WITH_AI 的 UDF 文档正文与 YAML 有分歧，本文环境实际拒绝。DDL 因同名表已存在失败，作者明确不把它当权限测试结论；另将邮箱 masking 与 RSS 叠加，验证“触及范围”与“可见值”两层控制。

限制包括活动会话内不能放宽 RSS，变更需新会话；用户策略不与账号策略合并，但优先级未在共享账号实测。`ADD AS` 的实际语法差异、非代理查询 scope 状态报错、个人库不能建表都被保留。其他客户端、个人库写入、性能和费用未测。

本次核对的[官方文档](https://docs.snowflake.com/en/user-guide/restricted-session-scope)还说明 PROGRAM_USAGE 可调用 owner 权限过程，其内部写操作不自动受直接只读限制。作者只测 caller 权限的简单返回过程，因此不能保留“允许程序后所有路径仍只读”的保证。面试应把直接 SQL、程序内部权限和字段 masking 分别验证。

**关注点：★★★★★**

保留真实对照及DDL、角色继承、存储过程边界。

## 3. 面接で使えるポイント

### 話題1：Enterprise AI / Rule-based / Workflow Design

**面试问题：**

> AIの概念実証で成果が出ないとき、何を見直しますか。

**约 30 秒自然日语回答：**

> AIに向く部分を選び直します。関電工の積算では、用語や書式の違いはAIで扱い、類似案件の呼び出しと金額計算はロジックにしました。算出手法の八～九割が従来のルールで、概算を数十分へ短縮した事例です。ただし、この割合は精度ではありません。既存案件と比べ、抽出ミスと計算ミスを分けて確認し、現場の例外も改善へ戻します。

**関連Project（学習用）：** 抽取与概算分离练习

**キーワード：** `関電工` / `積算` / `情報抽出` / `決定的ロジック`

### 話題2：AI Governance / Privacy / Shadow AI

**面试问题：**

> AIサービスが学習に使わないなら、顧客データを送ってよいですか。

**约 30 秒自然日语回答：**

> 学習利用だけでは判断できません。RIZAPの事例では、削除したファイルは学習されないとしても、事業者の社員が閲覧できたかは確認中でした。保管、閲覧、学習は別の条件です。認めた送信先と項目を決め、私用AIへ送らない運用にします。誤送信時は、削除の表示だけで終えず、送信範囲と事業者側の扱いを確認します。

**関連Project（学習用）：** 许可集计路径设计

**キーワード：** `RIZAP` / `Shadow AI` / `学習利用` / `閲覧可能性`

### 話題3：AI Security / DevSecOps / Cyber Defense

**面试问题：**

> セキュリティ修正の完了を、どう判断しますか。

**约 30 秒自然日语回答：**

> 配備したことに加え、問題が再現しなくなったかを確認します。共同書簡は、修正できない重要システムにも代替防御を適用し、その効果を検証するよう求めています。ただし本来の業務を止めない条件も必要です。対象の弱点を再試験し、正常な処理も通るかを確かめます。AIの生成した修正でも同じ基準を使い、結果を共有し、次の対応を速くします。

**関連Project（学習用）：** 补丁后复验表

**キーワード：** `共同書簡` / `検証済み修正` / `代替防御` / `重要インフラ`

### 話題4：Claude Code / Security / Agent Runtime

**面试问题：**

> AIツールを無人実行へ組み込むとき、確認待ちをどう扱いますか。

**约 30 秒自然日语回答：**

> 確認が必要なら、勝手に進めず止めます。Claude Codeのpermission-prompts noneは、確認が必要な操作を拒否し、元の権限モードの判断は残します。管理設定を読めない場合も起動を拒否する修正が入りました。ただし更新では機能の取り消しもあります。正常な処理と拒否すべき操作を両方試し、設定が効かないまま続行しないことを確認します。

**関連Project（学習用）：** 无人执行拒绝测试

**キーワード：** `Claude Code` / `--permission-prompts none` / `管理設定` / `fail closed`

### 話題5：Snowflake / AI Agent / Least Privilege

**面试问题：**

> 人と同じDBロールを使うAIだけ、操作を制限できますか。

**约 30 秒自然日语回答：**

> SnowflakeのRSSなら、Agentの会話だけ権限の上限を追加できます。実験では同じ利用者とロールで、本番へのINSERTはCoCoで拒否され、ワークシートでは成功しました。RBACの権限が増えることはありません。ただしdata writeは建表を含まず、変更後は新しい会話が必要です。直接のSQLだけでなく、許可したプログラム内部の権限も見ます。

**関連Project（学習用）：** RSS与mask比较练习

**キーワード：** `RSS` / `RBAC` / `data write` / `object management`

## 4. 今日技术主题

例句和关联项目是围绕当天主题制作的学习材料，不是原文引文或已证实的企业案例。JLPT 等级为学习参考。

## C-1. JLPT語彙

### 1. 脱却する（だっきゃくする）
**品詞：** 名詞・サ変動詞｜**意味：** 摆脱、脱离｜**目安：N1**  
**コロケーション：** 発想から脱却する / 属人化から脱却する / 従来方式から脱却する / 依存から脱却する  
**文脈：** Top 1 标题直接描述关电工从“AIありき”的前提出发方式中脱离。  
**例：** `Model中心の発想から脱却し、業務Process全体を見直します。`  
**中文：** 摆脱以模型为中心的思路，重新审视整个业务流程。  
**ニュアンス：** 比「やめる」正式，常用于组织改革、旧做法和依赖关系的结构性改变。

### 2. 成果（せいか）
**品詞：** 名詞｜**意味：** 成果、产出｜**目安：N2**  
**コロケーション：** 成果を得る / 成果につなげる / 具体的な成果 / 業務上の成果

**ニュアンス：** 可正可负；Security 语境常表示攻击者最初可利用的入口。

### 4. 上限（じょうげん）

**ニュアンス：** 软件现场常表示状态回到旧版本；与 Rollback 语感接近。

### 6. 頼る（たよる）

### 8. 絞る（しぼる）

**中文：** Incident 后向 Provider 查询 Data Retention 的实际情况。

### 10. 怠る（おこたる）

**中文：** 如果疏忽修复后的回归测试，可能漏掉其他故障。

### 11. 促す（うながす）

## C-2. IT/AI専門語彙

### 1. Deterministic Logic｜決定論的ロジック
**意味：** 相同输入稳定得到相同结果的规则或程序逻辑。  
**文脈：** Top 1 用于金额计算、历史项目检索等规则清晰的步骤，与 LLM 自然语言处理分工。

### 2. Shadow AI｜シャドーAI
**意味：** 未经企业批准或未被治理系统掌握的员工 AI 使用。  
**文脈：** Top 2 的个人 AI 处理真实客户敏感数据就是典型治理风险。

### 3. AI Management System (AIMS)｜AIマネジメントシステム
**意味：** 对 AI 的风险、Policy、角色、过程与持续改善进行组织化管理的体系。  
**文脈：** RIZAP 表示考虑在 ISMS 之外导入 AIMS。

### 4. Verification Speed｜検証速度
**意味：** 修复或 AI 生成变更后，确认其真正有效、没有引入新风险的速度。  
**文脈：** Top 3 公开信强调 AI 时代 Fix Speed 与 Verification Speed 同样重要。

### 5. Fail Closed｜フェイルクローズ
**意味：** 无法获得必要确认或验证时默认拒绝，而不是继续执行。  
**文脈：** Claude Code `--permission-prompts none` 在 Headless 环境下自动拒绝需要确认的操作。

### 6. Managed MCP Server｜管理対象MCPサーバー
**意味：** 由组织通过 Managed Settings 统一下发与治理的 MCP Server。  
**文脈：** Claude Code v2.1.259 新增 `managedMcpServers`。

### 7. Restricted Session Scope (RSS)｜制限付きセッションスコープ
**意味：** 对 Snowflake Agent Session 额外施加的权限上限。  
**文脈：** Top 5 使 Agent 在 Production Read-only、Sandbox Write，而普通 Worksheet 仍保留原 RBAC。

### 8. Effective Permission｜実効権限
**意味：** 各层 Policy、RBAC、Session Restriction 叠加后实际能执行的权限集合。  
**文脈：** Snowflake 场景可理解为 Human RBAC 与 RSS 的交集。

## C-3. JLPT文法

### 1. ～にとどまらず
**Level：N1｜意味：** 不止于……、不仅限于……  
**形：** `名詞 + にとどまらず / 動詞辞書形 + にとどまらず`  
**使い方：** 用于说明 AI Security 不能只修漏洞，还要扩展到验证、权限和 Agent Control。  
**例：** `AI時代のSecurityは脆弱性を修正することにとどまらず、修正後の検証とAgentの行動監視まで必要です。`  
**補足：** 与 Top 3 的核心范围扩展一致。

### 2. ～かねない
**Level：N1｜意味：** 有可能导致……、恐怕会……  
**形：** `動詞ます形去ます + かねない`  
**使い方：** 用于 Security、Privacy、Permission 风险警示。  
**例：** `Private AIへ機密情報を入力すると、Data Governance上の重大Incidentにつながりかねません。`  
**補足：** 与 Top 2、Top 3 的风险语境严格对应。

### 3. ～に至るまで
**Level：N1｜意味：** 从……一直到……，甚至包括……  
**形：** `名詞 + に至るまで`  
**使い方：** 用于表示 Security Control 覆盖范围广。  
**例：** `AI Agentの運用では、PromptからNetwork Access、Database権限に至るまでControl Pointを整理します。`  
**補足：** 对应 Top 3～5 中多层控制范围。

### 4. ～に応じて
**Level：N2｜意味：** 根据……相应调整  
**形：** `名詞 + に応じて / 名詞 + に応じた + 名詞`  
**使い方：** 用于 AI / Rule 分工、权限 Scope 等动态选择。  
**例：** `処理の性質に応じて、LLMとRule-based Logicを使い分けます。`  
**補足：** 与 Top 1 的 Hybrid Design 高度对应。

### 5. ～たうえで
**Level：N2｜意味：** 在……之后、在……基础上  
**形：** `動詞た形 + 上で / 名詞 + の上で`  
**使い方：** 表示 Analysis / Verification 是后续决策前提。  
**例：** `既存Dataを分析したうえで、AIに任せる範囲を決めます。`  
**補足：** 对应 Top 1 的实际咨询与设计过程。

### 6. ～一方で
**Level：N2｜意味：** 另一方面……  
**形：** `普通形 + 一方で`  
**使い方：** 比较 AI 与 Deterministic Logic 的优势和限制。  
**例：** `LLMは自然言語処理に強い一方で、金額計算の再現性はRule-based Logicの方が確保しやすい場合があります。`  
**補足：** 适合 Top 1 的 Trade-off。

### 7. ～にかかわらず
**Level：N2｜意味：** 不论……、不管……  
**形：** `名詞 + にかかわらず`  
**使い方：** 表达某控制在其他条件下仍独立适用。  
**例：** `Human側のRoleが高権限であるかどうかにかかわらず、Agent SessionではRSSの上限を適用します。`  
**補足：** 与 Top 5 的 Agent-only Restriction 语境对应。
