# A. 详细文字版

今天涵盖 Teams 协作、DSpark 投机解码、故障调查起票、后台会话和建筑行业 AI 应用，分别核对请求与权限、速度与质量、采用与实际收益。

## 1. 今日最值得看的 5 篇

### ① GitHub Copilot Cloud Agent × Microsoft Teams

**来源：CodeZine**

**原文：** https://codezine.jp/news/detail/29421

CodeZine 报道 **GitHub Copilot cloud agent 与 Microsoft Teams** 于8月21日开放 Public Preview。在频道、线程或私信中提及 `@GitHub` 即可开始共同会话，参与者追加背景、提问和方向。目标是把会议行动项直接交给调查流程，减少会后再次转述。

参与讨论不代表有修改仓库的权力。对话成员可帮助规划，但触发代码变更需目标仓库写权限。任务在云沙箱异步运行，线程呈现进展，终端、IDE、Copilot 应用可继续使用成果，因此关闭聊天界面不等于终止后台执行。

条件包括付费 Copilot 套餐和 AI credits 消耗。官方进一步说明 sandbox 使用独立计费，组织需启用相应服务；还要安装 GitHub Teams 应用、连接账户，并在需要时设默认仓库。不能将聊天入口视为免配置或免费执行通道。

原新闻把额外批准写成必需，但官方表述是 **管理员可启用额外批准要求**；启用后例如通常两票变三票。因此不保留“全部接入自动增加审批”的无条件断言。这是产品发表，不是团队生产率或质量对照实验。

补充核验：[GitHub 官方发布](https://github.blog/changelog/2026-08-21-shared-agentic-work-with-github-copilot-in-microsoft-teams/)。面试可按讨论、执行修改、合并批准和费用分别设计责任边界。

**关注点：★★★★★**

区分共同讨论、变更执行权限和合并条件。

### ② Liquid AI DSpark：Speculative Decoding

**来源：CodeZine**

**原文：** https://codezine.jp/news/detail/29423

Liquid AI **DSpark** 为 LFM2.5-1.2B-Instruct、2.6B、8B-A1B 提供约3亿参数的草稿模型。小模型提出候选，目标模型单次前向批量验证，把内存带宽受限的权重读取摊到多个 token；它并不把最终答案直接交给弱模型。

一次发布说明三部分：目标特征条件化的并行 backbone、补充相邻依赖的 **Markov head**、按存活概率截去低收益后缀的 confidence verifier。初版为5层纯 attention、block9，训练15个 epoch 后按最高接受率选取。在 greedy 条件下不接受的候选改用目标 token，因此输出与目标独立 greedy 一致；不能不注明采样条件就扩张此保证。

厂商测试固定 batch1、temperature0、五组基准。GPU 为 H10080GB/BF16/SGLang，端侧为 M4 Max/FP16 GGUF/llama.cpp Metal，最大输出256 token。**3.18倍**来自8B-A1B在H100的MATH500，端侧**2.87倍**来自1.2B的HumanEval，并非同一次比较。2.6B平均GPU2.67倍、端侧2.27倍，函数调用延迟平均降低57%也限定该模型的厂商评估。

8B-A1B接受率较高，端侧平均仍只有1.18倍；同时验证多个候选激活更多专家与权重传输，当时 Metal MoE 实现限制收益。还要为草稿模型增加内存，不能把最大值套给所有设备与输入。

权重以 safetensors、GGUF 公开，执行需要含 LFM2 DSpark 支持的对应 SGLang 或 llama.cpp build。首日提供集成不代表任意旧安装都兼容。面试可分别验证接受率、额外内存、greedy 输出一致和真实函数调用延迟。

条件补充：[Liquid AI 原始发布](https://huggingface.co/blog/LiquidAI/lfm25-dspark)。

**关注点：★★★★★**

具体解释投机解码的质量条件及不同硬件的性能差异。

### ③ AWS DevOps Agent × GitHub MCP：障害調査後はIssue作成だけを許可

**来源：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/aws-devops-agent-github-issue/

AWS DevOps Agent 实验目标是调查后**只创建 GitHub Issue**。当时原生 GitHub 集成提供14个只读工具，因此另接官方 remote MCP，实际枚举后仅开放 `issue_write`、`list_issues`、`search_issues`，排除可让 Copilot 开始编码或创建 PR 的工具；不能猜一个 create_issue 名称就使用。

权限有两关：Agent Association 允许工具，以及 GitHub App 具备 **Issues: Read and write**。作者先只做前者而遇403，补齐 App 权限并在安装端批准才成功。OAuth3LO 下创建者显示用户，App 记录在 `performed_via_github_app`，不能单用 Bot 类型判断自动操作。

人工故障为 CDK 漏掉 `topic.grantPublish()`，Lambda 三次发 SNS 均返回 AuthorizationErrorException。聊天路径约3分钟建出含日志、两处代码和修复方案的 Issue。investigation 以六个角色查 Metrics、CloudTrail、IAM 等，约9分钟发现已有 Issue 而不重复创建。另一例10秒处理但3秒超时，约5分半创建新问题，分别覆盖重複存在与不存在。时间只是这些条件的观察结果。

Git 管理的 runbook 规定原因明确后搜索重复，填入日志、代码、修复方案与确认范围，再报告编号 URL。许可清单限制可执行能力，文档规定其内的流程；journal 也确认没有创建分支或写文件调用。它是“可做什么”和“怎么做”的组合，而非只在提示里说不要改代码。

不过代理自诊断两次错误：将起票403解释为 READ_ONLY，真实原因是 App 权限；将读取失败说成 SCP，CloudTrail 却显示 identity policy 缺少 Lambda 操作权限。CloudWatch Logs 可读，部分查询失败是时间超出日志创建/保留范围。根因结论正确不代表所有推理和展示 JSON 都正确，需要回到原始错误。

CDK 自动日志名还让探索28分钟未完成，改为 `/aws/lambda/<函数名>` 后约3分钟走通；无法改名时可在 skill 中说明规则。限制是少量人工故障，不能保证所有事故的调查效率。面试价值在于双层权限、重复控制和原始日志校验。

**关注点：★★★★★**

区分工具许可和目标授权、代理解释和真实错误。

### ④ Claude Code Supervisor：SessionとCLI Processを分離

**来源：Zenn**

**原文：** https://zenn.dev/uehaj/articles/claude-code-supervisor-agent-view

这篇 Zenn 文章把 Claude Code 的 **supervisor daemon、Agent view** 放在终端、会话、进程三个层次解释。普通前台随终端结束，之后从历史 resume；经过 `/bg` 或 `claude --bg` 托管的独立会话则由 `claude daemon run` 管理。不能说任意 CLI 窗口直接关闭都持续工作。

daemon 按用户需要启动，**`roster.json`** 分别记录 sessionId、pid 与连接 socket，Agent view 可 attach、peek、停止。任务完成与进程活着是两套状态；回收进程后仍能从 transcript 重启。跨睡眠和更新保留的是继续/恢复能力，不代表机器睡眠时依然执行计算。

空输入时左箭头可能将当前会话整体移入后台，并非只切换列表；作者在v2.1.223确认可关闭 `leftArrowOpensAgents`。`/bg` 移走当前会话，`/fork` 将副本后台并行而人留在原会话，`/branch` 转到副本继续单线执行。会话内部 Bash 或子代理后台任务又是另一层。

独立会话成果不会像子代理那样自动交回父会话。Git 可在写入时用 worktree 隔离并通过分支/PR回收，非Git同目录没有此隔离。清理保护有未提交或未push工作仍不等于无需查收。跨会话消息提供发现与收发，不自动包含 Agent Teams 任务分配或 Dynamic Workflows 确定性编排。

作者用 status、台账和日志观察预热worker、按需启动及更新自重启。环境变量有 daemon 初启继承和每次 dispatch 刷新 PATH/提供方等两层；老 HTTP_PROXY 可能让新终端正常、后台却不通。排查应追踪值由哪个长寿命进程保存，而不是只检查当前 shell。

`/goal`、`/loop`、Stop hook 控制下一轮和停止条件，后台托管解决终端独立，Routines 另解决云端执行。限制是指定版本文档与个人观察，不能保证全部 OS 或未来版。面试可据此说明数据持久性、执行寿命、工作区隔离及成果回收的区别。

**关注点：★★★★★**

区分终端断开、进程结束和会话数据持久化。

### ⑤ 建設業界でAI活用が深化：ボトルネックは人材・Expert・ROIへ

**来源：＠IT**

**原文：** https://atmarkit.itmedia.co.jp/ait/articles/2608/25/news041.html

＠IT 引述建筑 AI 经营研究会调查，部门以上使用的 **Level2+ 从3月43.4%、6月61.3%升至8月68.5%**，Level4从3.8%到9.3%，平均层级1.57、1.84、2.02。但三次有效样本分别53、31、54名经营者，原文未证明同企业固定追踪，不能将其当成全建筑行业精确采用率。

公司付费 Claude 比例18.9%→71.0%→70.4%；8月 Claude Code57.4%、NotebookLM53.7%、Codex25.9%。购买不等于高频使用，更不说明某产品贡献相同比例业绩。Level4中“用自家数据学习”的分类，也无法确认所有企业都采用同一种 fine-tuning 架构。

初期“不知道先做什么”由50.9%减到31.5%，人才不足7.5%增至20.4%，专家伙伴不足11.3%增至27.8%。它提示关注组织支持，却不是同样本随机实验，不能推断工具导入直接导致人才问题。

感到 AI 已改变业绩的比例9.4%→19.4%→25.9%；按时间工数掌握效果15.1%升至24.1%，因尚无效果而不能把握47.2%降至20.4%。使用业务数字衡量与确认利润 ROI 并非同一指标。87.0%愿意参加行业服务监测，也由29.6%积极与57.4%视内容而定构成，是意向而非实际采用。

面试可说明部署阶段改变后，需重新安排人才、咨询与效果测量。具体选取估算、设计等业务，核对节时、返工和负责人支持，同时保留小型经营者调查与自家情况之间的边界。

**关注点：★★★★★**

区分付费采用、使用层级、业绩体感与量化测量。

## 3. 面接で使えるポイント

### 話題1：Team Agent / Governance

**面试问题：**

> TeamsからAIに開発を依頼する場合、権限をどう分けますか。

**约 30 秒自然日语回答：**

> 会話への参加と、変更を実行させる権限を分けます。TeamsのGitHub Copilotでは、参加者が背景を追加できても、コード変更にはリポジトリの書き込み権限が必要です。Public Previewで、AIクレジットとサンドボックスの費用も別です。追加承認は管理者が有効にする設定なので、自社のマージ条件と利用の上限まで確認して導入します。

**関連Project（学習用）：** 区分会议请求和修改权限的协作开发

**キーワード：** `Teams` / `GitHub Copilot` / `Public Preview`

### 話題2：LLM Inference

**面试问题：**

> 投機的デコードの速度向上を、どう評価しますか。

**约 30 秒自然日语回答：**

> ドラフトの採択率と、検証の追加負荷を見ます。DSparkはMarkov headで候補間の依存を補い、対象モデルがまとめて検証します。ただし最大3.18倍はH100での特定条件で、MoEの端末平均は1.18倍でした。greedy出力の一致を確かめたうえで、自社の入力分布、追加メモリ、関数呼び出しの待ち時間を測ります。

**関連Project（学習用）：** 验证 greedy 一致及接受率的推理实验

**キーワード：** `DSpark` / `Markov head` / `H100` / `MoE`

### 話題3：AIOps / Least Privilege

**面试问题：**

> 障害調査エージェントに起票だけを任せるには、どう設計しますか。

**约 30 秒自然日语回答：**

> 起票と重複確認に必要なツールだけを渡します。AWS DevOps Agentの例はissue_writeと検索を許可しますが、GitHub AppにもIssuesの書き込み権限が必要でした。ただし、403をREAD_ONLYとする自己診断は誤りで、実際のAPIエラーから切り分けています。ランブックで既存Issueを探し、根拠ログとコードを残して、修正の判断は人へ返します。

**関連Project（学習用）：** 只记录证据型 Issue 的故障处理练习

**キーワード：** `issue_write` / `GitHub App` / `READ_ONLY` / `403`

### 話題4：Long-running Agent Runtime

**面试问题：**

> ターミナルを閉じてもAI作業を続ける仕組みを、どう説明しますか。

**约 30 秒自然日语回答：**

> 端末とセッションの寿命を分ける仕組みです。Claude Codeではbgでセッションをsupervisorへ預け、roster.jsonが会話のIDと実行プロセスを管理します。ただし通常の対話セッションを閉じるだけでは同じになりません。非Gitの作業場所では隔離もないため、実行が続くかだけでなく、プロセスの状態、変更の衝突と成果の回収方法も確認します。

**関連Project（学習用）：** 管理后台状态及成果查收的任务流程

**キーワード：** `supervisor` / `roster.json` / `bg`

### 話題5：Enterprise AI / Adoption

**面试问题：**

> AI導入が進んだ組織で、次に何を支援しますか。

**约 30 秒自然日语回答：**

> 利用者を増やすだけでなく、人材育成と効果の測定を支えます。建築業の調査ではLevel2以上が68.5%となる一方、人材や相談先の不足が増えています。ただし三回の回答数は53人、31人、54人と違い、業界全体の変化とは断定できません。自社では対象業務を決め、相談経路と時間短縮、手戻りを継続して確認します。

**関連Project（学習用）：** 测量建筑业务工时和培养支持的采用计划

**キーワード：** `Level2` / `68.5%` / `建築業`

## 4. 今日技术主题

**明确执行范围，以及由谁验收成果。**

`请求 → 权限与输入条件 → 执行 → 核对证据 → 回收成果`

会议参与者不必然可改代码，起票有两层授权，后台任务也需查收。把确认责任放在自动化前后，才能判断流程是否真正完成。

## 5. 面试复习卡

### Q1

> Teamsの追加承認は、すべての環境で自動的に増えますか。

**回答ポイント：** 公式では管理者が有効にできる設定です。通常の承認条件と合わせて確認します。

### Q2

> DSparkの採択率が高ければ、端末でも最大倍率が出ますか。

**回答ポイント：** MoEのexpertと重み転送の負荷もあります。機器と入力条件を固定して測ります。

### Q3

> エージェントの根因が正しければ、途中の拒否理由も信用できますか。

**回答ポイント：** GitHubの403やCloudTrailの実エラーで確認します。正しい結論にも誤った説明が混じります。

# B. 重点知识与面试应用

## 1. GitHub Copilot Cloud Agent × Microsoft Teams

1. 能参与对话不等于能触发代码修改。
2. sandbox 另行计费。
3. 额外批准以管理员启用为条件。

## 2. Liquid AI DSpark：Speculative Decoding

1. 质量取决于目标模型的验证。
2. 高接受率仍可能受权重传输成本限制。
3. 最大值与各模型平均值应分开。

## 3. AWS DevOps Agent × GitHub MCP：障害調査後はIssue作成だけを許可

1. 工具可见和 API 授权是两个条件。
2. 根因正确也可能夹带错误诊断说明。
3. 重复存在与不存在的流程均需验证。

## 4. Claude Code Supervisor：SessionとCLI Processを分離

1. 会话状态和进程生死不同。
2. 内部后台任务与整会话托管不同。
3. 通信不等于自动分配和汇总任务。

## 5. 建設業界でAI活用が深化：ボトルネックは人材・Expert・ROIへ

1. 三轮样本数量不同。
2. 付费采用不能当作使用率或 ROI。
3. 参与意向与已取得成效不同。

# C. 日本語学习｜JLPT + IT日本語

例句和关联项目是围绕当天主题制作的学习材料，不是原文引文或已证实的企业案例。JLPT 等级为学习参考。

## C-1. JLPT語彙

### 1. 境界（きょうかい）
**品詞：** 名詞｜**意味：** 边界｜**目安：N2**  
**コロケーション：** 権限境界 / 責任境界 / Security境界  
**文脈：** AIOps 自动操作必须明确哪些范围可自动执行、哪些必须人工批准。  
**例：** `自動復旧が許可される権限境界を明確にします。`  
**中文：** 明确允许自动恢复的权限边界。  
**ニュアンス：** 技术语境常对应 boundary。

### 2. 候補（こうほ）
**品詞：** 名詞｜**意味：** 候选｜**目安：N2**

## C-2. IT/AI専門語彙

### 1. Collaborative Agent Session｜共同エージェントセッション
**意味：** 共同 Agent 会话  
**文脈：** 多人在 Teams 同一会话中补充背景与方向；触发仓库修改仍需要写权限。

### 2. Speculative Decoding｜投機的Decoding
**意味：** 推测解码  
**文脈：** 由小模型先生成候选 Token，再由目标模型批量验证以降低延迟。

### 3. Draft Model｜Draft Model
**意味：** 草稿模型  
**文脈：** Speculative Decoding 中负责快速提出候选 Token 的较小模型。

### 4. AIOps｜AIOps
**意味：** AI 驱动 IT 运维  
**文脈：** 利用 AI 支持运维分析；本文验证故障调查与起票，没有证明自动恢复的效果。

### 5. Permission Boundary｜権限境界
**意味：** 权限边界  
**文脈：** 明确 Agent 可以自动执行和必须人工批准的操作范围。

### 6. Long-running Session｜長時間Session
**意味：** 长时间会话  
**文脈：** Agent 在小时甚至天级任务中保存 State、Context 和进度。

### 7. Checkpoint｜Checkpoint
**意味：** 模型检查点  
**文脈：** 保存模型权重与配置的快照；使用 DSpark 时仍需匹配目标模型及运行引擎。

### 8. AI ROI｜AI投資対効果
**意味：** AI 投资回报  
**文脈：** 综合比较 AI Cost 与节省工时、质量提升、收入或风险降低。

## C-3. JLPT文法

### 1. ～つつ
**Level：N1｜意味：** 一边……一边……  
**形：** `動詞ます形去ます + つつ`  
**使い方：** 说明保持质量的同时降低推理 Latency。  
**例：** `品質を維持しつつ、Speculative DecodingでLatencyを下げます。`  
**補足：** 比「ながら」更书面。

### 2. ～に伴って
**Level：N1｜意味：** 随着……、伴随……  
**形：** `名詞 + に伴って`  
**使い方：** 说明 AIOps 自动化范围扩大后权限治理要求同步增加。  
**例：** `AIOpsの自動化範囲拡大に伴って、権限境界の設計も重要になります。`  
**補足：** 正式报告常用。

### 3. ～にとどまらず
**Level：N1｜意味：** 不仅限于……  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 说明 AI ROI 不只看 Token Cost，还包括节省工时、质量与风险。  
**例：** `AI ROIはModel Costにとどまらず、工数削減や障害復旧時間まで評価します。`  
**補足：** 适合范围扩展。

### 4. ～に応じて
**Level：N2｜意味：** 根据……相应调整  
**形：** `名詞 + に応じて`  
**使い方：** 用于 Task 分配、Agent 选择和权限边界。  
**例：** `Taskの専門性に応じて担当Agentを割り当てます。`  
**補足：** Team Agent 高频。

### 5. ～た上で
**Level：N2｜意味：** 在……之后、在……基础上  
**形：** `動詞た形 + 上で`  
**使い方：** 先确认 Risk / Permission，再自动执行恢复。  
**例：** `Riskと権限を確認した上で、自動復旧を許可します。`  
**補足：** 强调前一步是决策依据。

### 6. ～一方で
**Level：N2｜意味：** 另一方面……  
**形：** `普通形 + 一方で`  
**使い方：** 说明自动化和速度收益与治理复杂度。  
**例：** `AIOpsは復旧を高速化できる一方で、誤操作Riskもあります。`  
**補足：** 适合 Trade-off。

### 7. ～にかかわらず
**Level：N2｜意味：** 不论……都……  
**形：** `名詞 + にかかわらず`  
**使い方：** 表达所有 Agent / Session 都应遵守 Audit 和 Identity Rule。  
**例：** `Taskの長さにかかわらず、Agentの実行履歴を保存します。`  
**補足：** 适合统一规则。
