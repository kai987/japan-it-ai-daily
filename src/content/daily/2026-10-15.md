### 1. Claude Code on Bedrock：账号级护栏如何阻止输入侧提示词攻击

**原文：** https://dev.classmethod.jp/articles/claude-code-bedrock-account-level-guardrail-prompt-attack/

**发布时间：** 2026-10-15 00:51:17 JST

同样配置了 Bedrock Guardrails，调用入口不同，实际检查范围也可能不同。作者围绕 Claude Code on Bedrock 比较三种方式：账号级强制护栏、不关联护栏，以及在 settings.json 的自定义头部指定护栏。要回答的问题不是“模型会不会拒绝某句话”，而是输入是否真的经过护栏的提示词攻击检查。模型自身拒绝角色劫持，与护栏在输入侧拦截是两种不同结果。

实验环境为 Windows＋WSL2 Ubuntu、Claude Code v2.1.285、东京区域 ap-northeast-1，以及 jp.anthropic.claude-opus-5-5。作者只启用提示词攻击过滤器，动作设为 Block、强度为高，其他类别过滤器全部关闭；使用 APAC 跨区域护栏配置与 Standard 层。测试材料是三类无害示例：覆盖原有指示、要求扮演不受约束的人格，以及索取系统提示词。先在控制台确认三例都被识别，再通过实际客户端进行对照，避免把控制台通过直接当成客户端接入完成。

机制关键在输入标记。原文引用的 AWS 资料说明，InvokeModel 与 InvokeModelWithResponseStream 的普通调用需要标出用户输入，否则该路径的提示词攻击过滤不会检查未标记内容。账号级配置把 User prompts 设为 Comprehensive，便可不依赖客户端标记检查用户内容；System prompts 设为 Selective，是为了避免本次试验把正常工具说明也纳入检查。它并不证明所有系统指令都安全，也不应脱离自身需求照抄排除范围。

结果是：账号级 Comprehensive 方式在输入侧拦下三种示例；无护栏和自定义头部方式未得到相同的输入侧拦截。作者特意使用不同的输入、输出阻止提示，区分执行位置。无护栏时，模型仍会拒绝“不受约束人格”的设定，但这属于模型自身行为；头部方式下，系统提示词提取示例仍得到响应，响应的具体内容未公开。由此能支持的是“关联护栏不等于这一路径的输入检测已经生效”，不能把三例对照换算成总体检出率。

限制也需要保留：Claude Code 不附带输入标记是依据行为和 Issue 作出的推测，原文没有找到能直接确定这一实现的官方说明。一次拦截后，后续普通对话有时继续被拦，有时恢复，原因尚未查明。文中没有规模化误报统计，也没有证明所有版本、模型、语言和工具返回都受同等保护。企业接入时应以自己的实际入口分别验证正常输入、攻击输入及后续会话，记录拦截发生在哪一侧，再决定适用范围。

**阅读价值：** 适合说明“启用安全功能”和“真实调用受到检查”的差别，并在面试中区分模型拒绝与策略拦截。

### 2. React Native：用实机测量定位 TextDecoder 导致的触摸停顿

**原文：** https://zenn.dev/yskms/articles/5b1090cfa1a51e

**发布时间：** 2026-10-15 07:21:05 JST

RSS 阅读器初次引导时，“下一步”按钮短时间没有反应。作者最初怀疑默认订阅初始化和刷新同步并行的结构，但改动后实机测量并未支持这一猜想。真正的问题是 Expo Managed、React Native、Hermes 环境中，巨大 UTF-8 feed 的同步 TextDecoder.decode 长时间占用 JS 线程。网络请求并行，不代表返回后的解码也能让出界面处理时间；十路获取恰好让多个重解码集中到达。

定位首先依靠一个临时探针：每 50ms 调度定时器，把超出预期的漂移作为连续阻塞的近似指标，另设 20ms 的报告阈值。它不是精确的 CPU 分析器，其他调度延迟也可能混入。原先记录每个 feed 解码时间的共享变量又带来第二个问题：不同 worker 在 await 前后覆盖同一对象，导致对象和时间被错配。改为让每次函数返回自己的文本、字节数、编码与耗时，才得到可信的单 feed 对照；独立漂移统计并不受那项共享变量错误影响。

修正后的分项记录显示，3.2MB 的 MELOS feed 一次解码约 1379ms，1.7MB 的 WWD JAPAN 约 709ms，1.4MB 的 chiik 约 603ms。XML 解析在此次实验中的负荷远小于解码。因此作者没有仅仅调低并行度，而是把 UTF-8 按 65536 字节切块，用 TextDecoder 的流式状态保存跨块未完成字符，并在块间、解码前、解析前和单 feed 完成后让出执行机会。连续 Promise 微任务没有改善；改用 setTimeout(resolve, 0) 安排后续任务后，触摸等其他待处理任务才获得更实际的执行机会。

Android Pixel 11 实机在每轮清空应用数据的相同初装条件下，最大连续阻塞从 1793ms 降至 227ms，约减少 87%；超过 300ms 的次数从 7 次降到 0 次，整轮同步时间从 12.5 秒到 10.2 秒。总时长下降的直接原因没有单独切分，不能把作者提出的调度改善解释当成已经证实的因果。文本正确性另行比较：Android 实机 75 个 feed 与 iPhone 17 模拟器 78 个 feed 的一次解码和分块结果完全一致，mismatch 为 0。

边界尤其重要：iOS 模拟器改善并不如 Android 清晰，仍观察到最大 546ms 和两次超过 300ms 的阻塞；iPhone 8 经 TestFlight 做了体感确认，但文中没有给出等同 Android 的完整性能数字。此次优化只覆盖实际出现问题的 UTF-8，大型 Shift_JIS／EUC-JP 尚未按相同方案处理。64KB 也不是全部设备的最佳块长。可迁移的方法是先测真实设备，再检查测量本身，最后同时验证响应时间、整体耗时与文字一致性。

**阅读价值：** 前端面试中可以具体解释“异步不等于不阻塞”，并说明如何避免测量代码把并发数据张冠李戴。

### 3. dbt 与 Snowflake：PrivateLink 连通后，如何证明公开路径受到限制

**原文：** https://dev.classmethod.jp/articles/dbt-platform-snowflake-aws-privatelink-network-policy/

**发布时间：** 2026-10-15 09:43:26 JST

私有连接能够成功，不代表公开连接就已经关闭。作者在 dbt platform 的 AWS 多租户 Enterprise+ 环境中，把 us-east-1 的 dbt 接到 AWS 东京区域、Business Critical 版 Snowflake，并仅对作业用户 DBT_PL_SVC 设置 Network Policy，避免共享账号的其他使用者被一起影响。验证于 10 月 14 日进行，延迟的 ACCOUNT_USAGE 履历在 15 日确认；文章发布时间为 15 日 09:43 JST，属于本期窗口。

准备工作有两侧权限和审批：Snowflake 需要由账号所有者向 Support 申请允许 dbt 的 SaaS AWS 账号，不能简单把一般的自助授权命令当作第三方 SaaS 的同等方案。然后由 ACCOUNTADMIN 取得 SYSTEM$GET_PRIVATELINK_CONFIG() 的结果，在 dbt 的自助界面创建 endpoint，再在 Connection 中选择它。文中实际采用 Regionless 地址；未使用的 Support-led 流程属于资料整理，不应写成两条流程均经实测。自助功能当时仍为 beta，内部 Stage 的私有连接则需要另一个 endpoint，本实验未涵盖。

作者把作业和 Studio 的用户分开，并让模型写入用户、连接地址、session_id、作业与环境编号。作业执行成功后，用 LOGIN_HISTORY_BY_USER 对照 CLIENT_PRIVATE_LINK_ID 与 dbt 页面上的 Endpoint identifier，证明登录经过指定端点。这里很容易拿错标识：配置输出中的 privatelink-vpce-id 属于 Snowflake 一侧的服务信息，Network Rule 要填的是 dbt 一侧 endpoint 标识。私有 IP 只作为补充证据，不能替代端点对应关系。

为验证限制，允许列表放入 AWSVPCEID 规则，阻止列表另放 IPV4 的 0.0.0.0/0，并只赋给作业用户。只写私有端点规则，并不会自动拒绝公开 IPv4 请求。对照中，私有路径的作业继续成功且登录端点相符；本地电脑用同一作业用户从公开路径连接则被拒绝。随后用 session_id 关联 SESSIONS 与 LOGIN_HISTORY，再检查 INGRESS_NETWORK_ACCESS_HISTORY 的 REQUEST_AUTHORITY。前两类相关视图存在延迟，文中指出 SESSIONS 最多三小时、入口历史最多四小时，所以即时空白不能直接当成“没有访问”。

这是指定用户、指定身份认证和 IPv4 对照，不能扩展为“整个 Snowflake 账号已禁公网”。用户级策略对 Snowflake OAuth 的 token 请求原则上也不是同样的适用位置，需检查集成级或账号级规则及文中说明的内置集成例外。测试用未加密私钥只用于实验，生产还要另定保存、加密与轮换；原文没有完成这些生产治理验收。可借鉴的是同时验证允许与拒绝，并用真实登录记录将配置意图和实际流量对应起来。

**阅读价值：** 把“配置私有连接”拆成端点身份、允许路径、拒绝路径和履历延迟，适合数据平台与云基础设施面试。

### 4. LINE Yahoo：VM 在线迁移加密、TLS 密钥更新故障与性能边界

**原文：** https://techblog.lycorp.co.jp/ja/20261014b

**发布时间：** 2026-10-14 11:00:00 JST

维护物理主机时，Live Migration 能让运行中的虚拟机搬到另一台主机，但“在线”并非全程零暂停。文中先复制内存和磁盘，重复传送迁移过程中被改写的部分，剩余足够小后短暂暂停，再于目标主机恢复。由于传输可能包含内存、磁盘和寄存器等敏感状态，仅隔离网络并不能解释信任边界；作者在 LINE Yahoo 的私有云 Flava 中，为 QEMU 的主机间 TCP 连接加入 TLS，以缩小必须信任的范围。

实现跨越 OpenStack、libvirt 和 QEMU。OpenStack 负责上层编排，libvirt 抽象虚拟化操作，QEMU 建立实际传输连接。平台原先缺少主机证书的签发与管理流程，因此先开发 CA 与客户端：主机生成密钥和签名请求，CA 用有效 Keystone token 确认请求来源后签署证书，再由客户端保存密钥和证书。Ansible 同步修改各层配置。TLS 不只加密，还承担对端身份认证与完整性保护，单改某个“开启 TLS”开关不足以完成整套信任配置。

几百 MB 的小 VM 首先成功，抓包可看到 Client Hello 和 Server Hello。扩大到内存、磁盘各 100GiB 的 footprint 后，迁移失败且没有回滚，VM 进入 ERROR。跨层日志将范围指向源端 QEMU 的 SIGSEGV；gdb 回溯进一步定位到所链接的 GnuTLS。大 VM 能稳定复现，使问题不再只是偶发的业务失败，也说明短小的连通测试没有触及长连接的状态变化。

原文最终对应到 GnuTLS 的 TLS 1.3 KeyUpdate 缺陷，并找到 QEMU 的相关 Issue：该路径错误地同时更新发送与接收状态，而应处理对应方向的密钥。文中引用的 Issue 在约 32GB 传输附近触发更新，100GiB 用例因而会碰到；不能把这个触发量当作全部 TLS 实现的统一阈值。应用相关补丁后，大 VM 的加密迁移成功。原文没有公开所有环境版本组合的适用矩阵，也没有给出可泛化的修复保证。

性能测试中，TLS 相比未启用时，磁盘和内存迁移速度平均分别下降 25.9% 与 78.9%。这是速度下降比例，不是迁移时长增加的同义百分比，也不是实际停机时间。作者怀疑 QEMU 的单核 TLS 处理形成瓶颈，但明确仍需深入调查，不能把怀疑写成完成证明。本文没有据此承诺生产吞吐或所有主机的固定退化比例。实际验收要把身份和加密、长时间密钥更新、失败恢复与大数据量性能分别检查。

**阅读价值：** 展示从上层 ERROR 一直追到 TLS 库的排查链，同时训练区分握手成功、长传输成功和性能达标。

### 5. TypeScript unknown：运行时守卫与 Schema Library 的职责边界

**原文：** https://zenn.dev/nyaomaru/articles/validate-unknown-without-schema-library

**发布时间：** 2026-10-15 00:36:45 JST

外部 API、JSON、localStorage 和消息中的数据，并不会因为在 TypeScript 中写了 User 就自动满足 User 的约束。原文从 unknown 开始，区分“让编译器相信一个类型”和“运行时检查真实值”：as User 不做验证、不转换值，把数字当字符串后再调 toUpperCase，仍会在运行时出错。文章没有性能基准或库间胜负结论，关注的是边界上需要的最小验证模型。

题目中的“不用 Schema Library”并不是完全不用依赖。作者实际使用自己维护的 is-kit，把 isString、oneOfValues 和 struct 组合成可复用守卫。守卫在运行时返回 boolean，也让 TypeScript 在成功分支缩小类型。复杂对象继续组合：arrayOf 检查数组成员，optionalKey 表示属性可以不存在，nullable 表示值可以为 null。二者约束不同；缺少属性和存在但取 null 的字段不应混为一个“可选”概念。

需要把验证结果传给后续逻辑时，可以使用 safeParse：成功是带 valid:true 与 value 的结果，失败是 valid:false。它用同一守卫判定，不复制对象、不强制转换，也不会把不合法数据修补成合法数据。成功结果仍是原先接受的值，所以验证不是快照、也不是深度冻结。safeJsonParse 则把 JSON 解码与守卫放在同一个边界，不合法 JSON 和结构不符均归入失败，避免 any 未经验证扩散。

额外字段同样属于接口决策。struct 默认允许多出的字段，这有助于老客户端接受服务端新添字段；设置 exact:true 才拒绝声明之外的键。示例中带额外 admin 的凭据对象可被 exact 模式拒绝，但“键形状通过”不等于密码正确，也不等于获得管理员权限。原文没有实现身份认证或业务授权，不能将结构验证误写成完整安全机制。

若需要字段路径错误、同时返回多项问题、默认值、类型转换、变换、生成外部产物或深度表单框架整合，原文明确保留 Schema Library 的价值。小守卫适合只判断某个值是否满足谓词，并在成功分支安全使用它。例子说明的是职责选择，没有证明 is-kit 在全部场景更快、更安全或更省体积；本期不保留任何原文未给出的量化优势。

**阅读价值：** 能自然回答 TypeScript 的编译时与运行时边界，并明确 optional、nullable、exact 和业务授权的区别。

## 3. 面接で使えるポイント

### 1. Account-level enforcement guardrail で Claude Code on Bedrock のプロンプト攻撃を入力側でブロックできるか検証した

**面试问题：**

> AIサービスの安全設定が、実際の入力に効いているかをどう確かめますか。

## C-2. IT/AI 专业词汇

1. **Comprehensive（包括的な入力評価）**：不依赖输入标记，对指定类别内容整体评估的账号护栏模式。 本文仅将用户输入设为该模式，系统输入仍Selective。

2. **TextDecoder stream（テキストデコーダーのストリーム指定）**：分块解码时保存尚未组成完整字符的字节状态。 应另行比较一次解码与分块输出。

3. **CLIENT_PRIVATE_LINK_ID（私有接続の端点ID）**：Snowflake登录历史中标示私有连接端点的列。 与dbt侧Endpoint identifier对照，而不是只看IP。

4. **KeyUpdate（TLSの鍵更新）**：TLS会话继续运行时更新通信方向密钥的机制。 长时间大数据量会覆盖短小握手试验没有触及的处理。

5. **optionalKey / nullable（キー省略とnull許可）**：前者允许属性不存在，后者允许属性值为null。 原文强调它们是两种运行时契约。
