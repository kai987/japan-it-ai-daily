# A. 详细文字版

今天分别检查租户边界、浏览器兼容性、修改理由留存、图谱抽取质量和判定模型的输出契约。区分架构介绍与实测结果，并保留成功实验中尚未解决的问题。

## 1. 今日最值得看的 5 篇

### ① Amazon Bedrock AgentCoreでマルチテナントエージェントを構築する

**来源：AWS Japan**

**原文：** https://aws.amazon.com/jp/blogs/news/building-multi-tenant-agents-with-amazon-bedrock-agentcore/

AWS 官方文章以10个设计维度、3种隔离模式说明如何用 **Amazon Bedrock AgentCore** 建设多租户代理。它是后续实现教程的架构前篇，没有给出不同模式的成本对照或防泄漏成功率实验。问题在于代理可运行之后，租户隔离、费用分摊及资源争抢仍需要专门设计。

**Silo** 将 Runtime、Gateway、Memory 和数据层专属化，通过独立 IAM 边界便于隔离及审计，但每租户运维增加。**Pool** 共享资源，从已验证身份传播租户上下文，以 `actor_id` 命名空间及检索元数据过滤控制范围。Runtime 的会话级 microVM 隔离执行环境，不能代替共享数据库的授权。**Bridge** 则按客户等级或架构层组合专属与共享，不要求全系统只选一种模式。

身份层区分直接使用用户全部权限与 **Act-on-Behalf 委托**。验证 JWT 的 `iss`、`sub`、`exp`、`aud` 及租户信息后，在服务边界交换适用于下游且缩小权限的令牌；`act` 声明标识代理，让资源方同时识别用户和执行者。不能把任意请求头里的租户编号直接当作可信授权依据。

工具层使用 **AgentCore Policy 的 Cedar** 或拦截器检查输入、权限、额度；数据层以 ABAC 或租户过滤限制访问。Memory 区分全局、策略、租户、用户、会话五层命名空间。模型及工作流也可选择共享、分级或租户专属，从而把定制需求与维护成本分开权衡。

成本观测需要应用主动记录带租户标签的输入输出 Token、工具调用与执行时间，再接入 CloudWatch/OpenTelemetry。输入输出内容过滤不能代替授权，身份确认、Registry 发现与信任评估也不能混为一谈；文中 ANS v2 仍是 Internet-Draft。限制是这些是官方设计建议，实际选择还须验证共享模式的越权测试和计量能力，不能把构件齐全视为整个系统已经安全。

**关注点：★★★★★**

区分执行隔离与数据授权，说明共享、专属及混合架构各自增加哪些运维责任。

### ② タブもテーマも拡張機能もないAI専用の超軽量ヘッドレスブラウザ「Kitesurf」、Cloudflareが発表

**来源：Publickey**

**原文：** https://www.publickey1.jp/blog/26/aikitesurfcloudflare.html

Publickey 介绍 Cloudflare 发布的 **Kitesurf**：面向 AI 代理操作的轻量无头浏览器。设计去掉人类浏览器的标签页、主题、扩展、平滑滚动等前提，重视高密度并发与快速启动；文章时点仍为 Beta。

它主要以 Rust 实现，编译成 **WebAssembly 后运行于 Cloudflare Workers**，不依赖 Chromium 或 Node.js。操作接口包括 **CDP over WebSocket** 与 HTTP API，已有 Playwright、Puppeteer 等 CDP 工具可连接。但协议可连接与目标网站完整兼容是两个不同层次。

**CPU、内存效率为 Chromium 的3–7倍**来自 Cloudflare 的说明，不是报道者独立实测。开发团队介绍会运行 Web Platform Tests，并针对实际网站执行多步骤 Puppeteer 测试，对比 Chromium 结果。Doom 演示只能证明该实例可以运行，不能外推全部站点兼容。

原文把提示注入防护列为代理浏览器的需求，却没有验证某套防护覆盖率或攻击突破率，因此不保留“已经彻底防注入”这类推论。实际采用应在 Beta 条件下检查目标登录、表单和跳转流程，把资源消耗与任务完成能力一起评价。

**关注点：★★★★★**

将轻量化机制、操作协议、站点兼容性和厂商性能数字分开判断。

### ③ Zed開発チームが「Delta」発表。人間とAIの全対話とコード変更履歴をコンテキストとして保存共有するコラボレーションツール

**来源：Publickey**

**原文：** https://www.publickey1.jp/blog/26/zeddeltaai.html

Zed 团队发布的 **Delta** 让人和 AI 共同讨论、编辑指示、检查生成结果与代码修改。它针对仅有代码差分难以解释“为什么这样修改”的问题，将对话、提示、输出和变更历史一起留存，供后续人员及代理追溯。报道依据产品发表，没有测量团队生产力改善幅度。

底层 **DeltaDB** 使用 **CRDT**，使多人及代理同时编辑的共享数据能够保持一致并收敛。这个机制处理聊天和指示的协同数据一致性，不能被解释为自动化解业务需求冲突或代码语义错误。

除 Rust 客户端外，Delta.dev 浏览器版将客户端编译为 **WebAssembly**，通过 **WebGL** 绘制。Claude Code 终端会话同步到 Delta、供他人查看及评论的功能，在原文中属于计划支持，不能写成已经全面可用。

Delta 独立于 Zed，是为了让数据库和首个应用共同演进，而不是受已有编辑器形态限制。限制包括仍处私人 Beta、未来是否整合 Zed 尚未确定。可迁移的知识是把修改理由随成果物保存；保存范围、查看权限及敏感对话管理则需另行验证，报道没有对此提供完整评估。

**关注点：★★★★★**

解释修改上下文的价值与 CRDT 作用，避免把协同一致性误作代码正确性保证。

### ④ GraphRAG：Local FactからGlobal Structureへ

**来源：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/graphrag-gemini-gephi-lite/

DevelopersIO 使用 **GraphRAG 3.1.1** 处理普通片段检索较难回答的全文主题问题。索引阶段先由 LLM 抽取实体与关系，再用 **Leiden** 识别社区、生成分层报告；查询时综合报告，把部分工作提前到建索引阶段，不能简单称作换一个向量库。

实验采用 Python3.12、gemini-3.5-flash-lite 和 gemini-embedding-001。青空文库《少爷》经过 Shift_JIS 转换及注音、注记清理后，为 **88,997字、69个块**。初始化虽记录模型名称，`model_provider` 仍是 openai，作者把聊天与嵌入两处改为 gemini。`index --dry-run` 会实际各调用模型，并把成功写入日志，不只是 YAML 语法检查。

免费额度15请求/分钟与默认并发25冲突，429被 LiteLLM 包成 BadRequestError，未进入重试。作者在发送端设为 **60秒12次、并发1** 后，初次处理耗时 **28分52秒**；利用 LLM 缓存补输出 GraphML 耗时1分15秒。这两次缓存条件不同，不能视为直接提速对照。答案的 `Data: Reports` 指向生成的社区报告，而非原文逐字证据。

Gephi Lite 因 GraphML 没有 XML 声明而误用 JSON 解析，作者通过 networkx 转为 **GEXF**，得到 **132节点、233边**。图揭示了同一人物名寄せ失败：校长和狸、うらなり及古賀、叙述者“おれ”和“主人公”被拆开。`prompt-tune` 被提出作为针对业务表记调整抽取的方向，而非已修复的结果。

可视化使用 **Louvain**，索引内部使用 Leiden，因此图上分组不能直接等同社区报告。限制是一部作品的构建与观察，没有证明全面优于普通 RAG。面试可说明为什么要分别验证索引质量、引用链、实体归并及可视化算法。

**关注点：★★★★★**

用实际构建故障解释预先摘要、名寄せ和引用追溯，避免只谈 GraphRAG 抽象优点。

### ⑤ Nemotron 3.5 Lightning：専用LLM Routing Judgeを学習

**来源：DevelopersIO**

**原文：** https://dev.classmethod.jp/articles/dgx-spark-nemotron-lightning-switchyard-classifier-finetune/

作者用 **LoRA SFT** 将 **Nemotron 3.5 Lightning30B** 训练成 NeMo Switchyard 的判定器，替代原本284B、占用两台 DGX Spark 的席位。每个请求输出 `crux`、`primary_rule`、`capability_boundary`、`p_solve`，路由器按成功概率决定弱模型或强模型。未调教模型在237件中把234件归为无法判断，说明格式大致合规不等于具备判定能力。

数据包括195道题各让弱模型实际答两次，以及2,085个合成任务；判定词汇蒸馏教师，实测任务概率采用成功频率。评估中的14道难题等通过哈希排除训练泄漏。训练配置 H100两张、rank8/alpha32、2epoch、序列3072，一轮训练46分钟、合并2分钟，GPU约10美元。初版照搬教师的乐观盲点，第二轮把实测题增权6倍并删除偏置合成类别后才改善。

路由接入后约18%的请求在 JSON 结束后持续输出空白，直到4096Token、耗时52秒。定位发现 **Rust 路由器重新按字母排序，而 xgrammar 按 properties 顺序强制生成**，与训练标签固定顺序相冲突。字母顺序直连10次失败4次，自然顺序连续53次无故障。作者提交保序修复，并将4键24种排列混入 v2；随后5种顺序200次、真实路由100次均未重现。

**NVFP4** 将 BF16 的62GB降至 **21GB**，在237件保留集检查概率误差后，判定中位数1.27秒、长输入1.8–2.6秒。87件实际路由预期一致率从教师78/87升至82/87，但其中包含阈值0.75改0.80的调整，不是单独隔离训练方法的因果实验。

限制仍明显：难题只成功识别 **5/14**，量化后还有1种特定输入可确定性触发暴走。首日16小时零暴走、弱92次强24次的运行记录，不能抵消已知缺陷；失败转强模型虽保守，判定时间和费用仍存在。官方 cookbook 还遇到内部容器不可下载、API差异和导出张量命名问题，均需修正，不能把官方示例写成开箱即用保证。

**关注点：★★★★★**

从 JSON 顺序导致的故障切入，说明输出契约、蒸馏偏差与评估集独立性。

## 3. 面接で使えるポイント

### 話題1：Secure RAG / MCP

**面试问题：**

> 複数企業が使うエージェントで、データの混在をどう防ぎますか。

**约 30 秒自然日语回答：**

> 実行環境とデータへの権限を別々に分離します。AgentCore RuntimeのmicroVMで会話を分けても、共有データにはJWTから得たテナント情報による認可が必要です。Act-on-Behalfで下流への権限も絞ります。ただし、記事は構成の解説なので、別企業の検索結果やメモリを読めないことを、実際の権限設定で確認します。各層で確かめます。

**関連Project（学習用）：** 使用两个虚构租户的数据，检查搜索及记忆能否拒绝跨租户读取。

**キーワード：** `microVM` / `JWT` / `Act-on-Behalf`

### 話題2：Agent Browser Runtime

**面试问题：**

> エージェント用のブラウザーを選ぶとき、何を確かめますか。

**约 30 秒自然日语回答：**

> 軽さだけでなく、必要なサイト操作が最後まで通るかを確かめます。KitesurfはRustをWebAssemblyにしてWorkersで動かし、CDPで操作します。ただしベータ版で、効率が三倍から七倍という値も提供者の説明です。Playwrightで対象サイトのログインやフォームを試し、Chromiumとの動作の違いを確認します。プロトコル対応と互換性は別です。

**関連Project（学習用）：** 对测试站点在 Kitesurf 和 Chromium 执行相同操作，记录不兼容点。

**キーワード：** `Kitesurf` / `WebAssembly` / `CDP`

### 話題3：AI Coding / Traceability

**面试问题：**

> AIが行った変更の理由を、チームでどう共有しますか。

**约 30 秒自然日语回答：**

> 差分と一緒に、議論や指示の経緯を残します。Deltaは対話とコード変更を保存し、DeltaDBのCRDTで共同編集を支える構成です。ただし、データが整合しても仕様の判断まで正しいとは限りません。プライベートベータで連携予定もあるため、実際に使える範囲を確認し、レビューで判断の根拠を追えるかを試します。会話の閲覧範囲も点検します。

**関連Project（学習用）：** 对一个小修改同时保存指示、对话、差分和评审理由。

**キーワード：** `Delta` / `DeltaDB` / `CRDT`

### 話題4：GraphRAG

**面试问题：**

> GraphRAGの回答がもっともらしいとき、どこまで確認しますか。

**约 30 秒自然日语回答：**

> 回答だけでなく、索引の関係と参照先を確認します。記事ではGraphRAGがLeidenで要約を作りましたが、校長と狸が別ノードになり、名寄せに課題が残りました。Data: Reportsも原文そのものではありません。業務では同じ対象の表記を点検し、レポートから元の文章まで根拠をたどれるかを確かめます。図が描けても品質は別に点検します。

**関連Project（学習用）：** 用人物关系已知的文本检查别名拆分及报告引用。

**キーワード：** `GraphRAG` / `Leiden` / `Data: Reports`

### 話題5：Model Routing / Fine-tuning

**面试问题：**

> 調整したモデルが本番経路でだけ失敗するとき、何を調べますか。

**约 30 秒自然日语回答：**

> モデルに届く実際の要求を、直接呼び出した場合と比べます。Switchyardの例ではJSONのキー順が変わり、xgrammarの生成順と学習順が衝突しました。ただし、キー順を混ぜた学習で改善しても、特定入力の故障は残ります。形式の検査に加え、ルーターを通した再現試験と失敗時の切り替えを確認します。教師の盲点も引き継ぎ得ます。

**関連Project（学習用）：** 构造不同键顺序的请求，对照直连与路由调用的输出。

**キーワード：** `Switchyard` / `JSON` / `xgrammar`

## 4. 今日技术主题

### 检查中间结果，才能发现最终回答掩盖的问题

租户身份、会话历史、社区报告与判定 JSON 都处在最终成果之前。GraphRAG 答案自然仍可能实体分裂；判定器 JSON 语义不变，生成顺序却能使运行失效。

```text
输入来源 → 转换与抽取 → 保存和共享 → 实际调用路径 → 输出与证据
```

沿路径检查权限和格式变化，有助于定位故障。Delta 保存修改原因，对应过程留痕；Kitesurf 对照实际站点，则对应最后的操作能否真正完成。

## 5. 面试复习卡

### Q1

> セッションを分ければ、共有データの認可は不要ですか。

**回答ポイント：** 不要にはなりません。検証済みJWTのテナント情報を使い、検索とメモリでも対象を制限します。

### Q2

> GraphRAGの図が描けたら、索引は正しいと言えますか。

**回答ポイント：** 同一人物の別名が複数ノードになっていないかを確認します。LouvainとLeidenの違いにも注意します。

### Q3

> JSONの意味が同じなら、構造化出力の順序も無関係ですか。

**回答ポイント：** 学習した順序とxgrammarが強制する順序が衝突した例があります。実際のルーター経由で検査します。

# B. 重点知识与面试应用

## 1. Amazon Bedrock AgentCoreでマルチテナントエージェントを構築する

1. 专属架构便于整理隔离边界，共享架构增加授权与计量工作。
2. 执行隔离不能替代数据访问授权。
3. 这是架构说明，没有覆盖所有条件的安全和成本实测。

## 2. タブもテーマも拡張機能もないAI専用の超軽量ヘッドレスブラウザ「Kitesurf」、Cloudflareが発表

1. 去掉人类界面前提是轻量化设计的出发点。
2. 支持 CDP 不等于完整兼容所有网站。
3. 3–7倍是厂商说明，报道没有独立重复测量。

## C-3. JLPT文法

### 1. ～ことなく
**Level：N1｜意味：** 不……而……  
**形：** `動詞辞書形 + ことなく`  
**使い方：** 说明系统在不泄露机密数据的情况下完成检索或推理。  
**例：** `機密Dataを外部へ送信することなく検索を実行します。`  
**補足：** 比「～ないで」正式。

### 2. ～恐れがある
**Level：N1｜意味：** 有……风险  
**形：** `動詞辞書形 / 名詞 + の + 恐れがある`  
**使い方：** 用于说明 Permission Filter 缺陷或 Browser Session 泄漏风险。  
**例：** `権限Filterが不十分だと機密情報が漏えいする恐れがあります。`  
**補足：** 正式风险提示表达。

### 3. ～にとどまらず
**Level：N1｜意味：** 不仅限于……  
**形：** `名詞 / 普通形 + にとどまらず`  
**使い方：** 说明 Secure RAG 不只做 Retrieval，也包含认证、授权、审计和 Source Grounding。  
**例：** `Secure RAGは検索精度にとどまらず、認証・認可や監査まで設計する必要があります。`  
**補足：** 适合范围扩展。

### 4. ～に基づいて
**Level：N2｜意味：** 基于……  
**形：** `名詞 + に基づいて`  
**使い方：** 说明 Retrieval 和 Routing 依据 Role、Policy 或 Score。  
**例：** `UserのRoleに基づいて検索範囲を制御します。`  
**補足：** 强调有明确依据。

### 5. ～に応じて
**Level：N2｜意味：** 根据……相应调整  
**形：** `名詞 + に応じて`  
**使い方：** 动态选择 Model、Search Strategy 或 Review Flow。  
**例：** `Taskの難易度に応じてModelをRoutingします。`  
**補足：** 强调条件变化与对应措施。

### 6. ～た上で
**Level：N2｜意味：** 在……之后、在……基础上  
**形：** `動詞た形 + 上で`  
**使い方：** 说明先认证/验证，再执行后续授权或检索。  
**例：** `Userを認証した上で、Document Accessを認可します。`  
**補足：** 适合描述安全流程顺序。

### 7. ～にかかわらず
**Level：N2｜意味：** 不论……都……  
**形：** `名詞 + にかかわらず`  
**使い方：** 表达所有 Model / Agent 都必须遵守的共同 Access Policy。  
**例：** `利用するModelにかかわらず、TenantのAccess Policyを適用します。`  
**補足：** 适合统一规则。
