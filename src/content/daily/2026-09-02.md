本期优先筛选 2026 年 9 月 1 日上午至 9 月 2 日上午日本技术媒体的新内容。今天真正值得日本 AI / AI×Web 岗位面试准备的主线非常集中：**Coding Agent 的安全边界必须落到 Runtime、AI Review 需要异构模型交叉验证、企业接入新模型必须先看数据治理、Agent Skills 正在把领域知识变成可按需加载的工程资产，而 MCP / A2A 则继续向跨企业 Agent 基础设施演进。**

## 1. 今日最值得看的 5 篇

### ① Claude Code v2.1.257: Fable 5.1追加と権限すり抜け修正まとめ

**来源：Qiita｜2026年9月1日**  
**原文：** https://qiita.com/picnic/items/ba95f05d2b78799f238b

Claude Code v2.1.257 的重点并不只是增加 Fable 5.1，而是一次明显偏 Security 的更新。项目仓库中的 `.claude/settings.json` / `.claude/settings.local.json` 以后不能再用 `defaultMode: "bypassPermissions"` 强制跳过权限确认；如果组织确实要采用 bypass，必须转移到用户设置、Managed Settings 或启动参数等更高信任层。

同一版本还修复了复合 Shell 命令、Subshell、Symlink、Bash Redirect、不同 Shell 解析差异、Remote Control Consent、末尾带点 Hostname 等多条 Permission Bypass 路径，并增加 Containment Escape 相关限制。对于通过 Bedrock、Vertex、Foundry 等第三方 Provider 使用 Claude Code 的团队，还涉及 Authorization Header / Credential 混入与误发送修复。

**为什么值得看：★★★★★**

这是今天最适合面试准备的一篇 Agent Security 文章。核心判断不是“Prompt 里写禁止操作”，而是：**Repository 内的项目配置不应有能力强制关闭组织级 Permission Boundary；真正的 Security Boundary 要位于更高信任级别的 Runtime / Managed Policy。**

### ② VS Code上で開発のセカンドオピニオンを別のAIエージェントから得られる「Rubber Duck」機能が実験的実装

**来源：Publickey｜2026年9月2日**  
**原文：** https://www.publickey1.jp/blog/26/vs_codeairubber_duck.html

VS Code 1.135 实验性加入 `Rubber Duck`：开发者可以让**另一个 AI Agent / AI Model**对当前 Agent 的计划或工作给出第二意见，而不是只让同一个模型自我 Review。其出发点很清楚——如果最初的设计计划带有错误，同一模型可能因为共享同一偏差而继续合理化原判断，直到后续实现或测试阶段才暴露问题。

这个能力通过 Copilot Agent Host Session 中的 `/rubber-duck` 调用。它强调的是在 Implementation 之前就加入 Independent Review，使错误尽可能早地暴露，减少后续 Rework。

**为什么值得看：★★★★★**

它把 AI Coding Evaluation 从“让 Agent 再检查一遍”推进到 **Heterogeneous Review / Second Opinion**。真正值得面试掌握的是：**同模型 Self-review 并不独立；高风险设计判断最好引入不同 Model、不同 Prompt 或 Deterministic Test 作为另一条 Evidence Path。**

### ③ Amazon Bedrock で Claude Fable 5.1 が利用可能になったので Converse API から呼び出してみた

**来源：DevelopersIO｜2026年9月2日**  
**原文：** https://dev.classmethod.jp/articles/bedrock-claude-fable-5-1-converse/

Claude Fable 5.1 已可通过 Amazon Bedrock 与 Claude Platform on AWS 使用。文章最值得关注的并不是模型名，而是**使用前必须处理的 Data Retention 条件**：Fable 5.1 在 Bedrock 中属于 Covered Model，文章实测需要把 Account-level Data Retention Mode 切换到 `aws_review`；这意味着 Prompt 与 Output 会在 AWS Boundary 内最长保留 30 天，并可能供 Amazon 安全审查。

文章还实测了 `reasoning effort` 和 Prompt Cache：effort 可以设为 low / medium / high / xhigh / max；在作者单次测试里，`max` 明显增加 Thinking Token 和执行时间。Prompt Cache 需要满足最小 Token 条件，而且 Cache Checkpoint / TTL 也是实际成本和延迟设计的一部分。

**为什么值得看：★★★★★**

Enterprise LLM Selection 不应该先问“新模型 Benchmark 高不高”，而应先问：**Data Retention、Data Processor、Region、Compliance 能不能接受？** 然后才是 Model Quality、Reasoning Effort、Cache、Latency 和 Cost。

### ④ AIエージェントがRedshiftを操作してDWH構築や集計分析など可能に、Amazon RedshiftがAgent Toolkit for AWSと統合

**来源：Publickey｜2026年9月2日**  
**原文：** https://www.publickey1.jp/blog/26/airedshiftdwhamazon_redshiftagent_toolkit_for_aws.html

Amazon Redshift 已整合 Agent Toolkit for AWS。Agent Toolkit 并不是单纯给 Claude Code 一个通用 AWS API Tool，而是把 **Agent Skills + AWS MCP Server + Guardrail** 组合起来：Redshift Skill 中包含 Redshift-specific SQL、与 PostgreSQL 的微妙差异、Provisioned / Serverless 的说明、安全注意事项和 API Reference；MCP 则负责真正的 AWS API 调用。

这个设计有一个很值得学习的分层：**Skill 负责“怎样正确操作”，MCP / IAM / Guardrail 负责“能不能操作以及如何执行”。** Agent 只在需要时加载对应 Skill，也能减少无关领域知识长期占用 Context。

**为什么值得看：★★★★★**

这是“Agent Skills 为什么不是 Prompt 小技巧”的现实例子。生产 Agent 不应该只给一个巨大 System Prompt，而应按领域把知识、步骤、API Reference、Safety Rule 做成可按需加载和版本化的 Skill。

### ⑤ AAIF、MCPのガバナンスとA2Aの現状、AIエージェントにオープン標準が必要な理由を説明 ——9月10・11日に「AGNTCon + MCPCon Japan 2026」を渋谷で開催

**来源：gihyo.jp｜2026年9月1日**  
**原文：** https://gihyo.jp/article/2026/09/aaif-mcp-a2a-briefing

Agentic AI Foundation（AAIF）把 Agent 的特点概括成“推理—计划—行动—观察/学习”的**自律循环**，并指出 Long-running Agent 还会继续把任务与权限委托给 Sub-agent。随着 Agent 可以订票、发邮件、执行代码甚至支付，单次回答错误已经变成可能持续影响真实系统的 Workflow Risk。

AAIF 将“Agent Internet”成立的条件概括为：开放协议、无需单一中心许可即可扩展的架构，以及不由单一企业所有的中立治理。文章还解释了 MCP 技术决策仍由 MCP Project Maintainer Group 独立进行，而 AAIF 主要提供法务、商标、认证、生态与跨组织治理支持；A2A 则用于不同组织 / 技术栈的 Agent 相互发现能力、通信和委托任务。

**为什么值得看：★★★★★**

当 MCP / A2A 进入金融、医疗、物流和政府，问题已经不是“Tool Call 怎么写”，而是 **Interoperability、Identity、Trust、Observability、Responsibility 与 Neutral Governance**。这非常适合日本企业 AI Platform / Architecture 面试。

## 3. 面接で使えるポイント

### 话题 1：为什么 Agent Permission 不能放在 Repository 里决定？

**面试问题：**

> AIコーディングエージェントの権限設定を、Repository内の設定ファイルだけで管理してよいですか。

**约 30 秒回答：**

> Repository内の設定は開発ルールを共有するには便利ですが、Security Boundaryとしては信頼レベルが低いと思います。Repository自身が`bypassPermissions`を強制できると、Cloneしただけで危険な権限状態になる可能性があります。そのため、高RiskなPermissionはUser SettingsやManaged Settingsなど、Repositoryより上位の信頼レイヤーで管理し、Runtime側で強制することが重要だと考えています。

**可关联项目：** Claude Code、Codex、CI Agent、Enterprise Developer Platform  
**关键词：** `信頼境界` / `権限制御` / `管理設定`

### 话题 2：为什么 AI Review 要使用不同模型？

**面试问题：**

> AI Agentに自己レビューさせれば十分ですか。

**约 30 秒回答：**

> 自己レビューは有効ですが、同じModelでは最初の判断と同じBiasを共有する可能性があります。重要な設計やSecurity変更では、別ModelによるSecond Opinion、TestやStatic Analysisのような決定的な検証を組み合わせます。Reviewの目的はCommentを増やすことではなく、独立したEvidenceを増やすことだと考えています。

**可关联项目：** AI Code Review、Frontend Design Review、RAG Evaluation  
**关键词：** `セカンドオピニオン` / `独立検証` / `見逃し`

### 话题 3：Bedrock 上选择新模型时先确认什么？

**面试问题：**

> Amazon Bedrockで新しいModelを採用するとき、性能以外に何を確認しますか。

**约 30 秒回答：**

> まずData Retention、Data Processor、利用Region、社内Complianceを確認します。その条件を満たした上で、Quality、Reasoning Effort、Prompt Cache、Latency、Costを実Workloadで評価します。Account単位の設定が他のApplicationにも影響する場合があるため、Model単体ではなくAccount全体のGovernanceも確認することが重要です。

**可关联项目：** Enterprise RAG、AWS Bedrock、Multi-model Gateway  
**关键词：** `データ保持` / `推論強度` / `コンプライアンス`

### 话题 4：Agent Skills 为什么有用？

**面试问题：**

> AI AgentにDomain Knowledgeを与える場合、巨大なSystem PromptとSkillをどう使い分けますか。

**约 30 秒回答：**

> 全Taskに必要な共通RuleだけをSystem Promptに置き、Redshift固有SQLや運用手順のようなDomain KnowledgeはSkillとして分離する方法が良いと思います。必要な時だけSkillを読み込めばContext消費を抑えられ、内容もVersion管理しやすくなります。実行権限はSkillではなくMCPやIAM側で別に制御します。

**可关联项目：** AWS MCP、Enterprise Agent、Internal Skill Registry  
**关键词：** `オンデマンド読込` / `ドメイン知識` / `コンテキスト最適化`

### 话题 5：MCP / A2A 为什么需要开放治理？

**面试问题：**

> AI Agent間の連携で、Open Standardが重要なのはなぜですか。

**约 30 秒回答：**

> 企業やVendorごとに独自Protocolを作ると、AgentとToolの組み合わせごとに接続コードを保守する必要があります。MCPやA2AのようなOpen StandardがあればInteroperabilityを高められます。一方で金融や医療など重要業務へ広がるほど、一社が仕様と実装を独占しない中立的なGovernanceや、Identity・Security・Observabilityの共通要件も重要だと考えています。

**可关联项目：** MCP Gateway、Multi-agent、Enterprise Integration  
**关键词：** `相互運用性` / `中立的ガバナンス` / `標準化`

## 4. 今日の技術テーマ

# Heterogeneous Agent Verification
## ——同一个 Agent 的“自我反省”不等于独立验证

今天最值得系统掌握的是 **AI Coding 的独立验证路径**。

很多 Coding Agent Workflow 还是：

```text
Plan
 ↓
Same Agent
 ↓
Implement
 ↓
Same Agent Review
 ↓
"Looks good"
```

这里的根本风险不是模型不够聪明，而是 **Plan、Implementation、Review 共享同一个假设和偏差**。如果第一步的架构判断错了，后面的自我 Review 很可能继续在同一框架下证明自己“合理”。

VS Code 的 Rubber Duck 试图把流程改成：

```text
Main Agent
  ↓
Plan
  ↓
Different Agent / Model
  ↓
Second Opinion
  ↓
Implement
  ↓
Deterministic Tests
  ↓
Human Review（高风险部分）
```

### 优点

第一，**降低共同偏差**。不同 Model / Agent 的训练、Prompt 和推理路径不同，更容易发现主 Agent 忽略的假设。

第二，**错误发现更早**。在 Planning Stage 找到问题，通常比代码完成后再重构成本更低。

第三，**可以和确定性验证组合**。Different Model 负责语义和架构挑战，Type Check / Test / Lint / Security Scan 负责机械验证，人类只处理剩余高风险判断。

第四，**适合复杂 Coding Agent**。权限、认证、数据库迁移、架构重构这类任务的风险通常来自隐藏前提，而不是明显语法错误。

### 局限

不同 Agent 并不天然代表真正独立。如果它们使用同一 Model Family、相似 Prompt、同一错误 Context，依然可能共享盲点。

Second Opinion 也会增加 Token、Latency 和 Review Noise；如果每个简单任务都调用多个 Frontier Model，成本可能明显上升。

因此还需要定义：**哪些任务值得 Second Opinion，哪些问题可以交给 Deterministic Gate。**

### 日本企业落地时的注意点

建议按照 Risk 分级：

```text
低风险：
Formatter / Simple Refactor
→ Main Agent + Test

中风险：
API Contract / Business Logic
→ Main Agent + Second Model + Test

高风险：
Auth / Payment / Security / Migration
→ Main Agent + Independent Review + Security Gate + Human Approval
```

同时记录 Main Agent 和 Reviewer 的 Model / Version / Prompt / Evidence，避免未来无法解释“为什么当时两个 Agent 都认为正确”。

面试中可以这样总结：

> **AIによるReviewでは、同じAgentに自己確認させるだけでなく、別ModelによるSecond Opinionと決定的なTestを組み合わせ、独立したEvidenceを増やすことが重要だと考えています。**

# B. 重点总结和面试可用的知识点｜重要ポイントと面接で使える知識

## 1. Claude Code v2.1.257: Fable 5.1追加と権限すり抜け修正まとめ

### 中文知识点总结

1. **Repository-level Configuration 不应该能强制关闭 Permission Boundary。** v2.1.257 不再接受 Project Settings 中的 `bypassPermissions` 作为默认权限模式，把高风险控制移到更可信的用户 / 组织 / 启动层。
2. **Permission Check 必须覆盖真实 Shell 语义。** Subshell、Redirect、不同 Shell 解释、Symlink、Hostname Normalization 都可能成为“配置上已禁止，但实际仍能执行”的绕过路径。
3. **Containment 需要处理 Credential / Network Escape。** Auto Mode 开始显式关注 Cloud Metadata Credential、Egress Bypass、Cross-tenant Access 等边界逃逸动作。
4. **第三方 Provider 接入也属于 Security Boundary。** Authorization Header 与 Credential 混入 / 误发送说明 Gateway、Bedrock、Vertex、Foundry 等接入路径需要单独验证。

### 日本語の知識ポイント

1. **Repository内の設定から`bypassPermissions`を強制できないようにし、より信頼度の高いUser / Managed Settings側で権限を管理する設計が重要です。**
2. **Permission Ruleは単純なCommand文字列だけでなく、Subshell、Redirect、Symlink、Shell差異まで含めて実際の挙動を検証する必要があります。**
3. **Auto ModeでもCredential取得、Egress回避、Cross-tenant AccessなどContainment Escapeにつながる操作を別扱いする必要があります。**
4. **BedrockやVertexなど第三者Providerを利用する場合、認証HeaderやCredentialがどこへ送られるかもSecurity Reviewの対象です。**

## 2. VS Code上で開発のセカンドオピニオンを別のAIエージェントから得られる「Rubber Duck」機能が実験的実装

### 中文知识点总结

1. **同模型 Self-review 不是独立验证。** 最初的错误假设可能被同一模型继续合理化。
2. **Second Opinion 应尽量前移到 Planning Stage。** 越早发现设计错误，后续 Implementation / Test 的返工成本越低。
3. **AI Review 的价值在于增加 Independent Evidence。** 不应该只追求更多 Comment，而应该与不同模型和确定性测试形成互补。

### 日本語の知識ポイント

1. **同じModelによるSelf-reviewでは、最初の判断と同じBiasを共有して見逃す可能性があります。**
2. **実装後だけでなく、Plan段階で別AgentからSecond Opinionを得ることで、手戻りを早い段階で減らせます。**
3. **AI ReviewはComment数を増やすのではなく、別ModelやTestなど独立したEvidenceを増やすために使うことが重要です。**

## 3. Amazon Bedrock で Claude Fable 5.1 が利用可能になったので Converse API から呼び出してみた

### 中文知识点总结

1. **新模型采用前必须先确认 Data Retention。** Fable 5.1 在 Bedrock 使用时涉及 Account-level `aws_review`，影响不只是单一 Request。
2. **Reasoning Effort 是质量 / Token / Latency 的独立控制轴。** 高 Effort 不应该默认用于所有任务。
3. **Prompt Cache 有明确的最小输入、Checkpoint 和 TTL 条件。** Cache Strategy 是 Agent Cost Engineering 的一部分。
4. **Account-level 设置需要组织治理。** 某个开发者为了试模型修改 Retention Mode，可能影响同 Account 的其他应用，因此必须先确认数据政策。

### 日本語の知識ポイント

1. **新Modelを採用する前に、Data RetentionとData Processing条件を確認し、社内Policyと整合するか判断する必要があります。**
2. **Reasoning EffortはModel選択とは別のParameterで、Taskに応じてQuality、Token、Latencyを調整できます。**
3. **Prompt Cacheには最小Token数やTTLなどの条件があるため、実際のWorkloadでCache Hitを計測することが重要です。**
4. **Account単位のData Retention設定は他Applicationにも影響し得るため、個人判断ではなく組織Governanceとして管理すべきです。**

## 4. AIエージェントがRedshiftを操作してDWH構築や集計分析など可能に、Amazon RedshiftがAgent Toolkit for AWSと統合

### 中文知识点总结

1. **Agent Skill 负责领域知识，MCP 负责实际 Capability。** Redshift-specific SQL 与 PostgreSQL 差异可以进入 Skill，而 AWS API 执行走 MCP。
2. **On-demand Skill 可以降低固定 Context Cost。** 不需要让所有 AWS 服务知识永久进入 Agent Context。
3. **领域 Skill 应包含 Safety / Guardrail Knowledge。** 不只是命令范例，还应包括服务限制、安全注意点和 Reference。
4. **执行权限仍由 IAM / MCP Guardrail 控制。** Skill 告诉 Agent“怎么做”，不等于授予它“可以做”。

### 日本語の知識ポイント

1. **SkillはRedshift固有SQLや運用手順などDomain Knowledgeを提供し、MCPはAWS APIを実行するCapabilityを提供します。**
2. **必要なSkillだけをOn-demandで読み込むことで、Context Windowの無駄な消費を抑えられます。**
3. **実務向けSkillには手順だけでなく、Security上の注意点、Guardrail、Referenceも含めることが重要です。**
4. **Skillを読み込んでも権限が自動付与されるわけではなく、実行可否はIAMやMCP側で制御します。**

## 5. AAIF、MCPのガバナンスとA2Aの現状、AIエージェントにオープン標準が必要な理由を説明 ——9月10・11日に「AGNTCon + MCPCon Japan 2026」を渋谷で開催

### 中文知识点总结

1. **Agent 的风险来自持续的自主循环。** 推理、计划、行动和观察重复数分钟到数小时，错误也可能累积和扩散。
2. **Open Standard 的价值是降低 N×M 集成成本。** 没有 MCP / A2A，一家公司要为每种 Agent 与 Tool 组合维护独立连接。
3. **技术治理与基金会治理可以分离。** MCP 技术决策由 Maintainer Group 独立负责，基金会承担法务、认证、生态和中立治理支持。
4. **日本企业的差异化会越来越来自 Proprietary Data。** 共同 Protocol 应尽量标准化，自有数据、业务 Rule 与治理能力才是更值得投资的 Value Layer。

### 日本語の知識ポイント

1. **AI Agentは推論・計画・行動・観察を繰り返す自律Loopを持つため、単発Modelより長時間TaskのRiskが大きくなります。**
2. **Open StandardがなければAgentとToolの組み合わせごとに個別実装が必要になり、Integration Costが増大します。**
3. **MCPでは技術判断をMaintainerが担い、Foundationは法務・認証・Ecosystemなど別の層から支援することで技術的独立性を保ちます。**
4. **Protocolが共通化するほど、日本企業は現場Dataや業務Ruleを競争力へ変えることが重要になります。**

### 6. Data Retention Mode｜データ保持モード
**meaningZh：** 控制模型请求数据由谁保留、保留方式与审查条件的 Account-level 设置。  
**contextZh：** Fable 5.1 在 Bedrock 中要求 `aws_review`，因此需要先确认组织数据政策。

### 7. Reasoning Effort｜推論強度
**meaningZh：** 控制模型在单个 Request 上投入推理资源的参数。  
**contextZh：** Fable 5.1 支持 low / medium / high / xhigh / max，应按 Task 调整 Token、Latency 与质量。

### 8. A2A｜Agent2Agentプロトコル
**meaningZh：** 用于不同组织 / 技术栈 Agent 发现彼此能力、安全通信、委托和接管任务的开放协议。  
**contextZh：** AAIF 将其与 MCP 一起作为 Agentic AI Open Standard 生态的重要组成。

## C-3. JLPT语法

### 1. ～にとどまらず
**level：** N1  
**meaningZh：** 不止于……、不仅限于……  
**structure：** `名詞 + にとどまらず / 動詞辞書形 + にとどまらず`  
**usageZh：** 用于说明某项技术影响范围从单一功能扩展到更大的体系。  
**exampleJa：** `MCPの価値はTool接続にとどまらず、IdentityやGovernanceの共通化にも広がっています。`  
**exampleZh：** MCP 的价值不止于 Tool 连接，也扩展到 Identity 与 Governance 的统一。  
**noteZh：** 与今天 AAIF 对 MCP / A2A 从连接协议向 Agent Infrastructure 扩展的语境高度对应。

### 2. ～を余儀なくされる
**level：** N1  
**meaningZh：** 被迫……、不得不……  
**structure：** `名詞 + を余儀なくされる`  
**usageZh：** 说明 Breaking Change 或外部条件变化迫使团队迁移方案。  
**exampleJa：** `Project設定のbypassPermissionsに依存していたTeamは、設定方法の変更を余儀なくされます。`  
**exampleZh：** 依赖 Project 设置中 bypassPermissions 的团队将不得不改变配置方式。  
**noteZh：** 对应 Claude Code v2.1.257 的 Breaking Change；非常适合技术迁移与风险说明。

### 3. ～に至るまで
**level：** N1  
**meaningZh：** 从……一直到……、甚至包括……  
**structure：** `名詞 + に至るまで`  
**usageZh：** 强调 Capability 或影响范围很广。  
**exampleJa：** `AI AgentはWeb検索からCode実行、送金に至るまで現実の操作を行う可能性があります。`  
**exampleZh：** AI Agent 可能执行从 Web 搜索到代码执行、甚至汇款等真实操作。  
**noteZh：** 对应 AAIF 文章列出的订票、邮件、代码执行、支付等现实世界操作范围。

### 4. ～たうえで
**level：** N2  
**meaningZh：** 在……之后；在……基础上  
**structure：** `動詞た形 + 上で / 名詞 + の上で`  
**usageZh：** 表示前一步是后续实施的重要前提。  
**exampleJa：** `実装計画を立てたうえで、別ModelにSecond Opinionを依頼します。`  
**exampleZh：** 制定实现计划后，再请另一个模型提供第二意见。  
**noteZh：** Rubber Duck 文章本身就使用“実装計画を立てたうえで実装とテスト”的语境。

### 5. ～にあたって
**level：** N2  
**meaningZh：** 在……之际、在进行……时  
**structure：** `名詞 + にあたって / 動詞辞書形 + にあたって`  
**usageZh：** 用于正式说明部署、采用、迁移前的注意事项。  
**exampleJa：** `Fable 5.1を利用するにあたって、AccountのData Retention設定を確認します。`  
**exampleZh：** 在使用 Fable 5.1 时，确认 Account 的 Data Retention 设置。  
**noteZh：** 对应 Fable 5.1 Model Card “利用にあたって”要求 Retention Mode 的原文语境。

### 6. ～に伴って
**level：** N2  
**meaningZh：** 随着……、伴随……  
**structure：** `名詞 + に伴って / 動詞辞書形 + のに伴って`  
**usageZh：** 描述 Agent 普及扩大后 Security / Governance 同步增长。  
**exampleJa：** `AI Agentの利用拡大に伴って、IdentityとAuditの重要性も高まります。`  
**exampleZh：** 随着 AI Agent 使用扩大，Identity 与 Audit 的重要性也提高。  
**noteZh：** 很适合 AAIF 所描述的 Agent 从开发工具走向金融、医疗等重要业务的趋势。

### 7. ～一方で
**level：** N2  
**meaningZh：** 另一方面……、与此同时……  
**structure：** `普通形 + 一方で / 名詞・な形容詞 + である + 一方で`  
**usageZh：** 用于技术 Trade-off、反常关系与双面影响。  
**exampleJa：** `Modelの単価が下がる一方で、Agentの利用量はかえって増える可能性があります。`  
**exampleZh：** 模型单价下降的同时，Agent 使用量反而可能增加。  
**noteZh：** 对应 AAIF 文章中 API 价格下降而 Token 使用增长的 Jevons Paradox 语境。
