### 1. TTFBは速いのに表示が遅いVercelのページ、関数リージョンが既定のままだった

**原文：** https://dev.classmethod.jp/articles/vercel-slow-function-region-iad1/

**发布时间：** 2026-10-23 19:30:14 JST

这篇排障记录先区分“开始响应”和“页面数据处理完成”。作者的个人网站使用 Next.js 15 App Router，部署在 Vercel；API 由 AWS 东京区域的 API Gateway、Lambda 与 Hono 提供，数据保存在 DynamoDB。每页展示20条排名，最初首字节时间只有0.45～0.69秒，完整接收 HTML 却需1.79～2.74秒。原因是加载页面形成 Suspense 边界：先发送布局和加载提示，再把服务器取得的数据流入同一连接。浏览器网络面板看不到 Server Components 内部的 API 请求，后半段等待还可能被归入内容下载，不能据此直接断定是文件过大或网速不足。

第一个问题是计算与数据的位置不一致。未命中缓存的响应头显示，接入边缘节点在东京，但真正执行函数的区域在美国东部；服务器每次访问东京 API 都可能跨越太平洋。作者在 Vercel 配置的应用根目录提交东京区域设置，同时调整项目控制台，为没有包含新配置的旧分支或回退构建保留一致的区域选择。两种设置的适用范围不同，控制台变更也要从后续部署才生效。部署后还分别检查普通页面函数与 RSC 数据函数，避免只确认其中一项便认为页面内跳转也已修复。

区域一致后，未访问页面仍需0.74～1.53秒，于是继续数服务器调用。第一页先取一次排名，再为每行依次读取日次汇总和原始数据，总计41次；即使最多并发10个请求，单行内部仍有先后依赖。20幅小折线共读取798KB原始 JSON，也是额外成本。作者改为在日次汇总时预先生成最多60点的降采样序列，新增批量获取接口，用 DynamoDB 的 BatchGetItem 一并取得多个对象的汇总和资料，再以一次批量请求替代逐行获取，使第一页调用减为2次。后续分页另需取得全体第一名作为显示基准，文章没有把这次请求混入第一页的41次比较。

作者没有为追求单次请求而把序列塞进每条排名。一次结算会写入148,604条排名项目，10种统计期间和4种轴会令同一序列最多复制40份；估算新增存储为每天39.7MB，而放在日次汇总只增加0.38MB。排名项目从约250字节变为530字节，仍处在 DynamoDB 一次写容量单位的计费范围，因此不能把存储增量和写入费用直接等同。最终选择多一次 API 往返、约150毫秒的方案，以换取较少的重复存储。这是按数据基数和访问路径作出的取舍，而非“接口次数越少一定越好”。

三阶段测量都从作者东京家中使用 curl 进行，每阶段约10次，报告最小值与最大值。区域修复后的首字节时间为0.12～0.19秒；再消除逐行请求后仍为0.12～0.20秒，但未访问页面完整接收时间降为0.30～0.77秒。重复访问且服务器缓存命中时，三个阶段依次为0.63～0.83、0.27～0.58、0.17～0.45秒。两次修复分别减少往返距离与往返次数，因此指标变化不同。这里的总时间只到 HTML 接收完成，不含浏览器绘制，更不是 LCP；原文没有公开完整应用和受控实验环境，也不能据此推算所有 Vercel 网站都会得到相同倍数的改善。

**阅读价值：** 适合把 React／Next.js 性能面试讲到流式响应、函数位置、服务器调用链和数据建模，并能准确说明每个测量指标的边界。

### 2. AIに並行開発させたら、ブラウザテストのデータが衝突した話

**原文：** https://zenn.dev/3su3/articles/aaabea6298ca53

**发布时间：** 2026-10-23 22:27:13 JST

作者在个人旅行记录应用 Waymark 中使用 Next.js、TypeScript、Supabase、Playwright 和 GitHub，把实现、设计与开发基盘拆成最多3条 AI 工作线，并以 Git worktree 分开源码目录。问题出现在浏览器验收：测试所需的认证用户突然消失，与当前功能改动没有明显对应关系。调查发现，不同工作目录实际上连接同一个本地 Supabase。源码文件分开，并没有使数据库、认证用户和测试结果自动成为各自独立的资源，这正是并行开发需要另外设计的边界。

原文确认了两层事实：认证用户确实缺失，测试数据的准备与清理逻辑也确实可能删除固定用户；但作者没有定位到究竟是哪一次执行完成了删除。因此可以说明共享环境存在相互干扰的结构，不能把某个 Agent 或某次测试直接写成已确定的删除者。对故障调查而言，“发现一条可能的破坏路径”和“把这次现场事件归因到某次操作”是不同证据。文章保留了这个未解问题，没有用看似合理的解释替代执行记录。

已经进行的修复首先针对测试自身的依赖。作者为目标测试准备专用 Journey，降低它依赖其他测试数据的程度；保存操作的断言也改为比较前后的 Record ID 集合，确认预期记录确实加入，而非被既有数据影响。部分测试因此通过，但多 worker，也就是多个测试进程并行时仍有失败。这个结果说明，单条用例的数据准备更独立，与整个共享环境可以安全并发，是两项需要分别验收的性质，不能以部分测试恢复便宣布问题已全部解决。

后续方案有三类，而且原文明确将它们列为防止复发的方向，而非全部实现完成。其一是在继续共享本地 Supabase 时，对修改数据库状态的测试实施互斥，只把竞争资源的部分串行化；其二是为各 worktree 建立独立的 Supabase 环境，以增加启动、管理和清理成本换取并行空间；其三是按执行批次分开 Playwright 报告与结果目录，防止数据隔离后仍互相覆盖诊断文件。选择取决于资源共享范围和维护成本，不是工作线越多便必须复制越多环境。

这是一篇定性的个人项目经验，原文没有给出可复现的失败次数、计时对照、软件具体版本，也没有证实完整环境隔离已落地，因此不保留“并行效率提升多少”或“故障已根治”一类结论。它能迁移到面试的知识是：让 AI 并行修改代码之前，先列出数据库、认证账号、测试准备与清理、输出目录等共享对象，再为各对象确定归属、隔离或互斥方式。最终仍要以并行条件下的结果验证这些边界，而不能只检查 Git 分支是否发生文件冲突。

**阅读价值：** 适合解释 AI 并行开发中代码隔离与运行状态隔离的区别，也能练习在故障报告里清楚区分已观察事实、可疑机制和待实施措施。

### 3. AIレビュー1回 $2.43 を $0.77 に　最初のリクエストがキャッシュを読んでいなかった

**原文：** https://zenn.dev/tariki_yashiro/articles/na-20261020-193000

**发布时间：** 2026-10-23 21:46:09 JST

这篇 Zenn 文章解说 Cloudflare 的内部 AI 代码审查优化，本期也复核了它链接的 Cloudflare 原始报告。原报告称，平均每次审查费用由优化前最昂贵两周的2.43美元降为0.77美元，约减少68%；所需时间中位数从4分9秒降为1分32秒。这是提示词组织、无效调用减少以及模型和推理努力量调整共同形成的结果，不能全部归因于缓存。此前整体缓存命中率虽已升至97%，每次审查的 Token 却从91万增到299万，说明高命中率也可能伴随更多重复上下文和更高账单。

最有价值的诊断发生在首次请求。团队记录实际送到供应商的首个系统消息块哈希与 Token 用量，发现新会话首轮只有14%～26%能复用缓存。OpenCode v1 把共用 Agent 提示词与工作目录、日期等可变环境信息拼成一块，仅在末尾设置缓存断点；不同仓库因此无法复用原本相同的前缀。修复将静态提示词和变化信息分块，在共用部分结束处单独设断点，并保持此前的技能列表和工具说明不随任务改变。问题在真实请求的字节组织，而非界面上是否开启了缓存开关。

缓存之外还要减少会话轮次：把固定参考索引直接交给规则审查者、隐藏其无权调用的工具、一次读取共用资料和负责的差分，并在评论发布后停止不被使用的总结。首次集中读取设有150KB上限。三个审查者共享同一初始前缀时，后两个最多等待20秒，直到首个请求开始流式响应再读取缓存；这是等待与费用的取舍，不是延长缓存存活时间本身就降低单次费用。静态前缀整理与参考索引调整同日上线，使该阶段每次费用从2.47降至2.02美元，不能再把其中某一项单独当作受控实验结果。

更换模型和努力量必须同时检验审查质量。Cloudflare 对作者后续是否修改被指出的代码行，以及657条隐藏时间信息的指摘进行评估，后者由不同供应商的两个模型判断，分歧再交给第三个。采用 Sonnet 5.5 的代码质量审查切到 high，也就是较高推理努力量后，严重指摘被作者处理的比例由34%升至59%；但 medium，也就是中等努力量下，代码质量审查确实失去部分有效发现，性能审查的重要问题数量也减少约64%。因此“指摘更少”既可能是噪声减少，也可能是漏检，不能拿费用下降或输出缩短直接证明质量不变。

这些数字来自一项公司内部工作负载，既不是 Zenn 作者独立复现，也不代表其他 Agent 框架。原报告按变更前后平日时段估计代码优化与模型调整的贡献，并明确不是严格受控实验；作者修改某行也不等于原指摘一定正确。模型评审每组仅35～66条指摘，最新观察窗口只有一天。这些限制使68%的总节省不能直接迁移到其他系统；实际应用还需确认所用框架的请求组装方式、价格和缓存生命周期，并以首请求复用率、调用轮次与有效发现一同判断效果。

**阅读价值：** 适合把企业 Agent 成本问题讲到请求实际结构与审查有效性，避免只谈 Token 单价或把高缓存命中率当成已经优化完成。

### 4. 地球を指でちぎる: 1.6万個の粒の SPH を Web Worker で動かす

**原文：** https://zenn.dev/sishiya/articles/godview-tear-earth-sph-worker

**发布时间：** 2026-10-24 09:51:01 JST

作者在 CesiumJS 地球页面中加入“把地球撕开”的交互，用 SPH，也就是平滑粒子流体方法，让约1.6万个粒子表现地球材料的形变。粒距约408公里，平滑长度取其1.1倍，每个粒子在两倍平滑长度范围内约有45个邻居。模型采用 PREM 的内核与核幔边界半径，并以各层 Murnaghan 状态方程求解重力与压力平衡。得到的中心压力约340GPa、总质量5.66×10²⁴公斤，比真实地球轻约5%；作者明确说密度只是接近 PREM，不是完全一致。开始前还用300步阻尼松弛，每步把速度降为0.9倍，以抑制初始格点排列的震荡。

几个取舍会直接影响画面的“物理”。密度随连续方程更新，因为直接累加邻居质量会低估自由表面密度，扰乱压力；压力又被限制为不小于零，不计算拉力，因此材料容易撕裂。人工黏性取系数1和2，其耗散功转为热。为避免逐对求和，重力按各块材料球对称近似，以中心为基准分成256层壳，只用内侧质量计算吸引；这不是严格的多体自引力求解。由约11公里每秒的声速与粒距决定，每个物理时间步约代表10秒，同时还追踪卸压冷却、坍落转热和部分熔融。

计算与显示被分开：一个 Web Worker 执行物理更新，主线程用点着色器绘制粒子。作者在16核电脑上报告单步约30毫秒，不能把电脑核数写成用了16个计算线程；原文只明确一个 Worker，也没有披露 CPU 型号、浏览器版本或多次测量分布。这里的30毫秒是计算所花的现实时间，前面的10秒是模拟中前进的物理时间，两者不可混为一谈。共享代码也改为使用 Worker 可访问的全局对象，因为 Worker 内不存在浏览器窗口对象。

最大的调试问题反而是交互输入。抓取范围内的粒子通过临界阻尼弹簧追随手的位置，若直接照搬指针移动，材料会被加速到44公里每秒，温度异常增加35万摄氏度。作者为抓取器设置移动速度上限，但每秒3公里又慢得让洞在撕开前回填，最后采用拉起时8公里、搬运时15公里。搬运路线也不再穿过地球的直线，而是先抬到距中心1.4万公里，再沿弧线绕行，避免拿碎块刮过地表。这些是为该粗粒度交互模型减少异常表现的调参结果，不是真实地球材料的破裂速度。

裂缝判断最初依据粒子离开初始位置的距离，整个地球晃动也会误报；后来改看至多6个原始邻居间距是否变化35%以上，以区分整体平移和局部断裂。海水比408公里粒距薄得多，另用约3600个轻粒子表示，位置从 Blue Marble 图像的7000个球面样点中筛选；还修正了海水误触地下热岩导致大范围沸腾的问题，只让真正露出的热岩触发效果。原文把画面标为估计，且没有给出独立地球物理验证，因此阅读价值在于浏览器计算分工、数值近似和输入诊断，不能据此声称它能用于真实灾害预测。

**阅读价值：** 适合浏览器三维开发与计算型前端面试：能同时说明线程职责、性能口径、物理近似，以及交互输入为何会改变模拟结果。

### 5. render-blocking を消しても LCP は変わらなかった：日本語の Web フォントをやめてスマホの LCP が安定した記録

**原文：** https://zenn.dev/outsidernotes/articles/30921cc50fd3a6

**发布时间：** 2026-10-23 21:30:59 JST

这篇 Astro 静态站点的优化记录提醒读者：诊断项消失，不等于用户关心的指标变好。站点部署在 Vercel，作者使用 PageSpeed Insights API v5 的移动端性能检查、Lighthouse 13.5.0，通过 n8n 顺序测量首页、文章、运营者介绍和费用文章4个页面；同一次修复后间隔至少一分钟重复3～4轮。这轮10月16～17日的连续修复中，最初分数59～70，LCP，也就是最大内容绘制时间，为6.2～7.1秒，布局偏移 CLS 为0～0.07。所有数字都是实验室测试，原文尚无真实用户的 CrUX 数据。

最初阻塞绘制的是 Google Fonts 和站点样式。取回字体 CSS 后发现约349KB、386份字体声明，其中 Noto Sans JP 的3种字重就占372份，并按 Unicode 字符范围拆分。作者先把字体 CSS 改为预加载后异步应用，工具不再报告阻塞资源，但 LCP 仍为6.2～7.1秒，CLS 反而升到0.02～0.07。文章认为字体切换造成换行变化可能影响布局，但没有独立证明这一因果。移除某项警告与缩短关键显示路径，应各自重新测量。

下一步发现首页最大内容元素是第一张文章缩略图，却采用延迟加载；作者仅把这张优先图片改为立即读取并提高获取优先级，没有把全部图片一起提升。之后4页共16次测试，7次 LCP 为2.0～3.9秒，9次仍为6.2～7.1秒。进一步看网络请求，文章页实际读取38个 Noto Sans JP 字体文件、约880KB，优先级全部很高。于是让日文正文使用系统字体，只为英数字标题保留 Inter；这一阶段4页各3次，12次均得到93分、LCP 2.6秒、CLS 0。这是连续修复后的观察，不能把全部变化独立归给字体删除。

最后，作者把约30KB的站点 CSS 经 Astro 的样式内联设置放入各页 HTML，HTML 增至约70KB、压缩后约20KB。12次测量中，5次得到99分与1.7秒，另外7次为92～96分与2.6～2.7秒；四步累积后的总范围为92～99分、LCP 1.7～2.7秒、CLS 0。系统字体也有视觉取舍：在 Windows 上把 Yu Gothic UI 放前面曾令假名显得拥挤，作者改为优先 Meiryo。这里必须同时检验加载性能与文字可读性，不能把取消日文字体当成所有网站通用的设计答案。

作者还记录了测量有效性的边界：短时间重复请求同一页面可能取到连测量时间都相同的旧结果，因此重复次数不一定等于新的实验次数；404页面也能拿到性能分，需检查运行警告和网络响应，确认测到的是目标内容。原文没有核实 Lighthouse 数值为何分为两档、平台内部限速配置，也未独立拆开各次修复的贡献。外观只在 Windows Chrome 检查过，Mac、iPhone、Android 及真实用户表现仍未知。日报保留这些缺口，不把实验室评分写成已证实的所有设备加载体验。

**阅读价值：** 适合前端性能面试：既能谈 LCP 元素、资源优先级和日文字体拆包，也能解释重复实验、无效页面和跨设备验证的限制。

## 2. 四类速览

- AI工具与成本：先看首次请求能否复用公共提示前缀，再结合调用次数和严重问题检出评估成本变化。
- 测试与开发协作：worktree隔离源码，Supabase认证、数据库和报告目录仍需逐项辨认共享关系。
- 前端与交付性能：Vercel实例位置影响远程往返，日文字体会参与资源竞争；响应、HTML接收和LCP不能混为一谈。
- 浏览器计算：单个Web Worker负责SPH近似，主线程负责绘制，交互速度与物理可信度要分别审视。

## 4. 技术主题：先界定观测对象，再判断优化是否成立

五篇的共同点是“好看的中间指标”都不能单独代表最终目标。Vercel的TTFB快，仍可能在流式框架先回传外壳后持续等数据；AI评审总缓存命中率97%，首次跨仓库请求却只有14%～26%复用；Lighthouse的阻塞资源警告消失，也没有让最大内容绘制更快。工程判断应写清楚一次观察对应哪个阶段、哪些输入和什么缓存条件，再决定下一次该量什么。

对性能问题，可依次区分一次往返的距离、往返次数和争用的字节。把函数迁到东京处理跨区延迟，把41次调用聚合成2次处理请求数量，预计算展示用日序列减少读取原始数据；这三件事不能用同一个TTFB变化概括。字体实验则先改CSS加载，再改变首图优先级，最后替换日文字体并内联CSS，最终1.7～2.7秒属于累计过程。比较方案时应保留逐阶段结果、重复次数和未改变的条件，不能事后把总收益归给最喜欢的一项。

对并发和AI成本，重点是输入与共享状态的身份。worktree的路径不同，不会自动生成独立的认证用户；给提示词加上日日期和工作位置，也可能破坏公共前缀复用。学习项目可以为测试列出DB、用户和输出目录，为AI请求记录公共区块身份与首次使用量，再用明确的对象ID或已知问题集验证结果。记录实际身份能帮助定位干扰，但没有日志就不能断言谁删了用户，更不能将所有故障归因于AI。

面向团队采用时，还要分别说明体验、正确性和适用范围。SPH的单步约30毫秒只描述一台16核PC上的计算时间，不证明16路并行或地球物理精度；AI评审降费也伴随部分严重问题漏检。可先在可控测试数据与固定问题集上比较，再补真实设备、现场数据和失败样本。这里是从原文提炼的学习与设计建议，并非对日本企业采用率、通用速度或成本收益的承诺。

## 5. 面试复习卡

### Q1

> TTFBとLCPを、それぞれ何の判断に使いますか。

**回答要点：** TTFB表示响应开始，LCP表示最大内容绘制；流式外壳可能先到。再分辨HTML接收完成、客户端绘制与实验室或现场条件。

### Q2

> 並行実行やキャッシュでは、何を同じものとして扱うべきですか。

**回答要点：** 测试需追踪DB、认证用户、输出目录和Record ID；缓存需核对真正发出的公共前缀与可变环境信息。路径不同或总命中率高都不能代替身份检查。

### Q3

> 速く安くなった結果から、正しさも保たれたと言えますか。

**回答要点：** 不能。AI评审要检查严重问题检出与真实漏检；SPH要说明球对称、粗粒度和无拉力近似。单机时长或累计费用都不是正确性证明。


# B. 重点总结与可迁移知识

### 1. TTFBは速いのに表示が遅いVercelのページ、関数リージョンが既定のままだった

**知识点1：** 流式响应中，首字节时间与 HTML 接收完成时间应分开看；浏览器网络面板也不包含 RSC 在服务器内部发出的全部请求。

**日本語：** ストリーミングでは、TTFBとHTMLの受信完了、実際の描画を区別して測ります。

**知识点2：** 区域修复要核对真实函数执行位置、应用根目录配置和新部署结果，再排查逐行请求及重复读取。

**日本語：** 東京のエッジから返っても、関数が東京で動くとは限りません。デプロイ後の実行場所まで確かめます。

**知识点3：** 批量接口与降采样把第一页41次调用减为2次；是否进一步反规范化，应同时计算复制量、存储与延迟。

**日本語：** 41回を2回に減らすまとめ取りと、日次集計への事前加工で、往復回数とデータ複製の両方を抑えています。

### 2. AIに並行開発させたら、ブラウザテストのデータが衝突した話

**知识点1：** worktree 隔离源码工作目录，不会自动隔离 Supabase、认证用户或 Playwright 输出。

**日本語：** worktreeが分けるのは作業ディレクトリで、DBや認証ユーザーまで自動的に独立しません。

**知识点2：** 专用测试数据和保存前后 ID 集合检查已改善部分用例，但多进程失败仍在，实际删除来源也未定位。

**日本語：** 専用fixtureとRecord ID集合の比較で、テスト対象の変更を具体的に確かめています。

**知识点3：** 共享数据库互斥、各工作区独立环境、按执行批次分开输出，是原文提出的方案，尚未全部验收。

**日本語：** 共有資源の排他、環境の分離、結果出力の分離は検討段階で、全件解決とは報告されていません。

### 3. AIレビュー1回 $2.43 を $0.77 に　最初のリクエストがキャッシュを読んでいなかった

**知识点1：** 总体缓存命中率97%仍可能很贵；应单独观察每个新会话的首次请求，以及实际发送的静态前缀是否一致。

**日本語：** 全体の命中率に加え、最初の要求の使用量と送信済みブロックのハッシュを記録しています。

**知识点2：** 静态与可变信息分块、隐藏不可调用工具、批量读取和结果发布后停止，分别减少不同类型的重复费用。

**日本語：** 共通指示と日付などの可変情報を分け、共通部分を単独でキャッシュできるようにしています。

**知识点3：** 68%是多项改变后的整体结果；模型及努力量调整必须继续核验有效发现，尤其不能掩盖性能问题漏检。

**日本語：** 費用減と品質維持は別に検証し、レビュアーによって思考の強さを変えています。

### 4. 地球を指でちぎる: 1.6万個の粒の SPH を Web Worker で動かす

**知识点1：** SPH 地球采用粗粒度材料和各块球对称重力，压力不取负值，因此撕裂表现属于明确简化的教学模型。

**日本語：** 物理計算を1つのWeb Workerへ移し、描画と分けています。シミュレーション内の10秒と計算時間30ミリ秒は別です。

**知识点2：** 一个 Worker 计算、主线程绘制；单步约10秒的模拟时间与约30毫秒的作者电脑计算耗时必须分开。

**日本語：** 絶対的な移動量ではなく隣接粒の間隔を使い、地球全体の揺れを割れと誤認する問題を避けています。

**知识点3：** 抓取速度上限、先抬升再绕行，以及原始邻居间距变化检测，分别处理输入能量异常和整体晃动误报。

**日本語：** 球対称の重力や負圧を使わない設計には、軽さと引き換えの物理的な近似があります。

### 5. render-blocking を消しても LCP は変わらなかった：日本語の Web フォントをやめてスマホの LCP が安定した記録

**知识点1：** 异步加载字体 CSS 只消除了阻塞资源警告，LCP 没有改善；指标必须在每次改动后重新测量。

**日本語：** render-blockingの指摘が消えても、LCPの実測値が改善するとは限りません。

**知识点2：** 只提升真正的首屏最大内容图片，检查日文字体实际下载数量，再比较系统字体与样式内联的效果。

**日本語：** 日本語Webフォントの分割ファイル数と転送量を調べ、OSフォントへ切り替えています。

**知识点3：** 这是4页重复的累积修复实验，没有真实用户数据或完整跨设备视觉验证，也未独立分离每项改动的贡献。

**日本語：** 計測間隔、404の応答確認、ラボと実利用者データの違いまで条件を明記しています。

# C. 日语学习

## C-1. 新学 JLPT 词汇

从五篇原文中确认10个全历史未学词；未将既学表记变体、近义改写或未核实等级的候选凑成20词。复习项目由共享模块按当天用例独立选取。

### 1. 一目（ひとめ）｜N1

- 词性：名詞
- 含义：一眼；看一眼便能察觉
- 搭配：一目で分かる / 一目で見分ける
- 文章语境：Vercel案例指出，浏览器端请求本应一目了然，但服务器内的调用不会显示在浏览器网络面板中。
- 例句：画面だけでは、関数が動く場所を一目で見分けられません。
- 例句译文：仅看画面，无法一眼分辨函数在哪里运行。
- 语感区别：此处读「ひとめ」，不读「いちもく」；既学「一見」偏“乍看之下”，这里强调一次观察便能识别。

### 2. 内訳（うちわけ）｜N1

- 词性：名詞
- 含义：明细；总额内部各部分的构成
- 搭配：費用の内訳 / 内訳を調べる / 内訳を示す
- 文章语境：缓存文章拆开输出、缓存写入与缓存读取费用，才发现大量支出来自反复读取上下文。
- 例句：費用の内訳を調べ、読み取りと書き込みを分けて比較します。
- 例句译文：检查费用明细，将读取与写入分开比较。
- 语感区别：不是只列几个费用名称；内訳说明总数如何分成各部分。既学「費目」指单个费用类别。

### 3. つまむ（つまむ）｜N1

- 词性：動詞（五段）
- 含义：用指尖捏住；夹起
- 搭配：指でつまむ / 端をつまむ
- 文章语境：粒子模拟把指尖捏住的位置连接到一定范围内的粒子，拉动时还要限制速度。
- 例句：画面の点をつまむ操作で、周囲の粒に力を加えます。
- 例句译文：通过捏住画面上的点，对周围粒子施加力。
- 语感区别：指尖夹住的动作比既学「掴む」范围窄；这里不是“摘取要点”或“吃一点”的引申义。

### 4. 沸騰（ふっとう）｜N1

- 词性：名詞・サ変動詞
- 含义：沸腾；液体产生大量蒸气而翻滚
- 搭配：水が沸騰する / 沸騰を再現する
- 文章语境：模拟中曾把地表以下的热岩误当成露出的热岩，导致海水出现错误的沸腾判定。
- 例句：水が沸騰したように見えても、接触判定に誤りがないか調べます。
- 例句译文：即使看起来像水沸腾了，也要检查接触判定是否有误。
- 语感区别：本例是物理现象，不是“讨论升温”的比喻。画面演示不能据此证明真实地球会同样沸腾。

### 5. つり合う（つりあう）｜N2

- 词性：動詞（五段）
- 含义：达到平衡；相互抵消而保持稳定
- 搭配：力がつり合う / 重力と圧力がつり合う
- 文章语境：SPH初始化按各层状态方程式求解密度，使重力与压力保持平衡。
- 例句：初期状態では重力と圧力がつり合うように、密度を決めます。
- 例句译文：在初始状态下，确定密度，使重力与压力保持平衡。
- 语感区别：原文用假名「つり合う」，词典也列「釣り合う」；不是两张新词卡。平衡不表示模拟与真实地球完全一致。

### 6. 削る（けずる）｜N2

- 词性：動詞（五段）
- 含义：削掉；刮去一部分
- 搭配：表面を削る / 地面を削る
- 文章语境：直线移动地球碎块会擦过地表并削掉地面，作者因此改用先远离中心再绕行的路线。
- 例句：かけらが地面を削らないように、外側へ離してから運びます。
- 例句译文：为避免碎块削掉地面，先将它移到外侧再运送。
- 语感区别：这里只学物理上刮去表面的词义；不把既学「削減」的费用减少义换词再算新学。既学「荒削り」是尚粗糙的评价。

### 7. 仮名（かな）｜N2

- 词性：名詞
- 含义：假名；平假名和片假名的总称
- 搭配：仮名を使う / 仮名の字詰め
- 文章语境：字体文章说明，Windows上把Yu Gothic UI排在前面时，假名显得拥挤，因此调整了正文的字体顺序。
- 例句：仮名の間隔を確かめてから、本文用のフォントを選びます。
- 例句译文：确认假名间距后，再选择用于正文的字体。
- 语感区别：此处读「かな」，不是表示化名的「かめい」。既学「書体」指字形风格，仮名指文字类别。

### 8. 追いつく（おいつく）｜N3

- 词性：動詞（五段）
- 含义：赶上；达到对方的进度或水平
- 搭配：進歩に追いつく / 変化に追いつく
- 文章语境：并行开发案例认为，工作环境和运用规则尚未赶上AI同时推进多个任务的方式。
- 例句：並行作業が増えても、テスト環境の分離が追いつかなければ衝突します。
- 例句译文：即使并行工作增多，测试环境隔离跟不上仍会发生冲突。
- 语感区别：Jisho参考等级为N3，不为满足N1/N2比例上调。既学「追従」重在跟随，这里强调弥补差距并赶上。

### 9. 引っ張る（ひっぱる）｜N3

- 词性：動詞（五段）
- 含义：拉；用力牵引
- 搭配：手で引っ張る / 外側へ引っ張る
- 文章语境：地球模拟用拖动操作牵引粒子；手的位置若直接跟随指针，会产生极端速度与温度。
- 例句：指で強く引っ張っても、計算上の手の移動速度には上限を設けます。
- 例句译文：即使用手指用力拉动，也给模拟中的手的移动速度设置上限。
- 语感区别：原文写作「引っぱる」；与「引っ張る」是同一个词。既学「引きずる」偏拖着移动或受牵连，这里只学施加拉力。

### 10. 満足（まんぞく）｜N3

- 词性：名詞・サ変動詞
- 含义：满足；满意
- 搭配：結果に満足する / 改善に満足する
- 文章语境：Vercel案例反省，如果只对リージョン修正后的改善感到满意，另一个延迟来源就会被留下。
- 例句：一度の改善に満足せず、残った待ち時間も調べます。
- 例句译文：不满足于一次改善，也检查剩余的等待时间。
- 语感区别：参考等级保留N3。感到满意不等于达到所有验收条件；既学「満たす」强调使条件得到满足。

## C-2. IT/AI 专业词汇

1. **TTFB（最初の応答バイトが届くまでの時間）**：从发起请求到收到第一个响应字节的时间。 Vercel案例中先返回外壳，后续数据取得仍在继续，不能只看TTFB判断整页完成。

2. **Function Region（関数の実行リージョン）**：动态函数实际运行的地域，与接收请求的边缘节点可能不同。 原文通过响应头区分东京边缘节点与美国东部函数，并将函数与API放在同一地域。

3. **N+1（一覧取得後に行ごとの取得が増える問題）**：取得列表后再逐行发起额外查询，使请求数随行数增长。 Vercel案例把第一页的41次调用改为2次，并保留预聚合数据的容量权衡。

4. **fixture（テストの前提データと準備処理）**：测试运行前建立的数据及其准备、清理机制。 并行测试可能共享同一个用户；worktree只分离代码，不会自动分离数据库。

5. **Prompt caching（共通のプロンプト部分を再利用する仕組み）**：按相同前缀复用已处理输入，需分清缓存写入与读取。 文章把固定指令与目录、日期等可变部分拆开，为共用前缀设置独立保存边界。

6. **SPH（粒子を使った流体計算）**：用粒子及邻域关系近似计算流体状态的数值方法。 约1.6万粒的地球模型简化引力及材料性质，原文明确它不是精密地球破坏预测。

7. **Web Worker（画面の主スレッドと分けて動く処理）**：让计算在独立于页面主线程的环境中执行。 SPH计算在一个Worker中进行，主线程负责绘制粒子；16核PC上每步约30毫秒为作者测量。

8. **LCP（最も大きな主要要素の表示までの時間）**：用于观察主要内容中最大可见元素何时呈现的性能指标。 字体案例区分Lighthouse实验值与尚未取得的真实用户数据，不把指摘消失当成改善完成。

9. **unicode-range（フォントを適用する文字の範囲）**：声明字体文件负责哪些字符范围，可用于按字符拆分下载。 Noto Sans JP按字符范围分割后单页仍读取大量文件，作者改用端末字体再重复测量。

## C-3. 新学语法

五篇原文中经114个既学文法全历史核对，新语法仅1项「～わりに」。复习文法由共享模块根据当日实际用例另行生成，不混入新学或C-4，不为达到5项虚构表达。

### 1. ～わりに｜N3

- 含义：按……本来应当如此，却……；结果与按该条件形成的预期不相称
- 结构：動詞普通形・イ形容詞＋わりに／ナ形容詞＋なわりに／名詞＋のわりに
- 用法：先提出大小、投入或程度等判断基准，再说明与通常预期不相称的结果。原文不是直接比较两个文件，而是说125KB左右的文档，按这个大小来看接收却过慢，因而应继续调查。
- 原文形态：サイズのわりに遅い
- 原文依据：[実際のドキュメントは125KB程度なので、ここで「サイズのわりに遅い」と思えれば先に進めますが、](https://dev.classmethod.jp/articles/vercel-slow-function-region-iad1/)
- 独立例句：ファイルが小さいわりに、受信が終わるまで時間がかかります。
- 例句译文：文件明明很小，接收完成却花了相对较长的时间。
- 注意：既学「～に比べて」直接比较两个对象；这里比较的是条件所形成的预期与实际结果。Bunpro将其列为N3，另有N2教材收录，保留较保守的N3参考，不抬级。
