### 1. Claude Code v2.1.287 の主要アップデート - Claude Mods の追加とシェル書き込みの安全策強化

**原文：** https://dev.classmethod.jp/articles/20261002-cc-updates-v2-1-287/

**发布时间：** 2026-10-02 20:47:23 JST

这篇10月2日的文章整理了10月1日发布的 Claude Code v2.1.287，并用最小扩展示例解释 Claude Mods。Mods 以 JavaScript/TypeScript 在 Claude Code 进程内部运行，区别于另起进程的 shell hook、独立提示词技能或 MCP 服务。版本变更涉及扩展、界面和权限控制，但本文最值得学习的不是更新数量，而是事件拦截后是否继续原有执行，以及扩展自身拥有什么权限。

示例 first-mod 由插件 manifest、hooks.json 的 modules 配置和 register.js 组成。register(on) 注册四类事件：session.start 添加 /tally 命令；tool.call 累加共享 calls，要求界面重新渲染，再调用 next(e) 继续工具执行；command.run 只处理 /tally，直接返回计数而不调用 next；ui.render 则为 spinner 增添计数文字后继续处理。这里 next(e) 决定处理链是否继续，不能把所有事件都写成只记录后直接返回。计数展示是观察工具调用的方法，不是对生成文件或任务结果的验收。

作者以 v2.1.287、macOS/Linux 的 bash/zsh 为前提，先运行 claude plugin validate ./first-mod；该步骤是静态分析，不会执行 mod。随后用非交互的 /tally 命令、--plugin-dir 和 --max-turns 1 运行，得到0次调用，说明该次 session.start 和命令处理能够工作。交互式工具计数与 spinner 展示的第7步属于官方教程描述，不能说作者已经完整实测所有事件。文中还说明运行版本会写出 TypeScript 定义，发生签名冲突时应优先核对当前版本生成的定义。

安全边界需要单独确认：Mods 不在沙箱中，会继承用户权限访问文件、启动程序或网络，默认启用不等于任意插件可信。可按插件关闭，或用 --safe-mode、disableAllHooks 以及受管设置停用；旧的 CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=0 已被忽略，不能当成有效停用手段。此次 shell 防护修正涉及危险删除、已提交符号链接写出工作区和受保护凭据文件，即使存在 allow 也可能仍要求确认。OTEL 新增 prompt_text 时，启用提示词日志的脱敏必须同时覆盖 prompt 与 prompt_text。文章中1M上下文的更新日志与当时文档存在差异，本文不将其整理成所有提供商都已一致生效的结论；实际配置应按版本核实。

**阅读价值：** 把扩展代码的运行权限、静态检查和实际事件处理分开理解，能避免把“装得上”或“计数正常”当成任务成功。

### 2. 共変量に欠損があるとChronos-2の予測はどう変わるか

**原文：** https://dev.classmethod.jp/articles/how-chronos-2-forecast-changes-when-covariates-are-missing/

**发布时间：** 2026-10-02 16:15:17 JST

作者用 chronos-forecasting、AutoGluon-TimeSeries 和 Darts 调用同一个 amazon/chronos-2，调查共变量缺失时为什么结果不同。实验使用 OpenML 的 Bike Sharing Demand version 2，以租车数量为目标、温度为共变量。历史窗口是2011年1月1日至2012年12月30日，共17520个小时槽位，但实际只有17355行，缺少165个小时；预测窗口固定为2012年12月31日的24小时，未来温度有完整时间行但全部为 NaN。缺少一行与某行温度缺失是两种条件，不能混为一谈。

包装器的处理不同。过去某个时刻的整行缺失时，chronos-forecasting 不自动补时间行，Darts 补行并保留 NaN，AutoGluon 则补行并用最近的历史值填温度。已有历史行的共变量为 NaN 时，前两者保留，AutoGluon 会补值。未来少了时间行通常会报错，而时间行存在、共变量为 NaN 时，chronos-forecasting 和 Darts 保留 NaN；AutoGluon 先使用未来序列内可用的最近值，全缺失时才回退到历史中位数。原文示例历史间隙填入8.20，未来全缺失回退为20.5。

作者公开了 Python 3.11、chronos-forecasting 2.3.2、AutoGluon-TimeSeries 1.6.3、Darts 0.41.0、torch 2.10.0 和 pandas 2.3.3 等版本，在 CPU 上运行；Darts 设置8192历史输入长度、24输出长度、float32 与0.1/0.5/0.9分位数，用50%分位作为点预测，对12月31日实测租车量计算误差。原处理下，三者的 MAE/RMSE/MAPE 依次为36.48/57.88/71.33%、84.76/130.00/174.85%、46.58/66.28/93.09%。这些是指定一天与数据处理条件下的误差，不能解释成模型整体排名。

第二组实验先统一输入：按小时 reindex 补165行，目标缺失保留 NaN，温度用 ffill().bfill()，未来温度以历史中位数20.5补全。此时三套调用的 MAE/RMSE/MAPE 均在小数两位上为84.76/130.00/174.85%，与 AutoGluon 原处理相同。这说明所展示的差异可由前处理解释，却不证明补值使准确率提高：另外两套的本次误差反而增大。本文据此提出工程检查顺序——先存时间索引、缺失位置和补值结果，再比较模型输出；原文没有覆盖其他数据集、多个预测日或所有版本，不能把单日一致当作通用等价保证。

**阅读价值：** 用真实的缺失行、NaN 和误差对照，理解相同模型经不同包装器调用时，为什么应先比较实际输入。

### 3. [アップデート] Amazon GuardDuty の有効化を AWS Organizations の宣言型ポリシーで一元管理できるようになりました

**原文：** https://dev.classmethod.jp/articles/guardduty-org-enablement-policies/

**发布时间：** 2026-10-02 17:00:10 JST

GuardDuty 新增 AWS Organizations 的 GUARDDUTY_POLICY 声明式策略，将以往逐区域设置的组织自动启用改成可绑定 root、OU 或账户的策略。委托管理员或管理账户创建策略，被绑定范围内的账户按策略开启保护，新加入或移动到该 OU 的账户也继承设置。上层与下层策略可合并，同一保护计划冲突时优先靠近账户的层级；这是组织层级合并，与区域覆盖的“整体替换”是两种规则。

default 块应用到 GuardDuty 支持的所有区域；指定区域的块会整体替换该区域的 default，不能只写额外启用的一项而期待其他默认项自动合并。不写 default 时，仅明确命名的区域受此策略管理。同一块内开启其他保护计划还必须开启 foundational。文章的示例在默认块启用 Foundational 与 S3 Protection，在东京覆盖块再次写入这两项并增加 EKS Protection。它覆盖可用的商业区域及 GovCloud；特定区域新增配置应按实际支持范围核对。

作者在测试 Organizations 中已有 S3、RDS 自动启用的前提下，只给一个成员账户绑定策略，从东京控制台操作。起初委托管理员无法创建，因为管理账户尚未补委托权限；Attach statement 保留旧条目并补5个 Statement 后可以创建。绑定后约1分钟该账户显示 Policy managed，S3 按策略管理且控制台无法改，RDS 保持原有启用但不属于该策略。大阪 S3 按 default 管理，东京独有 EKS 并未成为大阪受管项目。这是单账户配置验证，不能说已经完成全组织迁移或广泛的探测效果测试。

风险在首次启用策略类型时便出现：组织原来的区域级自动启用整体停止，即使尚未绑定策略，或某保护计划没写入策略，也不能继续依靠旧自动启用覆盖新账户。迁移前应决定 root/OU 覆盖与既有所有保护计划，并调整 IaC 管理对象。仅撤销绑定会保留当前启用状态，停用策略类型则使旧自动启用恢复，二者都不会自动停止已启用的检测；明确 disabled 又会停止保护且阻止控制台/API重新打开。default 可能令所有区域产生费用，甚至没有资源的区域也处理 CloudTrail 全局事件。采用前核对范围与撤销步骤，不能以“一份JSON”推导低风险或低成本。

**阅读价值：** 小范围绑定也可能改变组织级自动启用行为；从具体迁移和撤销语义理解安全基线与费用边界。

### 4. JaSST'26 Niigata 参加レポート：基調講演・事例発表でLayerXメンバー4名がお話ししました #JaSST

**原文：** https://tech.layerx.co.jp/entry/2026/10/02/110935

**发布时间：** 2026-10-02 11:09:35 JST

LayerX 的10月2日文章回顾9月18日 JaSST'26 Niigata，4名成员分别谈质量责任、E2E 落地、概率输出和 QA 暗默知识；这是一篇活动报告，不是当日发布完整测试框架。基调讲演认为 AI 可承担测试工作，却不替人承担质量责任：计划、输入和判断要分工，最后的取舍仍由人负责。本文把这一点作为组织设计背景，不把它扩写为原文未给出的自动审批能力。

E2E 案例指出，单靠“大家写自动测试”的号召没有形成持续实践。推进者先提供编写指南、代码规则、示例代码，构成可参考的“型”，再逐步邀请成员，包括没有编程经验的人。初期代码审查集中到推进者以降低书写差异，等不再出现指正后结束这层审查。这说明支撑条件不仅是选测试工具，也包括可模仿的产物与审查退出条件；报告没有提供人数、覆盖率、执行时长或节省工时，不能捏造量化收益。

AI 产品案例将测试拆成“守り”与“攻め”：一层防止准确性降低，一层探索准确性改善，以分数差值（スコアの差分）辅助自动判定，并从用户反馈增加测试用例。对同一输入也可能改变输出的系统，两层目标可帮助明确是在检查退化还是追求提升。原文未给分数定义、样本构成、阈值、重复次数和数值结果，因此不能断言一次分数提高就统计显著，或推荐照抄某个通用阈值。企业使用时确定业务可接受错误与评测记录属于本日报的工程整理，不是原讲演已证明的结论。

另一案例围绕 Bakuraku 工资计算，将人按风险设计的自动测试，与 AI 编程助手建议的测试比较，通过差异暴露 QA 习惯但未明说的判断标准。与前两例合看，值得保留的是“输入有结构、输出可比较、责任有人承担”的流程。本文只据报告所述保留这些机制，不补写未读的演讲幻灯片实验细节，也不把相关实践当成 AI 在所有业务中优于人的证据。想复现仍需拿到具体评分与数据，并按业务风险重新确定验收条件。

**阅读价值：** 学习随机输出的两层测试与人的质量责任，同时辨认会议简报没有披露的度量和试验细节。

### 2. 共変量に欠損があるとChronos-2の予測はどう変わるか

**面试问题：**

**约30秒回答：**

## C-2. IT/AI 专业词汇

1. **Claude Mods（クロード・モッズ）**：在 Claude Code 内部执行的 JS/TS 扩展。 与外部 hook 进程不同，代码继承用户权限。

2. **next(e)（イベントを次へ渡す関数）**：事件处理后继续后续处理的调用。 tool.call 计数继续执行，而 /tally 命令直接返回。

3. **covariate（共変量）**：除目标外用于预测的变量。 Chronos-2 示例使用温度，必须记录其缺失处理。

4. **reindex（時間索引の付け直し）**：按指定索引对齐行，必要时补出缺行。 本次补165个小时槽位，补行不等于补值。

5. **ffill / bfill（前方／後方からの補完）**：用前一个或后一个有效值补缺失。 原文统一温度输入用 ffill().bfill()，目标仍为 NaN。

6. **GUARDDUTY_POLICY（ガードデューティーのポリシータイプ）**：Organizations 管理 GuardDuty 启用的策略类型。 首次启用会停止旧组织自动启用，不能只看绑定范围。

7. **regional override（リージョン別の上書き）**：为某区域完整替换 default 的设置块。 不是只合并增加的功能，基础项要重新声明。

8. **two-layer testing（二層テスト）**：分别检查退化防止和改善的测试组织。 LayerX 使用分数差值与用户反馈，但公开报告没给阈值。

9. **App Switcher snapshot（アプリ切替のスナップショット）**：应用切换器展示的应用画面图像。 Money Forward 在后台时全面遮挡机密内容。

10. **overlay（オーバーレイ）**：叠加在其他界面上方的显示层。 此处用于快照信息保护，不等于身份或存储保护。
