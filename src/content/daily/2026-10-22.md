### 1. Nulab Backlogの検索をローカルAIで拡張した — Ollama・SQLiteで意味検索を実装する

**原文：** https://zenn.dev/hidetzu/articles/backlog-fzf-semantic-search-ollama

**发布时间：** 2026-10-22 07:30:05 JST

作者把已有的 Backlog 命令行检索工具扩展为本地语义搜索，解决想不起工单标题、只能用近义词描述的问题。原有 SQLite FTS5 双字检索与 LIKE 没有被替换：输入过程中仍走关键词检索，明确按下 Ctrl-S 才调用 Ollama 生成查询向量，避免每次按键都承担模型调用。数据默认留在本机；这是一份具体工具的实现与测量报告，并不是所有企业知识库都适用的精度承诺。

索引按内容类型处理：工单把标题和说明前1200字合成一个向量，文档按约1000字拆分、最多8块，并给每块补上标题；状态、负责人、日期等变化频繁的字段不混入语义表示。向量按长度归一化后以 float32 二进制保存在 SQLite 普通表，Go 遍历并计算内积，相当于余弦相似度；同一文档取最高块分数。模型名称或维度不一致会要求重建，模型与内容的 SHA-256 用来判断哪些记录需要重新嵌入，批量提交保留中断后可续作的进度。

速度需要拆开看。作者以随机向量数据库、新进程启动到取回前50项为范围，重复3次取中位数；在 Arch Linux、Ryzen 7 5700X、原生 amd64 环境，17949条768维向量的 Go 全扫描约66毫秒，sqlite-vec 约28毫秒。另一组 Mac 测量经过 Rosetta，不能直接拿来推断两种 CPU 的优劣。作者据此先保留普通表与 Go 实现，并把规模超过5万作为重新考虑专用扩展的条件，而不是宣称向量数据库总是多余。

查询向量生成的暖启动测量在 M2 Max 上为27～65毫秒，因此包含检索的100～140毫秒是相加后的预期，不是端到端实测；首次加载还会增加数百毫秒到数秒。质量评估也有两个层次：实际约2500工单、300文档的6条改写查询做人工观察；另用25个虚构候选和22条改写问题比较维度。后者768维的 Recall@1为0.95、Recall@5为1.00、MRR为0.98，256维分别为0.95、0.95、0.96，因此最终保留768维。

25个候选中取前5项已经覆盖五分之一，且问题由知道答案的作者设计，高分只能作为当前配置的回归参考。虚构文档短到没有触发拆块，无法证明长文档分块加最高分聚合的效果。原文还区分了实数据“找到同类问题”和“指定目标进入前5”的口径，不能混成统一成功率；RRF混合搜索的追加12问又都被纯语义搜索排到第1，尚不足以证明混合方案更好。面试时可以用这些边界说明如何验证检索系统，而不是只背一个高分。

**阅读价值：** 把索引更新、显式触发、速度测量和有偏的小样本评估放在同一实现里，适合练习解释为什么暂时采用简单架构。

### 2. MapLibre React Native v11 入門：Expo で iOS / Android / Web に同じ地図を出す

**原文：** https://zenn.dev/sun_asterisk/articles/60d48ec339a739

**发布时间：** 2026-10-21 14:03:07 JST

这篇教程用 MapLibre React Native v11 和 Expo，让 iOS、Android 与 Web 使用一致的地点数据与地图样式，同时承认三端底层并不是同一个渲染器。共享的是组件输入、GeoJSON 和 paint/layout 定义，原生端与 Web 各自承担地图实例与生命周期。按平台后缀选择文件由 Metro 负责，TypeScript 的解析规则还要单独处理，不能以打包器选对了文件来推断类型检查也会选择相同实现。

地理语义同样需要转换。地图圆点的 circle-radius 是屏幕像素，不表示真实地面的搜索半径；教程以球面计算生成64个边界点、闭合为 GeoJSON 多边形。位置数据在组件边界统一成经度在前、纬度在后的顺序，避免一种 API 的坐标习惯被带到另一种 API。由共同的数据约定维持相同含义，比强迫两个地图 SDK 共用所有调用代码更可靠。

最有价值的 React 陷阱出现在相机调整：v11.5.0 的 fitBounds 类型声明返回 void，但底层原生模块实际返回 Promise。如果把这个调用直接作为 useEffect 的简写箭头返回值，React 会把 Promise 当成后续清理函数，更新或卸载时出错。作者改用带代码块的回调，明确丢弃相机调用的返回值，并以模拟 Promise 返回的 Jest 测试检查更新、卸载时没有相应报错。这不是靠放宽类型来隐藏问题，而是把副作用与清理函数分开。

相机还会因程序定位触发移动事件。如果移动事件再次更新选择，选择变化又执行相机移动，就可能循环。原生端只接收带用户操作标志的变化，Web 则区分带原始交互事件的变化，避免把程序移动误当成用户输入。Web 容器尺寸通过 ResizeObserver 触发地图重算，卸载时断开观察并移除地图实例，分别管理布局资源与地图资源。

原文记录的组合为 Expo57.0.26、React Native0.86.3、React19.2.3、原生 MapLibre11.5.0 与 Web MapLibre GL JS5.22.0，采用 Development Build，不能直接依赖 Expo Go。作者在 Android API36模拟器、iOS27模拟器和 Chromium 上确认过，尚未验证真实手机。浏览器测试用背景样式替身可检查操作和图钉，却不能证明真实瓦片、服务密钥限制或署名显示正常。平台价格与使用条款也属于文章指定时间的信息，正式接入仍需核对服务方要求。

**阅读价值：** 把 React 生命周期、声明与运行时的差异、事件循环和地理坐标单位串起来，对前端及 React Native 面试有直接价值。

### 3. Node.jsのfs.openAsBlob()で作成後にファイルを変更するとどうなるか

**原文：** https://zenn.dev/yukke_dev/articles/20261022-open-as-blob-file-change

**发布时间：** 2026-10-22 09:53:17 JST

作者针对一个容易误解的 Node.js 行为做了小实验：用 fs.openAsBlob() 把文件交给稍后读取的流程，并不等于创建时已经把文件内容复制成不可变快照。它返回的是由文件支撑的 Blob；创建对象和真正读取数据之间，底层文件仍然可能变化。原文同时引用官方资料，说明创建时及读取前会检查文件状态，而不是把测试结果当成全部实现细节的证明。

实验在 macOS arm64、Node.js26.0.0上进行，使用临时目录中的虚构文本文件。先写入5字节内容，再创建 Blob，并断言大小、内容类型和读出的文本；随后在同一路径写入14字节的新内容，再读取原来的 Blob，观察到 DOMException，错误名为 NotReadableError。最后重新打开文件形成新的 Blob，大小变为14，并能读到修改后的文本。断言和输出把最初读取、文件变化后失败、重新打开后成功三个阶段分开。

这个差异能解释上传、延迟处理或流水线中的偶发失败：持有一个 Blob 引用，并没有冻结它所依赖的外部文件。原文建议在真正读取前打开，或者让流程使用不会再被更新的文件；重新打开只在展示的执行顺序下成功，不能阻止打开之后、读取期间再次发生变更。若要设计稳定输入，还需要明确文件由谁更新、何时交接和何时结束使用，而不能把对象类型当作并发保护。

测试改变了文件长度，尚未覆盖等长覆盖、重命名、读取中的修改及其他操作系统，也没有穷尽状态变化检测的条件。NotReadableError 是本次环境下的观察值，不宜扩展成每一种文件读取失败都返回同名错误。文章提到26.10.0新增同步接口，但作者的26.0.0环境只执行了异步接口，因此不能将同步版列为已验证结果。面试中保留这些未测条件，比只回答“Blob不可变”更能体现对外部资源生命周期的理解。

**阅读价值：** 以可复现的5字节到14字节实验，区分 JavaScript 对象语义、外部文件状态和读取时机。

### 4. データベースとコードの長期的なリファクタリングを安全に進めるための取り組み —— 従業員データの複雑さを解きほぐす

**原文：** https://tech.smarthr.jp/entry/2026/10/21/123725

**发布时间：** 2026-10-21 12:37:25 JST

SmartHR 的员工数据由 Rails 应用管理，保存在相当于 PostgreSQL 的数据库中。一个长期积累的难点是两张互相关联的表都采用双时间历史：既记录业务上何时有效，也记录何时进入系统。查询历史时刻必须同时选择两张表的时间坐标，更新时又要维护父子记录的期间一致性，特殊处理逐渐扩散到依赖这些模型的功能中。父表已有千万量级的记录，因此改结构不能只考虑新功能，更要保留十余年的历史语义。

团队根据当前需求和 PoC，决定把两张表的信息合到父表，在不改变外部功能的前提下逐步去掉特殊处理。迁移期间同时维护旧结构和新结构：当前写入顺带写入目标结构，即ダブルライト；历史记录再通过回填搬迁。现阶段正式读取仍依赖旧实现，新侧写入失败不会改变当前读取结果；将来切换到新实现后，也继续写旧结构，为切回旧实现保留条件。这里的安全性来自保留可比较与可恢复的状态，不是一次性数据导出的自信。

代码使用 Branch by Abstraction，把旧、新两套实现放到相同的访问抽象之内，再通过功能开关选择路径。调用方依然按原来的方式取得子数据，不必每个模块都知道“现在处于迁移中”。如果把选择新旧结构的条件散落到全部调用方，就会把这次改造放大成全系统修改；在抽象边界内切换，才能允许旧实现维持服务、新实现分阶段补齐。

迁移逻辑也按正式应用代码管理：拆成模块，提供清晰接口并编写测试，供搬迁工具和监控作业共同使用，降低两处判断标准不一致的风险。日次检查只看前一天以来新增或更新的记录，确认双写与可合并状态，尽早发现新问题；全量 CLI 以并行方式检查包括旧数据在内的全部记录。对两张历史表之间难以对应的记录，持续执行发现、修正、再检查的循环，逐步缩小未知情况。

这是仍在推进的长期重构，不是最终迁移成功报告。作者在约半年工作之后，还处于准备切换到新实现的阶段，后续才计划删除旧实现；文章没有给出速度提升比例、零停机证明或所有写入路径的幂等保证。对日本企业面试而言，价值在于说明如何控制改造范围、保留回退路径、让数据验证长期可重复，而不是把使用了开关等同于迁移已经安全结束。

**阅读价值：** 用真实的千万级历史数据说明双写、回填、抽象化切换和整合性检查如何配合，适合回答长期系统改造问题。

### 5. ZKP・MPC・FHEを「学ぶ」から「作る」へ ――Advanced Cryptography Program 2026に参加して見えた、高機能暗号実装の難しさ

**原文：** https://gihyo.jp/article/2026/10/advanced-crypto-program-recap

**发布时间：** 2026-10-22 09:34:00 JST

作者回顾了为期7周的 Advanced Cryptography Program 2026，从学习零知识证明、多方安全计算、全同态加密，到最后实际做出作品的过程。三者分别关心证明主张或计算、让多方保有秘密的同时协作，以及在密文上计算，不能只因为都属于高功能密码技术就视为可以互换。文章把“隐藏哪些信息”“谁验证什么”作为设计起点，而不是先堆砌名词再寻找应用。

计算正确与信息保密同样不是一个保证。使用 FHE 可以在不公开明文输入的情况下计算，但仍需确认服务端是否确实执行了指定计算，课程因此讨论组合证明的 Verifiable FHE。即便证明通过，也不能证明事先提交的日志没有遗漏、内容确实反映现实；记录来源的签名、抗篡改存储、时间证明与访问控制仍在系统信任边界内。这是原文讨论的保障范围，不是对某个商业系统已发生问题的诊断。

作品 AuditGuard 以虚构审计日志为题材。先将每条日志哈希并聚合成 Merkle 树的根，用于识别保存后的改写；再用 Shamir 秘密分散把开放日志的密钥拆成5份，收集其中3份才能重建，避免只由一个管理员控制。Schnorr 型知识证明用于简易确认参与者是否知道对应分片。哈希承诺、分片恢复和知识证明各自回答不同的问题，不能用“上了零知识证明”概括全部功能。

演示确认了改动日志会使 Merkle 根的校验失败，以及3份分片能够恢复密钥的过程。但三个参与者的批准是在同一个 Python 进程里模拟，使用小型暗号参数和简化的自制加密处理，不是真正分布在不同组织或设备上的审批。原文明确说这只是用于检查学习内容的 PoC，并非能够保护企业真实数据的成品，也没有给出实际部署安全强度或延迟吞吐的测量。

工程上的收获是将不同保障拆开验证：能否发现保存后改写、单一主体能否独自开示、是否按指定过程计算、输入从何处进入系统。正式应用还要重新选择成熟实现并设计密钥、证明与保存基盘。不能把哈希一致说成内容真实，也不能把模拟3人批准说成已经完成多方治理；面试回答若能指出这两层差异，比罗列 ZKP、MPC、FHE 更有解释力。

**阅读价值：** 用一个明确标记为教育 PoC 的作品，练习区分加密、篡改检测、密钥分权和输入真实性。

## 3. 面接で使えるポイント

## 4. 技术深读：把“看起来相同”拆成可以验证的边界

机制：今天五篇都涉及一种表示到另一种表示的转换，但验证目标各不相同。检索向量把文字变成可比较的数值，必须另测真正想找的结果；GeoJSON统一地理含义，却不能统一地图SDK的返回值与生命周期；Blob对象连接文件资源，却不是自动复制。要先画出数据在何时、由谁持有，再为每个边界选择观测方法。

工程收益：SmartHR保留旧、新表示，使迁移结果能比较、发生问题还能回退；迁移逻辑被检查工具复用，减少验证标准自己漂移的风险。这种保留比较对象的方法，也适用于固定检索评估集、模拟Promise返回的生命周期测试和临时文件读取实验。这里是基于原文的教学归纳，不是对这些项目新做的性能测量。

限制与日本工程现场：日志哈希正确并不保证最初输入真实，小型检索集的排名也不表示企业全量知识库效果。日本团队在进行历史系统改造或跨端交付时，可以明确记录已验证环境、模拟部分、未测边界及切换条件。文章中的SmartHR改造仍在进行，AuditGuard尚是教育原型，因此不能把这些实践包装成已证实的普遍成功公式。

# B. 重点总结与可迁移知识

### 1. Nulab Backlogの検索をローカルAIで拡張した — Ollama・SQLiteで意味検索を実装する

**知识点1：** 保留关键词检索，只有 Ctrl-S 才触发本地语义检索；工单和长文档采用不同的向量组织方式。

**日本語：** 入力中は全文検索、Ctrl-Sだけ意味検索にし、ローカルの埋め込みと変更分だけの更新を組み合わせます。

**知识点2：** 66毫秒是指定 Linux 环境的向量检索部分；100～140毫秒和初始索引耗时属于预期，不能标成实测。

**日本語：** 17,949本・768次元の66ミリ秒はLinux上の検索部分の測定です。検索全体や初回索引の見込みとは分けます。

**知识点3：** 25候选、22问题的高分有样本和题目设计偏差，长文档拆块及混合检索仍需独立评价。

**日本語：** 25候補の評価では長い文書の分割や順位融合の効果を測り切れておらず、点数を一般化しません。

### 2. MapLibre React Native v11 入門：Expo で iOS / Android / Web に同じ地図を出す

**知识点1：** 共享 GeoJSON 与地图样式，按平台分离实例管理；像素半径、地理距离和坐标顺序不能混用。

**日本語：** GeoJSONや描画定義を共通化しても、座標順・単位・イベントと破棄処理は各プラットフォームの境界で扱います。

**知识点2：** fitBounds 的类型与实际 Promise 返回不一致，useEffect 必须避免把异步结果当清理函数。

**日本語：** fitBoundsの型がvoidでも実装はPromiseを返すため、useEffectではその戻り値を返さないようにします。

**知识点3：** 只处理真实用户操作引发的移动，管理 ResizeObserver 的释放；模拟器和瓦片替身测试有明确边界。

**日本語：** エミュレーターとブラウザの確認、タイルを置き換えたテスト、実機・実サービスの検証を区別します。

### 3. Node.jsのfs.openAsBlob()で作成後にファイルを変更するとどうなるか

**知识点1：** 文件支撑的 Blob 不是创建瞬间的内存副本，创建与读取之间存在外部状态变化。

**日本語：** ファイルを基にしたBlobは作成時のメモリコピーではなく、後の読み取りまで元ファイルの状態が関係します。

**知识点2：** 指定环境下，覆盖后旧 Blob 读取报 NotReadableError，重新打开后能读到新内容。

**日本語：** macOS arm64・Node.js v26.0.0では、5バイトから14バイトへの上書き後に既存Blobの読み取りが失敗し、作り直すと新しい本文を読めました。

**知识点3：** 等长修改、重命名、读中变更和其他系统未测；重新打开也不能消除后续竞争。

**日本語：** 同じ長さへの上書きや読取中変更は未検証です。呼び直しだけで競合がなくなるとは言えません。

### 4. データベースとコードの長期的なリファクタリングを安全に進めるための取り組み —— 従業員データの複雑さを解きほぐす

**知识点1：** 双时间父子历史把数据和代码耦合在一起，合表前必须保留外部行为与历史含义。

**日本語：** 二つのバイテンポラル履歴を親へ統合し、外部の機能と利用側のアクセス方法を維持する。

**知识点2：** 双写与回填维持可比较的数据，抽象接口和功能开关把新旧切换限制在模块内部。

**日本語：** ダブルライトとバックフィルでデータを保ち、Branch by Abstractionとフラグで実装の切り替えを局所化する。

**知识点3：** 日次增量检查与全量 CLI 共用迁移判断逻辑；当前仍未完成最终切换与旧实现删除。

**日本語：** 共通の移行ロジックを日次・全件チェックに使う。作業は継続中で、最終移行の成功値とは区別する。

### 5. ZKP・MPC・FHEを「学ぶ」から「作る」へ ――Advanced Cryptography Program 2026に参加して見えた、高機能暗号実装の難しさ

**知识点1：** 信息保密与计算正确是不同性质，FHE 也不自动提供指定计算已执行的证明。

**日本語：** AuditGuardはMerkle tree、Shamirの3-of-5、Schnorr型の知識証明を組み合わせた学習用PoCである。

### 13. 一様（いちよう）｜N1

- 词性：形容動詞
- 含义：同样；一致；一律
- 搭配：一様ではない / 一様な結果
- 文章语境：gihyo指出采用ZKP的产品，其使用方式并不一致。
- 例句：同じ方式でも、必要な条件は一様ではありません。
- 例句译文：即使使用相同方式，必要条件也不完全一样。
- 语感区别：书面语；「一様ではない」强调存在差异，不代表毫无共性。

## C-3. 新学语法

今日新学语法1项：原文中的「増やしていくわけにもいきません」表示基于责任或情况不能这样做，按「～わけにはいかない」统一处理。已对照前71期全部文型，与既学的「わけではない」「ないわけではない」功能不同。其他候选为既习或普通连接，不为凑足5项补造；复习由当日日文用例另行选择。

### 1. ～わけにはいかない｜N2

- 含义：出于责任、情况等理由，不能那样做
- 结构：動詞辞書形＋わけにはいかない／強調・追加の形では「わけにもいかない」
- 用法：并非能力不足，而是结合实际责任或条件判断不宜这样做。原文说长期迁移也不能放任一次性代码无序增长。
- 原文形态：増やしていくわけにもいきません
- 原文依据：[データ移行用とはいえ、書き捨てのコードを無秩序に増やしていくわけにもいきません。](https://tech.smarthr.jp/entry/2026/10/21/123725)
- 独立例句：旧実装へ戻す可能性があるので、今すぐ古いデータを消すわけにはいきません。
- 例句译文：由于可能需要切回旧实现，现在不能马上删除旧数据。
- 注意：与既学「わけではない」的部分否定不同，也不是「ないわけではない」的委婉肯定。「には／にも」是同一功能中的形式变化，不另计新语法。
