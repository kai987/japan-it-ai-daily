### 1. GuardDuty AI Protectionは日本語のプロンプトインジェクションを本当に防げるのか？

**原文：** https://dev.classmethod.jp/articles/guardduty-ai-protection-bedrock-guardrails-tier-verification/

**发布时间：** 2026-09-30 17:39:17 JST

这是一篇开发者攻防验证报告。背景是模型调用带来的新攻击面：盗用凭据、异常消耗 Token、提示注入与训练数据污染不能仅靠传统网络监控识别。文章介绍 GuardDuty AI Protection，但本次实验的核心不是证明它能单独阻止全部攻击，而是核对 PromptInjection.Direct 如何依赖 Bedrock Guardrails。Guardrails 负责内容判定，GuardDuty 读取结果形成 Finding，并可汇集到 Security Hub；AnomalousModelInvocation 和 CostHarvesting 是另外的异常检测类型。

实验在东京 ap-northeast-1 进行，作者通过 SSM 连接 EC2，再用 AWS CLI 调用 Bedrock Converse API。代码指定 APAC 的 Claude 3.5 Sonnet 模型、Guardrail 的 DRAFT 版本并开启 trace，Prompt Attacks 强度为 High。观察指标是实际响应、stopReason 与 actionReason，因此模型自己拒绝和 Guardrail 介入需要分别判断。Classic 第一轮包含正常日语请求、英日 DAN 以及英日 Base64 共5种输入；正常请求通过，英语 DAN 被阻止，其余3种攻击返回 No action。日语 DAN 即使被模型自行拒绝，也不能算过滤器成功介入。

第二轮先启用 Cross-Region inference，再将内容过滤层改为 Standard，保持攻击检测强度。作者仅重跑 Classic 漏过的3种攻击，均得到 guardrail_intervened 与 Guardrail blocked，随后展示 CloudTrail 事件及 GuardDuty Finding。文章对照表也列出英语 DAN 的结果，但明确说正常请求和英语 DAN 未重跑，因此这里不能写成两轮完整5组复测，更不能计算一般化的拦截率。

Standard 的跨区域处理是实质性采用条件，不能把东京发起请求等同于所有数据仅在日本处理。原文指出 APAC 处理可能到达日本以外地区；有国内限定要求时，需要另行选择配置并补足已知缺口。作者把 Word Filters 作为 Classic 的补充建议，但没有展示补充后的一整轮验证，不能宣称已达到 Standard 的效果。样本是少量人工构造输入，未提供大规模误报、变体攻击覆盖或业务性能测量。

面试时可以用此例解释防护与观测的责任：先明确谁执行拦截，再验证日志是否记录同一事件。本文整理的工程建议是保存配置版本、输入语言、编码方式和真实响应，把安全效果与数据所在地共同作为验收条件；这是一项设计判断，并非作者完成了生产环境部署。

**阅读价值：** 能够具体说明防御链、模型拒绝与过滤器介入的差异，以及跨区域推理的采用边界。

### 2. Claude Code と Miro を繋いで Web アプリの全画面を自動キャプチャして画面遷移図を作ってみた

**原文：** https://dev.classmethod.jp/articles/shoma-connect-claude-code-and-miro-to-auto-capture-all-web-app-screens-and-create-screen-transition-diagram/

**发布时间：** 2026-09-30 23:59:10 JST

作者在 React／TypeScript／antd 前端与 Django REST Framework 后端的本地应用中，用 Claude Code 分析界面，再用 Playwright 截图，最后通过 Miro REST API 生成迁移图。问题不是单纯批量截图，而是50多个画面、弹窗和不同模式逐一整理成本高。最终报告的成果是54张截图和68条连接；原文所说手工可能要半天到一天是估计，没有对照测时，因此不能写成实测节省比例。

第一步读取 App.tsx 的 Route、侧边菜单 onClick 与各页面 navigate()。作者发现25条路由不能代表全部界面：部分页面依赖 location.state 中的项目状态，直接输入 URL 无法呈现；菜单可能打开模态窗而非跳转；单个页面的5个标签页又有不同工具栏和模态窗。还发现2个没有菜单或按钮入口的画面。因而截图对象按直链、需要点击的页面、模态窗及子画面分类，用实际交互补足静态路由分析。

第二步在已运行的本地应用上自动登录并采集截图，然后将图像、说明与连接写入 Miro。REST 方式需要为目标团队安装应用，赋予 boards:read 与 boards:write；令牌的团队归属不匹配会出现403。有一小时失效选项时，也需要处理有效期。作者示例通过环境变量传入令牌，避免贴进会话；这只是本次认证处理方式，并不意味着环境变量会自动解决所有泄漏风险。

作者也比较了官方 Miro MCP 插件的工作流。文章中的逐图工具路径每张需要获取上传 URL 与创建图像两次调用，54张会超过100次；而保留下来的 REST 脚本适合按规则计算坐标并重复生成布局。MCP 更适合在已有看板上局部调整。这个判断基于所试用的路径，canvas_create_from_svg 的批量能力未测试，不能断言 MCP 所有方案都一定更慢。

作为前端面试案例，价值在于把“路由数量”“可见状态”“实际可达性”分开验证。本文建议把权限、测试数据与等待渲染的条件纳入截图清单，并检查到不了的旧入口是否仍有用途；这些是从实验提炼的实施建议，原文没有提供不同角色下的完整覆盖率。生成了54张图也不等于所有业务状态都已验证。

**阅读价值：** 保留前端特有的状态与可达性问题，也能说明脚本复现、认证与人工审查的边界。

### 3. [小ネタ] 日本語版Windows EC2のユーザーデータに日本語コメントを書いたら、スクリプトが1行も実行されなかった

**原文：** https://dev.classmethod.jp/articles/202609-windows-userdata-japanese-comment-parse-error/

**发布时间：** 2026-09-30 14:44:31 JST

这篇故障调查来自 Windows Server 2025 日语版 EC2 的初始配置。作者经 CloudFormation 传入含日语注释的 PowerShell 用户数据，原本用于设置时区和防火墙，但连 Start-Transcript 应生成的日志也没有出现。环境明确为 EC2Launch v2.5.2、Windows PowerShell 5.1.26100、日语系统区域 CP932，脚本换行为 LF。文章展示的是这个具体组合的复现，不应外推为所有 Windows 或 PowerShell 版本。

调查从 EC2Launch 的 agent.log 找到实际 UserScript.ps1 和 err.tmp 路径。后者显示 } catch { 前没有配对的 try，属于 ParserError，而不是执行中的防火墙权限错误。因此在脚本内部增加更多日志可能仍看不到结果，因为解析失败发生在第一行执行以前。EC2Launch 阶段完成的日志也不能证明脚本业务动作成功。

原因是 EC2Launch 写出的脚本没有 UTF-8 BOM，Windows PowerShell 5.1 用系统 ANSI 代码页 CP932 解释它。UTF-8 与 CP932 的字节分组错位，注释行尾“る”的最后一个字节8B和 LF 的0x0A被组合读取，原本的换行消失。紧随其后的 try { 于是变成注释的一部分，原来9行被读成8行。关键不是日语字面本身改变程序逻辑，而是读取编码、实际字节和换行边界不一致；换一段注释可能让结果随行尾字节变化。

作者列出4种对策：注释只用 ASCII；把实际用户数据换行改为 CRLF；在 powershell 标签内部紧接开头放置 BOM；或在日语注释后插入 ASCII 罫线。后两者有维护代价：BOM 不可见，分隔行若被删除会复发，作者就经历了删除后再次失败。CRLF 可以保住执行行，但注释仍可能乱码。建议核验传给 EC2Launch 的实际输出文件，不能只检查编辑器设置或模板名称。

补充核读 [Microsoft 的编码说明](https://learn.microsoft.com/ja-jp/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-5.1)确认 Windows PowerShell 在无 BOM 情况下按 ANSI 解释脚本；PowerShell 6+ 的默认行为不同，不能把本文对策当跨平台通用规则。面试中可围绕“解析前失败”说明为什么先看启动器外部错误文件，以及为何修复需要同时检查编码、字节序标记和换行。本文没有重新运行作者的 EC2 实验，所述复现结果均归属于原作者。

**阅读价值：** 提供“脚本未开始执行”和“执行中失败”的区别，并能用实际字节解释注释导致的故障。

### 4. LayerXのFDEインターンに参加した話

**原文：** https://tech.layerx.co.jp/entry/2026/09/30/200852

**发布时间：** 2026-09-30 20:08:52 JST

LayerX 这篇文章是2026年5至7月 FDE 实习生的工程回顾，9月30日公开，并非当天新推出产品。作者受课程安排影响未直接接触客户，而是根据实际业务需求做技术验证与实现。主要任务涉及资产负债表 OCR、Box 文件处理及工作流迁移；这里的价值是说明问题形态如何决定技术选择，而不是以实习感想代替测量结果。

既有 OCR 使用 Azure OpenAI，小字、“-”“▲”和叠加的透かし影响数值识别。作者比较直接用 pypdf 取出 PDF 文本与 Azure AI Document Intelligence 的 ocrHighResolution。客户大量使用扫描 PDF，缺少可直接提取的文本层，因而舍弃 pypdf 路径。ocrHighResolution 改善了小字与符号读取，却把透かし文字一起识别进数值，因此提高分辨率并没有消除全部下游问题。

此次观察到的输出保留了数值，主要错误是文字混入，作者于是在后段追加 LLM 检查与整形节点，移除不成立为数值的混入文字。文章报告在处理过的书类上几乎可以应对透かし重叠，但没有给出样本数、误识别率、负号保持率或模型参数。这个处理选择依赖“数值本身没坏”的前提；若数字缺失、位置错位或正负号误读，直接清理字符未必能恢复正确金额。不能把定性经验写成通用高准确率。

工作流方面，作者把预先固定处理顺序的旧版改写为由 LLM 按状况选择动作的新版，利用既有 Box 连携实现多个文件的动态处理。实际客户提案没有完成，因此实现可行性和客户采用成果应分开。另一个内部方向是为编程代理提供工作流执行工具，使其可以创建、运行、检验并修正；配套检索材料由 Slack 日志及 GitHub Pull Request 定期积累，而不是每次由人临时收集。

面试可以从扫描与文本 PDF 的输入区别开始，解释为何既要调整 OCR 工具，也要验证后处理成立条件。本文建议以金额、符号与原件对照建立测试集，分别记录 OCR 错误和整形变更；这属于工程建议，原文没有展示该测试集或上线后的客户效益。FDE 的学习点是围绕业务约束贯通工具、工作流和可验证结果。

**阅读价值：** 可具体说明输入格式、错误类型和后处理前提如何影响 AI 工具采用，并避免把定性经验说成测量结果。

### 5. [アップデート] Cloud Run のカスタムURL機能が Preview になりました

**原文：** https://dev.classmethod.jp/articles/update-cloud-run-custom-url/

**发布时间：** 2026-09-30 12:37:35 JST

这篇文章实际试用了 Cloud Run 的自定义 URL Public Preview。它让服务使用自己选择的 cloud.run 子域，而不是默认包含项目编号和区域的 run.app 地址；也与使用自有域名的自定义域不同，无需先配置 DNS 或外部负载均衡。文章标题与引言对功能公布日期写法不一致，因此本文保留已核对的9月30日文章发布时间和 Preview 状态，不另推断准确上线日。

作者分别在新建服务与既有服务的网络设置中创建映射，确认多个自定义 URL 可以同时访问同一服务，不必重部署修订版本。CLI 对应 gcloud beta run domain-mappings create。选择的子域名在整个 Google Cloud 范围共享，需符合6至63字符等 DNS 命名条件。对已有服务开启 IAP 后，作者也在自定义 URL 上确认访问限制生效；这说明所试验组合可用，不等于所有企业认证策略都已覆盖。

关键风险在于入口之间的独立性。关闭默认 HTTPS 端点不会关闭 cloud.run 映射，服务仍可经自定义 URL 访问。自定义 URL 没有临时停用与直接更新操作；更换名称时可先创建新入口、确认后删除旧入口，但若要把同一名称重新映射到别的服务，仍涉及删除和重建。映射删除后，其他人可立即取得该子域名，因此不能把先删后建理解为原子、无风险切换。

内部 ingress 或内部与 Cloud Load Balancing 的服务不支持这种入口。作者改为内部后看到 Not Found，但名称仍存在，不能把响应失败等同于释放名称。删除服务也不会自动解放映射。补充核读 [Google 官方文档](https://docs.cloud.google.com/run/docs/custom-urls?hl=ja)确认这些独立生命周期条件，文档还标注 Preview 支持限制及 Google 对域名的收回、重新分配权；因此该 URL 不应被当作永久品牌资产。

面试可围绕“简化部署是否降低运维责任”展开。本文建议维护服务与全部入口的映射清单，撤销访问时逐个验证默认地址、自定义地址及认证；这是依据原文的设计建议，不是作者展示了一套完整撤销测试。实例表明地址容易创建，但权限、名称所有权和撤销行为仍须单独验收，文章也未提供迁移可用率或延迟测量。

**阅读价值：** 能把地址易用性与认证、撤销和名称生命周期分开，明确“关掉默认地址”不等于“服务不可访问”。

### 2. Claude Code と Miro を繋いで Web アプリの全画面を自動キャプチャして画面遷移図を作ってみた

**面试问题：**

## 4. 今日技术主题｜验证自动化边界

今天的技术主题是“在跨层自动化中验证中间契约”。GuardDuty 使用的是 Guardrails 的判定，Playwright 需要的是可到达的页面状态，PowerShell 读取的是实际字节，OCR 后处理依赖的是尚未损坏的数字。每一层拿到的输入与名称上的成功状态并不相同。本文依据原文提出：对每个阶段保存真正的输入形态、输出与失败原因，明确接口之间的前提，再决定修复过滤器、操作路径、文件编码还是识别流程。这是跨文章的工程整理，不是原作者已实现的统一框架。

把这一思路用于日本企业项目，还需要确认处理区域、使用者权限和撤销入口。Standard 的多语言收益与国内限定可能冲突；Miro 团队授权与业务画面权限不同；Cloud Run 的默认端点与自定义映射又有独立生命周期。收益是故障和采用理由更容易解释，代价是测试数据、记录与跨团队协调成本。实际性能和效益仍应在自身条件下测量；不能把3个攻防成功例、54张图或“几乎可处理”的 OCR 描述换算成公司级成功率。

- 例句译文：这个界面仅接受创建和删除操作。
- 语感区别：接受操作不证明执行完成，区别于成功。

### 17. 見当（けんとう）｜N2

- 词性：名詞
- 含义：据线索作出的方向性估计或判断。
- 搭配：見当がつく / 見当がつかない / 見当を付ける
- 文章语境：没有错误详情时，作者对故障原因没有头绪。
- 例句：内部ログがないため、原因の見当がつきませんでした。
- 例句译文：由于没有内部日志，对原因没有头绪。
- 语感区别：判断方向不同于正式验证结果；别与検討混淆。

### 18. 取り消す（とりけす）｜N2

- 词性：動詞・五段
- 含义：撤回已经成立的许可、决定或状态。
- 搭配：許可を取り消す / 名前を取り消す / 決定を取り消す
- 文章语境：Google 保留收回自定义子域的权利。
- 例句：提供元が名前を取り消す可能性も、利用条件として確認します。
- 例句译文：提供方可能收回名称，也要作为利用条件确认。
- 语感区别：区别于删除文件；含撤回有效性或许可。

### 19. 余る（あまる）｜N3

- 词性：動詞・五段
- 含义：分组或使用后仍有剩余。
- 搭配：バイトが余る / 時間が余る / 一つ余る
- 文章语境：错位读取导致注释末尾剩一个字节。
- 例句：一バイトが余り、次の改行と一緒に読まれました。
- 例句译文：剩余一个字节，被与下一换行一起读取。
- 语感区别：不是不足，与资源耗尽相反；本例用于字节分组。

### 20. 連動する（れんどうする）｜N2

- 词性：名詞・サ変動詞
- 含义：一个状态或动作随另一个一同变化。
- 搭配：設定が連動する / 動作に連動する / 連動しない
- 文章语境：关闭默认 HTTPS 端点与自定义 URL 设定不连动。
- 例句：二つの入口は連動しないため、それぞれの公開状態を確認します。
- 例句译文：两个入口不联动，因此分别检查公开状态。
- 语感区别：比连接或集成更强调状态随动关系。

## C-3. 新学语法

已核对过去50期四目录及93个文法身份。原文可确认且语义未学的新文法为2项：名词＋次第だ的条件依赖、だけで的最小条件；后者是N3实用例，未伪装高阶。其余多为已学形式，复习由共享模块补充到5–8项，不换例句凑新文法。

### 1. ～次第だ｜N2

- 含义：结果取决于某个条件。
- 结构：名詞＋次第だ／次第で／次第なので
- 用法：指出结果的依赖条件，本例用于说明是否吞掉换行取决于行尾字节。
- 原文形态：行末のバイト次第なので
- 原文依据：[原因：どの行で起きるかは行末のバイト次第なので、コメントを書き換えると結果が変わります。](https://dev.classmethod.jp/articles/202609-windows-userdata-japanese-comment-parse-error/)
- 独立例句：改行が消えるかどうかは、行末のバイト次第です。
- 例句译文：换行是否消失取决于行末字节。
- 注意：区别于动词连用形＋次第表示“一……就……”；这里是名词条件依赖，不是时间顺序。

### 2. ～だけで｜N3

- 含义：只做某个动作就能带来结果，前提仍需明确。
- 结构：動詞辞書形＋だけで／名詞＋だけで
- 用法：用于说明最小操作。本例“切换层级就改善”成立于已开启防护、指定 Guardrail 和跨区域设置等条件，不能忽略前提。
- 原文形态：ClassicからStandardに切り替えるだけで
- 原文依据：[まとめ：Content filters tierをClassicからStandardに切り替えるだけで、日本語DANとBase64の攻撃パターンをブロック。](https://dev.classmethod.jp/articles/guardduty-ai-protection-bedrock-guardrails-tier-verification/)
- 独立例句：設定を変えるだけで、今回の三つの入力は遮断されました。
- 例句译文：仅改变配置，本次三个输入就被拦截了。
- 注意：N3 的有用例，不刻意标为高阶。与已学“～だけでなく”的追加功能不同；这不表示改变配置能解决所有攻击。
