### 1. EKS でスケーラブルな LLM 推論基盤を作る

**原文：** https://dev.classmethod.jp/articles/scalable-llm-inference-eks/

**发布时间：** 2026-10-29 12:45:29 JST

需要限制数据外传或指定开放权重模型时，可以自建LLM服务，但不能直接套用普通Web请求均匀、短促的假设。原文从两阶段解释原因：Prefill一次处理输入并建立KV缓存，主要消耗计算；Decode逐个生成Token，需要反复读取模型权重和缓存，更容易受到显存带宽影响。长会话会占用更多缓存，增加并发可能提升总吞吐，却同时拉长单个请求的生成间隔。GPU处于工作状态的时间比例，并不能单独区分轻载和饱和。

作者在EKS Auto Mode上组合vLLM、Envoy Gateway、Agent Router、llm-d的EPP、Prometheus、KEDA和Karpenter，使用Qwen3-4B-Instruct-2507。一Pod独占一块GPU，一GPU节点放一Pod。Envoy Proxy接收并转发请求，EPP负责挑选推理实例，参考等待请求数、KV缓存使用率和前缀缓存位置。不过这里的缓存位置来自LRU路由历史推定：曾把前缀送到哪个Pod，就假定它还保有缓存。实例因内存压力逐出缓存后，推定会与实际不一致；不是已经启用了真实缓存块事件索引。

零实例启动不能只依靠正在处理的请求数，因为没有接收者时该值始终为零。原文把请求留在EPP的Flow Control等待队列，由Prometheus收集队列长度，KEDA据此把副本从零变一；尚无GPU可放置的Pending Pod再触发Karpenter准备节点。一到多实例的伸缩交给HPA。队列同时承接饱和时的等待，但有保留期限：到期时没有Pod返回503，有Pod则返回429。GPU节点归零不代表整套系统零成本，网关、监控和伸缩控制仍运行在CPU节点。

从零启动包含节点、镜像、模型权重和推理进程的准备，作者观察到需要数分钟。Open WebUI客户端、HTTPRoute、Flow Control的等待期限，以及启动探针的宽限必须相互配合。镜像使用ECR拉取缓存，权重放同区域S3；查询模型列表用固定响应，避免仅打开界面就启动GPU。这是一套能运行的概念验证，没有性能或费用对照数据。批处理和开发环境可以容忍等待，面向聊天的产品则往往更适合至少保留一个实例，不能把“能缩到零”直接当成更好的用户体验。

**阅读价值：** 把推理请求的状态、缓存位置和零实例启动串成完整架构，理解为什么只看GPU利用率不足以扩缩容。

### 2. [アップデート] Amazon ECS の GPU 共有でコンテナごとのメモリ・演算の上限が守られるか試してみた

**原文：** https://dev.classmethod.jp/articles/amazon-ecs-gpu-sharing-nvidia-mps/

**发布时间：** 2026-10-29 12:54:27 JST

ECS新增的NVIDIA MPS共享允许多个容器使用同一块GPU，分别设置显存额度和计算比例，适合单个任务无法用满设备的情况。作者在g5.xlarge的A10G上验证，GPU有80个SM，ECS报告22,587 MiB显存。环境为GPU版Amazon Linux 2023 AMI 2023.0.20261022、ECS Agent 1.108.1、Docker 25.0.16、驱动580.178.04，以及PyTorch 2.14.1 / CUDA 12.6镜像。测试包含逐步申请显存和FP16的8192×8192矩阵乘法，不是LLM业务延迟基准。

设置4,096 MiB上限后，每次申请256 MiB时能到3,840 MiB，改为32 MiB粒度后到3,936 MiB；独占GPU可到22,272 MiB。CUDA初始化后可用3,960 MiB，作者推测额度与可申请量的差来自CUDA本身开销。计算比例设25、50、75时，容器分别看到20、40、60个SM，吞吐为独占64.3 TFLOPS的26.9%、53.2%、79.0%。单独运行测了三次，并发测试持续60秒。两个50%任务各得到34.16 TFLOPS，接近单任务50%的34.21；若各设75%而合计150%，就会争抢资源。

关键反例是额度通过容器环境变量传给共同的MPS服务，实验中的服务端未设置相应限制。在CUDA初始化前由容器内部代码更改这些变量后，限制可以被移除。此时的20,224 MiB是作者脚本主动停止的数值，不是物理容量极限。另一个设置4,096 MiB的任务在1,792 MiB就申请失败，而ECS账面仍显示剩余14,395 MiB。资源预留记录没有反映前一任务越额后的实际使用。

ECS按显存预约量判断能否放置任务，不按计算比例合计判断；正常预约不足时会以RESOURCE:GPU_MEMORY拒绝启动，但这不能证明容器内部不能越过约定。原文建议不同团队或客户的工作负载分开使用容量提供者或集群。计算比例总和不超过100%时互相影响较小，也只是在这一GPU、软件和矩阵计算条件下的结果。应用到实际推理时，仍需检查模型、带宽、延迟和监控缺口，不能把共享额度当成对恶意租户的强隔离。

**阅读价值：** 用实际资源实验区分“按约定共享”与“隔离不可信代码”，避免把ECS账面显存当成真实用量。

### 3. 仮想オフィスの「近くの人にだけ声が届く」を、LiveKit の購読の許可で SFU に守らせる

**原文：** https://zenn.dev/hotori/articles/5e2cd643a77ae6

**发布时间：** 2026-10-30 01:01:03 JST

Hotori的虚拟办公室让用户在二维地图上移动，靠近时连通语音。客户端由React、Phaser和livekit-client组成，LiveKit SFU自行托管，Python/FastAPI WebSocket服务掌握位置和邻近关系。原先只是接收方关闭自动订阅，再按附近名单订阅音轨。正常界面看似正确，但修改接收端浏览器、直接发出订阅请求，就可能听见远处成员，客户端的自律不构成授权边界。

修正办法是把“自己能听见谁”的关系反向计算成“谁可以接收自己的音频”，由服务器生成说话方的允许列表，再通过setTrackSubscriptionPermissions交给SFU执行。接收端的订阅选择仍负责使用体验，服务器中继负责拒绝未授权配送。大厅按横纵距离较大值不超过三格、最近八人计算；会议室包含同室全员，专注席为空。位置也由服务端裁定，拒绝一次超过两格和穿墙移动。

入室时允许列表尚未到达，必须在发布麦克风音轨前设为空，否则可能沿用默认的全员允许。控制用WebSocket断开时，也清空旧许可，等待重连后的最新状态。更新先发许可再发订阅名单，计算与状态写入之间不插入await，发送时读取最新值，减少旧结果后到造成的覆盖。若订阅先于许可而未接通，600毫秒后重试，单音轨最多五次。

作者测试了十二人会议室、专注席、八人上限、发送次序与重连，并在本地实音频测试中观察到远处浏览器强制订阅仍接收零字节。这是作者的验证，我们没有在其生产环境复现。边界也要保留：修改说话方可以把自己的声音公开，邻近成员本来就能接收，而SFU中继并不是端到端加密。因此这解决的是接收方绕过订阅规则，不等于提供保密会议的全部安全属性。

**阅读价值：** 把前端交互开关与真正的媒体配送权限分开，适合作为React/WebRTC面试中的具体安全设计。

### 4. Lambda Web Functions のリージョンを 4 つから 5 つに入れ替えてみた（オハイオ追加）

**原文：** https://dev.classmethod.jp/articles/lambda-web-functions-multiregion-add-ohio/

**发布时间：** 2026-10-29 18:47:07 JST

DevelopersIO把Next.js后端迁到Lambda Web Functions后，最初使用东京、弗吉尼亚、俄勒冈、法兰克福四区，随后加入俄亥俄。原文说明，端点创建后不能追加或删除区域，也不能把MultiRegion改为PerRegion。因此迁移不是原地修改数组，而是新建五区域端点，再切换公开CloudFront的源站。这一配置生命周期会影响回滚与上线方案。

文中统计的是到达Lambda的请求，不包含直接由缓存响应的全部页面访问。JST 10月21日至28日，俄亥俄通常占5.0%～9.8%，但22日达到22.5%；29日只统计到16时段，占10.4%。这些条件不能被压成“每天固定承接5%～10%”。典型日的区域对照中，弗吉尼亚从135,530件降到107,182件，俄亥俄承接32,974件，体现出部分流量分散。

22日急增伴随大量自称ShapBot的UA。JST 02～08时，全部区域源站收到158,026件，其中70,844件来自Google Cloud的ASN，后者91%使用该UA。这不能验证每次请求的真实运营者。另一个UA构成统计采用UTC 24～28日，浏览器名义约37%，其他约63%，云或托管ASN约67%。时间基准不同，不能直接拼成同一个样本；浏览器UA和云ASN也不能用来计算真实人数或用户地理位置。

区域配额分别管理，增加处理地点有望缩小单区突发负载的影响范围，但原文没有测出页面速度提升比例。Lambda相关费用仅增加数%，也有明确架构条件：大部分数据从Contentful CDN外部API获取，无须每区部署RDS或ELB。若自己的站点依赖区域数据库、数据复制或受SCP约束，就需要重新核算一致性、连接路径与成本，不能照搬作者对全区域使用的建议。

**阅读价值：** 从真实Next.js站点的切换与流量分布出发，区分区域数、源站请求、爬虫活动和多区域成本。

### 5. WASIじゃない、もう一つのインターフェース「WALI」という提案

**原文：** https://zenn.dev/progate/articles/wali-webassembly-linux-interface

**发布时间：** 2026-10-30 09:45:50 JST

Progate工程师在把语言、编辑器和CLI迁入浏览器时，反复遇到文件、进程和终端能力如何提供的问题。WebAssembly本身没有Linux系统调用指令，需要导入外部函数；WASI提供一组接口，但既有Linux程序的功能不一定能逐一映射。WALI选择更低的边界，把Linux系统调用直接表现为可导入函数，让musl等库更接近原有实现。文章是对已有研究及实际二进制的解读，不是当日刚推出的新标准。

作者检查预编译产物，看到读写、内存映射和bash进程创建等Linux风格函数导入。中间层把WebAssembly线性内存中的偏移转换到主机地址。由于不同CPU的系统调用编号不同，二进制按名称绑定，由引擎适配主机编号或替代实现。这种方式减少为每种语言单独补接口的工作，却以兼容的Linux运行环境和专用引擎为前提。

另一个技术要点是ABI，即类型尺寸和数据布局的约定。WALI保留wasm32的32位指针，但long采用64位，不能把普通WASI目标编译的库当成完全兼容的组件混用。Rust官方目标文档也确认了64位long差异、需要WALI引擎、Tier 3及实验状态；还没有该目标的官方预编译标准库。选用工具链时必须确认这些条件，而不是只看到LLVM或Rust里有目标名称便认为部署成熟。

内存隔离与文件、网络权限是两件事。WALI保持WebAssembly内存边界，但如果希望只允许读取指定目录，还需在上层构建WASI一类受限权限接口。它不会在浏览器中自动提供Linux，也不能直接搬到Mac或Windows上运行。Progate本身已有大量WASI构建产物，浏览器也没有可直通的Linux内核，因而只是借鉴其设计方向，并未原样采用。本文也没有给出浏览器性能对照或生产安全评测，不能由导入函数的观察推导出这些结论。

**阅读价值：** 从系统调用和ABI理解WebAssembly移植，避免把支持Linux程序误读成浏览器直接获得Linux能力。

## 3. 面接で使えるポイント

### 1. EKS でスケーラブルな LLM 推論基盤を作る

**面试问题：**

> 自前のLLM推論を、通常のWeb APIと同じ指標で増減させますか。

**约30秒回答：**

> GPU使用率だけではなく、推論の待ち件数と処理中の状態を見ます。記事では、EPPがKVキャッシュの再利用先を選び、待ち行列をKEDAの起動条件にしています。ゼロ台では処理中件数が増えないからです。ただし起動には数分かかるため、対話用途では一台を残すか、待ち時間を利用者に示すかを決めます。

**相关项目例：** 为内部聊天原型比较零实例和保留一实例的行为，记录排队、首个响应和超时，并确认打开模型列表不会意外唤起GPU。

**关键词：** KVキャッシュ / EPP / Flow Control / KEDA

### 2. [アップデート] Amazon ECS の GPU 共有でコンテナごとのメモリ・演算の上限が守られるか試してみた

**面试问题：**

> GPUを複数のコンテナで共有する際、何を確認しますか。

**约30秒回答：**

> 資源の割当と、信頼できない処理の隔離を分けます。ECSのMPSでは、演算割合を半分ずつにした二タスクの性能は、単独の半分設定とほぼ同じでした。ただし上限は環境変数で渡され、内部コードが変えると外れています。予約残量と実使用量を区別し、別の顧客の処理はクラスターなどの境界も分けます。

**相关项目例：** 用同一小型推理模型比较独占与各50%共享，分别记录实际显存和预约额度，并画出跨团队任务的资源隔离边界。

**关键词：** NVIDIA MPS / SM / GPUメモリ / 信頼の境界

### 3. 仮想オフィスの「近くの人にだけ声が届く」を、LiveKit の購読の許可で SFU に守らせる

**面试问题：**

> 近くの人だけが聞ける通話で、ブラウザの購読制御だけで十分ですか。

**约30秒回答：**

> 聞く側の購読切り替えだけでは十分ではありません。Hotoriでは、近接関係を裏返して話す側の許可を作り、LiveKitのSFUで配送を止めます。許可が届く前とWebSocket切断時は、誰にも許さない状態に戻します。ただし話す人が自分の声を公開することは防げず、これだけで機密性や暗号化まで保証するわけではありません。

**相关项目例：** 给React通话原型增加直接订阅、控制连接中断、刚入室和会议室第九位成员等用例，检查媒体配送而不只检查按钮状态。

**关键词：** LiveKit / SFU / 購読権限 / 既定拒否

### 4. Lambda Web Functions のリージョンを 4 つから 5 つに入れ替えてみた（オハイオ追加）

**面试问题：**

> Next.jsサイトの実行地域を増やす際、何を根拠に判断しますか。

**约30秒回答：**

### 5. WASIじゃない、もう一つのインターフェース「WALI」という提案

**面试问题：**

> 既存のLinuxソフトをWebAssemblyへ移すとき、何を調べますか。

**约30秒回答：**

> 必要なOS機能とABIを確認します。WALIはLinuxのシステムコールを名前で取り込み、既存のライブラリを生かします。ただしポインタは三十二ビットでも、longは六十四ビットなので、普通のWASIのライブラリとは混ぜられません。対応するLinux側の実行環境が必要で、メモリの隔離とファイルへの権限も別に設計します。

**相关项目例：** 选一个小CLI，列出必需OS接口、导入函数和类型尺寸，把浏览器目标与Linux目标分开，再确定可访问的目录和网络权限。

**关键词：** WALI / システムコール / musl / ABI

## 4. 技术主题：定义指标含义，明确执行约束的层次

五篇文章共同提醒我们，先定义一个指标究竟代表什么。GPU利用率不是饱和程度，ECS的预约余额不是容器真实用量，Lambda源站请求也不是页面总访问或人类人数。比较必须同时保留单位、采集层次、时间范围和异常值，再讨论优化。

实现边界还需要一个明确的执行者。LLM中EPP选择接收者、KEDA改变副本、Karpenter准备机器；虚拟办公室由SFU拒绝未授权配送，而不是只隐藏客户端操作；WALI则把内存隔离和OS权限分别交给不同层。这里是跨文整理的工程判断，并非要求把五个产品一起引入。

面试回答可以按“目标—文章里的具体机制—证据条件—限制”展开。说清零实例启动时由队列触发、多个期限必须协调、交互式用户可能无法接受数分钟等待，比只列扩缩容工具更有说服力。项目例是练习建议，不能把尚未进行的试验当成个人成果。

## 5. 面试复习卡

### Q1

> 使用率、予約残量、リクエスト数は、それぞれ何を表していますか。

**回答要点：** GPU忙碌比例不独立代表推理饱和；ECS按预约额度记账，不直接给出越额后的真实显存；Lambda到达请求不包含所有缓存命中，也不是人数。保留单位、采集层与时间范围。

### Q2

> クライアントや実行コードが変更されても、どの層で条件を守れますか。

**回答要点：** MPS环境变量不是不可信租户强隔离；LiveKit在SFU执行说话方许可，接收方改订阅也不放行；WALI的内存隔离不会自动限制文件网络权限，需额外受限接口层。

### Q3

> 準備や切り替えが終わる前の扱いを、どう決めますか。

**回答要点：** 零实例保留队列但设期限，并协调启动探针；音声许可未到或控制连接断开时默认拒绝；多区域用新端点切源站，先核对地区依赖和回退条件。

## C-1. 新学JLPT词汇

### 1. 中継（ちゅうけい）｜N1

- 词性：名詞・する動詞
- 含义：中继；在发送方和接收方之间转送信息。
- 搭配：音声を中継する / 中継サーバー
- 文章语境：LiveKit原文指出SFU中继音声和视频，这不是端到端加密。
- 例句：音声を中継するサーバーで、配送先を制限します。
- 例句含义：在中继音声的服务器上限制配送对象。
- 辨析：中継强调中间节点转送；引き継ぐ是交接职责，継承是继承。

### 2. 賄う（まかなう）｜N1

- 词性：五段動詞・他動詞
- 含义：供应、承担；以现有资源或方法满足所需。
- 搭配：費用を賄う / 一つの仕組みで賄う
- 文章语境：EKS原文用同一Flow Control机制承担饱和等待和零实例启动等待。
- 例句：起動待ちと混雑時の保留を、一つの待ち行列で賄います。
- 例句含义：用同一个等待队列处理启动等待与拥塞时的保留。
- 辨析：这里不是吃饭招待，而是满足两种处理需求。

### 3. 推測（すいそく）｜N1

- 词性：名詞・する動詞
- 含义：推测；根据有限线索推想尚未确认的事。
- 搭配：原因を推測する / 観測から推測する
- 文章语境：GPU原文对吞吐比例略高和资源争抢原因使用推测语气，并未宣称证实。
- 例句：測定値の差の理由は、まだ推測にとどまります。
- 例句含义：测量值有差异的原因目前仍只是推测。
- 辨析：予測着眼将来，推測也可针对已经发生但原因不明的事情；不是计测本身。

### 4. 裏返す（うらがえす）｜N2

- 词性：五段動詞・他動詞
- 含义：翻面、反过来；此处指把关系的方向倒转。
- 搭配：関係を裏返す / カードを裏返す
- 文章语境：Hotori把near集合反向变成每位发布者的allow集合。
- 例句：誰を聞けるかという関係を裏返し、話す側の許可を作ります。
- 例句含义：把“能听见谁”的关系反向，生成说话方的许可。
- 辨析：返す是归还或返回；裏返す在这里是关系转置，不是返回响应，也不意味着名单对称。

### 5. 見慣れる（みなれる）｜N2

- 词性：一段動詞・自動詞
- 含义：看惯、因经常看而熟悉。
- 搭配：見慣れた名前 / 見慣れない用語
- 文章语境：WALI原文先解释Web开发者可能不熟悉的系统调用、ABI等术语。
- 例句：見慣れた名前でも、型の大きさは別に確かめます。
- 例句含义：即使名称熟悉，也要另行确认类型尺寸。
- 辨析：慣らす是使人适应，手慣れる是操作熟练；見慣れる强调视觉和名称的熟悉，不等于理解契约。

### 6. 行儀（ぎょうぎ）｜N3

- 词性：名詞
- 含义：举止、行为规矩；这里比喻客户端遵守约定。
- 搭配：行儀よく振る舞う / 行儀がよい
- 文章语境：Hotori指出接收方浏览器“行儀よく振る舞う”是旧方案的隐含前提。
- 例句：クライアントの行儀のよさだけに、権限の判断を任せません。
- 例句含义：不会只依靠客户端行为守规矩来决定权限。
- 辨析：这是礼仪词的比喻，不是正式的安全机制名称，也不代表程序不可修改。

## C-2. IT/AI专业词汇

1. **KV cache（KVキャッシュ）**：保存注意力计算中间结果、供后续生成复用的缓存。 路由要同时考虑缓存位置与排队，历史推定不等于真实目录。

2. **Endpoint Picker（EPP）**：根据推理实例内部状态选择请求接收Pod的组件。 与负责实际转发的Envoy Proxy分工。

3. **NVIDIA Multi-Process Service（NVIDIA MPS）**：让多个进程共享GPU执行资源的机制。 文中ECS额度通过容器环境变量传入，不等于不可信租户隔离。

4. **Selective Forwarding Unit（SFU）**：选择并转发媒体音轨的服务器。 LiveKit通过发布者许可拒绝向未授权接收者配送。

5. **MultiRegion endpoint（マルチリージョンエンドポイント）**：把Web后端部署到多个区域的接入端点。 文章中的区域变更需新建端点再切CloudFront源站。

6. **WebAssembly Linux Interface（WALI）**：以Linux系统调用导入作为WebAssembly与宿主之间薄层的提案。 需要对应Linux运行环境，不是浏览器直接获得Linux。

7. **Application Binary Interface（ABI）**：类型大小、数据布局等二进制组件之间的约定。 WALI的32位指针和64位long与普通WASI构建物不兼容。
