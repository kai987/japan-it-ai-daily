### 1. Claude Code v2.1.286 の主要アップデート - --bare の変更とプラグインの npm ソース制限

**原文：** https://dev.classmethod.jp/articles/20261001-cc-updates-v2-1-286/

**发布时间：** 2026-10-01 19:03:20 JST

本篇是 Claude Code v2.1.286 的更新整理与小规模实测，重点在更新后行为是否符合现有脚本前提。原文按自身口径将88项变化分为45项修复、19项改善、7项新功能、7项破坏性变化、6项安全相关等；这不是独立的完整兼容性基准。--bare 现在只连接命令行明确指定的 MCP 服务，不发送 system reminders，也不启动后台任务；超时 shell 命令会停止，不能继续假设它会转到后台。

插件实验采用独立 CLAUDE_CONFIG_DIR，避免影响日常配置。同一市场定义相对路径、npm 的 file: 文件夹和 github: 仓库三种来源。claude plugin validate 校验通过，相对路径可安装，另外两种 npm 指定在 install 阶段被拒绝并返回退出码1。作者另测 git+https: 也被拒绝。错误信息还允许 npm registry 包或 tarball 链接；不能把这项限制说成所有本地来源与 Git 来源都禁止。

更新整理同时涉及 verify 技能、会话恢复、同一 tier 上一模型的一次重试，以及日志中认证信息的掩码修复。这些项目属于版本说明，不能冒充作者逐项执行的验证。尤其“插件依赖仅来自 registry”没有在此次实验验证；verify 也只是提交前执行的指示，不能因此保证测试必过。面试中的工程判断是分别测配置语法、真实安装与原有 CI 起动路径，并确认限制发生在哪一阶段。

**阅读价值：** 可说明配置校验与实际安装为何要分别验收，避免把版本升级当成无行为变化。

### 2. DevOps AgentにMCPサーバーを追加してEC2のOS調査をしてみた

**原文：** https://dev.classmethod.jp/articles/devops-agent-mcp-ec2-os-investigation/

**发布时间：** 2026-10-01 14:21:12 JST

DevOps Agent 的自主 Investigation 无法直接在 EC2 内执行任意 shell，因此未送往 CloudWatch 的进程与日志会形成观察空白。Directed Actions 虽可执行 SSM Document，却需逐次批准，不能当成自主调查中的普通取证。作者用 MCP 扩展只读调查，让 Agent 选择调查类型与实例，而不是提交任意命令。

路径为 Agent → Lambda Function URL → SSM Run Command → 固定 SSM Document → EC2。Function URL 使用 AWS_IAM，客户端以 SigV4 调用。Agent 本身不持有 SSM 权限；Lambda 的角色只能向指定 Document 发 SendCommand，不能调用 AWS-RunShellScript。七个工具分别读取 OS、资源、磁盘、网络、服务、系统日志和内核日志；action 采用 allowedValues，target 与 limit 采用 allowedPattern。READ_ONLY 分类由接入方负责，标签必须与实际命令和 IAM 约束一致。

验证在 Amazon Linux 2023 中，把两个 yes 进程改名为 report-batch 制造 CPU 饱和，且不上传 OS 内部指标。未接 MCP 时不能根据本次观测定位进程；虽有同名假设，但来自先前测试。接入后可读取进程而定位问题，Run Command 留下调用历史。随后另用获准的 Agent Action 停止进程并确认 CPU 恢复；不能说只读 MCP 自己执行了停止。

这是单一人工故障的演示，没有测出通用定位率、响应时间或所有 OS 的覆盖。Windows 扩展只是建议。面试可解释为：让模型选择受约束的观测能力，用真实结果支持结论，修改环境则分离到另外的批准过程。还需检查目标实例范围、输出敏感性和参数边界，本文并未完成组织级安全评估。

**阅读价值：** 能说明信息采集与环境修改的权限边界，以及假设和真实 OS 证据的区别。

### 3. AI に伴走してもらうチームマネジメントの試み

**原文：** https://tech.layerx.co.jp/entry/ai-empowered-team-management

**发布时间：** 2026-10-01 11:00:05 JST

文章回顾一个 Engineering Manager 用 AI 陪伴管理的半年经验。背景是开发活动量快速增长，一人更难完整观察团队与项目。前后两个半期 PR 合并数从1,982增至5,326，作者也列出人员、文件和 ADR 的变化；这些数字描述活动量，不能当作 AI 单独造成的生产率增幅。此次团队在4至9月为13至20人，人员流入与项目增加也是重要条件。

实现上使用个人应用，把资料作为 .md 保存在本机 Obsidian 专用 Vault，Claude Code 等读取这些资料；skills 和 tools 收集来源，Claude Code 或 Shepherd routines 定期执行，本地 Todo 接收1on1事项，Web viewer 辅助会话。重点是扩大可观察范围，提供 OKR、任务分配与称赞的谈话材料，原文没有把它写成自主决定绩效的系统。

边界来自不完整观察：敏感会议与对话排除在外，采集可能失败却未及时发现，未参加会议的记录也不在范围内。不定期1on1有时拖到一月，项目视野仍然粗。AI 输出只作为本人确认的假设，心理状态、负荷和评价仍由人理解与判断。作者提出改善 metrics、alerts 与自身参与，未提供改善后的定量验证。

目前资料只在作者本地；推广到组织还需访问控制和常时运行的调度基座。收益是回顾时有更具体的活动证据，限制是缺口与语境仍依赖人的介入。面试可以说明为什么采集成功、摘要质量与最终管理判断是三个不同问题，并提出采集时间及缺失状态的展示；后者是本文的设计建议，不能写成原系统已经实现。

**阅读价值：** 可区分采集自动化与人员判断，说明缺失数据如何影响管理决策。

### 4. TORCSのレースAIを122秒から106秒台へ：区間ごとの切り替え、衝突区間の特定、補正ネットワーク

**原文：** https://zenn.dev/sean_from_japan/articles/torcs-racing-ai-106s

**发布时间：** 2026-10-01 21:03:47 JST

作者回顾 TORCS 单一赛道从122秒到106秒级的调优过程。全周使用一套参数会让直线与急弯要求相冲突，因此用单圈位置切换速度规则，在末弯前更换系数、出弯恢复，最后直线全油门；只在明确区间改规则，便于单独移除后比较效果。这不是通用自动驾驶结论，春季项目的回顾也不是当天发布的新模型。

故障诊断先把66段赛道的半径、长度和累计距离列成表，再用碰撞时 distRaced 对照。碰撞集中于一组急弯，于是在2,339至2,510米使用 CMA-ES 探索并设置71.4 km/h天花板，原规则更慢时不干预，从而达到108.692秒。不是全周降速，也不是把71.4当成每时刻目标速度。区间定位说明为何特定失败不应靠全局调参掩盖。

下一层保留规则，网络只修正油门/刹车：23维输入经过32、32、1的线性层与激活函数，输出限制在0.2倍，结合上次0.7、本次0.3的平滑。输出层零初始化，从既有完走行为起步；中间层用91,329条规则动作预训练后固定，ARS只搜索输出层33参数。约6.6小时72次评价的最好一轮是106.630秒，但不是平均速度，也没有证明限制修正幅度就能保证所有环境安全。

提交时 .gitignore 排除了 .pt 权重，TORCS、比赛设置与 gym_torcs 修改在仓库外，其他电脑只能到约112秒，未逐项隔离全部原因。后来锁定容器镜像并自动应用9处修改，另一台 Apple Silicon Mac 的规则版108.538秒、残差版107.082秒，并未精确复制106.63。原文还说明源码未附许可，复用前需联系权利方。面试重点是保存模型与环境并重复评价，把最良值、单机结果与跨环境结果分开。

**阅读价值：** 可说明局部故障定位、保留已有控制的残差学习，以及重现所需权重和环境。

### 5. vCPUを減らせばVMが速くなる！？ Linux 7.4でマージが期待される“Steal Governor”

**原文：** https://gihyo.jp/article/2026/10/daily-linux-261001

**发布时间：** 2026-10-01 11:41:00 JST

Steal Governor 面向虚拟化中“已分配 vCPU 不等于实际可用计算量”的问题。持锁的 vCPU 被 hypervisor 抢占时，不仅自身失去时间，依赖锁的其他 vCPU 也可能等待。锁或线程依赖密集的 OLTP/OLAP 混合任务会遭遇这种连带损失，简单增加 vCPU 数未必解决。

机制观察本 VM 的 steal time，认为被夺走的时间过长时动态减少优先使用的 Preferred CPU 数，降低协作等待与竞争。它不是减少云账单中的规格，也不是与其他 VM 直接通信的协调协议。文章介绍起源于 IBM Power，并引用社区反馈称对 x86、s390 也有效；没有给出同一条件下的完整测量配置与改善比例，因此不能据此自行补出速度提升百分数。

作者引用开发者指出，全部 VM 协作部署时效果最好，显式加载模块是有意部署的条件。但纯 CPU 消耗型任务可能出现轻微回归。文章将其与 cache-aware scheduling 对比，说明调度应考虑缓存与虚拟化状态；这不是两种机制优劣的实测排名。

发布状态是9月28日进入 tip tree 队列，预期向 Linux 7.4 合并窗口提交；不应写成 Linux 7.4 已提供且默认启用。用于日本企业的采用判断，可设计不同锁依赖负载下的等待、steal time 与吞吐比较，再确认实际 kernel、hypervisor 和模块支持。本段是评价建议，文章未执行该企业环境实验。面试价值是用因果链解释资源规格与实际进展的区别。

**阅读价值：** 可区分分配 CPU 数与有效性能，解释锁依赖导致的连带损失。

## 4. 今日技术主题｜动作边界与真实结果

今天的主题是“限制自动化的可选动作，观察真实输出”。Claude 插件配置通过检查不代表安装可行；MCP 调查只让 Agent 选择固定 Document 的调查类型；赛车网络也只在既有控制上加小幅油门补正，转向保留规则。三者都应说明动作范围，并分别保存校验、执行或控制输出。这是本文基于原文的工程整理，不是原作者共同实现的框架。

选择越受约束，也不意味着所有情形下更好。团队采集仍有敏感会话与失败缺口；CPU 调度减少可并行数可能改善锁等待，也可能伤害独立 CPU 负载。企业采用时，应说明何种前提支持结论，按业务条件设计试验并保留反例。PR增长、单次最快圈速与作者定性体验是不同证据，不能组合成通用生产率或安全保证。收益是判断更可解释，成本是记录、环境固定与持续核验。

## C-2. IT/AI 专业词汇

## C-3. 新学语法

### 1. ～以上（は）｜N2

- 含义：既然具有这一前提，就应承担相应义务。
- 结构：普通形＋以上（は）／名詞・な形容詞＋である以上（は）
- 用法：前提后接责任或判断，不是数量超过。
- 原文形态：実行する以上
- 原文依据：[OS上でコマンドを実行する以上](https://dev.classmethod.jp/articles/devops-agent-mcp-ec2-os-investigation/)
- 独立例句：OS上で処理する以上、実行権限を限定します。
- 例句译文：既然在 OS 上处理，就限制执行权限。
- 注意：独立教学例句；不把任意只读标签当作安全证明。
